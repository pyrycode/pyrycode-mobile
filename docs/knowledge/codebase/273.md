# #273 — Mobile Protocol v2 wire models + envelope codec

The **root of the Phase 4 wire layer**: typed, serializable Kotlin models for the exact byte contract the pyrycode v2 server already speaks, plus a thin codec (one configured `Json`, base64-std helpers, a 32-byte pubkey decoder). Greenfield — **no consumers yet**; it ships the wire types with their own round-trip tests so [#275](https://github.com/pyrycode/pyrycode-mobile/issues/275) (Noise session), [#276](https://github.com/pyrycode/pyrycode-mobile/issues/276) (relay WS client), and [#277](https://github.com/pyrycode/pyrycode-mobile/issues/277) (QR scan + fingerprint) encode/decode against bytes the 2026-05-29 Noise spike already proved end-to-end against the live `wss://pyrycode-relay.pyryco.de`. Reuses #272's serialization substrate — **no new dependency**. `security-sensitive` ticket (the contract carries the device-pairing token + server static pubkey).

See the feature doc [`mobile-protocol-v2-wire-layer.md`](../features/mobile-protocol-v2-wire-layer.md) for the evergreen "how the wire layer works / how consumers use it" reference; this file is the implementation record.

## Summary

Five `@Serializable` models + a top-level codec, all under the `data/network/` namespace #272 seeded, verified by one JUnit4 test file (13 `@Test` methods). The models are the camelCase analog of the server's snake_case wire shapes; `@SerialName` carries the mapping — **that mapping is the Go-interop contract, not cosmetic**. The codec is deliberately *not* wrapped in an object/class: the wire layer's exported surface is the five models, and `MobileJson` + the two base64 helpers + `decodeServerStaticPubkey` are top-level (no per-model encode/decode wrappers — those would only inflate the surface the ticket asked to keep minimal).

The single load-bearing subtlety is the `MobileJson` configuration — a default `Json` would silently break the wire contract two ways (see Lessons).

## Files touched

All three **NEW**, under `app/src/main/java/de/pyryco/mobile/data/network/` (+ test mirror):

- **`MobileWireModels.kt`** (93 lines) — the five models:
  - `InnerFrameV2` (`:22-27`) — `{ v=2, type, data }`, the bare WS text payload. `data` is the base64-std string; `v` defaults to `2` and **must be emitted**.
  - `Envelope` (`:37-44`) — `{ id: Long, type, ts: String, payload, in_reply_to? }`. `payload` is a generic `JsonElement` carrier (the `json.RawMessage` analog, `:42`); `inReplyTo: Long? = null` maps to `in_reply_to` and is **omitted when null** (`:43`). `ts` stays a `String` (RFC3339, not parsed to a typed instant this ticket — AC).
  - `HelloClientPayload` (`:54-65`) — `hello` payload (in `noise_init` early-data); `role="client"` + `protocol_versions=["v2"]` defaults. **`toString()` redacts `token` to `***`** (`:62-64`).
  - `HelloAckPayload` (`:68-73`) — `hello_ack` payload (in `noise_resp` early-data); server-supplied, decoded only.
  - `QrPayload` (`:84-92`) — decoded pairing payload; `serverStaticPubkey` is the base64-std raw 32-byte X25519 key as a string. **`toString()` redacts `token`** (`:91`).
- **`MobileWireCodec.kt`** (61 lines):
  - `MobileJson` (`:29-34`) — the single configured `Json`: `encodeDefaults = true`, `explicitNulls = false`, `ignoreUnknownKeys = true`. Immutable, thread-safe.
  - `base64StdEncode` / `base64StdDecode` (`:37`, `:40`) — `java.util.Base64` getEncoder/getDecoder, the exact JVM analog of Go's `base64.StdEncoding` (standard alphabet, with padding).
  - `decodeServerStaticPubkey(qr)` (`:50-61`) — base64-std-decodes then `require(size == 32)`; throws `IllegalArgumentException` with a field-named, no-echo message on bad base64 **or** length ≠ 32. Never silently truncates (AC #4).
- **`MobileWireCodecTest.kt`** (test, 214 lines) — JUnit4 mirroring `NoiseSuiteSmokeTest.kt` (`org.junit.Test`, `org.junit.Assert.*`). Per-model decode-the-fixture + encode-then-decode; `encodeDefaults`/`explicitNulls` guards; base64 pinned against `//8=` and `/w==` (proves standard alphabet + padding, `!= "__8"`); 31/33-byte + invalid-base64 rejection; and the redaction test asserting `toString()` hides the token while `encodeToString` still emits it.

**No build edits** — `kotlinx-serialization-json` 1.8.1 + the `kotlin-serialization` plugin came from #272 and were already smoke-tested as wired (`NoiseSuiteSmokeTest.serializationPluginIsWired`).

## Patterns established

- **The configured `Json` IS the codec; no per-model wrappers.** Consumers call `MobileJson.encodeToString(value)` / `MobileJson.decodeFromString<T>(text)` directly. The "encode/decode helpers" an AC asks for = the configured singleton + the base64 helpers, not a zoo of `encodeInnerFrame`/`decodeEnvelope` functions. This is the wire-layer's minimal-surface convention — future wire additions stay top-level under `data/network/`.
- **Generic `JsonElement` payload carrier, polymorphic-by-`type`, instead of a sealed payload hierarchy.** `Envelope.payload` stays untrusted raw JSON until a consumer bridges it: `MobileJson.decodeFromJsonElement<HelloAckPayload>(envelope.payload)` on decode, `MobileJson.encodeToJsonElement(HelloClientPayload(...))` on encode. This ticket ships only the two Hello payloads as typed models; **consumer tickets add their own application payloads (`send_message`, `conversations`, …) — do not pre-model a type-zoo for types no one decodes yet.**
- **Redacting `toString()` is the deterministic safety net for secret-carrying data classes.** A `data class`'s auto-`toString()` renders every field, so a stray `Log.d("hello: $payload")` would leak the pairing token to Logcat. Both token-carrying models override `toString()` to print `token=***`. The two invariants: (1) **do not** override `equals`/`hashCode` (round-trip tests assert structural equality via the generated `equals`); (2) redaction touches `toString()` only — kotlinx-serialization encodes from the `@Serializable` descriptor, so the wire still carries the real token. Belt-and-suspenders done right: a deterministic override backing the stochastic "remember not to log it," with a regression test pinning both halves. Reuse this shape for any future secret-bearing wire model.
- **`java.util.Base64`, not `kotlin.io.encoding.Base64`, for std-base64 in the data layer.** 1:1 byte-correspondence with Go's `base64.StdEncoding`, zero opt-in (avoids the `@ExperimentalEncodingApi` annotation), available in plain JVM unit tests (no Robolectric) and on min SDK 33 (`java.util.Base64` is API 26+). This is the one JVM-only seam in an otherwise-portable data layer — a contained `expect/actual` *if/when* the Compose-Multiplatform walk-back lands (the models themselves stay fully portable). Conscious, documented trade-off; see the feature doc's "CMP seam" note.
- **Base64 vectors are pinned literals, asserted independent of the impl.** `//8=` / `/w==` are written out, never computed from `base64StdEncode` at test time — otherwise the test would tautologically pass against a url-safe/unpadded impl.

## Lessons learned

Lifted from the PR's *Lessons learned* section, plus one from the build:

- **`MobileJson`'s configuration is load-bearing, not cosmetic — a default `Json` silently breaks the wire two ways.** `encodeDefaults = true` is required so `v:2` / `role:"client"` / `protocol_versions:["v2"]` actually reach the wire (default `Json` omits fields equal to their Kotlin default → a server-breaking `{"type":...,"data":...}` with no `v`). `explicitNulls = false` is what omits `in_reply_to` when absent (default `Json` would emit `"in_reply_to":null`, AC #5). Both are guarded by deterministic tests (`defaults_areEmittedOnEncode` asserts `"v":2` present; `inReplyTo_isOmittedWhenNull` asserts the key is absent) — the failure mode is invisible at compile time, so the guard tests are the oracle. **Any new wire type added under `data/network/` must serialize via `MobileJson`, never a fresh `Json {}`.**
- **`payload_encrypted` is dropped on decode today.** The Go envelope carries an optional `payload_encrypted` (omitempty) for the encrypted-application-payload path; `ignoreUnknownKeys = true` drops it silently rather than throwing. It is **not modeled here** (encryption is #275). **#275 must add it as a typed field** rather than assume it round-trips today — flagged so the gap is intentional, not forgotten.
- **A file-level overview KDoc directly preceding a declaration's KDoc trips ktlint `standard:no-consecutive-comments`** (`spotlessCheck` failure). The shipped fix (commit `66d7993`) folds each file-level overview KDoc into the *first declaration's* KDoc so no KDoc is immediately preceded by another KDoc. Cost a follow-up style commit after the feature commit; future new files that want a file banner + a first-decl doc should write them as **one** KDoc block on the first declaration from the start.
