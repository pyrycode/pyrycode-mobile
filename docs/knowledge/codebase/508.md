# #508 — Hide unavailable conversation actions (overflow menu + Channel Info sheet)

**Issue:** [#508](https://github.com/pyrycode/pyrycode-mobile/issues/508) ·
**Spec:** [`docs/specs/architecture/508-hide-unavailable-conversation-actions.md`](../../specs/architecture/508-hide-unavailable-conversation-actions.md) ·
**PR:** [#513](https://github.com/pyrycode/pyrycode-mobile/pull/513) ·
Size **S**, not `security-sensitive`.

## Summary

Consumer half of #491's 4+4 split (the foundation half is [#507](507.md)). In relay mode the conversation
mutations are unimplemented (`archive` / `unarchive` / `rename` / `startNewSession` / `changeWorkspace` throw
`UnsupportedOperationException` on [`RemoteConversationRepository`](../features/remote-conversation-repository.md);
`delete` inherits the throwing interface default), so this ticket **hides** the affordances that would reach
them on the two surfaces that present them:

- **Thread overflow menu** ([`ThreadOverflowMenu`](../features/thread-overflow-menu.md)) — New session / Rename /
  Change workspace / Archive are gated out.
- **Channel Info sheet** ([`ChannelInfoSheet`](../features/channel-info-sheet.md)) — the entire **Actions**
  section (Rename / Change workspace / Archive / Delete) is gated out; the sheet stays viewable as read-only info.

Both gate on the single `ThreadUiState.mutationsSupported` signal #507 introduced, and on **nothing else** — no
`USE_RELAY_REPOSITORY` / instance-type / relay-vs-fake check inside the composables. Purely additive threading of
one already-existing `Boolean`: no new types, no ViewModel change, no string resources. In fake mode (the
default) `mutationsSupported` is `true`, so every action stays present and nothing changes. Complement of the
deterministic call-site guard [#490](490.md) — hide-the-affordance (product) + guard-the-call (safety net), a
belt-and-suspenders pair of different fabric that together unblock flipping `USE_RELAY_REPOSITORY`.

## Patterns established

- **A capability gate is a param, defaulted `= true`, placed after `modifier`.** Every gated composable
  (`ThreadOverflowMenu`, `ThreadTopAppBar`, `ChannelInfoSheet`, `ChannelInfoSheetContent`) takes
  `mutationsSupported: Boolean = true`. The default is a **preview/test ergonomic seam only** — it mirrors
  `ThreadUiState.mutationsSupported = true` and keeps the 10 existing `ThreadOverflowMenu(...)` test call sites and
  the 2 `ChannelInfoSheetContent` previews compiling **untouched** (avoids a ~12-site fan-out cascade). It does
  **not** weaken the fail-safe-deny: every production path threads the VM-captured value (`repository.mutationsSupported`
  through the [`StableConversationRepository`](../features/stable-conversation-repository.md) facade, which returns
  `false` while no connection is live), so the default is never what reaches the UI in relay mode. **Do not
  "harden" these to required params** — that cascade buys no correctness. Contrast `isPromoted`, which stays
  **required** (the host always knows promotion) — only capability gates get the defaulted-seam treatment.
- **Hide the whole section, not disable the cells.** AC#5 resolves the treatment as **hide** on both surfaces
  (this ticket builds both together, so the cross-surface consistency decision lives here). In the sheet, all four
  Actions cells are unsupported at once, so hiding `SectionHeader("Actions")` + `ActionsGrid` together reads
  cleaner than a lone header floating over four inert cells. In the dropdown, hiding four contiguous items reads
  cleaner than greyed-out rows.
- **Gate on the client capability signal, never on the mode.** Both surfaces read `state.mutationsSupported` and
  nothing else (AC#4). No composable imports `USE_RELAY_REPOSITORY`, checks the repository instance type, or
  branches on relay-vs-fake — the single signal from #507 is the one seam, which is why #491 was split into a
  foundation ticket (expose the capability) + this consumer (read it on both surfaces).

## Lessons learned

- **A new defaulted `@Composable` param placed *before* `modifier` is an Android Lint `ComposeParameterOrder`
  error** (it compiles fine and passes `test`; it fails `./gradlew lint`, and `spotlessApply` will **not** fix it).
  The spec's suggested signature put `mutationsSupported` before the trailing lambdas / `modifier`; that tripped
  the lint on `ThreadOverflowMenu` and `ThreadTopAppBar` (3 errors). Fix: order params **required → `modifier` →
  defaulted `mutationsSupported`**. A composable with **no** `modifier` param — `ChannelInfoSheetContent` — is
  exempt: a trailing defaulted param is fine there. (`ChannelInfoSheet` places `mutationsSupported` after
  `modifier` but before the also-defaulted `sheetState`, which is allowed — the rule is "defaulted after
  `modifier`," not "defaulted last.") See [[compose-parameter-order-lint-defaulted-after-modifier]].
- **`New session` never reproduces a live throw.** `ThreadViewModel.onOverflowEvent` maps `ThreadEvent.NewSession
  -> Unit` — it never calls `startNewSession`, so today it is a no-op, not a throw. It is still an
  impossible/misleading action in relay mode (and would surface the throw once wired), so it is gated with the
  other three; just don't expect a crash to reproduce against it.

## Testing

`./gradlew spotlessApply compileDebugAndroidTestKotlin test lint assembleDebug` — all green (lint clean after the
param-order fix). The two new cases are instrumented (`androidTest`), **compiled** via
`compileDebugAndroidTestKotlin` but **not executed** — no emulator/device was connected, so `connectedAndroidTest`
did not run (see [[androidtest-not-compiled-by-mandatory-gates]]: the mandatory `test` / `lint` / `assembleDebug`
gates never compile `androidTest`, hence the explicit `compileDebugAndroidTestKotlin` step).

- **`ThreadOverflowMenuTest.mutation_actions_are_hidden_when_mutations_unsupported`** (component-level, drives
  `ThreadOverflowMenu` directly with `mutationsSupported = false, isPromoted = true`) — asserts New session /
  Rename / Change workspace / Archive each `assertDoesNotExist()`, and Show literal screen / Channel info /
  Install memory plugin each `assertIsDisplayed()` (they survive the gate). The two pre-existing render-order
  tests exercise the defaulted `mutationsSupported = true` path unchanged — no edit.
- **`ThreadScreenChannelInfoTest.actions_section_is_hidden_when_mutations_unsupported`** (screen-level, drives
  `ThreadScreen` with `channelInfoOpen = true` and `channelInfoState().copy(mutationsSupported = false)`) — asserts
  `"Actions"` / `"Rename"` / `"Change workspace"` / `"Archive"` / `"Delete"` each `assertDoesNotExist()`, and
  `"About"` + the workspace path `assertIsDisplayed()` (read-only info remains). The sheet cell labels are literal
  strings in `ChannelInfoSheet.kt` and the overflow menu is closed in this test, so those texts appear only in the
  sheet — no false match from the menu.
