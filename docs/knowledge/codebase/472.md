# #472 — Layer 1b: tool-step rows (running → done, and failed) on the scripted-stream harness

Adds the **component-level** tool-step coverage of the mobile interactive-stream e2e ladder
(`docs/e2e-interactive-stream.md`, **rung 2 / Layer 1b**): a scripted `tool_use` / `tool_result`
sequence driven through the **real `RemoteConversationRepository` correlation fold (#387)** →
`ThreadViewModel` → `ThreadScreen`, asserting the shipped tool-row states (#388) render
**running → done** and **failed**. It rides the already-shipped **#432 `ScriptedThreadHarness`**; the
only change is two scripting methods + two private envelope builders **inside the harness file** plus
one new test file — all `androidTest`. **Zero production Kotlin.**

This is the Layer-1 component twin of **#455** (Layer 2c, the emulator-level tool-step scenarios,
already shipped over a real emulator + Noise/relay + `fakeclaude`). The two exercise the same render
path; the only difference is the running→done fence, which is **simpler here** (see Lessons learned).
First of the three children #435 was split into 2026-06-23: **#472 (this, tool rows)**, #473 (session
divider, `blockedBy` the unshipped #336 fold), #474 (connection banner, `blockedBy` #472).

The faithful production path the test reproduces (identical to #432's, with the tool fold arm
exercised):

```
scripted tool_use/tool_result Envelope
  → FakeSessionPump.inbound → RemoteConversationRepository
      (decode #385 + correlation fold #387 → messagesByConversation → observeMessages)
  → ThreadViewModel (state = combine(…, threadItems, …))
  → ThreadScreen → MessageBubble routes Role.Tool → ToolCallRow → rendered status icon + name
```

## Patterns established

- **The imperative-push fence replaces #455's two-drop dance for the running→done transient.** AC #4
  requires **running** be asserted while the turn is in flight, with no false-green from a race straight
  to the terminal result. On the emulator (#455) the only injection was `send_message`, so it needed a
  two-drop causal fence keyed on the 2nd `send_message.enqueued`. Here the harness pushes envelopes
  imperatively from the test thread, so the fence is just **sequencing**: `pushToolUse` opens a `Running`
  row that **persists** (it flips only on a correlated `tool_result`) → `waitUntil` running present →
  assert in-flight → **only then** `pushToolResult` flips it to `Done`. The `waitUntil` between the two
  pushes guarantees the running window was observed; no timing dependency, no `send_message` indirection.
  This is the spinner test's present→absent shape (`ScriptedThreadRenderTest`: `pushTurnState("thinking")`
  → assert present → `pushTurnEnd` → assert absent) applied to `pushToolUse` / `pushToolResult`.
- **Done has no positive content-description → the absence triad.** `ToolCallStatus.Done`'s icon carries
  `contentDescription = null` (`ToolCallRow.kt:151`), so "resolved to done" is asserted tolerantly as the
  triad #455 introduced: the **running** CD that was present is now **absent**, the **failed** CD
  `assertDoesNotExist()`, and the **verbatim tool name** is still displayed (the row resolved in place,
  did not vanish). Uniquely identifies a `Running → Done` resolution without keying on timing. The
  rejected alternative — adding a test tag or a positive "done" CD to the production component — would be
  an out-of-scope production change.
- **Cross-push correlation is load-bearing.** `applyToolResult` drops a `tool_result` with no prior
  matching `tool_use` (keyed by `tool_use_id`), so the use's `toolUseId` MUST equal the result's — same
  literal in both calls. A mismatch fails **loud** (the row never resolves → `waitUntil` timeout), never
  silent. Distinct ids across the two tests (`tu1` / `tuf`) keep the scripts independently readable;
  per-test isolation is already guaranteed by the fresh `@Before` harness.
- **Assertions key only on status CDs + the verbatim tool name — never the summaries.** `name` passes
  through verbatim, but `input_summary` / `result_summary` are server-derived (may be summarized), so
  the tests deliberately do not assert on them — only `cd_tool_running` / `cd_tool_failed` and `"Bash"`,
  per the ladder doc's tolerant-assert rule.
- **New test file, not extending `ScriptedThreadRenderTest`.** A dedicated `ScriptedToolRowTest.kt`
  keeps the tool-row scenarios cohesive and **decouples this ticket's diff from sibling #474** (banner),
  which rides the same harness next and would otherwise collide in `ScriptedThreadRenderTest.kt`. The
  harness file is the one unavoidable shared edit point, and the #472→#474 blocking chain serializes
  those edits. (The spec's open question #2 left extending `ScriptedThreadRenderTest` as acceptable; the
  lower-merge-surface choice was taken and flagged in the PR body.)

## Lessons learned

- **The component-level running→done fence is just push sequencing — no two-drop machinery.** The
  emulator twin (#455) needed two fixture drops fired on successive `send_message.enqueued` because it
  could only inject indirectly; the in-process harness pushes from the test thread, so withholding the
  `tool_result` until after the running assertion passes **is** the fence. When a harness can inject
  imperatively, prefer sequencing over the indirect causal-fence dance.
- **`tool_use` must precede `tool_result`, and the `tool_use_id` must match.** The #387 fold is
  use-before-result and id-correlated; a stray or mismatched result is silently dropped, so the row
  would hang and the test would time out. (Mirrors #455's cross-drop correlation, here as cross-push.)
- **Tool rows are robust to the subscribe-before-push race that bit the spinner.** Unlike
  `turn_state`/`isThinking` (which flow through the `replay = 0` `liveSessionEvents` SharedFlow and are
  *dropped* if pushed before the VM subscribes — the #432 spinner flake), the tool fold writes into
  `messagesByConversation`, a `MutableStateFlow` projection that retains and re-emits to late
  subscribers; `FakeSessionPump`'s inbound `Channel` is `UNLIMITED` (a pre-subscription push is buffered,
  not dropped). So a tool row survives a push at any time after construction. All `push*` calls still go
  **after** `start()` (which runs `awaitReady()`), matching the existing cases — `awaitReady` proves the
  screen composed and the conversation seeded, so the thread is rendering (not loading/empty) before the
  first assertion. No new readiness gate needed. See [[two-folds-repo-wins-vm-dormant]].

## Verification

The deliverable **is** the tests; there is no unit test of the harness. Host-JVM checks (no device, per
the spec's strategy):

- `./gradlew compileDebugAndroidTestKotlin spotlessCheck test lint assembleDebug` all green — the
  androidTest sources compile (the mandatory gates do **not** compile androidTest, so the
  `compileDebugAndroidTestKotlin` run is explicit — [[androidtest-not-compiled-by-mandatory-gates]]).
  `onAllNodesWithContentDescription` / `onNodeWithContentDescription` / `onNodeWithText` /
  `assertDoesNotExist` / `assertIsDisplayed` are members/imports already covered by the
  `ScriptedThreadRenderTest` template; the new `.kt` filename matches its sole public class.
- **`connectedAndroidTest` NOT run** — no device/emulator attached; both cases are instrumented
  `createComposeRule` (the `ScriptedThreadRenderTest` precedent), so the actual on-device render run is
  operator-run, alongside `ScriptedThreadRenderTest` / `ThinkingIndicatorTest`.
