# #397 — green "up" status token + two-part `ConnectionStatusLine` component

The **build slice** (slice A) of the two-part `● Relay   ● Pyrycode` connection-status line: a
reusable, tested, previewable component plus the one new theme colour it needs — a green "up"
`success` token. It renders the combined [`ConnectionStatus`](../features/connection-status.md)
`{relay, pyrycode}` model ([#392](392.md)) but does **not** wire the live data path or touch the
Settings screen — that is the sibling wiring slice **#398** (`blockedBy #397`).

The motivating bug: the app had **no positive connection indicator** — `Connected` was conveyed only
by the *absence* of the [`ConnectionBanner`](../features/connection-banner.md), so a user couldn't
glance and confirm "I'm connected." Live phone↔daemon testing on **2026-06-08** surfaced a
daemon-not-on-relay case (the daemon 4404-looping behind a base relay URL) that presented only as a
generic "Offline" with no hint of *which* leg was broken. The path is **phone → relay → pyrycode
daemon** — two legs that fail independently — so a two-part line makes both glanceable, and the
daemon-absent case reads as "Relay = up, Pyrycode = down" instead of an opaque "Offline."

Split from #390 (slice A — component + token; slice B = #398 wiring). `## Figma` N/A: a new
live-testing diagnostic conceived after the design lock; the line lands under the server row in
Settings frame `17-2` when the design is drawn (**design-owed**, same resolution as
[#343](343.md)). The green shades and micro-spacing are placeholders the design will pin later — the
**behaviour** (which leg → which colour-category + label) is the load-bearing part.

## Summary

Four production files: three are the irreducible theme-token plumbing the AC mandates (palette
literal → holder → provider, mirroring the `WarningColors` precedent one-for-one), the fourth
co-locates the small presentation mapper with its sole consumer, the component. One unit-test file.
The pure mapper (`RelayLinkStatus`/`PyrycodeLinkStatus → (category, label, contentDescription)`) is
the unit-tested core; the component, the category→token colour resolver, and the previews are
preview-verified, matching the `ConnectionBanner` idiom (which carries no unit test either).

The green token is a **new `SuccessColors` sibling**, not an additive field on `WarningColors` —
extending `WarningColors` to carry an unrelated green value would leave a holder named
`WarningColors` owning `colorScheme.success`, semantically muddled; a sibling keeps
`import …theme.warning` / `import …theme.success` cleanly separate and mirrors the precedent exactly.

## Files touched

Production — 2 new files, 2 modifications:

- **`ui/theme/SuccessColors.kt`** (new, `+24`) — a line-for-line analog of `WarningColors.kt`:
  `@Immutable data class SuccessColors(val success: Color)`, an `internal val LocalSuccessColors:
  ProvidableCompositionLocal<SuccessColors>` via `staticCompositionLocalOf { error("SuccessColors
  not provided. Wrap content in PyrycodeMobileTheme.") }` (fail-fast on missing provider, never a
  silent `Color.Unspecified`), and a `val ColorScheme.success: Color @Composable @ReadOnlyComposable
  get() = LocalSuccessColors.current.success` extension so call sites read
  `MaterialTheme.colorScheme.success` — same surface as a real M3 slot. Its own file per the ktlint
  single-public-class rule.
- **`ui/theme/Color.kt`** (`+2`) — two palette literals beside the `warning*` ones:
  `successLight = Color(0xFF316B2B)` (medium-dark green, ≈green tone 40, contrast on `surfaceLight`
  `#F8F9FF`) and `successDark = Color(0xFFA6D388)` (light green, ≈green tone 80, contrast on
  `surfaceDark` `#101418`). **Placeholders** (design-owed) — isolated here so a later design
  reconciliation is a two-literal edit. No medium/high-contrast variants (the theme only selects
  light/dark for `WarningColors`).
- **`ui/theme/Theme.kt`** (`+8/-1`) — three additive touches mirroring `WarningColors`:
  `private val lightSuccessColors = SuccessColors(successLight)` / `darkSuccessColors` beside the
  warning instances (`:249-250`); a `val successColors = if (darkTheme) darkSuccessColors else
  lightSuccessColors` selected after the existing `when` (`:297`) — chosen over folding `success`
  into the `when`'s destructured tuple, since it keys on the same `darkTheme`; and
  `LocalSuccessColors provides successColors` added to the existing `CompositionLocalProvider`
  (vararg) alongside `LocalWarningColors` (`:300-303`). `PyrycodeMobileTheme`'s signature is
  **unchanged**.
- **`ui/conversations/components/ConnectionStatusLine.kt`** (new, `+190`) — one file holding the
  pure mapper, its value types, the category→colour resolver, the component, and the previews:
  - **`internal enum class ConnectionLegCategory { Up, InProgress, Down }`** — the load-bearing
    colour category, kept separate from the concrete M3 token so the mapping stays pure
    (JVM-unit-testable, **no Compose import** on the mapper).
  - **`internal data class ConnectionLegVisual(category, label, contentDescription)`** — the full
    presentation triple for one leg: category + visible state word + leg+state phrase for TalkBack.
  - **`internal fun RelayLinkStatus.toLegVisual()`** + **`internal fun
    PyrycodeLinkStatus.toLegVisual()`** — the pure mappers, **exhaustive `when` with no `else`** (a
    future link-status case becomes a compile error — the desired failure mode). `DaemonAbsent →
    (Up, "Reachable", "Relay: reachable, no daemon")` is **AC#2**: the relay is up; the missing
    daemon is the pyrycode leg's story. The distinct `"Reachable"` label (vs `"Connected"`) keeps the
    text/a11y channel honest while staying green. `Reconnecting(secondsRemaining)` maps to
    `InProgress` with a plain `"Reconnecting"` label — the optional countdown was **not** adopted
    (design-owed placement).
  - **`@Composable @ReadOnlyComposable internal fun ConnectionLegCategory.color(): Color`** — the
    **only** colour-resolution site (AC#3): `Up → colorScheme.success`, `InProgress → .warning`,
    `Down → .error`. No hardcoded hex anywhere in the component.
  - **`fun ConnectionStatusLine(status: ConnectionStatus, modifier: Modifier = Modifier)`** — the
    stateless public surface: a `Row` (`spacedBy(24.dp)`, `CenterVertically`) of two private
    `StatusLeg`s ("Relay" / "Pyrycode"). Each `StatusLeg` is a `Row` of **[8.dp dot] [name] [state
    label]** where the dot is `Box(size(8.dp).background(visual.category.color(), CircleShape))` and
    name (`labelMedium`/`onSurface`) + label (`labelSmall`/`onSurfaceVariant`) make status legible
    **without colour perception** (AC#5). The leg `Row` carries
    `clearAndSetSemantics { contentDescription = visual.contentDescription }` so TalkBack announces
    one clean phrase per leg ("Relay: connected") instead of fragmented child texts.
  - **Previews** — a private `ConnectionStatusLinePreviewMatrix` rendering the four AC-required
    combinations (both up; **`DaemonAbsent` + `Down`** = the motivating green-relay/red-pyrycode
    diagnostic; both down; `Reconnecting(12)` + `Handshaking`), wrapped by Light + Dark `@Preview`
    pair at `widthDp = 412` in `PyrycodeMobileTheme(darkTheme = false/true)` — the
    `ConnectionBanner` preview idiom.

Tests — 1 new file:

## Patterns established

- **A second instance of the custom-colour-slot pattern — by sibling holder, not by widening the
  existing one.** [`warning-color.md`](../features/warning-color.md) anticipated "future ones (e.g.
  brand-specific `success`, `info`)"; this is the first realization. The rule it sets: each custom
  semantic slot gets its **own** `XxxColors` holder + `LocalXxxColors` + `ColorScheme.xxx`
  extension + per-mode literals, threaded through the same three `Theme.kt` sites. Don't pile
  unrelated colours into one holder — one holder per semantic concept keeps
  `import …theme.<token>` honest and `colorScheme.<token>` reads self-documenting. See
  [`success-color.md`](../features/success-color.md).
- **Split the colour *category* (pure, testable) from the colour *token* (Compose-resolved).** The
  mapper returns a `ConnectionLegCategory` enum, never a `Color`; a separate
  `@Composable ConnectionLegCategory.color()` resolves the M3 token. This keeps the product
  behaviour (which state → which category + label + a11y text) in a plain JVM unit test, with no
  Compose/Robolectric harness, while the trivial category→token step is preview-verified. Mirrors
  [`ThreadStatusRow`](../features/thread-status-row.md)'s `tokenPercentColor`. The reusable shape:
  **map state → semantic category in pure code, resolve category → token at the one Compose site.**
- **Exhaustive `when` with no `else` over a consumed sealed hierarchy is the total-mapping guard.**
  Both `toLegVisual()` mappers are total over their sealed input with no `else`, so adding a future
  `RelayLinkStatus`/`PyrycodeLinkStatus` case is a **compile error** that forces a mapping decision —
  the desired failure mode for a presentation layer that must cover every state.

## Lessons learned

- **Only the light/dark `WarningColors` instances are actually selected in `PyrycodeMobileTheme` —
  the medium/high-contrast holders are defined-but-dead** (the theme `when` keys only on
  `darkTheme`/dynamic, never an accessibility-contrast level). `SuccessColors` deliberately matches
  that scope (two instances, light + dark) rather than introducing four unused contrast variants.
  Whichever future ticket routes the accessibility-contrast level through `PyrycodeMobileTheme` is
  the one to add `success` (and the already-dead `warning`) contrast variants — not this slice.
  (Lifted verbatim from the PR's *Lessons learned*.)
- **The hex literals belong in `Color.kt`, never the component.** AC#3 ("no hardcoded hex") is
  satisfied structurally: every dot colour resolves through `category.color()` →
  `colorScheme.success/warning/error`, and the only hex in the diff is the two palette `val`s in
  `Color.kt` — exactly where `warningLight`/`warningDark` live. A green literal in the component
  would have passed the eye test but failed the token contract.

  [#399](https://github.com/pyrycode/pyrycode-mobile/pull/399)). 8 unit tests map 1:1 onto the
  sealed cases. No instrumented test — the component is preview-verified, matching `ConnectionBanner`
  (no device connected; `connectedAndroidTest` N/A for a pure-presentation slice).
- **Code review: PASS** ([PR #399](https://github.com/pyrycode/pyrycode-mobile/pull/399)) — **zero
  blocking findings**; one optional NIT (rename `color()` → `tokenColor()` for call-site clarity,
  left as-is to match the spec verbatim). The reviewer verified all eight ACs, that recomposition is
  clean (`ConnectionStatus` + both sealed hierarchies incl. `Reconnecting(Int)` are stable → the
  component is **skippable**, no captured/unstable lambdas), the additive blast radius
  (`PyrycodeMobileTheme` signature unchanged, no pre-existing `success` symbol to clash with,
  `ConnectionStatusLine` referenced nowhere else — confirming the build-only slice), and the token
  contract (hex confined to `Color.kt`).
- **Not `security-sensitive`**; Design source N/A (design-owed, [#343](343.md) resolution) — the
  security-goggles and visual-fidelity passes were correctly skipped. The green shades are
  acknowledged placeholders isolated in `Color.kt`.
