## Summary

Adds `interactiveTurn_changeWorkspace_relabelsChipToNewWorkspace` to `InteractiveStreamE2ETest` — the
operator-facing change-workspace happy path #533's Definition-of-done note asked PO to file separately.
Creates a plain discussion, drives the **real** thread overflow "Change workspace…" → Workspace Picker →
"Create new folder…" → a runtime-unique target name, completes a `change_workspace` round-trip, and asserts
the conversation's recorded workspace durably re-labels the `WorkspaceChip` to it — a genuine
absence-before → presence-after inversion on the same surface. Zero production code: one new always-on
`@Test` + two companion constants, one `scripts/e2e-emulator.sh` LIVE-curation edit (quintet → sextet, still
3 turns), and the ladder doc — all landed in this single PR.

This ticket had previously been parked in Inbox on a catch-22: the `WorkspaceChip` is
`!isPromoted && !hasMessages`-gated (any turn hides it), and the overflow "Change workspace…" item was
`mutationsSupported`-gated (hidden against the live relay) — see [#561](561.md)'s own note that "e2e sibling
#562 remains parked ... pending the family-wide per-mutation gate." PR #572 flipped
`RemoteConversationRepository.mutationsSupported` to `true` in relay mode, clearing the gate for the whole
family (#537/#541/#545/#551/#562/#566); this ticket re-verified #562 specifically as buildable — the chip
gate turned out not to matter because the scenario never sends a message, so `hasMessages` stays false and
the chip stays mounted throughout.

`change_workspace` is **conversation-scoped** (`{conversation_id, cwd}`, a line-for-line mirror of `rename`,
**no** session transition), so — unlike the session-scoped settings e2e (#545, blocked on
`currentSessionId == ""`) — it carries no session dependency and sits in the same clean-buildable camp as
the already-shipped conversation-scoped e2e's (#541/#554/#551).

## Files touched

- **`app/src/androidTest/java/de/pyryco/mobile/e2e/InteractiveStreamE2ETest.kt`** (+119, one new `@Test`,
  a 6-step scenario):
  1. Wait for the channel-list FAB (`CD_NEW_DISCUSSION`), `awaitConnected()`.
  2. Create a plain discussion; wait for the send button (thread-arrival marker). A plain discussion
     suffices — "Change workspace…" is `mutationsSupported`-gated only, not promotion-gated.
  3. **Absence guard (before-state, deterministic, no claude turn):** `newWorkspace = "e2e562-" +
     System.currentTimeMillis()` asserted `assertCountEquals(0)` on screen.
  4. Drive the **real** overflow: `CD_MORE_ACTIONS` → wait for `"Change workspace"` (substring — the
     production string ends in a real U+2026 ellipsis) → tap. Opens the Workspace Picker sheet.
  5. Picker → "Create new folder…" (`CREATE_FOLDER_ROW`) → wait for `hasSetTextAction() and isFocused()` →
     `performTextInput(newWorkspace)` → `CREATE_BUTTON`.
  6. **After-state (durable post-condition):** one `waitUntil` spans **both** sequential daemon round-trips
     (`create_workspace_folder` → `change_workspace`) for the unique name to appear, then
     `onFirst().assertIsDisplayed()` — on success the chip reads `"Workspace: <newWorkspace> (change)"`.
  - New companion constants (reusing `CREATE_FOLDER_ROW`/`CREATE_BUTTON`/`CD_NEW_DISCUSSION`/
    `CD_SEND_MESSAGE`/`CD_MORE_ACTIONS`/timeouts from #566/#554 unchanged):

    #566's `FOLDER_NAME_PREFIX = "e2e566-"` — the shared companion object forbids redeclaration).

## Patterns established

None new at the harness level — a confirming instance of the rung-3 real-claude scenario shape
(#481/#482/#566/#541/#554/#551's template): create → drive the real affordance → tolerant substring/presence
assert on a runtime-unique token. One reusable move for future e2e's whose picker/dialog opens **over a
screen with its own editable field** (the thread composer, here): disambiguate the target field by
**auto-focus** (`hasSetTextAction() and isFocused()`), not by node count — the same technique #554 uses for
RenameDialog-over-thread, now confirmed twice.

## Lessons learned

(Lifted from the PR body's own Lessons-learned section.)

- **Picker-over-thread field disambiguation.** Unlike #566 (picker opens over the message-less channel
  list, so `onNode(hasSetTextAction())` is unambiguous), this scenario's picker opens over the **thread**,
  whose composer (`ThreadInputBar`'s `BasicTextField`) is also an editable field. Once `CreateFolderDialog`
  opens there are **two** `hasSetTextAction()` nodes; the dialog's field is selected by its auto-focus
  (`hasSetTextAction() and isFocused()`) — the same disambiguation #554 uses for RenameDialog-over-thread.
  Generalizes: whenever a dialog opens over a screen that itself has an editable field, count-based
  selectors break and focus-based selectors are the fix.
- **Two sequential daemon round-trips, one wait.** The Create tap chains `create_workspace_folder` →
  `change_workspace`; a single `waitUntil` must span both before the chip re-labels — splitting into two
  waits (one per round-trip) would need an intermediate observable that doesn't exist on screen, so the
  combined wait is the only viable structure.
- **A stale park rationale doesn't auto-clear per-ticket.** #561's own doc noted #562 "remains parked ...
  pending the family-wide per-mutation gate" even after PR #572 shipped; this ticket had to be individually
  re-verified against `main` (chip gate turns out irrelevant since no message is ever sent) rather than
  assuming the family-wide gate flip alone made every parked sibling reachable. Matches the
  `po-gate-clear-expires-prior-demote-premise` memory lesson: re-verify each parked ticket, don't trust the
  old park note.
