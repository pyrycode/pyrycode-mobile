# #239 — test(ui/conversations): Introduce `makeVm` helper in `ChannelListViewModelTest`

Pure test-infra refactor inside `ChannelListViewModelTest`: lifts the [`SettingsViewModelTest`](../features/settings-viewmodel.md) `TemporaryFolder` + class-level `dispatcher` + `TestScope.newDataStore()` rig into the channel-list test class and routes all 18 VM construction sites through a new `TestScope.makeVm(repository, prefs = AppPreferences(newDataStore()))` helper. Production code (`ChannelListViewModel`, [`ConversationRepository`](../features/conversation-repository.md), `AppModule`) is untouched. The helper *builds* an `AppPreferences` it doesn't *pass* to the VM — the unused `prefs` parameter is the seam the next ticket changes one line of when it wires `AppPreferences.defaultWorkspace` into the FAB short-press, instead of cascading through 18 call sites.

Split from #236. The whole point of front-loading the split was the architect's >10-consumer-call-site red line: any future ticket adding a constructor dep to [`ChannelListViewModel`](../features/channel-list-viewmodel.md) (defaults-derived deps from the four-key schema in #231 are the obvious candidates — `defaultWorkspace`, `defaultModel`, `defaultEffort`, `defaultYolo`) would have inherited an 18-edit cascade and been forced to split anyway. Doing the split now means the next ticket's diff is "one parameter on `ChannelListViewModel`, one parameter on `makeVm`" — zero call-site touches.

## Summary

- **`@get:Rule val tmp = TemporaryFolder()`** added at the top of the test class, the per-test JUnit rule that scopes each test's DataStore file lifecycle (creates a fresh `app_prefs.preferences_pb` per test, deletes it in `after()`).
- **`private val dispatcher = UnconfinedTestDispatcher()`** is now a class-level field, replacing the per-`@Before` `Dispatchers.setMain(UnconfinedTestDispatcher())` construction site. The `@Before` body changes to `Dispatchers.setMain(dispatcher)` so the same dispatcher instance backs both `setMain(...)` (covering `viewModelScope` work on `Dispatchers.Main.immediate`) and the `runTest(dispatcher) { … }` test bodies. Single source of truth; matches `SettingsViewModelTest:41-51` verbatim.
- **`private fun TestScope.newDataStore(): DataStore<Preferences>`** lifted verbatim from `SettingsViewModelTest`: returns `PreferenceDataStoreFactory.create(scope = backgroundScope, produceFile = { tmp.newFile("app_prefs.preferences_pb") })`. `TestScope` extension (not a plain instance method) so it can reach `backgroundScope` — which `runTest` cancels on test exit, winding down the DataStore writer coroutine deterministically.
- **`private fun TestScope.makeVm(repository: ConversationRepository, @Suppress("UNUSED_PARAMETER") prefs: AppPreferences = AppPreferences(newDataStore())): ChannelListViewModel = ChannelListViewModel(repository)`** is the new construction seam. The `@Suppress("UNUSED_PARAMETER")` is load-bearing — without it the Kotlin compiler warns on every test run, and the suppression is what advertises "this parameter exists deliberately, not by accident". When the next ticket adds the VM dep, the suppression annotation comes off and `prefs` is threaded into the `ChannelListViewModel(...)` call; everything else stays the same.
- **All 18 `val vm = ChannelListViewModel(...)` sites become `val vm = makeVm(...)`** — three input shapes (`stubRepo(channels, discussions)`, `erroringRepo("…", throwOn = …)`, `FakeConversationRepository()` or a local `repository` val) all collapse onto the same helper. The semantic content of every test — assertions, ordering, the repository each test uses, the `MutableSharedFlow(replay = 0)` emission timing — is unchanged.
- **Every `runTest { … }` becomes `runTest(dispatcher) { … }`** so `TestScope.newDataStore()` (and therefore `TestScope.makeVm(...)`) is in scope. Eighteen-site mechanical change, no semantic difference; the `UnconfinedTestDispatcher` was already the effective scheduler via `Dispatchers.setMain(...)`, this just plumbs the same instance through both seams.

## Files touched

- `app/src/test/java/de/pyryco/mobile/ui/conversations/list/ChannelListViewModelTest.kt` — only file changed. +60 / -37 lines; one new `@get:Rule` field at the top, one new class-level `dispatcher` field, two new helper functions (`newDataStore`, `makeVm`) between the `@After` and the first `@Test`, eighteen `ChannelListViewModel(...)` → `makeVm(...)` migrations + eighteen `runTest` → `runTest(dispatcher)` migrations. Five new imports (`DataStore`, `PreferenceDataStoreFactory`, `Preferences`, `AppPreferences`, `TestScope`, `Rule`, `TemporaryFolder`); imports for `UnconfinedTestDispatcher` / `runTest` / `Dispatchers` / `resetMain` / `setMain` retained.

No edits to `ChannelListViewModel.kt` (constructor still `ChannelListViewModel(repository: ConversationRepository)`), `AppPreferences.kt`, `AppModule.kt`, `SettingsViewModelTest.kt`, or any other test class. No new test methods; the 18-test count and the assertion bodies are unchanged.

## Patterns established

- **The "lift the `SettingsViewModelTest` rig into a peer VM test" pattern is now reusable.** Future `*ViewModelTest` classes that need to backfill `AppPreferences` as a future constructor dep — without adding it to the VM today — should copy this file's exact shape: `@get:Rule TemporaryFolder` + class-level `UnconfinedTestDispatcher` field + `TestScope.newDataStore(): DataStore<Preferences>` + `TestScope.makeVm(repo, prefs = AppPreferences(newDataStore())): VmType = VmType(repo)`. The `@Suppress("UNUSED_PARAMETER")` on `prefs` is the documented hook for the follow-up ticket. **Rule:** when a planned next ticket is going to add a constructor dep that would cascade across more than ~10 test sites, do the cascade once now in a pure test-infra slice; the next ticket then changes one helper line. The architect's >10-consumer-call-site red line is the trigger to split this way.
- **`makeVm` is a `TestScope` extension, not a plain method, on purpose.** The default-argument expression `AppPreferences(newDataStore())` needs `backgroundScope` from `runTest`, which is only available inside a `TestScope`. Making `makeVm` a `TestScope` extension is the compile-time guardrail — calling it outside `runTest(dispatcher) { … }` won't compile, which is the desired failure mode (a runtime error would defer the diagnostic to a CI run; a compile error catches it at typing time).
- **Two distinct `makeVm` helper shapes now exist — same name, different return types and call patterns; not interchangeable.** `SettingsViewModelTest`'s `makeVm(prefs, repo = stubRepo())` returns a `SettingsViewModel` and *passes* `prefs` to the VM (the VM takes an `AppPreferences` dep today). `ChannelListViewModelTest`'s `makeVm(repository, prefs = ...)` returns a `ChannelListViewModel` and *holds* `prefs` without passing it (the VM doesn't take an `AppPreferences` dep yet). The naming is intentional — both helpers are the construction seam for their VM, and when the next ticket promotes the channel-list `prefs` parameter into a real VM argument, the two helpers become structurally identical. Don't unify them; the shared name + per-class scope is the right cost.

## Lessons learned

- **A default-argument expression on a `TestScope` extension does not evaluate at declaration time — it evaluates per call.** The first migration attempt eyeballed the `default = AppPreferences(newDataStore())` line and worried that every test would share a single `AppPreferences` (because the default looks like a class-level binding). It doesn't — Kotlin default arguments evaluate at each call site each time the call is made, inside the caller's `TestScope` (because the receiver-bound `newDataStore()` resolves through the call-site scope, not through some captured outer scope). Each `runTest(dispatcher) { … makeVm(...) … }` invocation therefore gets a fresh DataStore over a freshly-named `tmp.newFile(...)` file. The 18 tests *do* share the same `TemporaryFolder` rule instance (lifecycle-scoped to the test class), but `TemporaryFolder.newFile("app_prefs.preferences_pb")` would collide on the second test if it weren't for JUnit's `before()` / `after()` wiping the folder between tests — which it does. Net: zero cross-test leakage; each test sees an empty DataStore.
- **`@Suppress("UNUSED_PARAMETER")` on the `prefs` default is not a code-smell, it's a contract anchor.** Removing the suppression to "clean up" the warning would force one of two regressions: (a) drop the `prefs` parameter entirely (cancels the whole point of this ticket — the next ticket re-does the 18-site cascade), or (b) use `prefs` inside the helper body for nothing (e.g. assign it to a `val`), which would be cargo-cult. The suppression annotation makes the deliberate-disuse legible at the source — when the next ticket lands, the diff is "remove the annotation, add `prefs` to the `ChannelListViewModel(...)` argument list, add a constructor parameter on the VM". Three lines, one helper file, zero call-site cascade.
- **The `runTest { … }` → `runTest(dispatcher) { … }` migration is bigger than it looks until you realise it's the only way `TestScope.newDataStore()` resolves.** Bare `runTest { … }` returns a `TestScope` too, but the receiver-binding for the extension function chains through the surrounding `TestScope`; passing the dispatcher explicitly is the established `SettingsViewModelTest` shape and keeps the dispatcher field as the single source of truth for both `setMain(...)` and the test body. Doing one without the other would work today (the `UnconfinedTestDispatcher` matches what `runTest` would have created anyway) but would diverge from the `SettingsViewModelTest` template and trip the next person who reads the file looking for the convention.
