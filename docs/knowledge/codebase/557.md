# #557 — Surface restore failure from the Archive screen (no silent no-op)

**Issue:** [#557](https://github.com/pyrycode/pyrycode-mobile/issues/557) · split from #550 (itself split
from #531) · **Spec:** [`docs/specs/architecture/557-surface-restore-failure-from-archive-screen.md`](../../specs/architecture/557-surface-restore-failure-from-archive-screen.md) ·
**PR:** [#559](https://github.com/pyrycode/pyrycode-mobile/pull/559), `fc25828` ·
**Feature doc:** [Archived Discussions screen](../features/archived-discussions-screen.md) (updated) ·
Size **S**, `security-sensitive` (PASS).

## Summary

The failure path of `ArchivedDiscussionsViewModel.RestoreRequested` was a silent no-op: `runCatching {
repository.unarchive(id) }.onSuccess { emit RestoreSucceeded }` caught (and swallowed) everything on
failure, per an explicit "unarchive yields no UI surface in this slice" deferral comment dating to #177.
This ticket is that deferral — it adds a new payload-free `ArchivedDiscussionsEffect.RestoreFailed`
variant and rewrites the handler to an explicit try/catch that rethrows `CancellationException` first (JVM:
`j.u.c.CancellationException extends IllegalStateException`), then catches `RelayErrorException` (server
`error` — reachable because `unarchive` is request/reply, #549) and `IllegalStateException` (disconnected,
the repository's `live` path) → `RestoreFailed`. The screen's existing `effects` collector renders it as a
transient snackbar with a fixed local string (`restore_failed`); the server-supplied exception message is
never read. The success path (`RestoreSucceeded`, list-driven removal via `observeConversations`) is
unchanged. Twin of [#556](556.md) (archive-from-thread) — same "no crash, no silent no-op" mutation-surface
pattern, disjoint files (`ui/settings/` vs `ui/conversations/thread/`) — but strictly smaller: it reuses the
screen's existing `effects` `Channel`, so there is no new flow and **no `MainActivity` change** (`effects =
vm.effects` was already wired since #177).

## Files touched

- **`ui/settings/ArchivedDiscussionsViewModel.kt`** (+33/−10):
  - New `data object RestoreFailed : ArchivedDiscussionsEffect` beside the existing `RestoreSucceeded`.
  - `RestoreRequested` branch rewritten from `runCatching{}.onSuccess{}` to an explicit `try { unarchive();
    send(RestoreSucceeded) } catch (CancellationException) { throw e } catch (RelayErrorException) {
    send(RestoreFailed) } catch (IllegalStateException) { send(RestoreFailed) }` inside the same
    `viewModelScope.launch`. `IllegalArgumentException` (`conversation.not_found`) and the #318 decode
    exception are **deliberately not caught** — not_found is unreachable (you can only restore a
    conversation currently shown in the Archived list) and a malformed reply is a fail-loud protocol
    violation; exact parity with #556/#530's posture. New imports: `kotlinx.coroutines.CancellationException`,
    `de.pyryco.mobile.data.network.RelayErrorException`.
- **`ui/settings/ArchivedDiscussionsScreen.kt`** (+4): third `when` branch on the effects collector —
  `ArchivedDiscussionsEffect.RestoreFailed -> snackbarHostState.showSnackbar(resources.getString(R.string.restore_failed))`
  — a structural clone of the `RestoreSucceeded` branch. Composable stays stateless; no new param.
- **`res/values/strings.xml`** (+1): `restore_failed = "Couldn't restore this conversation. Try again."`,
  beside `archive_failed` — fixed local text covering both failure modes, deliberately omitting
  "check your connection" since it must also cover the server-error case.
- **`ArchivedDiscussionsViewModelTest.kt`** (+182/−27, net +3 tests):
  - **Rewritten:** `restoreRequested_doesNotEmitEffect_whenUnarchiveThrows` →
    `restoreRequested_whenDisconnected_surfacesRestoreFailed` — now asserts `RestoreFailed` is emitted
    (not that nothing is), driven by `IllegalStateException("not connected")` (AC's required disconnected
    case). Captures the default uncaught-exception handler to prove the typed catch ran rather than the
    throw escaping (necessary because the new catch is narrower than the old `Throwable`-wide one).
  - **New:** `restoreRequested_whenServerError_surfacesRestoreFailed_withoutLeakingMessage` — same shape,
    driven by `RelayErrorException(message = "leak me")`; the payload-free `RestoreFailed` assertion is
    structurally the proof the message can't surface (AC #5).
  - **New:** `restoreRequested_scopeCancellationMidRestore_isInert_notMisSurfaced` — new private
    `GatingUnarchiveRepo` whose `unarchive` suspends on a `CompletableDeferred` until cancelled; drives
    cancellation via `ViewModelStore().clear()` (mirrors #556's `GatingArchiveRepo` shape); asserts zero
    effects and an empty uncaught-handler capture (AC #4).
  - **Helper change:** `throwingUnarchiveRepo(source)` → `throwingUnarchiveRepo(source, error: Throwable)`
    so the two failure tests inject different exception types through one double.
  - Unchanged, stay green: `restoreRequested_callsUnarchive_withConversationId`,
    `restoreRequested_emitsRestoreSucceededEffect_afterUnarchive` (AC #2), all state/tab/partition tests.
  - Dropped unused `org.junit.Assert.assertNull` import (no longer asserting `null`).

**Not touched (deliberate scope decision):** the `mutationsSupported == false` reachability gate (#508/#537
family) — against the real relay, `unarchive` stays hidden, so this path is exercised via fakes in tests,
not live UI. e2e sibling #551 remains parked in Inbox pending the family-wide per-mutation gate decision.

## Patterns established

Fourth confirming instance of the one-shot-effect-channel surfacing idiom (`modalSendErrors` #452 →
`newSessionErrors` #540 → `archiveErrors` #556 → `RestoreFailed` #557), and the **first** to ride an
*existing* effect channel rather than adding a new one — because `ArchivedDiscussionsEffect` already
existed (`RestoreSucceeded` since #177), the new failure surface is just a sibling sealed variant plus a
`when`-branch, with zero `MainActivity` fan-out. When a mutation's *success* effect already has a channel,
add the failure as a sibling variant on that same channel before reaching for a new one.

## Lessons learned

- **Adding a variant to a sealed `Effect` interface forces exhaustiveness across the whole family (the
  screen's `when`), which gives a clean RED/GREEN split for free.** Land the new variant + screen branch +
  string first while leaving the old (over-broad) handler in place — the two new surfacing tests fail on
  the *assertion* (`RestoreFailed` not emitted) rather than on a compile error, giving a real RED before the
  catch-block rewrite turns them GREEN. Useful whenever a ticket both adds a sealed-interface variant and
  changes the logic that emits it — sequence the plumbing ahead of the logic to get assertion-level RED.
