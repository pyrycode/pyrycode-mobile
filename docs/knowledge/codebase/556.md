# #556 — Surface the archive result from the thread (no crash, no silent no-op)

**Issue:** [#556](https://github.com/pyrycode/pyrycode-mobile/issues/556) · split from #550 (itself split
from #531) · **Spec:** [`docs/specs/architecture/556-surface-archive-result-from-thread.md`](../../specs/architecture/556-surface-archive-result-from-thread.md) ·
**PR:** [#558](https://github.com/pyrycode/pyrycode-mobile/pull/558), `638e6e5` · **Feature doc:**
[Thread overflow menu](../features/thread-overflow-menu.md) § ViewModel dispatcher / edge cases (updated) ·
Size **S**, `security-sensitive` (PASS).

## Summary

Archive from the thread overflow menu / Channel Info Sheet routed through the shared
`launchGuardedRepoCall`, which inert-swallows every failure (#490) and, on a throw, short-circuited the
`navigationChannel.send(PopBack)` that followed in the same block — so a failed archive was a silent no-op
that *also* stranded the user on the thread. This ticket gives archive its own surfacing path, cloning the
`sendNewSession`/`newSessionErrors` idiom (#540) with one deliberate addition: a second caught exception
type, because archive is **request/reply** (`sendAndAwaitReply`, awaits `conversation_updated` — #549)
where `new_session` is fire-and-forget, so a correlated server `error` (`RelayErrorException`) is a real,
reachable outcome here.

- **Success is passive** — `sendArchive()` calls `repository.archive(conversationId)` then
  `navigationChannel.send(ThreadNavigation.PopBack)`; the confirmed upsert makes `observeConversations`
  re-emit with the conversation now in the Archived tier, so it leaves the main list with **no explicit
  removal call**.
- **Failure surfaces** — a caught `RelayErrorException` or `IllegalStateException` (not-connected)
  `trySend(Unit)`s on a new one-shot `archiveErrors: Flow<Unit>`, collected by `ThreadScreen` as a third
  transient snackbar with a **fixed local string** (`archive_failed`) — never the caught exception's
  message. `PopBack` never fires on this path; the user stays on the thread.
- **Cancellation is preserved** — `CancellationException` is rethrown **first** (it extends
  `IllegalStateException` on the JVM), so `viewModelScope` teardown mid-archive is never mis-surfaced as an
  archive failure.

## Files touched

- **`ui/conversations/thread/ThreadViewModel.kt`** (+61/−16):

    `val archiveErrors: Flow<Unit> = archiveErrorChannel.receiveAsFlow()` (beside `newSessionErrors`) —
    payload-free one-shot signal; nothing sensitive can flow through a bare `Unit`.

    navigationChannel.send(PopBack) }` wrapped in three catches in this order — `CancellationException`

## Patterns established

Third confirming instance of the **surfacing** one-shot-channel idiom (`modalSendErrors` #452 →
`newSessionErrors` #540 → `archiveErrors` #556): when a repository call's only client-observable failure
needs a user-visible surface rather than a swallow, clone `Channel<Unit>(BUFFERED).receiveAsFlow()` + a
paired `LaunchedEffect` snackbar collector. This is also the **first** instance where the wrapped call is
request/reply rather than fire-and-forget, establishing the catch-set rule: **match the catches to what the
specific wire call can actually produce** — request/reply calls that await a correlated reply must also
catch `RelayErrorException`; fire-and-forget calls (like `sendNewSession`) must not, since a correlated
server error can never originate for them.

## Lessons learned

- **A verb moving from "guarded and silent" to "surfaced" is a full extraction, not an added catch.** Archive
  had been one of the shared guard's four verbs since #227/#490; giving it a user-visible failure surface
  meant pulling it out of `launchGuardedRepoCall` entirely (own coroutine, own catch set, own channel) rather
  than teaching the guard to sometimes surface — the guard's whole contract (#490's confidentiality posture:
  never log or expose a caught message) is verb-invariant, so a per-verb "surface this one" flag would have
  been the wrong shape. Watch for this pattern whenever a ticket asks one item out of a shared
  swallow-everything helper to start talking to the user.
- **Editing a shared multi-failure test loop when a verb leaves the guard is not optional cleanup — it's
  required for correctness, not just tidiness.** The guard's swallow loop iterated all four verbs against all
  three caught exception types; once `Archive` stopped catching `UnsupportedOperationException`, leaving its
  call in the loop would make that specific iteration throw uncaught and fail the test outright (not just
  assert something stale). Any ticket that moves a verb off a shared guard needs to audit every test that
  iterates "all guarded verbs" as a group.
