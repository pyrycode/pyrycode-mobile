# #221 — feat(ui/list): FAB long-press → `WorkspacePicker` on Channel List

First concrete consumer of the [`WorkspacePicker`](../features/workspace-picker.md) host ([#220](./220.md)). Long-pressing the Channel List's new-discussion FAB now opens the workspace picker sheet; on pick, the new discussion is created with `cwd = pickedPath` and the user navigates to its thread. Single-tap behaviour from [#22](./22.md) (create-scratch-discussion → navigate) is unchanged.

The implementation walks the M3 `FloatingActionButton` *back* — `Modifier.combinedClickable` cannot be wrapped around the M3 widget because its inner `Surface(onClick = ...)` swallows tap events (the failure mode documented in [`./25.md`](./25.md)'s "Lessons learned"). Instead the FAB is now a manually-composed non-clickable `Surface` carrying the `combinedClickable` directly on its modifier, reproducing the M3 visual but moving the click ownership to the outer node. Two equivalent patterns for "add a long-press to an existing primitive" now coexist in the codebase: (1) optional `onLongClick: (() -> Unit)? = null` parameter on a primitive we own ([`ConversationRow`](../features/conversation-row.md), [#25](./25.md)); (2) replace the primitive with a non-clickable equivalent we control ([`ChannelInfoSheet.Footer`](./217.md)'s `Box.combinedClickable { Text(...) }`, and now `ChannelListFab`). Pick by ownership — own the primitive → use (1); don't own it → use (2).

ViewModel-side shape mirrors `DiscussionListViewModel.pendingPromotion` ([#78](./78.md)) and the `SaveAsChannelDialog` visibility arm ([#142](https://github.com/pyrycode/pyrycode-mobile/issues/142)): a private `MutableStateFlow<Boolean>` added as a fourth arm to the existing 3-way `combine` over channels / discussions / last-messages, projecting onto a new `workspacePickerVisible: Boolean = false` field on both `ChannelListUiState.Loaded` and `ChannelListUiState.Empty`. The flag is cleared *synchronously before* the suspend in the `WorkspacePicked` handler (same discipline as [#78](./78.md)'s `confirmPromotion`) so the sheet's exit animation starts immediately instead of waiting on `createDiscussion`.

## Summary

- **Three new `ChannelListEvent` variants** (in `ChannelListScreen.kt`): `LongPressFab` (data object), `WorkspacePicked(workspace: String)` (data class), `WorkspacePickerDismissed` (data object). The three-variant split (not two) mirrors [#78](./78.md)'s `PromoteConfirmed` / `PromoteCancelled` shape — the "dismissed without picking" path is distinct from "picked a path" and must NOT trigger `createDiscussion`.
- **`workspacePickerVisible: Boolean = false`** field added to both `ChannelListUiState.Loaded` and `ChannelListUiState.Empty`. Default preserves every existing positional/named call site (six previews, eleven test fixtures, and the VM's own `combine` body). `Error` and `Loading` do not carry the field — the FAB renders only in `Loaded`/`Empty`, so the picker cannot be reached from those states.
- **Private `pendingWorkspacePicker: MutableStateFlow<Boolean>`** on the VM, added as a fourth arm to the existing `combine(channelsFlow, discussionsFlow, lastMessagesFlow)`. The 4-arity `combine` overload ships with kotlinx-coroutines (up to 5 args); no infrastructure change. Initial value `false` so combine doesn't suspend on it; loading semantics from [#22](./22.md) and [#161](./161.md) preserved.
- **Three new `onEvent` arms** on the VM. `LongPressFab` and `WorkspacePickerDismissed` are one-liners flipping `pendingWorkspacePicker.value` to `true` / `false` respectively. `WorkspacePicked(path)` is the same shape as [#22](./22.md)'s `CreateDiscussionTapped` arm but passes `workspace = event.workspace` and clears the visibility flag *synchronously before* the `viewModelScope.launch { repository.createDiscussion(workspace = path); navigationChannel.send(ToThread(c.id)) }`.
- **`ChannelListScreen`'s FAB is now `ChannelListFab` — a manually-composed `Surface` with `combinedClickable`**, replacing the M3 `FloatingActionButton` widget. The visual treatment is unchanged (56dp, `FloatingActionButtonDefaults.shape`, `primaryContainer` fill, 6dp tonal+shadow elevation); the change is structural — the inner `Surface(onClick = ...)` that the M3 widget composes was swallowing tap events before `combinedClickable`'s `onClick` arm could see them (the lesson from [`./25.md`](./25.md)). The non-clickable `Surface { content }` overload has no internal click handler, so `combinedClickable` is the sole pointer-input subscriber on the node.
- **`WorkspacePicker` host wired in as a sibling of the `Scaffold`** (not inside its content lambda). `pickerVisible` is computed from a `when (state)` block that maps `Loaded` / `Empty` to their `workspacePickerVisible` field and `Loading` / `Error` to `false`. `onPicked` dispatches `WorkspacePicked(path)`; `onDismiss` dispatches `WorkspacePickerDismissed`. Placing the host outside the Scaffold matches [#78](./78.md)'s dialog-as-overlay pattern and keeps the `ModalBottomSheet`'s window-level scrim away from the body's `LazyColumn` layout.
- **`MainActivity`'s `composable(Routes.CHANNEL_LIST)` block** forwards the three new variants into `vm.onEvent` via a comma-grouped arm (`CreateDiscussionTapped, LongPressFab, is WorkspacePicked, WorkspacePickerDismissed -> vm.onEvent(event)`). The existing `navigationEvents` collector at lines 140-147 is unchanged — `WorkspacePicked → createDiscussion → ToThread` rides the same channel as [#22](./22.md)'s tap path.
- **New string `R.string.cd_long_press_fab_pick_workspace = "Pick a workspace for the new discussion"`** in `values/strings.xml`. The existing `cd_new_discussion` tap label is reused as the FAB's `onClickLabel`; the new string is the `onLongClickLabel`. Combined, TalkBack announces "New discussion, button, double-tap to activate, long-press to pick workspace."
- **Two new unit tests** on `ChannelListViewModelTest`: `longPressFab_setsWorkspacePickerVisibleToTrue` (state-flag flip via the `stubRepo` helper) and `workspacePicked_createsDiscussionWithPickedWorkspace_emitsNavigation_andClearsVisibility` (the end-to-end create + nav + visibility-clear path via `FakeConversationRepository()`). The existing `createDiscussionTapped_*` tests cover the AC's [#22](./22.md) regression requirement verbatim — not duplicated.
- **`./gradlew test`** passes.

## Patterns established

- **"Replace the M3 widget with a non-clickable equivalent we control" is the canonical fix for "I need a gesture on a primitive whose inner `clickable` shadows the outer modifier."** When the primitive is ours (`ConversationRow`), the optional `onLongClick: (() -> Unit)? = null` parameter ([#25](./25.md)) is the right shape. When the primitive is M3's and we don't own it (`FloatingActionButton`), the right shape is to ditch the widget and reproduce the visual on a non-clickable surface where `combinedClickable` is unobstructed — same shape as [`ChannelInfoSheet.Footer`](./217.md)'s `Box.combinedClickable { Text(...) }`. **Rule:** if you can't add a parameter to the primitive, replace the primitive. Do not try to wrap the M3 widget in an outer `combinedClickable` — the inner `Surface(onClick = ...)` will swallow events, and the failure mode is silent (the tap path appears to work in cursory testing but the long-press never fires).
- **Manually-composed `Surface` reproduces M3 component visuals at the cost of the press-elevation animation.** `Surface(modifier = …combinedClickable(…), shape = FloatingActionButtonDefaults.shape, color = primaryContainer, contentColor = onPrimaryContainer, tonalElevation = 6.dp, shadowElevation = 6.dp) { content }` matches the M3 standard FAB visual (56dp + the public `FloatingActionButtonDefaults.shape` token + `primaryContainer` fill + 6dp tonal+shadow elevation matching the internal `FabPrimaryTokens.ContainerElevation`). What's lost: the inner FAB's "lower elevation while held" animation. What's preserved: the M3 ripple via `combinedClickable`'s default indication (`LocalIndication.current` resolves to M3 ripple inside the theme). **Rule:** when reproducing M3 component visuals on a `Surface` to take control of click ownership, accept the press-elevation animation loss — the ripple covers the user-facing feedback gap, and the cosmetic delta isn't worth maintaining a fork of M3's internal animation code. If a future BOM exposes the inner FAB's `onLongClick` natively, revert to the native widget and delete the manual composition.
- **Three-variant event split (`Action`, `Confirmed(payload)`, `Cancelled`) is the canonical shape for "transient modal that fires a side effect on confirm."** Same shape as [#78](./78.md)'s `PromoteChannelRequested` / `PromoteConfirmed` / `PromoteCancelled`. The "dismissed without picking" path is distinct from "picked a path" and must NOT trigger the side effect; collapsing the two into a single variant forces the consumer to invent a nullable-payload sentinel that loses type safety. **Rule:** every transient-modal event surface uses three variants — open, confirm-with-payload, cancel. The VM's `Cancel` arm is one line (`flag.value = false`); the `Confirm` arm clears the flag *synchronously before* the suspend launches.
- **`combine(upstream, MutableStateFlow<Boolean>)` 4th-arm visibility projection is now the second instance** ([#78](./78.md)'s `pendingPromotion` was the first; this ticket is the second). Add a `private val pending<Sheet> = MutableStateFlow(false)` to the VM, widen the existing N-way `combine` to N+1, and project onto a `<sheet>Visible: Boolean = false` field on every non-`Loading`/`Error` `UiState` variant. **Rule:** for any host composable that's hoisted-`visible`-driven and reached from a ViewModel-mediated screen, use the combine-arm pattern. Don't hoist a `MutableState<Boolean>` to the screen — that conflates UI state with VM-driven decisions and breaks the "single source of state per ViewModel" principle from CLAUDE.md.
- **Bare `Boolean` (not a nullable-payload sentinel) for transient-modal visibility when there's no per-target payload.** [#78](./78.md)'s `pendingPromotion: PendingPromotion?` carries the conversation being promoted; this ticket's `pendingWorkspacePicker: Boolean` has no equivalent payload (the picker is a one-off "create a discussion" trigger from the FAB, not "promote *this specific* discussion"). **Rule:** lift the visibility flag out of a nullable-payload wrapper when the payload is empty. A bare `Boolean` is the minimum sufficient surface; over-engineering it as `pendingWorkspacePicker: PendingWorkspacePicker?` reads as "we'll need a payload later" when no use case has emerged.
- **`stringResource` hoisting above the `Scaffold` when the resource is consumed inside a slot lambda.** `Scaffold`'s `floatingActionButton` slot is a `@Composable () -> Unit`; calling `stringResource(...)` inside it works but the resource lookup is captured in the slot's recomposition scope. Hoisting the lookup to the composable's outer scope keeps the lookup stable and lets the `String` flow into the slot as a parameter — same shape as constants. Cosmetic but consistent with the project's "hoist what you can" lean.
- **The destination's `when (event)` comma-groups events that share a body.** `MainActivity`'s arm now reads `CreateDiscussionTapped, LongPressFab, is WorkspacePicked, WorkspacePickerDismissed -> vm.onEvent(event)`. Four variants share one body (`vm.onEvent(event)`) — comma-grouping them keeps the diff to one arm and makes the "events that forward to VM vs. events that resolve to nav" split visually obvious. **Rule:** when N events share the same destination-side handling, comma-group them in the `when` rather than duplicating the body N times.
- **`pickerVisible` derived via exhaustive `when (state)`, not a `state is X && state.flag` chain.** The host's `visible` argument is `true` only when the state is `Loaded`/`Empty` *and* the field is `true`; expressing this as `(state is Loaded && state.workspacePickerVisible) || (state is Empty && state.workspacePickerVisible)` works but obscures the exhaustiveness. The `when` form (`Loaded -> state.workspacePickerVisible; Empty -> state.workspacePickerVisible; Loading, is Error -> false`) is what the compiler can check for completeness — adding a fifth `ChannelListUiState` variant later forces a decision here. **Rule:** when computing a derived value from a sealed UiState, use `when (state)` exhaustively. Pay the verbosity for the compiler check.

## Lessons learned

- **`@OptIn(ExperimentalFoundationApi::class)` is required on the `ChannelListScreen` composable too**, not only on the new `ChannelListFab` private composable. `combinedClickable` is used inside the FAB's modifier chain, but the `floatingActionButton` slot's lambda body is part of the outer `ChannelListScreen`'s composable scope. The compiler points at the outer composable's annotation site, not the inner one. Both annotations are needed; the inner one keeps the seam local to the FAB extraction, and the outer one is what actually satisfies the experimental-API requirement at the call site. Costs one annotation; no runtime impact.
- **`stringResource` lookups inside a `Scaffold` slot's `@Composable` lambda recompose with the slot, but hoisting them above the `Scaffold` is the cleaner shape.** Both forms work — `stringResource(R.string.cd_new_discussion)` inside the slot recomposes when the resource table changes (locale switch) just like the hoisted form. The hoist makes the FAB extraction (`ChannelListFab(onTap, onLongPress, onTapLabel, onLongPressLabel)`) testable from outside the slot and matches the project's "treat resources as constants where you can" lean. Functionally identical, structurally cleaner.
- **`pendingWorkspacePicker.value = false` *before* the `viewModelScope.launch` is the dismissal animation timing fix.** If the assignment ran inside the launch (after `createDiscussion` returned), the sheet's exit animation would not start until the suspend completed — visibly laggy on a real Phase 4 backend. Doing the flip synchronously means the state's `workspacePickerVisible` flips to `false` immediately, the host re-composes with `visible = false`, the `ModalBottomSheet` starts its exit animation, and the suspend can take as long as it needs. The same discipline applies in [#78](./78.md)'s `confirmPromotion`. **Lesson:** for any "modal closes on confirm AND a suspend fires" handler, the close (state flag flip) goes before the launch, not inside it. The dismissal animation timing depends on it.
- **The `WorkspacePicker` host is composed as a sibling of `Scaffold`, not inside its content lambda.** `WorkspacePicker` wraps a `ModalBottomSheet` which manages its own `Popup`/`Window`; placing it inside the `Scaffold` content slot works but conflates the sheet's window-level scrim with the body's `LazyColumn` layout (awkward to reason about, especially if a future ticket adds insets handling). Sibling placement keeps the responsibilities clean: `Scaffold` owns the body's layout + chrome; the host owns its own overlay window. Same shape as [#78](./78.md)'s `SaveAsChannelDialog` rendering. **Lesson:** host composables that wrap `ModalBottomSheet` / `AlertDialog` / `Popup` / `Window` belong as siblings of the `Scaffold`, not inside its content.
- **`Surface { content }` (no `onClick`) is the non-clickable overload — distinct from `Surface(onClick) { content }`.** The two overloads have different parameter lists; `Surface` without `onClick` accepts `shape`, `color`, `contentColor`, `tonalElevation`, `shadowElevation`, and renders the visual with no inner `clickable`. The `Surface(onClick = ...)` overload installs its own `Modifier.clickable` on a leaf node, exactly like `FloatingActionButton` does internally — which is the failure mode for outer `combinedClickable`. The non-clickable overload is what lets `combinedClickable` be the sole gesture subscriber on the node. **Lesson:** when reaching for `Surface` to take control of click ownership, verify you're using the non-clickable overload (no `onClick` parameter) — the clickable overload re-introduces the same shadowing the rewrite was meant to fix.
- **`Box(modifier = Modifier.fillMaxSize(), contentAlignment = Alignment.Center)` is required inside the `Surface` to centre the `Icon`.** The `Surface { content }` overload doesn't centre its content automatically — without the inner `Box`, the `Icon` renders at the top-left of the 56dp Surface. The M3 `FloatingActionButton` widget does this centring internally; reproducing the visual on a bare Surface means reproducing the centring too. One line; obvious in retrospect.
- **The architect's first-pass design wrapped the M3 `FloatingActionButton` in an outer `Box.combinedClickable`; the spec was revised mid-ticket to the manually-composed `Surface` approach** (see commits `d18d630` for the original spec and `c5bbae6` for the revision). The revision was necessary because the wrap-the-M3-widget approach fails silently — the long-press never fires because the inner `Surface(onClick = ...)` consumes pointer events first. The lesson at [`./25.md`](./25.md) (originally about `ConversationRow`'s inner `ListItem.clickable`) generalises directly to M3's `FloatingActionButton`'s inner `Surface(onClick = ...)`. **Lesson:** when designing a long-press affordance on an M3 widget, check the widget's source for inner `Surface(onClick = ...)` / `clickable` / `pointerInput` modifiers *before* committing to a wrap-the-widget approach. The architectural failure mode is silent (tap works, long-press doesn't); the fix is structural (replace the widget), not cosmetic (add an opt-in).
- **`pendingWorkspacePicker`'s retained-true behaviour across an `Error` transition is acceptable Phase 0 behaviour, but the VM's internal flag becomes unobservable.** If a flow throws while the picker is open, the `combine` collapses to `Error` (which carries no `workspacePickerVisible` field). The VM's `pendingWorkspacePicker.value` retains `true`, but no consumer state exposes it. When upstream recovers (`Loaded` emits again), the picker reappears — the projection reads `pendingWorkspacePicker.value` directly. This is the "single source of truth" shape working as intended: the VM remembers the decision, the projection re-applies it whenever a renderable state lands. Phase 4 may revisit if `Error` becomes a routine transient state and "picker visibility survives a flow error" reads as surprising. **Lesson:** the combine-arm pattern's "flag survives across non-renderable states" property is a feature for now; if a UX review later finds the auto-reappearance surprising, the fix is a `LaunchedEffect` on `Error` that flips the flag to false, not a redesign of the projection.
- **`async { vm.navigationEvents.first() }` launched *before* the trigger** — same as [#22](./22.md)'s tests. The collector must be attached when the channel sends; launching after the trigger races the send. `advanceUntilIdle()` between the trigger and `.await()` to drain the in-flight launch. Two new tests reuse the pattern verbatim.
- **`stubRepo` works for `LongPressFab` because no repository call is involved.** Pure state-flag flip; the file's existing `stubRepo` helper returns `TODO("not used")` for `createDiscussion`, which is fine because the test doesn't reach that method. `WorkspacePicked` does reach it, so its test uses `FakeConversationRepository()` directly — the same split [#22](./22.md) established. **Lesson:** state-derivation tests use the stub (control over emission timing); side-effect tests use the production fake (faithful integration of `createDiscussion` + `observeConversations`). Don't extend the stub to cover `createDiscussion`; the fake already does it correctly.
- **The new `Loaded`/`Empty` `workspacePickerVisible: Boolean = false` default kept 26 construction sites unchanged.** Previews, screen tests, VM tests, and the VM's own `combine` projection all construct `Loaded(...)` / `Empty(...)` via named-arg syntax; the default lets every site omit the new argument. Same shape as [#161](./161.md)'s `recentDiscussionLastMessages: Map<String, Message> = emptyMap()` widening — generalised rule: when adding a `Boolean` (or any field with a sensible "no data" identity) to a widely-constructed `UiState` data class, default it. The only reason to omit the default is when *forcing every site to acknowledge the new field* is the actual goal (rare).
