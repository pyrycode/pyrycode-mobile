# Ticket #597 — render "Compacting conversation" in the thread status slot

**Issue:** [#597](https://github.com/pyrycode/pyrycode-mobile/issues/597) ·
**Spec:** [`docs/specs/architecture/597-compacting-status-render.md`](../../specs/architecture/597-compacting-status-render.md) ·
**PR:** [#604](https://github.com/pyrycode/pyrycode-mobile/pull/604) (`d818d3f`) ·
**Feature doc:** [Compacting indicator](../features/compacting-indicator.md) ·
Split from #583. The visible reaction to sibling data slice [#596](596.md) (PR #600, `da4c3f9`), which
this consumes and was natively blocked on. Size **S**, `security-sensitive` (architect self-review
**PASS**).

## Summary

Renders #596's already-decoded `compacting` projection in the thread, so a tens-of-seconds auto-compact
silence reads as busy rather than hung. `ThreadViewModel.isCompacting` hoists `observeCompacting` as a
sibling `StateFlow<Boolean>` — a verbatim clone of `isStalled` — and `ThreadScreen`'s foot-of-list status
slot grows from #594's two-way `if` into a three-way `when`: api-retry (top arm) → compacting → the
generic thinking spinner. The new `CompactingIndicator` clones `ThinkingIndicator`'s M3 idiom with a
compaction label pair and, correctly, clones neither of `ApiRetryIndicator`'s two extra decisions — no
`isRenderableCounter` display gate (no counter exists on the wire) and no "dedup may not be added" KDoc
caveat (a `Boolean` has no intermediate values to collapse, so dedup is correct and already applied
upstream). Four production `.kt` files plus one new, exactly the shape sized against #594. Both edges
proven at two levels — 3 new JVM `ThreadViewModelTest` tests (closing the coverage gap #594's review
flagged) and 5 rung-2 `ScriptedCompactingTest` scenarios — plus the e2e coverage doc records the
producer-side carve-out for rungs 3/4. All gates green; code review **PASS** (2 non-gating NITs).

## Load-bearing design choices

- **Dedup inverts relative to `apiRetry`, and the KDoc says so explicitly.** `observeApiRetry`'s KDoc
  warns "no dedup may be added" because a climbed counter must reach the screen as a fresh emission;
  `observeCompacting` is a bare `Boolean` with no intermediate values, so `distinctUntilChanged` (already
  applied upstream in #596) is correct and no extra operator is needed. Stating the inversion in the
  hoist's own KDoc — rather than leaving the next reader to infer it — is the single most valuable line
  in the diff per code review.
- **No display-sanitisation gate, correctly not cloned.** `ApiRetryIndicator.isRenderableCounter()`
  exists because two daemon-supplied ints reach that label; the `compacting` wire payload
  (`{conversation_id, active}`) has no counter or free text at all, so there is nothing to gate and
  cloning the pattern would have been dead code.
- **Precedence stays single-sourced in `ThreadScreen`, not `ThreadViewModel`** — #594's decision,
  extended rather than revisited. `isThinking` is kept as a pure `turn_state` reduction; the three-way
  `when` that decides which status wins is a screen-level rendering decision, so suppressing `isThinking`
  at its source to fold in compaction would make the VM's contract lie to the tests that assert it
  directly.
- **api-retry keeps the top arm over compaction, by fiat, with the reason on record.** The two signals
  have never been observed overlapping and no AC is spent on the combination, but the tie-break needed a
  reason: api-retry is the "something is going wrong" signal, compaction is benign progress, and the
  benign affordance must never mask the alarming one. This is also the render-side half of the ticket's
  bounded security question — see § Security below.

## Patterns established

Nothing genuinely new at the architecture level — this is the fourth instance of the early-return /
sibling-`StateFlow` / defaulted-hoisted-parameter / merged-`semantics` / design-owed-M3 pattern
(`ThinkingIndicator` #406/#407, `StallPromotionBanner` #395/#396, `ApiRetryIndicator` #593/#594). Two
points worth carrying forward for the next status-affordance ticket:

- **The foot-of-list slot's either/or (#594) generalizes cleanly to a `when` with more arms** — extending
  a two-way `if` to a three-way `when` required no restructuring, just one more arm and an extended
  comment. The next status affordance to join this slot should do the same rather than reaching for a
  shared status-event abstraction; #593's spec explicitly deferred that abstraction until it's clearly
  warranted, and three arms still doesn't cross that bar.
- **A `Boolean`-shaped signal correctly clones `isStalled`'s hoist shape wholesale, with zero new
  decisions** — when a future ticket's data half is a bare on/off edge with no payload (as opposed to
  `api_retry`'s counter-carrying type), the render half should default to the `isStalled` /
  `ThinkingIndicator` template and explicitly *decline* to clone any of `ApiRetryIndicator`'s
  counter-specific machinery (the display gate, the dedup caveat) rather than copying it out of habit.

## Lessons learned

- **`spotlessApply` reorders imports, but the ordering violation only surfaces on `spotlessCheck`.** An
  alphabetically-misplaced new import for `CompactingIndicator` compiled and passed
  `test`/`assembleDebug`/`lint` cleanly; only `spotlessCheck` caught it. Don't trust the mandatory-gate
  trio alone to catch import-ordering drift — run `spotlessCheck` explicitly after adding a new import to
  an existing file.
- **A wrong FQCN in `-Pandroid.testInstrumentationRunnerArguments.class` surfaces as an instrumented
  `initializationError` *failure*, not a "no tests matched" skip** — it reads exactly like a real
  regression. `ThinkingIndicatorTest` lives under `ui/conversations/thread/`, not
  `ui/conversations/components/` beside the composable it tests; when scoping a single-class instrumented
  run, verify the test class's actual package before assuming a red result means the code is broken.
- **`get_metadata` alone discharges the Figma fidelity gate when the ticket's contract is "clone the
  sibling exactly."** #597 re-verified Figma `16:8` via `get_metadata` (not `get_screenshot`) and that
  was sufficient, because the design-owed-gap finding only needed to confirm no status-affordance row is
  drawn — the same conclusion #594 reached. Reach for the heavier screenshot fetch only when the ticket
  is matching pixel values, not confirming an absence.
