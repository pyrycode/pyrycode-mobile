# #234 — feat(ui/settings): Default YOLO toggle persistence

Wires the previously inert "Default YOLO" Switch in `SettingsScreen` through to `AppPreferences.defaultYolo` so the value persists across app restarts. Pure plumbing — no new types, no new files, no new visuals. **First writer of `defaultYolo`** (the schema shipped in [#231](./231.md); until this slice it was write-dead — [#229](./229.md) reads it only to explicitly *ignore* it). Mirrors the [#89](./89.md) `useWallpaperColors` boolean-`Switch` persistence pattern — **not** the [#232](./232.md) / [#233](./233.md) picker-dialog pattern; YOLO is a single bool with no dialog, so the toggle is the fire-and-forget setter wired straight onto `Switch.onCheckedChange` with no confirm step. Fourth/fifth depending on how you count: this is the **fifth** `(StateFlow<X>, fun onToggleX/onSelectX)` pair on `SettingsViewModel` (`themeMode`, `useWallpaperColors`, `defaultModel`, `defaultEffort`, now `defaultYolo`). Split from [#147](https://github.com/pyrycode/pyrycode-mobile/issues/147) ("Defaults for new conversations").

## Summary

- **`SettingsViewModel.kt` extension** — fifth `(StateFlow<X>, fun …)` pair, placed between `defaultEffort` and `archivedDiscussionCount`: `val defaultYolo: StateFlow<Boolean> = appPreferences.defaultYolo.stateIn(viewModelScope, WhileSubscribed(STOP_TIMEOUT_MILLIS), initialValue = false)` (`:50-55`) and `fun onToggleDefaultYolo(enabled: Boolean) { viewModelScope.launch { appPreferences.setDefaultYolo(enabled) } }` (`:84-86`). `initialValue = false` matches `AppPreferences.defaultYolo`'s data-layer default when no value is persisted (#231) — same first-emission-vs-initial-literal alignment the other four flows use. Reuses the existing `STOP_TIMEOUT_MILLIS = 5_000L` companion constant. Structurally identical to the `useWallpaperColors` boolean pair from #89 (both are `StateFlow<Boolean>` + `fun onToggleX(enabled: Boolean)`), distinct from the enum-typed `(StateFlow<Enum>, fun onSelectX)` shape of `defaultModel` / `defaultEffort`.
- **`SettingsScreen.kt` rewiring** — required `defaultYolo: Boolean` parameter inserted after `defaultEffort` (`:58`) and required `onToggleDefaultYolo: (Boolean) -> Unit` inserted after `onSelectDefaultEffort` (`:63`), keeping the signature's state-values-then-callbacks grouping and tracking the Defaults-section row order. The local `var defaultYolo by remember { mutableStateOf(false) }` was **removed** — `pushNotifications` is now the only remaining placeholder-`Switch` local in the body. The Default YOLO row's `Switch` (`:186`) rebinds from `onCheckedChange = { defaultYolo = it }` to `Switch(checked = defaultYolo, onCheckedChange = onToggleDefaultYolo)`. `supporting = "off"` literal is **preserved unchanged** (the dynamic-supporting-text question — showing "on"/"off" reflecting Switch state like the sibling picker rows — is flagged in the spec's Open questions as a candidate follow-up, explicitly out of this ticket's "only the `checked` source and the `onCheckedChange` target change" scope). Both `@Preview` composables pass `defaultYolo = false` (`:346`, `:368`) and `onToggleDefaultYolo = {}` (`:351`, `:373`).
- **`MainActivity.kt` Settings route** — one new collector `val defaultYolo by vm.defaultYolo.collectAsStateWithLifecycle()` (`:226`) next to the other defaults collections, and two new pass-through args into `SettingsScreen(...)`: `defaultYolo = defaultYolo` (`:233`) and `onToggleDefaultYolo = vm::onToggleDefaultYolo` (`:238`). Mirrors the #232/#233 `defaultModel`/`defaultEffort` lines exactly.
- **`SettingsViewModelTest.kt`** — three new `@Test` methods (`:300-339`) mirroring the `useWallpaperColors` trio (not the five-test enum template #232/#233 used — a boolean has no `.entries` boundaries to round-trip, so the effort/model "cover both enum edges" coverage collapses to a single `false → true → false` walk): `defaultYolo_initialState_emitsFalse_whenNoStoredValue` (fresh DataStore), `defaultYolo_initialState_mirrorsPersistedTrue` (pre-write `true` before constructing the VM), and `onToggleDefaultYolo_persistsAndFlowReEmits` (`true` then `false`, asserting both `prefs.defaultYolo.first()` and `vm.defaultYolo.value` on each step — covers AC #4's "persists" + "flow re-emits" clauses in one body). Each reuses the existing `newDataStore()` / `makeVm(prefs)` rig verbatim and launches a no-op collector + `advanceUntilIdle()` before reading `.value` to keep the `WhileSubscribed(5_000L)` upstream subscribed.
- **`SettingsScreenTest.kt` (androidTest)** — all six `setContent { SettingsScreen(...) }` call sites updated to pass the new required params (`defaultYolo = false`, `onToggleDefaultYolo = {}`) **and** #232's still-missing params (`defaultModel = Model.OPUS_4_7`, `onSelectDefaultModel = {}`), plus a new `import de.pyryco.mobile.data.preferences.Model`. ## Patterns established

- **Nothing new in shape** — this is the boolean-`Switch` variant of the #89 persistence pattern, applied a second time. The reusable rule it reinforces: **a persisted boolean Settings row mirrors `useWallpaperColors` (Switch `checked`/`onCheckedChange` straight onto a `(StateFlow<Boolean>, fun onToggleX)` VM pair, no dialog), while a persisted enum Settings row mirrors `themeMode` (#87) / `defaultModel` (#232) / `defaultEffort` (#233) — picker `AlertDialog` + `(StateFlow<Enum>, fun onSelectX)` pair + OK/Cancel confirm.** Pick the variant by the value type, not by which sibling you copy-pasted last. The fire-and-forget `viewModelScope.launch { appPreferences.setX(...) }` and the `WhileSubscribed(5_000L)` projection are identical across both variants.
- **Boolean-pref VM tests collapse the five-test enum template to three.** #232/#233 used a five-`@Test` template (fresh-default, pre-write mirror, two enum-boundary round-trips, one re-emit walk) because an enum has `.entries` edges worth pinning against off-by-one. A boolean has no boundaries, so the right coverage is the #89 trio: fresh-default emits `false`, pre-write `true` mirrors on construction, and one `false ↔ true` walk asserting both persistence and re-emission. **Rule:** match the test template to the value type — three tests for a boolean pref, five for an enum pref.

## Lessons learned

- **The androidTest `setContent` cascade was missed a second consecutive time — code review caught it, and the fix bundled #232's outstanding debt.** Adding required parameters to `SettingsScreen` invalidates all six `setContent { SettingsScreen(...) }` call sites in `SettingsScreenTest.kt` (a separate `androidTest` compilation unit that `./gradlew test` does **not** exercise). The first implementation commit (`8336526`) updated the production wiring, the `@Preview`s, and the unit tests, but not the instrumented test — so `./gradlew compileDebugAndroidTestKotlin` failed with `No value passed for parameter 'defaultYolo'` / `'onToggleDefaultYolo'` at each of the six sites. Code review **FAILED** the PR with two MUST FIX items: (1) thread this ticket's two params through all six blocks, and (2) bundle the fix for #232's `defaultModel` / `onSelectDefaultModel`, which had *also* never been threaded through — so the six sites surfaced both tickets' missing-arg errors together and wouldn't compile until both were resolved. The rework commit `584e561` added all four params + the `Model` import and re-ran `compileDebugAndroidTestKotlin` (now green). This is **exactly the failure [#232](./232.md) § Lessons learned predicted** ("whoever picks up the next slice that touches the `SettingsScreen` signature should add `defaultModel = Model.OPUS_4_7, onSelectDefaultModel = {}` to all six `setContent` blocks") — #234 *was* that next slice, missed it on the first pass, and only caught it via review. The PR body's gate list shows why: `./gradlew test` (run, green) doesn't compile the `androidTest` source set; `compileDebugAndroidTestKotlin` (the only pre-merge task that does) wasn't in the developer's gate list. **Pre-flight checklist when adding a required `SettingsScreen` parameter (now demonstrated three times — #232 missed it, #233 got it, #234 missed it again):** (1) the `SettingsScreen` signature, (2) both `@Preview` blocks, (3) all six `setContent` blocks in `SettingsScreenTest.kt` (androidTest), (4) the `composable(Routes.SETTINGS)` block in `MainActivity.kt`. And run `./gradlew compileDebugAndroidTestKotlin`, not just `./gradlew test`, before opening the PR.
- **Process follow-up flagged by code review (own ticket, not actioned here):** the architecture spec's "Files to read first" lists every `main`/`test` source path but omits the `androidTest` source set — the second time in two weeks the same omission slipped through. Code review suggested either adding "androidTest call sites for any touched composable" to the architect's per-file checklist, and/or wiring `compileDebugAndroidTestKotlin` into `CLAUDE.md`'s pre-PR command list (it currently lists `./gradlew test`, `lint`, `assembleDebug`, `connectedAndroidTest` — but `connectedAndroidTest` needs a device and is skipped in CI/headless, so the *compile* of the instrumented set goes unchecked). **This is a deterministic-safety-net candidate** (a build task that fails the cascade mechanically beats relying on the architect/developer to remember the source set every time) — it belongs in its own ticket; recording here so the trail isn't lost across the #232 → #234 repeat.
- **`defaultYolo` is now write-live but still read-dead.** This slice gives `defaultYolo` its first writer, so the persisted value is real and round-trips. But **no consumer reads it to act on it**: per [#229](./229.md)'s design the StatusSheet does *not* seed per-conversation YOLO from this default (`ThreadViewModel.yoloEnabled` is hardcoded `false`, and `ThreadViewModelTest.kt:375-416` explicitly pins that invariant — code review confirmed no regression). The Settings default exists today purely as a persisted user-intent signal and a hook for the future new-conversation materialiser. **Don't "fix" the apparent dead-end by wiring it into new-conversation creation** — that's a deliberate architectural decision (#229), not an oversight. If a future ticket wants the default to actually drive new conversations, that's a product decision that has to revisit #229's "per-conversation YOLO always starts off" invariant first.

## Sealed-`SettingsState` lift status

This ticket was the named re-evaluation point for the long-deferred "lift the parallel `(StateFlow<X>, fun onSelectX)` pairs into a sealed `SettingsState` / `SettingsEvent` envelope" decision — [#232](./232.md) and [#233](./233.md) § Lessons learned both wrote "the next defaults consumer (YOLO switch row or workspace picker, whichever lands first) is the unambiguous re-evaluation point," and the YOLO switch row landed first. **The lift was not evaluated** — #234's spec scoped it as XS plumbing ("mirror `useWallpaperColors`") and didn't raise the question, so the mechanical-copy pattern continued to a fifth pair. The **workspace picker is now the last remaining defaults slice** and the final natural re-evaluation point before the shape simply settles at five-plus pairs by default. See [`settings-viewmodel.md`](../features/settings-viewmodel.md) § Edge cases for the live threshold note.
