# #313 — `RemoteConversationRepository.observeMessages` via backfill + live `message` stream

Fills the throwing `observeMessages` stub [#312](312.md) left (and [#329](329.md) narrowed) with the
**live v2 thread read**: a conversation's backfilled history (`backfill_since` → `message_chunk`)
merged **ahead of** the live `message` stream into one chronological, `message_id`-deduped
`List<ThreadItem.MessageItem>`, in wire/arrival order. The thread screen now renders real history
across sessions instead of the Fake. Like its siblings it extends the **same** single `init` inbound
collector — a new `message_chunk` demux arm plus the existing `message` arm now **also** appending to
the thread — and adds one cold per-conversation projection. No second `pump.inbound` consumer.

See the evergreen [`remote-conversation-repository.md`](../features/remote-conversation-repository.md)
for the "how the remote repo works / what plugs into it" reference (updated by this slice). This file
is the implementation record. **No new ADR, no new feature doc** — pure `data/`-layer orchestration
extending the #312 class over existing seams; no crypto, no new dependency, no DI/build edit.
**`security-sensitive`** (like #329, unlike the list slice #312): it dispatches message **content** off
the network inbound stream — same trust surface as #329 and the [#317](317.md) decode boundary it reuses.

## Scope

**The thread read path only — one stub replaced in the existing class.** Sized **S**. This slice
**owns**: the `message_chunk` demux arm in `onInbound`, the thread-append on the existing `message`
arm, the `messagesByConversation` projection + the `appendMessages` accumulator, the cold
`observeMessages` fan-out + its `threadProjection`/`backfillSinceRequest` helpers, the two new wire
DTOs, and four companion consts. Out of scope, **by design and confirmed against the server SSOT** —
neither absence is a bug:

- **Session-boundary delimiters → [#336](https://github.com/pyrycode/pyrycode-mobile/issues/336).**
  The v2 wire has no session-transition representation: a `message`/`message_chunk` row is
  `{conversation_id, message_id, role, text}` — no `session_id`, no per-message timestamp, no boundary
  field — and the type catalog has no `session_boundary`. `ThreadItem.SessionBoundary` **cannot be
  constructed mobile-side**; #336 is blocked on a server-side v2 protocol addition. This slice emits
  `MessageItem`s only. See [[phase4-v2-wire-no-session-boundary]].
- **Live token-streaming → [#337](https://github.com/pyrycode/pyrycode-mobile/issues/337).** The wire
  carries no partial / `done` flag; every `message` is *finished* and `message_chunk` is a batch of
  *finished* rows. [#317](317.md)'s `toMessage` hardcodes `isStreaming = false`; an `isStreaming == true`
  value can't be produced without inventing a wire field. #337 is blocked on a server-side v2 streaming
  addition. See [[phase4-v2-wire-no-streaming]].
- **The mutation path** (`sendMessage`/`createDiscussion`/`promote`) — still #314 stubs.

## Summary

**One production file modified (`RemoteConversationRepository.kt`, +122/−5), one wire-model file
modified (`MessagePayload.kt`, +36, two new DTOs), two test files extended — zero new files, zero new
*exported* API, no DI/dependency/gradle change.** `observeMessages`' signature is unchanged from the
stub, so no consumer cascades; the class is still constructed only by the #279/#302 wiring (not yet
live).

The load-bearing facts, all test-pinned (`RemoteConversationRepositoryTest.kt` gains **7** new
`observeMessages` cases; `MessagePayloadTest.kt` gains **3** wire-model cases):

1. **Same single inbound consumer; one `message` arm now feeds two projections.** No new collector or
   scope. The existing `init` collector gains a `TYPE_MESSAGE_CHUNK` arm, and the existing
   `TYPE_MESSAGE` arm (the #329 last-message fold) now **also** calls `appendMessages` — so one inbound
   `message` envelope updates **both** `lastMessages` (preview) **and** `messagesByConversation`
   (thread). New state: `private val messagesByConversation =
   MutableStateFlow<Map<String, List<Message>>>(emptyMap())` (`RemoteConversationRepository.kt:81`),
   written **only** by that one sequential collector.
2. **`message_chunk` arm: decode the whole chunk in one `try`, self-routing by each row's
   `conversation_id`** (`:139-153`). `MobileJson.decodeFromJsonElement<MessageChunkPayloadDto>(payload)`
   then `chunk.messages.map { it.conversationId to it.toMessage(envelope, sessionId = "") }` →
   `appendMessages`. A single bad row (unmappable role → `SerializationException`; bad `ts` →
   `IllegalArgumentException` via `Instant.parse`, the former a subtype) drops the **entire chunk** in
   one `catch (IllegalArgumentException)` → `return`, so the lone collector survives. **No correlation
   map**: the chunk carries each row's own `conversation_id`, so it self-routes; the
   `Envelope.inReplyTo` link to the `backfill_since` request is never read.
3. **`appendMessages(rows)` — one atomic, order-preserving, id-deduped batch fold** (`:171-187`). A
   single `messagesByConversation.update { }` over the whole batch: a first-seen `message_id` is
   appended at the end, a repeat id replaces its row **in place** (`indexOfFirst { it.id == … }`,
   position fixed at first occurrence, last write wins). No-op on an empty batch, so a malformed/empty
   chunk never re-emits. Batching a chunk into one update avoids an intermediate list per row.
4. **`observeMessages` is a cold flow mirroring `observeConversations` exactly** (`:230-235`):
   `flow { pump.send(backfillSinceRequest(id)); emitAll(threadProjection(id)) }`. Replaces the eager
   expression-body `throw` with a real cold flow that defers work to collection (the shape #312's NIT
   asked the owning slices to adopt). Re-sends `backfill_since` on **every** subscription; re-delivered
   history is absorbed by the `message_id` dedup, so **no idempotency guard** is needed. A pre-`Open`
   `send` returns `false` and is dropped — the live stream still fills the thread, and the next
   subscription re-backfills.
5. **`threadProjection(id)` is the per-conversation cold fan-out** (`:243-247`):
   `messagesByConversation.map { it[id].orEmpty().map(ThreadItem::MessageItem) }.distinctUntilChanged()`.
   `distinctUntilChanged()` means a change to **another** conversation's slot does not re-emit this flow
   (AC #3). A `StateFlow` always has a value, so a fresh collector gets the current thread (empty until
   backfill/live arrives) on subscription.
6. **Wire/arrival order, no client-side timestamp sort (AC #1).** A `message_chunk` carries **one**
   envelope `ts` for many rows, so a timestamp sort is impossible *and* wrong. The pump's `inbound` is a
   single ordered stream that cannot skip a frame: the backfill chunk arrives before the live `message`s
   the server emits afterward, so appending in arrival order yields history-then-live naturally. The
   `preservesArrivalOrder_notTimestampSort` test pins this with an earlier-`ts` live message that still
   appends last.
7. **`backfill_since` is encode-only; `backfill_done` is a no-op.** `backfillSinceRequest(id)` (`:222`)
   builds `Envelope(id = requestId.incrementAndGet(), type = "backfill_since", ts = Clock.System.now(),
   payload = BackfillSincePayloadDto(epoch, id, 10_000))` — reusing the **same** `requestId` `AtomicLong`
   as `list_conversations`. `backfill_done` (`{delivered}`) needs no action — the chunk already
   delivered the full history; the count is informational — so it falls through to `else -> Unit`.

## Patterns established

- **One inbound `message` arm can feed multiple projections.** Until #313, each sibling added *one*
  demux arm + *one* projection. #313 is the first to have a single arm (`message`) update **two**
  projections (`lastMessages` for the #329 preview **and** `messagesByConversation` for the thread) —
  the live `message` is simultaneously "the most-recent preview" and "the newest thread row." Keep the
  per-projection folds independent (preview = strictly-greater-by-`timestamp` replace; thread =
  arrival-order append+dedup); they read the **same** decoded DTO but answer different questions.
- **Self-routing batch payloads need no request→conversation correlation.** Because each
  `message_chunk` row carries its own `conversation_id`, the chunk routes itself; the
  `Envelope.inReplyTo` link to `backfill_since` is never consulted. This is simpler than the
  request-id→conversationId map an earlier spec draft proposed and satisfies every AC. Prefer
  self-routing over correlation tracking whenever the response payload is self-describing.
- **Re-send the request on every subscribe; let dedup absorb re-delivery.** `observeMessages` mirrors
  `observeConversations`: re-issue `backfill_since` per subscription, no send-once guard — `message_id`
  dedup makes a re-backfilled thread idempotent, and a dropped pre-`Open` send self-heals on the next
  subscribe. The cold-flow + per-subscribe-request shape is now the canonical read-path idiom on this
  class (`observeConversations`, `observeMessages`).
- **Full history is the epoch, not an absent field.** `backfill_since.since_ts` is a *required*
  RFC-3339 timestamp on the wire (#272), so "all history on first load" is encoded as the Unix epoch
  (`BACKFILL_ALL_HISTORY_SINCE = "1970-01-01T00:00:00Z"`), behind a named const — not a nullable/absent
  cursor. See Lessons.

## Lessons learned

Lifted from the PR's *Lessons learned* section + the code review:

- **`backfill_since`'s wire shape differs from the spec's guess — confirm request payloads against the
  server SSOT before modeling.** The spec flagged the payload as the one unconfirmed wire detail and
  guessed `{conversation_id, since}`. The real shape, confirmed against server SSOT
  [#272](https://github.com/pyrycode/pyrycode/issues/272) `BackfillSincePayload`
  (`internal/protocol/messaging.go`), is **`{since_ts, conversation_id, max_messages}`**: `since_ts` is a
  *required* RFC-3339 timestamp (not a nullable cursor — so "all history" is the epoch), and there is a
  `max_messages` advisory cap with no spec analogue. The server's `ConversationID` is `*string` (nil =
  "all conversations"); modeled **non-null** here because the repo only ever backfills one specific
  conversation (documented on the DTO). `message_chunk` = `{messages: [MessagePayload]}` and
  `backfill_done` = `{delivered}` matched the assumptions. See [[v2-app-payload-shapes-ssot]].
- **`BACKFILL_MAX_MESSAGES = 10_000` is a forward-looking default, not yet exercised against a live
  server.** The backend backfill dispatcher (pyrycode #248) isn't built, so the cap (sized to avoid
  truncating a full thread; the server chunks and may deliver fewer) lives behind a named const to
  revisit at server-integration time. Same posture for the whole backfill path: the round-trip is
  pinned only against the JVM test double until the real dispatcher lands.
- **`appendMessages` dedup is O(n²) over thread size — accepted, deferred (review NIT).** The
  `indexOfFirst { it.id == … }` + `existing + message` per row is quadratic in time and allocation on
  the backfill path; the spec recommended a `LinkedHashMap<messageId, Message>` accumulator for O(1)
  insert/dedup. **Appropriately deferred**, not a blocker: no live backfill yet (`BACKFILL_MAX_MESSAGES`
  unexercised), no observed performance failure, and the simpler list shape matches the project's
  evidence-based-fix posture + the architect's own S2 (unbounded-growth) deferral. **Revisit when
  large-thread backfill goes live** — the swap is internal to `appendMessages`, no API change.
- **Test idiom carried from #312/#329: drive the push→demux→project→emit cascade with `runCurrent()`,
  not `advanceUntilIdle()`** — the `FakeSessionPump`'s `Channel.receiveAsFlow()` inbound feeds a
  `backgroundScope` collector with no timers to elapse, so `advanceUntilIdle()` leaves the buffered
  emission undelivered. See [[remote-repo-test-runcurrent-not-advanceuntilidle]].
