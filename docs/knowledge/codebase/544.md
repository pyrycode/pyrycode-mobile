# #544 — send session-settings changes from the Status sheet, revert on failure

**Issue:** [#544](https://github.com/pyrycode/pyrycode-mobile/issues/544) ·
**Spec:** [`docs/specs/architecture/544-status-sheet-session-settings.md`](../../specs/architecture/544-status-sheet-session-settings.md) ·

**Feature docs:** [Status sheet](../features/status-sheet.md) § Hosting in `ThreadScreen` ·
[Stable conversation repository](../features/stable-conversation-repository.md) § One-shots ·
Size **S**, `security-sensitive` (PASS).

Split from [#536](536.md) (3-way: [#543](543.md) data → **#544 UI/ViewModel** → #545 e2e).

## Summary

Wires the Status sheet's three run-configuration controls (Model / Effort / YOLO) to #543's
`ConversationRepository.setSessionSettings` seam. Before this ticket the three handlers
(`onModelSelected` / `onEffortSelected` / `onYoloToggled`) only wrote `ThreadViewModel`-local
`MutableStateFlow`s — a Tier-3 placebo per the 2026-07-03 backend-gaps audit: the operator believed the
session changed and nothing reached the daemon. Each handler now: no-ops if the tapped value already
matches the displayed one, optimistically moves the control, sends **only the changed field** to
`Conversation.currentSessionId` (the routing key, not the conversation id — the first UI-layer caller of
#543's session-scoped verb), and on failure reverts the control to its captured prior value and fires a
payload-free one-shot signal that `ThreadScreen` renders as the standard transient snackbar. Success is
passive: `set_session_settings`'s ack does not echo the applied settings, so "confirmed" means "the value
that was sent and acked" — the sheet never settles on a value the daemon did not confirm.

## Files touched

- **`app/src/main/java/de/pyryco/mobile/ui/conversations/thread/ThreadViewModel.kt`** (+104, the only
  substantive file):
  - `ThreadUiState.currentSessionId: String = ""` — a new routing field, sourced from `conv?.currentSessionId`
    in the existing `state` combine (mirrors how `mutationsSupported` rides the state for gating, not
    display). Empty until the conversation resolves; also empty on the live path today (see § Lessons /
    pre-existing gap below), never in tests (the Fake populates it).
  - `sessionSettingsErrorChannel: Channel<Unit>` / `sessionSettingsErrors: Flow<Unit>` — cloned verbatim
    from `changeWorkspaceErrors` ([#561](561.md)): payload-free so nothing daemon-derived, least of all
    `RelayErrorException.message`, can ride the signal to the snackbar surface.
  - `sendSessionSettings(model, effort, yolo, revert)` — the one shared private send helper. Reads
    `state.value.currentSessionId` at entry, launches on `viewModelScope`, and clones
    `sendChangeWorkspace`'s catch triad with `revert()` added to the two failure arms:
    `catch (CancellationException) { throw e }` **first** (JVM: `CancellationException extends
    IllegalStateException`, so ordering is load-bearing — see [[catch-illegalstate-swallows-cancellation]]),
    then `catch (RelayErrorException) { revert(); signal }`, then `catch (IllegalStateException) { revert();
    signal }`. `IllegalArgumentException` / decode exceptions are **not** caught — a malformed ack is a
    fail-loud protocol violation, parity with `sendArchive`/`sendChangeWorkspace`.
  - `onModelSelected` / `onEffortSelected` / `onYoloToggled` — signatures unchanged. Each: no-op guard →
    capture the **previous nullable override** (not the resolved `Model`/`Effort`, so a revert restores the
    pre-existing "null = track the app-preferences default" semantics) → optimistic set → `sendSessionSettings`
    with a revert lambda restoring the capture.
  - File-private `Effort.wire(): String = name.lowercase()` (exact daemon `validEffort` vocabulary) and
    `Model.wire(): String` (explicit `when` mapping to version-pinned canonical claude ids
    `claude-opus-4-7` / `claude-sonnet-4-6` / `claude-haiku-4-5`). Kept file-private, not promoted to
    `Model.kt`/`Effort.kt`, to hold the ticket's production file count at four.
- **`app/src/main/java/de/pyryco/mobile/ui/conversations/thread/ThreadScreen.kt`** (+9) — a fifth
  `sessionSettingsErrors: Flow<Unit> = emptyFlow()` param plus a `LaunchedEffect` collecting it into
  `snackbarHostState.showSnackbar(sessionSettingsFailedMessage)`, identical shape to the four pre-existing
  one-shot-error blocks. The fixed local string (`R.string.session_settings_failed`) is what keeps the
  server-supplied error text out of the (un-secured) Activity window.
- **`app/src/main/java/de/pyryco/mobile/data/repository/StableConversationRepository.kt`** (+7) — the
  one-line facade delegation `#543` deliberately deferred: `override suspend fun setSessionSettings(...) =
  live.setSessionSettings(...)`. `live` throws `IllegalStateException` when no connection is live, which is

- **`app/src/main/java/de/pyryco/mobile/MainActivity.kt`** (+1) — `sessionSettingsErrors = vm.sessionSettingsErrors`

## Design decisions worth flagging

- **`currentSessionId`, not `conversationId`, is the routing key.** Every prior mutation on this VM
  (`sendMessage`, `sendArchive`, `sendChangeWorkspace`, `sendRename`) routes by conversation id;
  `setSessionSettings` is the first UI-layer call to route by session id — following the precedent #543
  established on the repository side.
- **Where the revert is observed differs by control**, driven by pre-existing `ThreadScreen` behaviour, not
  new code: selecting a Model or Effort closes the sheet (`sheetVisible = false` in the `ThreadScreen`
  callback wrapper), so that revert is observed **on reopen**; the YOLO switch keeps the sheet open, so its
  revert is observed **live** — the switch visibly flips back. This made YOLO the natural control for the
  revert unit tests (no sheet-visibility state to route around).
- **No generation token / sequencing guard against rapid same-control re-changes.** A second tap on the
  same control before the first send resolves could let a stale revert clobber a fresher optimistic value.
  Accepted as evidence-based non-fix: Model/Effort's sheet-close-on-select makes a second change require
  reopening (by which time the first send has resolved); YOLO's window is real but self-correcting on the
  next successful change or reopen. No observed failure, so no defensive sequencing was added.

## Testing strategy

Six new `ThreadViewModelTest.kt` scenarios (`runTest`), covering every AC without a Compose test:

- **Send-on-change** (one per control) — asserts the Fake's `setSessionSettingsCalls` holds exactly one
  entry with only the changed field non-null and `sessionId == currentSessionId`; the optimistic value
  persists after settling (no revert on the happy path).
- **No-op guard** — re-selecting the already-displayed `Model` sends nothing.
- **Revert on server error** (`onModelSelected`, injecting `RelayErrorException`) — control reverts, exactly
  one `sessionSettingsErrors` emission, and (via a swapped `Thread.setDefaultUncaughtExceptionHandler`) the
  throw is proven **caught**, not leaked into `viewModelScope`'s `SupervisorJob`.
- **Revert on disconnected** (`onYoloToggled`, injecting `IllegalStateException`) — same assertions, over
  the other control, satisfying AC #5's "at least one control" across both failure modes.
- **Cancellation is inert** — a `setSessionSettings` that suspends on a never-completing `CompletableDeferred`,
  then `ViewModelStore.clear()` mid-send: **zero** `sessionSettingsErrors` emissions, proving the
  `CancellationException`-first catch ordering actually holds (a bare `catch (IllegalStateException)` would
  false-fire here, per [[catch-illegalstate-swallows-cancellation]]).

## Lessons learned

- **The shared `ThrowingConversationRepository` test double does not cover `setSessionSettings`.** It
  delegates that method to a real `FakeConversationRepository` (which records and always succeeds), so the
  revert-on-error / revert-on-disconnected tests each construct an inline
  `object : ConversationRepository by FakeConversationRepository() { override suspend fun
  setSessionSettings(...) = throw ... }` instead. Worth checking first for any future session-scoped
  mutation ticket that wants an error-injecting double.
- **Pre-existing gap, not introduced or fixed here:** both v2 conversation DTO mappers
  (`ConversationsPayload.kt`, `ConversationResponseDto.kt`) hardcode `currentSessionId = ""` — the v2 wire
  carries no session id. Against the live daemon a settings send therefore currently routes to an empty
  session id, which the daemon rejects as `session.not_found` → the fail-safe revert + snackbar path (never
  a crash). Every unit test passes because `FakeConversationRepository` populates the field. Resolving the
  live-path session id is out of scope here and orthogonal to this ticket's wiring — flagged for whoever
  picks up #545 (which may need to be `@Ignore`-manual, since a settings ack leaves no durable UI artifact
  to assert against in the emulator harness).
