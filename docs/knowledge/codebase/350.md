# #350 — flag-gated Fake↔Remote `ConversationRepository` binding swap

Adds the build-time flag that selects which implementation wins the `ConversationRepository` binding:
the existing [`FakeConversationRepository`](../features/conversation-repository.md) (the default —
previews, tests, unchanged behaviour) or the already-constructible relay-backed
[`StableConversationRepository`](../features/stable-conversation-repository.md) facade ([#352](352.md)).
The flag defaults **OFF** (Fake), so this slice is safe to land before the relay backend is functional
end-to-end. No new repository wiring — only a binding selector.

This is the **last piece of the #279 lineage**: #279 → #349 (wiring) + #350 (this swap); #349 → #351
(connection-scoped coordinator) + #352 (stable facade). The coordinator already publishes a live
`RemoteConversationRepository` per connection and the facade already wraps it as a process-lifetime
singleton — both were registered but **bound to nothing**. This slice gives the interface a flag-selected
binding. The original "swap `FakeConnectionStateSource`" half of #279 was already done by #307
(`RelayConnectionSupervisor` is the real, bound `ConnectionStateSource`), so `ConversationRepository` was
the only binding still needing a fake/real choice.

## Design — a dedicated selector module, not a `bind` on the facade

Two prior docs ([`stable-conversation-repository.md`](../features/stable-conversation-repository.md),
[`remote-conversation-repository.md`](../features/remote-conversation-repository.md)) anticipated #350 as
*"add `bind ConversationRepository::class` to the facade `single` and rewire the ViewModels."* **It
shipped differently — and more cleanly:**

1. **The flag** — `buildConfigField("boolean", "USE_RELAY_REPOSITORY", "false")` in
   `app/build.gradle.kts` `defaultConfig`, beside the existing `GIT_SHA` field. Generates
   `BuildConfig.USE_RELAY_REPOSITORY: Boolean = false`. `buildConfig = true` is already enabled, so no
   `buildFeatures` change.
2. **The selector module** — a new top-level `fun conversationRepositoryModule(useRelay: Boolean =
   BuildConfig.USE_RELAY_REPOSITORY): Module` in `AppModule.kt` (same file, no new production file) that
   binds `single<ConversationRepository> { if (useRelay) get<StableConversationRepository>() else
   get<FakeConversationRepository>() }`. The selector **resolves** the two already-registered concrete
   singletons by type — it never constructs either, so it carries none of their dependency weight and
   opens no connection.
3. **`appModule` registers both candidates concrete-only.** The `bind ConversationRepository::class` was
   dropped from the Fake's `single`; after this slice **`appModule` binds the interface nowhere** — the
   selector is the single, sole definition that binds it (no duplicate-definition / `DefinitionOverride`
   risk).
4. **`PyryApp` loads both:** `modules(appModule, conversationRepositoryModule())`. Module load order is
   irrelevant — the selector's `get<…>()` is lazy and resolves the concrete singletons from `appModule`
   cross-module.

**No ViewModel was touched.** Every consumer keeps resolving the `ConversationRepository` *interface*;
only what answers it changes. The "rewire the ViewModels" the sibling docs predicted was never necessary —
they already injected the interface, so swapping the binding is invisible to them.

## Why this mechanism

- **`buildConfigField` boolean over a build flavor / build type / DataStore setting** — minimal seam
  (one line), follows the existing `GIT_SHA` precedent, no new variant matrix. It is a **compile-time
  constant baked into the binary** with no runtime setter, no settings UI, no persisted key. This is
  exactly the "flag is not settable by any untrusted input" property the ticket required, satisfied
  *structurally* — a DataStore-backed user toggle was the obvious alternative and was rejected precisely
  because it would create a runtime trust boundary letting a confused/hostile setting flip the backend.
- **Separate module, not folded into a parameterized `appModule`** — so the binding is unit-testable via
  real Koin resolution **without** dragging in `appModule`'s Android-bound graph (`appModule` eagerly
  wires `LifecycleConnectionDriver` needing `ProcessLifecycleOwner` and the keystore/Noise chain needing
  `androidContext()` + `Build.MODEL`, forcing Robolectric/instrumented). Isolating the selector lets a
  plain JVM test load only `conversationRepositoryModule(…)` + a tiny stub-deps module and assert the
  resolved type. The minimal seam that makes the AC a fast unit test, not over-engineering.

## Patterns established

- **Flag-gated binding selector as its own Koin module.** When a binding needs a build/test-time
  fake↔real choice, isolate it in a dedicated `fun fooModule(useX: Boolean = BuildConfig.USE_X): Module`
  that **resolves** the already-registered concrete candidates by type (`get<…>()`) rather than
  constructing them — keep `appModule` registering every candidate *concrete-only* and let exactly one
  module bind the interface. This avoids the duplicate-definition collision, isolates the risky flip into
  one tiny testable unit, and lets a plain JVM test load only the selector + stubs (no Android graph).
  This is the **Koin-module swap** CLAUDE.md's "Don't special-case the fake in the UI" rule mandates —
  the swap is architectural, not a UI conditional. Pairs with #352's *register-now-bind-later* pattern
  (that slice registered the facade; this slice supplies the flag-gated binding).
- **Force-fake via the module parameter, not Koin override semantics.** Tests and `@Preview`s that need
  fake mode regardless of the build flag construct their graph with `conversationRepositoryModule(useRelay
  = false)` — pinning the Fake without depending on Koin's later-module-wins override behaviour. This is
  the preferred force-fake mechanism (AC #4).
- **Default-param-tracks-build-flag + a tripwire test.** The selector's `useRelay` defaults to
  `BuildConfig.USE_RELAY_REPOSITORY`, and a unit test asserts that default is `false` *and* binds the
  Fake. If anyone flips the `buildConfigField` literal to `"true"`, that test goes red **on purpose** —
  turning the flag on for real use must be a deliberate, reviewed change, not a silent default flip.
- **A compile-time `buildConfigField` constant is a security control for free.** "Not settable by
  untrusted input" needs no enforcement code when the flag is a baked-in constant with no runtime setter
  — no QR payload, deep link, intent extra, push body, or DataStore key can reach it. Prefer this shape
  over a persisted/user-settable toggle whenever a flag selects a trust-relevant target (here: which
  backend the app talks to).

## Lessons learned

- **ktlint (spotless 1.5.0) collapses a single-parameter function signature onto one line.** The selector
  was first written multi-line (`fun conversationRepositoryModule(\n    useRelay: …,\n): Module`) and
  `spotlessCheck` flagged it — a single parameter with a default value belongs on one line. This is a
  *formatting* rule distinct from [[ktlint-filename-rule-single-class]] (which polices single-public-type
  filenames); `spotlessApply` fixes this one automatically, unlike the filename rule.
- **#350 shipped differently than the sibling feature docs predicted, and the prediction was the weaker
  design.** [`stable-conversation-repository.md`](../features/stable-conversation-repository.md) and
  [`remote-conversation-repository.md`](../features/remote-conversation-repository.md) framed #350 as
  *"add `bind` to the facade `single` + rewire the ViewModels."* The dedicated-selector-module approach is
  cleaner: it keeps the binding unit-testable in isolation and needs **zero** ViewModel changes (they
  already resolve the interface). When a downstream slice's shape is sketched by an upstream doc, treat it
  as a hypothesis, not a spec — the better mechanism may only be obvious once the surrounding code exists.
  (Those docs were updated by this ticket to match what landed.)

## Out of scope (named)

- **Flipping the flag ON for real use, and any live-network verification.** That production flip
  additionally depends on the v2 mutations (#346/#347/#348) and the two server-side gaps #336 (session
  boundaries) and #337 (streaming).
- **The ViewModel error surface.** The facade throws `IllegalStateException` (not connected) /
  `RelayErrorException` on the live mutations; the UI call sites (`ThreadViewModel.sendMessage`,
  `DiscussionListViewModel.confirmPromotion`) are still fire-and-forget with no `try/catch`. This is
  harmless while the flag is OFF (the Fake never throws those) — widening the ViewModel error handling
  belongs to the production flip, **not** this binding-only slice. #350 touches no ViewModel.
