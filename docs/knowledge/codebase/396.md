# Ticket #396 — surface the screen-snapshot action prominently on a stall

**Issue:** [#396](https://github.com/pyrycode/pyrycode-mobile/issues/396) ·
**Spec:** [`docs/specs/architecture/396-stall-promotion-snapshot-cta.md`](../../specs/architecture/396-stall-promotion-snapshot-cta.md) ·
**PR:** [#415](https://github.com/pyrycode/pyrycode-mobile/pull/415) ·
**Feature doc:** [Stall promotion banner](../features/stall-promotion-banner.md) ·
Split from #373 (the UI-reaction slice; the data slice is the merged sibling [#395](395.md), which this
consumes). Size **S**, **not** `security-sensitive` (the untrusted parse lives entirely in #395; this
slice surfaces a single `Boolean`).

## Summary

The **visible reaction** to a stall. [#395](395.md) reduced the inbound `stall` envelope to a
thread-observable [`observeStall(conversationId): Flow<Boolean>`](../features/stall-state.md); this slice
renders it. While the active conversation is stalled, a new stateless
[`StallPromotionBanner`](../features/stall-promotion-banner.md) is rendered **below**
[`ConnectionBanner`](../features/connection-banner.md) in the thread content `Column`, raising the
always-available screen-snapshot action (pyrycode ADR-025 § Safe degradation) to a prominent CTA so it
reads as the recommended next step instead of leaving the user staring at silence. Tapping it triggers
the **same** already-shipped `onShowLiteralScreen` navigation (#382) — **no new event, no new data
path** (AC #4). The promotion clears the instant the stall resolves (AC #3). `isStalled` is exposed as a
sibling `StateFlow<Boolean>` on `ThreadViewModel` (matching `connectionState` / `isThinking`), sourced
from the **already-injected** `repository.observeStall` — **no constructor, DI, or interface change**.
Code review **PASS**, zero blocking findings.

## Load-bearing design choices

- **Sibling `StateFlow`, not a `ThreadUiState` field (deliberate deviation from the ticket's Technical
  Note).** The ticket said "hoist the stall flag into the thread `UiState`"; the spec instead exposes it
  as a sibling `StateFlow<Boolean>` beside `connectionState` / `isThinking`. Rationale: a stall is the
  **same signal class** as `isThinking` (transient, connection-scoped, conversation-routed, live-derived
  cross-cutting signal driving one piece of UI prominence) — putting stall in `UiState` while
  `isThinking` sits beside it as a sibling would be internally inconsistent. It also keeps the `state`
  `combine` at its 5-arg typed maximum (a 6th source would force a vararg-`combine` or a re-grouping
  refactor). The ACs are behavioural about the *screen*, not about where the flag lives, so compliance
  is unaffected. Code review explicitly endorsed this as the correct call.
- **Banner placement below `ConnectionBanner`, outside the `LazyColumn`.** A persistent top banner is
  the most prominent surface and the direct analogue of `ConnectionBanner` (connection-degraded → top
  banner; parse-degraded/stalled → top banner). Being outside the scrolling list, it stays pinned while
  the stall holds rather than scrolling away. Contrast the sibling
  [`ThinkingIndicator`](../features/thinking-indicator.md) (#407), which sits at the **foot** of the
  content `Column` — a stall promotion is a "do this now" CTA (top), thinking is an at-work status
  (foot).
- **Same callback, no new data path (AC #4).** The banner's `onClick` is the identical
  `onShowLiteralScreen` the overflow "Show the literal screen" item (#382) calls — the test asserts a
  single invocation of that same lambda, proving no new `ThreadEvent` and no new repository surface.
- **No coordination with `ThinkingIndicator`.** A stall and `thinking` are in practice mutually
  exclusive (a `turn_state` event clears the stall, and `isThinking` *is* a `turn_state` phase), so both
  flags being `true` at once is not expected and no either/or logic is specified. Flagged so the absence
  of coordination isn't read as a gap; an explicit either/or is a design follow-up.

## Patterns established

Nothing genuinely new — this slice **follows** established precedents: the `ConnectionBanner` /
`ThinkingIndicator` early-return show/hide idiom, the sibling-`StateFlow` shape `connectionState` /
`isThinking` already use, the defaulted-hoisted-boolean threading through `ThreadScreen`, the
`collectAsStateWithLifecycle()` at the `MainActivity` call site, file-private spacing `val`s, and the
`cd_*` content-description convention. The one point worth carrying forward: **a clickable banner can
anchor a single `semantics(mergeDescendants = true) { contentDescription = … }` on its `Surface`, which
lets a Compose test assert both visibility (`onNodeWithContentDescription`) and the tap (`performClick`)
on one node** — the `ThinkingIndicatorTest` merged-semantics idiom extended to a clickable surface.

## Lessons learned

- **A clickable M3 banner only needs the one merged-`semantics` content-description anchor for testing.**
  Putting `semantics(mergeDescendants = true) { contentDescription = … }` on the clickable `Surface`
  collapses the explanatory `Text` + the CTA `Text` into a single accessible node that is also the click
  target, so `onNodeWithContentDescription(…).assertIsDisplayed()` and `.performClick()` both resolve
  against it. (Lifted from the [PR #415](https://github.com/pyrycode/pyrycode-mobile/pull/415) *Lessons
  learned*.)
