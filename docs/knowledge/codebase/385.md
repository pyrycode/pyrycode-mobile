# Ticket #385 — decode v2 structured live-session stream envelopes

**Issue:** [#385](https://github.com/pyrycode/pyrycode-mobile/issues/385) ·
**Spec:** [`docs/specs/architecture/385-decode-structured-live-session-stream.md`](../../specs/architecture/385-decode-structured-live-session-stream.md) ·
**PR:** [#404](https://github.com/pyrycode/pyrycode-mobile/pull/404) ·
**Feature doc:** [Live-session events](../features/live-session-events.md) ·
Split from #368. Size **S**, `security-sensitive`.

## Summary

Decodes the five v2 **binary → phone** structured-stream envelopes — `turn_state`,
`assistant_delta`, `tool_use`, `tool_result`, `turn_end` — into one typed `LiveSessionEvent`
family, surfaced as a hot `SharedFlow` on the **concrete** `RemoteConversationRepository`, gated on
the negotiated `interactive` capability (#401). **Decode seam only**: no `tool_use`↔`tool_result`
correlation, no `assistant_delta` accumulation, no turn-lifecycle state machine, no rendering —
those belong to the consumer slices ([#386] thinking indicator, [#387] tool timeline, [#337] live
assistant text, all now unblocked). Follows the established v2 decode-slice pattern
([#316](316.md)/[#317](317.md)/[#318](318.md)/[#374](374.md)). Built test-first, RED→GREEN; all
gates green (`test`/`lint`/`assembleDebug`/`spotlessCheck`).

## Load-bearing design choices

- **The gate is a lazy supplier, not a captured value.** `negotiatedCapabilities: () ->
  Set<String>` is read **per structured envelope**, not snapshotted at construction. The repo is
  built while the pump is still `Handshaking` (capability set empty), but structured envelopes only
  arrive **post-`Open`**, by which point the negotiated set is connection-constant — so the lazy
  read always sees the final set. A value captured at construction would be empty forever. The
  supplier reads `pump.state.value` — a **non-suspending** `StateFlow.value` read — so the
  coordinator's `onConnection` cancellation-atomicity invariant (no suspension point in the
  non-suspending critical section) is preserved. (Lifted verbatim from the PR's *Lessons learned*.)
- **Gate evaluated _before_ decode** (`if (CAPABILITY_INTERACTIVE in negotiatedCapabilities())`): a
  non-`interactive` phone never even decodes the payload. Defense-in-depth — even a buggy/hostile
  daemon that ignores the negotiated set and pushes structured events to a non-`interactive` phone
  has them ignored (AC#2).
- **`SharedFlow`, not `StateFlow`** (`replay = 0`, `extraBufferCapacity = 64`, `onBufferOverflow =
  DROP_OLDEST`): these are *events*, not current-value state, so late subscribers get no history
  (holding "latest" is a consumer projection concern). The bounded buffer + `DROP_OLDEST` make
  `tryEmit` **infallible and non-blocking** — the load-bearing invariant is that a slow live-event
  consumer must **never** back-pressure the single shared `pump.inbound` collector and stall the
  connection's `conversations`/`message`/`ack` processing. Delivery is therefore best-effort under
  extreme backpressure; a consumer needing lossless accumulation ([#337]) owns its own buffering.
- **`turn_state.state` is a `String` in the DTO, mapped in `toEvent()`** — not a strict enum.
  `WireRole`'s strict-enum approach would make an unrecognized `state` a *decode* failure,
  conflating "unknown state" with "malformed envelope". Instead `TurnStatePayloadDto.toEvent():
  LiveSessionEvent?` returns `null` for an unrecognized `state` (via a private `String.toPhase()`),
  the demux drops that one envelope, the stream survives (AC#3). An **absent** `state` is the other
  path: the required field makes *decode* throw → also dropped (AC#4). Both converge on
  drop-without-crash — and there is deliberately **no `Phase.Unknown`** member to push an
  interpretation decision onto consumers.
- **One `try/catch (IllegalArgumentException)`** wraps the whole `decodeLiveSessionEvent` body.
  `SerializationException ⊂ IllegalArgumentException`, so a malformed/partially-decodable payload
  (missing or wrong-typed field) yields `null` → the one envelope is dropped, the lone inbound
  collector survives, the next envelope is processed normally ("one bad envelope does not drop the
  next", AC#4). Mirrors the existing `TYPE_MESSAGE` drop idiom.
- **Flow on the concrete repo, not the `ConversationRepository` interface.** Adding it to the
  interface would force `FakeConversationRepository` to implement it and `StableConversationRepository`
  to delegate it (+2 prod files → 6 total → trips the ≥5 split gate). This is the exact accepted
  `registerPushToken` ([#359](359.md)) pattern: a non-interface capability on the concrete repo,
  reached by the consumer through a concrete handle. Facade/coordinator reachability for the UI
  consumers is downstream consumer-slice work (see [[post-352-connection-scoped-repo-behind-facade]]).

## Patterns established

- **Decode-slice with a value-mapped enum field uses a nullable mapper, not a strict serialized
  enum.** When the wire field has a closed value set the seam must map but AC requires tolerating
  unknown/absent values, keep the DTO field a `String` and do the value→enum mapping in `toEvent()`,
  returning nullable so the unmappable case drops one envelope instead of failing the whole decode.
  Contrast `WireRole` (strict, throws at decode — correct when an unknown value *is* a protocol
  error). This is the first decode slice to need the distinction.
- **A connection-state gate that must be read after construction is threaded as a `() -> T`
  supplier** (defaulted so existing constructions compile), reading a non-suspending `StateFlow.value`
  — not captured eagerly, not an added suspension point in the coordinator's critical section.

## Lessons learned

- **Don't capture connection-negotiated state at repository construction time.** The construction
  happens during `Handshaking`; anything negotiated in the handshake (capabilities, here) isn't
  populated yet and a captured snapshot stays empty forever. Read it lazily at the point of use
  (`pump.state.value` per envelope) — which is sound precisely because the data this gate guards
  (structured envelopes) can only arrive **after** the state it reads has stabilized. The same shape
  would apply to any future per-envelope gate that depends on handshake-negotiated state.

  findings (MUST/SHOULD/NIT). Reviewer cross-checked every DTO `@SerialName` and type against the
  server SSOT (`pyrycode docs/protocol-mobile.md § Interactive events (v2, capability-gated)`,
  pyrycode#607) — all five match exactly. The envelope-level `event_id` (replay cursor, #402) and
