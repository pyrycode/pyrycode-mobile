# #347 — `RemoteConversationRepository.createDiscussion` over v2 (`create_conversation`)

Fills the `createDiscussion` stub on the already-merged [`RemoteConversationRepository`](../features/remote-conversation-repository.md)
with a live [Mobile Protocol v2](../features/mobile-protocol-v2-wire-layer.md) round-trip: encode a
`create_conversation` request, correlate its **typed `conversation_created` reply** through the class's
**single** `init` inbound collector, **decode** that reply into the returned `Conversation`, and
**confirmed-insert** it into the list projection only after the decode succeeds. This is the **second
mutation method** to land (after [#346](346.md) `sendMessage`); it **reuses** #346's `sendAndAwaitReply`
correlation primitive and [#318](318.md)'s `ConversationResponseDto.toConversation()` decode mapper, and
adds **one new** `create_conversation` request encoder. The sibling #348 (`promote`) lands next on the
same class.

See the feature doc [`remote-conversation-repository.md`](../features/remote-conversation-repository.md)
§ "`createDiscussion`" for the evergreen reference; this file is the implementation record.

## The central design contrast with #346 (load-bearing)

`send_message`'s reply is an empty **`ack`**, so #346 *reconstructs* its return `Message` from the
input. `create_conversation`'s reply is a **typed `conversation_created` payload** carrying the
**server-assigned** `id` and `cwd`, so this slice *decodes* its return `Conversation` from the reply —
it cannot reconstruct it (the client does not pick the id, and a null `workspace` means the server picks
the scratch `cwd`). The reply still rides the **same** correlation primitive: `sendAndAwaitReply` hands
the raw reply `JsonElement` back to the caller, which then decodes it. The only `onInbound` change is
routing `conversation_created` into the completion path — it previously fell through to `else -> Unit`.

## Summary

One production class touched (`RemoteConversationRepository`) plus one new encode-only request DTO under
`data/network/`. Mirrors the #346 `sendMessage` slice; the response mapper (#318) and correlation
primitive (#346) are **reused, not built**.

- **`data/network/`** — `CreateConversationPayloadDto` (encode-only `create_conversation` request DTO,

## Patterns established

- **Confirmed-insert via an upsert-by-id CAS fold (`upsertConversation`).** The returned `Conversation`
  is folded into the list `projection` **only after** both `sendAndAwaitReply` *and* the reply decode
  succeed — so every failure path throws before the fold and the list never shows a conversation the
  server did not create (the security property, by construction; the #346 confirmed-insert pattern
  applied to the conversation list). The fold is **upsert by `id`** (not blind append), so it's
  idempotent against a re-delivered create and retry-merges with a concurrent authoritative
  `conversations` snapshot rather than clobbering it. Because #316 and #318 fill the **same** four
  list-tier placeholders (`currentSessionId=""`, `sessionHistory=emptyList()`, `isSleeping=false`,
  `archived=false`), the folded `Conversation` is field-equal to the one a later snapshot maps, so
  `StateFlow` conflation suppresses a redundant re-emit. **#348 (`promote`) inherits this** — it folds
  an *updated* `Conversation` the same way; it either reuses `upsertConversation` or extracts a shared
  helper then (the second call site is the evidence — do not generalize ahead of it).
- **Typed correlated reply rides the shared `ack` arm; decode in the caller, not the collector.** A
  `conversation_created` is a correlated success reply with the *same completion shape* as an `ack`, only
  with a non-empty payload — so it shares the one `when` branch (`complete(envelope.payload)`). The
  decode (`decodeFromJsonElement<ConversationResponseDto>`) happens in the **caller's** coroutine after
  `sendAndAwaitReply` returns, so a malformed `conversation_created` throws the #318 decode exception in
  the caller — **never** inside the single inbound collector (which would freeze all updates). This is
  the template for any future typed correlated reply (#348's `conversation_updated`).
- **`name` is unmodeled on the create request — encode only what is sent.** Discussions are
  **server-auto-named** (CLAUDE.md), so the create flow never sends a `name`; the DTO models only the
  two fields it sends (`is_promoted` always `false`, optional `cwd`), with KDoc forbidding "add `name`
  for completeness". User-naming is the separate `promote_conversation` flow (#348). This is the #346 /
  `BackfillSincePayloadDto` encode-only-DTO discipline: an encode-only request DTO models the *request*,
  not the full decode surface (#318's job). See [[phase4-request-encoders-live-in-mutation-tickets]].

## Lessons learned

The PR ([#355](https://github.com/pyrycode/pyrycode-mobile/pull/355)) carried no *Lessons learned*
section; the non-obvious points worth recording:

- **A null `workspace` is a null `cwd` is an *omitted* `cwd` key — and that is wire-correct, not a bug.**
  Under `MobileJson` (`explicitNulls = false`), `createDiscussion(null)` encodes to `{"is_promoted":false}`
  with **no** `cwd` key (not `"cwd":null`). The server's `CreateConversationPayload.Cwd` is `*string`
  **without** `omitempty`, and Go's `encoding/json` decodes an absent key identically to explicit `null`
  (both leave the pointer nil), so the omitted key means "server assigns the scratch cwd" (#274 sanctions
  filling server-side defaults when the field is absent). Do **not** force an explicit `"cwd":null` — it
  would need a per-call `Json` config and buys nothing. The returned `cwd` is the **server's** reply
  value, asserted as `DEFAULT_SCRATCH_CWD` (the constant, not the literal), never the input arg — this is
  the AC #1 crux and has a dedicated test.
- **`sendAndAwaitReply` is reused verbatim — the typed-vs-bare reply difference is entirely in the
  caller.** The registry is typed `<JsonElement>` precisely so #346's bare-`ack` caller ignores the
  payload while this slice decodes it. No change to the primitive, the registry, or `mapError` was
  needed — only a new success-`type` in the `when` arm and a decode in the caller. This validates the
  #346 "the registry serves both bare and typed callers" design.

- The nine new tests map to the ACs: request shape for null workspace (`{"is_promoted":false}`, no `cwd`
  key — AC #1/#4) and explicit workspace (`{"is_promoted":false,"cwd":"/work/proj"}` — AC #1/#4);
  created-reply → unpromoted `Conversation` with the **server's** `cwd` (AC #1); `observeConversations`
  re-emit in both the `All` and `Discussions` tiers (AC #2); server `error` →
  `RelayErrorException(code)` with the list unchanged (AC #3); not-`Open` (`sendResult = false`) →
  `IllegalStateException` with the list unchanged (AC #3/#4); malformed `conversation_created` (omitted
  `cwd`) → the #318 decode exception (a `SerializationException`, an `IllegalArgumentException` subtype)
  with the list unchanged; and correlation hygiene (an uncorrelated `conversation_created` is a no-op and
  a later real create still round-trips). Driven with the `runCurrent()` (not `advanceUntilIdle()`)
  idiom — see [[remote-repo-test-runcurrent-not-advanceuntilidle]].
- **Pure `data/`-layer slice** — no instrumented test, no `ComposeTestRule`; zero `android.*` imports.
  See [[data-layer-android-import-exception]].

  The reviewer verified all four ACs, the `toConversation()` call binds unambiguously to #318's public

  opened/resolved).

### One pre-existing NIT (no action — flagged for the record)

`observeConversations` has **no `distinctUntilChanged`**, so a confirmed-insert of a *discussion* mutates
`projection` and triggers a value-equal re-emit to `Channels`-filtered collectors (the new row is
filtered out, so the projected list is unchanged). Harmless — absorbed downstream by `stateIn` / Compose
structural equality — and **pre-existing** (not introduced by this slice). Adding `distinctUntilChanged`
would be an out-of-scope touch (Simplicity First), so it was not made.

## Open hand-offs (carried, not introduced)

- **Connection-drop-mid-create leak.** The same single-entry `pendingRequests` leak [#346](346.md)
  documented: if the connection scope is cancelled while a caller awaits, the deferred never completes
  until the *caller* is cancelled (the ViewModel scope on screen exit → `CancellationException`). No
  timeout added (no observed hang; a timeout value is a product call). A future slice or the connection
  coordinator ([#302](302.md) / [#351](351.md)) may fail all `pendingRequests` on disconnect. Flagged,
  not fixed (Evidence-Based Fix Selection).
- **Unsolicited single-row `conversation_created`/`conversation_updated` *pushes* are still no-ops.**
  This slice routes a `conversation_created` that **correlates** to a pending create-request into the
  completion path; a server-initiated single-row delta (no `inReplyTo` match) still falls through to a
  no-op and the list refreshes on the next `conversations` snapshot. Merging unsolicited deltas into the
  live projection remains future work.
