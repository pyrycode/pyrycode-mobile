# #142 — feat(ui/dialogs): Save as channel dialog (Figma 19:24)

Replaces the `Unit` no-op on the `ThreadEvent.SaveAsChannel` branch of `ThreadViewModel.onOverflowEvent` (introduced by [#204](./204.md)) with the full promote-from-thread flow: a Material 3 `AlertDialog` (`SaveAsChannelDialog`) collecting a channel name (pre-filled with the stub auto-suggested title `"New channel"`) and a binary workspace choice (dedicated channel folder vs. keep in scratch), then calling `repository.promote(conversationId, name, workspace)` on Save with `workspace = "pyry-workspace/channels/<slug>"` (slug derived from the name) for the dedicated radio and `workspace = null` (preserve the discussion's existing `cwd`) for the scratch radio. Second per-item follow-up of the four `[NewSession, ChangeWorkspace, ChannelInfo, SaveAsChannel]` cases left as exhaustive `Unit` arms by [#204](./204.md); structurally parallel to [#141](./141.md)'s rename slice but with three substantive deviations (radio rows, single-gate `isSaveEnabled`, nested `combine` to stay at arity-5).

## Summary

- **New `SaveAsChannelDialog` composable lives in `ui/conversations/components/`**, public visibility (host is in the sibling `ui/conversations/thread/` package). Lifts the [`RenameDialog`](../features/rename-dialog.md) structure wholesale — public composable → file-private `*Internal` seam → `AlertDialog` + `OutlinedTextField` + `FocusRequester` + `TextFieldValue` + `derivedStateOf`-gated `enabled` flag — with three substantive deltas: (i) `onSubmit: (name: String, workspace: WorkspaceChoice) -> Unit` carries the workspace choice alongside the trimmed name; (ii) `isSaveEnabled = trimmedName.isNotEmpty()` (single-gate — submitting the unchanged seeded `"New channel"` is valid; no `trimmedName != initialName` clause because the dialog has no semantic notion of "unchanged"); (iii) the `AlertDialog.text` slot is a `Column` of an `OutlinedTextField` plus a private `WorkspaceRadios` composable rather than just the field. `WorkspaceRadios` is two `Row`s wrapped in `Column.selectableGroup()` per M3 accessibility convention — each row uses `Modifier.selectable(selected = …, onClick = …, role = Role.RadioButton)` with `RadioButton(onClick = null)` so the row (not the radio glyph) is the click target.
- **The DEDICATED radio renders a mono-font path caption.** `~/pyry-workspace/channels/<auto-slug>/` styled `MaterialTheme.typography.labelSmall.copy(fontFamily = FontFamily.Monospace)` in `colorScheme.onSurfaceVariant`. The caption is a **static literal** in `SaveAsChannelDialog.kt`, not a string resource — it's fixed example text matching Figma `19:35`'s Roboto Mono rendering. The scratch radio has no caption. The literal placement is deliberate: a translator wanting to localize the `~/` prefix or path separator semantics later can convert to a resource trivially, but the Phase-0 literal is cheaper than a resource that doesn't change.
- **`ThreadEvent` grew two variants** for the dialog flow alongside the pre-existing `SaveAsChannel`: `data class SaveAsChannelSubmit(val name: String, val workspace: WorkspaceChoice)` and `data object SaveAsChannelDismiss`. Placed immediately after `SaveAsChannel` so the family stays contiguous in the sealed surface. `SaveAsChannelSubmit.name` is the trimmed name — the dialog is the trim authority; the VM forwards `event.name` to `repository.promote` without re-trimming. `SaveAsChannelSubmit.workspace` is the `WorkspaceChoice` enum (`DEDICATED` / `SCRATCH`), not the resolved path string — keeping the enum at the event boundary lets the dialog stay path-agnostic and makes the unit-test assertions read cleanly (`WorkspaceChoice.DEDICATED` vs. an opaque `"pyry-workspace/channels/foo"`).
- **New top-level `enum class WorkspaceChoice { DEDICATED, SCRATCH }`** in `ThreadViewModel.kt`. Top-level (not nested inside `ThreadEvent` or `SaveAsChannelDialogState`) because two callers consume it from different packages — the dialog (in `ui/conversations/components/`) and the VM/event (in `ui/conversations/thread/`) — and a top-level placement keeps both imports flat. Placed immediately after the `sealed interface ThreadEvent` block at the top of the file. **The enum is the only cross-package type added by this slice** — `SaveAsChannelDialogState` stays in the `thread/` package because only the screen overlay block reads it.
- **`ThreadUiState` gained `saveAsChannelDialog: SaveAsChannelDialogState? = null`** as nullable sub-state, placed between `showRenameDialog` (#141) and `items` (#246). The nullable carrier (rather than `Boolean visible` + `String initialName` sibling fields) bundles the seed value with the visibility flag — "visible iff non-null" — and matches the [#78](./78.md) `PendingPromotion` pattern explicitly called out as the established shape for transient UI sub-state composed with the repository stream. Different posture from #141's `showRenameDialog: Boolean` because the rename dialog reads `initialName` from `state.displayName` (already available; no separate seeding step) while this dialog needs the seeded `"New channel"` carried alongside the flag.
- **`data class SaveAsChannelDialogState(val initialName: String)`** in `ThreadViewModel.kt` (file-level, alongside `ThreadUiState`). Single-field; deliberately a `data class` not a `value class` so `equals`/`hashCode`/`toString` come for free for the unit-test equality assertions (`assertEquals(SaveAsChannelDialogState(initialName = "New channel"), vm.state.value.saveAsChannelDialog)`). Phase 4's real auto-suggested-title generator will plug in by changing the value passed to `SaveAsChannelDialogState(initialName = ...)` in the VM handler — the type shape stays.
- **`ThreadViewModel.onOverflowEvent` `when` was rewritten** to handle the three save-as-channel cases explicitly: `SaveAsChannel → pendingSaveAsChannelDialog.value = SaveAsChannelDialogState(initialName = AUTO_SUGGESTED_CHANNEL_NAME)` (replaces the [#204](./204.md) `Unit` no-op); `is SaveAsChannelSubmit → pendingSaveAsChannelDialog.value = null; viewModelScope.launch { repository.promote(state.value.conversationId, event.name, resolveWorkspace(event.name, event.workspace)) }`; `SaveAsChannelDismiss → pendingSaveAsChannelDialog.value = null`. The clear-flag-before-launch order matches [#141](./141.md)'s `RenameSubmit` for the same reasons — deterministic dismiss before the suspend point; well-defined state on a double-tap of the menu item during in-flight promote. The `Unit` no-op group collapses from four cases (`NewSession`, `ChangeWorkspace`, `ChannelInfo`, `SaveAsChannel`) to three (`NewSession`, `ChangeWorkspace`, `ChannelInfo`) — same shrink shape #141 produced when it filled the `Rename` branch.
- **`pendingSaveAsChannelDialog: MutableStateFlow<SaveAsChannelDialogState?>` would have been the sixth combine source — but the outer combine stays at five.** [#141](./141.md) recorded the `combine` arity ceiling at five (the native typed-overload limit). #142 cashes in that warning by introducing a private `data class TransientDialogs(val renameVisible: Boolean, val saveAsChannel: SaveAsChannelDialogState?)` plus a pre-combiner `transientDialogs: Flow<TransientDialogs> = combine(pendingRenameDialog, pendingSaveAsChannelDialog) { rename, save -> TransientDialogs(...) }`, and the outer `combine(observeConversations, observeMessages, pendingWorkspacePicker, transientDialogs, selectedModelFlow)` stays at five-arity. Both transient dialog flags travel through the new bundle; the destructure inside the reducer lambda is `dialogs.renameVisible` and `dialogs.saveAsChannel`. **The vararg `combine(vararg flows, transform)` overload was the alternative** (one fewer indirection in exchange for losing per-position typing); the typed nested form was chosen because it makes the `TransientDialogs` semantics ("the two transient overlays the thread screen owns") explicit in code.
- **`ThreadScreen` renders `SaveAsChannelDialog` as a fourth `Scaffold` sibling** alongside [`WorkspacePicker`](../features/workspace-picker.md), [`RenameDialog`](../features/rename-dialog.md), and [`StatusSheet`](../features/status-sheet.md), gated on `state.saveAsChannelDialog?.let { dialogState -> SaveAsChannelDialog(initialName = dialogState.initialName, onSubmit = { name, workspace -> onOverflowEvent(ThreadEvent.SaveAsChannelSubmit(name = name, workspace = workspace)) }, onDismiss = { onOverflowEvent(ThreadEvent.SaveAsChannelDismiss) }) }`. **`?.let { … }` over `if (state.saveAsChannelDialog != null)`** because the let-binding gives the lambda a non-null receiver for `dialogState.initialName` without a second `state.saveAsChannelDialog!!` deref.
- **Slug derivation lives at file scope** in `ThreadViewModel.kt`, alongside the existing `displayName()` / `workspaceLabel()` private extensions: `private fun resolveWorkspace(name: String, choice: WorkspaceChoice): String?` and `private fun String.toChannelSlug(): String`. Phase 4 swap point: replace with a generator that reads `state.value.items` and synthesizes a title from the first user message. ## Patterns established

- **Nested pre-combiner for transient-dialog sources.** When the outer `combine(...)` block already sits at the native 5-arity ceiling and a new transient-dialog source needs to join, fold two transient flags into a private `data class TransientDialogs(...)` plus a pre-combiner `transientDialogs: Flow<TransientDialogs>`, then swap the outer combine's existing dialog-source arm for the new bundle. The outer combine stays at five-arity, the reducer lambda destructures the bundle (`dialogs.renameVisible`, `dialogs.saveAsChannel`), and the named-receiver-lambda ergonomics are preserved. Document the bundle's semantic ("the two transient overlays the thread screen owns") in the class name itself; semantic naming beats anonymous tuple types. **The next ticket that adds a third transient flag** (e.g. an in-progress confirmation dialog for `Archive`) extends `TransientDialogs` with a third field rather than nesting a second pre-combiner — the bundle's purpose is heterogeneous-dialog-state, not strict-pair grouping.
- **Nullable sub-state vs. boolean-plus-siblings for dialogs.** When a dialog needs seed data (e.g. a pre-fill name) at open time, the nullable-sub-state shape (`val saveAsChannelDialog: SaveAsChannelDialogState? = null`) bundles the seed with the visibility flag — `visible iff non-null`, no out-of-band "what was the seed value" lookup. When a dialog reads its seed from existing `ThreadUiState` fields (rename reads `state.displayName`), the simpler `Boolean` flag suffices. Discriminator: does the seed value need to be captured at *open* time (it differs each open) or can it be read at *render* time (always available)? The save-as-channel dialog will eventually take a Phase-4 generator output captured at open; the rename dialog always renders against the current `displayName`. Both shapes coexist on `ThreadUiState` post-#142.
- **Enum payload on a `ThreadEvent` data class.** `SaveAsChannelSubmit(val name: String, val workspace: WorkspaceChoice)` is the first event carrying an enum field. The discriminator vs. encoding the workspace as a path `String` directly: keeping the enum at the event boundary lets the dialog stay path-agnostic and makes test assertions read cleanly (`WorkspaceChoice.DEDICATED` vs. an opaque path string). The VM is the resolver — `resolveWorkspace(name, choice): String?` translates enum → repository-layer path string. Apply to any future event whose payload represents a closed-set choice the UI surfaced.
- **File-scope `private` extension functions for VM-local helpers.** `resolveWorkspace(name, choice)` and `String.toChannelSlug()` live at file scope (outside the `ThreadViewModel` class) in `ThreadViewModel.kt`, alongside the pre-existing `Conversation.displayName()` / `Conversation.workspaceLabel()`. Tested through the public `onOverflowEvent` surface (the VM tests assert on `repository.promote` arguments), not in isolation. The `private` visibility is the gate that says "no other consumer should be allowed to import this"; the file-scope placement is the gate that says "this is too specific to the VM to belong in `data/model/`." If a sibling Phase-0 ticket needs to derive slugs for a different surface, promote to a shared `data/model/Slug.kt`; until then, don't pre-shareify.
- **Workspace caption renders as a literal, not a string resource.** The `~/pyry-workspace/channels/<auto-slug>/` caption under the DEDICATED radio is a Kotlin literal inside `SaveAsChannelDialog.kt`, not a `R.string.*` resource. The literal is "fixed example text styled like the running app's filesystem display" — semantically not localizable in Phase 0 (translators wanting to localize the `~/` prefix or path separator can convert to a resource later). Apply to any future example-text caption whose content is structurally fixed (filesystem paths, URL templates, mono-font placeholders) and only varies by example.

## Lessons learned

- **`combine`-arity-5 ceiling fix via a nested pre-combiner is cheap.** [#141](./141.md) flagged the ceiling and proposed two alternatives: switch to `combine(vararg flows, transform)` (loses per-position typing) or pre-fold two inputs into a `data class`. The pre-fold path costs one extra `data class` (private, 2-line), one extra `combine(...)` block (2-line), and zero call-site churn — the outer combine's `pendingRenameDialog` arm becomes `transientDialogs`, the lambda renames one parameter (`renameDialogVisible` → `dialogs` plus a `dialogs.renameVisible` deref), nothing else moves. No need to wait for a true 6-arity demand to do this refactor; the typed nested form pays for itself in lambda-readability on the next combine consumer. Apply when the next ticket adds a source — pre-fold an existing pair before reaching for vararg.
- **`?.let { dialogState -> SaveAsChannelDialog(initialName = dialogState.initialName, ...) }` is cleaner than `if (state.saveAsChannelDialog != null) { SaveAsChannelDialog(initialName = state.saveAsChannelDialog!!.initialName, ...) }`.** Both compile and behave identically; the `?.let` form gives the lambda a non-null receiver named `dialogState` and avoids the `!!` bang at the read site. Kotlin's smart-cast does *not* extend through the `if` block to the `state.saveAsChannelDialog` property reads inside, because `state` is a `data class` field reachable from outside the block (the compiler can't prove it stays non-null between the check and the read). The `let` shape sidesteps the smart-cast limitation entirely. Apply to any nullable sub-state on a `data class`-projected `state`.
- **`assertEquals(SaveAsChannelDialogState(initialName = "New channel"), vm.state.value.saveAsChannelDialog)` does the equality with named-argument readability.** The single-field `data class` autogenerates `equals` byte-identically to a `String?` field, but the named-argument construction makes the assertion read as "the dialog opened with the seeded name" rather than "the nullable string equals this value." Apply to any nullable sub-state assertion where the sub-state's *meaning* is what's load-bearing.
- **The slug-helper empty fallback (`ifEmpty { "channel" }`) is defensive against a non-blank name that strips to an empty slug.** A user typing `"!!!"` passes the dialog's `trimmedName.isNotEmpty()` gate (the trimmed name is `"!!!"`, not empty) but `toChannelSlug` strips it to `""` after `replace(Regex("[^a-z0-9-]"), "")`. Without `ifEmpty { "channel" }` the workspace path becomes `"pyry-workspace/channels/"` — a directory-with-trailing-slash that would either fail or silently shadow the parent in a real backend. Phase 4's remote impl will compute the canonical slug server-side; the fallback is a one-line guard until then. No test in isolation (the helper is `private`); the failure mode is contained to dev workflow.
- **`Modifier.selectable(role = Role.RadioButton)` + `RadioButton(onClick = null)` is the M3 idiom for tappable radio rows.** The row, not the radio glyph, is the touch target; the `RadioButton`'s `onClick = null` opt-out delegates click handling to the row's `selectable` modifier. `Modifier.selectableGroup()` on the parent `Column` is what enables single-select-radio-group accessibility semantics — without it, screen readers announce two independent radios. Apply to any future radio-row stack; do not give the `RadioButton` its own `onClick` (it produces double click targets in semantics).
- **`assertIsSelected()` / `assertIsNotSelected()` work on the *row* node, not the `RadioButton` node, when `Modifier.selectable(role = Role.RadioButton)` is on the row.** The selectable semantic lives on the row; the `onNodeWithText("Move to dedicated channel folder")` lookup resolves to the row (because the row carries `Modifier.selectable` semantics + the row contains the label text). `composeTestRule.onNodeWithText("Move to dedicated channel folder").assertIsSelected()` is the correct shape. A `onNode(hasContentDescription(...))` lookup against the `RadioButton` glyph would not match the selected semantic.
- **Six strings, not four.** The ticket AC said "four new strings"; the actual count is six (title, field label, two radio labels, two buttons). The architect spec called this out as an estimation artifact — the developer caught it during string-resource extraction. No regression risk, but worth noting that AC counts are approximate and the spec-level enumeration is authoritative.
- **The `WorkspaceChoice` enum's top-level placement is one cross-package import vs. zero.** The enum lives in `ThreadViewModel.kt` (package `ui/conversations/thread/`); the dialog (package `ui/conversations/components/`) imports it via `import de.pyryco.mobile.ui.conversations.thread.WorkspaceChoice`. The alternative placements considered: (a) `ConversationRepository.kt` data-side — rejected, the enum is a UI-layer choice translated to a path string at the VM boundary, not a repository-layer concept; (b) `SaveAsChannelDialog.kt` UI-side — would invert the import direction (the VM would import from the dialog file, which is structurally backward). The current placement is correct; the one cross-package import is the price of putting the enum where it semantically belongs (a `ThreadEvent` payload type).
- **`SaveAsChannelDialogState` is a `data class`, not a `value class`.** Single-field carriers tempt `@JvmInline value class SaveAsChannelDialogState(val initialName: String)` for zero allocation. Rejected because the unit-test `assertEquals(SaveAsChannelDialogState(...), vm.state.value.saveAsChannelDialog)` against `state.value.saveAsChannelDialog: SaveAsChannelDialogState?` would force the test to construct a wrapped nullable that the compiler treats inconsistently across nullable/non-null comparisons. The allocation cost (one tiny object per dialog open) is acceptable. Apply: prefer `data class` over `value class` for nullable-state carriers regardless of field count.
