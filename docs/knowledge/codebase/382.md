# #382 — Literal-screen entry-point action + navigation destination

The **wiring half** of the manual "show the literal screen" feature: the *only* path to the merged
[`LiteralScreenViewModel`](../features/literal-screen-viewmodel.md) ([#378](378.md)) +
[`LiteralScreenSurface`](../features/literal-screen-surface.md) ([#381](381.md)), both of which were
reachable from nowhere until now. Adds an **always-available** "Show the literal screen" item to the
Conversation Thread overflow menu that opens a dedicated `literal_screen/{conversationId}` destination
rendering #381's surface, driven by a **per-back-stack-entry** `LiteralScreenViewModel` (fresh VM per
open ⇒ no cross-conversation text bleed + automatic re-fetch). Adds no wire types; touches neither
`ThreadViewModel`, `ThreadEvent`, nor the repository. Split from #379 (which split #372 → #378/#379;
#379 then split on the surface-vs-entry seam → **#381** surface + DI / **#382** entry + nav);
`blockedBy #381`, itself `security-sensitive`.

It is the entry-point + nav face of pyrycode ADR 025's always-available, parser-independent
safe-degradation floor (pyrycode#596). "Surface this prominently on a stall" is a **separate** ticket
(#373, blocked on a stall signal that does not yet exist on the wire); here the action is **always
manually available**, independent of connection / parse / promotion state.

## Summary

Four existing production `.kt` files change (no new production source file); one string is added; two
test files are updated and one new test file is added. The action is a **pure navigation callback**
threaded `ThreadScreen → ThreadTopAppBar → ThreadOverflowMenu` (mirroring Settings' `onOpenAbout`), so
the sealed `ThreadEvent` surface and its exact-count overflow tests stay untouched. The
security-load-bearing AC#3 invariant — a fresh, per-conversation VM per open — is correct **by
construction**: `koinViewModel()` is obtained *inside* the destination composable (binds to the
back-stack entry's `ViewModelStoreOwner`), DI is a factory (not a `single`), and the VM reads
`conversationId` from a `SavedStateHandle` seeded by the route arg.

## Patterns established

- **Pure-navigation callback over the sealed-event sink, for a view-only nav action.** When an overflow
  action is *pure navigation* and its argument (`conversationId`) is already in hand at the destination
  layer, thread a `() -> Unit` callback `ThreadScreen → ThreadTopAppBar → ThreadOverflowMenu` (mirroring
  Settings' `onOpenAbout`) **instead of** widening `ThreadEvent`. This keeps `ThreadViewModel` /
  `ThreadEvent` / the repository untouched and avoids rippling a new variant through the overflow tests'
  exact-count event assertions. It is a **deliberate divergence** from the menu's single-`onEvent`-sink
  convention ([`thread-overflow-menu.md`](../features/thread-overflow-menu.md)) — justified because the
  action carries no VM authority; the install-memory-plugin item (`LocalUriHandler.openUri`) is the prior
  precedent for "an overflow item that bypasses `onEvent`." The tap test pins the divergence: it asserts
  `["dismiss", "show"]` and that **no** `ThreadEvent` is dispatched.
- **Per-back-stack-entry VM scoping enforced by call-site placement (correctness-by-construction).** The
  cross-conversation-text-bleed threat (AC#3) is closed by **two fabrics**: (a) the deterministic
  framework guarantee that each `navigate("literal_screen/<id>")` pushes a distinct `NavBackStackEntry` /
  `ViewModelStore`, so `koinViewModel<LiteralScreenViewModel>()` *inside the destination composable*
  yields a fresh VM with a fresh per-entry `SavedStateHandle`; and (b) the spec-mandated placement — the
  VM is obtained **only** inside the destination lambda, **never** hoisted to NavHost/activity scope and
  **never** registered as a Koin `single` (it's a `viewModel { }` factory). The fresh VM starts in
  `Loading` and the surface's `LaunchedEffect(Unit) { Request }` re-fetches, so no prior conversation's
  `text` is reachable. Same proven mechanism as `ThreadViewModel`. This is the reusable shape for any
  future per-conversation (or per-entity) sensitive surface.
- **The route-arg name is a load-bearing cross-slice contract.** The destination's `navArgument` and the
  inline `navigate(...)` string **must** use exactly `conversationId`, because
  `LiteralScreenViewModel.savedStateHandle.get<String>("conversationId")` (a string literal in #378) reads
  it. A divergence wouldn't be caught by the compiler — `LiteralScreenNavigationTest` pins it at the
  nav-compose framework level (a `StringType` arg named `conversationId` survives `navigate`).
- **Required vs. defaulted along the callback chain.** `ThreadOverflowMenu` / `ThreadTopAppBar` take
  `onShowLiteralScreen` as **required** (a nav action must not silently default to a no-op); `ThreadScreen`
  takes it **defaulted** (`= {}`) so previews + existing tests compile unchanged and only `MainActivity`
  wires the real callback — the same required-at-the-leaf / defaulted-at-the-screen-edge split
  `onOverflowEvent` uses.
- **Route-contract test without `TestNavHostController`.** A minimal two-destination `NavHost` under
  `createComposeRule` + `currentBackStackEntry` assertions guards the route template + arg-name contract
  using only `navigation-compose` (already present) — deliberately avoiding
  `androidx.navigation:navigation-testing`, which is **not** in the version catalog. Matches the repo's
  existing inline-route idiom.

## Lessons learned

The PR ([#384](https://github.com/pyrycode/pyrycode-mobile/pull/384)) carried **no** "Lessons learned"
section; the points below are drawn from the diff + the code-review comment.

- **The nav test hard-codes the route template literal, not `Routes.LITERAL_SCREEN`** (code-review NIT,
  non-blocking). `LiteralScreenNavigationTest` copies `"literal_screen/{conversationId}"` rather than
  referencing the production constant, so it pins the *nav-compose framework contract* but **not** the
  production route string / arg name — a future divergence in `Routes.LITERAL_SCREEN` would not be caught.
  This matches the repo's existing inline-route idiom (`"conversation_thread/$id"` is also built inline,
  separate from `Routes.CONVERSATION_THREAD`); the right consolidation is a shared `internal` route
  builder, deferred to a future ticket that touches route building (introducing one here is adjacent-refactor
  scope creep). Documented as an open question in the spec.
- **"Always available" is proven by asserting the item in *both* the promoted and unpromoted render
  tests**, not by a comment. Because the item is the first `DropdownMenuItem` *above* both promotion
  conditionals, the two assertions together demonstrate it is never gated (AC#1).
- **No `MainActivity` glue is unit-tested, by design.** The `onShowLiteralScreen = { navigate(…) }` line
  and the per-entry VM-freshness framework guarantee are correctness-by-construction (call-site placement),
  covered by code review — the same altitude #381 used for `FLAG_SECURE`'s no-op-under-test. `PyryNavHost`
  is `private` + Koin-bound, so no `MainActivity`-level nav test exists in the repo.

## Verification

- `./gradlew spotlessCheck test lint assembleDebug` all green (PR
  [#384](https://github.com/pyrycode/pyrycode-mobile/pull/384)); `compileDebugAndroidTestKotlin` confirms
  the instrumented tests compile. `connectedAndroidTest` not run — no device/emulator (instrumented tests
  run on-device per repo convention).
- **Code review: PASS** ([PR #384](https://github.com/pyrycode/pyrycode-mobile/pull/384)) — one
  non-blocking NIT (route-template literal in the nav test, above). The reviewer confirmed AC#3 is
  implemented correctly: `koinViewModel<LiteralScreenViewModel>()` inside the destination
  (`MainActivity.kt:381`), factory DI (`AppModule.kt:101`, not a `single`), VM reads `conversationId` from
  `SavedStateHandle` (`LiteralScreenViewModel.kt:65-66`); both new required params have all call sites
  updated (1 prod + 10 test for the menu; `ThreadScreen` is the only `ThreadTopAppBar` caller); no
  `Log.*`/`println`, no secrets, no file/storage writes, no manifest/exported change.
- **Security review: PASS** (architect self-review in the spec, label-gated). The slice moves no data
  across a trust boundary; the only datum it handles is the **non-sensitive** `conversationId`. The
  sensitive snapshot `text` never enters this slice (fetched in the VM, rendered by the surface — #378/#381).
  The boundary that matters is the **VM-instance boundary** — closed by the per-entry scoping above. The
  new route is an **internal** NavHost destination (not exported, no intent-filter/deep-link/PendingIntent,
  no manifest change), so the IPC attack surface is unchanged. Accessibility-service / overlay eavesdropping
  of on-screen text remains an app-wide platform residual (no per-view defense beyond #381's `FLAG_SECURE`),
  out of scope.
