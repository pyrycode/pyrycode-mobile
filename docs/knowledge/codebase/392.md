# #392 — pyrycode-leg Noise-session readiness + combined two-part connection status

The **pyrycode-leg half** of an honest two-part connection status, plus the **combined** model that
joins it with the relay leg. The relay path has two independently-failing legs — **phone → relay**
and **relay → pyrycode daemon** — and [#391](391.md) shipped the relay leg
([`RelayLinkStatus`](../features/relay-link-status.md), socket-level). This slice adds the **pyrycode
leg** (end-to-end session readiness, derived from the Noise pump) and publishes the combined
[`ConnectionStatus`](../features/connection-status.md) `{relay, pyrycode}` model off the
[`RelayRepositoryCoordinator`](../features/relay-repository-coordinator.md) for the Settings
connection-status line (**#390**, `blockedBy #392`) to consume.

The problem it closes: [`RelayConnectionSupervisor`](../features/relay-reconnect-supervisor.md)'s
`Connected` means **socket-open**, not Noise-session-open (its own KDoc flags this). A status dot
driven straight off the socket goes green whenever the relay socket is up — even when the handshake
failed or no daemon is behind the relay. That **false green bit live testing on 2026-06-08**. The
pyrycode leg reaches `Connected` **only** once the Noise handshake completes (pump `Open`), so the
two-part surface can show an honest "relay up, session not yet live."

**No server polling, no heartbeat, no status endpoint** — readiness is purely the handshake
completion the pump already surfaces ([`NoiseSessionPump.state`](../features/noise-session-pump.md)).
Split from #389 (the two-part-status parent) → #391 relay leg + #392 pyrycode-leg + combined.
`security-sensitive` (a session-machine signal driven by an untrusted relay crosses into trusted
status).

## Summary

Two new portable `data/model/` types plus a focused derivation added to the coordinator that already
owns the connection-scoped pump. The pyrycode leg is **pure derivation** off a private live-pump
mirror — no new mutable status state. The combined model is `combine(relayStatus, pyrycodeStatus)`
lifted to a hot `StateFlow`. `Connected` is reachable **only** via `PumpState.Open`, which the pump
sets only after `readResp` authenticates `noise_resp` — so a socket-up-but-no-handshake relay yields
`Handshaking`/`Down`, never `Connected`. The mapping discards `Open.connId` and `Closed.cause`,
holding the no-log contract structurally. One DI line; **no new Koin binding** (#390's call).

## Patterns established

- **A combined multi-part status model is pure derivation over per-source signals — no new mutable
  status state.** The pyrycode leg's single source is a private `activePumpFlow` mirror of the
  lifecycle the coordinator already tracks; `connectionStatus` is `combine(relayStatus,
  pyrycodeStatus)`. Adding a second source-of-truth `MutableStateFlow<ConnectionStatus>` would have
  invited the two legs drifting out of sync. The reusable shape: **mirror each leg's source, combine,
  `stateIn`** — never hand-maintain the joined value.
- **Track a connection-scoped child across reconnects by mirroring it into a `StateFlow` and
  `flatMapLatest`-ing onto its inner flow.** `activePumpFlow.flatMapLatest { it?.state ?: flowOf(null)
  }` is the same idiom [`StableConversationRepository`](../features/stable-conversation-repository.md)
  uses over `currentRepository` — `flatMapLatest` cancels the prior pump's `state` collection on every
  change, so the leg follows the *current* pump with no carryover and no collector leak. "No live
  child" maps through a `null` sentinel to the not-ready floor.
- **An untrusted-driven signal crosses into trusted status at exactly one total mapping, which
  discards every relay/crypto-derived string.** `toPyrycodeLinkStatus()` discriminates on the sealed
  `PumpState` subtype only; `Open.connId` and `Closed.cause` are dropped (`Connected`/`Down` are
  static `data object`s). No relay-supplied text flows into `ConnectionStatus` — the no-log /
  no-leak contract is **structurally enforced** by the mapping shape, not by a discipline rule. Mirror
  of #391's "single integer comparison" trust boundary on the relay leg.
- **Expose only the combined model; keep the leg private until a consumer needs it standalone.**
  `pyrycodeStatus` stays `private`; AC1's "observable pyrycode-leg readiness" is satisfied through
  `connectionStatus.value.pyrycode`. Evidence-Based Fix Selection: no consumer wants the leg alone —
  promote to a public property if one appears. Same restraint as deferring the Koin binding to #390.

## Lessons learned

- **`stateIn(scope, Eagerly, …)` runs at *property initialization*, so a derived-flow property must
  be declared *after* every field it references** (here `scope` and `activePumpFlow`). Kotlin
  initializes the class body top-to-bottom; referencing `scope`/`activePumpFlow` from an
  earlier-declared property is a **construction-time NPE**, not a compile error — it would surface
  only at first instantiation. The spec flagged this as a gotcha; placing `connectionStatus` /
  `pyrycodeStatus` beside `mutableRepository` (already below `scope`) satisfies it, and the
  code-review verified the ordering held. (`Lazy`/`by lazy` is the escape hatch if a forward
  reference is ever unavoidable — not needed here.)
- **`SharingStarted.Eagerly` chosen for an always-live process-global indicator** so `.value` is
  correct at any glance and tests read it directly after `runCurrent()`. `WhileSubscribed(5_000)` is a
  drop-in if lifecycle pressure is ever observed (a `StateFlow` caches the last value) — deferred, no
  observed need.
