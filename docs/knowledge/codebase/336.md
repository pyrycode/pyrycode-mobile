# #336 — Fold `session_transition` into the remote thread as `ThreadItem.SessionBoundary`

**Issue:** [#336](https://github.com/pyrycode/pyrycode-mobile/issues/336) ·
**Spec:** [`docs/specs/architecture/336-session-boundary-fold-remote-thread.md`](../../specs/architecture/336-session-boundary-fold-remote-thread.md) ·
**PR:** [#485](https://github.com/pyrycode/pyrycode-mobile/pull/485) ·
**Feature doc:** [Session-transition fold](../features/session-transition-fold.md) ·
Split from #313. Size **S**, `security-sensitive`.

## Summary

Closes the session-boundary de-scope #313 carried: `RemoteConversationRepository.observeMessages` now
interleaves `ThreadItem.SessionBoundary` delimiters at session transitions, so the real-backend thread
shows `/clear` / idle-evict / workspace-change boundaries between message runs instead of one flat run —
the way [`FakeConversationRepository`](../features/conversation-repository.md) does. Two halves:

1. **The load-bearing store unification.** The thread store moved from `messagesByConversation:
   MutableStateFlow<Map<String, List<Message>>>` to `threadByConversation: MutableStateFlow<Map<String,
   List<ThreadItem>>>` — it now holds both row kinds (`MessageItem` + `SessionBoundary`) so a non-`Message`
   boundary can interleave in arrival order with messages (no shared ordering key otherwise — messages
   are id-fixed, boundaries have no id). The five existing `Message.id`-keyed folds were lifted to
   `ThreadItem` **output-preserving** (the existing suite is the guard).
2. **The decode + fold.** A new capability-gated `session_transition` wire event decodes to a
   `ThreadItem.SessionBoundary` and pure-appends into the conversation thread keyed by the payload's
   `conversation_id`.

Pure data-layer wire→thread fold. The render side already ships and is untouched: the
[`SessionBoundaryDelimiter`](../features/session-boundary-delimiter.md) (#135/#192) and the
above-boundary de-emphasis (#136) already render whatever `SessionBoundary` rows arrive. Unit-only;
test-first, all gates green (`test`/`lint`/`assembleDebug`/`spotlessCheck`). Code review **PASS**, zero
findings.

Every upstream gate was closed before this landed: `pyrycode#656`/`#657` define and emit the
`session_transition` interactive event (capability-gated fan-out); `pyrycode#740`/`#741`/`#739` closed
the **routing-key gap** the 2026-06-23 architect review found — the payload now carries `conversation_id`
(plain `string`, no `omitempty`), the producer resolves and stamps the owning conversation on every emit
(**dropping server-side** any transition it can't bind), and the conversation↔session binding survives
`/clear` + eviction. So `session_transition` now routes exactly like `turn_state` / `assistant_delta` /
`tool_use`.

## Patterns established

- **Unify a thread store to `List<ThreadItem>` when a non-`Message` row must interleave by arrival
  order.** Two separate stores can't be re-interleaved (no shared ordering key); the elegant move is one
  store holding both row kinds, with each fold guarded by `is ThreadItem.MessageItem`. The lift is
  mechanical and behaviour-preserving — the existing test suite is the guard, run green before adding new
  cases.
- **A `ThreadItem` fold ≠ a `LiveSessionEvent`.** A `SessionBoundary` folds into the thread projection
  (`observeMessages`), **not** onto `liveSessionEvents` — the thinking-indicator / tool-timeline
  consumers must not see boundaries. The DTO therefore has no `toEvent()`. Contrast the
  [live-session](../features/live-session-events.md) DTOs.
- **No dedup on an id-less wire row.** `session_transition` carries no row id (`envelope.eventId` is the
  [replay cursor](../features/replay-cursor.md), not row identity) and the repo is connection-scoped
  (#351), so within a connection arrival order is correct → pure append, the same posture as
  `applyAssistantDelta`'s arrival-order concatenation. Cross-reconnect replay dedup is a #402-class
  concern, deferred — do not add a dedup guard.

## Lessons learned

- **`appendMessages` keeps role-agnostic dedup — do NOT route it through the role-requiring
  `indexOfMessage` helper.** Four of the five folds (`applyToolUse`/`applyToolResult`/
  `applyAssistantDelta`/`finalizeAssistantTurn`) match `id == key && role == Role.X`, so they share the
  new `List<ThreadItem>.indexOfMessage(id, role)` guard. But `appendMessages`' original predicate had
  **no role check** (a `message_id` dedups regardless of role), so it keeps an inline `existing.indexOfFirst
  { it is ThreadItem.MessageItem && it.message.id == message.id }` — adding only the type-guard.
  Collapsing it into the role-taking helper would have silently changed the message-dedup semantics.
  (Lifted from the PR's *Lessons learned*; confirmed by the code-review's line-by-line verify.)
- **Every `as ThreadItem.MessageItem` cast after an `indexOfMessage` hit is safe by construction** — the
  index can only come from a `MessageItem` match (the guard is the first conjunct), so the unchecked cast
  never throws. The type-guard namespaces message rows from boundary rows in one place.
- **The one security trap is the decode `catch`: keep it a bare `null`.** A `SerializationException`
  message and an `Instant.parse` failure both echo the offending payload field values, and
  `conversation_id` / session ids / `workspace_cwd` are sensitive (a logged or mis-routed boundary is a
  cross-conversation leak). Copy the sibling `decodeStall`/`decodeQueueState` bare-catch verbatim — no
  `Log`/`println`/`Timber` of `e` or `e.message`. Grep-confirmed clean.

## Notes / out of scope (deliberate, not bugs)

- **Live transitions only.** `session_transition` is a live emit; the `message_chunk` backfill carries no
  boundaries. Historical boundaries that occurred before the phone connected have no wire representation —
  a deliberate fidelity gap vs the fake (which derives boundaries from full in-memory history). No
  follow-up owed unless a future server capability adds historical replay.
- **`workspace_change` never arrives today.** The producer (#741) emits only `clear` / `idle_evict`;
  `workspace_change` stays a valid decode arm so the mapping is exhaustive and the
  `workspaceCwd`-non-null-iff-`WorkspaceChange` invariant is expressible, but no such event lands until a
  future server source exists. Decode is built and tested regardless.
- **Arrival order, not `occurred_at` sort.** The fold appends at the current end (the same posture as
  every existing fold); `occurredAt` is carried for display only. Within a single connection the wire
  delivers in causal order, so arrival order is correct.
