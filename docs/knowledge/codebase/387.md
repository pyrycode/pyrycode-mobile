# Ticket #387 — correlate `tool_use`/`tool_result` into live tool-call timeline items with status

**Issue:** [#387](https://github.com/pyrycode/pyrycode-mobile/issues/387) ·
**Spec:** [`docs/specs/architecture/387-correlate-tool-use-result-live-tool-call-items.md`](../../specs/architecture/387-correlate-tool-use-result-live-tool-call-items.md) ·

**Feature doc:** [Live tool-call](../features/live-tool-call.md) ·
Split from #368; blocked by [#385](385.md) (decoded live-session events, merged). The **visible**

`security-sensitive`.

## Summary

Turns [#385](385.md)'s decoded `tool_use` (start) / `tool_result` (completion)
[`LiveSessionEvent`](../features/live-session-events.md)s into **one evolving thread row** carrying a
status. A `tool_use` opens a `Running` `Role.Tool` [`Message`](../features/data-model.md) (name +
input); the matching `tool_result` (correlated by `toolUseId`, **not** by position) updates **that same
row in place** to `Done`/`Failed` and attaches the output. Both folds ride the **existing** single
inbound collector and `interactive` gate, mutating the existing `messagesByConversation`, so tool rows
**interleave by arrival order** with messages in `observeMessages` — no merge, no second flow, no sort.
Tolerant of missing / duplicate / out-of-order `tool_result` (no crash, no duplicate row, no orphan).
Built test-first, RED→GREEN; all gates green (`spotlessCheck`/`test`/`lint`/`assembleDebug`).

## Load-bearing design choices

- **Tool rows ARE thread rows — fold into `messagesByConversation`, do not invent a flow.** A live
  tool call is a `Role.Tool` `Message` carrying the `ToolCall`, written into the **same**
  `MutableStateFlow<Map<id, List<Message>>>` the live `message` arm writes. `observeMessages`'s
  `threadProjection` maps that list to `ThreadItem.MessageItem`s **in arrival order, with no re-sort**,
  so the tool row interleaves chronologically with messages **for free** (AC #4) — no ViewModel-side
  merge, no second flow, no timestamp sort. A ViewModel-side merge *cannot* satisfy AC #4 because
  ordering is owned by the repository surface. This is the structural reason the correlation lives in
  the repository, not a composable/ViewModel.
- **Correlation key = `toolUseId` AND `role == Role.Tool`.** The `&& role == Role.Tool` namespaces the
  match to tool rows so a server-supplied `toolUseId` can **never** collide with a real `message_id`
  and clobber a message. `toolUseId` is also the row's `Message.id` (the dedup handle).
- **Two small focused folds, not a generalized `appendMessages`.** Both are the same "find index in the
  per-conversation list, rebuild that one entry" shape as the existing `appendMessages`, but kept
  separate because the match predicate (tool-only) and absent-behavior differ:
  - `applyToolUse` — **append if absent, leave untouched if present.** A repeat `tool_use` (possibly
    already completed by an earlier `tool_result`) never adds a second row nor resets a finished one to
    `Running` (AC #3). One atomic `messagesByConversation.update {}`.
  - `applyToolResult` — **update the matching row in place (position + `timestamp` preserved), no-op if
    absent.** `output = resultSummary`, `status = if (isError) Failed else Done` (AC #2). A
    `tool_result` with no matching `tool_use` — including a result *before* its use (out-of-order) — is
    dropped, leaving no orphan half-row (AC #3). A duplicate `tool_result` re-applies the same in-place
    update (idempotent / last-write-wins, one row). `row.toolCall?.copy(...)` handles the theoretical
    null gracefully — no `!!`.
- **In-place status flip re-emits through `distinctUntilChanged`.** `ThreadItem.MessageItem` is a
  `data class`, so replacing a row's `toolCall` makes the projected list structurally **unequal** →
  `distinctUntilChanged` re-emits and the `Running → Done/Failed` transition propagates to the thread.
- **Single writer, no new state, no new gate, no new coroutine.** Both folds write the **existing**
  `messagesByConversation`, written only from the lone `init` inbound collector (and `sendMessage`'s
  confirmed insert, through the same atomic `update {}`). Tool events are processed on that one
  collector in wire arrival order, so insert-then-update never races; an out-of-order result simply
  finds no row and drops. Inside the **existing** `CAPABILITY_INTERACTIVE in negotiatedCapabilities()`
  gate (fail-closed defence-in-depth on top of the server-side fan-out gate). Exactly the #395 posture.
- **`Clock.System.now()` at `tool_use`, not `envelope.ts`.** Thread order is arrival order (never a
  timestamp sort), so the value does not affect placement; it is the established locally-assembled-row
  clock (`sendMessage`, `createDiscussion`); and it cannot throw, so a valid tool event's survival is
  never coupled to a malformed `envelope.ts` in the un-try-wrapped `.let` block. The `tool_result`
  update **preserves** the original `tool_use` timestamp.
- **`content` = the tool name, a non-empty fallback the UI ignores** (`MessageBubble` renders the
  `toolCall`, ignoring `content` for a `Role.Tool` row). **Not folded into `lastMessages`** — a tool
  invocation never becomes a conversation-list preview (`recordLastMessage` is not called).

## Patterns established

- **A live thread item that must interleave chronologically with messages folds into the same
  `messagesByConversation` list — keyed so it can't collide with a real `message_id` — rather than
  being a separate flow a ViewModel merges.** This is the deliberate contrast with #395: stall is a
  *separate* `Set<String>` projection surfaced as its own `observeStall` flow because it is not a thread
  item; a tool row *is* a thread item, so it joins the message list and inherits arrival-order
  interleave + `distinctUntilChanged` re-emit for free. The deciding question: *is this live signal a
  row in the thread, or state beside it?* — row → fold into `messagesByConversation`; state →
  separate projection.
- **An additive lifecycle status on an existing payload uses a trailing defaulted enum field whose
  default is the pre-existing semantics** (`Done` = "finished", the only state every prior construction
  represented), so the model gains a state machine with **zero fixture cascade** and equality
  assertions stay green. (Same defaulted-field discipline as `Message.toolCall` #191 and `observeStall`
  #395 — reused here, not new, but worth the cross-reference.)

## Verification

- **11 new unit tests** in `RemoteConversationRepositoryTest` (all `runCurrent()`-driven per
  [[remote-repo-test-runcurrent-not-advanceuntilidle]], RED→GREEN): `tool_use` → `Running` row;
  `tool_result` → `Done` in place; `isError` → `Failed`; correlate-by-id-not-position (two concurrent
  uses, only the matched one completes); result-with-no-matching-use → no row; result-before-use →
  single `Running` row (early result dropped); duplicate `tool_use` → single row, status stable;
  duplicate `tool_result` → idempotent; chronological interleave (`[user, tool(done), assistant]`);
  capability-gate-closed → no row; malformed `tool_use` dropped + later valid one surfaces (collector
  survived).
- **Code review PASS**, **zero blocking findings** ([PR #409](https://github.com/pyrycode/pyrycode-mobile/pull/409)).
  `codegraph_impact ToolCall` → 2 symbols, both in `Message.kt`, no consumer cascade; all three
  existing `ToolCall(...)` constructions named-arg and omit `status` → inherit `Done`, no fixture
  cascade; no exhaustive `when` over `ToolCallStatus` exists downstream (#388 consumes it).
- **`security-sensitive` honored:** no new parse point (consumes the already-typed `LiveSessionEvent`);
  `name`/`inputSummary`/`resultSummary` carried **verbatim** into `toolName`/`input`/`output` with no
  trim/parse/sanitize (output-encoding is #388's job); **zero `Log`/`println`/`print` touch
  tool-derived data** (grep-verified, including the drop/no-op branches) — the load-bearing
  no-payload-logging finding preserved. In-memory only; fail-closed `interactive` gate; unbounded-growth
  posture identical to the existing `message_id` path under the same authenticated-paired-daemon model.
- **`data/` portability:** only `kotlinx.datetime.Clock` + model imports added; no `android.*`.

## Open questions (carried from the spec; flagged to #388, not pre-built here)

1. **Out-of-order result is dropped, not buffered.** A `tool_result` arriving before its `tool_use`
   leaves the row permanently `Running`. This is the conservative "tolerate without crashing/
   duplicating" contract the AC asks for; a well-ordered stream never hits it. If real streams reorder
   under load, a small pending-results map (keyed by `toolUseId`, drained on the matching `tool_use`)
   would recover it — out of scope, flagged for the #388 architect only if the UX needs it.
2. **`turnId` is carried but unused for correlation.** Correlation is by `toolUseId` alone (globally
   unique per the wire SSOT). If the daemon ever reuses a `toolUseId` across turns, add `turnId` to the
   match key — not observed today.
3. **`content` = the tool name is a pure fallback.** The UI ignores it. If #388 wants a richer
   single-line label, that's a UI derivation over `toolCall`, not a data-layer change.
