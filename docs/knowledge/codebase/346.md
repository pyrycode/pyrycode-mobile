# #346 — `RemoteConversationRepository.sendMessage` over v2 (`send_message`)

Fills the `sendMessage` stub on the already-merged [`RemoteConversationRepository`](../features/remote-conversation-repository.md)
with a live [Mobile Protocol v2](../features/mobile-protocol-v2-wire-layer.md) round-trip: encode a
`send_message` request, correlate its `ack`/`error` reply through the class's **single** `init` inbound
collector, and **confirmed-insert** the user's message into both read-path projections only after the
correlated `ack`. This is the **first mutation method** to land on the remote (the three prior slices —
[#312](312.md)/[#329](329.md)/[#313](313.md) — were all read paths), and it introduces the **shared
request↔reply correlation primitive** that siblings #347 (`createDiscussion`) / #348 (`promote`) reuse.

See the feature doc [`remote-conversation-repository.md`](../features/remote-conversation-repository.md)
§ "`sendMessage`" and § "The ack/error correlation primitive" for the evergreen reference; this file is
the implementation record.

## The corrected wire premise (load-bearing)

`send_message` does **not** echo the sender its own persisted `Message`. The only sender-correlated
reply is an empty **`ack`** on success (`in_reply_to == requestId`, payload `{}`) or an **`error`** on
failure (`{code, message, retryable}`; codes `protocol.malformed` / `conversation.not_found` /
`server.binary_offline`). A `message` envelope reaching this device is either a user-echo to *other*
paired devices or the assistant's *later, unsolicited* reply (`in_reply_to: null`), **never** a
sender echo. So there is nothing to map for the return value, and **the sender's own thread updates
only if `sendMessage` projects the message locally** — and per the PO decision, only after the `ack`.

This corrects an earlier premise (in the original #346 body, and still recorded in the sibling
[#317](317.md) file as "the server echoes this same `message` payload as the persisted-message answer
to a `send_message`") that `send_message` returns a `Message` echo mappable by #317's `toMessage`. It
does not. Verified against the server SSOT on `pyrycode` `main` (`internal/relay/handlers/send_message.go`).
See [[phase4-send-message-acks-not-message-echo]] and [[phase4-request-encoders-live-in-mutation-tickets]].

## Decision — confirmed-insert, not optimistic (PO-owned, `security-sensitive`)

The message is projected into the read path **only on the correlated `ack`** — never before, never on
failure. No rollback path exists because nothing is inserted speculatively. Rationale (from the ticket):
`Message` has no delivery-status field, so an optimistic insert could only render as a normal-looking
message that might silently vanish — the *worse* trust outcome. It also satisfies the safety property
the prior review demanded — the thread never shows a message that did not reach the server — **by
construction**. Perceived send latency (the `ack` is the relay's fast receipt, not the assistant's
reply) is a future UI-layer concern and does not change this data-layer contract.

## Summary

One production class touched (`RemoteConversationRepository`) plus two new wire models and one
exception under `data/network/`. The data layer was previously read-only with mutation stubs; this
slice lands the first live mutation and the reusable correlation infrastructure.

- **`data/network/`** — `SendMessagePayloadDto` (encode-only request DTO, mirrors the existing
  `BackfillSincePayloadDto`); `ErrorPayload` (decode-only `{code, message, retryable}`); and
  `RelayErrorException` (the thrown form of a non-contract-mapped server `error`).
- **`RemoteConversationRepository`** — a `pendingRequests` registry, a `sendAndAwaitReply` helper, a
  `mapError` mapper, two new `onInbound` `when` branches (`ack`/`error`), the `recordLastMessage`
  extraction (the one sanctioned edit to the existing `TYPE_MESSAGE` body), and the filled `sendMessage`.
- **Tests** — seven new cases mapping 1:1 to the ACs, plus a togglable `sendResult` on `FakeSessionPump`.

## Patterns established

- **The shared request↔reply correlation primitive (#347/#348 inherit it).** `pendingRequests` +
  `sendAndAwaitReply` are the reusable register→send→await machine. Register **before** send (no
  lost-reply window); key on the **envelope id**, never the payload `message_id` (two distinct ids);
  `finally`-remove on every exit; idempotent `complete`/`completeExceptionally`. Siblings #347/#348 add
  their own success-type `when` branches (`conversation_created`/`conversation_updated`) that complete
  the **same** registry's deferreds with a typed payload; the `error` branch and `mapError` are shared
  as-is. The registry is typed `<JsonElement>` (the raw reply payload) precisely so a bare-`ack` caller
  ignores it while a future typed-reply caller decodes it.
- **Confirmed-insert is a correctness property by construction.** The two projection writes (`recordLastMessage`
  + `appendMessages`) run **only after** `sendAndAwaitReply` returns normally, so every failure path
  (`error` reply, `conversation.not_found`, `pump.send` → `false`, malformed error payload) throws
  *before* any insert — no projection mutates on failure, with no rollback/removal path to get wrong.
- **A stochastic-free safety net: `mapError` never hangs the collector.** A malformed/undecodable
  `error` payload is caught and converted to a fallback `RelayErrorException` rather than propagating —
  so the **single** inbound collector survives and the awaiting caller is always unblocked. Re-uses this
  file's established "`SerializationException`/`MissingFieldException` are subtypes of `IllegalArgumentException`,
  so catch IAE" convention (same as the read-path decode-drop arms).
- **Two writers per projection, still data-safe.** `lastMessages` and `messagesByConversation` were
  documented single-writer; this slice relaxes that to collector + `sendMessage`. Every write goes
  through an atomic `MutableStateFlow.update {}` over a **pure** fold (strictly-greater-by-timestamp /
  id-dedup), so concurrent writes from the two coroutines retry-merge correctly. The KDoc invariant was
  updated on both fields rather than left stale.
- **A structured transport-error type for ViewModel branching.** `RelayErrorException(code, retryable, message)`
  carries the server's machine-readable `code` and the `retryable` flag so a future UI can branch (retry
  vs surface), while `conversation.not_found` maps to `IllegalArgumentException` to preserve cross-impl
  parity with the fake. Its `message` is the server's human-facing text only — **never** the user's `text`.
- **`sessionId = ""` placeholder reused, not resolved.** The reconstructed message uses the remote's
  established `""` placeholder (the v2 wire carries no `session_id`; boundaries are #336) — `currentSessionId`
  is deliberately **not** resolved, matching the inbound mappers.

## Lessons learned

Lifted from the PR's *Lessons learned* section:

- **The request envelope id and the payload `message_id` are two distinct ids.** Correlation keys on
  `Envelope.inReplyTo == requestId` (the `AtomicLong` envelope id), **not** on the message id. Conflating
  them would silently break correlation. The registry is keyed on the envelope id for exactly this reason.
- **`send_message` returns only an empty `ack` or an `error` — there is no server echo of the sender's
  own message.** The sender's thread therefore updates **only** via the local confirmed-insert. The
  original ticket premise ("map the echo via #317") was false; this was a *body* defect, not a server
  gap. See [[phase4-send-message-acks-not-message-echo]]. The same stale "send_message echo" phrasing
  survives in code comments (`MessagePayload.kt:14-15`, `RemoteConversationRepository.kt` `TYPE_MESSAGE`
  body) and in the [#317](317.md) ticket file — left untouched per spec (sibling-file rule); the
  **evergreen** [wire-layer](../features/mobile-protocol-v2-wire-layer.md) feature doc was corrected by
  this ticket.

## Forward hand-off (to #350, the remote-wiring slice)

Two review NITs are out of scope here and handed to the #350 ViewModel/remote-wiring ticket so they
aren't lost:

- **`ThreadViewModel.sendMessage` is fire-and-forget** (`viewModelScope.launch { repository.sendMessage(…) }`,
  no `try/catch`). Harmless today (the UI runs on `FakeConversationRepository`, which only throws
  `IllegalArgumentException` for an unknown id that can't arise from `state.value.conversationId`), but
  once the live remote is wired in, this slice's new `RelayErrorException` and `IllegalStateException`
  (not-connected) would escape uncaught into the ViewModel scope. The UI needs an error surface.
- **`ConversationRepository` interface KDoc still pins only `IllegalArgumentException`.** The remote now
  also throws `RelayErrorException`/`IllegalStateException`. Reasonable to keep these as
  remote-transport-specific (the cross-impl invariant stays IAE), but #350 should document the widened
  surface for consumers.

A separate spec/architect concern, flagged not fixed (Evidence-Based Fix Selection): **connection-drop-mid-send
leak** — if the connection scope is cancelled while a caller still awaits, the deferred never completes
and the suspend hangs until the *caller* is cancelled (the ViewModel scope on screen exit). No timeout
is added (no observed hang; a timeout value is a product call). A future slice or the connection
coordinator ([#302](302.md)) may fail all `pendingRequests` on disconnect.
