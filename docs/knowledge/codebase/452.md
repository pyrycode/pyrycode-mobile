# #452 — render the armed second-confirm affordance + send-error; wire the route host

**Issue:** [#452](https://github.com/pyrycode/pyrycode-mobile/issues/452) ·
**Spec:** [`docs/specs/architecture/452-render-armed-second-confirm-and-send-error.md`](../../specs/architecture/452-render-armed-second-confirm-and-send-error.md) ·
**PR:** [#456](https://github.com/pyrycode/pyrycode-mobile/pull/456) ·
**Feature doc:** [Permission-modal overlay](../features/permission-modal-overlay.md) (extended) ·
Split from #444 (the **interaction** half of #439). **This is the render half** — it draws the
armed/second-confirm affordance, adds an explicit Cancel button, surfaces a payload-free send-error on the
snackbar, sets a tapjacking net, and **wires the route host** so the previously-inert option-tap / cancel
hooks go live. The sibling **behavior** half [#451](451.md) (the VM decision logic + outbound send)
**shipped** and is this slice's `blockedBy`. Builds on [#446](446.md) (base overlay) and [#445](445.md)
(`currentModal` projection). Leaf dependent: **#440** (reactive read-only on ungranted-device reject) is
`blockedBy` this. Size **S**, `security-sensitive`.

## Summary

The **render + wire glue** of the permission/choice-modal interaction surface. [#451](451.md) shipped the
ViewModel decision logic and exposed two signals this slice consumes **verbatim, with no UI-side
re-derivation**: `ThreadViewModel.armedOptionId: StateFlow<String?>` (the VM-scoped armed non-default
option) and `modalSendErrors: Flow<Unit>` (a payload-free one-shot send-failure event). This slice (1) draws
a distinct **second-confirm affordance** on the armed option (off the `armedOptionId` input — no UI-side
arming), (2) adds an explicit low-emphasis **Cancel** `TextButton` so `onModalCancel` becomes reachable, (3)
surfaces the **send-error** on the existing snackbar via a **mapped local string** (payload-free event + a
local string ⇒ nothing modal-derived reaches the un-secured Activity window), (4) sets a deterministic
**tapjacking net** on the dialog's own window now that the taps are live, and (5) **wires the route host**
so the inert `onModalOption` / `onModalCancel` hooks forward to `vm::onModalOption` / `vm::onModalCancel` and
the two new signals reach the screen. Two production files + 3 strings + the AC#4 screen test. **No new
public type, no VM change, no data-layer change.** Built test-first; all gates green; code review **PASS**,
one optional NIT.

## Patterns established

- **The render slice renders the VM-owned interaction state; it never re-derives it** — the #445→#446 /
  #451→#452 seam, now closed. `isArmed = option.id == armedOptionId` is a plain `==` against the VM's
  **already-scoped** projection (`armedOptionId` is `null` unless the arm's `modalId` matches the open
  modal, #451), so a stale arm is structurally undisplayable; the UI inherits that property rather than
  re-enforcing it. Every tap forwards verbatim; the second-confirm gate stays entirely in the VM.
- **Tapjacking net on a Compose dialog's own window** (new in the codebase): obtain the dialog window via
  `(LocalView.current.parent as? DialogWindowProvider)?.window` and set
  `decorView.filterTouchesWhenObscured = true` in a `SideEffect`. This is the **deterministic View-level
  analog** of #446's `securePolicy = SecureOn` — a code-level net, **different fabric** from the
  second-confirm UX belt (belt-and-suspenders: a single obscured tap can at worst arm/deny, the filter
  additionally hardens the deliberate two-tap tapjack of an *allow*). Like a window flag generally, it has
  **no Compose-test semantics node** ⇒ **code-review-verified by inspection**, not runtime-asserted (the
  same posture as `SecureOn` and `FLAG_SECURE`). Any future live-tap dialog follows this.
- **Collect a VM one-shot where its effect lives, not uniformly in the route host.** `modalSendErrors` is
  collected **inside `ThreadScreen`** (its effect — the snackbar — is a screen concern, and the
  `snackbarHostState` is owned there since #446), a deliberate deviation from the ticket's "collect in
  `MainActivity`" note. `navigationEvents` stays in `MainActivity` because its effect (`navController`) is a
  host concern. The "mirrors the `navigationEvents` one-shot idiom" AC is still met (a `LaunchedEffect`-
  scoped `Flow.collect`); the `ArchivedDiscussionsScreen` precedent is the exact shape. `modalSendErrors`
  is a single-consumer `Channel.receiveAsFlow()`, so it must be collected in exactly one place —
  `MainActivity` only forwards the reference.
- **Confidentiality by construction: payload-free event + fixed local string.** Because the source event is
  `Flow<Unit>` (#451) and the snackbar shows a fixed `modal_send_failed`, it is **structurally impossible**
  for a `modalId` / `optionId` / command / path to reach the snackbar — which draws in the **un-secured
  Activity window** (the dialog's `FLAG_SECURE` covers only the dialog). The exact mirror of #446's mapped-
  not-echoed `dismissReasonText` posture.

## Lessons learned

- **The `androidTest` source set is not compiled by the mandatory gates** (`test` / `lint` /
  `assembleDebug` skip it — only `connectedAndroidTest` / `assembleDebugAndroidTest` touch it). With no
  device in the CI/build env, run `./gradlew compileDebugAndroidTestKotlin` explicitly to catch a broken
  instrumented test before PR, or it ships silently. (PR #456 closed this gap by running it as an extra
  gate — green.) See [[androidtest-not-compiled-by-mandatory-gates]].
- **In `androidx.compose.ui.test`, `onNode` / `onAllNodes` / `assertExists` / `assertDoesNotExist` are
  *members* of `SemanticsNodeInteractionsProvider` / `SemanticsNodeInteraction` (no import)**, whereas
  `onNodeWithText` / `assertIsDisplayed` / `hasText` are top-level extensions (need imports). This is why
  the existing modal test compiles without importing the former — re-confirmed here (first noted in
  [#446](446.md)).
- **A stateful "VM-mimicking stand-in" makes the two-tap flow observable at the screen layer without
  re-implementing the VM.** The VM's authoritative arm/confirm rule is unit-tested in #451; the AC#4 screen
  test backs `armedOptionId` + `onModalOption` with a tiny `var armed by remember {
  mutableStateOf<String?>(null) }` whose `onModalOption` faithfully mimics #451's branch order (default →
  record send; armed-match → record send + clear; else → arm), recomposing `armedOptionId = armed`. So
  "first tap arms (no send) and renders the affordance; second tap confirms" is genuinely exercised at the
  render layer. Reusable shape for any "behavior-on-the-VM, render-here" split test.

## Security (`security-sensitive`)

This slice makes the permission-answer taps **live** (a high-consequence action: it injects allow/deny into
the supervised `claude`) and adds two render surfaces + a snackbar fed by a failure event. Architect
self-review **PASS**; code review **PASS**, security properties verified implemented in the diff:

- **No payload to the un-secured window.** The error snackbar shows the fixed local `modal_send_failed`;
  the source event is `Flow<Unit>` (#451), so structurally no `modalId` / `optionId` / command / path can
  reach the snackbar. `RelayErrorException.message` is caught and dropped in #451, never threaded here.
  Mirrors #446's mapped dismiss reason.
- **Inert output-encoding preserved.** The armed affordance, Cancel button, and snackbar add only **local**
  strings; the verbatim `title` / `prompt` / option `label` still render through plain `Text` (#446) —
  never `MarkdownText`, no `SelectionContainer`, no `String.format` pattern. The armed render does **not**
  reconstruct or re-emit the command — the already-shown verbatim `label` is the only server text on the
  armed button.
- **Fail-safe-deny preserved; the UI cannot make an allow easier.** The render only *reflects*
  `armedOptionId` (VM-owned, scoped); it never re-derives the arm, never interprets option-id semantics,
  never auto-answers. Every tap forwards verbatim via `onClick = { onOption(option.id) }`; the
  second-confirm gate is the VM's (#451). Cancel sends `modal_cancel` — a withdrawal, never an allow.
- **Tapjacking — the named #446/#451 hand-off discharged.** `filterTouchesWhenObscured = true` on the
  dialog's own window (deterministic, View-level, min SDK 33), now that the taps are live.
- **No new trust boundary, no persistence, no minted value.** Operates on already-decoded in-process state;
  nothing modal-derived reaches `rememberSaveable` / `SavedStateHandle` / DataStore; no token/key/nonce
  (the `answer_token` is #438's, server-validated); no `Log.*` / `Timber`.

## Code-review NIT (optional, not gating)

- The send-error confidentiality test drives the error over a `Hidden` modal, so the `prompt`
  (`rm -rf …`) is never composed and the `assertDoesNotExist("rm -rf")` passes **vacuously**. The contract
  is enforced **structurally** (the event is `Unit` + a fixed local string), so this is not a real gap —
  but the assertion would be stronger driven over an **`Open`** modal (where the payload is actually on
  screen) to prove the snackbar specifically does not echo it. A candidate strengthening when **#440**
  (which extends this surface) next touches the test.
