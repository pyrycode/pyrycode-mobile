# Ticket #601 — StatusSheet: render "Context usage unavailable"

**Issue:** [#601](https://github.com/pyrycode/pyrycode-mobile/issues/601) ·
**Spec:** [`docs/specs/architecture/601-status-sheet-context-usage-unavailable.md`](../../specs/architecture/601-status-sheet-context-usage-unavailable.md) ·
**PR:** [#607](https://github.com/pyrycode/pyrycode-mobile/pull/607) (`17432ae`) ·
**Feature doc:** [StatusSheet](../features/status-sheet.md) ·
Split from #584 (chain: #601 → #602 → #603). Sibling: #591 (serve the real figure — blocked on
daemon-side pyrycode PR #1215). Size **S**. Client-only — no wire call, no DTO, no repository method.
Code review **PASS** (0 findings).

## Summary

`StatusSheet`'s `ContextWindowSection` rendered `"73% used (146K of 200K tokens)"` with a
`warning`-coloured `LinearProgressIndicator` filled to 73% — on every conversation, on every device,
always, because the values came from `ThreadViewModel`'s `STUB_TOKEN_PERCENT` / `STUB_TOKENS_USED` /
`STUB_TOKENS_TOTAL` companion constants. This was the only warning an operator got before their context
window actually filled and started dropping messages, and it could never fire. This ticket deletes the
stub render and replaces it with the literal **"Context usage unavailable"**, no bar, no severity
colour — matching the desktop wording captured in pyrycode#1214 verbatim, including the decision to
keep the existing "When full, oldest messages get dropped…" caption alongside it.

The key structural fact that made this shippable alone: `ThreadUiState` keeps `tokenPercent` /
`tokensUsed` / `tokensTotal`, and `ThreadViewModel` keeps populating them from the stub constants. The
sheet simply stopped *reading* them — `ThreadViewModel.kt` was not touched, so nothing upstream needed
re-testing, and #591 re-wires the same three fields when the daemon has a real number.

- **`androidTest/…/components/StatusSheetTest.kt`** (`-55` net) — `renders_context_window_section_with_header_label_and_caption`

Untouched, deliberately: `ThreadViewModel.kt` (`STUB_TOKEN_PERCENT` / `STUB_TOKENS_USED` /
`STUB_TOKENS_TOTAL` intact at `:932-934`, `ThreadUiState` keeps all three fields), `ThreadStatusRow.kt`
(its own `tokenPercentColor` helper is unrelated to the deleted `progressColor` and still consumes the
`warning` theme slot), `strings.xml` (the unavailable text is an inline literal — every other string in
this file is inline, and a `stringResource` here would have been the odd one out).

## Load-bearing design choices

- **A hardcoded stub is a worse UX than an honest blank.** The 73% figure was pinned regardless of the
  real conversation state — it could show 2% when the window was actually at 99%, i.e. it actively
  suppressed the one signal an operator has before messages start dropping. Deleting the number rather
  than fixing its accuracy was correct because there was no accurate number to compute client-side; the
  daemon has never served one.
- **No sealed `Unavailable | Known(...)` type.** There is exactly one possible value today, so a variant
  type would be speculative generality — a new public type plus consuming composables for zero present
  benefit. #591 reintroduces state only when it has a real figure to carry.
- **`ContextWindowSection` stays a private composable, not inlined**, even though it's now
  parameterless and trivial — the `SectionHeader(...)` + section-composable pairing is the structural
  rhythm the other three sections (Model, Effort, YOLO) all follow, and #591 needs the seam back.
- **Colour is `onSurface`, not `onSurfaceVariant`.** Severity was never on the label — it lived on the
  now-deleted bar via `progressColor`. `onSurface` is the same neutral slot the figure already used, and
  de-emphasising to `onSurfaceVariant` would have been an unrequested visual change colliding with the
  caption's own tone.

## Patterns established

Nothing new at the architecture level. This is the inverse of the #230 pattern it undoes: #230 added
three defaulted `Int` params across a signature chain to introduce a display; #601 shows that removing
*defaulted* params is symmetric and cheap — call sites that never passed them explicitly (5 of 9
previews, 11 of 14 tests) needed zero edits. The one thing worth carrying forward: **a parameter default
can hide a stale test from the compiler** — see Lessons learned.

## Lessons learned

- **Parameter defaults hide stale tests from the compiler.** `label_format_handles_zero_values_gracefully`
  passed no token args and leaned on the `= 0` defaults to assert `"0% used (0K of 0K tokens)"`, so
  `compileDebugAndroidTestKotlin` stayed green with it still exercising a deleted formatter — it would
  have failed only at run time, on device. When removing *defaulted* params, a clean `androidTest`
  compile is not evidence the test source set is done; find the stale cases by name, not by build error.
- **`git stash` + re-run is the cheap way to baseline a surprise red.** Three instrumented tests failed
  in files this change touches or neighbours on the Pixel_8 run. Stashing to a clean tree and re-running
  the same filter took ~30s each and turned "did I break this?" into documented evidence that the change
  hadn't — which is what justified filing #605/#606 instead of debugging an obviously-unrelated red.

## Verification

- `spotlessCheck`, `lint`, `assembleDebug`, `compileDebugAndroidTestKotlin`,
  `testDebugUnitTest --tests ThreadViewModelTest` — all green.
- Instrumented on a Pixel_8 API 35 emulator: `StatusSheetTest` 10/12 and the
  `…conversations.thread` package 89/90 — every failure in both runs reproduced identically on clean
  `main` (stashed tree, same commit) and is filed as #605 / #606, not fixed here. This ticket's own case,
  `renders_context_window_section_as_unavailable_with_header_and_caption`, went red→green.
- Figma node `20:151` fetched directly during code review (not trusted from the spec's description):
  confirmed no unavailable variant exists, confirming the divergence is real and deliberate rather than
  an oversight.
- Code review: **PASS**, zero findings. Full blast-radius grep confirmed `formatTokens` / `progressColor`
  have zero references anywhere in `app/src`, and the two imports that look orphaned but aren't
  (`foundation.layout.height`, still used by the `Spacer` at `:99`; `Arrangement`, still used by
  `EffortChipRow`) were correctly kept.
- No rung-3 real-claude scenario — correctly not required. There is no stream event, wire call, DTO, or
  repository method in this slice; the section renders two static strings. Both the ticket and the spec
  state this carve-out explicitly.
