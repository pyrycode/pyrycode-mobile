# #268 — feat(ui/settings): Push notifications toggle persistence

Wires the previously inert "Push notifications when claude responds" Switch in `SettingsScreen` through to a **new** `AppPreferences.notificationsEnabled` preference so the value persists across app restarts. Pure plumbing — no new types, no new files, no new visuals. Mirrors the [#234](./234.md) `defaultYolo` boolean-`Switch` persistence pattern **with one deliberate deviation: the preference defaults to `true`, not `false`** (Figma `17:2` renders the toggle ON). Persists the **preference only** — actual notification delivery is Phase 4 (same scope boundary as #234); nothing consumes `notificationsEnabled` today beyond the Settings switch reflecting its own state.

This is the **seventh** `(StateFlow<X>, fun onToggleX/onSelectX)` pair on `SettingsViewModel` (`themeMode`, `useWallpaperColors`, `defaultModel`, `defaultEffort`, `defaultYolo`, `defaultWorkspace`, now `pushNotifications`) — and the **first one outside the "Defaults for new conversations" group**: it lives in the Settings "Notifications" section.

**Difference from #234:** there, the `AppPreferences` surface (`defaultYolo` flow + `setDefaultYolo` + the DataStore key) already shipped in [#231](./231.md), so #234 only *consumed* it. Here the `AppPreferences` surface does **not** exist yet — this ticket *creates* it. That is why this slice adds production changes *and* tests to `AppPreferences` / `AppPreferencesTest`, whereas #234 did not.

## Summary

- **`AppPreferences.kt`** — new key + getter + setter mirroring the `defaultYolo` block, with the inverted default. Companion key `NOTIFICATIONS_ENABLED = booleanPreferencesKey("notifications_enabled")`; getter `val notificationsEnabled: Flow<Boolean> = dataStore.data.map { prefs -> prefs[NOTIFICATIONS_ENABLED] ?: true }` (`:67`) — **`?: true`**, the **only** boolean preference in the file that defaults to `true` (`pairedServerExists`, `useWallpaperColors`, `defaultYolo` all default `false`); setter `suspend fun setNotificationsEnabled(enabled: Boolean)` → `dataStore.edit { … }`. No new imports (`booleanPreferencesKey`/`Flow`/`map`/`edit` already in scope). This is `notificationsEnabled`'s **first definer and first writer** in one slice — the 8th `AppPreferences` key.
- **`SettingsViewModel.kt`** — seventh `(StateFlow<Boolean>, fun onToggle…)` pair, placed between `defaultYolo` and `defaultWorkspace`: `val pushNotifications: StateFlow<Boolean> = appPreferences.notificationsEnabled.stateIn(viewModelScope, WhileSubscribed(STOP_TIMEOUT_MILLIS), initialValue = true)` (`:64`) and `fun onTogglePushNotifications(enabled: Boolean) { viewModelScope.launch { appPreferences.setNotificationsEnabled(enabled) } }`. **`initialValue = true`** matches the upstream's `?: true` default — an `initialValue = false` here would cause a visible OFF→ON flicker on cold open. Same boolean-pair shape as `useWallpaperColors` / `defaultYolo`, not the enum-pair shape of `defaultModel` / `defaultEffort`. Reuses the existing `STOP_TIMEOUT_MILLIS = 5_000L` constant.
- **`SettingsScreen.kt`** — required `pushNotifications: Boolean` param inserted after `defaultYolo` (`:56`) and required `onTogglePushNotifications: (Boolean) -> Unit` after `onToggleDefaultYolo` (`:64`), keeping the signature's state-values-then-callbacks grouping. The local `var pushNotifications by remember { mutableStateOf(true) }` was **removed** — this was the **last** placeholder-`Switch` local in the body; after #268 only the three dialog open-state flags (`showThemeDialog`/`showModelDialog`/`showEffortDialog`) remain. The Push-notifications row's `Switch` (`:208-213`) rebinds from `onCheckedChange = { pushNotifications = it }` to `Switch(checked = pushNotifications, onCheckedChange = onTogglePushNotifications)`. The row carries **no** `supporting` arg — preserved as-is (matches Figma `17:2`). Both `@Preview` blocks pass `pushNotifications = true` and `onTogglePushNotifications = {}`.
- **`MainActivity.kt`** — inside `composable(Routes.SETTINGS)`: one new collector `val pushNotifications by vm.pushNotifications.collectAsStateWithLifecycle()` (`:236`), plus `pushNotifications = pushNotifications,` (`:246`) and `onTogglePushNotifications = vm::onTogglePushNotifications,` (`:254`) pass-throughs into `SettingsScreen(...)`.
- **`AppPreferencesTest.kt`** — two new `@Test`s mirroring the `defaultYolo` pair with the inverted default: `notificationsEnabled_defaultsToTrue` (fresh DataStore → assert `true` — the deterministic guard for the non-obvious default) and `setNotificationsEnabled_roundTripsBothValues` (`false → true → false`; starting from `false` proves an explicit write overrides the `true` default in both directions). 19 `@Test`s total post-#268.
- **`SettingsViewModelTest.kt`** — three new `@Test`s mirroring the `defaultYolo` trio, inverting the default expectations: `pushNotifications_initialState_emitsTrue_whenNoStoredValue`, `pushNotifications_initialState_mirrorsPersistedFalse` (persisting `false` — the non-default — proves a stored value overrides the `true` default), `onTogglePushNotifications_persistsAndFlowReEmits` (`false → true` walk asserting both `prefs.notificationsEnabled.first()` and `vm.pushNotifications.value`). Three tests, not five — a boolean has no `.entries` boundaries to round-trip. 38 `@Test`s total post-#268.
- **`SettingsScreenTest.kt` (androidTest)** — the three `setContent { SettingsScreen(...) }` call sites threaded with `pushNotifications = true` (state group) + `onTogglePushNotifications = {}` (callback group). This landed in a **separate rework commit (`f74ec6e`)** after the first code-review pass **FAILED** — see § Lessons learned.

## The load-bearing deviation: default = `true`

Every other boolean preference in `AppPreferences` defaults to `false`. This one is the exception, and **three sites carry the `true` default — all three must agree**, with a fourth (a test) pinning them:

1. `AppPreferences.notificationsEnabled` getter — `prefs[NOTIFICATIONS_ENABLED] ?: true` (`AppPreferences.kt:67`).
2. `SettingsViewModel.pushNotifications` — `stateIn(… initialValue = true)` (`SettingsViewModel.kt:64`).
3. `AppPreferencesTest.notificationsEnabled_defaultsToTrue` — the deterministic guard against a stochastic copy-paste of the `false` default from the mirrored `defaultYolo` block.

Code review (PASS) verified all three agree and that the `false` default was correctly **not** copied. Cross-checked against **Figma `17:2`**: the "Push notifications when claude responds" toggle renders **ON** (filled `Schemes/primary` track), contrasting the OFF Default-YOLO toggle directly above it; the row has no supporting text in Figma → code correctly omits the `supporting` arg.

## Patterns established

- **Nothing new in shape** — the boolean-`Switch` variant of the #89/#234 persistence pattern, applied again: Switch `checked`/`onCheckedChange` straight onto a `(StateFlow<Boolean>, fun onToggleX)` VM pair, fire-and-forget `viewModelScope.launch { appPreferences.setX(...) }`, `WhileSubscribed(5_000L)` projection. The boolean-pref **three-test** template (not the five-test enum template) is reused per the [#234](./234.md) rule.
- **The mechanical-copy `(StateFlow, onToggleX)` shape has now propagated *outside* the "Defaults for new conversations" group.** `pushNotifications` is the first persisted Settings preference in the Notifications section, and it was copied from `defaultYolo` without the long-deferred sealed-`SettingsState` lift ever being evaluated — confirming the shape has **settled by default** (see [`settings-viewmodel.md`](../features/settings-viewmodel.md) § Edge cases). There is no longer a "natural trigger" row pending; any future lift is its own dedicated refactor ticket.
- **`notificationsEnabled` is the first `AppPreferences` boolean to default `true`.** The reinforced rule: the data-layer default is **Figma-sourced per preference**, not a blanket `false` — copy the *shape* of a sibling preference, but source the default value from the design, not from whichever sibling you cloned. See [`app-preferences.md`](../features/app-preferences.md).

## Lessons learned

- **The androidTest `setContent` cascade FAILED code review again — the FOURTH occurrence (#232 missed → #233 caught → #234 missed → #268 missed).** Adding two **required** (no-default) params to `SettingsScreen` invalidates every `setContent { SettingsScreen(...) }` call site in `SettingsScreenTest.kt` — a separate `androidTest` compilation unit. The first implementation commit (`50e8660`) updated the production wiring, both `@Preview`s, and the unit tests, but not the instrumented test, so `./gradlew compileDebugAndroidTestKotlin` failed with `No value passed for parameter 'pushNotifications'` / `'onTogglePushNotifications'` at the three sites. **The PR's gate list shows exactly why:** the developer ran `test`, `lint`, `assembleDebug`, `spotlessCheck` — **none of which compile the `androidTest` source set**; only `compileDebugAndroidTestKotlin` (or `connectedAndroidTest`, skipped here for lack of an emulator) does. Review FAILED with a single MUST FIX; the rework commit `f74ec6e` threaded the two params through all three blocks and confirmed `compileDebugAndroidTestKotlin` green; re-review PASSED.
- **The #234 process follow-ups were not actioned, so the same failure recurred.** [#234](./234.md) § Lessons learned flagged this as a **deterministic-safety-net candidate** — wire `compileDebugAndroidTestKotlin` into `CLAUDE.md`'s pre-PR command list and/or CI (it currently lists `./gradlew test`, `lint`, `assembleDebug`, `connectedAndroidTest`, but `connectedAndroidTest` needs a device and is skipped headless, so the *compile* of the instrumented set goes unchecked). That net was **not built**, and #268's architecture spec's "Files to read first" **again omitted the `androidTest` source set** (it lists the `main` and `test` paths but not `SettingsScreenTest.kt`). Per the pipeline's **Evidence-Based Fix Selection** principle, this is now a *repeated, observed* failure (4×), and per **Belt-and-Suspenders Means Different Fabric**, the advisory rule (architect/developer remembering the source set) is the wrong fabric for a recurring mechanical break — a deterministic build gate is warranted. **Recorded as a follow-up below.**
- **Pre-flight checklist when adding a required `SettingsScreen` parameter (now demonstrated four times):** (1) the `SettingsScreen` signature, (2) both `@Preview` blocks, (3) all `setContent` blocks in `SettingsScreenTest.kt` (androidTest), (4) the `composable(Routes.SETTINGS)` block in `MainActivity.kt`. Run `./gradlew compileDebugAndroidTestKotlin`, not just `./gradlew test`, before opening the PR.
- **`notificationsEnabled` is write-live but read-dead** (like `defaultYolo` after #234). The toggle persists end-to-end — flip it, force-stop, relaunch, it sticks — but **nothing reads `notificationsEnabled` to act on it.** Notification *delivery* is Phase 4 (same scope boundary as #234). Don't "fix" the apparent dead-end by wiring delivery or a system-notification channel — that's a deliberate Phase-0 scope boundary, not an oversight.

## Threshold notes (both named re-evaluation points reached and passed unevaluated)

- **`AppPreferences` split.** [`app-preferences.md`](../features/app-preferences.md) named "the first non-defaults Phase-3 key (**notifications**)" as the natural seam to split `AppPreferences` into `AppPreferences` (pairing/theme + defaults bundle) + a new `NotificationPreferences`. #268 **is** that key — and the split was **not** evaluated: the ticket was scoped as XS plumbing mirroring `defaultYolo` and added `notificationsEnabled` inline. The file is now at **8 keys**. Same deferral pattern as the sealed-state lift; recorded so the trail isn't lost.
- **Sealed `SettingsState` lift.** [`settings-viewmodel.md`](../features/settings-viewmodel.md) § Edge cases had already concluded the lift threshold's last natural trigger (the #235 workspace picker) passed unevaluated and "the shape has settled by default." #268 confirms it: a *seventh* pair, the first outside the defaults group, copied mechanically with the lift never weighed.

- **INDEX + `settings-screen.md` drift predating #268.** `docs/knowledge/INDEX.md`'s `SettingsViewModel` one-liner is frozen ~#233 (lists three projections; omits `defaultModel`/#232, `defaultYolo`/#234, `defaultWorkspace`/#235) and its `Settings screen` one-liner is frozen post-#234/#271 but pre-#235 (the signature omits `defaultWorkspace`/`workspacePickerVisible`, and "Default model / Default YOLO / Default workspace … still no-op `onClick = {}`" is false after #232/#234/#235). The `settings-screen.md` feature doc was likewise not updated by #235's doc run (its Default-workspace row, the reused `WorkspacePicker` host, and `workspacePickerVisible` are undocumented). This run brings the `settings-screen.md` signature/usage/preview code blocks to true HEAD and corrects the #268-adjacent prose, but a full #232→#235 reconciliation of the two INDEX one-liners is out of #268's scope — flagging it (the role doc's "auto-generation or dispatcher-side pre-doc rebase" is the durable fix).
