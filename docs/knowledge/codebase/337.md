# Ticket #337 — accumulate live `assistant_delta` into a growing streaming thread message

**Issue:** [#337](https://github.com/pyrycode/pyrycode-mobile/issues/337) ·
**Spec:** [`docs/specs/architecture/337-streaming-assistant-turns.md`](../../specs/architecture/337-streaming-assistant-turns.md) ·
**PR:** [#418](https://github.com/pyrycode/pyrycode-mobile/pull/418) ·
**Feature doc:** [Streaming assistant turns](../features/streaming-assistant-turns.md) ·
Split from #313. Size **S**, `security-sensitive`.

## Summary

Feeds the live `assistant_delta` stream into the [#313](313.md) finished-message remote thread so an
in-flight turn renders as a **single growing `isStreaming == true` assistant message** whose text
accumulates as deltas arrive and settles into the finished message when the turn ends — the real
backend thread now streams the way the fake-backed thread already does (#184), instead of snapping in
only finished messages. **Purely the `ThreadViewModel` `items` derivation**: no data-layer change, no
DI change, no new visual. It folds the #313 `observeMessages` projection together with the
[#385](385.md) `liveSessionEvents` stream and swaps the result into the existing 5-flow `state`
combine (arity unchanged). The third VM-layer consumer of the generic
[`liveSessionEvents`](../features/live-session-events.md) seam after `isThinking` ([#406](406.md)) and
the live tool-call row ([#387](387.md)).

The premise the ticket inherited from its #313 split was rewritten before this slice: streaming did
**not** land as an `isStreaming` flag on the `message` payload — it landed as a separate
`assistant_delta` envelope on `liveSessionEvents`, correlated by `turnId`/`seq`.
`MessagePayloadDto.toMessage`'s `isStreaming = false` STAYS correct (finished `message` envelopes ARE
finished) and was not touched. See [[phase4-v2-wire-no-streaming]].

## Load-bearing design choices

- **A fold over *both* flows, not a sibling `StateFlow` + stateless combine.** Unlike `isThinking`
  (#406) and `isStalled` (#395) — sibling `StateFlow`s the screen takes as *separate* params — the
  streaming message is a **`ThreadItem` in the thread**, so it must land in `ThreadUiState.items`. The
  seam is therefore the `items` derivation itself (the choice the ticket flagged for the architect).
- **The finalise/dedup is structural, not id-correlated** — because the finished `message` carries
  **no `turn_id`** (verified against the server structs, [[phase4-v2-wire-no-streaming]]) so
  correlation by id is impossible, **and** `observeMessages` / `liveSessionEvents` are two separate hot
  flows fed by uncoordinated server emitters, so there is **no wire ordering** between `turn_end` and
  the finished `message`. At turn start the fold snapshots `baselineAssistantIds` = the set of
  assistant `MessageItem` ids already in the finished list; the streaming item is dropped the moment
  the finished list gains an assistant `MessageItem` whose id is **not** in that snapshot — i.e. *this
  turn's persisted message has arrived*, whether before or after `turn_end`. This is
  **race-direction-independent**: the ticket's fallback suggestion ("clear the streaming item on
  `turn_end`") would flicker a gap if `turn_end` won the race and a transient duplicate if the finished
  `message` won — AC #3 forbids both. Both directions are tested.
- **Conversation-id guard checked *first* for every live event** (`reduceLive`: `if
  (event.conversationId != conversationId) return this`, `:485`) — mirrors `thinkingTransition`. This
  is the AC #2/#3 confidentiality property: no foreign conversation's text can reach this thread.
- **`seq` ordering/dup guard** (`reduceDelta`, `:506`): a new `turnId` starts a turn (superseding any
  unfinalised prior turn); `seq > lastSeq` appends (`text + delta.text`); `seq <= lastSeq` (replayed /
  out-of-order) is ignored — AC #2 "in `seq` order".
- **`turn_end` settles, it does not remove.** `TurnEnd` for the in-flight turn sets `ended = true`
  (renders `isStreaming = false`, settling the typewriter) but keeps the row until the finished
  `message` replaces it. A turn that never produces a finished `message` (cancelled / refusal) leaves
  the settled partial text rendered — graceful degradation, not an orphan streaming state.
- **Synthetic message id = `turnId`** (`render`, `:530`) — a stable per-turn id in a distinct namespace
  from the server `message_id`, so the `LazyColumn` key `"msg:$turnId"` never collides with
  `"msg:$messageId"` (and they are never both present: finalise drops the streaming item in the **same**
  emission the finished message appears). `sessionId`/`timestamp` are derived from the last finished
  item (fallbacks: empty string / epoch) — render-irrelevant for an appended assistant row, and a live
  clock is deliberately avoided to keep the fold pure/testable.
- **Inert empty-flow default = true no-op for the fake graph.** The fake graph and pre-existing tests
  inject `liveSessionEvents = emptyFlow()`; `merge` then yields only the `observeMessages` arm and the
  thread behaves byte-identically to #313 — every pre-existing `ThreadViewModelTest` stays green with
  no fixture change. Same inertness lever #406 used for `isThinking`.

## Patterns established

- **A live-event consumer that must land *in* the thread (not a sibling flag) folds `observeMessages`
  + `liveSessionEvents` with `merge → scan → render`, swapped in place into the `state` combine arm.**
  Where #406/#395 reduce `liveSessionEvents` to a sibling `StateFlow<Boolean>` beside `state`, a
  consumer whose output is a `ThreadItem` reduces *both* the finished projection and the live stream
  into one accumulator and replaces the `observeMessages` arm — keeping combine arity and every
  downstream field unchanged. The next thread-row live consumer follows this shape.
- **Dedup two uncoordinated hot flows structurally, not by id or by ordering, when no shared
  correlation key exists.** When a "live" item must reconcile with a "persisted" item arriving on a
  separate flow with no shared id and no ordering guarantee, snapshot the persisted-id set at the live
  item's start and finalise when a *new* persisted id appears. Race-direction-independent; needs no
  wire field and no timer.

## Lessons learned

- **The inert empty-flow default makes the change a true no-op for the fake graph** (lifted from the
  PR's *Lessons learned*): `merge` yields only the `observeMessages` arm when `liveSessionEvents =
  emptyFlow()`, so all pre-existing `ThreadViewModelTest`s stay green with no fixture change — the same
  inertness lever #406 used for `isThinking`.
- **The #184 typewriter restarts its reveal on every delta — by existing design, now exercised live
  for the first time.** `StreamingAssistantBody` keys its `produceState` reveal on `content`
  ([Message bubble](../features/message-bubble.md), `key1 = content`), so each appended
  `assistant_delta` that grows `Message.content` restarts the 50-char/sec reveal from 0. #337 is the
  first slice to drive that path with real backend deltas (Phase 0 only ever fed it one static
  streaming demo). The effect is self-limiting — the reveal rate outpaces typical delta cadence and the
  item flips to the static `MarkdownText` path on `turn_end` — and the code review did not flag it, but
  it is the one place a fast/bursty real delta stream could read as a "stutter." VM-side reveal hoisting
  was already noted as a possible Phase-4 follow-up by #184; revisit only if observed against a live
  daemon.
- **Reconnect mid-turn is an accepted edge** (spec § Open questions): if a backfill on reconnect adds a
  *new-to-us* assistant message id while a turn is in flight, the baseline-id dedup could finalise the
  streaming item early. Worst case is an early settle to the finished text — **never a duplicate**. The
  reconnect-replay handling is itself deferred (#402/#416/#417); revisit if observed.

  growing streaming message (accumulated text, `isStreaming == true`, single item); seq order + replay/
  out-of-order dedup (AC #2); conversation-id scoping (AC #2 confidentiality oracle); both finalise race
  directions — `turn_end`-then-finished and finished-before-`turn_end` (AC #3/#5); backfill ordering

  the inert empty-flow no-regression guard (AC #5). No `ComposeTestRule` — no new composable; the

  blocking findings**. Verified: the fold branches against AC #1/#2/#3; the structural finalise is
