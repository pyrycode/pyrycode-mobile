# #235 — feat(ui/settings): Default workspace row opens Workspace Picker + persists selection

Wires the previously inert "Default workspace" `SettingsRow` (hardcoded `supporting = "scratch"`, empty `onClick = {}`) to open the existing [`WorkspacePicker`](../features/workspace-picker.md) host (#143/#220, reused unchanged), persist the chosen cwd via `AppPreferences.setDefaultWorkspace(...)`, and render the current persisted default in the row's supporting text. **First Settings-side *writer* of `defaultWorkspace`** — the schema shipped in [#231](./231.md), and the first *reader* was [#240](./240.md) (FAB short-press new-conversation cwd). With this slice the `defaultWorkspace` round-trip is closed end-to-end (write here, read in #240), unlike [#234](./234.md)'s `defaultYolo` which stays write-live / read-dead. This is the **last of the four "Defaults for new conversations" rows** (model [#232](./232.md), effort [#233](./233.md), YOLO [#234](./234.md), now workspace) and the final natural re-evaluation point for the long-deferred "lift to sealed `SettingsState`" decision — which passed **unevaluated again** (see § Patterns established). Split from [#147](https://github.com/pyrycode/pyrycode-mobile/issues/147) ("Defaults for new conversations").

**The structurally new thing in this slice:** it is the **first Settings row backed by the `WorkspacePicker` host (`visible` / `onPicked` / `onDismiss` seam) rather than a local `AlertDialog` picker dialog.** The theme/model/effort rows each open an `if (show…Dialog)`-gated dialog whose open-state lives in a local `remember { mutableStateOf(false) }` inside the screen body. The workspace row instead hoists its visibility to the ViewModel (`workspacePickerVisible: StateFlow<Boolean>`) and renders the reused host conditionally on it — copying the [`ThreadViewModel`](../features/thread-screen.md) picker-host shape (`onWorkspaceChipTapped` / `onWorkspacePicked` / `onWorkspacePickerDismissed`), not the in-screen dialog shape. This asymmetry is **intentional**: AC #6 explicitly requires the VM to expose the picker visibility flag, and the `WorkspacePicker` host is designed to be driven by a hoisted `Boolean` (see [`workspace-picker.md`](../features/workspace-picker.md) § Usage). Code review flagged it `[INFO]` so a future cleanup pass doesn't "tidy" it into local state.

## Display label — `workspaceLabel` (intentionally duplicated)

```kotlin
private fun workspaceLabel(cwd: String): String =
    if (cwd.isEmpty() || cwd == DEFAULT_SCRATCH_CWD) "scratch"
    else cwd.substringAfterLast('/').ifEmpty { cwd }
```

- Sentinel (or empty) → `"scratch"`, matching the placeholder copy and the Theme/Model/Effort summary style.
- Real path → **trailing folder name** (e.g. `~/Workspace/Projects/pyrycode-mobile` → `pyrycode-mobile`), **not** the full path. The Settings supporting line is a one-line summary, semantically identical to the thread workspace chip ([`ThreadViewModel.workspaceLabel()`](../features/thread-screen.md) `:294`), which already uses trailing-folder-name. The picker's recent rows show full monospace paths because they're a *selection* list needing disambiguation — a different role. Folder-name also avoids overflow/wrap of a long path in a `body-small` slot.
- The helper is **duplicated locally**, not extracted from `ThreadViewModel` (whose copy is `private`). Extracting it would touch `ThreadViewModel.kt`, which [#208](https://github.com/pyrycode/pyrycode-mobile/issues/208) is concurrently editing — out of scope, and "touch only what's necessary". Code review confirmed this as an acknowledged `[NIT]`, not an oversight. **Consolidation into a shared workspace util is the deferred follow-up** (three `workspaceLabel`-style helpers now exist: this one, `ThreadViewModel:294`, and the chip logic) — do it once #208 has merged and the concurrent-edit hazard is gone.

## Patterns established

- **Picker-*host* visibility belongs in the ViewModel; picker-*dialog* visibility stays in local `remember`.** This slice draws the line the prior three defaults rows didn't have to: a row that opens a self-contained `AlertDialog` (theme/model/effort) keeps its `show…Dialog` flag in a screen-local `remember { mutableStateOf(false) }` (the dialog is a leaf composable with no other consumer). A row that opens the **reused `WorkspacePicker` host** hoists `workspacePickerVisible` to the VM and exposes it as a `StateFlow<Boolean>`, copying the [`ThreadViewModel`](../features/thread-screen.md) picker-host shape. **Rule:** when wiring a new consumer of `WorkspacePicker`, add a `private val pending… = MutableStateFlow(false)` + `asStateFlow()` projection + open/pick/dismiss triple to the *ViewModel* — do not reach for a screen-local `remember`. The host is built to be driven by a hoisted `Boolean` (its `if (!visible) return` gate is the dismiss mechanism). Don't let the asymmetry with the sibling dialog rows tempt a "consistency" refactor into local state — see code review's `[INFO]`.
- **`onPicked` is the single funnel for recent-pick AND create-new.** AC2 (tap a recent path) and AC3 (create a folder) both arrive through `onSelectDefaultWorkspace(path)`; the host's create-folder dialog already routes a newly-created path through the same `onPicked` callback (see [`workspace-picker.md`](../features/workspace-picker.md) § What it does). One handler, no need to distinguish the source — the persisted action is identical.
- **The "lift to sealed `SettingsState`" threshold passed unevaluated for the third consecutive slice — the shape has now settled by default.** [#232](./232.md)/[#233](./233.md)/[#234](./234.md) each named "the next defaults consumer (… or workspace picker, whichever lands first)" as the unambiguous re-evaluation point, and the workspace picker was explicitly the **last** remaining defaults slice. It landed scoped as S plumbing ("mirror the existing per-field StateFlow + callback style") and **the lift question was not raised** — so `SettingsViewModel` now carries five `(StateFlow<X>, fun onToggle/onSelectX)` preference pairs *plus* this picker-host triple (`StateFlow<Boolean>` flag + three callbacks) + the read-only `archivedDiscussionCount` projection, with no sealed envelope. There are no more defaults rows to act as a natural trigger; any future lift would have to be its own dedicated refactor ticket, not a rider on a feature slice. Recorded here as the terminal entry in the [#87](./87.md)→#232→#233→#234 deferral trail — the threshold drifted permanently. See [`settings-viewmodel.md`](../features/settings-viewmodel.md) § Edge cases.

## Lessons learned

- **The androidTest `setContent` cascade was missed a *third* consecutive time (#232 → #234 → #235), code review caught it again, and this exposed a blind spot in the QA gate that was supposed to catch it.** Adding five required params to `SettingsScreen` invalidated all six `setContent { SettingsScreen(...) }` call sites in `SettingsScreenTest.kt` (a separate `androidTest` compilation unit `./gradlew test` does **not** exercise). The first implementation correctly updated `MainActivity.kt` and both `@Preview` bodies but **not** the instrumented test — so `./gradlew compileDebugAndroidTestKotlin` failed with **30 `No value passed for parameter…` errors** (5 params × 6 sites). Code review **FAILED** the PR on this single blocker; rework commit `670dcb4` threaded the five params + the `DEFAULT_SCRATCH_CWD` import through all six blocks and re-ran `compileDebugAndroidTestKotlin` (green).
  - **The new finding (the part #234's lessons didn't yet have):** QA runs `compileDebugAndroidTestKotlin` **only when the PR already touches `app/src/androidTest/`**. That heuristic has a blind spot *exactly* for this class of miss — a required-param change in `main/` that *should* cascade to `androidTest` but the developer *forgot* to touch `androidTest` means the PR doesn't touch `androidTest`, so QA skips the compile, so the break sails through QA. It's chicken-and-egg: the gate only fires once the bug is already fixed. On this PR the sequence was visible — first QA pass ran `./gradlew check` + `assembleDebug` (both green, neither compiles `androidTest`), the break slipped to code-review which caught it deterministically; the *second* QA pass ran `compileDebugAndroidTestKotlin` "(run because the PR touches `app/src/androidTest/`)" and confirmed green — but only because the rework commit had by then touched `androidTest`.
  - **The deterministic fix [#234](./234.md) flagged is now validated three times over and should be filed:** run `./gradlew compileDebugAndroidTestKotlin` **unconditionally** in QA (not gated on whether the PR touches `androidTest`), and/or add it to `CLAUDE.md`'s pre-PR command list (which today lists `./gradlew test`, `lint`, `assembleDebug`, `connectedAndroidTest` — but `connectedAndroidTest` needs a device and is skipped headless, so the *compile* of the instrumented set goes unchecked). A build task that fails the cascade mechanically beats relying on the architect to enumerate the `androidTest` source set and the developer to remember it — which has now failed on three of the last four `SettingsScreen`-signature slices (#232 missed, #233 got it, #234 missed, #235 missed). This belongs in its own follow-up ticket; recording here so the #232→#234→#235 trail isn't lost.
  - **Pre-flight checklist when adding a required `SettingsScreen` parameter** (unchanged from #234, restated because it was missed again): (1) the `SettingsScreen` signature, (2) both `@Preview` blocks, (3) **all six `setContent` blocks in `SettingsScreenTest.kt` (androidTest)**, (4) the `composable(Routes.SETTINGS)` block in `MainActivity.kt`. Run `./gradlew compileDebugAndroidTestKotlin`, not just `./gradlew test`, before opening the PR.
- **`defaultWorkspace`'s round-trip is now closed (writer here + reader in [#240](./240.md)).** Unlike `defaultYolo` (write-live / read-dead after #234), the workspace default both persists (this slice) and is consumed: [`ChannelListViewModel.CreateDiscussionTapped`](../features/channel-list-viewmodel.md) reads `appPreferences.defaultWorkspace.first()` for the FAB short-press new-conversation cwd (#240). So a path picked in Settings actually changes where the next short-press discussion is created. The long-press FAB picker path (`ChannelListEvent.WorkspacePicked`) deliberately bypasses the default — an explicit per-conversation pick always overrides it. No further wiring is "missing" here; the loop is complete.
