# #359 — `RemoteConversationRepository.registerPushToken` over v2 (`register_push_token`)

Adds the **outbound wire capability** for FCM push registration on
[`RemoteConversationRepository`](../features/remote-conversation-repository.md): encode a
`register_push_token` request, send it over the live [Mobile Protocol v2](../features/mobile-protocol-v2-wire-layer.md)
Noise pump, and await the correlated `ack`/`error` — so the paired daemon knows where to send a wake
notification when the phone is backgrounded. It **reuses** [#346](346.md)'s `sendAndAwaitReply`
request↔reply primitive and `mapError` → `RelayErrorException` mapping **verbatim** (no new error
mapping, no new `onInbound` branch, no projection mutation), and adds one new encode-only request DTO.

Scope is deliberately **one wire round-trip**. No Firebase, no token persistence, no lifecycle policy,
no UI — those are sibling slices. The capability is **dormant**: nothing in the shipped app calls it yet
(the Firebase sibling adds the live caller and the live device-name value). Split from #356.

See the feature doc [`remote-conversation-repository.md`](../features/remote-conversation-repository.md)
§ "`registerPushToken`" for the evergreen reference; this file is the implementation record.

## The two load-bearing departures from the three #314 mutations

1. **It is NOT a `ConversationRepository` interface method.** Push-token registration is a
   device/connection concern, not a conversation operation, so `registerPushToken` is a public method on
   the **concrete** `RemoteConversationRepository` only — never an interface override. Per
   [[post-352-connection-scoped-repo-behind-facade]] the repo is now connection-scoped behind the
   process-lifetime [`StableConversationRepository`](../features/stable-conversation-repository.md) facade
   that ViewModels hold, and that facade only delegates the `ConversationRepository` interface — so a
   non-interface method **deliberately will not reach consumers through the facade**. That is intentional
   and correct: reaching the dormant capability from a live caller is the **Firebase sibling's** job, not
   this slice's. No facade exposure, no new interface method, no DI reachability was added here.

2. **It is a pure request/reply with no projection side effect.** Unlike `sendMessage` /
   `createDiscussion` / `promote`, this capability registers a token and produces **no domain object** —
   the success signal is simply "the call returned without throwing". `projection` / `lastMessages` /
   `messagesByConversation` are untouched, so (in contrast to #346, which had to amend their writer-list
   KDocs) **no projection KDoc needed updating**.

## Summary

One production class touched (`RemoteConversationRepository`) plus one new encode-only request DTO under
`data/network/`. The `sendAndAwaitReply` correlation primitive, the `ack`/`error` `onInbound` arms, and
`mapError` are **reused, not built** — this slice writes ~12 lines of new method body and a 4-field DTO.

- **`data/network/`** — `RegisterPushTokenPayloadDto` (encode-only `register_push_token` request DTO, its
  own file per the ktlint single-public-type rule; three required fields `platform`/`token`/`device_name`).
- **`RemoteConversationRepository`** — a last/defaulted `deviceName` constructor param, the public
  `registerPushToken(token)` method, and two new companion constants. **No `onInbound` change** (the
  reply types `register_push_token` draws — `ack`/`error` — are already wired by #346).
- **Tests** — five new cases mapping 1:1 to the ACs, plus a `startRegisterPushToken` launch helper.

## Files touched

- **`app/src/main/java/de/pyryco/mobile/data/network/RegisterPushTokenPayloadDto.kt`** (new, 32 lines) —
  `RegisterPushTokenPayloadDto(platform: String, token: String, @SerialName("device_name") deviceName:
  String)`. All three **non-nullable, no defaults** — all required on the wire, in Go-struct order. Lives
  in its **own file** (the #347/#348 file-per-DTO convention; ktlint's single-public-class filename rule
  makes a dedicated file mandatory anyway — see [[ktlint-filename-rule-single-class]]). `platform` and
  `token` are single-word wire names needing no `@SerialName`. **`platform` is a plain `String`, not an
  enum** — the value is the constant `"fcm"` supplied at the call site, and an encode-only DTO models only
  what it sends (the server also keeps `Platform` a `string` and accepts `"apns"` for iOS, out of scope
  here). KDoc cites the wire SSOT (server `internal/protocol/push.go` `RegisterPushTokenPayload`, spec
  #275; golden `internal/protocol/testdata/register_push_token.json`; `docs/protocol-mobile.md`
  § `register_push_token`) and pins the no-logging posture on `token`.
- **`app/src/main/java/de/pyryco/mobile/data/repository/RemoteConversationRepository.kt`** (+52):
  - **`deviceName: String = ""` constructor param** (`:68-78`) — **last and defaulted**, so the one
    production construction site (`RelayRepositoryCoordinator.onConnection()` →
    `RemoteConversationRepository(pump, childScope)`) and all ~30 existing test sites compile **unchanged**.
    Zero edit fan-out; **`AppModule` and the coordinator are not touched** — which is precisely what keeps
    this slice off the (now-merged) #352 conflict path. KDoc documents the deferred live-value handoff.
  - `registerPushToken(token)` (`:541-571`) — build the `register_push_token` `Envelope` (`id =
    requestId.incrementAndGet()`, payload `MobileJson.encodeToJsonElement(RegisterPushTokenPayloadDto(
    platform = PLATFORM_FCM, token = token, deviceName = deviceName))`), then `sendAndAwaitReply(request)`
    and **ignore the returned `{}` ack payload**. ~12 lines. No `UUID` mint, no `recordLastMessage` /
    `appendMessages` / `upsertConversation`, no decode of the reply.
  - New companion constants (`:618-622`): `TYPE_REGISTER_PUSH_TOKEN = "register_push_token"` (request wire
    type), `PLATFORM_FCM = "fcm"` (the Android push platform value, AC #2). **No new error-code constant**
    — the push error codes (`server.binary_busy`, `auth.invalid_token`) flow through `mapError`'s existing
    `else` arm to `RelayErrorException` untouched.
  - **Reused as-is:** `sendAndAwaitReply` + `pendingRequests` + `requestId` (#346), the `TYPE_ACK` /
    `TYPE_ERROR` `onInbound` arms (#346 — they already complete/complete-exceptionally the pending
    deferred), and `mapError` (#346 — the non-`conversation.not_found` arm already yields
    `RelayErrorException(code, retryable, message)`, so AC #4 needs **no** new mapping).
- **`app/src/test/java/.../RemoteConversationRepositoryTest.kt`** (+111) — five new `@Test`s (below) and a
  `startRegisterPushToken(repo, token): () -> Result<Unit>` launch-on-`backgroundScope` helper mirroring
  `startSend`. The repo is constructed with an injected `deviceName = "Pixel-8"` to assert the wire field.

## Patterns established

- **A non-interface device-concern capability hosted on the concrete repo (the first of its kind).** Until
  now every live method on `RemoteConversationRepository` was a `ConversationRepository` override. This is
  the **first** public method that is *not* on the interface — a device/connection concern, reachable only
  by a caller holding the concrete instance (not via the facade ViewModels hold). The template for any
  future device-concern wire capability: host it on the concrete repo over the existing private
  `sendAndAwaitReply`, do **not** widen the interface, and treat live-caller reachability as a separate
  wiring concern owned by the slice that adds the caller. See [[post-352-connection-scoped-repo-behind-facade]].
- **A shared-sender extraction was explicitly NOT taken (simplicity-first default).** Extracting
  `sendAndAwaitReply` (plus `pendingRequests`, `requestId`, the `ack`/`error` arms, and `mapError`) into a
  shared collaborator touches the correlation core and re-wires the three existing call sites — it balloons
  past S and is its own ticket. The ticket's instruction stands: if a future device-concern slice makes the
  "why is a device op on the conversation repo" tension acute, **route the extraction back to PO as a
  separate refactor ticket** rather than smuggling it in. The fifth reuse of the private primitive (after
  #346/#347/#348 + the read paths) is evidence the in-place home is still right-shaped.
- **The fifth encode-only request DTO; reply still unmodeled.** `RegisterPushTokenPayloadDto` follows the
  #346/#347/#348 encode-only discipline (model only what is *sent*; `@SerialName` snake_case; Go-struct
  field order; always `MobileJson`). Like `send_message`, the reply is a bare `ack` — **no response DTO is
  modeled** (correlation is purely on `Envelope.inReplyTo`). See
  [[phase4-request-encoders-live-in-mutation-tickets]].

## Lessons learned

The PR ([#363](https://github.com/pyrycode/pyrycode-mobile/pull/363)) carried no *Lessons learned*
section; the non-obvious points worth recording:

- **`device_name` is a connection-level constant, so it is threaded as a constructor param, not a method
  argument.** It must equal `NoiseClientInfo.deviceName` (the same value the `hello` payload sends), which
  lives at the session/transport layer and is the same for every call on a connection — so it belongs on
  the repo's constructor, not on `registerPushToken(token)`. Making it a **last, defaulted** param is the
  whole reason this slice touches neither `AppModule` nor `RelayRepositoryCoordinator` (and so re-introduces
  no #352 conflict). See [[post-352-connection-scoped-repo-behind-facade]].
- **The default `""` is a loud cross-slice invariant the Firebase sibling owns, not a production value.**
  The default is **never exercised in production today** because the capability has no live caller. The
  Firebase sibling that adds the live caller **must also** thread the live `NoiseClientInfo.deviceName` — by
  adding a `deviceName` param to `RelayRepositoryCoordinator` and supplying it from `NoiseClientInfo` in the
  `AppModule` coordinator block (the deferred two-line change). A live caller wired *without* that threading
  would send `device_name: ""`, **polluting the server's `(platform, token, device_name)` dedup triple**.
  This is named in the spec and the constructor KDoc so a future developer does not silently rely on the
  default.
- **`platform` is a plain `String "fcm"`, not an enum, on purpose.** An encode-only DTO models only the one
  value it sends; the server keeps `Platform` a `string` and validates at the dispatcher. Do not "improve"
  it to a sealed/enum type — there is no second platform value to send from this Android client.

## Verification

- `./gradlew spotlessCheck test lint assembleDebug` — all green (PR body; RED→GREEN, 5 new tests on the
  existing fake-pump idiom). `connectedAndroidTest` N/A — pure `data/`-layer slice, no instrumented test,
  no `ComposeTestRule`, zero `android.*` imports. See [[data-layer-android-import-exception]].
- The five new tests map 1:1 to the ACs, driven with the `runCurrent()` (not `advanceUntilIdle()`) idiom
  (see [[remote-repo-test-runcurrent-not-advanceuntilidle]]):
  - **AC #1/#2 request shape** — `registerPushToken("fcm-tok-123")`; assert exactly one sent envelope with
    `type == "register_push_token"` and payload `{"platform":"fcm","token":"fcm-tok-123","device_name":
    "Pixel-8"}` (all three fields, `device_name` sourced from the injected ctor param), then feed
    `ackEnvelope(sent.id)` so the coroutine completes cleanly.
  - **AC #3** — ack completes the call successfully (`Result.isSuccess`, no throw).
  - **AC #4 retryable** — `errorEnvelope(sent.id, "server.binary_busy", retryable = true)` →
    `RelayErrorException` with `code == "server.binary_busy"` and `retryable == true`.
  - **AC #4 non-retryable** — `errorEnvelope(sent.id, "auth.invalid_token", retryable = false)` →
    `RelayErrorException` with `retryable == false` (proves a caller can branch on `retryable`).
  - **AC #5 not-Open** — `pump.sendResult = false`; the call throws `IllegalStateException` and does **not**
    hang (no reply is ever fed).
- **Code review: PASS** ([PR #363](https://github.com/pyrycode/pyrycode-mobile/pull/363), **no** MUST
  FIX / SHOULD FIX / NIT findings). The reviewer verified wire fidelity against the server SSOT, that
  `registerPushToken` mirrors `sendMessage` minus the confirmed-insert, the zero-edit-fan-out
  defaulted-param wiring (coordinator + `AppModule` untouched, confirming the post-#352 surface carries no
  conflict), and all five ACs. **Security review (label-gated, `security-sensitive`):** the architect's
  self-review PASSed (9 findings); finding [2]'s developer constraint was **verified** — no
  `Log.*`/`Timber`/`println` of the token, payload, or envelope anywhere in the new code, and
  `RelayErrorException.message` carries only server-authored control text, never the token.

## Open hand-offs (carried, not introduced)

- **Live device-name threading is the Firebase sibling's job** (see Lessons learned) — a `deviceName` param
  on `RelayRepositoryCoordinator` supplied from `NoiseClientInfo` in `AppModule`. Intentionally deferred,
  not an open question for this slice.
- **Connection-drop-mid-await leak** — inherited verbatim from [#346](346.md): a stranded deferred is freed
  on caller cancellation; no timeout added (no observed hang; Evidence-Based Fix Selection). Not specific to
  this slice.
