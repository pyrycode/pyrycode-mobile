# #307 — relay reconnect supervisor + `ConnectionStateSource` over the WS transport

The Phase 4 **reconnect-policy layer** on top of the single-connection relay WS transport ([#306](306.md)).
It owns the loop that re-dials on drop with capped-exponential backoff, maps live socket state onto the
existing [`ConnectionState`](../features/connection-state.md) surface, and **swaps the Koin binding**
`FakeConnectionStateSource → RelayConnectionSupervisor` so the connection banner reflects real
connectivity. Split from #301; sibling of the #309 Noise-session pump (code-independent, no blocker).

See the feature doc [`relay-reconnect-supervisor.md`](../features/relay-reconnect-supervisor.md) for the
evergreen "how the supervisor works / what plugs into it" reference. This file is the implementation
record. **No new ADR** — consumes [ADR 0005](../decisions/0005-okhttp-websocket-engine.md) (OkHttp WS
engine) via #306; the two cross-sibling calls (`Connected` = socket-open; transport-instance ownership)
are scoped to this layer and captured below + in the feature doc, same as #306's no-ADR posture.

## Scope

**The reconnect loop + the real `ConnectionStateSource` + the DI swap.** Out of scope, by design and
named in the spec:

- **Noise handshake + the open-state `noise_msg` decrypt/dispatch loop** — the sibling pump, [#309](https://github.com/pyrycode/pyrycode-mobile/issues/309).
  It collects #306's `inbound`; this supervisor collects only `events`. Different single-consumer streams
  → no contention, no blocker between the two. A fresh pump is built per fresh connection.
- **Process-lifecycle reconnect** (close on background / reconnect on foreground/push) — [#302](https://github.com/pyrycode/pyrycode-mobile/issues/302),
  which *drives* this supervisor's `connect()`/`close()`. This ticket's reconnect is the on-drop backoff
  loop only.
- **`4401` auth-reject handling** (`Down.code == 4401` → stop retrying / re-pair) — [#308](https://github.com/pyrycode/pyrycode-mobile/issues/308).
  This ticket retries every `Down` **uniformly**; a code comment marks the seam (`RelayConnectionSupervisor.kt:126-129`).
- **Re-implementing the dial / frame I/O** — never. Consumes #306's transport surface only.

## Summary

**Two new production files** (`RelayConnectionSupervisor.kt` + the `RelayTransportFactory.kt` fun
interface) and **one Koin edit** (`AppModule.kt`), verified by **one new JVM test file**
(`RelayConnectionSupervisorTest.kt`, 8 `@Test`) driven against a fake `RelayTransport`, the
`kotlinx-coroutines-test` virtual clock, and a **seeded `Random`** so backoff intervals are
deterministic. **No new dependency** (`kotlinx-coroutines-test` already in the catalog).

The load-bearing facts, all test-pinned:

1. **State machine.** `Connecting` while dialing → `Connected` on transport `Up` → on drop, `backoff()`
   emits either a per-second `Reconnecting(secondsRemaining)` countdown (sub-cap) or `Offline` (at the
   30 s cap) → loops back to `Connecting`. The AC-1 observed transition on an unexpected drop is
   `Connected → Reconnecting(secondsRemaining) → Connecting → Connected`. The loop discards the spent
   transport and asks the factory for a **fresh** instance to reconnect (#306 sockets are single-use).
2. **Backoff cadence** (wire-spec, `protocol-mobile.md` § Reconnect, mirrored from Go sibling pyrycode
   #247): capped-exponential bases `1 / 2 / 4 / 8 / 16` (attempts 1–5) then `30` (cap, attempt ≥ 6), with
   **±20 % jitter** — `factor = 0.8 + random.nextDouble() * 0.4`, **exactly one `nextDouble()` per
   interval** so a seeded `Random` replays deterministically. `attempt` resets to 0 only after a
   connection has been **stable ≥ 60 s** (`stableReached`).
3. **`Offline` at the cap keeps retrying.** `Offline` is "sustained unavailability → tap to retry", not a
   terminal stop — the loop keeps redialing every ~30 s while showing `Offline`.
4. **`retry()` collapses the pending backoff and never throws.** Each collapsible wait is
   `withTimeoutOrNull(ms) { retrySignal.receive() }`; `retry()` ensures the loop is running, then
   `retrySignal.trySend(Unit)` (CONFLATED — a burst collapses to one wakeup). It does **not** reset
   `attempt` (a manual retry that immediately re-fails must not let the user hammer the relay from 1 s —
   an anti-storm property). A `retry()` arriving while unpaired re-checks paired state and stays idle.
5. **Benign-unpaired = no dial, stays `Connected`.** `pairedServerStore.load() == null` → the loop sets
   `Connected` and returns; `factory.create` is never called, so the banner stays hidden (AC 3). The
   `MutableStateFlow` initial value is `Connected`, matching the Fake and `ThreadViewModel`'s
   `initialValue` — so the swapped-in-but-dormant supervisor preserves today's hidden-banner behavior
   until #302 calls `connect()`.
6. **No logs.** The only outward signal is the 4-case `ConnectionState` (no strings beyond
   `secondsRemaining: Int`). `PairedServer`, `relayUrl`, the transport, and `Down`'s `code`/`reason`/
   `cause` are never logged — mirrors #306's posture; code-review confirmed zero `Log`/`Timber`/`println`.

    — `dispatcher` + `random` are injection seams (tests pass `StandardTestDispatcher` + `Random(SEED)`),
    mirroring the `NoiseSessionFactory` injected-dispatcher idiom (`:48-53`).
  - Owns one app-singleton `CoroutineScope(SupervisorJob() + dispatcher)` (`:54`); the loop runs as a
    single child `loopJob` of it. The scope is never torn down (singleton); `close()` cancels `loopJob`.
  - `connect()` (`:72`, `@Synchronized`) — idempotency guard `if (loopJob?.isActive == true) return` so a
    repeated call can't spawn a second loop (= two dials on one transport surface).
  - `close()` (`:80`, `@Synchronized`) — cancel `loopJob`, `liveConnection.value?.close()`, reset
    `state = Connected` (intentional disconnect, banner hidden).
  - `retry()` (`:92`) — `connect()` + `retrySignal.trySend(Unit)`; non-blocking, never throws.
  - `runLoop()` (`:97`) — `load()` once; `null` → idle. Else the `while (isActive)` dial/collect/backoff
    loop. `Up` sets `liveConnection`, `Connected`, and launches the **stability timer** child; `Down` is a
    no-op (the #308 seam comment). A `try/finally` around `connect()` + `events.collect` releases the
    socket on **both** a normal `Down` and loop cancellation — incl. a transport cancelled mid-dial before
    `Up` (which `liveConnection.value?.close()` alone would miss). `stableReached` is read **after**
    `stabilityTimer.cancel()`.
  - `backoff(attempt)` (`:146`) — sub-cap per-second countdown vs at-cap `Offline`; each wait is
    `collapsibleWait()`.
  - `collapsibleWait(ms)` (`:167`) — `withTimeoutOrNull(ms) { retrySignal.receive() } != null`; true ⇒
    retry collapsed the wait.
  - top-level `internal fun backoffBaseSeconds(attempt)` (`:176`) and `jitteredBackoffMs(attempt, random)`
    (`:180`) — pure helpers the test **replays** through a fresh `Random(SEED)` for exact expected ms.
  - **Concurrency MUST-FIX (architect security self-review):** `stableReached` is an **`AtomicBoolean`**
    (`:110,123,140`), not a plain `var` — the timer child and the loop may run on different
    `Dispatchers.Default` threads, and `cancel()` alone establishes no happens-before for a plain field

## Patterns established

- **Reconnect by discard-and-rebuild, with the factory as the seam.** The supervisor never *resets* a
  spent #306 transport — it discards it and asks `RelayTransportFactory` for a fresh one. This is the
  consuming half of #306's "single-use instance = the reconnect-state-machine boundary": the lower layer
  stays a pure single-shot, and the state machine lives in exactly one place (here). When a layer above
  rebuilds all per-connection state on reconnect (Noise ephemerals are per-handshake), a per-dial factory
  beats a resettable object.
- **The `withTimeoutOrNull(ms) { channel.receive() }` collapsible wait.** A clean **stable-API** way to
  race a virtual-clock timeout against a CONFLATED signal without the experimental `select { onTimeout }`:
  non-null ⇒ the signal arrived (collapse the wait), null ⇒ full elapse. Reach for this whenever a
  cancellable/interruptible `delay` is wanted under the test clock.
- **Pure, seedable timing helpers (`jitteredBackoffMs`) replayed by the test.** Keeping the jitter formula
  in a top-level `internal fun` with an **invariant of exactly one `random.nextDouble()` per interval**
  lets the test compute the *exact* expected ms by replaying the same seeded `Random` — no tolerance
  windows, no flakiness. The pattern: when randomness must be asserted deterministically, expose the pure
  generator and have the test consume the same seed in the same order.
- **`runCurrent()` for event-driven transitions, `advanceTimeBy`/`advanceUntilIdle()` only for waits.**
  Under the test clock, settle an `Up`/`Down`-driven transition with `runCurrent()` (no virtual time
  elapses, so the 60 s stability timer can't fire by accident) and reserve time-advancing calls for the
  backoff waits. Mixing them up silently fires the stability timer mid-test and resets escalation. (See
  also Lessons.)
- **`AtomicBoolean` for a flag written by a child coroutine and read by the parent after `cancel()`.**
  Under a multi-threaded dispatcher, `cancel()` is not a memory barrier — a plain `var` read can be stale.
  This was the architect's one MUST-FIX. Belt-and-suspenders applies: the deterministic fix is the atomic,
  not "hope the threads line up".

## Lessons learned

Lifted from the PR's *Lessons learned* section:

- **`withTimeoutOrNull(ms) { retrySignal.receive() }` is the clean collapsible wait** — it races a
  virtual-clock timeout against a CONFLATED retry channel without the experimental
  `select { onTimeout(...) }`. Returns non-null ⇒ retry collapsed the wait; null ⇒ full elapse.
- **A `try/finally` around the per-connection dial+collect closes the socket on *both* a normal `Down`
  and loop cancellation** — including a transport cancelled mid-dial **before** it ever reached `Up`
  (which `liveConnection.value?.close()` alone would miss, since `liveConnection` is only set on `Up`).
- **Under the test virtual clock, settle event-driven transitions with `runCurrent()` (no time elapses)
  and reserve `advanceTimeBy`/`advanceUntilIdle()` for backoff waits** — otherwise an `advanceUntilIdle()`
  right after a `Connected` silently fires the 60 s stability timer and resets escalation mid-test. (This
  is the inverse of the #306 lesson "use `runBlocking { withTimeout }`, not `runTest`": #306's transport
  is fed by *real* OkHttp threads, so virtual time can't advance them; #307's supervisor is pure
  orchestration + `delay`, so virtual time is exactly right — the test-harness choice tracks who owns the
  threads.)
