# #532 — Wire `delete` to the daemon's `delete_conversation` v2 message

**Issue:** [#532](https://github.com/pyrycode/pyrycode-mobile/issues/532) ·
**Spec:** [`docs/specs/architecture/532-wire-delete-conversation.md`](../../specs/architecture/532-wire-delete-conversation.md) ·
**PR:** [#555](https://github.com/pyrycode/pyrycode-mobile/pull/555), `16218a3` ·
**Feature doc:** [Remote conversation repository](../features/remote-conversation-repository.md) §
`delete` (new) ·
Size **S**, `security-sensitive` (PASS).

## Summary

Replaces `RemoteConversationRepository.delete`'s inherited interface-default throw
(`error("delete is not implemented")`, `IllegalStateException`, previously inert-swallowed by the #490
guard) with a live v2 round-trip against the daemon's `delete_conversation` (server-side
pyrycode/pyrycode#822, PR #884, merged 2026-07-09). This is the delete twin of the shipped write-verbs
`rename` ([#530](530.md)) and `archive`/`unarchive` ([#549](549.md)), but diverges from both in two
load-bearing ways rather than being a blind clone: the reply is a dedicated `conversation_deleted` `{id}`
ack (not a reused `conversation_updated`), so the new reply type had to be registered in the inbound demux;
and the fold **removes** the conversation from all three read projections instead of upserting. Data layer
only — `ThreadEvent.DeleteConfirm` → `launchGuardedRepoCall { repository.delete(...) }` was already wired
by an earlier ticket and is untouched. The affordance stays `mutationsSupported`-hidden (dormant-but-ready,
family-consistent with rename/archive); the operator-facing rung-3 e2e is a separate follow-up, **#554**
(Inbox, blocked by this ticket).

## Files touched

- **`app/src/main/java/de/pyryco/mobile/data/network/DeleteConversationPayloads.kt`** (new, 40 lines) —
  bundles two DTOs in one file (the `SessionSettingsPayloads.kt` precedent, sidesteps the ktlint
  single-class-filename rule): `DeleteConversationPayloadDto` (encode-only request, `{conversation_id}`)
  and `ConversationDeletedPayloadDto` (decode-only ack, bare `{id}` — **not** `conversation_id`, no
  `@SerialName` needed). The ack's sole purpose is reply-shape validation (the `SessionSettingsUpdatedPayloadDto`
  posture); its decoded value is discarded.
- **`app/src/main/java/de/pyryco/mobile/data/repository/RemoteConversationRepository.kt`** (+99/−9):
  - `onInbound`'s correlated-success-reply `when` arm (`:335`, **load-bearing**) — adds
    `TYPE_CONVERSATION_DELETED` alongside `TYPE_ACK, TYPE_CONVERSATION_CREATED, TYPE_CONVERSATION_UPDATED,
    TYPE_SCREEN_SNAPSHOT, TYPE_SESSION_SETTINGS_UPDATED`. Without this, `conversation_deleted` falls
    through to `else -> Unit` (:474) and is silently dropped — the pending `CompletableDeferred` never
    completes, so `sendAndAwaitReply` would suspend until teardown (`failAllPending` → `IllegalStateException`,
    swallowed by the guard) and delete would silently no-op forever. `rename`/`archive` didn't need this
    step because `conversation_updated` was already registered; delete's reply type is new.
  - New `private fun removeConversation(conversationId: String)` (~:928) — the REMOVE contrast to
    `upsertConversation`: filters the id out of all **three** read projections (`projection`,
    `threadByConversation`, `lastMessages`), not just the list. The interface contract documents delete's
    post-condition across all three streams (`observeConversations`, `observeMessages` → `emptyList()`,
    `observeLastMessage` → `null`); the remote holds three separate `StateFlow`s read independently
    (unlike the fake's unified `state: Map<id, ConversationRecord>`, where `state - conversationId` empties
    all three at once), so a list-only removal would leave the other two streams emitting a hard-deleted
    conversation's rows. Idempotent by construction (`List.filterNot` / `Map - missingKey` return
    element-equal results on an absent id → `StateFlow` conflation re-emits nothing).
  - `override suspend fun delete(conversationId: String)` (~:1446) — encode
    `DeleteConversationPayloadDto` → `sendAndAwaitReply` inside a `try` scoped **only** to the await →
    `catch (IllegalArgumentException)` (exactly `conversation.not_found`, since `mapError` produces IAE at
    no other site) → `removeConversation`; return (converges as **success**, the deliberate divergence
    from rename/archive's IAE-crash-on-not-found). On the non-caught path: decode
    `ConversationDeletedPayloadDto` (the #318 shape-validation boundary — a malformed ack throws **here**,
    strictly before any removal) → `removeConversation`.
  - Two new companion constants: `TYPE_DELETE_CONVERSATION = "delete_conversation"` (request) and
    `TYPE_CONVERSATION_DELETED = "conversation_deleted"` (reply) — unlike rename/archive, both are
    referenced (no reused pre-existing reply constant).
- **`app/src/test/java/de/pyryco/mobile/data/repository/RemoteConversationRepositoryTest.kt`** (+226) —
  a `delete_*` suite (8 tests) mirroring the `archive_*` shape (`startDelete` helper +
  `conversationDeletedEnvelope(inReplyTo, id)` reply builder, cloned from `sessionSettingsUpdatedEnvelope`):
  request-encode (single `conversation_id` key), success removes from all three streams, the `id`-not-
  `conversation_id` ack field pin (a `{"conversation_id":"…"}` ack is treated as malformed — decode
  throws, no removal), not-connected → `IllegalStateException` with all streams unchanged,
  `conversation.not_found` → converges as **success** with the id removed (including an already-absent-id
  no-op case, proving conflation), other server error → `RelayErrorException` with streams unchanged, and
  malformed ack → decode throws before any removal (pins the decode-before-remove ordering, AC #2).
  No `ThreadViewModelTest.kt` change — the guard's swallow behavior for ISE/RelayErrorException is already
  covered by the pre-existing `guardedRepoCalls_whenRepositoryThrowsEachHandledType_areSwallowedWithoutCrashing` test.

## Patterns established

- **Not every reply reuses `conversation_updated`.** `rename`/`archive`/`unarchive` all fold into the
  pre-existing `conversation_updated` reply arm — easy to assume every write-verb does. Delete is the
  first to introduce a genuinely new correlated reply type, and that meant a required demux registration
  step (§ Files touched, `onInbound` :335) that the prior two mutations didn't need. When speccing a new
  mutation, check whether its reply is really a `conversation_updated` fold or needs its own type +
  registration before assuming the rename/archive template covers it end-to-end.
- **A verb's not-found mapping follows its own tolerance contract, not the family default.** `rename`/
  `archive` let `conversation.not_found → IllegalArgumentException` propagate uncaught (the #490 guard
  deliberately crashes on IAE, treating it as an impossible-by-construction bug). Delete's interface
  contract is explicitly tolerant of unknown ids, so it catches that same IAE locally and converges as
  success instead. The lesson for future mutations: read the interface KDoc's stated tolerance before
  defaulting to "propagate like the last one did."
- **REMOVE-shaped mutations need a projection-count audit, not just "mirror the fold helper."** The remote
  repo holds three separate `StateFlow`s where the fake holds one unified record; an upsert only needs to
  touch the list (`projection`), but a removal needs to touch all three or two of them silently keep
  serving a deleted conversation's rows. `removeConversation` is the first helper in this class shaped
  around that — any future removal-style mutation should reuse it rather than re-deriving the three-stream
  list from scratch.

## Lessons learned

None beyond what's captured under Patterns established above — this ticket's scope was scoped tightly
enough (spec pre-verified the daemon SSOT against the merged Go structs) that no implementation-time
surprises came up; the two structural divergences from rename/archive were anticipated in the architecture
spec, not discovered mid-build.
