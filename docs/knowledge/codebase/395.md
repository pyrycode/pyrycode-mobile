# Ticket #395 — observe the `stall` v2 wire event as a thread-observable stall state

**Issue:** [#395](https://github.com/pyrycode/pyrycode-mobile/issues/395) ·
**Spec:** [`docs/specs/architecture/395-observe-stall-state.md`](../../specs/architecture/395-observe-stall-state.md) ·
**PR:** [#405](https://github.com/pyrycode/pyrycode-mobile/pull/405) ·
**Feature doc:** [Stall state](../features/stall-state.md) ·
Split from #373 (data slice; the UI reaction is sibling #396, blockedBy this). Size **S**, `security-sensitive`.

## Summary

Decodes the capability-gated v2 `stall` control envelope into a per-conversation, thread-observable
stall **state** — `observeStall(conversationId): Flow<Boolean>` on the
[`ConversationRepository`](../features/conversation-repository.md) interface, reachable by the thread
layer through the [`StableConversationRepository`](../features/stable-conversation-repository.md)
facade (AC #4). **Onset** flips on for a decoded `stall`; **clearing** is inferred mobile-side from the
next forward-progress [`LiveSessionEvent`](../features/live-session-events.md) (the wire is onset-only —
tui-driver's `stall_detected` has no clearing edge, server SSOT pyrycode#638). Gated on the negotiated
`interactive` capability (fail-closed, defence-in-depth on top of the server-side fan-out gate);
malformed payloads dropped without tearing down the single inbound consumer (AC #3). No new class, no
new file — four additive production edits. Built test-first, RED→GREEN; all gates green
(`test`/`spotlessCheck`/`lint`/`assembleDebug`).

## Files touched

- **`data/network/InteractivePayloads.kt`** (+14, `internal`): one new `@Serializable internal data
  class StallPayloadDto(@SerialName("conversation_id") val conversationId: String)` — the peer of
  [`TurnStatePayloadDto`](../features/live-session-events.md) minus `state`. **No `toEvent()` mapper**:
  a stall is *state*, not one of the five `LiveSessionEvent` streaming events, so it never lands on
  `liveSessionEvents`. The required-`String` field is the fail-closed posture (missing/wrong-typed
  `conversation_id` fails the structural decode → dropped). Lands here, not a new file: the file doc
  already notes it carries multiple top-level types, so [[ktlint-filename-rule-single-class]] does not
  apply (cf. `MobileWireModels.kt`).
- **`data/repository/ConversationRepository.kt`** (+13): the `observeStall(conversationId): Flow<Boolean>
  = flowOf(false)` interface method, defined next to `observeLastMessage`. **Defaulted** — the
  cascade-avoidance lever (same as `delete`/`requestScreenSnapshot`/`recentWorkspaces`): the Fake and
  every inline test double inherit "never stalled" and compile unchanged; only the facade and the remote
  impl override it. The default is a semantically-meaningful zero (`flowOf(false)`), like
  `recentWorkspaces`'s `flowOf(emptyList())`.
- **`data/repository/StableConversationRepository.kt`** (+2): the facade override
  `observeStall(id) = switchToLive(false) { it.observeStall(id) }`, mirroring `observeLastMessage`.
  `whenAbsent = false` → no live connection reports "not stalled"; `flatMapLatest` cancel-old-on-switch
  means a stall never survives a reconnect (each connection builds a fresh remote repo with an empty
  set, #351).
- **`data/repository/RemoteConversationRepository.kt`** (+70): the connection-scoped
  `private val stalledConversations = MutableStateFlow<Set<String>>(emptySet())` (membership = stalled),
  the `observeStall` override (`stalledConversations.map { id in it }.distinctUntilChanged()`, 1:1 with
  `observeLastMessage`), the **onset** arm (new `TYPE_STALL` branch in the `onInbound` `when`), the
  **clearing** hook folded into the **existing** live-session arm, the `decodeStall(envelope): String?`
  helper (mirrors `decodeLiveSessionEvent`'s one-`try`/`catch (IllegalArgumentException)` drop idiom),
  and the `TYPE_STALL = "stall"` companion const.
- **`data/repository/RemoteConversationRepositoryTest.kt`** (+223): 10 new tests + a `stallEnvelope(id)`
  builder + a `collectStall`/`assertClearsStall` helper, on the existing #385 `FakeSessionPump` harness.
- **`data/repository/StableConversationRepositoryTest.kt`** (+45): 2 facade-delegation tests + a
  `pushStall`/`observeStall` override on `RecordingConversationRepository`.

## Load-bearing design choices

- **Onset and clearing are both single-writer on the one inbound collector.** `stalledConversations` is
  written **only** from `onInbound` (the lone `init`-launched collector on the connection scope), so
  onset (`+= id` on a `stall`) and clearing (`-= event.conversationId` on any decoded `LiveSessionEvent`)
  are processed in wire arrival order with **no cross-coroutine race**. `MutableStateFlow.update {}` (not
  `.value =`) matches the sibling projections' memory-visibility posture.
- **Clearing is inferred from forward progress — there is no `stall_cleared` wire type and there won't
  be one.** The `stall` payload is `{conversation_id}` only; recovery is the next *successfully decoded*
  forward-progress `LiveSessionEvent` for the conversation (ADR-025's stated model: "the phone infers
  'responding' from delta arrival"). The clearing hook reads `event.conversationId` off the
  **already-decoded** event — **no second decode**. It covers all five event types (incl.
  `turn_state: idle` and `turn_end` — both mean the quiet-while-not-idle condition no longer holds), and
  a removal of an absent id is a harmless no-op, so clearing rides every live event cheaply.
- **What does NOT clear, deliberately.** A *malformed* live envelope decodes to `null` (no trustworthy
  `conversationId` to route a clear) and an *unrecognized* `turn_state` value (e.g. a future
  `"compacting"`) maps to `null` via `TurnStatePayloadDto.toEvent()` — neither clears. Correct: we don't
  attribute forward progress we couldn't parse, and the stall persists until a *recognized*
  forward-progress event arrives rather than guessing an unknown state's semantics.
- **Capability gate on both arms (fail-closed).** Onset and clearing both sit inside
  `if (CAPABILITY_INTERACTIVE in negotiatedCapabilities())`, identical to the #385 live-session arm — a
  non-interactive phone that receives a spurious `stall` from a buggy/hostile daemon (ignoring the
  server-side fan-out gate) never decodes it and never surfaces it (defence in depth). Symmetric: onset
  and clearing share the gate.
- **On the interface (with a default), unlike #385's `liveSessionEvents`.** AC #4 requires thread
  reachability through the facade the thread already holds, and `StableConversationRepository` only
  delegates the `ConversationRepository` interface (a concrete-only capability would be stranded, per
  [[post-352-connection-scoped-repo-behind-facade]]). Stall is current-value **state** the thread needs
  through the facade — the **opposite** shape from `liveSessionEvents` (replay=0 events, concrete-only,
  deliberately off the interface). The **default body** is what keeps this from tripping the ≥5-file
  split gate: it absorbs the implementer cascade (Fake + inline test doubles inherit `flowOf(false)`),
  and there is no consumer cascade (consumers gain a callable method, none are forced to change).

## Patterns established

- **State that the thread must reach through the facade goes on the interface with a `flowOf(default)`
  body; events the thread does not need stay on the concrete repo.** #395 is the deliberate counterpoint
  to #385: same inbound collector, opposite surfacing decision, decided by *whether the consumer needs
  current-value state through the connection-churn facade*. A defaulted interface method is the
  cascade-bounded way to add a facade-reachable observable (the Fake/test-double cascade is absorbed by
  the default; cf. `recentWorkspaces`/`delete`/`requestScreenSnapshot`).
- **Inferred-recovery state from an onset-only wire signal.** When the wire carries an onset edge but no
  clearing edge, model recovery as "the next event in the *same* signal family that contradicts the
  condition" rather than waiting for a clear that will never come — and only off *successfully decoded*
  events, so unparseable/unknown traffic neither clears nor crashes.

## Lessons learned

- **`spotlessMisc` can fail with a spurious `Cannot fingerprint input property 'lineEndingsPolicy' …
  cannot be serialized` Gradle build-cache glitch.** It is environmental (a fingerprinting hiccup on
  Spotless's git-attributes line-endings policy), not a code issue — it passed unchanged on
  `--rerun-tasks`. A bare retry clears it; don't chase it as a real Spotless violation. (Lifted from the
  [PR #405](https://github.com/pyrycode/pyrycode-mobile/pull/405) *Lessons learned*.)

## Verification

- **10 new unit tests** in `RemoteConversationRepositoryTest` (onset flips on; the explicit on→off
  round-trip; each of the seven forward-progress event types clears — incl. `idle`/`turn_end`, the
  deliberate contract; malformed-stall dropped + later valid stall still flips, proving the collector
  survived; capability gate closed / other-token-only both block; per-conversation isolation; a stall to
  another conversation does not re-emit (`distinctUntilChanged`); repeated onset is an idempotent `Set`
  add; only a *successfully decoded* forward event clears — an unrecognized `turn_state` and a malformed
  live envelope both leave the stall up). **2 facade tests** in `StableConversationRepositoryTest`
  (`observeStall` emits `false` while absent; delegates to the live repo and a prior stall does not leak
  across a connection switch). All `runCurrent()`-driven per
  [[remote-repo-test-runcurrent-not-advanceuntilidle]]. RED→GREEN.
- **`security-sensitive` honored:** `decodeStall` logs nothing on the drop path (bare `catch { null }`),
  uniform with every other `onInbound` arm; the data layer surfaces only a `Boolean`. The `stall`
  payload is the **narrowest** of the interactive boundaries — `{conversation_id}` only, no free-form
  `text`/`summary`/`stop_reason` — so there is no verbatim-sensitive-content surface. Memory posture is a
  `Set<String>` of conversation ids (membership, not accumulation): repeated `stall` for the same
  conversation is an idempotent add and grows nothing — the same per-conversation-id growth posture
  `lastMessages`/`messagesByConversation` already accept under the authenticated-paired-daemon threat
  model, with the lightest footprint of the three.
- **Architect self-review PASS** (no MUST-FIX). Onset is gated, clearing rides the gated arm, single
  writer so no onset/clear race, cold per-collector flow (no cross-screen leak), connection-scoped
  lifetime.

## Open questions (flagged to #396, not pre-built here)

- **`idle`/`turn_end` clearing vs the #396 UX.** The data-layer contract is the conservative, faithful
  one: *any* forward-progress event ends the stall. If #396 wants a distinct "finished" vs "recovered
  mid-turn" presentation, that is a UI-layer derivation over `observeStall` + the existing
  `liveSessionEvents`/turn state — **not** a data-layer change here.
- **Mobile UI-leakage threats** (screenshot/overlay/accessibility eavesdropping of a stall banner) are
  out of scope for this data slice and belong to #396 (the visible reaction).
