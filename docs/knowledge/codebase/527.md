# #527 — Live-mode rung-3 e2e harness (`LIVE=1`) over the real relay

Adds a **`LIVE=1` branch** to the rung-3 harness (`scripts/e2e-emulator.sh`) that runs the existing
ping scenario — same real app, same headless emulator, same real `pyry` daemon spawning real claude —
against the **production relay** (`wss://pyrycode-relay.pyryco.de`) over TLS instead of a local loopback
relay. This is the harness-as-its-own-ticket split (mirrors pyrycode daemon #860, desktop #40): no new
test scenario, the existing #421/#481/#482 `InteractiveStreamE2ETest` methods ride the new mode as-is.
It exists to catch the live-environment failure class a local-relay run structurally cannot — the
2026-07-03 connect-drop loop was a five-week-stale relay deploy, invisible to any local run. Prerequisite
pyrycode#854 (daemon interactive-bootstrap deadlock + liveness gate) had landed, unblocking the real
round-trip. **Zero app-side Kotlin change** — `E2eTestApplication` already stores the injected `relayUrl`
verbatim and `OkHttpRelayTransport` already rides TLS for `wss` without special-casing the scheme.

## Files touched

- **`scripts/e2e-emulator.sh`** — the only code change (+103/-29 lines), all in the existing config →
  preflight → relay → pair → daemon → test-run pipeline; the non-`LIVE` paths are byte-identical.
  - Config block: `LIVE="${LIVE:-}"` plus a mutual-exclusivity guard with `DETERMINISTIC` (real vs
    scripted claude can't both apply). The relay-URL and instance-name assignments now branch on `LIVE`:
    both `DAEMON_RELAY_URL`/`PHONE_RELAY_URL` derive from one `LIVE_RELAY_HOST` (default
    `pyrycode-relay.pyryco.de`) so an operator override can't break the daemon-needs-`/v1/server`
    vs. phone-gets-base-URL asymmetry. `PAIR_NAME`/`PYRY_NAME` default to `e2e-live` (distinct from
    default-mode's `e2e-emulator`).
  - Preflight: the `RELAY_BIN` `command -v` check is skipped when `LIVE` is set (no local relay to find).
  - Relay start + `/healthz` poll: wrapped in `if [ -z "${LIVE}" ]`. `RELAY_PID` stays unset on LIVE, so
    the existing `cleanup()` trap's guard no-ops — no new teardown logic.
  - Pairing: **unchanged** — LIVE takes the existing non-deterministic `else` branch verbatim (real
    `$HOME`, `-pyry-name="${PYRY_NAME}"`), pairing before the daemon starts (load-bearing: the daemon
    loads `devices.json` once at boot and never reloads it).
  - Daemon start: a new `elif [ -n "${LIVE}" ]` arm sibling to the `DETERMINISTIC`/default arms. Dials
    `PYRY_RELAY_URL="${DAEMON_RELAY_URL}"` (now `wss://…/v1/server`) and **never sets
    `PYRY_ALLOW_INSECURE_RELAY`** — the flag is omitted by construction in this arm, not gated by a
    runtime conditional.
  - Test-run: `TEST_TARGET` scopes to
    `InteractiveStreamE2ETest#interactiveTurn_pingPrompt_streamsPingReplyIntoThread` only on LIVE (one
    real-claude turn; the full class also runs the #481 tool-use test, a second turn).
- **`docs/e2e-interactive-stream.md`** — new "Live mode (rung 3, live relay)" section (what it runs,
  how it differs from default rung 3, prerequisites, cost, first-run assumptions) plus updates to the
  ladder's rung-3 bullet and the "How to run" verification-status list. Written directly against the
  AC by the developer as part of the same commit — this file does not duplicate that content.
- **`docs/specs/architecture/527-live-mode-e2e-harness.md`** — the architect's spec (design source for
  the above; includes the mode matrix, error-handling table, and security review).

**Not touched:** any Kotlin, Gradle, or the `InteractiveStreamE2ETest` / `E2eTestApplication` /
`E2eInstrumentationRunner` credential seam — confirmed by design and by the diff. No new instrumented
test method, no new fixture.

## Patterns established

- **Isolation-by-instance-name, not by HOME, when the scenario needs real claude.** Rung 4
  (`DETERMINISTIC`) isolates via a short-lived `/tmp` HOME because `fakeclaude` needs no auth. LIVE (real
  claude) cannot do that — an isolated HOME would strip the operator's `~/.claude` subscription auth — so
  it isolates via `-pyry-name=e2e-live` under the **real** `$HOME` instead, namespacing identity +
  `devices.json` + `conversations.json` under `~/.pyry/e2e-live/` and leaving production instances
  (different names, this Mac and pyrybox) untouched. Any future real-claude-against-live-infra mode
  should follow this same by-name isolation, not attempt an isolated HOME.
- **Security-load-bearing flags belong in a dedicated arm, not a runtime conditional.** LIVE's
  never-set-`PYRY_ALLOW_INSECURE_RELAY` guarantee comes from a separate `elif` daemon-start branch that
  simply never writes the flag — the same shape as `promote`/`rename`'s dedicated encode paths elsewhere
  in the codebase. Prefer this over `[ -n "${LIVE}" ] || …` conditionals wrapping a shared line when the
  omission itself is the security property.
- **Derive asymmetric URL pairs from one shared host var.** `DAEMON_RELAY_URL`/`PHONE_RELAY_URL` both
  compute from a single `LIVE_RELAY_HOST`, so an operator override of the host can't accidentally
  reintroduce the base-vs-`/v1/server` mismatch (which would silently 404-loop the daemon). Same
  principle as the existing loopback pair (`127.0.0.1:${PORT}` vs `10.0.2.2:${PORT}`).

## Lessons learned

None beyond what's captured in Patterns established — this ticket was scoped tightly (S) and landed
