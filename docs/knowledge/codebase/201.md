# #201 — feat(ui/thread): wire ConnectionBanner into ThreadScreen

Wires the [`ConnectionBanner`](../features/connection-banner.md) composable (#200) into [`ThreadScreen`](../features/thread-screen.md) via [`ThreadViewModel`](../features/thread-screen.md), completing the connection-banner triad started by [#196](./196.md) (data-layer source) and [#200](./200.md) (composable). The banner sits **between** `ThreadTopAppBar` and the message `LazyColumn` inside a `Column` wrapper — pushing content down, not overlaying — and short-circuits to zero height under the `Connected` steady state. The VM grows one constructor arg (`ConnectionStateSource`), a `connectionState: StateFlow<ConnectionState>`, and a non-`suspend` `retry()` that launches `source.retry()` on `viewModelScope`.

See the updated [Thread screen](../features/thread-screen.md) feature doc for the full design rationale on the `Column` wrapper, `weight(1f)` choice, and the separate-`StateFlow` posture.

## Summary

- **Banner is structural, not overlay.** The `Scaffold` content slot becomes `Column { ConnectionBanner(...); LazyColumn(weight=1f) { ... } }` rather than `Box`-with-overlay or `topBar = { Column { TopAppBar; ConnectionBanner } }`. Per the AC the banner pushes the message list down by its intrinsic height; under `Connected` the banner's early `return` collapses to zero height so the steady-state look is byte-identical to pre-#201.
- **`Modifier.padding(inner)` moved from `LazyColumn` to the outer `Column`.** The scaffold's content-inset wraps the banner *and* the list — applying `padding(inner)` only to the `LazyColumn` would let the banner draw under the AppBar's status-bar inset on edge-to-edge devices. The list now carries `Modifier.fillMaxWidth().weight(1f)` (not `.fillMaxSize()`); inside a `Column`, `fillMaxSize` ignores `weight` semantics and would over-claim vertical space.
- **`reverseLayout = true` is preserved.** No semantic flip; the banner sits at the top of the visual column, the message list still scrolls upward from the bottom — unchanged from #126's scaffolding decision.
- **Connection state is exposed as a separate `StateFlow<ConnectionState>`, not folded into `ThreadUiState`.** The AC explicitly allowed either; separating keeps the existing `state` derivation (`observeConversations(All).map { ... }.stateIn(...)`) untouched and avoids `combine(...)` ceremony plus churn to the existing seven `ThreadViewModelTest` methods that pattern-match `ThreadUiState`. The destination block consumes two `collectAsStateWithLifecycle()` calls — the same shape already used at `MainActivity.kt:218-225` for `SettingsViewModel`'s four separate flows.
- **`SharingStarted.WhileSubscribed(5_000)` matches the existing `state` flow.** Both flows share the same `viewModelScope` and subscription window; no asymmetry to reason about. If the screen resumes within 5s of leaving, the existing upstream collector is reused — no `Connected` flash from re-subscription.
- **`initialValue = ConnectionState.Connected`** matches the fake's seeded value and gives the screen a non-null first frame without a `Loading` shim. The banner's `Connected` short-circuit means the first paint shows no banner — correct steady-state.
- **`fun retry()` is non-suspend.** The VM owns the `viewModelScope.launch` that calls `connectionStateSource.retry()`. UI callers bind `vm::retry` directly to `ConnectionBanner`'s `onRetry: () -> Unit` slot — no `rememberCoroutineScope { ... }.launch { ... }` wrapping at the destination. Same shape as the existing `fun sendMessage(text: String)` from #188.
- **No `try/catch` around `connectionStateSource.retry()`.** Per the interface KDoc (#196), failures surface as state transitions (`Offline`), not exceptions; the Phase-2 no-op fake cannot throw. No `.catch { ... }` on the upstream `observe()` either — premature defense.
- **`viewModel { ThreadViewModel(get(), get(), get()) }` resolves all three deps via the existing Koin bindings.** The third `get()` lands on the `FakeConnectionStateSource` singleton bound at `AppModule.kt:31` since #196 (`single { FakeConnectionStateSource() } bind ConnectionStateSource::class`). No new bindings, no new imports.
- **Destination block at `MainActivity.kt:197-211` adds one `collectAsStateWithLifecycle()` and two named arguments.** `connectionState = connectionState`, `onRetry = vm::retry`. Method-reference syntax — no fresh-lambda allocation per recomposition. `collectAsStateWithLifecycle` is already in scope from the prior `state` collection.
- **`ThreadScreen` signature grows two non-default params** (`connectionState: ConnectionState`, `onRetry: () -> Unit`) placed **between** `onSendMessage` and `modifier`. The convention in this codebase is `modifier` between required params and optional defaulted ones; the order is `(state, onBack, onSendMessage, connectionState, onRetry, modifier, onTitleClick = {}, onOverflowClick = {})`. The previews update with `connectionState = ConnectionState.Connected, onRetry = {}` — steady-state baseline only, no `Offline` / `Connecting` previews here because the four-state matrix already lives in `ConnectionBannerPreviewMatrix` from #200; duplicating would add no fidelity.
- **Three new VM tests + a `makeVm(...)` helper.** Every existing `ThreadViewModel(handle, repository)` site grew a third arg; rather than threading a new fixture through seven call sites, `private fun makeVm(handle, repository, source = FakeConnectionStateSource())` was added as a file-private helper (same pattern as `ChannelListViewModelTest.makeVm` from #239). The default arg keeps tests that don't care about connection state terse; the three new tests pass a custom source explicitly.
- **`RecordingConnectionStateSource` is a 10-line file-private test double.** The shipped `FakeConnectionStateSource.retry()` is a no-op, so an assertion-of-effect through the fake has nothing to observe. The recording double increments a `retryCallCount: Int` counter on each `retry()` call; pre-staging this as a public-ish helper under `data/repository/` would be premature (no other consumer needs it). Same "test fixture lives at the bottom of the test file" posture as `fixedRepo(...)`.

## Patterns established

- **When a global concern (connection state, future: auth/idle/online-presence) needs to land on an existing screen, prefer a separate `StateFlow` on the existing VM over folding into the screen's `UiState` data class.** The fold would require `combine(...)` plumbing, would couple a per-screen state shape to a cross-screen concern, and would churn every test that pattern-matches the existing `UiState`. The separate-flow pattern means the destination block consumes two `collectAsStateWithLifecycle()` calls — already canonical in this codebase (see `MainActivity.kt:218-225` for `SettingsViewModel`'s four-flow shape). The fold-into-`UiState` posture is reserved for state that's *intrinsic* to the screen's data load (loading / error / empty); orthogonal global state stays separate.
- **`fun <action>()` on a ViewModel is non-suspend; the VM owns the `viewModelScope.launch` body that calls the suspend dependency.** UI callers bind `vm::<action>` directly to the composable's `() -> Unit` slot. Same shape as `fun sendMessage(text: String)` from #188; same shape as `fun retry()` here. Pattern: never expose `suspend fun` on a VM — the destination block is recomposable and binding `vm::suspendThing` as a `() -> Unit` would not compile. The wrap-in-`viewModelScope.launch` boilerplate is one line; pay it at the VM, not at the destination.
- **`makeVm(...)` file-private helper with a defaulted dependency arg is the right shape when one of a VM's deps gets a non-trivial test fixture but most tests don't care about it.** Existing call sites swap `ThreadViewModel(...)` → `makeVm(...)` mechanically (`grep`-replace clean); new tests that care about the dep pass an explicit fixture. Same shape as `ChannelListViewModelTest.makeVm` from #239. Pattern applies whenever a VM grows a new constructor arg and the existing test file has more than three call sites — a default-arg helper is cheaper than threading the new fixture through every site.
- **A "recording" test double (counter-only, no state-machine) is a 10-line file-private fixture; don't promote to `data/repository/` until a second consumer needs it.** The recording double is purpose-built for "assert that `retry()` was called" — pre-staging a `RecordingConnectionStateSource` under `data/repository/` would have added a non-test API surface that no production code or other test needs. Two consumers is the canonical extract threshold here.
- **For `Column { Banner; LazyColumn }` shapes, the `LazyColumn` carries `.fillMaxWidth().weight(1f)`, not `.fillMaxSize()`.** Inside a `Column`, `fillMaxSize` ignores `weight` semantics and over-claims vertical space, fighting with siblings. The right shape: width via `fillMaxWidth`, height via `weight(1f)`. Pattern applies to any future "horizontal-rule banner above scrolling list" layout (session-boundary delimiters from #135, future status rows from #145).

## Lessons learned

- **`Modifier.padding(inner).fillMaxSize()` belongs on the new outer wrapper, not the `LazyColumn`.** Pre-#201 the `LazyColumn` directly consumed the `Scaffold`'s `inner` padding. Post-#201 the wrapper `Column` owns the inset and the `LazyColumn` only carries `fillMaxWidth().weight(1f)`. If the inset stays on the `LazyColumn` and the banner is appended *outside* it, the banner draws under the AppBar's status-bar inset on edge-to-edge devices. The spec called this out; the fix is one-modifier-relocation but easy to miss when the diff is "add a `Column` wrapper".
- **Inside a `Column`, `Modifier.fillMaxSize().weight(1f)` and `Modifier.fillMaxWidth().weight(1f)` are not equivalent.** `fillMaxSize` claims both `width = max` and `height = max` *before* the `Column`'s `weight` distribution runs, so the child over-claims and pushes its siblings off-axis. The correct shape is `fillMaxWidth().weight(1f)` — width pinned, height computed by the parent's weight pass. The spec's "use `.fillMaxWidth().weight(1f)` not `.fillMaxSize()`" was the load-bearing modifier note for this slice.
- **`vm::retry` (method reference) is one character shorter than `{ vm.retry() }` and Compose-stable across recompositions because `vm` itself is stable.** No `remember { ... }` wrapping needed at the destination block. Same shape as `vm::sendMessage` from #188. The spec called this out as an "open question" with a documented preference; settling it here keeps a code-review nit off the table.
- **The recording test double cannot reuse `FakeConnectionStateSource` because the fake's `retry()` is a no-op.** The fake exists to seed and update `ConnectionState` via `emit(...)`; it has no `retryCallCount`. An assertion-of-effect through the fake would have nothing to observe. The recording double exists strictly to test the VM-to-source forwarding contract, not to test the Phase-2 fake's behaviour. When Phase 4 lands a real `ConnectionStateSource` implementation, the test contract stays the same — only the source binding swaps.
