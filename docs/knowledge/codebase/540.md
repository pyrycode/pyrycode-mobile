## Summary

Replaces the `ThreadEvent.NewSession -> Unit` silent no-op (`ThreadViewModel.kt:621` pre-change) with a call
to `ConversationRepository.startNewSession`, the bare fire-and-forget `new_session` v2 send #539 shipped.
Two observable outcomes, both cloning an existing VM idiom rather than inventing a new one:

- **Success is passive.** `new_session` has no ack/reply; the client learns it worked when the daemon later
  emits `session_transition (reason: "clear")`, which the pre-existing [#336](336.md) fold already renders
  as a thread delimiter. This slice sends and discards the placeholder `Session` return — no delimiter
  rendering of its own.
- **Failure is not-connected only,** surfaced as a transient snackbar with a **fixed local string**
  (`new_session_failed`), never the exception's message — the #452/#490 confidentiality posture applied to a
  new send path.

**Deliberately not `launchGuardedRepoCall`** — that helper inertly swallows failures with no surface (#490),
the opposite of this ticket's contract. A dedicated `sendNewSession()` method was added instead, cloning the
`modalSendErrors` one-shot-channel idiom (#452) rather than the guarded-call idiom the other four overflow
mutations use.

## Files touched

- **`ui/conversations/thread/ThreadViewModel.kt`** (+41/−2):
  - New `private val newSessionErrorChannel = Channel<Unit>(capacity = Channel.BUFFERED)` +
    `val newSessionErrors: Flow<Unit> = newSessionErrorChannel.receiveAsFlow()` (`:368`) — payload-free
    one-shot signal, structurally identical to `modalSendErrors`; nothing sensitive can flow through a
    `Unit`.
  - New `private fun sendNewSession()` (`:550`): `viewModelScope.launch { repository.startNewSession(conversationId) }`
    wrapped in **exactly two catches, in this order**:
    1. `catch (e: CancellationException) { throw e }` — **must precede** the typed catch below, because
       `j.util.concurrent.CancellationException extends IllegalStateException` on the JVM; a bare ISE catch
       would swallow `viewModelScope` teardown mid-send.
    2. `catch (e: IllegalStateException) { newSessionErrorChannel.trySend(Unit) }` — the not-connected
       surface. No `RelayErrorException` branch: `startNewSession` is fire-and-forget (no awaited reply), so
       a correlated server `error` can never originate — an unreachable branch was deliberately omitted
       (evidence-based fix selection), a documented deviation from the `sendInterrupt`/`onDropQueued` swallow
       twins, which keep an inert `RelayErrorException` catch for parity.
  - `ThreadEvent.NewSession -> Unit` (`:621`) → `ThreadEvent.NewSession -> sendNewSession()`.
- **`ui/conversations/thread/ThreadScreen.kt`** (+8): new defaulted `newSessionErrors: Flow<Unit> = emptyFlow()`
  parameter placed **after `modifier`**, alongside `modalSendErrors` (the Compose `ComposeParameterOrder`
  lint rule errors on a defaulted param placed before `modifier`/trailing lambdas — this placement satisfies
  it). A second `LaunchedEffect(newSessionErrors,
  snackbarHostState) { newSessionErrors.collect { snackbarHostState.showSnackbar(newSessionFailedMessage) } }`,
  a structural clone of the `modalSendErrors` collector, reusing the same `SnackbarHostState`.
- **`MainActivity.kt`** (+1): `newSessionErrors = vm.newSessionErrors` added to the `ThreadScreen(...)` call
  site. `onOverflowEvent = vm::onOverflowEvent` already carried `NewSession` — no other wiring needed.
- **`res/values/strings.xml`** (+1): `new_session_failed` = "Couldn't start a new session. Check your
  connection." — fixed local text, added beside `modal_send_failed`.
- **`ThreadViewModelTest.kt`** (+132): adapted the three `sendInterrupt` test shapes
  (`ThreadViewModelTest.kt:638-720`) to the *surfacing* (not swallowing) contract, driving a fake
  `ConversationRepository` whose `startNewSession` throws (the archive/delete throwing-repo shape,
  `:840-920`) rather than an injected lambda double:
  - routing — `onOverflowEvent(NewSession)` invokes `startNewSession` exactly once with the VM's own
    `conversationId`; no error emitted.
  - not-connected failure surface — fake throws `IllegalStateException`; asserts `newSessionErrors` emits
    exactly one `Unit` **and** installs a default uncaught-exception handler (the #430 interrupt-affordance
    lesson) to prove the throw never escaped the launched coroutine — `viewModelScope` is a separate
    `SupervisorJob`, so a leaked throw would not otherwise fail `runTest`.
  - cancellation not swallowed — a suspending-gate `startNewSession` held in-flight, then `viewModelScope`
    cleared; asserts no crash and no error emission, guarding the catch **ordering**.

**Not touched (deliberate scope decision):** `ThreadOverflowMenu.kt`'s `if (mutationsSupported)` gate
(`:49-78`) that hides the whole "New session / Rename / Change workspace / Archive" group in relay mode. The
architect declined to un-gate `NewSession` alone — it would produce an inconsistent partial menu (Rename is
also wired via #530 yet would stay hidden; Change workspace / Archive still throw and must stay hidden). A
coherent per-item gate is a family-wide decision, not a #540-local one. A real relay user cannot reach this
wiring yet; it is verified at the component/VM seam only. See the #537 family ("gate cleared ≠ buildable").

## Patterns established

Second confirming instance of the **surfacing** one-shot-channel idiom (first was `modalSendErrors`, #452):
when a fire-and-forget send's only client-observable failure needs a user-visible surface (not a swallow),
clone `Channel<Unit>(BUFFERED).receiveAsFlow()` + a paired `LaunchedEffect` snackbar collector, rather than
routing through `launchGuardedRepoCall`. Also reinforces the `CancellationException`-must-precede-`IllegalStateException`
catch ordering as the default shape for any VM send path wrapping a `check(...)`-throwing repository call —
third instance after `sendInterrupt`/`onDropQueued` (which swallow) and now `sendNewSession` (which surfaces).

## Lessons learned

- **A repository call's exception-catch set should mirror what the *wire contract* can actually produce, not
  what a sibling send path happens to catch.** `sendInterrupt`/`onDropQueued` keep an inert `RelayErrorException`
  catch for parity even though it's dead code for their fire-and-forget frames; this ticket's spec explicitly
  declined to copy that dead branch into `sendNewSession`; since `startNewSession` awaits no reply, a
  correlated server `error` can never reach the catch. Copy-pasting a sibling's catch list is not automatically
  correct — verify against what the specific call can throw.
- **"Surface" and "swallow" are both valid one-shot-channel consumers of the same idiom shape** — the channel
  mechanics (`Channel<Unit>(BUFFERED).receiveAsFlow()`, `LaunchedEffect` collector) are identical whether the
  VM chooses to notify the user (`modalSendErrors`, now `newSessionErrors`) or stay silent (`sendInterrupt`'s
  empty catch body). The decision of *which* is a per-call contract question, not a mechanical one — don't
  assume the presence of the idiom implies either surfacing or swallowing.
