# #482 — Layer 3 (real claude): thinking spinner during a real turn

Adds **one** real-claude emulator e2e scenario on the **shipped #421 harness**
(`InteractiveStreamE2ETest`, rung 3 / **Layer 3** of the mobile interactive-stream e2e ladder,
`docs/e2e-interactive-stream.md`): a **pure-reasoning, no-tool** prompt makes **real claude think for a
beat**, and the test asserts the **thinking spinner is displayed while the turn is active**. It is the
**real-claude twin** of [#454](454.md) (rung 4 / Layer 2a, deterministic scripted spinner coverage) and
[#432](432.md) (Layer 1a, the in-process component twin) — the `turn_state(thinking)` → `isThinking` →
`ThinkingIndicator` render path is now exercised at **all three ladder layers**.

The render path it exercises — `turn_state(thinking)` → [`ThreadViewModel.isThinking`](406.md) →
`ThinkingIndicator` (#406) — is **already shipped and reviewed**. This ticket *exercises* it end to end
against real claude; the only seam that changes is **the prompt + the asserted spinner affordance**. **No
production Kotlin, no new files, no new types** — one additive `@Ignore`d `@Test` method + one private
helper val + one companion prompt constant + two imports in the existing test, plus a coverage/assumptions
update in the developer-owned `docs/e2e-interactive-stream.md`. NOT `security-sensitive` (no new
untrusted-input parse point; the author-controlled prompt flows to real claude on the operator's host, not
to a parser on the phone), no Figma (asserts against the already-anchored thinking spinner, thread `16-8`).

**Why this is the only layer that catches the drift it targets:** the spinner is **screen-sourced** —
pyrycode's daemon derives `turn_state` by watching real claude's live TUI screen. The scripted rung-4
backend (#454) emits a *fixed* `turn_state` and is structurally **blind** to claude changing its own screen
text. Layer 3 is the only rung that runs real claude over the real Noise/relay path, so claude changing the
pre-output screen text the spinner pattern is matched from surfaces *here* — as a `waitUntil` timeout —
**that is the finding the layer exists to produce**, not a flake to paper over.

## The central design decision — assert the *transient* spinner's presence mid-turn, and ship `@Ignore`-gated

This is the **flakiest** scenario on the ladder, and it diverges from **both** twins. Each twin has a lever
to hold the turn open so the transient `thinking` state is observable in flight:

- **Rung 4 (#454, scripted)** uses a **two-drop causal fence**: drop A is a `thinking`-only fixture that
  leaves the turn open with `isThinking == true` indefinitely (presence assertable), then a 2nd message
  fires drop B (end-of-turn) clearing it (absence assertable).
- **Rung 1 (#432, component)** drives `pushTurnState` imperatively in-process — it can pause between
  `thinking` and the resolution.

**Neither lever exists at rung 3.** There is no scripted backend to hold the turn, and the test cannot
imperatively pause real claude between `turn_state(thinking)` and the first `assistant_delta`. The moment
claude emits its first token the daemon flips `turn_state` to `responding`, `isThinking` goes false, and
`ThinkingIndicator` **early-returns** (`ThinkingIndicator.kt:45`) — **the node disappears with no trace.**
[#481](481.md) solved its analogous problem by keying on a **durable** terminal signal (the verbatim
`"Bash"` tool name that survives turn-end in the resolved tool row). **The thinking spinner has no durable
equivalent**: once the turn moves on, nothing of it remains on screen.

So the design is:

1. **Presence-only, mid-turn.** The single load-bearing assertion catches the spinner content-description
   while the turn is in its thinking phase, with the same tolerant idiom as the twins:
   `waitUntil(REPLY_TIMEOUT_MS) { onAllNodes(hasContentDescription(thinkingDescription))…isNotEmpty() }`
   then `…onFirst().assertIsDisplayed()`. Tolerant, never on counts or timing.
2. **No absence-after-end assertion.** Asserting "the spinner cleared" would need the two-drop fence to make
   the transition deterministic; at rung 3 a second real-claude turn would itself re-enter `thinking` and
   re-show the spinner, so an absence check would race a 2nd turn — exactly the "never on timing" failure
   the ladder forbids. The AC explicitly authorizes *not* asserting absence-after-end.
3. **`@Ignore`-gated by default (a documented manual case).** The developer cannot verify reliability —
   green is operator-gated on real infra (no device in the dev loop), and the window is transient and
   unfenceable. The safe landing is a documented **manual** case: the positive `@Test` ships `@Ignore`d with
   a one-line un-ignore instruction (mirroring #421's negative-control and #481's sibling precedent), *not*
   an unproven always-on test that would inject flake into the operator suite. The operator un-ignores on
   first run; **if** the spinner proves reliably catchable, the operator *may* promote it to always-on.

**The assertion target is a production content-description, not a claude-output substring** —
`cd_thread_thinking` ("Agent is thinking") is emitted only by `ThinkingIndicator` (merged onto the `Row` via
`semantics(mergeDescendants = true)`, `ThinkingIndicator.kt:54`). This makes it materially simpler than the
#481/#421 siblings:

- **No prompt-collision concern.** #481/#421 assert on claude *output* substrings (`"Bash"`, `"ping"`) and
  must engineer the prompt to omit/baseline-count the token. Here the matched token is a UI string that
  never appears in any user bubble, title, or claude output — so the prompt's *only* job is to widen the
  thinking window, never to avoid the token.
- **No negative control needed (a deliberate divergence from the sibling pattern).** #481/#421 each ship an
  `@Ignore`d negative control to prove their *substring matcher is selective*. There is no analogous
  selectivity to disprove here — the assertion keys on a unique production content-description. The
  `@Ignore`d positive test *is* the manual case. This divergence is documented in the test KDoc so code
  review does not read the missing negative control as a gap.

### The prompt

`THINK_PROMPT` is a **pure-reasoning** determinism lever that invokes **no tool**:

```
Without using any tools, take a moment to reason this through silently, then reply with only
the single word: ready. (Reason through first: what is the 12th prime number?)
```

- **No tool → the #481 permission-modal unknown does not apply.** #481's chief first-run risk was the #428
  permission modal interposing on a real tool call (the rung-3 daemon spawns claude with no bypass flag,
  `scripts/e2e-emulator.sh:342`). A prompt that keeps claude *thinking* with no tool call sidesteps that
  surface entirely — the prompt explicitly forbids tool use so claude does not reach for one.
- **Widen the thinking window.** The spinner shows during `turn_state(thinking)` — the gap between send and
  the first `assistant_delta`. Asking claude to reason a beat and answer with only a short token widens that
  gap. **Correctness does not depend on the window being reliably catchable** — that is precisely why the
  test ships `@Ignore`d. The exact wording is the developer's to tune on first operator run.

## Patterns established

- **At a layer that can't hold a turn open, a transient signal with no durable artifact ships
  `@Ignore`-gated, not always-on.** #481 keyed on the durable tool name that survives turn-end; the thinking
  spinner has no such equivalent (the node vanishes the instant `isThinking` flips false), and rung 3 has no
  fence (#454's two-drop) and no imperative pause (#432's `pushTurnState`) to make the mid-turn window
  deterministic. The general rule this slice sets: **when you cannot prove a transient assertion reliable,
  land it as a documented manual case the operator may promote** — never inject an unproven always-on test
  into the suite. This is the spinner-side complement of #481's "key on the durable terminal signal" rule:
  where #481 *had* a durable signal and used it, #482 *has none* and gates instead.
- **No negative control when the asserted token is a production content-description (deliberate divergence
  from the substring-asserting siblings).** #421/#481 assert on claude *output* substrings and each ship an
  `@Ignore`d negative control to prove the matcher is selective. The spinner assertion keys on
  `cd_thread_thinking`, a UI string emitted only by `ThinkingIndicator` and never present in any user
  bubble, title, or claude output — there is nothing for a negative control to disprove, so the `@Ignore`d
  positive test *is* the manual case. Document the divergence in the KDoc so review does not read the
  absence as a gap.
- **A content-description target removes the prompt-collision tax.** Because the matched token never appears
  on screen except from the spinner itself, the prompt has *one* job — widen the thinking window — and never
  has to omit or baseline-count the asserted token the way #421's "ping" and #481's "Bash" prompts must.

## Lessons learned

*(Lifted from the PR #484 Lessons-learned section.)*

- **At a layer that can't hold a turn open, a transient signal with no durable artifact ships
  `@Ignore`-gated, not always-on.** #481 keyed on the durable tool name that survives turn-end; the thinking
  spinner has no such equivalent, so the safe landing is a documented manual case the operator may promote —
  not an unproven always-on test that injects flake.
- **No negative control here, deliberately.** The spinner assertion keys on a production content-description
  (`cd_thread_thinking`) that never appears in any user bubble, title, or claude output — there is nothing
  for a negative control to disprove. The `@Ignore`d positive test *is* the manual case; the KDoc documents
  this so review doesn't read the absence as a gap.
- **No absence-after-end assertion.** At rung 3 a second real-claude turn would re-enter `thinking` and
  re-show the spinner, so asserting "cleared" would race a 2nd turn — the "never on timing" failure the
  ladder forbids.
- **The chief first-run unknown is whether the screen-sourced window is catchable at all.** Whether a
  pure-reasoning, no-tool prompt yields a `turn_state(thinking)` window long enough to lay out and poll the
  spinner over the relay depends on how pyrycode's daemon maps claude's pre-output state and on claude's own
  latency — **unverifiable from this repo**. If real claude answers too fast to catch, keeping the test
  `@Ignore`d is the documented manual outcome, **not** a build failure. If claude streams its reasoning as
  *visible* text, `turn_state` flips to `responding` immediately and the spinner clears at once — the "reply
  with only a short token after thinking" framing is the lever; tune the prompt on first run.

## Verification

The deliverable **is** the test; there is no unit test of it. Host-JVM checks (no device, per the rung-3
precedent), confirmed green:

- `./gradlew compileDebugAndroidTestKotlin spotlessCheck test lint assembleDebug` — all green. The explicit
  `compileDebugAndroidTestKotlin` is required because the mandatory gates do **not** compile androidTest
  ([[androidtest-not-compiled-by-mandatory-gates]]); the two new imports (`InstrumentationRegistry`, `R`)
  resolve.
- `connectedAndroidTest` not run (no device/emulator); the actual green is operator-gated via
  `bash scripts/e2e-emulator.sh` (the **default** rung-3, real-claude path), exactly as #421/#481. Because
  the method ships `@Ignore`d, the operator runs it explicitly after temporarily removing `@Ignore` (or via
  a runner arg that includes ignored tests):
  `-Pandroid.testInstrumentationRunnerArguments.class=…InteractiveStreamE2ETest#interactiveTurn_thinkPrompt_showsThinkingSpinnerDuringTurn`.
  No script change.
- First-green prototype, not a hardened gate — expect to tune the prompt and confirm the screen-sourced
  window on first run, exactly as #421/#431/#454 did.
