# #141 — feat(ui/dialogs): Rename dialog wiring (Figma 19:14)

Replaces the `Unit` no-op on the `ThreadEvent.Rename` branch of `ThreadViewModel.onOverflowEvent` (introduced by [#251](./251.md), mounted by [#252](./252.md)) with the real flow: a Material 3 `AlertDialog` (`RenameDialog`) pre-filled with the current conversation name and full-range selected so typing immediately overwrites, exposing `Save` (disabled when trimmed input is blank or unchanged) and `Cancel`. On Save the dialog emits the trimmed name; the VM clears the visibility flag synchronously and launches `repository.rename(state.value.conversationId, name)`. On Cancel / outside-tap / back-press the dialog closes with no repository call. First per-item follow-up of the four `[Rename, ChangeWorkspace, ChannelInfo, NewSession]` cases left as exhaustive `Unit` arms by [#252](./252.md).

## Summary

- **New `RenameDialog` composable lives in `ui/conversations/components/`**, public visibility (sibling [`CreateFolderDialog`](../features/create-folder-dialog.md) is `internal` only because its host lives in the same package; this dialog's host is in `ui/conversations/thread/`, hence `public`). Lifts the [`CreateFolderDialog`](../features/create-folder-dialog.md) structure wholesale — public composable → file-private `*Internal` seam → `AlertDialog` + `OutlinedTextField` + `FocusRequester` + `TextFieldValue` + `derivedStateOf`-gated `enabled` flag — with two substantive deltas: (i) the seam seeds `TextFieldValue(initialName, TextRange(0, initialName.length))` so the full name is selected on first composition (AC #2 "typing immediately overwrites" comes for free from the M3 `OutlinedTextField`'s standard replace-selection behaviour on keystroke); (ii) `isSaveEnabled` is a two-part gate `trimmedName.isNotEmpty() && trimmedName != initialName` rather than just `trimmedName.isNotEmpty()` — the unchanged-name check is what makes the rename dialog distinct from the create dialog.
- **`ThreadEvent` grew two variants** for the dialog half of the flow: `data class RenameSubmit(val name: String)` and `data object RenameDismiss`. Placed immediately after the existing `data object Rename` so the rename family stays contiguous in the sealed surface. `RenameSubmit.name` is the trimmed name — the dialog is the trim authority; the VM forwards `event.name` to `repository.rename` without re-trimming. **The `data class` is the first parameter-bearing case in `ThreadEvent`** — until #141 all five cases were `data object`. This sets the precedent (per the [#251](./251.md) feature-doc note) that "a future menu item with a payload migrates that case to `data class`."
- **`ThreadUiState` gained `showRenameDialog: Boolean = false`**, placed next to the existing `workspacePickerVisible: Boolean = false` so dialog-visibility flags cluster. Default `false`; the data-class default position keeps every pre-existing equality assertion in `ThreadViewModelTest` compiling unchanged.
- **`ThreadViewModel.onOverflowEvent` `when` was rewritten** to handle the three rename cases explicitly and keep `NewSession`, `ChangeWorkspace`, `ChannelInfo` as the only remaining `Unit` arms. The three new arms: `Rename → pendingRenameDialog.value = true` (replaces the [#251](./251.md) no-op); `RenameSubmit(name) → pendingRenameDialog.value = false; viewModelScope.launch { repository.rename(state.value.conversationId, name) }` (flag flips **synchronously before** the launch so dismissal is immediate and a re-tap of `Rename` during an in-flight rename has well-defined state); `RenameDismiss → pendingRenameDialog.value = false`. The `viewModelScope.launch { repository.rename(...) }` shape is byte-identical to the existing `Archive` / `sendMessage` / `changeWorkspace` launchers — fire-and-forget, no `Job` retention, conversation id read from `state.value.conversationId` for one-grep convention.
- **`pendingRenameDialog: MutableStateFlow<Boolean>` is the fourth source folded into the main `combine(...)` block** on `ThreadViewModel.state` — `combine(observeConversations(All), observeMessages(id), pendingWorkspacePicker, pendingRenameDialog, selectedModelFlow)`. Five flows total, which is exactly the native overload arity ceiling for `kotlinx.coroutines.flow.combine` — adding a sixth source in a future ticket will require either a `combine(vararg ...)` switch or pre-folding two of the inputs (the latter is cheap; `pendingRenameDialog` and `pendingWorkspacePicker` could collapse into a `data class DialogVisibility(...)` pre-combiner). **The VM-owned vs. screen-hoisted decision matters.** `showRenameDialog` lives on `ThreadUiState` (VM-driven) rather than as `var showRenameDialog by rememberSaveable { mutableStateOf(false) }` on `ThreadScreen` (which is how `sheetVisible` from [#254](./254.md) and `overflowExpanded` from [#252](./252.md) work) because dialog visibility here carries semantic content — the user invoked `Rename`, the dialog represents an in-progress operation against `Conversation` state, and a future tap-to-rename TopAppBar entry point will dispatch through the same `ThreadEvent.Rename` event. Hoisting on the screen would force the screen to know about every alternative entry point; centralising on the VM keeps the dialog single-sourced. The opposite choice for `overflowExpanded` / `sheetVisible` is documented at [#252](./252.md) as "UI-local presentation state with no business meaning the VM needs to react to" — `showRenameDialog` fails that test.
- **`ThreadScreen` renders `RenameDialog` as a `Scaffold` sibling** alongside [`WorkspacePicker`](../features/workspace-picker.md) and [`StatusSheet`](../features/status-sheet.md), gated on `if (state.showRenameDialog) { RenameDialog(initialName = state.displayName, onSubmit = { onOverflowEvent(ThreadEvent.RenameSubmit(it)) }, onDismiss = { onOverflowEvent(ThreadEvent.RenameDismiss) }) }`. **`initialName` is `state.displayName`**, not the raw `Conversation.name` — `displayName` already encodes the `"Untitled channel"` / `"Untitled discussion"` fallback for blank names (via the private `Conversation.displayName()` extension at `ThreadViewModel.kt:172-174`), so the Save-disabled-on-unchanged check uses the same string the user sees in the title bar. Sourcing from a different field would create a UX divergence where the title bar says `"Untitled channel"` but the dialog opens with `""` and Save is enabled on `"Untitled channel"`.
- **Four new `R.string.rename_dialog_*` keys** in `strings.xml` (`_title`, `_field_label`, `_save`, `_cancel`). Namespace is `rename_dialog_*` rather than `thread_overflow_*` because a future TopAppBar tap-to-rename entry point will reuse them without their key suggesting a wrong origin. Different posture from [`CreateFolderDialog`](../features/create-folder-dialog.md), which kept its labels inline — the architect spec called out string extraction explicitly here for the multi-entry-point reuse case.
- **`MainActivity` is not touched.** The `onOverflowEvent = vm::onOverflowEvent` binding was wired at [#252](./252.md); method-reference syntax handles the two new `ThreadEvent` variants automatically. No new arguments on the `composable(Routes.CONVERSATION_THREAD)` destination block.
- **`RecordingRepo` (the private test double in `ThreadViewModelTest.kt`) grew a real `rename(...)` body** — gained `val renameCalls = mutableListOf<Pair<String, String>>()` and replaced the previous `TODO("not used")` body with a recorder that returns a minimal `Conversation(id, name, ...)`. Tests assert on `renameCalls` directly; the return value is unread. Same direct-call-shape-assertion idiom established by [#251](./251.md) for `archiveCalls`. The `onOverflowEvent_otherCases_doNotCallArchive` test (also [#251](./251.md)) dropped `ThreadEvent.Rename` from its iteration list — `Rename` now mutates state, so it's no longer a no-op case.

## Patterns established

- **VM-owned dialog-visibility flags (vs. screen-hoisted `rememberSaveable`) when the dialog represents in-progress operation state.** `pendingRenameDialog: MutableStateFlow<Boolean>` on `ThreadViewModel` mirrors the existing `pendingWorkspacePicker` shape from [#137](./137.md) — both surface to `ThreadUiState` (`workspacePickerVisible`, `showRenameDialog`) and both are written by VM event handlers. Contrast against `var overflowExpanded by rememberSaveable { mutableStateOf(false) }` ([#252](./252.md)) and `var sheetVisible by rememberSaveable { mutableStateOf(false) }` ([#254](./254.md)), which live on `ThreadScreen`. The discriminator: a flag belongs on the VM when (a) the dialog represents semantic state (in-progress rename, in-progress workspace selection) the VM has authority over, or (b) the dialog has multiple potential trigger points the VM unifies (the rename dialog's eventual TopAppBar tap-to-rename entry point will dispatch the same `ThreadEvent.Rename`, and centralising on the VM keeps the dialog single-sourced). A flag belongs on the screen when it's pure UI presentation state with no business meaning (`overflowExpanded`, `sheetVisible`).
- **First parameter-bearing case in `ThreadEvent`.** `data class RenameSubmit(val name: String)` — the [#251](./251.md) feature doc reserved this shape for future need (`"a future menu item with a payload migrates that case to data class"`). #141 is that future. The trimmed-name-at-the-event-boundary contract (rather than passing raw text and trimming in the VM) keeps the trim authority at the UI layer, where blank/whitespace validation also lives. Apply to any future event whose payload originates in a UI-validated input.
- **Public-plus-file-private-`*Internal`-seam shape lifted wholesale from [`CreateFolderDialog`](../features/create-folder-dialog.md).** This is now the canonical shape for any pre-filled-input `AlertDialog` in this codebase. Public wrapper takes `initialName: String`, seeds `TextFieldValue(initialName, TextRange(0, initialName.length))`, delegates to the seam. Previews target the seam directly so they can demonstrate "edited" states without runtime input. Tests target the public composable (the seam stays file-private).
- **`combine` arity ceiling at five.** `ThreadViewModel.state` is now `combine(observeConversations, observeMessages, pendingWorkspacePicker, pendingRenameDialog, selectedModelFlow)` — exactly at the native overload ceiling. The next ticket that adds a source must either switch to `combine(vararg ...)` (loses the named-receiver-lambda ergonomics) or pre-fold two inputs (e.g. roll `pendingWorkspacePicker` + `pendingRenameDialog` into a `data class DialogVisibility(...)`). Recording the ceiling here so the next pull doesn't accidentally hit it without a plan.

## Lessons learned

- **`performTextReplacement(...)` (not `performTextInput(...)`) is the right Compose-test primitive for a pre-seeded `OutlinedTextField`.** `RenameDialog` opens with `initialName` populated and full-range selected — `performTextInput` would *append* to the seeded text (resulting in `"old name" + "new name"` = `"old namenew name"`) because it doesn't honour the pre-set selection. `performTextReplacement` replaces the entire field content, which is what the dialog's runtime UX produces when the user starts typing over the selection. The first three iterations of `RenameDialogTest` used `performTextInput` and the trimmed-equality assertions silently passed because `"old name" + "new name"` trim-equals neither `"new name"` nor `"old name"` — the assertion was wrong but green. The fix landed on the fourth iteration after `tapping_save_invokes_onSubmit_with_trimmed_text` started asserting on the captured value rather than just the disabled state. Apply to any future `androidTest` of a pre-seeded field.
- **`hasSetTextAction() and hasText("old name")` is required to disambiguate the field node from the title `Text`.** The dialog title is `Text("Rename")` and the field is pre-filled with the conversation name; in the field-prefill test (`field_prefills_with_initial_name`) using just `onNodeWithText("old name")` would either fail (no match — the title doesn't carry `"old name"`) or accidentally match a future test where the conversation happened to be named `"Rename"`. `hasSetTextAction()` narrows to the editable node (`OutlinedTextField` and `BasicTextField` both expose the `SetText` semantics action; static `Text` does not). Same idiom is documented in [`CreateFolderDialog`](../features/create-folder-dialog.md)'s test suite at [#213](./213.md); copied verbatim here.
- **`isSaveEnabled` keyed on `initialName` (`remember(initialName) { derivedStateOf { ... } }`) is defensive, not load-bearing.** Under current flow `initialName` is stable for the dialog's lifetime — the host gates the dialog with `if (state.showRenameDialog)`, which tears it down between renames. The keying is there so that if a future caller binds `initialName` to a value that mutates while the dialog is open (e.g. a streaming rename from another device in Phase 4), the `enabled` flag recomputes correctly. Without the key, Compose's `derivedStateOf` captures the *initial* `initialName` value and never recomputes the `trimmedName != initialName` comparison against an updated anchor — leading to a silently-disabled Save in the cross-device-rename scenario. Worth keeping even though the scenario is hypothetical; the cost is one `remember` key argument.
- **`fire-and-forget viewModelScope.launch { repository.rename(...) }` is correct here even though `rename` returns `Conversation`.** The return value is unread by the VM (the state flow re-emits naturally when `repository.rename` mutates the underlying `observeConversations` set; no manual `_state.value = ...` write needed — same shape as `Archive`). A future ticket that needs the *new* `Conversation` reference immediately (e.g. to surface a "renamed to X" snackbar) would need a `Job` retention pattern or a different shape; out of scope at #141. The `FakeConversationRepository.rename` may throw `IllegalArgumentException` on unknown id; the launch does not catch — exceptions propagate to the coroutine exception handler. Same posture as `Archive`. Production unreachability is by construction (the id we pass is `state.value.conversationId`, which by construction exists or the screen wouldn't be open).
- **The `data class RenameSubmit(val name: String)` placement after `data object Rename` matters for grep readability.** Sealed surface order is now `[NewSession, Rename, RenameSubmit, RenameDismiss, ChangeWorkspace, Archive, ChannelInfo]` — the rename family stays contiguous, which makes `grep -n "Rename" ThreadViewModel.kt` produce three adjacent lines instead of three scattered ones. Apply to any future event family that adds dialog Submit/Dismiss companions.
- **Trim-before-compare (`trimmedName != initialName`, not `fieldValue.text != initialName`) is the load-bearing equality choice.** The `save_disabled_when_trimmed_input_equals_initial_name` test types `"  kitchenclaw  "` against `initialName = "kitchenclaw"` and asserts Save stays disabled — without the `trim()` before compare, surrounding whitespace would silently enable Save and the user could submit a "rename" that the repository then trims to a no-op. The test is the regression artifact; the `derivedStateOf { trimmedName.isNotEmpty() && trimmedName != initialName }` body is the implementation.
