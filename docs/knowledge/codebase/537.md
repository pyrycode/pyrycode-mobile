## Summary

Adds `interactiveTurn_renameConversation_relabelsTopBarAndListRow` to `InteractiveStreamE2ETest` — the
**last** ticket in the mutation-e2e family (#541/#551/#554/#562/#537), and the one that closes it out.
Creates a scratch discussion, drives the **real** thread overflow "Rename" → `RenameDialog` to a
runtime-unique title, submits, and asserts the new title appears **durably** on **two** surfaces after the
`rename_conversation` round-trip: the **thread top bar** (in-thread, immediately after submit — there is
**no** `PopBack`, so `state.displayName` re-labels in place) and the **conversation list** recents row
(after popping back). Zero production code: one new always-on `@Test` + one companion constant
(`RENAME_NAME_PREFIX = "e2e537-"`), one `scripts/e2e-emulator.sh` LIVE-curation edit (sextet → **septet**,
still 3 turns), and the ladder doc — all landed in this single PR.

Rename is the **lowest-risk** member of the family: the four shipped siblings already drive the real
`RenameDialog` as a **seeding** step (renaming a scratch discussion to a runtime-unique name before delete /
archive / change-workspace). This ticket promotes rename from a seed to the **subject** of its own scenario
— the flow was already de-risked, only the assertion target changes.

This card had previously parked in Inbox on the same family-wide reachability gate as its siblings: the
"Rename" overflow item is `mutationsSupported`-gated, and that flag was hard-`false` in relay mode. PR #572
flipped `RemoteConversationRepository.mutationsSupported` to `true`, clearing the gate for the whole family;
four of the five siblings had already shipped through the pipeline by the time this ticket was pulled,
proving the family buildable. `rename` is **conversation-scoped** (`{conversation_id, name}`, a line-for-line
mirror of `change_workspace` and `delete`, **no** session transition), so — unlike the session-scoped
settings e2e (#545, blocked on `currentSessionId == ""`) — it carries no session dependency and sits in the
same clean-buildable camp as the already-shipped conversation-scoped e2e's.

## Files touched

- **`app/src/androidTest/java/de/pyryco/mobile/e2e/InteractiveStreamE2ETest.kt`** (+122, one new `@Test`,
  a 7-step scenario):
  1. Land on the channel list (`CD_NEW_DISCUSSION` present), `awaitConnected()`.
  2. Create a plain discussion; wait for the send button (thread-arrival marker). A plain discussion
     suffices — "Rename" is `mutationsSupported`-gated only, reachable on it.
  3. **Absence guard (before-state, deterministic, no claude turn):** `uniqueName = RENAME_NAME_PREFIX +
     System.currentTimeMillis()` asserted `assertCountEquals(0)` on screen — same guard as #562 step 3.
  4. Drive the **real** overflow: `CD_MORE_ACTIONS` → wait for `RENAME_ITEM` ("Rename") → tap → wait for
     `hasSetTextAction() and isFocused()` (disambiguates the dialog's field from the thread composer, which
     is also editable) → `performTextReplacement(uniqueName)` on the pre-filled + fully-selected field →
     `RENAME_SAVE` ("Save").
  5. **Top-bar assertion (AC-2, surface #1 — in-thread, no PopBack):** `waitUntil` spans the
     `rename_conversation` round-trip for `uniqueName` (substring) to appear, then `onFirst()
     .assertIsDisplayed()`. By the time this wait first matches, `RenameDialog` has already left composition
     (`Save` flips `showRenameDialog` false synchronously) — the match is the top bar, not the dismissing
     field (see § Gotcha below).
  6. **List assertion (AC-2, surface #2 — after popping back):** tap `CD_BACK`; wait for the list marker
     (`CD_NEW_DISCUSSION`), then wait for `uniqueName` on a recents row and confirm displayed — a genuine
     inversion of step 3's absence, on a different surface, same unique token.
  - New companion constant (all other constants — `RENAME_ITEM`, `RENAME_SAVE`, `CD_NEW_DISCUSSION`,
    `CD_SEND_MESSAGE`, `CD_BACK`, `CD_MORE_ACTIONS`, the timeouts — reused verbatim from the shared
    companion object, first declared by #554): `RENAME_NAME_PREFIX = "e2e537-"` (kept distinct from
    #554's `CONVERSATION_NAME_PREFIX`, #551's `ARCHIVE_NAME_PREFIX`, #562's `WORKSPACE_FOLDER_PREFIX` — the
    shared companion object forbids redeclaration; each scenario owns its own prefix).
- **`scripts/e2e-emulator.sh`** (+22/−12) — the LIVE branch's `TEST_TARGET` extends sextet → **septet**
  (ping + create-workspace-folder + new-session + delete + archive-restore + change-workspace + rename);
  every "sextet / 6 methods" prose spot (header, usage line, run-block comments, PASS log) bumped to
  "septet / 7 methods, still 3 turns" — rename adds a method, not a turn.
- **`docs/e2e-interactive-stream.md`** (+86/−17) — ladder rung-3 description (now nine scenarios), the
  rename scenario's always-on rationale, the no-PopBack / top-bar-re-labels-in-place distinction from
  delete/archive, the field-disambiguation gotcha, Pre-ship gate / Live-mode "what it runs"/cost (septet,
  still 3 turns), and the Follow-ups section — all updated in this same PR, the developer wiring the doc
  note directly per the architecture spec (matching #554/#551/#562's discipline).

**Not touched:** no production `app/src/main` file changes — this ticket exercises the already-shipped
#530 `rename` wire, the existing `ThreadOverflowMenu`/`RenameDialog`/`ThreadScreen` UI, and PR #572's
`mutationsSupported` flip.

## Patterns established

None new at the harness level — the **closing** instance of the rung-3 real-claude scenario shape
(#481/#482/#566/#541/#554/#551/#562's template): create → drive the real affordance → tolerant
substring/presence assert on a runtime-unique token, absence-before → presence-after inversion. This ticket
completes the **mutation-e2e family** (#541/#551/#554/#562/#537) — all five conversation-scoped write verbs
(new-session, archive/restore, delete, change-workspace, rename) now have a rung-3 real-claude scenario in
the LIVE pre-ship gate. No new production surface, no new companion helper beyond the one prefix constant.

## Lessons learned

(Lifted from the PR body's own Lessons-learned section.)

- **`README.md` § Pre-ship gate is stale, independent of this ticket.** It still describes only "the live
  rung-3 ping scenario / one real claude turn" and was never synced through #566/#541/#554/#551/#562 either
  — the doc-sync gap predates #537 and was already flagged owed by #551. This ticket's spec scoped doc
  edits to `docs/e2e-interactive-stream.md` only, so the README stays out of sync; a dedicated doc-sync
  ticket is still owed (same follow-up #551 flagged, now carried by a fifth sibling).
- **The family's last member confirms the reachability-gate lesson need not repeat per-ticket once
  re-verified.** Unlike #562 (which had to individually re-verify its own park rationale against `main`
  after PR #572 landed), #537 only needed to confirm the general family gate was cleared — four of five
  siblings had already shipped, which was itself sufficient evidence this ticket was buildable without a
  fresh per-ticket reachability investigation.
