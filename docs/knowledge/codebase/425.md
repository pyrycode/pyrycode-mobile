# Ticket #425 — streaming synthetic turn must never share a LazyColumn key with a persisted message

**Issue:** [#425](https://github.com/pyrycode/pyrycode-mobile/issues/425) ·
**Spec:** [`docs/specs/architecture/425-streaming-turn-id-collision-dedup.md`](../../specs/architecture/425-streaming-turn-id-collision-dedup.md) ·
**PR:** [#426](https://github.com/pyrycode/pyrycode-mobile/pull/426) ·
**Feature doc:** [Streaming assistant turns](../features/streaming-assistant-turns.md) ·
Surfaced by the [#421](https://github.com/pyrycode/pyrycode-mobile/issues/421) rung-3 live e2e. Size **S**, `security-sensitive`.

## Summary

A render-time **key-uniqueness guard** on the [#337](337.md) streaming fold. Against the live pyrycode
`main` daemon a turn's `turnId` can **equal** the persisted assistant `message_id`. The fold renders an
in-flight turn as a synthetic `MessageItem` whose `id` is the `turnId`, and the thread keys every
`MessageItem` as `"msg:<id>"` — so when the synthetic and the finished message are both in the list they
produce the **same** LazyColumn key and Compose throws
`IllegalArgumentException: Key "msg:<id>" was already used`. The #337 structural finalise misses this
collision (see Lessons). The fix appends the synthetic **only when no finished `MessageItem` already
carries the turn's id** — one guard clause in `ThreadFold.render()`, plus the now-false render comment
corrected and one new collision test. **No new types, no data-layer change, no DI change, no visual
change.**

Production — **2 files**, zero new files, zero new types:

  file-private pure `ThreadFold.render()` (`:532`):
  - **The guard** (`:539`), immediately after `val turn = stream ?: return finished` and **before** the
    synthetic is constructed:
    ```kotlin
    if (finished.any { it is ThreadItem.MessageItem && it.message.id == turn.turnId }) return finished
    ```

left unchanged — the invariant is enforced upstream at the assembly point.

## Load-bearing design choices

- **Render-level guard, not a reduce/finalise change.** The crash is a list-key uniqueness failure, and
  `render()` is the single point where the rendered `items` list (and therefore its keys) is assembled.
  Enforcing the invariant there is **source-independent** (it makes no assumption about *why* the ids
  collide) and **total over every interleaving**. A reduce-time fix cannot catch the load-bearing
  ordering: the `Finished` projection carrying the colliding message arrives *before* the first delta
  creates `stream`, and the `turnPersisted` finalise in `reduce` is guarded by `stream != null`, so it
  never re-fires for that already-passed projection. Only a render-time check sees both the live `stream`
  and the standing `finished` together.
- **Belt-and-suspenders, different fabric.** The existing baseline-diff finalise (suspenders) still drops
  the stream in the *non-colliding* case. The render guard (belt) deterministically guarantees key
  uniqueness in the *colliding* case. Both are deterministic code; neither relies on the other.
- **Why not a `stream:` key prefix** (the ticket's alternative "root" option). Namespacing the synthetic
  key would stop the *crash* but not the *double-render*: in the colliding-at-baseline window both the
  finished message and the synthetic are present, so the thread would show **two** assistant bubbles with
  the same text — AC #2 forbids that. A prefix would therefore *also* need a finalise fix. The render
  guard alone satisfies AC #1 (no crash) **and** AC #2 (settles to exactly one), so it is strictly less
  code for a better result.
- **The lingering `stream` is left alone.** In the colliding ordering the baseline-diff finalise never
  fires, so `stream` lingers as non-rendered state until the next turn's first delta supersedes it. This
  is harmless: `render()` keeps suppressing the synthetic while the persisted message is present, and
  `distinctUntilChanged` (`ThreadViewModel.kt:180`) collapses the no-op re-emissions, so no flicker. No
  reduce-time null-out was added — it would be dead in the load-bearing ordering and no AC needs it
  (Evidence-Based Fix Selection: no observed failure from the lingering stream).

## Patterns established

- **Enforce list-key uniqueness at the assembly point, not in the reducer — especially when the colliding
  key is server-controlled.** A render-time guard over the already-assembled list is total over every
  interleaving; a reduce-time finalise can only catch the orderings in which its trigger fires. When a
  list key can collide for *any* reason (here a server-chosen `turnId` equalling a `message_id`), assert
  uniqueness where the keys are produced, source-independently.
- **A comment asserting a property of a server-controlled value is an assumption, not an invariant.** The
  #337 comment claimed the synthetic id lived in a namespace "distinct from the server message_id" — a
  property of an attacker-/daemon-chosen value that held against the fake and broke against the live wire.
  Encode the real invariant defensively in code (the guard), not as a comment that the next reader trusts.

## Lessons learned

- **The #337 dedup's documented worst case was wrong in *direction*, and the live e2e proved it.** #337's
  § Open questions (and `streaming-assistant-turns.md`) framed the reconnect-mid-turn risk as a backfilled
  **new** assistant id finalising the streaming item **early** — "worst case is an early settle, **never a
  duplicate**." The real live failure is the **opposite**: the colliding id is *already in*
  `baselineAssistantIds` at turn start, so the structural finalise never sees a "new" id, never fires, and
  the synthetic and finished message coexist → **duplicate key → crash**. "Never a duplicate" was false
  against the live daemon. A long-standing structural-dedup assumption that looks airtight against a fake
  can have an unconsidered ordering the real wire hits; the #337 codebase/feature docs are corrected to
  match.
- **`turnId == message_id` is a real daemon behaviour, not a hypothetical.** The finished `message` carries
  no `turn_id` ([[phase4-v2-wire-no-streaming]]), so mobile correlates structurally and *assumed* the two
  id spaces were disjoint. pyrycode `main` sets them equal. The fix makes **no** assumption about the
  relationship between `turnId` and `message_id`; whether the daemon should stop doing this is a separate
  server question, out of mobile scope.
- **`spotlessCheck` is repo-wide and inherits unrelated red gates.** A single pre-existing unused
  `asStateFlow` import on `main` made `./gradlew check` fail independent of this diff; removed mechanically
  to green the gate. The accompanying `Format was not able to resolve all violations … in …/Theme.kt` line
  is a **benign ktlint warning, not a failure** (a fresh `spotlessCheck --rerun-tasks` is BUILD SUCCESSFUL
  with `Theme.kt` untouched) — QA initially misread it as a needed manual edit. See
  [[spotless-could-not-autocorrect-warning-benign]]. The unused import is worth a hygiene ticket.

## Verification

- **2 new `ThreadViewModelTest` cases**, test-first RED→GREEN (the collision test fails `["t1","t1"]`
  without the guard). The key-uniqueness assertion `messageIds(vm) == messageIds(vm).distinct()` is the
  VM-level proxy for the LazyColumn crash — a duplicate id is exactly a duplicate `"msg:<id>"` key. No
  `ComposeTestRule` (no new composable; the behaviour is entirely the VM fold). All pre-existing fold
  tests use distinct ids and stay green unchanged — proof the non-colliding path (AC #3) is preserved.
- `./gradlew test lint assembleDebug` all green; `./gradlew check` and `spotlessCheck --rerun-tasks` green
  after the import removal. `connectedAndroidTest` not run (no device; unit-only, no new composable).
- **Code review: PASS** ([PR #426](https://github.com/pyrycode/pyrycode-mobile/pull/426)), **zero blocking
  findings** (one NIT: the `assertEquals(expected, actual)` operands are swapped in the new asserts — reads
  correctly either way, left as-is). The reviewer traced all four ACs against the fold internals, confirmed
  the guard lands at the render altitude the spec prescribes, and that `render()` is `private` with a
  single internal caller (contained blast radius).
- **Security re-audit (`security-sensitive`): PASS.** The fold sits on the network-input boundary
  (consumes the server-controlled `turnId`). The guard runs only over already-confined sources — `finished`
  (conversation-scoped `observeMessages`, #313) and `stream` (populated only after `reduceLive`'s
  `conversationId` guard) — so no foreign-conversation path is introduced. `turnId`'s only use is an
  equality compare whose worst case **withholds the synthetic** (the safe outcome — the persisted message
  renders); it never mutates or evicts a persisted message. **No logging** of `turnId`, delta text, or any
  payload field was added (the #337 MUST holds). The change **closes** a server-triggerable dup-key crash
  (DoS) rather than opening one — net posture improves.
