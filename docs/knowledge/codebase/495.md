# #495 — Recover re-keying after a lost re-key `noise_resp` (bounded response watchdog)

**Issue:** [#495](https://github.com/pyrycode/pyrycode-mobile/issues/495) ·
**Spec:** [`docs/specs/architecture/495-rekey-response-watchdog.md`](../../specs/architecture/495-rekey-response-watchdog.md) ·
**PR:** [#516](https://github.com/pyrycode/pyrycode-mobile/pull/516) ·
**Feature doc updated:** [Noise session pump](../features/noise-session-pump.md) ·
Size **S**, `security-sensitive`. Commit `7341e2a`.

## Summary

Closes a mobile-initiator gap in the [#304](304.md) re-key loop: `initiateRekey` sets
`rekeyInFlight = true` **before** sending the re-key `noise_init`, and the inbound `noise_resp` handler was
the **only** code that cleared it and re-armed the 1-hour cadence (`rebaseRekeyTimer`). The one-shot timer
coroutine that fired *this* re-key had already completed its `delay`, so a **single dropped `noise_resp`**
wedged `rekeyInFlight` `true` forever — every future `initiateRekey` hit the `if (rekeyInFlight …)
return@withLock` guard and silently skipped, running the transport indefinitely on **un-rotated keys**. No
response timeout existed.

The fix arms a bounded, injectable **response watchdog** (`rekeyRespTimeoutMs`, default `30_000L`)
immediately after the re-key `noise_init` is sent; the completing `noise_resp` cancels it, and on timeout it
funnels to the existing idempotent `teardown` → the [reconnect supervisor](../features/relay-reconnect-supervisor.md)
([#307](307.md)) rebuilds a fresh pump → fresh handshake → fresh keys → the cadence re-arms. This is the
mobile mirror of the Go initiator's WS-4426 reply deadline (`pyrycode`
[#450](https://github.com/pyrycode/pyrycode/issues/450)). One production file + its test.

**This supersedes #304's deliberate "no phone-side re-key reply timeout" deferral.** #304 omitted the
timeout as evidence-based YAGNI ("no observed stuck-session"); the Cross-Repo Code Review 2026-07-03
supplied the evidence — a *deterministic* wedge provable from the code (lost resp → `rekeyInFlight` stuck
→ guard skips forever) plus the server already defending the mirror case — so the deferred fix (the
`withTimeoutOrNull`-style bounded window #304 named) landed here. See [`noise-session-pump.md`](../features/noise-session-pump.md)
§ Re-key triggers for the evergreen "how completion + the watchdog work" reference (the now-stale "why no
reply timeout" note was rewritten by this ticket).

## Why teardown, not same-session retry

`NoiseIkSession.writeRekeyInit` requires `check(pendingRekey == null)` (`NoiseIkSession.kt:189`). An
abandoned re-key leaves `pendingRekey` **non-null**, and only `session.close()` clears it (`:281-282`). So a
"just clear `rekeyInFlight` and retry" path silently dead-ends at `writeRekeyInit` unless a new session-level
abandon API is added — extra surface for no gain. Given the **single-re-key-in-flight** invariant there is no
in-session state worth salvaging once a re-key is abandoned, so funnelling the timeout through the existing
`teardown(cause)` **is** the recovery: it wipes keys, downs the transport, and #307 rebuilds. Per the
pipeline **"different fabric"** rule, the safety net for a stochastic dropped frame is code-level teardown,
not a second best-effort retry.

## Patterns established

- **Bound a "before-the-observable-side-effect" flag with a watchdog on the same event that would clear it.**
  When an in-flight flag is set before an irreversible send and is cleared *only* by the reply, a lost reply
  wedges the flag forever. Arm a finite watchdog with the flag and cancel it on the same reply that clears
  the flag; on timeout, recover deterministically. Here the flag is `rekeyInFlight`, the reply is the re-key
  `noise_resp`, and the recovery is `teardown` (not a re-arm — see below).
- **Recover an abandoned single-in-flight protocol op via teardown, not same-session retry, when the retry
  precondition can't be re-established in-session.** `writeRekeyInit`'s `check(pendingRekey == null)` means a
  same-session retry dead-ends unless a new abandon API is added; teardown + fresh handshake reaches the same
  recovered state (fresh keys, cadence re-armed) with **zero** new surface. The "different fabric" safety net
  for a dropped frame is deterministic code (teardown), never a second best-effort send.
- **Arm the watchdog after the send and inside the `try` — placement is correctness, not style.** Arming
  *after* `writeRekeyInit`/`send` means a racing-teardown `IllegalStateException` (caught just below) never
  arms an orphan watchdog; arming *inside* the `try` means only an init actually put on the wire starts the
  clock. Cancel *before* `readRekeyResp` so the disarm is unconditional once a resp for an in-flight re-key
  is confirmed (a MAC-fail resp is then both cancelled here and redundantly cancelled by teardown's
  `scope.cancel()` — either order is correct).
- **Job-cancellation suffices; no generation counter needed.** The single-re-key-in-flight invariant means a
  new re-key can only start after the resp handler cleared `rekeyInFlight` — and that same handler cancelled
  the prior watchdog first. So watchdog A is always cancelled by resp A before re-key B can arm watchdog B; a
  stale watchdog cannot fire during a later re-key. (The only unguarded window — a resp processed *between*
  the `send` and the field assignment — is not physically realizable: a network reply can't precede the init
  it answers, the same assumption the file's existing off-mutex `rekeyInFlight = false` already rides.)
- **The watchdog only calls `teardown` — it never re-arms the 1-hour timer.** Routing the timeout through
  teardown (rather than clearing the flag + re-arming `rekeyTimerJob`) preserves `rekeyTimerJob`'s
  documented **drive-coroutine-only** single-writer invariant. Recovery is transport-driven: teardown always
  `transport.close()`s, and #307 reconnects on the `Down` event regardless of the `Closed` cause — the fault
  cause is for observability, not for triggering the reconnect.

## Lessons learned

Lifted from the PR's *Lessons learned* section (and already saved as a reusable memory,
[[injectable-timeout-breaks-advanceuntilidle-tests]]):

- **Adding *any* finite watchdog changes what `advanceUntilIdle()` does to sibling tests.**
  `advanceUntilIdle()` fast-forwards through **all** pending delays — including the newly-armed
  `delay(rekeyRespTimeoutMs)`. So every existing `#304` re-key test that fired a re-key and then called
  `advanceUntilIdle()` *before* delivering the `noise_resp` now fast-forwards past the watchdog deadline and
  **tears the session down** — failing an `assertEquals(Open …)` or silently preempting the teardown the
  test meant to exercise. The fix is to change the **driving**, not the deadline: replace the re-key-firing
  `advanceUntilIdle()` with a bounded `advanceTimeBy(REKEY_MS); runCurrent()` that reaches the timer but
  leaves the watchdog dormant (the default 30 s watchdog sits far beyond any bounded advance these tests
  make). **Growing the timeout does not help** — `advanceUntilIdle()` reaches *any* finite delay. The
  `rekey_request` path is a `scope.launch{…}` at current time, so bare `runCurrent()` (no clock advance)
  runs it. Only pre-`#304` tests (no re-key in flight → no watchdog) and post-`close()`/post-teardown drains
  may safely keep `advanceUntilIdle()`.
- **A code-review-proven logic gap is valid evidence to revisit an evidence-based YAGNI deferral.** #304
  deferred this timeout on "no observed stuck-session"; the deterministic wedge (provable from the code) plus
  the server already defending the mirror case was sufficient evidence to land the deferred fix — no field
  observation of a real stuck session was required, because the failure mode is deterministic given a lost
  frame.

Non-blocking NIT from code review (left as-is, harmless): `NoiseSessionPumpTest.kt`'s `REKEY_MS` KDoc still
reads "drives the timer in a single `advanceUntilIdle`", which this PR's migration made stale.

**not run** — pure `data/`-layer change driven by `runTest`'s virtual clock, no device (same posture as
#304/#309). **Code review: PASS** ([PR #516](https://github.com/pyrycode/pyrycode-mobile/pull/516)), one
non-blocking NIT (the stale `REKEY_MS` KDoc). `security-sensitive` gate satisfied — architect self-review
PASS, code-review confirmed: no logs/secrets added (the `Closed` cause is category-only, matching the sibling
handshake-timeout message), no `android.*`, no crypto/RNG change (the watchdog is a pure `delay`); key
hygiene (AC #3) preserved and in fact **improved** — where a lost resp today keeps `pendingRekey` (and its
copy of `s`) alive for the whole remaining session, the timeout now bounds it to `rekeyRespTimeoutMs`,
strictly narrowing the [#298](298.md) device-static-key RAM window.
