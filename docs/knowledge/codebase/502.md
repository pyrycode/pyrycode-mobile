# #502 — untrack the leftover `.idea/.gitignore`

Removes the single `.idea/` file that was still **tracked** from the initial scaffold (`ddd9178`), via `git rm --cached .idea/.gitignore`. The physical file stays on disk and remains IDE-managed; only the git-index entry is dropped. **No `.gitignore` edit** — the broad `.idea/` rule already exists and keeps the (now-untracked) file ignored. Git-tracking change only: zero source files, no tests, no runtime behaviour. Filed from the Cross-Repo Code Review 2026-07-03 (same batch as [#494](494.md)).

## Summary

PR #503 (`51501f3`) already fixed the *untracked-noise* symptom by adding `.idea/` to the root `.gitignore` (line 28), so `git status` on `main` was already clean. But git keeps tracking files that were committed **before** a matching ignore rule existed, so `.idea/.gitignore` — committed in the scaffold before the rule — stayed in the index, contradicting the "ignore all of `.idea/`" policy. This ticket untracks that one file.

## Files touched

- `.idea/.gitignore` — removed from the git index only (`git rm --cached`). Was 3 lines of Android Studio's default ignored-files list (`# Default ignored files` / `/shelf/` / `/workspace.xml`). Working-tree copy left untouched; the line-28 `.idea/` rule keeps it ignored going forward.

Deliberately **not** touched:

- `.gitignore` — the `.idea/` rule at line 28 (from [#503](https://github.com/pyrycode/pyrycode-mobile/pull/503)) is preserved, **not** re-added or duplicated (AC #3). The redundant pre-scaffold subset at `.gitignore:4-9` (`/.idea/caches`, `/.idea/libraries`, `/.idea/modules.xml`, etc.) is a subset of line 28 and was left in place — out of scope ("don't refactor adjacent code while you're there").

## Patterns established

- **IDE-owned metadata under `.idea/` stays untracked, never committed.** Ignoring a directory (`.gitignore` rule) and untracking already-committed files under it are two separate operations — the rule alone does nothing to files git already tracks. When a build-host/IDE-owned file shows up as tracked, the fix is `git rm --cached <file>` plus the ignore rule, not just the rule. Consistent with the [#84](84.md) principle that IDE/daemon-owned files (`.idea/**`, `.fleet/**`, caches, agent-dispatcher symlinks) live outside the repo's source-of-truth contract and shouldn't be conformed-to or committed.

## Lessons learned

- **A `.gitignore` rule does not untrack already-committed files.** Adding `.idea/` to `.gitignore` (#503) silenced new untracked noise but left the pre-existing `.idea/.gitignore` tracked. Untracking a file that predates its ignore rule always needs an explicit `git rm --cached`; use `--cached` (index only) so the working-tree copy — which the IDE still manages — stays on disk. Never plain `git rm` here: that would delete the on-disk file the AC requires to remain.
- **Distrust "None tracked" anchors — verify with `git ls-files`.** The original ticket asserted *"None tracked, so no `git rm --cached` needed"*; against current `main` that was stale — `git ls-files .idea/` returned exactly one entry (`.idea/.gitignore`). Before acting on a claim about git-tracking state, re-check it (`git ls-files <path>`); the index moves under old notes.

## Verification (1:1 with acceptance criteria)

- AC #1 — untracked, file stays on disk: `git rm --cached .idea/.gitignore` staged a deletion (`git show 5eaaf9a` → `.idea/.gitignore | 3 ---`), working-tree copy left in place.
- AC #2 — nothing left committed under `.idea/`: `git ls-files .idea/` → empty (exit 0, no lines).
- AC #3 — line-28 rule preserved: `grep -n '^\.idea/$' .gitignore` → `28:.idea/`, intact and not duplicated.
