# #375 — snapshot repository read (`requestScreenSnapshot`)

The **consumer / trust-boundary half** of the mobile screen-snapshot slice: it turns the wire vocabulary
[#374](374.md) landed (`RequestSnapshotPayloadDto` / `ScreenSnapshotPayloadDto`) into a usable
`ConversationRepository` read. Adds `suspend fun requestScreenSnapshot(conversationId: String): String`,
fills it on the live [`RemoteConversationRepository`](../features/remote-conversation-repository.md) by
sending a `request_snapshot` and returning the correlated `screen_snapshot` reply's rendered `text`,
gives the [fake](../features/conversation-repository.md) a deterministic canned contract, and routes it
through the [`StableConversationRepository`](../features/stable-conversation-repository.md) facade. It is a
near-verbatim mirror of the [#346](346.md) `sendMessage` slice — same request↔reply correlation primitive —
with **one genuinely-new bit**: routing a *new* correlated reply type (`screen_snapshot`) to its waiter.
Mirrors server pyrycode#618 (merged). **`security-sensitive`**: the snapshot `text` is server-originated
network input returned *literally* to consumers.

The snapshot is the **always-available, parser-independent floor** of ADR 025's safe-degradation strategy
(pyrycode#596): a one-shot text picture of the current claude screen, rendered server-side by the daemon's
tui-driver, depending on no screen parser — so it survives any parser break. **Not gated on the
`interactive` capability (#369):** pyrycode#618's handler validates only registry membership + a live
snapshotter, and ADR 025 § Security model places read-only screen viewing *outside* the per-device
permission gate. No blocker.

## Summary

Four production files, **zero** new files, **zero** new exported types, three override sites — the throwing
default means **no** override cascade into the inline `object : ConversationRepository` test doubles (the
same precedent as `delete` / `createWorkspaceFolder`). The new wire DTOs already existed (#374); this slice
only *uses* them.

1. **Interface** — `ConversationRepository.requestScreenSnapshot` with a throwing `error(...)` default
   (the **fourth** cascade-escape-valve member; a `String` return has no meaningful zero, so it takes the
   `error(...)` shape, not an empty-flow/`null`).
2. **Remote** — encodes `RequestSnapshotPayloadDto`, `sendAndAwaitReply`, decodes
   `ScreenSnapshotPayloadDto`, returns `.text` **verbatim**. A pure read: mutates **no** projection.
3. **Fake** — returns a deterministic canned constant for a known id, throws `IllegalArgumentException`
   (via the existing `unknown(id)` helper) for an unknown one. Pure read, no network, no mutation.
4. **Facade** — an explicit one-line override delegating to `live` (not the inherited throw, exactly as
   `delete` / `createWorkspaceFolder` do — the facade must reach the live impl).

## Patterns established

- **First pure-read request/reply over the #346 correlation primitive.** Every prior user of
  `sendAndAwaitReply` either reconstructs its return from the *input* on `ack` (`sendMessage`, #346) or
  **confirmed-folds** a decoded reply into a projection (`createDiscussion` #347 / `promote` #348 via
  `upsertConversation`). `requestScreenSnapshot` **decodes its reply** (like the mutations) but folds
  nothing — it returns a value and touches no `projection` / `lastMessages` / `messagesByConversation`. The
  "two-or-more writers" KDoc on those fields is therefore untouched. When adding a wire read that returns
  data the UI consumes directly, decode-the-reply + mutate-nothing is the shape; don't invent a projection
  to fold into.
- **A new correlated reply type extends the success-arm `when` by one constant — the seam #346 was built
  for.** The single `init` collector's `inReplyTo?.let { pendingRequests[it]?.complete(payload) }` guard
  already makes an unmatched/unsolicited reply a harmless no-op, so adding `TYPE_SCREEN_SNAPSHOT` to the
  arm is the entire wiring cost. `screen_snapshot` is **always** correlated on this wire (pyrycode#618 sets
  `InReplyTo`; there is no unsolicited snapshot push), so unlike `conversation_updated` it needs no
  unsolicited-broadcast handling. **No second pump subscription, no new collector** — the absolute
  constraint inherited from #346/#313 holds.
- **Snapshot type strings are companion `TYPE_*` constants, like every other wire type.**
  `RemoteConversationRepository` has a **complete** `TYPE_*` registry (`:636-687`): every wire type string
  is a named constant and every request envelope uses `type = TYPE_*` (there are **no** inline `type =
  "..."` literals). #375 added `TYPE_REQUEST_SNAPSHOT` / `TYPE_SCREEN_SNAPSHOT` consistent with that. This
  **corrects** the prediction in [#374](374.md)'s notes (and the wire-layer feature doc) that the snapshot
  types would be "inline literals … with no mobile-side type-constants registry" — the registry already
  existed; #374 just couldn't see how #375 would land. (Wire-layer feature doc corrected by this ticket.)
- **The throwing default is the fourth cascade-escape-valve member.** Joins `recentWorkspaces` (#209) /
  `createWorkspaceFolder` (#210) / `delete` (#218). Confirms the contract's rule: prefer a semantic zero
  when one exists, else `error("…")` — a `String`-returning read has no meaningful zero, so `error(...)`.
  The facade still **explicitly overrides** it (delegating to `live`), because inheriting the throw would
  make the facade unreachable to the live impl.

## Lessons learned

The PR ([#377](https://github.com/pyrycode/pyrycode-mobile/pull/377)) carried no *Lessons learned*
section; the non-obvious points worth recording:

- **Don't trust a predecessor slice's prediction of how the downstream slice will look — verify against
  merged code.** [#374](374.md)'s "Patterns established" asserted there is "no type-constants registry on
  the mobile side" and the snapshot type strings would be inline literals at the #375 call site. The
  registry (`TYPE_LIST_CONVERSATIONS` … `TYPE_ERROR`) already existed and #375 simply extended it. The
  forward-looking claim was wrong about the *existing* state, not just the future. The wire-layer feature
  doc inherited the same error and is corrected by this ticket; #374's own file is left as the historical
  record (never edit a sibling ticket's file).
- **The reply decode runs caller-side, *after* `sendAndAwaitReply` returns — so a malformed
  `screen_snapshot` never threatens the collector.** The collector hands the raw `JsonElement` payload to
  the waiter and moves on; `decodeFromJsonElement<ScreenSnapshotPayloadDto>` (which throws
  `SerializationException` ⊂ `IllegalArgumentException` on a missing-`text` frame) executes in the caller's
  coroutine. A dedicated test pushes a `text`-less `screen_snapshot`, asserts the throw, then proves a
  following valid round-trip still resolves — the single inbound collector survives. Same posture as
  `createDiscussion` / `promote` decoding their typed replies.
- **The verbatim-return invariant is pinned with whitespace.** Both the Remote happy-path test value
  (`"  top line\n    indented body  \n"`) and the fake's `FAKE_SCREEN_SNAPSHOT_TEXT` carry leading/trailing
  spaces and newlines on purpose, so any accidental `trim()`/normalization would fail the byte-for-byte
  assertion. Decode fidelity is the whole point of the parser-independent floor; the test makes "verbatim"
  observable rather than aspirational.
- **`security-sensitive` here = a logging discipline, not new code.** The snapshot `text` is rendered
  screen content (potentially sensitive) returned *literally*, so the method adds **zero** `Log.*` /
  `println` (the request, envelope, reply, `conversationId`, and `text` are all unlogged — preserving the
  #346 "content may be sensitive" collector posture). No new error mapping, no redaction added to the DTO
  (`ScreenSnapshotPayloadDto` keeps its auto-`toString()`, matching the content-bearing `MessagePayloadDto`
  — `toString`-redaction is reserved for the `token` credential). Display-time concerns (`FLAG_SECURE`,
  control-sequence rendering, screenshot leakage) are the UI slice's (#372), explicitly out of scope here.

## Verification

- `./gradlew test spotlessCheck lint assembleDebug` — all green (PR body; QA gate `./gradlew check` +
  `assembleDebug` green). `connectedAndroidTest` N/A — pure `data/`-layer suspend method, no Compose, no
  `ComposeTestRule`. See [[data-layer-android-import-exception]].
- Remote tests use the `runTest` + `runCurrent()` + `FakeSessionPump` idiom (push→demux→resolve), **not**
  `advanceUntilIdle` — see [[remote-repo-test-runcurrent-not-advanceuntilidle]]. The six scenarios map to
  the ACs: verbatim happy path (AC #2), `server.binary_offline` → `RelayErrorException` (AC #3),
  `conversation.not_found` → `IllegalArgumentException` (AC #3), not-`Open` send → `IllegalStateException`
  (AC #3), uncorrelated-reply no-op + collector survives, malformed-reply throw + collector survives.
- **Code review: PASS** ([PR #377](https://github.com/pyrycode/pyrycode-mobile/pull/377), no blocking
  findings — "a clean, minimal, spec-faithful slice … a faithful mirror of the #346 send-message slice").
  Reviewer verified the security-review pass present, the no-log-of-snapshot-text discipline (grep of all
  four touched files: zero `Log.*`/`println`/`Timber`), the verbatim fail-closed decode through
  `MobileJson`, `data/` portability (no `android.*`, no `kotlinx.datetime` parse), and that the new
  interface method's throwing default gives zero blast radius across implementers.
