# #318 — `conversation_created` / `conversation_updated` response payloads → domain `Conversation` mapping

The **third application payload** decoded on top of the [#273](273.md) wire layer (after [#316](316.md) `conversations` and [#317](317.md) `message`): a typed `@Serializable` DTO for the Mobile Protocol v2 **mutation-response** payloads plus a pure function that maps it to a domain [`Conversation`](../features/data-model.md). It is the single decode-and-validate boundary for the create/promote write paths — `create_conversation` is answered by `conversation_created`, `promote_conversation` by `conversation_updated`, and both carry one conversation object — turning untrusted `Envelope.payload` JSON into a domain `Conversation`, with malformed / field-incomplete payloads rejected **at decode** rather than producing a partial or `null`-punned object. Greenfield, no consumers yet: the future `create_conversation` / `promote_conversation` mutation slices of `RemoteConversationRepository` route by `Envelope.type` and call this mapper.

Scope is *mutation-response* → `Conversation` **only** — no flows, no repository, no networking. `send_message`'s response is the `message` echo (mapped by [#317](317.md), **not** this slice); `ack` is a wire-correlation signal with no domain target (a repository-orchestration concern, out of scope). See [[v2-app-payload-shapes-ssot]].

See the feature doc [`mobile-protocol-v2-wire-layer.md`](../features/mobile-protocol-v2-wire-layer.md) § "Application payloads" for the evergreen reference; this file is the implementation record.

## Summary

One `@Serializable data class` + a pure mapper extension, under `data/network/` next to the siblings [#316](316.md) / [#317](317.md) it mirrors, verified by one JUnit4 test file (5 `@Test` methods). The DTO is the camelCase analog of the server's two snake_case write-response Go structs (`@SerialName` carries the mapping — the Go-interop contract); the mapper is the wire→domain edge.

The single load-bearing design move: **one DTO models BOTH response types** — `conversation_created` and `conversation_updated` carry the identical field set and differ only in key order, so a single DTO decodes both (see Patterns).

## Patterns established

- **One DTO models multiple wire `type`-strings when they share a shape.** The Go SSOT (`internal/protocol/conversations_write.go`, #274) pins `ConversationCreatedPayload` and `ConversationUpdatedPayload` to the **identical** field set (`id`, `is_promoted`, `name?`, `cwd`, `last_used_at`), differing **only** in struct key order (`cwd`↔`name` swapped). JSON object key order is semantically irrelevant and kotlinx-serialization decodes by key **name**, not position, so a single `ConversationResponseDto` decodes both wire orderings losslessly. The `conversation_created` vs `conversation_updated` distinction is a **wire-`type`-string routing concern** handled at the `Envelope.type` layer by the future mutation slices — **not** a shape concern at the decode boundary. (Same principle as #317's one `MessagePayloadDto` for both inbound `message` and the `send_message` echo.) The DTO's KDoc states this explicitly so a future reader does not "fix" it by splitting into two byte-identical classes.
- **Bare object vs object-wrapped is per-payload — check the Go struct.** These payloads are a **bare conversation object** at `Envelope.payload`, so it decodes directly to `ConversationResponseDto` — the opposite of #316's array-wrapping `{ "conversations": [ … ] }`. As #317 established: object-wrap vs bare is decided per payload by the server struct, never assumed from a sibling.
- **Both validations at decode — the #316 posture, not #317's split.** `last_used_at` decodes to `kotlinx.datetime.Instant` via an explicit `InstantIso8601Serializer`, so a malformed RFC 3339 string fails **at decode** (`IllegalArgumentException`) and a missing required field fails at decode (`SerializationException`). The mapper stays a total, pure field-copy with **no second throw site** — unlike #317, whose timestamp is the envelope `ts` parsed in the mapper (a map-time throw). Decode is all-or-nothing: a payload that can't fully populate the DTO throws before any `Conversation` is constructed (AC #4).
- **Four wire-absent domain fields are mutation-response-tier placeholders, never `null`-punned.** `currentSessionId`/`sessionHistory`/`isSleeping`/`archived` are not on the write-response wire — the **same rule as #316**, reused verbatim. The mapping site documents them as defaults and cross-references #316 as the canonical rule source. **No shared helper was extracted** (deliberate): factoring `(id, name, cwd, isPromoted, lastUsedAt) → Conversation` would require editing the landed `ConversationsPayload.kt` for a four-constant DRY win — the "don't refactor adjacent code while you're there" case — and #317 set the precedent of a self-contained per-shape file with no cross-slice shared mapper. **Deferred until a third consumer of the rule lands** (then revisit; evidence-based, the divergence risk is low and unobserved).
- **A single-class payload file is named after its class, not the spec's `*Payload.kt`.** ktlint `standard:filename` (spotless) forces a file with exactly **one** top-level class to be named after it, so the file is `ConversationResponseDto.kt` (test `ConversationResponseDtoTest.kt`), **not** the spec's proposed `ConversationResponsePayload.kt`. Code review confirmed this is *more* idiomatic, not less (Kotlin "file named after its primary declaration"). The siblings escape the rule only because each holds **two** top-level declarations — #316's `ConversationsPayload.kt` (wrapper + row DTO) and #317's `MessagePayload.kt` (DTO + `WireRole` enum). The trigger is a genuinely single-class file: name future single-DTO payload files after the DTO.

## Lessons learned

Lifted (and corrected) from the PR's *Lessons learned* section:

- **ktlint `standard:filename` overrides the spec's filename for a single-class file.** The architecture spec's file-layout table prescribed `ConversationResponsePayload.kt`, but because this slice ships exactly one top-level class (`ConversationResponseDto` + its extension function — top-level functions don't count toward the rule), spotless requires the file be named after the class: `ConversationResponseDto.kt`. The PR's note cited #317's `MessagePayloadDto` as a future example of the same constraint, but #317 in fact already landed as `MessagePayload.kt` holding **two** declarations (its DTO *and* the `WireRole` enum) — so, like #316, it escapes the rule. The accurate trigger is a genuinely single-class file. **Takeaway:** when a payload slice ships exactly one class, expect spotless to dictate the filename — don't fight the spec's `*Payload.kt` suggestion through it.

## Verification

- `./gradlew test` (5 `ConversationResponseDtoTest` cases + full suite), `./gradlew lint`, `./gradlew assembleDebug`, `./gradlew spotlessCheck` — all green in the PR.
- **No instrumented test** — pure `data/`-layer slice, nothing to instrument; the decode/map path is fully exercised by JVM unit tests.
- **Code review: PASS** ([PR #328](https://github.com/pyrycode/pyrycode-mobile/pull/328), no MUST/SHOULD FIX). One **NIT**: the spec-vs-code filename divergence (`ConversationResponsePayload.kt` → `ConversationResponseDto.kt`), flagged only for the record as *more* idiomatic — no change needed (see Patterns / Lessons). The reviewer confirmed the DTO byte-mirrors the Go SSOT, the one-DTO-for-both-types decision is correct and well-documented, all nine domain fields get defined non-`null` values (no `null`-pun), and all four ACs are covered. The architect security-review (in the spec, **Verdict: PASS**) confirms this is the explicit untrusted-JSON→typed-value boundary, the payload carries no secret (only `id`/`name`/`cwd`/a bool/one timestamp), `cwd` is opaque display data here (canonicalization deferred to whoever turns it into a `File`), and no file / IPC / crypto / network surface is introduced. The promoted⇒named semantic invariant is **not** re-validated client-side (a server-registry concern, #274 — `Conversation.name` is validly `null` for any `isPromoted`).
