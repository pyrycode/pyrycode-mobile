Size **S**, not `security-sensitive`.

## Summary

Adds `interactiveTurn_deleteConversation_removesFromListAndClosesThread` to
`InteractiveStreamE2ETest` — a rung-3 real-claude scenario for the operator-facing Delete happy path,
cloning the #541/#566 structural shape but spending **zero** claude turns. It creates a scratch
discussion, renames it to a runtime-unique name (`"e2e554-" + System.currentTimeMillis()`) to give it a
test-controlled, list-visible identity, confirms that name **present** on the channel list, re-enters the
thread, then drives the real Delete flow — thread overflow → "Channel info" → the sheet's "Delete" → the
"Delete conversation?" dialog → confirm — and asserts **both** durable post-conditions: the unique name is
**gone from the list** (`assertCountEquals(0)`, a genuine inversion of the presence check) and the
**thread has popped back** (the list marker reappears). Zero production code: one new `@Test` + 7
companion constants, one `scripts/e2e-emulator.sh` LIVE-curation edit (trio → quartet), and the ladder doc.

Both blockers the ticket had been parked on were already cleared before this ticket started: #532 shipped
the `delete` data path (PR #555), and PR #572 flipped `RemoteConversationRepository.mutationsSupported`
to `true`, making the Delete affordance (gated on that flag inside the Channel Info sheet's Actions block)
reachable on the live relay path. Delete is conversation-scoped, so it carries none of the orthogonal
blockers that re-park siblings #545 (`currentSessionId=""`) or #562 (workspace-chip catch-22).

## Files touched

- **`app/src/androidTest/java/de/pyryco/mobile/e2e/InteractiveStreamE2ETest.kt`** (+170) — the new
  `@Test`, structured as a 9-step scenario:
  1. Land on the channel list, `awaitConnected()`.
  2. Create a plain discussion (regular tap) — sufficient since both "Rename"
     (`mutationsSupported`-gated) and "Channel info" (ungated) reach it.
  3. Rename to `CONVERSATION_NAME_PREFIX + System.currentTimeMillis()` via the overflow → "Rename" →
     `RenameDialog`, using `hasSetTextAction() and isFocused()` to target the dialog's field over the
     thread composer's (see § Gotchas) and `performTextReplacement` (not `performTextInput`) to overwrite
     the pre-filled, pre-selected auto-name.
  4. Back to the list; **presence check (AC-3)**: `waitUntil` + `assertIsDisplayed()` on the unique name.
  5. Re-enter the thread by tapping the recents row (a 2nd presence observation).
  6. Overflow → "Channel info" (ungated) → the sheet's "Delete" `ActionCell`.
  7. Wait for the "Delete conversation?" dialog, then tap the **confirm** "Delete" — disambiguated from
     the sheet's still-composed "Delete" via `hasText(DELETE_ACTION) and
     hasAnySibling(hasText(DELETE_DIALOG_CANCEL))` (see § Gotchas).
  8. **Both durable post-conditions (AC-2):** `waitUntil` for the list marker (`CD_NEW_DISCUSSION` —
     thread popped back), then `assertCountEquals(0)` on the unique name (gone from the list).
  - New companion constants: `RENAME_ITEM = "Rename"`, `RENAME_SAVE = "Save"`,
    `CHANNEL_INFO_ITEM = "Channel info"`, `DELETE_ACTION = "Delete"` (flagged inline as the colliding
    literal), `DELETE_DIALOG_TITLE = "Delete conversation?"`, `DELETE_DIALOG_CANCEL = "Cancel"`,
    `CONVERSATION_NAME_PREFIX = "e2e554-"`.
- **`scripts/e2e-emulator.sh`** (+13/−10) — the `LIVE` branch's `TEST_TARGET` extends from a curated trio
  to a curated **quartet** (ping + create-workspace-folder + new-session + delete); every "trio / 3 turns"
  prose spot (header, usage line, run-block comments, PASS log) updated to "quartet / 4 scenarios, still 3
  turns" — delete adds a method, not a turn.
- **`docs/e2e-interactive-stream.md`** (+82/−36) — ladder rung-3 description, "What rung 3 is made of"
  (now six scenarios), the delete scenario's always-on/durable-post-condition rationale and the "Delete"

## Patterns established

None new — a confirming instance of the rung-3 real-claude scenario shape (#481/#482/#566/#541's
template): clone the create-discussion/overflow-driven skeleton, extend the LIVE `TEST_TARGET`
comma-separated `class#method` list by one more entry, constants added to the shared companion object.
The one genuinely new move this ticket adds to the family repertoire is **using Rename to mint a
runtime-unique identity purely so a later absence assertion is a real inversion** — worth reusing verbatim
if a future e2e needs to prove something is gone rather than present.

## Lessons learned

(Lifted from the PR body's own Lessons-learned section.)

- **Rename-in-thread has two editable fields.** `RenameDialog` opens over the thread's `ThreadInputBar`
  `BasicTextField`, so a bare `hasSetTextAction()` matches two nodes. The dialog auto-focuses its field on
  open and the composer never requests focus, so `hasSetTextAction() and isFocused()` uniquely targets the
  dialog field — without needing to know the server-assigned auto-name at runtime (the pre-filled-name
  matcher the component-level `RenameDialogTest` uses can't apply here).
- **`and` is an infix member on `SemanticsMatcher`, not a top-level import.** Adding
  `import androidx.compose.ui.test.and` fails to resolve; write `matcher1 and matcher2` with no import
  (the existing `RenameDialogTest` establishes this). `hasAnySibling` / `hasText` / `isFocused` /
  `onNodeWithText` / `performTextReplacement` *are* real imports. Captured as
  [[compose-test-and-member-and-rename-field-disambig]].
- **The sheet's "Delete" and the dialog's confirm "Delete" collide.** `ThreadEvent.Delete` sets
  `pendingDeleteConfirm` without clearing `pendingChannelInfo`, so the Channel Info sheet stays composed
  *behind* the confirm dialog — both literal `"Delete"` nodes are on screen at confirm time. Disambiguated
  by `hasText("Delete") and hasAnySibling(hasText("Cancel"))` (the dialog's sibling cancel button, which
  the sheet has no equivalent of — its dismiss is a close icon), never by `onFirst()` z-order.
