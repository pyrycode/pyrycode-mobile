# #364 — Persist the FCM push token in `AppPreferences`

Adds **durable storage only** for the phone's FCM registration token, so it survives process death and
is available to re-register with the daemon on every reconnect without waiting for Firebase to re-mint
it. One new DataStore key plus a getter/setter pair on
[`AppPreferences`](../features/app-preferences.md), cloning the `defaultWorkspace` shape — **except the
getter has no default**. Eight production lines; XS.

The slice is **dormant until written**. Its two collaborators are sibling slices:

- **Origin** (Firebase `onNewToken` → `setPushToken`) — the Firebase slice **#361**.
- **Reader** (connect-time re-registration) — the orchestration sibling, which then calls the wire sender
  [#359](359.md)'s `RemoteConversationRepository.registerPushToken`.

A `null` read is the load-bearing **"nothing to register yet"** signal the reader depends on; downstream
stays inert until the first write lands.

## The one deliberate departure from every other getter in the file

`pushToken` is the **first preference in `AppPreferences` with no fallback default** — every sibling
coalesces (`?: false` / `?: true` / `?: SYSTEM` / `?: DEFAULT_SCRATCH_CWD`). Here absence reads as
`null`:

```kotlin
val pushToken: Flow<String?> =
    dataStore.data.map { prefs -> prefs[PUSH_TOKEN] }

suspend fun setPushToken(token: String) {
    dataStore.edit { prefs -> prefs[PUSH_TOKEN] = token }
}
```

The `null` is **not** an oversight to be "fixed" with a default — it is the dormant signal. Single key +
`edit` overwrite → writing a new value replaces the prior one (AC #4, the rotation path #361 drives via
`onNewToken`); no history is retained, last-write-wins.

## Patterns established

- **The no-default getter as a meaningful-`null` signal.** Until now the "Adding a preference" recipe in
  the [feature doc](../features/app-preferences.md#adding-a-preference) said *"add a `Flow<T>` reader with
  an explicit default via elvis."* `pushToken` is the first deliberate exception: when absence itself is
  semantically load-bearing (here: "dormant / nothing to register"), the getter returns `Flow<String?>`
  with **no** `?: fallback`. The recipe now carries this as the documented exception — don't pattern-match
  a default onto every new key.
- **Storage-tier classification is deliberate, not default-by-habit.** An FCM registration token is a
  device-scoped wake *address*, not a credential — possessing it is insufficient to push (an attacker also
  needs the project's FCM server key, which lives only on the daemon). It rotates and is overwrite-only. So
  it sits on the **non-secret side** of the codebase's trust boundary: plain `DataStore<Preferences>` in
  `AppPreferences`, **not** Keystore-wrapped under `data/crypto/` (which holds the device static key + paired
  server keys). This mirrors the KitchenClaw ADR-007 split (DataStore for non-sensitive, encrypted store
  for auth tokens). The template: classify by *value × revocability*, not by "it came from a network/SDK,
  so encrypt it." Do **not** "upgrade" this key to Keystore — that miscategorises it.

## Lessons learned

The PR ([#366](https://github.com/pyrycode/pyrycode-mobile/pull/366)) carried no *Lessons learned*
section; the non-obvious points worth recording:

- **The process-death test needs `cancel()` + `job.join()` between the two DataStore instances.** AC #3
  proves persistence by writing with one `AppPreferences`/`DataStore` and reading back with a *second*
  instance over the **same `File`**. DataStore enforces **one active instance per file path** and throws
  `IllegalStateException("There are multiple DataStores active for the same file…")` if instance #2 opens
  while #1 is still live. A bare `scope.cancel()` is async — the release isn't guaranteed by the time the
  next line runs. The fix is `scope1.cancel()` **then** `job1.join()` (the scope built over an explicit
  `Job()` so it's joinable) before constructing instance #2. Capture the file once with
  `tmp.newFile("…​.preferences_pb")` and feed it to both via `produceFile = { file }` —
  `TemporaryFolder.newFile` throws on a duplicate name, so you cannot re-derive it per instance.
- **No "never logged" unit test (AC #5); it's a code-level invariant, not unit-testable.** Enforced
  deterministically by (a) the production methods containing zero logging — grep-verifiable, and a
  *preserve* constraint since `AppPreferences` has never logged — and (b) the spec's security review.
  Code-review confirmed no `Log.*`/`println`/`Timber` references the token in the diff. Don't add a
  try/catch around `edit`/`map` that echoes the token in an error path.
- **Store the token verbatim — no trim/parse/validate.** The value is opaque infra data from Firebase; the
  content trust boundary is the daemon at registration time, not local storage. Over-validating here would
  defend an unobserved failure mode and risk rejecting valid future FCM token shapes. Deliberate non-defense
  (Evidence-Based Fix Selection).
