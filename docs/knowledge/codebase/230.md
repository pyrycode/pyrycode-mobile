# #230 — feat(ui/sheets): StatusSheet — Context window section (Figma 20:100)

Lands the **Context window** section — the fourth and final section of `StatusSheetContent` ([#254](./254.md) shell + Model, [#229](./229.md) Effort + YOLO). Pure read-only visualisation: a `bodyLarge` `"NN% used (XXK of YYK tokens)"` label over an 8dp `LinearProgressIndicator` whose fill colour follows the same `< 50 / < 95 / ≥ 95` threshold rules as [`ThreadStatusRow.tokenPercentColor`](./145.md) — but the **colours differ** (`primary` / `warning` / `error` for fill chroma, vs `onSurfaceVariant` / `warning` / `error` for text emphasis), so the two threshold helpers stay separate. `ThreadUiState` gains two trivially-additive stub fields `tokensUsed: Int = 0` / `tokensTotal: Int = 0` populated by sibling companion constants (`STUB_TOKENS_USED = 146_000`, `STUB_TOKENS_TOTAL = 200_000`) alongside the existing `STUB_TOKEN_PERCENT = 73` (`73% × 200_000 = 146_000` is the Figma reference value and a sharp "this is the stub" reader signal). No ViewModel logic, no new flows, no mutators — purely additive display state. Split from [#146](https://github.com/pyrycode/pyrycode-mobile/issues/146); siblings [#254](./254.md) (shell + Model) and [#229](./229.md) (Effort + YOLO).

## Summary

- **`progressColor` is a new private helper in `StatusSheet.kt`, deliberately separate from `ThreadStatusRow.tokenPercentColor`.** Same `< 50 / < 95 / ≥ 95` boundary values, different colour slots: this helper colours **fill** (`primary` → `warning` → `error`), the existing one colours **text** (`onSurfaceVariant` → `warning` → `error`). Sharing would force one consumer onto the wrong slot — `primary` is fill chroma, `onSurfaceVariant` is low-emphasis text. Two `@Composable` helpers of ~8 LOC each cost less surface than a shared enum or threshold class. The architect's spec called this out as load-bearing — "duplicated boundaries are cheap; a wrong slot is not". If a third consumer ever shares both the boundaries and a colour mapping, that ticket can extract a `TokenPressure { Low, High, Critical }` enum — premature here.
- **Below-50% choice resolved to `colorScheme.primary`.** The ticket Technical Notes framed it as a binary choice between `primary` and the M3 `LinearProgressIndicator` default — those are the same thing, so the spec picked `primary` to avoid introducing a third tone. Result: bar is M3-default-coloured for low usage, warning-tinted for the danger zone, error-tinted at the edge.
- **`gapSize = 0.dp, drawStopIndicator = {}` worked on the BOM-pinned M3.** The architect's open question was whether these stop-indicator-suppression params would be on the `compose-bom = 2026.02.01` version. They are — Figma `20:153/154` shows no stop dot or gap, and the production code uses both params with no TODO marker. The fallback path (accept the default stop indicator + file a follow-up) was not needed.
- **`formatTokens` is a private file-local helper, not a util module.** `private fun formatTokens(n: Int): String = "${n / 1000}K"`. Integer-divide truncation is intentional — sub-1K precision isn't meaningful at this display scale, and `formatTokens(999) == "0K"` is acceptable. Per ticket Technical Notes: "single formatter helper site… not a shared util module for it." Lives at the top of `StatusSheet.kt` alongside `progressColor`. If a second consumer ever needs the same shape, that ticket extracts; until then the cost of a future re-declaration is two lines.
- **Three new parameters on `StatusSheet` and `StatusSheetContent`, all defaulted to `0`.** `tokenPercent: Int = 0, tokensUsed: Int = 0, tokensTotal: Int = 0` appended after `onDismiss` (kept after the existing `modifier`/`sheetState` defaulted tail on the public `StatusSheet`, so both signatures stay coherent). The `= 0` defaults are semantically correct: `0` means "no context window data yet" — exactly what the initial/empty state shows. They also let the 10 existing `StatusSheetTest` call sites and 5 existing `@Preview`s compile untouched, holding edit fan-out at 5 deliberate edits (1 production `ThreadScreen` call site + 4 `ThreadScreen` previews). Without the defaults the raw fan-out would have been 16 call sites — over the architect's red line.
- **Caption copy is verbatim from Figma `20:155`, including the lowercase `"claude's"`.** `"When full, oldest messages get dropped from claude's view (delimiter still shows; old messages stay in your scroll)."` Inline string literal in `StatusSheet.kt`'s existing convention — no `strings.xml` extraction this slice, first-localisation pass migrates all sheet copy together.
- **`LinearProgressIndicator` uses the deferred `progress = { lambda }` overload, not the eager `progress = Float` form.** The lambda reads `tokenPercent` lazily on draw, which is the Compose-recommended shape for progress indicators (it avoids re-allocating the layout when only the fill width changes). `tokenPercent.coerceIn(0, 100) / 100f` clamps defensively over the eventual Phase 4 backend swap — `agentStatus.tokenPercent` could conceivably overshoot during a usage spike, and clamping at the leaf means the threshold compare in `progressColor` and the bar width never branch incorrectly.
- **Three new `STUB_*` companion constants now share one swap-point comment.** `STUB_TOKEN_PERCENT = 73`, `STUB_TOKENS_USED = 146_000`, `STUB_TOKENS_TOTAL = 200_000` all sit under a single `// Phase 4 swap point: replace with backend AgentStatus flow.` line. Phase 4 replaces all three together when the backend `AgentStatus` flow lands — the values are coupled (the percent must agree with the used/total ratio) and the comment groups them for the future replacer.
- **`ThreadViewModel.state`'s populator gains two lines, no signature change.** The existing `combine(...) { conversations, items, picker, dialogs, runConfig -> ThreadUiState(...) }` block at lines ~117-138 stays five-arg; the `RunConfig` pre-combine from [#229](./229.md) is untouched; the new fields are constants read from the companion alongside `STUB_TOKEN_PERCENT`. No new flow source, no new dispatcher, no `viewModelScope.launch`.
- **Four new `@Preview` composables sweep the threshold transitions** — `StatusSheetContextWindow20Preview` (`primary` band), `StatusSheetContextWindow60Preview` + `StatusSheetContextWindow88Preview` (both `warning` band, different fill widths), `StatusSheetContextWindow97Preview` (`error` band). All fix `Model.OPUS_4_7` + `Effort.HIGH` + `yoloEnabled = false` for visual stability — only the three context-window params vary. Matches the AC's "20%, 60%, 88%, 97%" examples and pins the threshold transitions visually since Compose colour assertions on draw layers are awkward (the test surface is the four previews, not a colour-asserting Compose test).
- **Three new `StatusSheetTest` Compose tests; no negative-colour assertion.** `renders_context_window_section_with_header_label_and_caption` (asserts header + 73% formatted label + caption — one assertion covers both `formatTokens` correctness and the label-assembly contract since the private helper is verified through its visible output); `label_format_uses_integer_K_division` (asserts `"5% used (12K of 200K tokens)"` for `tokensUsed = 12_345` — pins the integer-divide-truncation behaviour indirectly); `label_format_handles_zero_values_gracefully` (renders with defaults, asserts `"0% used (0K of 0K tokens)"` — pins the empty/initial-state shape and prevents a future divide-by-zero regression). Progress-bar fill colour is **not** asserted — `SemanticsNodeInteraction` doesn't expose draw colours; the four previews are the visual gate.
- **Two existing `ThreadViewModelTest` methods gain four assertion lines total.** The two `*Defaults` / `*Default*` tests from [#229](./229.md) now also assert `tokensUsed == 0` / `tokensTotal == 0` on the initial frame and `tokensUsed == 146_000` / `tokensTotal == 200_000` on the post-subscription frame. Literal values mirror the companion constants (which stay `private` and are not exposed for test reference) — same pattern as the existing `assertEquals(73, ...)` line for `tokenPercent`.
- **No new dependencies, no Koin changes, no `gradle/libs.versions.toml` edits, no `strings.xml` keys.** `LinearProgressIndicator` ships in the existing Compose BOM (`composeBom = 2026.02.01`); `gapSize` + `drawStopIndicator` are exposed. The two new caption + label strings inline alongside the existing `"Run configuration"` / `"Model"` / `"Effort"` / `"YOLO mode"` literals.

## Patterns established

- **When two visualisations share threshold boundaries but differ on colour mapping, keep the threshold helpers separate.** This is the explicit precedent set by `progressColor` (fill chroma: `primary` / `warning` / `error`) and `tokenPercentColor` (text emphasis: `onSurfaceVariant` / `warning` / `error`) — same `< 50 / < 95 / ≥ 95` boundaries, different colour slots. The temptation to share via `enum class TokenPressure { Low, High, Critical } -> Color` would force one consumer onto the wrong slot. Re-extract only when a third consumer arrives that *also* needs the same colour mapping as one of the existing two; until then, duplicated `when` blocks of ~8 LOC are cheap. Same posture as [`Model.label()`](./253.md)'s co-location rule but applied to threshold helpers instead of label tables.
- **Stub constants for related fields share one Phase-4 swap-point comment.** `STUB_TOKEN_PERCENT` + `STUB_TOKENS_USED` + `STUB_TOKENS_TOTAL` sit under a single `// Phase 4 swap point: replace with backend AgentStatus flow.` line in the companion. The three values are mutually consistent (`73% × 200_000 = 146_000`) and will be replaced together when the backend `AgentStatus` flow lands. Apply to any future stub group whose members are derived from the same future producer: one comment over the whole group, not one per constant. The grep-able breadcrumb for Phase 4 is `STUB_` in the companion + the swap-point comment.
- **`Int = 0` defaults on additive display-state parameters are semantically correct, not just compile-time convenient.** Three new `Int` params on a sheet whose body has grown four sections all default to `0` because `0` is the meaningful "empty/initial state" value at the leaf composable. The architect's spec called out the distinction between this and a "default-param escape hatch" rationalisation — the rule is: if the default value is what the empty/initial-state preview would render, the default is load-bearing; if it's a placeholder that would crash or look broken in production, it's an escape hatch and you should bite the fan-out instead. The 10-call-site red line for signature changes should be enforced on the *escape hatch* path, not on the load-bearing-default path.
- **Suppress the M3 `LinearProgressIndicator` stop indicator via `gapSize = 0.dp, drawStopIndicator = {}`** when Figma shows no stop dot. The two params shipped together on the M3 version in `compose-bom = 2026.02.01`; the architect's pre-emptive open question (do we need a BOM bump or a TODO?) resolved cleanly to "use the params, no follow-up needed". Apply to any future progress indicator whose design omits the stop dot — the canonical shape is `LinearProgressIndicator(progress = { ... }, color = ..., trackColor = ..., gapSize = 0.dp, drawStopIndicator = {})`. If a future BOM downgrade ever removes the params, the M3-default stop dot is the only visual regression — non-crashing, recoverable with a one-line TODO.

## Lessons learned

- **Compose colour assertions on draw layers are awkward; previews are the right verification surface for threshold transitions.** `SemanticsNodeInteraction` exposes text + semantics but not draw colours, so writing a `assertProgressBarTint(...)` Compose test against `LinearProgressIndicator`'s `color = ...` is not feasible without reaching into private Compose-test APIs. The right shape is what this slice does: four `@Preview`s sweeping the threshold boundaries (20 → `primary`, 60 + 88 → `warning`, 97 → `error`) so the colours render in the IDE preview pane, plus Compose tests that assert text / structure / callback invocation. The same trap will apply to any future threshold-driven fill colour (e.g. a battery-level bar, a download-progress chip) — don't try to write the colour assertion, write the preview sweep.
- **Integer-divide truncation in display formatters is fine and should be tested.** `formatTokens(999) == "0K"` looks wrong at first read but is the right shape for context-window display — sub-1K precision is noise at this scale, and rounding-to-nearest would only matter for hypothetical mid-range producers Phase 4 will never emit. The `label_format_uses_integer_K_division` test pins this explicitly with `tokensUsed = 12_345 → "12K"` so a future "let's round nicely" PR has an assertion to flip rather than silently changing the format. Apply when any future formatter makes a deliberate truncation choice — write the test that pins the choice, not the test that masks it.
- **The architect's "raw fan-out" count includes test files; the "deliberate edits" count after defaults does not.** This slice's raw call-site count was 16 (1 public production caller + 5 in-file previews + 10 test call sites); after `= 0` defaults it became 5 deliberate edits (1 production + 4 previews, all in `ThreadScreen.kt`). Test files were excluded from the "deliberate edits" count because the new params default to `0` and none of the existing 10 tests exercise the Context window section — adding `0` defaults to every test call would have been pure ceremony. Future signature-change tickets should follow the same convention: count all call sites for the raw red-line check, exclude untouched test calls when reporting deliberate edits.
