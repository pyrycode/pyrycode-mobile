# #477 — Layer 2d: post-reconnect replay ordering (events buffered while offline replay in order)

Adds the **`replay-order`** scenario on the **#454 deterministic emulator harness** (rung 4 / **Layer 2d**
of the mobile interactive-stream e2e ladder, `docs/e2e-interactive-stream.md`): a *sequence* of ≥3 distinct
events produced **entirely while the phone's relay link is severed** must replay **in production order, each
exactly once**, after reconnect. Where the continuity case (#476) proves a single in-flight reply *survives*
a drop, this proves an ordered backlog buffered during the outage replays **in order** — and is the home for
the **buffered-during-outage re-delivery** the #476 hand-off explicitly deferred here.

It closes the gap #476 called out in its own code review (`codebase/476.md` Lessons): #476's reply arrived
strictly *after* reconnect, so its `event_id` was above the advertised `last_event_id` → it was **delivered
once, never deduplicated**, and the fold's high-water / `message_id`-upsert path was never actually stressed.
This slice produces the whole sequence **before** the restore, so the buffered events replay strictly above
the cursor and genuinely fold idempotently (#337/#385). **No production Kotlin** — it *exercises* shipped,
security-reviewed behaviour (#416 cursor advertise + in-ring replay, #391/#392 reconnect, #337/#385 dedup
fold; server-side oracle pyrycode #647); it does not modify it. NOT `security-sensitive`, no Figma.

**Buildability (the #431 "right-shape" gate): BUILDABLE by construction.** The doc still flags cross-reconnect
`seq`-ordering as "#337 / #402 full scope" (the fold is proven correct only *within a single connection*, and a
reconnect opens a new one). This slice sidesteps that exactly as #476 did: drop A carries **no** renderable
text, so nothing partial lives on the torn-down repo; the **complete** ordered sequence is produced after the
sever and replays after reconnect into the fresh, empty repo, which folds the daemon's ascending-`event_id`
delivery in arrival (= production) order. If the replay does *not* arrive in production order, that is the
finding to surface — **do not restart the daemon to force it** (that trips #417's gap path this test avoids).

## Patterns established

- **Split an atomic drop/restore primitive into halves to straddle an offline window.** #476's
  `severAndRestoreLink()` was atomic (close → await-null → connect → await-non-null) because continuity needs
  no gap. Ordering needs the gap: `severLink()` and `restoreLink()` are the two halves, and
  `severAndRestoreLink()` is preserved as their composition (`severLink(); restoreLink()`) so #476's test is
  unchanged. The await contracts are identical to #476's: `close()` leaves the supervision loop cancelled (no
  auto-redial racing the explicit drive) so the `currentRepository == null` phase is **stable** → the
  `first { it == null }` await is race-free; `restoreLink()` awaits `currentRepository != null` (Open-gated),
  proving *true end-to-end readiness* — an idle-`Connected` `ConnectionState` after `close()` would false-green
  a `ConnectionState.Connected` check ([[two-folds-repo-wins-vm-dormant]] / `codebase/476.md`).
- **A host-observable disconnect fence for a drop that must fire while the phone is offline.** The #454/#476
  two-drop fence drops B on the phone's 2nd `send_message.enqueued` — but a **severed** phone cannot send a 2nd
  `send_message`, so the offline-window drop needs a fence the host can observe without the phone. Drop B is
  fenced on the **relay logging the phone-leg disconnect** (`DISCONNECT_LOG`/`DISCONNECT_TOKEN`, default a
  `"disconnect"` substring in `relay.log`). This is the **third** watcher mode (`DROP_B_FENCE=disconnect`),
  selected by the `replay-order)` arm; the `enqueue` default keeps every other two-drop scenario unchanged.
- **Baseline-count a recurring log token, never `grep -q`.** Drop B waits for the disconnect-token count to
  **increase** past the level captured *after* drop A — so a **stale** connection-churn `disconnect` line from
  before the sever cannot false-fire drop B before the phone actually severs. (A bare `grep -q` would.)
- **The offline-window hold is a principled wait, not the forbidden catch-a-transient delay.** The buffered
  events are **durable** (they replay whenever the phone returns), so erring **long** is free and a slow
  host/emulator cannot lose them; the order / exactly-once asserts hold whether the deltas arrive as pure
  replay (window long enough — the intended path, AC #1) or a replay/live mix (window too short). A too-short
  window only *under-exercises* "entirely offline"; it never false-greens (a reordering still breaks the
  substring) nor false-reds. The window is a determinism **quality** knob, not a correctness razor — distinct
  from the ladder's banned "fixed delay to catch a transient before it vanishes".
- **Drop A carries no partial text by design — "no missing segment, in order" holds by construction.**
  Inherited load-bearing choice from #476: on the sever the connection-scoped repo tears down
  (`currentRepository → null`) and the thread clears, so the fresh repo starts empty and the **whole** ordered
  sequence arrives post-reconnect. Partial text in drop A would live only on the torn-down repo and be lost
  (events ≤ `last_event_id` aren't re-delivered by the gap-free path) — exactly the cross-reconnect-ordering
  uncertainty this sidesteps rather than relies on.
- **The ordered substring proves order; the one count assertion proves dedup.** `ORDERED_REPLY_SUBSTRING`
  spans all three delta boundaries, so matching it requires the deltas to have assembled in production order —
  a reordered replay (`"bravo alpha charlie"`) fails the match (explicit sequence, **not** mere presence).
  `assertCountEquals(1)` on it is the load-bearing dedup invariant (`event_id` high-water + `message_id` upsert,
  #337/#385) on a **genuinely buffered-during-outage re-delivery** — the path #476's after-reconnect reply
  never reached. It keys on the final assembled text (stable — any duplicate is a stable extra row, not a
  transient), so it does **not** violate the ladder's "never assert on counts" rule (which targets delta /
  timing counts). Called out in the method KDoc.

## Lessons learned

- **The existing two-drop watcher's `grep -cF … || echo 0` count idiom is fragile.** On a zero-match
  *existing* file, `grep -c` prints `0` **and exits 1**, so `|| echo 0` appends a *second* `0`, yielding
  `"0\n0"` — which breaks the `[ … -lt N ]` integer compare (the fence loop exits early). Confirmed under both
  bash and zsh, and **reproduced under bash by code review** as a *genuine* latent bug, not theoretical. The
  new disconnect-fence branch uses the robust `|| true` (+ `${v:-0}`) idiom; the older `spinner`/`tool`/`reconnect`
  branches still use `|| echo 0`, **left untouched** here (out of scope — don't refactor adjacent code). Those
  branches *have* been operator-run (e.g. #476 reconnect), so the discrepancy is real → **worth a tracked
  follow-up** to unify on the robust idiom (the only non-blocking finding in the PR review). (Lifted from the
  PR's Lessons-learned section + the code-review NIT.)
- **Baseline-count, don't `grep -q`, for a recurring log token** — see Patterns; drop B fences on the count
  *increasing* so a stale churn line can't false-fire it. (Lifted from the PR's Lessons-learned section.)
- **The offline-window hold is a principled wait, not the forbidden catch-a-transient delay** — durable
  buffered events make erring long free, and the asserts hold for both a pure-replay and a replay/live-mix
  arrival. (Lifted from the PR's Lessons-learned section; also a Pattern above.)

## Verification

The deliverable **is** the test harness; there is no unit test of it. Host-JVM checks (no device, per the
spec's strategy), confirmed green by QA:

- `./gradlew test lint assembleDebug` + `compileDebugAndroidTestKotlin` + `spotlessCheck` all green — the
  androidTest sources compile (the mandatory gates do **not** compile androidTest, so the explicit
  `compileDebugAndroidTestKotlin` run is required; [[androidtest-not-compiled-by-mandatory-gates]]).
  `assertCountEquals` is imported (an extension, not a member); the `delay` import is used.
- Both new fixtures validate as one-JSON-object-per-line and assemble to exactly `"alpha bravo charlie"`; the
  watcher disconnect-fence logic was verified in isolation (ignores stale churn, fires on a fresh disconnect).
- **Operator-run (device + host `pyry`/`pyrycode-relay`/`fakeclaude`):** NOT executed from the pipeline (no
  device); expect to tune on first run. First-run unknowns (documented in `e2e-interactive-stream.md`):
  - **Disconnect-fence token (PRIMARY UNKNOWN).** The exact relay/daemon log token for the phone-leg drop is
    unverifiable from this repo (that source is in pyrycode). Best guess: a `"disconnect"` substring in
    `relay.log`; `daemon.log` as fallback. Override `DISCONNECT_TOKEN` / `DISCONNECT_LOG` and **confirm on
    first operator run** — if the token never appears, drop B never drops and the test times out.
  - **Offline-window length.** `OFFLINE_WINDOW_MS = 5_000L` must exceed [relay disconnect-detect + watcher poll
    0.5 s + `fakeclaude` append + producer tail]; lengthen if the replay arrives as a live mix.
  - **Buffered sequence replays in production order.** The shipped #416/#647 contract, but unverified end-to-end
    *with the whole sequence produced during the outage* — the buildability finding to surface if it doesn't
    (never restart the daemon to force it → #417's gap path).
  - **No `resync` (AC #4).** Not cleanly UI-observable; the exactly-once ordered render is the proxy, and the
    brief in-window reconnect guarantees the gap-free path. Confirm no `resync` in `daemon.log`.
  - **`ProcessLifecycleOwner` driver** doesn't fight the explicit drive (same caveat as #476: a stable
    foreground instrumented run emits no lifecycle edges; if a focus blip fires one, prefer the
    real-transport-drop variant `supervisor.currentConnection.value?.close()` + `supervisor.retry()`).
