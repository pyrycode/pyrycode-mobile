## Summary

Adds `interactiveTurn_archiveRestore_roundTripsListMembership` to `InteractiveStreamE2ETest` — a rung-3
real-claude scenario for the operator-facing Archive/Restore happy path, extending the #554 delete twin
into a **two-direction round trip**. It creates a scratch discussion, renames it to a runtime-unique name
(`"e2e551-" + System.currentTimeMillis()`), confirms that name **present** on the channel list, re-enters
the thread, archives it (overflow → "Archive", **immediate — no confirm dialog**) and asserts it is **gone**
from the active list, then navigates to Settings → "Archived discussions" → the Archive screen, restores it,
and asserts it is **present in the active list again**. Both list assertions key on the same unique token, so
each is a genuine inversion of the other. Zero production code: one new always-on `@Test` + 6 companion
constants, one `scripts/e2e-emulator.sh` LIVE-curation edit (quartet → quintet), and the ladder doc.

Steps 1–6 (land → `awaitConnected` → create discussion → rename to unique → back-to-list presence check →
re-enter thread) are reused **verbatim** from #554; the archive/restore divergence begins at step 7. All
three blockers were already cleared before this ticket started: #549 shipped the data path (PR #553), #556
and #557 shipped both surfacing halves (PR #558, PR #559), and PR #572 flipped
`RemoteConversationRepository.mutationsSupported` to `true`, making the "Archive" overflow item reachable on
the live relay path. Archive/restore is conversation-scoped (`{conversation_id}`, reply reuses
`conversation_updated`), so it carries none of the orthogonal session-scoped blockers that re-park siblings
#545 (`currentSessionId=""`) or #562 (workspace-chip catch-22).

## Patterns established

None new at the harness level — a confirming instance of the rung-3 real-claude scenario shape
(#481/#482/#566/#541/#554's template). The one genuinely new move: extending the #554 "Rename to mint a
runtime-unique identity so an absence assertion is a real inversion" pattern to a **round trip** — the same
unique token is asserted absent, then present again, on the same surface, making the *re-appearance*
attributable to a specific action (restore) rather than a fresh coincidence. Worth reusing verbatim for any
future e2e that needs to prove a two-direction state flip (not just a one-way disappearance).

## Lessons learned

(Lifted from the PR body's own Lessons-learned section, plus one code-review NIT.)

- **The restore-coroutine cancellation race.** `ArchivedDiscussionsViewModel.RestoreRequested` runs
  `viewModelScope.launch { repository.unarchive(id); _effects.send(RestoreSucceeded) }`, scoped to the
  **Archived screen's own ViewModel** — not the channel list's. Tapping restore and immediately navigating
  back would `popBackStack` that ViewModel and cancel a launched-but-unstarted `unarchive` before it ever
  sent the request, silently failing the restore and flaking the closing presence check to a timeout.
  Waiting for the "Restored" success snackbar before the return-nav closes the race — the snackbar can only
  render after `unarchive` returned and `RestoreSucceeded` was sent. Generalizes #554's discipline: whenever
  a mutation's success signal is scoped to a ViewModel the test is about to navigate away from, the
  completion guard must be observed *before* the nav, not assumed from the tap.
- **`README.md` § Pre-ship gate is stale, independently of this ticket.** It still describes only "the live
  rung-3 ping scenario" / "one real claude turn" and was never refreshed through the trio→quartet→quintet
  extensions (#566/#541/#554/#551), even though `docs/e2e-interactive-stream.md` asserts the two docs are
  cross-linked and "cannot drift" — they already have. Left untouched (outside this ticket's deliverable
  list); flagged as a follow-up doc-sync ticket, not fixed here.
- **A restored conversation is not cleaned up (code-review NIT, no change needed).** Unlike the delete
  scenario (which leaves nothing behind), the archive/restore round-trip's final state is the seeded
  `e2e551-<millis>` discussion sitting **restored** in the operator's active list — by AC design (the
  round-trip must close). Each LIVE gate run leaves one more such discussion; the "keeps repeated runs
  clean" companion-object comment is accurate re: no *collision* (unique token) but not re: no
  *accumulation*. Inherent to a round-trip test, not a defect — noted for operator awareness only.
