## Summary

Two behavioural fixes to the relay supervision loop that surface **only** when `USE_RELAY_REPOSITORY`
is flipped on (this ticket is a HIGH blocker for that flip):

1. **Connect-on-pairing.** Nothing called [`RelayConnectionController.connect()`](../features/lifecycle-connection-driver.md)
   when a fresh pairing persisted, so the loop only (re)started on the next process-lifecycle `onStart`
   ([`LifecycleConnectionDriver`](../features/lifecycle-connection-driver.md)) — a first pairing appeared
   to connect only after a background→foreground cycle. Now a **successful** persist through the Scanner
   confirm/paste flow starts the loop immediately.
2. **Stale-record dial.** The loop read the paired record **once**, before `while (isActive)`, so a loop
   started against server A kept dialing A even after the user re-paired to B. Now every dial re-reads the
   store, so a re-pair is picked up on the next dial.

Plausibly the exact symptom the temporary `PYRYDBG` connection-diagnosis logging ([#500](https://github.com/pyrycode/pyrycode-mobile/issues/500))
was chasing. ~30 lines of production code across 3 files + one new free function; code review **PASS**,
zero findings.

## Patterns established

- **`binds arrayOf(A::class, B::class)` for a Koin `single` exposed under two-plus secondary types.**
  Chained `single { … } bind A::class bind B::class` **fails type inference in this Koin version** — the
  second `bind` narrows the receiver to `KClass<A>` so the third type won't attach. Use
  `binds arrayOf(A::class, B::class)` (plural `binds`, needs `import org.koin.dsl.binds`). The spec had
  sketched the chained form; the developer corrected it to `binds` at implementation. This is the first
  multi-secondary-type bind in `AppModule` — reach for `binds` whenever a singleton needs to satisfy two
  or more interfaces.
- **Extract an inline composable side-effect into a free Android-free `suspend fun` when it needs a JVM
  unit test.** The persist→connect→navigate orchestration cannot be reached by a `testDebugUnitTest` while
  it lives in the composable lambda (it captures the `NavController` inside the private, Koin-bound
  `PyryNavHost` — the codebase's own `LiteralScreenNavigationTest` documents why that is untestable
  directly). Lifting it to a plain `suspend fun` that takes callbacks (`onPersisted`/`onFailed`) instead
  of a `NavController` gives a fast regression test of the real code path, **without** pushing logic into
  the VM and breaking its Android-free contract. The composable becomes a thin caller that supplies the
  navigate/log callbacks.
- **Order a persist-then-side-effect as `save → connect → onPersisted`, not `save → onPersisted →
  connect`.** `onPersisted` navigates away and pops the Scanner, cancelling the composable's coroutine
  scope; calling `connect()` **before** it means the loop is already launched (on the supervisor's own
  `SupervisorJob` scope, which survives the navigation) rather than racing the cancellation. `connect()`
  runs **only after** `save()` returns, so a failed persist never dials a record that isn't on disk
  (fail-closed).

## Lessons learned

- **Koin chained `bind` breaks at three types; `binds arrayOf(...)` is the fix.** (Lifted from the PR's
  Lessons-learned section.) `single { RelayConnectionSupervisor(get(), get()) } bind
  ConnectionStateSource::class bind RelayConnectionController::class` does not compile in the Koin version
  here — the second `bind`'s return type narrows so the third `::class` won't attach. The working form is
  `single { … } binds arrayOf(ConnectionStateSource::class, RelayConnectionController::class)`. Watch for
  this any time a spec sketches a two-plus-interface bind with chained `bind`.
- **Moving the `load()` inside the loop adds one suspension point per dial, but the virtual-clock test
  idiom is unchanged.** A returning suspend `load()` schedules its continuation at the current virtual
  time, which `runCurrent()` drains — so the existing `runCurrent()`/`advanceUntilIdle()` transitions
  still settle without extra clock nudging. The `benignUnpaired_…` first-iteration test still passes: a
  `null` on the very first dial idles at `Connected` and ends the loop exactly as the pre-change
  early-return did. (Reload-per-dial simply applies that same AC-3 semantics on **every** iteration.)
- **`return`, not `continue`, on the mid-loop `null` read.** A `continue` would busy-spin the `while
  (isActive)` loop when unpaired (no dial, no backoff wait). `return` ends the job; the loop is restarted
  fresh by the next `connect()`/`retry()`, which re-reads the store — matching the pre-change
  benign-unpaired behaviour with zero CPU spin.

## Security (`security-sensitive`)

Architect self-review **PASS** (spec `## Security review`); code review **PASS**, zero findings.
Load-bearing properties:

- **The change closes a trust-boundary gap, it doesn't open one.** The paired record is the trusted
  credential (validated at pairing time by the fingerprint-confirm gate, [#320](320.md)/[#342](342.md)/[#343](343.md)).
  Reload-per-dial re-reads that already-trusted store each dial, so the encrypted transport tracks the
  **current** paired server instead of one captured once — eliminating the stale-record dial. `connect()`
  is payload-free by the `RelayConnectionController` contract, so the Scanner cannot inject data into the
  connection path.
- **Fail-closed persist.** `connect()` fires only after `save()` returns; a throwing persist never dials.
- **No secret logging.** The extracted helper is log-free; the retained `Log.w` in `MainActivity`'s
  `onFailed` prints only `e.javaClass.simpleName`; `PairedServer.toString()` redacts the bearer token.
  No new file/IPC/crypto/network surface — `OkHttpRelayTransport` is created per dial via the **unchanged**
  factory.
- **No connection-spam amplification.** `connect()` is idempotent (`@Synchronized`, early-returns if a
  loop is active), so a rapid re-pair loop no-ops while a loop runs.
- **Residual (scoped out, not a merge gate):** *immediate* teardown-and-reconnect on re-pair. While a
  loop is **connected** to A, re-pairing to B does not converge until A's socket drops — a hostile A
  holding the socket open keeps the transport bound to A. This is a *narrowing* of a pre-existing gap
  (pre-fix the loop dialed A **forever**, even across drops), inert until `USE_RELAY_REPOSITORY` is on,
  and explicitly scoped out. Recommended PO follow-up: **"relay: tear down and re-dial immediately on
  re-pair."** The `attempt` backoff counter also carries across an A→B switch (benign; resetting it is
  not required by any AC).
