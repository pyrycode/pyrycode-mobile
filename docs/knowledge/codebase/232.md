# #232 — feat(ui/settings): Default model picker dialog + wire row

Wires the previously inert "Default model" row in `SettingsScreen` to a Material 3 single-choice `AlertDialog` backed by `AppPreferences.defaultModel` (the schema delivered by [#231](./231.md), with the `Model.label()` extension co-located via [#253](./253.md)'s partial walk-back). Mechanical third instance of the [#87](./87.md) `ThemePickerDialog` precedent — same dialog shape, same `(StateFlow<X>, fun onSelectX)` VM-pair shape, same fire-and-forget setter forward. Third consumer of the four-key defaults schema added in #231 (first was #233 — effort picker; second is this ticket — model picker; YOLO switch + workspace picker still pending). This slice closes the loop the StatusSheet model override (#254) was already reading via `ThreadViewModel.selectedModelFlow` (#253) — that consumer's read of `appPreferences.defaultModel` now has a Settings-side writer feeding it.

## Summary

- **New `ModelPickerDialog.kt`** in `ui/settings/` (`internal` composable, sibling to `ThemePickerDialog.kt` and `EffortPickerDialog.kt`). M3 `AlertDialog` (`title = stringResource(R.string.settings_model_dialog_title)`) over a `Column(Modifier.selectableGroup())` of three `Row`s (one per `Model.entries`); each row carries `Modifier.fillMaxWidth().selectable(selected, role = Role.RadioButton, onClick = { pending = model }).padding(vertical = 8.dp)` + `RadioButton(selected, onClick = null)` (row owns the gesture) + 8.dp `Spacer` + `Text(model.label(), style = bodyLarge)`. OK / Cancel `TextButton`s use `android.R.string.{ok,cancel}` — no app-side string ids. Pending: `var pending by remember(selected) { mutableStateOf(selected) }` — keying on `selected` resets the radio when the parent reopens the dialog after a background change. **Imports `Model.label()` from `data/preferences/Model.kt`; does not declare its own extension** — diverges from `EffortPickerDialog.kt` (which had to declare `Effort.label()` because the data-layer enum was identifier-only at the time, per #231's "defer labels to first UI consumer" convention). `Model.label()` was co-located with the enum in [#253](./253.md)'s partial walk-back (StatusSheet model section + status-row consumer pre-empted the deferral), so this slice consumes the existing extension rather than creating a third instance.
- **`SettingsViewModel.kt` extension** — fourth `(StateFlow<X>, fun onSelectX)` pair on the VM, inserted between the `useWallpaperColors` and `defaultEffort` blocks. `val defaultModel: StateFlow<Model> = appPreferences.defaultModel.stateIn(viewModelScope, WhileSubscribed(STOP_TIMEOUT_MILLIS), Model.OPUS_4_7)` and `fun onSelectDefaultModel(model: Model) { viewModelScope.launch { appPreferences.setDefaultModel(model) } }`. `Model.OPUS_4_7` as the `initialValue` matches `AppPreferences.defaultModel`'s fallback when no value is persisted (#231) — same first-emission-vs-initial-literal alignment the existing three flows use. Reuses the same `STOP_TIMEOUT_MILLIS = 5_000L` companion constant.
- **`SettingsScreen.kt` rewiring** — required `defaultModel: Model` parameter inserted between `archivedDiscussionCount` and `defaultEffort`; required `onSelectDefaultModel: (Model) -> Unit` inserted between `onToggleUseWallpaperColors` and `onSelectDefaultEffort`. Parameter ordering still groups state values first, then event callbacks, then nav callbacks, then `modifier`. New local `var showModelDialog by remember { mutableStateOf(false) }` inside the `Scaffold` content lambda alongside `showThemeDialog` / `showEffortDialog`. An `if (showModelDialog) ModelPickerDialog(selected = defaultModel, onConfirm = { model -> onSelectDefaultModel(model); showModelDialog = false }, onDismiss = { showModelDialog = false })` block sits between the existing `ThemePickerDialog` and `EffortPickerDialog` blocks. The Defaults-section "Default model" row's hardcoded `supporting = "Opus 4.7"` becomes `supporting = defaultModel.label()`; the `onClick = {}` becomes `onClick = { showModelDialog = true }`. Both `@Preview` composables now pass `defaultModel = Model.OPUS_4_7, onSelectDefaultModel = {}`. New imports: `de.pyryco.mobile.data.preferences.Model` and `de.pyryco.mobile.data.preferences.label` (the latter for `Model.label()` from `data/preferences/Model.kt`, since the extension lives at the top level of that package — unlike the `Effort.label()` resolution which goes through the same-package `EffortPickerDialog.kt`).

Mirrors the #233 `defaultEffort` lines exactly.

The three model labels stay in the existing `Model.label()` (`"Opus 4.7"`, `"Sonnet 4.6"`, `"Haiku 4.5"`) rather than fanning into `strings.xml` — same single-source-of-truth rationale as `ThemeMode.label()` / `Effort.label()`, plus the product-vendor names are intentionally non-localised (the `Model` partial walk-back's rationale).

## Patterns established

- **When the data-layer enum already has a co-located `.label()`, the picker dialog imports rather than declares.** `EffortPickerDialog.kt` (#233) declares `Effort.label()` at file scope because `Effort` was identifier-only at the time — the first UI consumer convention from [#231](./231.md) put the responsibility on the dialog file. `Model.label()` was added to `data/preferences/Model.kt` in [#253](./253.md)'s partial walk-back (StatusSheet pre-empted the deferral), so `ModelPickerDialog.kt` imports `de.pyryco.mobile.data.preferences.label` and reuses it. **Rule:** check `data/preferences/<Enum>.kt` before adding a sibling-file `.label()` extension; only declare a new one if the data-layer enum is still identifier-only. The two paths converge at the call site (`model.label()` resolves identically either way); the choice is purely about where the `when` body lives. The `Effort.label()` location (in `EffortPickerDialog.kt`) is the legacy of pre-walk-back ordering — if `Effort` ever gets a second walk-back nudge from a third consumer in `data/`-adjacent code, the move-into-`Effort.kt` follow-up is mechanical.
- **Picker dialog ordering in `SettingsScreen.kt` matches `Defaults for new conversations` row order.** The three picker-dialog `if (show…Dialog)` blocks now sit in the same order as the rows they back: Theme → Model → Effort. `ThemePickerDialog` sits at the top because the Appearance row sits above the Defaults section. `ModelPickerDialog` precedes `EffortPickerDialog` because the "Default model" row precedes "Default effort" within the Defaults section (matching Figma `17:2`). The matching `var show…Dialog` locals also follow the same ordering. **Rule for future picker-dialog additions:** insert the dialog block at the position matching the row's position in the screen's visual order; don't append at the bottom by default. This keeps the file's reading order matching the screen's reading order.
- **`(StateFlow<X>, fun onSelectX)` setter-handler pair location in `SettingsViewModel` also matches row order.** `defaultModel` sits between `useWallpaperColors` and `defaultEffort` (the rows render in the same order on `SettingsScreen`). `onSelectDefaultModel` sits between `onToggleUseWallpaperColors` and `onSelectDefaultEffort`. **Rule:** when adding a new `(flow, setter)` pair to a thin VM that mirrors a screen's section ordering, slot it positionally rather than appending — readers scanning the VM top-to-bottom can map directly to the screen's top-to-bottom row order.

## Lessons learned

- **`SettingsScreenTest.kt`'s six `setContent` blocks were not updated to pass the new required `defaultModel` / `onSelectDefaultModel` parameters.** Adding required parameters to `SettingsScreen` invalidates every existing `androidTest` call site against that signature — Kotlin's required-arg rules mean each `setContent { SettingsScreen(...) }` block must be threaded explicitly, the same way #164 threaded `archivedDiscussionCount = 0` through the then-four blocks and #233 threaded `defaultEffort = Effort.HIGH, onSelectDefaultEffort = {}` through all six. This ticket missed that cascade. As of HEAD `271f1ef` the test source will not compile against the new `SettingsScreen` signature — `./gradlew test` (the unit-test gate code-review ran) passes because the instrumented module is a separate compilation unit, but `./gradlew compileDebugAndroidTestSources` / `./gradlew connectedAndroidTest` would surface six missing-arg errors. **Whoever picks up the next slice that touches Settings screen testing OR the `SettingsScreen` signature** should add `defaultModel = Model.OPUS_4_7, onSelectDefaultModel = {}` to all six `setContent` blocks alongside their own change — it's a six-line pure-mechanical edit, and the next screen-signature slice has to walk those blocks anyway to add its own params. **Pattern for future slices that add required `SettingsScreen` parameters:** the parameter cascade extends to `SettingsScreenTest.kt`'s six `setContent` blocks, not just to the two `@Preview` composables. Pre-flight checklist when adding a required `SettingsScreen` parameter: (1) `SettingsScreen` signature, (2) both `@Preview` blocks, (3) all six `setContent` blocks in `SettingsScreenTest.kt`, (4) the `MainActivity.kt:219-236` `composable(Routes.SETTINGS)` block. #233's spec called out all four; #232's spec listed (4) but stopped short of explicitly enumerating (3), and the developer's mechanical-copy pass didn't catch the gap.
- **The deliberate-deferral pattern from [#233](./233.md) for the "lift to sealed `SettingsState`" threshold cleared on schedule.** [#233](./233.md)'s § Lessons learned explicitly named #232 (this slice) as the reason for not lifting at the third writable preference: "the sibling #232 (model picker) was in flight at architect time and lifting under #233 would force #232 to either rebase onto a new envelope or land its own mechanical-copy pair and rebase later". This ticket landed the mechanical copy as planned — four writable preferences now exist (`themeMode`, `useWallpaperColors`, `defaultEffort`, `defaultModel`). **Threshold status:** the trigger is now firmly past — three was the threshold #87 set, three was crossed by #233 (deferred), four is the count after this slice. **The next defaults consumer (YOLO switch row or workspace picker, whichever lands first after this slice settles)** is now unambiguously the right re-evaluation point — there are no remaining in-flight siblings to make the deferral cheaper than the lift. Whoever picks up that ticket should look at the four-pair shape and decide whether to lift to a sealed `SettingsState` with a per-field reducer before adding a fifth pair, or to leave the shape and let the threshold drift further. See [`settings-viewmodel.md`](../features/settings-viewmodel.md) § Edge cases for the live threshold note.
- **Two pickers landing in the same release window is the natural trigger to verify dialog-file ordering matches row ordering.** Pre-#232 the only picker was `ThemePickerDialog` (#87) — ordering had no meaning. #233 added `EffortPickerDialog` at the bottom of the Defaults section, and the dialog block in `SettingsScreen.kt` was correctly appended after the Theme block. This slice adds the third picker, and the dialog block is now positioned **between** the existing two to match the row ordering Figma `17:2` mandates ("Default model" appears before "Default effort" in the Defaults section). Without active attention, the natural lazy default would have been to append at the bottom — an avoidable scan-order divergence between the file and the screen. **Pattern:** when adding a new picker dialog to a screen with multiple, insert the dialog block in the screen file at the position matching the visual row order, not at the end of the file.
- **`Model.label()`'s data-layer placement saved a follow-up move.** `Effort.label()` will eventually want to live next to `Effort` in `data/preferences/Effort.kt` (matching where `Model.label()` already lives), but the `internal → public` widening from [#229](./229.md) deferred that as cheap-enough. `Model.label()` skipped the detour entirely — [#253](./253.md) put it directly next to the enum, so #232's dialog imports cleanly without contributing to any future move. The cost flip [#253](./253.md) cited ("two private helpers across two slices, plus an inevitable third extract-on-third-use later, are more expensive than co-locating once") was vindicated here: this is the third use, and it's a one-line import rather than a third declaration or a move. **Pattern:** when a `.label()` extension's second consumer triggers a walk-back, co-locate with the enum directly rather than widening visibility in place — the next consumer (any consumer) gets a clean import for free.
