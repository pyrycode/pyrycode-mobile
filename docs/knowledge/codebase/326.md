# #326 — stateful `ScannerScreen` + camera-permission flow

Turns the Phase-0 stateless `ScannerScreen` stub into a stateful MVI screen: introduces a `ScannerViewModel` + sealed `ScannerUiState` (`PermissionRequesting` / `ReadyToScan` / `Denied` / `Error`) and wires the runtime camera-permission flow in the `SCANNER` route — request on entry; granted → the locked viewport; denied → the existing [`ScannerDeniedScreen`](../features/scanner-denied-screen.md) (#61). **No live camera in this slice** — `ReadyToScan` renders the existing viewport unchanged; the CameraX preview + ML Kit decode that fills it is the immediately-following sibling slice and consumes this state machine. Split from #322 (itself from #277); the camera engine is the sibling slice.

## Summary

Six production/test files, no `data/` changes, no new dependency. The composable's whole former body is extracted **verbatim** into a private `ScannerViewport` and `ScannerScreen` becomes a thin `when(state)` renderer over `ScannerUiState`. A pure-synchronous `ScannerViewModel` maps `ScannerEvent` → `ScannerUiState`; the route owns the Android permission API (launcher + `checkSelfPermission`) and feeds the VM via `onEvent`, keeping the VM Android-free and its transitions unit-testable. The existing tap / "paste the pairing code instead" affordance still drives the unchanged #295 stub-pair persist + navigate. `Routes.SCANNER` stays a single nav destination — `Denied` is an in-route state render, **not** a new route.

## Patterns established

- **Route owns the VM + Android permission API; the VM stays Android-free.** The runtime permission launcher and `checkSelfPermission` live in `composable(Routes.SCANNER)`; the `ScannerViewModel` is a pure synchronous mapper fed via `onEvent`. This is what makes the state transitions unit-testable as plain JUnit (no Robolectric / no instrumentation), and keeps `ScannerScreen` a stateless `when(state)` renderer the Compose tests can drive directly. Same "route owns VM, screen is stateless" shape every other destination uses.
- **Define a state/event seam ahead of its producer, justified by testability.** `CameraError → Error` has **no live producer this slice** (the permission contract only yields granted/denied), but defining it keeps the `Error` state reachable and its transition unit-testable **now** (AC5 — an unreachable state can't have its transition tested), and hands the camera-engine slice a defined entry point for CameraX-bind / decode failure.
- **In-route state render, not a new route.** `Denied` is rendered inside the existing `SCANNER` destination via `when(state)`, reusing the #61 screen — no `Routes` entry is added (AC2: "no new denied screen is invented"). Contrast `ScannerConnectingScreen` (#62/#122), which still has no route at all.

## Lessons learned

Lifted from [PR #330](https://github.com/pyrycode/pyrycode-mobile/pull/330)'s *Lessons learned*:

- **A local `val` lambda whose body's last expression is `scope.launch { … }` infers `() -> Job`, not `() -> Unit`.** Unit-coercion only applies to lambda *literals* checked against an expected `() -> Unit` type — it does **not** apply when the lambda is bound to a `val` and later passed to a `() -> Unit` parameter. Annotate the val explicitly (`val stubPairAndNavigate: () -> Unit = { … }`) to coerce, rather than appending a bare `Unit` to the body. This bit when factoring the inline `onTap = { scope.launch { … } }` into a shared `stubPairAndNavigate` lambda.

Known limitations carried forward to the camera-engine slice (both **non-blocking NITs** from the code review, by design):

- **Process-death restores `requested = true` but the VM re-inits to `PermissionRequesting`.** `requested` is `rememberSaveable` (survives process death); the resolved `Denied`/`ReadyToScan` state lives only in the `ViewModel` (does **not** survive process death). After process death on the scanner screen with permission previously denied, `LaunchedEffect(Unit)` sees not-granted + `requested == true` → no branch fires → the viewport shell renders instead of `Denied`. **Benign** — the viewport is tappable, so the stub-pair / paste path still completes onboarding. The spec already defers on-resume re-checking to the camera-engine slice (which owns CameraX lifecycle handling); fold the fix in there rather than now.
- **The `TopAppBar` back arrow is wired to `onTap` (→ stub-pair-and-advance), not a pop.** Pre-existing Phase-0 stub behaviour ("every interactive element fires `onTap`"), preserved verbatim per AC4 — not introduced by this slice. The real back affordance lands when per-affordance lambdas split out.
