# #188 — feat(ui/thread): input bar (text input + send + voice stub)

Adds the bottom-of-screen composer to the thread surface: a new public `ThreadInputBar` composable (stateful + stateless overload pair) mounted in `ThreadScreen`'s `bottomBar`, a new `ThreadViewModel.sendMessage(text)` method that early-returns on blank and fires-and-forgets the repository mutator otherwise, and a one-line wire-up in `MainActivity`. Builds on the `ConversationRepository.sendMessage` mutator from [#187](./187.md). See the new [Thread input bar](../features/thread-input-bar.md) feature doc for the full design rationale.

## Summary

- **`ThreadInputBar` is a stateful + stateless overload pair** in a single new file (`ui/conversations/thread/ThreadInputBar.kt`). The stateful overload holds `var text by rememberSaveable { mutableStateOf("") }`, delegates to the stateless overload, and on send invokes `onSend(text)` then resets `text = ""` **only when `text.isNotBlank()`** (so the IME `Send` action on a blank field is a true no-op, not a clear). Stateful is what `ThreadScreen` mounts; stateless is what the four previews call directly.
- **Root layout is `Column` + `HorizontalDivider` + composer `Row`,** not the `Modifier.drawBehind` alternative the spec listed as equally acceptable. `HorizontalDivider(thickness = 1.dp, color = outlineVariant)` at the top of the `Column` is one M3 primitive and respects theme tokens; `drawBehind` would have needed manual `density.toPx()` math. The outer `Column` carries `Modifier.fillMaxWidth().background(surface).imePadding()`; the inner composer `Row` carries the 12dp horizontal / 8dp top / 12dp bottom padding, `Arrangement.spacedBy(8.dp)`, and `verticalAlignment = Alignment.Bottom` so the pill grows upward while the send button stays anchored.
- **The pill is `Surface(shape = RoundedCornerShape(28.dp), color = surfaceContainerHigh, modifier = Modifier.weight(1f).heightIn(min = 48.dp))`** containing a nested `Row` (padding `start = 16.dp, end = 4.dp, vertical = 4.dp`, 4dp gap, vertical-center alignment) with `BasicTextField` left + mic `IconButton` right.
- **`BasicTextField` over `TextField`.** The pill `Surface` already supplies the container styling; a material `TextField` would have to override `TextFieldDefaults.colors` to transparent on every container slot. Notable settings: `cursorBrush = SolidColor(MaterialTheme.colorScheme.primary)` (BasicTextField's default cursor is solid black and fails dark theme), `singleLine = false, maxLines = 5` (multi-line, capped at 5 visible lines), `KeyboardOptions(imeAction = ImeAction.Send) + KeyboardActions(onSend = { onSend() })` so the IME `Send` action invokes the same path as the button. `decorationBox = { innerTextField -> Box { if (text.isEmpty()) Text(R.string.thread_input_placeholder, color = onSurfaceVariant.copy(alpha = 0.6f)); innerTextField() } }` — placeholder uses `text.isEmpty()` not `isBlank()` so a leading space doesn't clobber the placeholder mid-typing.
- **Mic stub: `Toast` only, no ViewModel routing.** `val context = LocalContext.current` and `val voiceToast = stringResource(R.string.voice_input_toast)` captured once at composable scope. The mic `IconButton`'s `onClick` is `{ Toast.makeText(context, voiceToast, Toast.LENGTH_SHORT).show() }`. `Icons.Outlined.Mic` 22.dp inside a 40.dp `IconButton`, tinted `onSurfaceVariant`. The toast string `"Voice input — Phase 6"` (em dash) lives in `R.string.voice_input_toast` rather than as a Kotlin literal at the call site, matching the project's string-resource convention; the spec was ambiguous (recommended Kotlin literal) — picking the string-resource route keeps user-visible copy on the translation surface and is also cheaper to grep when Phase 6 lands.
- **Send button: `FilledTonalIconButton` with two overrides from M3 defaults.** `shape = CircleShape` (M3 default for `FilledTonalIconButton` is a rounded rectangle; Figma is a 48dp circle); `colors = IconButtonDefaults.filledTonalIconButtonColors(containerColor = surfaceContainerHigh)` (M3 default is `secondaryContainer` which renders as a tinted teal/lavender under dynamic color; Figma uses the same `surfaceContainerHigh` as the pill so the composer reads as one cluster). `enabled = text.isNotBlank()` — UI half of belt-and-suspenders. Icon: `Icons.Outlined.ArrowUpward` 22.dp, `modifier = Modifier.size(48.dp)`. No manual disabled-color plumbing — `IconButtonDefaults` handles disabled alpha automatically.
- **`Modifier.imePadding()` lives on `ThreadInputBar`'s outer `Column`, not on the `Scaffold` body modifier or the screen root.** Putting it on the screen would shift the top app bar and the `LazyColumn` upward when the keyboard opens (wrong); putting it only on the input bar lifts just the bar above the keyboard, and the `LazyColumn(reverseLayout = true)` keeps the latest item visible immediately above the lifted bar. This was called out in the spec and survived implementation unchanged.
- **`ThreadViewModel.sendMessage(text: String)` is six lines:**
  ```kotlin
  fun sendMessage(text: String) {
      if (text.isBlank()) return
      viewModelScope.launch {
          repository.sendMessage(state.value.conversationId, text)
      }
  }
  ```
  The `if (text.isBlank()) return` is the VM half of belt-and-suspenders (UI disables the button; VM double-checks because the IME `Send` action can fire on a blank field on some keyboards). Fire-and-forget by design — `repository.sendMessage` returns the appended `Message` but the UI re-renders from the (future #128) `observeMessages` subscription, so the return value is discarded. The only documented failure mode is `IllegalArgumentException` on unknown conversation id, which cannot happen at this call site (the VM only ever passes its own observed `conversationId`). Phase 4 adds error surfacing.
- **`repository` promoted from unmarked constructor parameter to `private val repository: ConversationRepository`** so the new method can call it. Pre-#188 the VM only referenced `repository` inline inside the `state` initializer; promotion is a one-token edit. The Koin binding `viewModel { ThreadViewModel(get(), get()) }` at `di/AppModule.kt:28` is unchanged — the constructor signature did not change shape, only the visibility of an existing parameter.
- **`ThreadScreen` grows one new required parameter `onSendMessage: (String) -> Unit`.** No default. Mounted as `bottomBar = { ThreadInputBar(onSend = onSendMessage) }`. The signature stays a flat callback list (`onBack`, `onSendMessage`, `onTitleClick`, `onOverflowClick`) rather than collapsing into a sealed `ThreadEvent`. The #139 [Thread screen doc](../features/thread-screen.md#shape) predicted the signature would widen to `(state, onBack, onEvent)` "when the first VM-owned event lands (#133's composer send is the most likely first)" — when #188 actually shipped, flat-callbacks for one event arm was cheaper than a `ThreadEvent` scaffold; the fold is deferred again to the first ticket that lands a *second* VM-owned event (#140 overflow or #141 rename).
- **`MainActivity.kt` edit is one named-argument line.** `MainActivity.kt:206` now passes `onSendMessage = vm::sendMessage` into the destination's `ThreadScreen` call. Method-reference syntax — no new lambda allocation per recomposition.
- **Both `@Preview`s in `ThreadScreen.kt` get a one-line update** to pass `onSendMessage = {}` so they still compile. No new screen-level preview variants — the empty-input-bar state is already covered through the stateful overload at the screen level, and the filled state is covered by the four `ThreadInputBar` previews.
- **Four `R.string.*` entries added** in `app/src/main/res/values/strings.xml`: `thread_input_placeholder = "Message"`, `cd_voice_input = "Voice input"`, `cd_send_message = "Send message"`, `voice_input_toast = "Voice input — Phase 6"` (em dash; the literal matters). Content descriptions follow the existing `cd_*` convention.
- **Two new `ThreadViewModelTest` methods** (file already had seven from #126/#139):
  - `sendMessage_blankText_isNoOp` — instantiates VM with `FakeConversationRepository()`; collects `repository.observeMessages("seed-channel-personal")` into a list; captures initial count; calls `vm.sendMessage("")` then `vm.sendMessage("   \n\t ")`; asserts unchanged. Pins the VM-side blank rejection.
  - `sendMessage_nonBlankText_appendsToConversation` — same setup; calls `vm.sendMessage("Hello world")`; asserts the observed list grew by one, the appended `ThreadItem.MessageItem` has `content = "Hello world"`, `role = Role.User`, `sessionId = "seed-session-personal"`. Pins the VM → repository forwarding contract end-to-end against the live fake.
  Both reuse the existing `Dispatchers.setMain(UnconfinedTestDispatcher())` + `runTest { launch collector; advanceUntilIdle(); … collector.cancel() }` scaffold from #139. No mock framework — the fake is real and `observeMessages` re-emits on append.

## Patterns established

- **Stateful + stateless composable overload pair, in one file, with the stateful overload as the primary public entry point and the stateless one carrying the four previews.** The pattern was already in use elsewhere (`WorkspacePicker` is the closest sibling), but #188 is the cleanest version of it for a single-`Row` UI element. Future composers / pickers / form-row primitives that need both a "ViewModel mounts this" entry point and a "previews / UI tests want fully-hoisted state" entry point should follow the same shape verbatim — overload by parameter list (no `Stateful` / `Stateless` naming suffix), `rememberSaveable` for the internal state in the stateful overload, the stateless overload taking `(text, onTextChange, onSend, modifier)` in that order.
- **`R.string.voice_input_toast` is a user-facing string in `res/values/strings.xml`, not a Kotlin literal.** Sets the precedent for future UI-layer-only side effects (Phase 6 voice input, future snackbars, future system-broadcast toasts) — user-visible copy goes on the translation surface even when there is no plan to ship a non-English locale before Play Store launch. Cheaper to localize later than to scatter `"…"` literals across composables.
- **`@Preview` naming convention `<Component> — <Theme>, <Variant>`** (e.g. `InputBar — Light, Filled`). The em-dash separator and the `<Theme>, <Variant>` two-axis suffix scales to N × M preview matrices without renames; matches `ThreadScreen.kt`'s existing `Thread — Light` / `Thread — Dark` shape and extends it cleanly to the two-variant case here.

## Lessons learned

- **`BasicTextField`'s default `cursorBrush` is `SolidColor(Color.Black)`,** which renders invisible against dark theme's near-black surfaces. `cursorBrush = SolidColor(MaterialTheme.colorScheme.primary)` is the one-line fix and matches what M3 `TextField` does internally. If a future composable uses `BasicTextField` against a dark surface and ships without the override, the regression will look like "cursor missing on dark mode" — the next ticket touching `BasicTextField` should be checked for this.
- **`FilledTonalIconButton`'s M3 default container is `secondaryContainer`, not `surfaceContainerHigh`,** and under Material You dynamic color the `secondaryContainer` slot renders as a tinted teal/lavender depending on the seed wallpaper. Figma `surfaceContainerHigh` (used here for both pill and send button) is intentionally the same neutral token as the pill so the composer reads as one cluster. Any future `FilledTonalIconButton` in this codebase that needs to match a neutral surface (and not a tinted accent) must override `containerColor = surfaceContainerHigh` (or `surfaceContainer`, depending on Figma). The naked `FilledTonalIconButton(...)` call defaults to tinted.
- **`Modifier.imePadding()` placement matters and is easy to put in the wrong spot.** On the input bar's outer `Column`: correct, only the bar lifts. On the `Scaffold` body modifier or the screen root: wrong, the top app bar and the `LazyColumn` shift upward when the keyboard opens. The spec called this out and the implementation got it right; documenting here so the next composer-shaped ticket doesn't have to re-derive the answer.
- **`decorationBox`'s placeholder uses `text.isEmpty()`, not `text.isBlank()`.** Using `isBlank()` would clobber the placeholder visually the instant the user types a space, then re-reveal it when they delete the space — flickery and surprising. `isEmpty()` matches how M3 `TextField` handles placeholders internally.
- **The architect's prediction that `ThreadScreen`'s signature would widen to `(state, onBack, onEvent)` when the first VM-owned event lands was wrong by one ticket.** #188 added one VM-owned action (`onSendMessage`) and the cheapest shape was a flat callback, not a sealed event. The fold to `ThreadEvent` is now deferred to whichever ticket lands the second VM-owned event. This isn't a process failure — the prediction was a reasonable read of the codebase convention at the time, and shipping with a flat callback for one arm is cheaper than scaffolding a sealed envelope for one arm. The doc-level prediction in `features/thread-screen.md` should be updated to reflect the actual landing.
