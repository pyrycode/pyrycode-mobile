# #329 — `RemoteConversationRepository.observeLastMessage` via the live v2 `message` stream

Replaces the throwing `observeLastMessage` stub [#312](312.md) left behind with a **live**
implementation, so the channel list shows real last-message previews instead of nothing. It rides the
connection's live `message` stream (**Design A** — no `backfill_since` request, no `message_chunk`
parsing): a new `lastMessages` `StateFlow<Map<String, Message>>` is fed by the **same** single `init`
inbound collector via a new `message` branch in `onInbound`, mapped through the [#317](317.md)
boundary, and `observeLastMessage` is a cold `distinctUntilChanged` projection of it.

See the evergreen [`remote-conversation-repository.md`](../features/remote-conversation-repository.md)
for the "how the remote repo works / what plugs into it" reference (updated by this slice). This file
is the implementation record. **No new ADR, no new feature doc** — pure `data/`-layer orchestration
extending the #312 class over an existing seam; no crypto, no new dependency, no DI/build edit.
**`security-sensitive`** (unlike the deliberately-unlabelled list slice #312): this dispatches message
**content** off the network inbound stream — same surface as the message-content siblings #313/#314
and the #317 decode boundary it consumes.

## Scope

**The last-message preview only — one stub replaced in the existing class.** Sized **S**. This slice
**owns**: the `message`-demux branch in `onInbound`, the `lastMessages` projection, the cold
`observeLastMessage` fan-out, and the `TYPE_MESSAGE` companion const. Out of scope, by design:

- **Cold-start historical population.** With Design A a quiescent conversation's preview stays empty
  until a live `message` arrives on this connection. Filling previews from history on connect is
  deferred to **#313**'s backfill plumbing (`backfill_since` → `message_chunk` → `backfill_done`); a
  later follow-up can fold `message_chunk` rows into `lastMessages` using #313's per-row-`ts`
  reconciliation. This slice deliberately does **not** pre-build `message_chunk` handling — that
  per-row reconciliation is "shared with #313, do not solve it twice."
- **The thread read path** (`observeMessages`) — still a #313 stub; the plural `messages` thread-read
  type stays an `onInbound` no-op here.
- **The mutation path** (`sendMessage`/`createDiscussion`/`promote`) — still #314 stubs.

## Summary

**One production file modified, one test file modified — zero new files, zero new exported types, no
DI/dependency/gradle change.** The class is still constructed only by the #279/#302 wiring (not yet
live); `observeLastMessage`'s signature is unchanged from the stub, so the sole consumer
([`ChannelListViewModel`](../features/remote-conversation-repository.md), #158/#162) is unaffected.

The load-bearing facts, all test-pinned (`RemoteConversationRepositoryTest.kt`, now **17 `@Test`** —
the 8 from #312 plus 9 new):

1. **Same single inbound consumer, a second projection.** No new collector or scope is added — the
   existing `init` collector (the sole consumer of the hot single-consumer `pump.inbound`) gains a
   `TYPE_MESSAGE` branch that writes a new `private val lastMessages =
   MutableStateFlow<Map<String, Message>>(emptyMap())` (`RemoteConversationRepository.kt:69`). Written
   **only** by that one sequential collector; `observeLastMessage` fans out from it. Mirrors the
   `projection`/`observeConversations` hot-source + cold-fan-out split exactly.
2. **`message` branch: decode → map via #317 → strictly-greater fold** (`:98-123`).
   `MobileJson.decodeFromJsonElement<MessagePayloadDto>(envelope.payload)` then
   `dto.toMessage(envelope, sessionId = "")`. The map key is `dto.conversationId`, **read from the DTO
   before mapping** (the domain `Message` has no conversation id — see Lessons). The fold uses
   `MutableStateFlow.update { }` for an atomic check-then-replace: replace the stored entry **iff** the
   incoming `timestamp` is *strictly greater* (`:115-122`) — so out-of-order older arrivals and
   re-delivered duplicates are no-ops, matching the Fake's `maxByOrNull { it.timestamp }`
   most-recent semantics.
3. **`observeLastMessage` is a pure cold projection** (`:174`):
   `lastMessages.map { it[conversationId] }.distinctUntilChanged()`. **No `pump.send`** — it rides the
   live stream, issues no request. A `StateFlow` always has a current value, so every collector
   (including a `flatMapLatest` re-subscription from the list ViewModel) gets the current most-recent
   (or `null`) on subscription (AC #4), re-emits only on change (AC #3), and unlimited concurrent
   collectors fan out off the one inbound consumer. `null` whenever the conversation is absent from the
   map — unknown or never-seen (AC #2).
4. **`sessionId = ""` is a list-tier placeholder, not a `null`-pun.** The `message` wire payload
   carries no session id, and the preview renders only `content` + `timestamp`, never `sessionId` — so
   `""` (the same posture #312 uses for `currentSessionId`) is correct. No fabricated session id is
   plumbed; when #313 lands session-aware thread mapping, the preview is unaffected because it never
   reads `sessionId`.
5. **Malformed `message` is dropped; the single inbound consumer survives.** The decode+map is wrapped
   in one per-envelope `try/catch (IllegalArgumentException)` (`:107-112`) covering both failure
   families — an unmappable role (`system`/unknown → `SerializationException` ⊂ `IllegalArgumentException`
   at decode, since `WireRole` models only `user`/`assistant`) and a bad `envelope.ts` (→
   `Instant.parse` `IllegalArgumentException` in `toMessage`). The bad envelope is dropped, the fold
   skipped, the lone collector keeps running — identical posture to the `conversations` branch. **The
   drop is silent**: message content may be sensitive, so nothing logs the payload (spec Security
   review §7).
6. **`TYPE_MESSAGE = "message"`** added to the companion (`:222`) — the singular live/echo `message`
   type (#317), distinct from the plural `messages` thread-read response owned by #313, which the
   `when` still ignores.

## Patterns established

- **Siblings extend the same `onInbound` `when` + add a parallel projection — never a second inbound
  collector.** #329 is the first sibling to land on top of #312, proving the [#312
  pattern](312.md#patterns-established): one demux branch + one `MutableStateFlow` projection + one cold
  `observe*` fan-out, all fed by the single `init` collector. #313 (`messages`) and #314 (mutation
  deltas) follow the same shape against the same collector.
- **Key a message by its DTO's `conversation_id`, not the mapped `Message`.** The #317
  `MessagePayloadDto.toMessage` **discards** `conversation_id` by design (`MessagePayload.kt:26-29` — the
  domain `Message` has no conversation id; the consuming repo already knows which conversation it asked
  for). Any per-conversation routing of `message` envelopes must read the key from the decoded DTO
  *before* mapping. See Lessons.
- **`sessionId = ""` for content sourced outside a session context.** The #317 mapper takes a
  caller-supplied `sessionId`; a list-tier consumer that never renders it passes `""` (matching #312's
  `currentSessionId` placeholder) rather than fabricating one. The thread path (#313) supplies a real
  session id; the preview path does not need to.
- **`MutableStateFlow.update { }` for the most-recent fold.** Even with a single sequential writer, the
  check-then-replace is expressed as an atomic `update { }` (spec Security review §8) — a deterministic
  safety net, not a convention, for the TOCTOU-shaped read-then-write.

## Lessons learned

Lifted from the PR's *Lessons learned* section and the review record:

- **`MessagePayloadDto.toMessage` discards `conversation_id` — read the map key from the DTO before
  mapping, not from the resulting `Message`.** The domain `Message` carries no conversation id, so a
  `message`-routing consumer that keys off the mapped object has nothing to key on. The branch
  destructures `val (conversationId, message) = …` straight off the DTO at the decode site
  (`RemoteConversationRepository.kt:106-109`). (This is the one non-obvious seam of an otherwise
  mechanical slice.)
- **Verify a "missing import" finding against `gh pr diff` + grep before failing.** The first
  code-review pass returned **FAIL** with a MUST-FIX claiming `import kotlinx.coroutines.flow.update`
  was absent (and a NIT about an un-destructured `Pair`) — **both were review-side errors from a garbled
  file read**; the import is present at `:20` and the branch already destructures cleanly. The review
  was retracted to a clean PASS and the `needs-rework` label removed. A `Read` can silently drop import
  lines, so cross-check any missing-import / missing-override finding against the raw diff and a grep
  exit code before posting a verdict. See [[grep-before-fail-verify-impl]].
- **Test idiom carried from #312: drive the push→demux→project→emit cascade with `runCurrent()`, not
  `advanceUntilIdle()`** — the `FakeSessionPump`'s `Channel.receiveAsFlow()` inbound feeds a
  `backgroundScope` collector with no timers to elapse, so `advanceUntilIdle()` leaves the emission
  undelivered. See [[remote-repo-test-runcurrent-not-advanceuntilidle]] and
  [312.md](312.md#lessons-learned).
