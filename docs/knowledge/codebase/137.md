# #137 — feat(ui/thread): workspace chip on empty new-discussion thread

Ships the [`WorkspaceChip`](../features/workspace-chip.md) — an M3 `AssistChip` rendered at the top of a [`ThreadScreen`](../features/thread-screen.md) body when the conversation is a fresh, unpromoted discussion with zero messages. Tap routes to the existing [`WorkspacePicker`](../features/workspace-picker.md) host (the picker landed in [#220](./220.md); the canonical wiring pattern was set by [#221](./221.md) for the Channel List FAB long-press). Also widens `ThreadUiState` with the four fields that the imminent overflow-entry-point ticket ([#208](https://github.com/pyrycode/pyrycode-mobile/issues/208)) and empty-state copy ticket ([#138](https://github.com/pyrycode/pyrycode-mobile/issues/138)) inherit for free.

## Summary

- **One new production file: `WorkspaceChip.kt`.** Stateless 67-line composable + two `@Preview`s (Light/Dark). Pure `AssistChip` with `Icons.Outlined.Folder` leading icon and `"Workspace: $workspaceLabel (change)"` label. No new design tokens, no theme additions — M3 defaults carry it.
- **`ThreadUiState` widened from 2 → 6 fields.** Added `isPromoted: Boolean = false`, `hasMessages: Boolean = false`, `workspaceLabel: String = "scratch"`, `workspacePickerVisible: Boolean = false`. All defaulted; the seven existing test cases compile unchanged because the `stateIn(initialValue = …)` block still constructs `ThreadUiState(conversationId = …, displayName = …)` with the four new fields falling through to defaults.
- **`ThreadViewModel.state` flow upgraded from `.map { … }` to `combine(observeConversations(All), observeMessages(id), pendingWorkspacePicker) { … }`.** Three upstreams instead of one. `pendingWorkspacePicker = MutableStateFlow(false)` is the new private hot source backing the picker-open signal. The `initialValue` block is byte-identical to the pre-#137 placeholder so `state_initialValue_isConversationIdPlaceholderBeforeSubscription` continues to assert `ThreadUiState(id, id)` equality.
- **Three new VM event handlers, three new flat callbacks on `ThreadScreen`.** `onWorkspaceChipTapped()` / `onWorkspacePicked(path)` / `onWorkspacePickerDismissed()`. The picked-path handler clears the flag *then* launches `repository.changeWorkspace(conversationId, path)` on `viewModelScope`; the returned `Session` is discarded — the `Conversation.cwd` update propagates via `observeConversations` re-emission, which the `combine` arm picks up to recompute `workspaceLabel`. **No `ThreadEvent` sealed type yet** — the screen now has five flat callbacks (`onBack`, `onSendMessage`, `onRetry`, `onTitleClick`/`onOverflowClick`, plus the three new ones); the fold is deferred to whichever later ticket lands the next event arm. Same posture inherited from [#188](./188.md) / [#201](./201.md).
- **`WorkspacePicker` is rendered as a sibling to the `Scaffold`, not inside its content slot.** Mirrors `ChannelListScreen.kt:180-184` exactly. The host's `ModalBottomSheet` lives in its own window, so source-order placement doesn't affect Z-order. The picker host was already imported and shipped by [#220](./220.md); this slice only adds the second trigger.
- **`Conversation.workspaceLabel()` derivation matches `FakeConversationRepository.bumpWorkspace`'s no-bound-workspace filter exactly** (`cwd.isEmpty() || cwd == DEFAULT_SCRATCH_CWD` → `"scratch"`, else `cwd.substringAfterLast('/').ifEmpty { cwd }`). Identical to the data-layer filter at `FakeConversationRepository.kt:274-277`, ensuring the chip and the recents-bumping logic agree on what "scratch" means. The `.ifEmpty { cwd }` guard against `substringAfterLast` returning empty on no-separator inputs is load-bearing — without it a bare `"X"` would render an empty label.
- **The chip's visibility predicate lives at the call site as `if (!state.isPromoted && !state.hasMessages)`, not as a derived `showWorkspaceChip` field on `ThreadUiState`.** Two reasons: (a) the `&&` of two raw fields is trivially correct to inline; (b) #208 (overflow entry) and #138 (empty-state copy) will each read the same raw signals — pre-fusing them into a hidden derived would force re-derivation downstream.
- **Six new `ThreadViewModelTest` cases (now 17 total).** All pass through the `makeVm(handle, repository, source = FakeConnectionStateSource())` helper from [#201](./201.md). Three label-derivation cases lock the `workspaceLabel()` rule (empty / sentinel / arbitrary); one consolidated case walks both raw fields (`isPromoted`/`hasMessages`) across a seeded channel and a `sendMessage`-driven flip on a fresh discussion; two event-handler cases lock the picker-open / picker-write / picker-dismiss state transitions and assert the persisted `cwd` change via `repository.observeConversations(All).first()`. No new test doubles; the existing `fixedRepo(...)` helper carries the bespoke-`cwd` cases.
- **`MainActivity.kt` destination block grows three method-reference bindings.** `onWorkspaceChipTapped = vm::onWorkspaceChipTapped`, `onWorkspacePicked = vm::onWorkspacePicked`, `onWorkspacePickerDismissed = vm::onWorkspacePickerDismissed`. No constructor change; no DI change.
- **AC#5 satisfied by previews, not androidTest.** The `app/src/androidTest/java/de/pyryco/mobile/ui/conversations/thread/` directory does not exist (verified) — adding ComposeRule infrastructure for this ticket would have been a 100+ LOC sidewinder the AC doesn't request. Visual regression artifact is the Light/Dark preview pair.

## Patterns established

- **Mirror the canonical `ChannelListViewModel` / `ChannelListScreen` picker-trigger shape exactly.** `MutableStateFlow<Boolean>` → combined into `state` → flat field on `UiState` → three handlers on the VM (open / picked / dismissed) → `WorkspacePicker` rendered as a `Scaffold` sibling at the screen root. Apply the same shape to the third planned trigger ([#208](https://github.com/pyrycode/pyrycode-mobile/issues/208), thread overflow "Change workspace…") — reuse the same `workspacePickerVisible` field and the same three handlers; do **not** introduce a parallel state machine for the overflow path. This slice introduces the field and the handlers on the thread side so #208 lands as a pure-additive "new trigger" rather than a "new trigger + new state".
- **Defaulted-field widening to `ThreadUiState` preserves existing test pattern-matches.** The seven pre-#137 `ThreadViewModelTest` cases that compare full `ThreadUiState` equality (e.g. `state_initialValue_isConversationIdPlaceholderBeforeSubscription`) compile unchanged because the new fields all default. When widening a `data class` that participates in `assertEquals(ThreadUiState(...), vm.state.value)`, default every new field and leave the `stateIn(initialValue = …)` block constructing only the originally-required fields — the data-class default propagation does the rest. Apply to future `*UiState` widenings.
- **Mirror data-layer filter rules at the UI label boundary; do not re-derive.** `workspaceLabel()`'s `cwd.isEmpty() || cwd == DEFAULT_SCRATCH_CWD` predicate is byte-identical to `FakeConversationRepository.bumpWorkspace`'s no-bound-workspace filter. The shared rule ("what counts as the scratch workspace?") lives twice — once in the recents-bumping data layer and once in the chip label — but both copies agree on intent because they cite the same `DEFAULT_SCRATCH_CWD` sentinel and the same empty-string check. Worth promoting to a shared `Conversation.isScratchWorkspace(): Boolean` extension when the third caller arrives (#208 overflow may be it); two occurrences is below the canonical extract-on-third-use threshold.
- **`changeWorkspace` return value is discarded; rely on the `observeConversations` re-emission to propagate the update.** The repository's `changeWorkspace(id, workspace): Session` returns the freshly-minted `Session`, but the VM ignores it. The `Conversation.cwd` change lands via the same flow that backs every other read on this screen — no second source of truth, no risk of the chip label diverging from the picker's selection. Apply to any future call to a repository write that emits through `observeConversations` (e.g. `rename`, `archive`, `promote` from existing screens).
- **Flat callbacks on `ThreadScreen` continue to scale past five.** The screen now takes `onBack`, `onSendMessage`, `onRetry`, `onTitleClick`, `onOverflowClick`, `onWorkspaceChipTapped`, `onWorkspacePicked`, `onWorkspacePickerDismissed` — eight callbacks total. Still cheaper than scaffolding a sealed `ThreadEvent` envelope. The fold is deferred until the next ticket lands the *ninth* arm (likely #128's message bubble interactions or #145's status row). Don't pre-emptively fold for #208 — the overflow ticket adds zero new callbacks (it reuses the three picker handlers introduced here).

## Lessons learned

- **`combine` with three upstreams over `.map` with one is the right shape when the three signals are independent.** The pre-#137 flow was `observeConversations(All).map { … }`. Adding `observeMessages` and `pendingWorkspacePicker` as conjoined fields could have been done by collapsing them into the map (e.g. by calling `observeMessages(id).first()` inside the map — wrong, blocks the upstream) or by `combineTransform`-ing in side-channels — `combine` is the canonical shape and the test scaffold (`UnconfinedTestDispatcher` + `runTest { launch collector; advanceUntilIdle(); … }`) already inherited from #139 picks up the multi-upstream wiring without changes. Verified by the six new tests passing on first run.
- **`ThreadUiState` defaults must match the chip's *safe-to-render* state, not the *don't-render* state.** With `isPromoted = false, hasMessages = false, workspaceLabel = "scratch"`, the initial-value (pre-emission) frame renders the chip — which is correct UX for a brand-new discussion's loading window. If `isPromoted = true` had been the default, channels resolving slowly would briefly *hide* the chip and then flicker it visible only to hide it again on the conversation lookup. The "wrong default" cases (channels, discussions-with-messages) self-correct on the first emission, which the fake's synchronous `MutableStateFlow.map` chain delivers immediately; the initial-value frame is invisible in practice but exists for the process-death restoration path.
- **`createDiscussion(workspace = null)` seeds `cwd = ""` (empty string), not `DEFAULT_SCRATCH_CWD`.** Caught at architect-spec time — the `workspaceLabel()` derivation's two-arm check (`cwd.isEmpty() || cwd == DEFAULT_SCRATCH_CWD`) is necessary because the data layer emits *both* values to mean "scratch": fresh discussions get `""`, the seeded sentinel-bound conversations get `DEFAULT_SCRATCH_CWD`. A single-arm check on the sentinel alone would render the empty-string case as `""` (empty label). The matching test `state_workspaceLabel_isScratch_whenCwdIsEmptyString` calls `repository.createDiscussion(workspace = null)` and asserts the chip's label so any future refactor that aligns the two paths on a single sentinel value still passes.
- **Test imports in `ThreadViewModelTest` are now sorted out of alphabetical order.** `kotlinx.coroutines.flow.first` lands at L29 (between `kotlinx.datetime.Instant` at L28 and `org.junit.After` at L30) because the IDE's Kotlin import-organizer applies the standard import-order rules and `kotlinx.coroutines.flow.*` is a distinct top-level package from `kotlinx.datetime.*` for sort purposes. Cosmetic only; do not chase. If a future ticket touches this file with a stricter formatter pass, the import block re-sorts en bloc.
- **`AssistChip` with `modifier = Modifier.fillMaxWidth()` does not stretch the chip — it stretches the chip's clickable region.** The chip itself stays compact and left-aligned; the surrounding container is full-width. This was confirmed visually at preview time; the chip looks centered within its padded row but the actual touch target is the full row width. Consistent with M3 chip semantics — `AssistChip` has intrinsic sizing and the modifier shapes the parent slot, not the chip surface. If a future design wants a stretched chip (e.g. across the whole thread body), switch to a different M3 component (`Button` / `OutlinedButton`); `AssistChip` is fundamentally a chip.
- **The chip's call site lives between `ConnectionBanner` and `LazyColumn` *inside* the existing `Column`** introduced by [#201](./201.md), not inside the `LazyColumn` as a header item. Two reasons: (a) the chip is not a list item (it doesn't participate in scroll, doesn't get recycled, doesn't need a `key`); (b) the empty `LazyColumn` body is `items(emptyList<Unit>()) { }` and there is no `item { … }` slot in the current shape — adding one would force a structural rewrite of #128's eventual `items(state.messages) { … }`. The `Column` slot is where this kind of chrome-above-list belongs.
