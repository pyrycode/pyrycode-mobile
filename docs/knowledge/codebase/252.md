# #252 — feat(ui/thread): mount ThreadOverflowMenu in ThreadTopAppBar + wire to ViewModel

Mounts the stateless `ThreadOverflowMenu` composable (landed in [#251](./251.md)) inside `ThreadTopAppBar`'s `actions` slot, hoists screen-owned `overflowExpanded: Boolean` state on `ThreadScreen` via `rememberSaveable`, and binds `onOverflowEvent = vm::onOverflowEvent` at the `MainActivity` destination block. After this slice tapping the `MoreVert` overflow icon opens the M3 `DropdownMenu`; tapping any item closes the menu and routes through `ThreadViewModel.onOverflowEvent(...)` (whose `Archive` branch already calls `repository.archive(state.value.conversationId)` — the other four cases stay no-ops until the per-item follow-ups land). Split from [#203](https://github.com/pyrycode/pyrycode-mobile/issues/203).

## Summary

- **`ThreadTopAppBar` mounts `ThreadOverflowMenu` in its `actions` slot inside a `Box`.** The pre-existing `IconButton(onClick = onOverflowClick) { Icon(MoreVert, …) }` and the new `ThreadOverflowMenu(expanded, onDismiss, onEvent)` render as siblings inside one `Box`. `Box` (not the implicit `actions` `Row`) is the right anchor because M3's `DropdownMenu` anchors to its parent layout — the row's bounds would mis-position the menu against a hypothetical multi-icon `actions` slot. Same `Box` shape as `androidx.compose.material3` source for single-icon overflow menus. Only new import on the file is `androidx.compose.foundation.layout.Box`.
- **Three new parameters on `ThreadTopAppBar`.** `overflowExpanded: Boolean`, `onOverflowDismiss: () -> Unit`, `onOverflowEvent: (ThreadEvent) -> Unit`, placed after `onOverflowClick` and before `modifier`. All three are non-defaulted — `ThreadTopAppBar` has only one caller (`ThreadScreen`), so requiring the host to pass them keeps the contract explicit. The existing `onOverflowClick: () -> Unit` parameter survives unchanged so the icon-tap path stays a single hop (`{ overflowExpanded = true }` lives at the call site, not buried inside the top bar).
- **`ThreadScreen` owns `overflowExpanded` via `rememberSaveable { mutableStateOf(false) }`.** Hoisted at the top of the body, immediately below the existing `sheetVisible by rememberSaveable { mutableStateOf(false) }` ([#254](./254.md)). `rememberSaveable` (over plain `remember`) survives configuration changes — same idiom as `sheetVisible` and the [`WorkspacePicker`](../features/workspace-picker.md) `visible` flag's host pattern. The flag is **UI-local presentation state** with no business meaning the VM needs to react to; pushing it onto `ThreadUiState` would dirty the VM contract with screen-presentation concerns. Inside the `topBar` slot, the screen passes `onOverflowClick = { overflowExpanded = true }`, `overflowExpanded = overflowExpanded`, `onOverflowDismiss = { overflowExpanded = false }`, `onOverflowEvent = onOverflowEvent` to `ThreadTopAppBar`.
- **`ThreadScreen.onOverflowClick` is renamed in place to `onOverflowEvent`.** The previous `onOverflowClick: () -> Unit = {}` parameter on `ThreadScreen`'s signature becomes `onOverflowEvent: (ThreadEvent) -> Unit = {}` — same defaulted shape so the four `@Preview` composables (which never pass it) keep compiling unchanged. The icon-tap surface is now an *internal* concern of the screen (the screen flips its own `overflowExpanded`); only the menu-item event needs to escape, and it escapes through the renamed parameter directly to `ThreadViewModel.onOverflowEvent`.
- **`MainActivity` binds `onOverflowEvent = vm::onOverflowEvent`.** Single-line addition inside the `composable(Routes.CONVERSATION_THREAD)` block at `MainActivity.kt:210`, between `onRetry = vm::retry` and `onModelSelected = vm::onModelSelected`. Method-reference syntax (rather than a fresh lambda) avoids new lambda allocations per recomposition of the destination block — same shape as the other six `vm::*` bindings.
- **No ViewModel changes; no new strings; no new dependencies.** `ThreadViewModel.onOverflowEvent(event)` and the `sealed interface ThreadEvent` landed in [#251](./251.md); this slice only mounts and binds. Five `R.string.thread_overflow_*` keys already exist. `Box`, `DropdownMenu`, `DropdownMenuItem` all ship in the existing `composeBom = 2026.02.01`. No `gradle/libs.versions.toml` edits, no Koin changes, no `AppModule.kt` edits.
- **New instrumented test `ThreadScreenOverflowTest.kt` covers the screen-level integration.** Seven `@Test` methods: (1) tapping the `cd_more_actions` icon renders all five `R.string.thread_overflow_*` labels; (2)–(6) tapping each individual menu item dispatches the matching `ThreadEvent.*` case **exactly once** (asserted by `assertEquals(listOf(ThreadEvent.NewSession), events)`) and dismisses the menu (asserted by `assertDoesNotExist()` on the tapped item — `DropdownMenu` removes its content from composition on dismiss); (7) `Espresso.pressBack()` after opening dismisses the menu and fires zero events. Compose-test scaffold mirrors [`ThreadOverflowMenuTest`](../features/thread-overflow-menu.md#threadoverflowmenutestkt-compose-gradlew-connectedandroidtest) — `createComposeRule` + `PyrycodeMobileTheme` + `InstrumentationRegistry.getInstrumentation().targetContext.getString(resId)`. Lives in `androidTest/` (not unit `test/`) because `DropdownMenu` renders into a separate platform popup window that requires a real Android `Activity`/window for positioning.

## Patterns established

- **`Box` (not the implicit `actions` `Row`) is the canonical anchor for a single-icon M3 `DropdownMenu` overflow.** The M3 `DropdownMenu` anchors to its parent layout; placing the menu as a sibling of the `IconButton` directly inside `actions`' implicit `Row` anchors against the row's bounds — wrong for a single-icon column. Wrapping both children inside a `Box` whose only content is the icon makes the menu open directly below the icon. Re-use this shape for any future top-bar overflow menu in this codebase.
- **Screen-owned `var <visible> by rememberSaveable { mutableStateOf(false) }` for UI-local presentation flags.** Third occurrence on `ThreadScreen` after `sheetVisible` ([#254](./254.md)) and `workspacePickerVisible` ([#137](./137.md), via the VM but consumed identically). The rule: a flag that controls whether a host-rendered surface (menu / sheet / dialog) is shown, has no business meaning the VM needs to react to, and must survive rotation, belongs on the screen via `rememberSaveable` — not on `ThreadUiState`.
- **Rename-in-place when collapsing a `() -> Unit` callback into a `(Event) -> Unit` sink.** The previous `onOverflowClick: () -> Unit = {}` became `onOverflowEvent: (ThreadEvent) -> Unit = {}` — same defaulted shape, same position in the signature. Existing `@Preview` callers that defaulted-through the old name default-through the new name; only the one production binding (`MainActivity`) gets edited. Apply to any future per-callback → sealed-event collapse on this screen.

## Lessons learned

- **`assertDoesNotExist()` (not `assertIsNotDisplayed()`) is the right assertion for "menu closed" in Compose tests.** `DropdownMenu` removes its content from composition on dismiss rather than just hiding it — the menu items no longer exist in the semantics tree. `assertIsNotDisplayed()` requires the node to exist but not be drawn; against a dismissed dropdown it throws `AssertionError: Failed: assertIsNotDisplayed. The component does not exist!`. Use `assertDoesNotExist()` whenever the dismissal path is "remove from composition", not "fade out in place". Same gotcha applies to `ModalBottomSheet` on dismiss.
- **`Espresso.pressBack()` + `composeTestRule.waitForIdle()` is the deterministic dismiss-without-event proof for `DropdownMenu`.** AC #4(c) said "tapping outside the open menu dismisses it" but simulating a literal tap outside a popup is brittle in Compose tests because `DropdownMenu` renders into a separate platform window — the popup scrim is a real Android window the test rule doesn't own. Back-press exercises the same `onDismissRequest` path (the documented M3 dismiss surface) and is deterministic across emulator configurations. The `composeTestRule.waitForIdle()` after `pressBack()` is non-optional — the back-press dispatch is asynchronous and the next assertion would race against the dismiss animation otherwise. Apply to any future test that needs to dismiss a popup-window-rendered M3 surface without triggering its action.
- **Method reference `vm::onOverflowEvent` doesn't need an explicit `ThreadEvent` import in `MainActivity`.** The Kotlin compiler infers the type from `ThreadViewModel.onOverflowEvent(event: ThreadEvent)`'s signature; adding an unused `import de.pyryco.mobile.ui.conversations.thread.ThreadEvent` would only get flagged by Android Lint's unused-import warning. The same pattern holds for any future `vm::*` binding that consumes a sealed event type co-located with its VM.
- **The `Box` anchor wrap is essential — verified by hand-removing it.** Replacing the `Box { IconButton(...); ThreadOverflowMenu(...) }` shape with two siblings directly inside `actions` (relying on the implicit `Row` as anchor) opens the menu under the screen-edge gutter instead of under the icon on a 360dp portrait device. The Material 3 source for `actions` is `Row(verticalAlignment = Alignment.CenterVertically, content = actions)` — anchoring against the `Row`'s bounds resolves to the row's right edge minus a `48.dp` slot, not the icon's centre. Stay with the `Box` shape; if a future ticket adds a second `actions` icon (next to the overflow), wrap *just* the overflow icon + its menu in a `Box`, not the entire `actions` slot.
