# #476 — Layer 2b: reconnect continuity (reply survives a mid-turn drop)

Adds the **`reconnect`** scenario on the **#454 deterministic emulator harness** (rung 4 / **Layer 2b**
of the mobile interactive-stream e2e ladder, `docs/e2e-interactive-stream.md`): an in-flight reply must
survive a mid-turn relay-link drop and render **exactly once** after the phone reconnects. It proves the
shipped continuity path end-to-end — the daemon's turn stays open across the phone's outage, and on
reconnect the phone re-advertises its `last_event_id` (#416) so the `event_id` high-water + `message_id`
upsert fold (#337/#385) renders the reply once: no missing text, no duplicate row.

The reusable deliverable is a new harness primitive, **`severAndRestoreLink()`**, which #477 (ordering,
`blockedBy #476`) builds on. **No production Kotlin** — it *exercises* already-shipped, already
security-reviewed behaviour (#416 cursor advertise, #391/#392 reconnect, #337/#385 dedup fold); it does
not modify it. NOT `security-sensitive`, no Figma.

## Patterns established

- **`severAndRestoreLink()` — the phone-side drop/restore harness primitive (#477 reuses it).** A
  test-thread helper that severs and restores the relay link by driving the **concrete**
  `RelayConnectionSupervisor` (it implements `RelayConnectionController`): `close()` cancels the
  supervision loop and synchronously sets `liveConnection.value = null`; the cancelled loop does **not**
  fall through to `backoff()`/re-dial, so the `currentRepository == null` phase is genuinely **stable** →
  the `first { it == null }` await is race-free (no StateFlow-conflation hazard). `connect()` then starts a
  fresh loop → new dial → a new Noise `hello` re-advertising `last_event_id`, read live off the
  coordinator's **surviving** `replayCursor`. This is a **phone-side** sever only: the daemon's relay
  session is independent and stays up, so its in-ring buffer survives and it can never trip the
  `resync`/gap path a daemon **restart** (#417) would. From the daemon's view it is identical to a network
  drop; `connect()` exercises the same `last_event_id` advertise as an auto-reconnect, so replay
  continuity is tested identically — but test-triggered (no backoff jitter), which is the rung-4
  determinism contract.
- **Await `currentRepository`, NOT `ConnectionState.Connected`, to prove a reconnect.** After an
  intentional `close()` the supervisor reports an idle-`Connected` `ConnectionState`, which would
  **false-green** a `Connected` check. `coordinator.currentRepository: StateFlow<ConversationRepository?>`
  is **Open-gated** — non-null only once the fresh Noise pump reaches `Open` — so `first { it != null }`
  proves *true end-to-end readiness* (the step-5 `sendMessage` won't throw `IllegalStateException`), not
  bare socket-up. The `null`-then-non-null transition also proves the drop **landed** (not a no-op).
- **The #454 two-drop causal fence generalises to spanning a mid-turn link drop.** Drop A
  (`reconnect-open.jsonl`, fired on the 1st `send_message.enqueued`) opens and **holds** the turn (a lone
  `thinking`, no `end_turn`); the test asserts the spinner, severs/restores the link, then sends a 2nd
  (inert) message whose enqueue fires drop B (`reconnect-done.jsonl`) to complete the turn to the
  reconnected phone. The held-open window is arbitrarily long → no timing dependency, no race. Same
  mechanism as `spinner`/`tool` — the only insertion is the sever/restore in the gap, which adds no
  `send_message`, so the watcher is reused unchanged. (Rule of thumb, from #455: two-drop iff the state
  must persist across a test action; here the action is the drop/restore, not a state assertion.)
- **Drop A carries no partial text by design — "no missing text" holds by construction.** On the drop the
  connection-scoped repo tears down (`currentRepository → null`) and the thread projection clears, so the
  fresh repo on reconnect starts empty and the **whole** reply arrives post-reconnect in drop B, once. If
  drop A had streamed partial text, that partial would live only on the torn-down repo, and whether the
  daemon re-delivers it depends on uncertain partial-turn replay semantics (events at or below
  `last_event_id` are not re-delivered by the gap-free path) — exactly the buildability risk the ticket
  flags. Keeping drop A text-free **sidesteps** that risk rather than relying on it.
- **The one deliberate count assertion is load-bearing, not a timing count.** `assertCountEquals(1)` on
  the assembled reply text is the dedup invariant (`event_id` high-water + `message_id` upsert, #337/#385):
  a re-delivered event must render the reply exactly once. It keys on the **final assembled text** (stable
  — any duplicate from replay/snapshot is a stable extra row, not a transient), so it does **not** violate
  the ladder's "never assert on counts" rule, which targets delta/timing counts. Called out in the method
  KDoc.

## Lessons learned

- **`assertCountEquals` needs an explicit import** (`androidx.compose.ui.test.assertCountEquals`) — it is
  an extension on `SemanticsNodeInteractionCollection`, unlike `onAllNodes` / `assertDoesNotExist` /
  `assertIsDisplayed`, which are members and need no import ([[androidtest-not-compiled-by-mandatory-gates]]
  — caught by the explicit `compileDebugAndroidTestKotlin` run, not the mandatory gates). (Lifted from the
  PR's Lessons-learned section.)
- **Drop A is `thinking`-only (no partial text) by design.** See the Patterns "no missing text by
  construction" point — the whole reply arrives post-reconnect, so continuity is proven without depending
  on uncertain partial-turn replay semantics. (Lifted from the PR's Lessons-learned section.)
- **This scenario proves continuity, not a genuine re-delivery dedup** (code-review observation, deferred
  to #477). Because drop B's reply arrives entirely *after* reconnect, its `event_id` is strictly greater
  than the advertised `last_event_id` → it is **delivered once**, not deduplicated. The `assertCountEquals(1)`
  guards against a *duplicate* render, but the fold's high-water/upsert path isn't actually exercised on an
  already-seen event. That is the correct, explicitly-documented scoping (it sidesteps the partial-turn
  replay uncertainty); the natural home for stressing an actual buffered-during-outage re-delivery against
  the dedup fold is **#477 (ordering)**, which reuses this `severAndRestoreLink()` primitive.

## Verification

The deliverable **is** the test harness; there is no unit test of it. Host-JVM checks (no device, per the
spec's strategy), confirmed green by QA:

- `./gradlew check` (unit tests + Android lint + spotless/ktlint) and `assembleDebug` green.
- `./gradlew compileDebugAndroidTestKotlin` green — androidTest sources compile (the mandatory gates do
  **not** compile androidTest, so this is run explicitly; [[androidtest-not-compiled-by-mandatory-gates]]).
- Both new fixtures validate as one-line JSON.
- **Operator-run (device + host `pyry`/`pyrycode-relay`/`fakeclaude`):** `DETERMINISTIC=1
  SCENARIO=reconnect … bash scripts/e2e-emulator.sh` green and re-running back-to-back yielding the same
  pass. **Not run from the pipeline** (no device); expect to tune on first run. First-run assumptions
  (documented in `e2e-interactive-stream.md`): the held-open turn resumes to the reconnected phone (the
  buildability risk to surface — never restart the daemon to work around it, that trips #417's gap path);
  the brief drop stays in the in-ring window → no `resync`; the `ProcessLifecycleOwner` driver doesn't fire
  lifecycle edges that fight the explicit `close()`/`connect()` (if a focus blip does, prefer the
  real-transport-drop variant `supervisor.currentConnection.value?.close()` + `supervisor.retry()`, which
  doesn't cancel the loop).
