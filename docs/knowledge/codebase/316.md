# #316 — `conversations` payload → domain `Conversation`-list mapping

The **first application payload** decoded on top of the [#273](273.md) wire layer: a typed `@Serializable` DTO surface for the Mobile Protocol v2 `conversations` reply plus a pure function that maps it to domain [`Conversation`](../features/data-model.md) values. It is the single decode-and-validate boundary for the conversation-list read path — untrusted `Envelope.payload` JSON in, domain `Conversation` list out, with malformed/field-incomplete payloads rejected **at decode** rather than producing a partial or `null`-punned object. Greenfield, no consumers yet: [#312](https://github.com/pyrycode/pyrycode-mobile/issues/312) (`RemoteConversationRepository`) wires the flow/repository around it.

Scope is `conversations` → `Conversation` **only** — no flows, no repository, no networking, no tiering/sorting. The last-message preview is **not** in this payload (the wire carries a `last_message_ts` timestamp but no message content); that mapping is #317's (`message` → domain `Message`), wired into the read path by #312. See [[v2-app-payload-shapes-ssot]].

See the feature doc [`mobile-protocol-v2-wire-layer.md`](../features/mobile-protocol-v2-wire-layer.md) § "Application payloads" for the evergreen reference; this file is the implementation record.

## Summary

Two `@Serializable` DTOs + a pure mapper, all under the `data/network/` namespace next to the [#273](273.md) wire models, verified by one JUnit4 test file (5 `@Test` methods). The DTOs are the camelCase analog of the server's snake_case wire shapes (`@SerialName` carries the mapping — the Go-interop contract); the mapper is the wire→domain edge, the client-side analog of the role #303's Go handler plays server-side.

The single load-bearing correctness pin: **the payload is an object-wrapped array, not a bare array** (see Patterns).

## Patterns established

- **Application-payload DTOs live in `data/network/`, co-located with the wire models, paired with a pure `toX()` domain mapper.** This refines #273's "application payloads live with their features": the decode-and-map unit sits next to the `Envelope`/`MobileJson` it decodes from, exporting a minimal surface (the DTO(s) + one mapper extension; the per-row mapper is `private`). The consumer path is `MobileJson.decodeFromJsonElement<XPayload>(Envelope.payload).toX()`. **#317 (`message`) and #318 (write-responses) follow this same shape** — one file per payload `type`, DTO + mapper together, decode the single validate boundary.
- **The payload is object-wrapped, NOT a bare array.** Server SSOT `internal/protocol/conversations_read.go` (#273) wraps the rows in `{ "conversations": [ … ] }`. Modeling it as a top-level `List<…>` would fail to decode the real frame. This is the one easy-to-miss pin — the AC prose ("the array of per-conversation summaries") describes the *contents*, not the top-level shape.
- **Timestamps decode to `kotlinx.datetime.Instant` at the DTO**, via an explicit `@Serializable(with = InstantIso8601Serializer::class)`. This makes **decode** the single validate boundary — a malformed RFC 3339 string fails before the mapper runs, so the mapper stays a total, pure field-copy with no second throw site. It is a **deliberate departure** from #273's choice to keep `Envelope.ts` a `String`: there no domain `Instant` consumed it, here domain `lastUsedAt` does. The explicit serializer is version-independent and removes any "serializer not found for `Instant`" risk in kotlinx-datetime 0.6.2.
- **Four wire-absent domain fields are list-tier placeholders, never `null`-punned.** `currentSessionId`/`sessionHistory`/`isSleeping`/`archived` are not on the conversation-list wire; full session/sleep/archive state arrives via the detail + message read paths. They get defined, non-null defaults documented at the mapping site — the `Conversation` domain type stays unmodified and the AC's "no partially-populated or `null`-punned object" holds.
- **Decode-only payload — no encode round-trip test.** `conversations` is server→phone; the phone never sends it. Re-encoding a `name: null` row under `MobileJson`'s `explicitNulls = false` would omit the key and diverge from the Go wire, so a round-trip test would spuriously fail. Test decode → map only. (Contrast #273's wire models, which are bidirectional and *do* round-trip.)

## Lessons learned

Lifted from the PR's *Lessons learned* section:

- **The decode boundary surfaces two exception hierarchies, not one — and the spec's error table got it wrong.** The architecture spec listed a malformed RFC 3339 timestamp as throwing `SerializationException`. In practice kotlinx-datetime 0.6.2's `InstantIso8601Serializer` surfaces it as **`IllegalArgumentException`** (`DateTimeFormatException`) — `Instant.parse` throws **unwrapped** straight through `decodeFromJsonElement`, not re-wrapped as a `SerializationException`. The missing-required-field case still throws `MissingFieldException` (which *is* a `SerializationException`). So the test asserts `IllegalArgumentException` for the bad-timestamp case and `SerializationException` for the field-incomplete case. **Consequence for #312:** the consumer must catch **both** families (or `Exception`) when surfacing decode errors as a UI banner/retry — catching only `SerializationException` would let a malformed-timestamp row crash the read path. Both are still "a typed decode failure at the boundary" (AC #5 holds): no partial `Conversation` is ever constructed.
