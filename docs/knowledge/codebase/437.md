# #437 — decode `modal_shown` + `modal_dismissed` into observable modal state

The **inbound (data-in) half** of the permission/choice modal feature (Phase 3 of epic pyrycode#597,
ADR 025; split from #428 → **this** / #438 answer-send / #439 render UI / #440 read-only mode). Decodes
the two v2 **binary → phone** modal envelopes — `modal_shown` and `modal_dismissed` — into a typed
`ModalEvent` family surfaced as a hot `modalEvents` `SharedFlow` on the concrete
`RemoteConversationRepository`. **Decode + surface seam only:** no send, no render, no "current modal"
projection. Greenfield — no mobile-side modal types existed before. Follows the established
[`liveSessionEvents`](../features/live-session-events.md) decode-slice pattern (#385) verbatim, with two
deliberate departures (own family + own flow; verbatim strings, no enum).

See the [Modal events](../features/modal-events.md) feature doc for the full design rationale; this file
records what shipped, the line refs, and the lessons.

## Summary

- New **portable** `sealed interface ModalEvent { Shown, Dismissed }` + top-level `ModalOption`, pure
  data, no Android imports (`data/model/ModalEvent.kt`). `Shown` carries `modalId`, `modalClass`,
  `title`, `prompt`, ordered `options: List<ModalOption>`, `defaultOptionId`; `Dismissed` carries
  `modalId`, `outcome`, `source`. The common key is `modalId` — modal payloads carry **no
  `conversation_id`** (the structural reason this is its own family, not a sixth `LiveSessionEvent`).
- Three `@Serializable internal` DTOs + two **total** `toEvent()` mappers (`data/network/InteractivePayloads.kt`):
  `ModalOptionDto`, `ModalShownPayloadDto` (`@SerialName("class") modalClass`, `@SerialName("default_option_id")`),
  `ModalDismissedPayloadDto`. All fields required non-null `String`/`List` (no `omitempty` server-side).
- `modalEvents` flow + capability-gated demux arm + `decodeModalEvent` helper + two `TYPE_*` constants
  (`RemoteConversationRepository.kt`), all **append-only** — no existing signature changed, **zero edit
  fan-out** (no `RelayRepositoryCoordinator`/`AppModule` touch; the arm reuses the already-wired #385
  `negotiatedCapabilities` supplier).
- 10 new unit tests in `RemoteConversationRepositoryTest.kt`, test-first RED→GREEN.

## Patterns established

None new — this slice deliberately reuses the [#385](./385.md) decode-slice pattern end-to-end (three
layers: `internal` DTOs → `toEvent()` mappers → portable sealed family; concrete-only hot `SharedFlow`
with `replay = 0` + bounded `DROP_OLDEST`; single existing `pump.inbound` collector, one new gated demux
arm, no second subscription; `try/catch (IllegalArgumentException)` drop-on-malformed). It **confirms**
two existing patterns rather than setting new ones:

- **A wire field that must *tolerate* unknown values is a verbatim `String` with a total mapper — the
  inverse of #385's `turn_state.state` nullable-enum mapper.** #385 maps `state → Phase` and drops an
  unrecognized value (AC there: an unknown state is a no-op). #437's AC #3 requires the **opposite** —
  `class`/`source`/`outcome` must survive a forward-compat value, so they stay plain `String` carried
  verbatim and both mappers are total (never `null`). The decision of *which* posture to use is driven by
  the AC ("drop unknown" vs "preserve unknown"), and the SSOT's framing ("plain string over a closed wire
  set, not a named enum") was the tell. A typed projection, if ever wanted, is a **consumer-side** mapper
  that preserves the raw string in an `Other(raw)` case — never the decode seam's job.
- **Family-vs-flow choice follows what the data *is*.** Modal payloads carry no `conversation_id` and
  don't fold thread rows ⇒ own family on own flow (not a sixth `LiveSessionEvent`, whose every subtype
  mandates `conversationId`). This is the same "shape follows the data" call as #387 (a tool row *is* a
  thread row → fold into the message list) and #395 (a stall is state *beside* the thread → its own
  `Set` projection). When a new interactive event arrives, decide family/flow/fold by its routing key and
  whether it is a row, not by where it's convenient to bolt on.

## Lessons learned

- **A separate `ModalEvent` family + `modalEvents` flow (not a sixth `LiveSessionEvent`) is *forced* by
  the wire, not a style preference.** Modal payloads carry no `conversation_id`, while every
  `LiveSessionEvent` subtype mandates `conversationId` and the structured demux arm routes on it
  (`stalledConversations.update { it - event.conversationId }`). Folding modal events into
  `LiveSessionEvent` would mean making `conversationId` nullable across all five existing subtypes + every
  consumer `when` + the stall-clearing fold — a wide, semantically-wrong cascade. Check the routing key
  before reusing an existing event family.
- **The modal demux arm decode-and-emits *only* — it must NOT clear a stall.** Every successfully decoded
  `LiveSessionEvent` clears an active [stall](../features/stall-state.md) (#395) because it is turn
  forward-progress. A `modal_shown` is the **opposite**: it means `claude` is *waiting* for input, so
  clearing a stall on it would be wrong. The arm sits beside the live-session arm but deliberately does
  **not** reuse its stall-clear fold (nor its thread-row fold — modals are not rows and carry no
  `conversation_id`). When adding an arm next to the structured-stream arm, do not inherit its side
  effects by reflex.
- **AC #3's "trailing/unknown fields tolerated" is automatic via `MobileJson` (`ignoreUnknownKeys =
  true`)** — no per-DTO `@JsonIgnoreUnknownKeys`. All decode goes through the single configured
  `MobileJson`, so the `modalShown_trailingUnknownFieldTolerated` test passes for free. The only thing the
  DTO shape buys is fail-closed on *missing/wrong-typed required* fields (a `SerializationException`).
