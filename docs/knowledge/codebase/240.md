# #240 — feat(ui/conversations): short-press FAB uses Settings `defaultWorkspace` via `AppPreferences` wiring

First consumer of the `defaultWorkspace` schema landed in #231. [`ChannelListViewModel`](../features/channel-list-viewmodel.md) gains [`AppPreferences`](../features/app-preferences.md) as a second constructor dep, and the `CreateDiscussionTapped` arm reads `appPreferences.defaultWorkspace.first()` inside the existing `viewModelScope.launch { … }` and passes it to `repository.createDiscussion(workspace = …)`. The `WorkspacePicked` long-press arm is unchanged — an explicit user pick keeps overriding the default. This is precisely the diff [#239](./239.md) front-loaded the `makeVm` seam for: one parameter on the VM, one parameter on the helper, drop the `@Suppress("UNUSED_PARAMETER")` — zero call-site cascade across the 18 existing tests.

## Summary

- **Constructor surface widens by one parameter, in position 2.** `ChannelListViewModel(repository, appPreferences)` — matches `SettingsViewModel`'s precedent (`SettingsViewModel(appPreferences, conversationRepository)`'s same-shape but reversed order — the convention is "the dep that the next event will read goes wherever the existing param order makes sense"; the test-seam helper is what insulates call sites from the ordering choice).
- **`CreateDiscussionTapped` becomes a two-suspend sequence inside the existing `viewModelScope.launch { … }`.** First `val workspace = appPreferences.defaultWorkspace.first()`, then `val conversation = repository.createDiscussion(workspace = workspace)`, then `navigationChannel.send(ChannelListNavigation.ToThread(conversation.id))`. No additional scopes, no `runBlocking`, no parallel-`async`, no `StateFlow<String>` projection of `defaultWorkspace` — the read is one-shot per event, sequenced before the create.
- **`WorkspacePicked` is byte-for-byte unchanged** — `repository.createDiscussion(workspace = event.workspace)` already takes the explicit user pick. Don't factor a shared helper that funnels both paths through `appPreferences`; the AC explicitly requires the long-press path to bypass the default.
- **Koin wiring is a one-token edit.** `AppModule.kt:32` `viewModel { ChannelListViewModel(get()) }` → `viewModel { ChannelListViewModel(get(), get()) }`. The `single { AppPreferences(get()) }` registration on line 29 (from #11) provides the second `get()` resolution; no module-level additions.
- **`makeVm` helper spends the #239 seam.** Two lines change: drop the `@Suppress("UNUSED_PARAMETER")` annotation on `prefs`, and the body `ChannelListViewModel(repository)` becomes `ChannelListViewModel(repository, prefs)`. All 18 existing call sites are untouched — they pass the helper's default `prefs` (a fresh `AppPreferences` over a `TemporaryFolder`-backed DataStore whose `defaultWorkspace` flow emits `DEFAULT_SCRATCH_CWD`).
- **Two new tests sit next to the existing FAB-path block.** Both use `FakeConversationRepository` end-to-end (need `createDiscussion` to actually run) and isolate the created conversation via `(after - before.toSet()).single { it.id !in beforeIds }`:
  - `shortPressFab_usesPersistedDefaultWorkspace` — `prefs.setDefaultWorkspace("~/projects/my-thing")` + `advanceUntilIdle()` before `makeVm(repo, prefs = prefs)`, then `onEvent(CreateDiscussionTapped)` + `advanceUntilIdle()`; asserts the new `Conversation.cwd == "~/projects/my-thing"`.
  - `longPressPicker_overridesDefaultWorkspace` — `prefs.setDefaultWorkspace("~/projects/default-path")` + `advanceUntilIdle()`, then `onEvent(LongPressFab)` + `onEvent(WorkspacePicked("~/projects/user-pick"))` + `advanceUntilIdle()`; asserts the new `Conversation.cwd == "~/projects/user-pick"` — the user pick wins over the default.
- **Incidental `cwd`-string change for users who haven't customized the default.** Before this ticket, an unconfigured short-press created a `Conversation` with `cwd = ""` (`FakeConversationRepository.kt:108` — `workspace ?: ""` with `workspace = null`). After, the same user creates `cwd = "~/.pyrycode/scratch"` (the `DEFAULT_SCRATCH_CWD` constant `AppPreferences.defaultWorkspace` falls back to). Both old (`""`) and new (`DEFAULT_SCRATCH_CWD`) hit `FakeConversationRepository.bumpWorkspace`'s `if (cwd.isEmpty() || cwd == DEFAULT_SCRATCH_CWD) return` early-return — no recent-workspaces list pollution. None of the 18 existing tests assert on `cwd` for the freshly-created discussion (the `workspacePicked_*` test asserts on `cwd` but uses the user-picked value, not the default), so they pass unchanged. Don't add a normalization step that maps `DEFAULT_SCRATCH_CWD` → `""` to preserve the old shape — that's a defense for a problem that hasn't been observed and would obscure the wiring.

## Patterns established

- **One-shot `.first()` read over an `AppPreferences` flow, sequenced inside the existing event-handler `viewModelScope.launch`, is the right shape when the read happens exactly once per event.** No need for a `StateFlow<String>` projection of `defaultWorkspace` — the value is consumed at the call site and discarded. The `.first()` inherits `viewModelScope`'s dispatcher (`Dispatchers.Main.immediate` on Android); DataStore's `Flow<Preferences>` switches internally to its own IO dispatcher for the file read and switches back to the collector's context for emission, so no manual `withContext(Dispatchers.IO)` is needed. **Rule for future ViewModel-side default-pref reads inside an event handler:** prefer `appPreferences.<flow>.first()` inside the existing `viewModelScope.launch { … }` over a class-level `StateFlow` projection unless the value is read by `combine` into UiState or by more than one event arm — in which case the projection shape from [`SettingsViewModel`](../features/settings-viewmodel.md) (`appPreferences.<flow>.stateIn(viewModelScope, WhileSubscribed(5_000L), <initial>)`) is the right reach.
- **Even rapid double-taps are race-free under independent-launch.** Each `CreateDiscussionTapped` event spawns a fresh `viewModelScope.launch { … }`; both coroutines do their own `.first()` read against the same DataStore. If the user opens Settings between taps and changes the default, each tap reads the value visible at the moment its `.first()` resumes — that's the desired "the default the user sees right now applies to the next tap" behaviour. Don't add a single-flight / debounce — the AC reads "single tap creates exactly one new discussion" per-tap, and the equivalent edge case for the no-default-pref world (#22's note about "two rapid FAB taps create two discussions") was already accepted.
- **Spend a deliberate test-infra seam exactly when its consumer ticket lands; don't accumulate seam debt.** #239 created the `makeVm(repository, prefs = AppPreferences(newDataStore()))` helper with `@Suppress("UNUSED_PARAMETER")` on `prefs` explicitly to make this ticket's diff "one helper line, one VM constructor line, two new tests". If a follow-up ticket had landed first that needed a different `AppPreferences`-derived dep (`defaultModel`, `defaultEffort`, `defaultYolo`), the same single-helper-line change would have served it instead — the seam is consumer-agnostic. **Rule:** when an architect splits a feature ticket into "prep test infra" + "wire it", the wire-it ticket spends the seam in one diff; don't leave the seam half-spent ("threaded but unused") for the next ticket to revisit.

## Lessons learned

- **The `static-check` invariant from the spec is worth keeping in the project's tool belt.** The spec's closing line — `grep -n "appPreferences" app/src/main/java/de/pyryco/mobile/ui/conversations/list/ChannelListViewModel.kt` should return exactly two hits (the constructor parameter declaration and the `.first()` call) — is a cheap over-build detector. A third hit means a derived field or `StateFlow` projection slipped in; a one-hit result means the parameter is declared but unread (regression of the #239 seam). The grep is a single-file scope, runs in milliseconds, and catches the failure mode that the unit tests can't directly assert on (you can test "the VM does pass the workspace" but not "the VM doesn't *also* hold a projection"). **Pattern for future single-purpose constructor-dep additions:** the architect should specify the exact use-site grep invariant in the spec, and the developer should run it as the final sanity check before commit.
- **The two new tests' shape is "drive the real fake end-to-end and diff conversations", not "verify the suspend call was made with workspace = X".** Mocking the repository to intercept the `createDiscussion` call would have shaved a few lines off each test but would have decoupled the assertion from the production code path — a future change to `FakeConversationRepository.createDiscussion`'s `cwd` projection (today `workspace ?: ""`) would silently pass the mock-based test while breaking the actual UI behaviour. The diff-based shape (`(after - before.toSet()).single { it.id !in beforeIds }`) is the same idiom the existing `workspacePicked_*` test uses at line 408–435; **rule for ViewModel-side side-effect tests that need to read state from a repository after an event:** use the real fake + observe-and-diff over a mock + interaction-verify, even at the cost of a few extra lines. This is the same belt-and-suspenders shape the project encodes in CLAUDE.md ("integration tests must hit a real database / real fake").
- **`AppPreferences.setX(...)` requires `advanceUntilIdle()` before the value is observable through `.first()` in the same `runTest` block.** The setter is `suspend` and the DataStore commit hops through DataStore's internal writer coroutine on a different dispatcher; without `advanceUntilIdle()` after the `setDefaultWorkspace(...)` call (and before the `makeVm(...)` / `onEvent(...)` chain that triggers the read), the test reads the pre-write value (i.e. the `DEFAULT_SCRATCH_CWD` fallback) and the assertion fails with a confusing "expected `~/projects/my-thing` but got `~/.pyrycode/scratch`" — the value is _correct_ for the moment the read happened, just sequenced wrong. Both new tests explicitly `advanceUntilIdle()` after the `setDefaultWorkspace(...)` call. **Pattern for future `AppPreferences`-backed tests:** any test that writes a preference and then expects to read it back must `advanceUntilIdle()` between the write and the subsequent read — the same shape `SettingsViewModelTest` uses around its `setThemeMode` / `setUseWallpaperColors` write paths since #87 / #89.
