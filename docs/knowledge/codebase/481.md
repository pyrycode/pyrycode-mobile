# #481 — Layer 3 (real claude): tool-use renders

Adds **one** real-claude emulator e2e scenario on the **shipped #421 harness**
(`InteractiveStreamE2ETest`, rung 3 / **Layer 3** of the mobile interactive-stream e2e ladder,
`docs/e2e-interactive-stream.md`): a constrained prompt makes **real claude run a shell tool**, and the
test asserts the resulting **tool step renders** in the thread. It is the **real-claude twin** of #455
(rung 4 / Layer 2c, deterministic scripted tool-step coverage) and #472 (Layer 1b, the in-process
component twin) — the `tool_use` → tool-row render path is now exercised at **all three ladder layers**.

The render path it exercises — `tool_use` → a running row, `tool_result` → done (#387 correlation fold,
#388 tool-row status UI) — is **already shipped and security-reviewed**. This ticket *exercises* it end
to end against real claude; the only seam that changes is **the prompt + the asserted tool-row markers**.
**No production Kotlin, no new files, no new types** — one additive `@Test` method + an `@Ignore`d
negative-control twin + three companion constants in the existing test, plus a coverage/assumptions
update in the developer-owned `docs/e2e-interactive-stream.md`. NOT `security-sensitive` (no new
untrusted-input parse point; the author-controlled prompt flows to real claude on the operator's host,
not to a parser on the phone), no Figma (asserts against the already-anchored tool rows `16-28`).

**Why this is the only layer that catches the drift it targets:** the scripted rung-4 backend (#455) is
pinned to a JSONL fixture and is **blind** to real claude changing its own tool-use output. Layer 3 is
the only rung that runs real claude over the real Noise/relay path, so a claude update that changes the
actual `tool_use` envelope (a different tool name, a changed shape) surfaces *here* — as a `waitUntil`
timeout — and **that is the finding the layer exists to produce**, not a flake to paper over.

## The central design decision — assert the *durable* terminal signal, not the transient running spinner

This is where Layer 3 differs from both its twins. The tool row has three status affordances, but only
the **transient Running** (`cd_tool_running`) and **Failed** (`cd_tool_failed`) states carry a positive
content-description; **Done has `contentDescription = null`** (`ToolCallRow.kt:151`). #455 (rung 4) and
#472 (component) catch the *running* state **while in flight** by holding the turn open — #455 via a
two-drop causal fence on the scripted backend, #472 via imperative `pushToolUse` → `waitUntil` →
`pushToolResult`. **Neither lever exists in rung 3:** there is no scripted backend to hold the turn, and
the test cannot imperatively pause real claude between its `tool_use` and `tool_result`. Racing the
transient running spinner over a real relay turn is exactly the *"never on timing"* failure the ladder
forbids (it is why #454/#455 needed the two-drop fence in the first place).

So the load-bearing assertion is the **durable terminal signal: the verbatim tool name renders in the
tool-row header.** `buildSummaryAnnotated` (`ToolCallRow.kt:212`) appends `toolCall.toolName` **verbatim**
to the collapsed header, which `CollapsedHeaderRow` renders **unconditionally in all three states**
(the `:224` lowercasing is icon-selection only, not the displayed text — confirmed by code review against
production source). After the turn completes the row sits in `Done` still showing `Bash` — present and
stable, no CD needed, no timing dependency. Because `TOOL_PROMPT` deliberately contains **neither "Bash"
nor "bash"**, the substring is absent from everything on screen before claude responds (the echoed user
bubble, the auto-derived thread title, the thinking spinner) — so a non-empty match can only come from
the rendered tool row. This is a **presence** check, not a count — *stricter* than #421's baseline-count
"ping" trick (which needed the count only because "ping" was already in its own prompt).

## Patterns established

- **At a layer that can't hold a turn open, key on the durable terminal signal, never race the
  transient.** Rung 4 (#455) and the component twin (#472) catch the *running* spinner by pausing the
  backend mid-turn — a lever rung 3 lacks. The general rule this slice sets: **when you cannot fence the
  turn, assert on the state that persists** (the verbatim tool name in the resolved `Done` row), which
  has no timing dependency, rather than the auto-resolving Running CD. This is the rung-3 analogue of
  #455's "absence-triad" choice for `Done` (which also has no positive CD) — both reach for a stable
  signal because `Done` carries no content-description to wait on.
- **Engineer the prompt so the asserted substring is provably absent before the response.** `TOOL_PROMPT`
  omits both "Bash" and "bash", so any non-empty `onAllNodesWithText("Bash", substring = true)` match can
  *only* originate from a rendered tool row — converting a substring check into a clean **presence** check
  with no baseline-count bookkeeping. Stricter than #421's "ping" path (where the token lives in the
  prompt, forcing a before/after count). Reusable lever for any future real-claude render assertion: pick
  an asserted token the prompt itself never contains.
- **`onAllNodesWithText(…).onFirst().assertIsDisplayed()` over `onNodeWithText(…)` for a real-claude
  assertion.** Code review flagged this as the correct resilience choice: in a real-claude run claude's
  prose could *also* contain "Bash", and `onNodeWithText` throws on multiple matches. The `onAllNodes…
  onFirst()` form tolerates claude's natural prose variation (AC #2) where the single-node selector would
  flake. The match is also **case-sensitive** (`ignoreCase` defaults false), further narrowing lowercase
  prose collisions.

## Lessons learned

- **The load-bearing assertion keys on the durable terminal signal, not the transient running spinner.**
  Rung 3 has no scripted backend to hold a turn open — the two-drop causal fence #455/#472 use to catch
  "running" in flight cannot exist here, and racing the spinner over a real relay turn is the "never on
  timing" failure the ladder forbids. (Lifted from the PR's Lessons-learned section.)
- **The tool prompt deliberately omits both "Bash" and "bash",** so the asserted substring is absent from
  everything on screen before claude responds (user bubble, auto-derived thread title, spinner) — a
  non-empty match can therefore only come from the rendered tool row, a clean presence check stricter than
  #421's baseline-count trick. (Lifted from the PR's Lessons-learned section.)
- **Tool permission behaviour is the chief first-run unknown — #421's ping path never hit it.** The
  rung-3 daemon (`scripts/e2e-emulator.sh:342`) spawns default real claude with **no permission-bypass
  flag**. If a real tool call interposes the mobile permission modal (#428 epic), the tool never runs
  without approval → the tool-row assertion times out. Preferred resolution is **daemon-side
  auto-approve** (a host/daemon-side config — *pyrycode-side, not a mobile change*) so `echo` runs without
  a modal; the fragile fallback is tapping the approve affordance in-test (couples the test to the
  #437/#438 modal UI). Confirm on first operator run; documented in the ladder doc's Assumptions. (Lifted
  from the PR's Lessons-learned section.)
- **The one tolerated weakness — prose collision.** A bare "Bash" substring could in principle match
  claude's *prose about* the tool rather than the row. A genuinely row-only signal would need a production
  test tag, which the ticket forbids. The residual tolerance is bounded by: the direct-imperative prompt
  (claude runs the tool → the row renders the name regardless of prose), the prompt omitting the token,
  the case-sensitive match, and the `@Ignore`d negative control proving the matcher's selectivity. This
  is the same documented trade-off #455/#472 accepted when keying "done" on the verbatim tool name.

## Verification

The deliverable **is** the test; there is no unit test of it. Host-JVM checks (no device, per the spec's
strategy), confirmed green:

- `./gradlew compileDebugAndroidTestKotlin spotlessCheck test lint assembleDebug` — all green. The
  explicit `compileDebugAndroidTestKotlin` is required because the mandatory gates do **not** compile
  androidTest ([[androidtest-not-compiled-by-mandatory-gates]]); no new imports were needed (the
  selectors are all already imported in the file).
- `connectedAndroidTest` not run (no device/emulator); the actual green is operator-gated via
  `bash scripts/e2e-emulator.sh` (the **default** rung-3, real-claude path), exactly as #421. The new
  method joins the existing ping method in the same `InteractiveStreamE2ETest` class; scope a single-method
  run with
  `-Pandroid.testInstrumentationRunnerArguments.class=…InteractiveStreamE2ETest#interactiveTurn_toolPrompt_rendersToolStepInThread`
  (operator invocation note, no script change).
- This is a first-green prototype, not a hardened gate — expect to tune the prompt and confirm the
  Assumptions on first run, exactly as #421/#431/#455 did. First-run unknowns (documented in
  `e2e-interactive-stream.md`): real claude emits the expected `tool_use`/`tool_result` shape with
  `name = "Bash"` (if the rendered name differs, adjust `TOOL_NAME` — **do not weaken the assertion to a
  generic match**); the permission-modal question above; whether `echo pyry481` reliably triggers the
  shell tool vs an inline answer (if irreducibly flaky, `@Ignore`-gate the positive test like the negative
  control, per AC #4).
