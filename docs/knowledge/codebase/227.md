# #227 — feat(ui/thread): archive/delete actions from ChannelInfoSheet with pop-back nav + confirm dialog

Fills the two placeholder lambdas the [#226](./226.md) Channel Info sheet host left dismiss-only. Tapping **Archive** now archives the conversation, closes the sheet, and pops the thread off the back stack to land on the channel list; tapping **Delete** opens a Material 3 confirmation `AlertDialog` and only mutates (delete + close + pop) on confirm — the initial tap touches no data. Pop-back rides the project's established `Channel` + `receiveAsFlow` nav pattern, collected in `MainActivity` and consumed exactly once. Split from #219 (← #144).

## Summary

- **Decision 1 — Reuse `ThreadEvent.Archive`, don't add a sheet-scoped archive event.** The sheet's Archive button emits the existing `ThreadEvent.Archive`; its handler is extended from "archive in place" ([#251](./251.md)/[#252](./252.md)) to "close sheet → archive → pop back." This is coherent for **both** entry points — after archiving, the conversation leaves the active list, so remaining on its now-orphaned thread makes no sense. The in-place archive from #251/#252 was the half-done placeholder the [#226](./226.md) `ThreadScreen` comment anticipated; reuse *completes* it. **Intentional consequence (accepted per ticket):** the overflow-menu Archive path now also closes-and-pops. The overflow menu still *emits* `ThreadEvent.Archive` unchanged — only the VM handler behavior changed — so the emission-only `ThreadScreenOverflowTest`/`ThreadOverflowMenuTest` are unaffected.
- **Decision 2 — New delete surface: three `data object` members on `ThreadEvent`.** `Delete` (open the confirm dialog; **no repo call**; sheet stays open), `DeleteConfirm` (delete, close dialog + sheet, pop back), `DeleteDismiss` (close dialog only; sheet stays open; nothing deleted). Naming is `Confirm`/`Dismiss`, not `Submit`/`Dismiss`: `Dismiss` keeps the dominant `ThreadEvent` suffix (`RenameDismiss`, `ChannelInfoDismiss`), and `Confirm` reads correctly for a **no-input** irreversible action — the `*Submit` pairs in this hierarchy (`RenameSubmit`, `SaveAsChannelSubmit`) all carry form input; delete has none.
- **Decision 3 — One-shot nav via a `Channel` + `receiveAsFlow`, collected in `MainActivity`.** A new single-member `sealed interface ThreadNavigation { data object PopBack }` (mirrors `ChannelListNavigation`, leaving room for future thread nav), a private `navigationChannel = Channel<ThreadNavigation>(capacity = Channel.BUFFERED)`, and `val navigationEvents: Flow<ThreadNavigation> = navigationChannel.receiveAsFlow()`. Collected in **`MainActivity`** (not the screen) because the consumer — `navController.popBackStack()` — lives in the NavHost; the new `LaunchedEffect(vm) { vm.navigationEvents.collect { … popBackStack() } }` block sits alongside the existing `state`/`connectionState` collection in the thread `composable`. This is the exact twin of the `ChannelListNavigation` collection site, and calls the same `popBackStack()` that `onBack` already calls — no need to route the programmatic pop through the `onBack` lambda. (Contrast `ArchivedDiscussionsViewModel.effects`, collected *in-screen* because that effect drives a snackbar; pop-back is a NavHost concern.)
- **Decision 4 — Delete-confirm dialog state + render.** A private `pendingDeleteConfirm = MutableStateFlow(false)` folds into the existing `transientDialogs` pre-combiner (**3 → 4 input flows**; `combine` has a 4-arg overload, and the outer `state` `combine` stays at its 5-arg ceiling), surfacing as `ThreadUiState.deleteConfirmVisible: Boolean = false`. `ThreadScreen` renders `DeleteConfirmationDialog`, gated on `state.deleteConfirmVisible`, **independent of** the `if (state.channelInfoOpen)` sheet block — so the dialog layers over the still-open sheet (AC #3: Cancel returns to the sheet). `DeleteConfirmationDialog` is a private composable mirroring `PromotionConfirmationDialog` ([#78](./78.md), `DiscussionListScreen.kt`): `AlertDialog(onDismissRequest = onDismiss, title, text interpolating the name, confirmButton/dismissButton as TextButtons)`, all `stringResource`. `onDismissRequest = onDismiss` is what makes scrim-tap / back-press route to `DeleteDismiss` (AC #3).
- **Handler contracts** (in `onOverflowEvent`, the sole exhaustive `when` over `ThreadEvent`):
  - `Archive` → `pendingChannelInfo.value = false`, then `viewModelScope.launch { repository.archive(state.value.conversationId); navigationChannel.send(PopBack) }`.
  - `Delete` → `pendingDeleteConfirm.value = true`. (No repo call — AC #2.)
  - `DeleteConfirm` → `pendingDeleteConfirm.value = false; pendingChannelInfo.value = false`, then `viewModelScope.launch { repository.delete(state.value.conversationId); navigationChannel.send(PopBack) }`.
  - `DeleteDismiss` → `pendingDeleteConfirm.value = false`. (Sheet untouched — AC #3.)
- **Sheet-button wiring** in the `ChannelInfoSheet(...)` call: `onArchive = { onOverflowEvent(ThreadEvent.Archive) }`, `onDelete = { onOverflowEvent(ThreadEvent.Delete) }` — replacing the two `ChannelInfoDismiss` placeholders and deleting the stale comment that named this ticket.
- **No error handling.** Bare `repository.archive(...)` / `repository.delete(...)`, no try/catch, matching the in-place-archive precedent. `archive` throws on unknown id; `delete` is tolerant of unknown ids (see Lessons learned). In Phase 0 the id always exists (it came from a live thread), so no failure path is reachable — and the sibling `ArchivedDiscussionsViewModel.RestoreRequested` only wraps `runCatching` because *its* AC scoped a success-snackbar; #227 has no such surface.
- **Four new `strings.xml` keys** next to `promote_dialog_*`: `delete_dialog_title` ("Delete conversation?"), `delete_dialog_body` (`"This permanently deletes \"%1$s\" and all its sessions and messages. This can't be undone."` — `%1$s` is the display name), `delete_dialog_confirm` ("Delete"), `delete_dialog_cancel` ("Cancel"). Title is type-neutral ("conversation", not "channel"/"discussion") because the sheet is reachable for both promoted and unpromoted conversations — the spec's open question, resolved to the simpler default.

## Patterns established

- **Complete the half-done placeholder by extending its existing event, don't add a parallel one.** When an earlier slice ([#226](./226.md)) deliberately wired a button to a placeholder (`ChannelInfoDismiss`) because the full behavior wasn't coherent yet, the completing ticket extends the *real* event's handler rather than minting a sheet-scoped twin — **provided** the completed behavior is coherent for every entry point. Here archive→close→pop is correct from both the sheet and the overflow menu, so reuse beats split (which would double the `ThreadEvent` surface to preserve a now-incoherent in-place archive). The discriminator is coherence-across-callers, not "is there a second caller."
- **One-shot nav now established on the thread screen too.** `sealed interface …Navigation` + `Channel<…>(capacity = Channel.BUFFERED)` + `val navigationEvents = …receiveAsFlow()`, with the suspend repo call ordered **before** `send(nav)` inside one `viewModelScope.launch`. The collection-site rule: a **NavHost** concern (`popBackStack()`, `navigate(...)`) collects in `MainActivity` (twin of `ChannelListNavigation`); an **in-screen** effect (snackbar) collects in the screen (contrast `ArchivedDiscussionsViewModel.effects`). Single-member sealed interface is the idiomatic start even with one nav event — it mirrors `ChannelListNavigation` and pre-shapes the file for a second event.
- **`Confirm`/`Dismiss` for no-input irreversible actions; `Submit`/`Dismiss` for form dialogs.** Within `ThreadEvent`, `*Submit` cases (`RenameSubmit`, `SaveAsChannelSubmit`) are `data class`es carrying validated UI input; a `data object DeleteConfirm` reads correctly for an action with no payload. Keep each dialog family contiguous in the sealed surface (`Delete, DeleteConfirm, DeleteDismiss`).
- **`DeleteConfirmationDialog` follows the `PromotionConfirmationDialog` (#78) convention.** Private composable in the screen file, `AlertDialog(onDismissRequest = cancel, title, text interpolating the name via `stringResource(id, name)`, confirmButton/dismissButton as `TextButton`s)`, all strings from resources. The destructive confirm is a **plain `TextButton`** (no `colorScheme.error` tint) — matching #78; code review flagged the lack of destructive emphasis as a non-blocking NIT and judged it correct per the convention (`MaterialTheme.colorScheme.error` on the confirm label is the M3 touch if the team ever wants it).
- **Render the confirm dialog independent of the sheet block, not nested inside it.** Two sibling top-level `if`s (`if (channelInfoOpen) { Sheet }` then `if (deleteConfirmVisible) { Dialog }`) let the dialog layer over the still-open sheet, so Cancel returns to the sheet rather than to the thread.

## Lessons learned

- **`delete`'s production impl lives on `FakeConversationRepository`, not the interface — the interface default *throws*.** `ConversationRepository.kt:61` is `suspend fun delete(id): Unit = error("delete is not implemented for this ConversationRepository")`, but the Phase-0 production-bound repo (`AppModule.kt:30` — `single { FakeConversationRepository() } bind ConversationRepository::class`) **overrides** it at `FakeConversationRepository.kt:218-222` with a tolerant `state.update { it - conversationId }` (removing a missing key returns an equals-identical map, so `StateFlow` doesn't even re-emit). **A grep that stops at the interface misreads the production path as a guaranteed crash.** The first code-review pass did exactly that — it posted a **FAIL / MUST FIX** ("Delete crashes the app; `FakeConversationRepository` never implemented `delete`; AC #4 not met") after an incomplete grep, then **retracted to PASS** once it read the Fake in full and found the override + the DI binding. Before failing on a "missing override," read the concrete impl file and confirm the DI wiring — the throwing default is a decoy. (See the user-memory note on this exact trap.)
- **Mutation-before-`send` ordering is load-bearing, not stylistic.** Inside each launched coroutine the suspend `archive`/`delete` runs to completion *before* `navigationChannel.send(PopBack)`. Once `MainActivity` receives `PopBack` and calls `popBackStack()`, the thread destination is removed and `ThreadViewModel` is cleared (its `viewModelScope` cancelled) — but because the mutation already returned by the time we `send`, cancellation can't truncate it. Same ordering `ChannelListViewModel.CreateDiscussionTapped` relies on. Inverting it (send first, then mutate) would race the VM's own cancellation.
- **`Channel(BUFFERED).receiveAsFlow()` is the one-shot guarantee — a `StateFlow<Boolean>` is not (AC #5).** The channel delivers each element to its single collector exactly once and does not replay consumed elements. On rotation, `LaunchedEffect(vm)` re-collects the *same* VM's flow, but the already-consumed `PopBack` is gone — no second pop. This is precisely why the project uses a `Channel` for nav rather than a boolean flag; `navigationEvents_eachPopBackDeliveredExactlyOnce_notReplayed` pins it. No extra de-dupe state needed.
