# #507 — Expose a "mutations supported" capability signal on the conversation repository

**Issue:** [#507](https://github.com/pyrycode/pyrycode-mobile/issues/507) ·
**Spec:** [`docs/specs/architecture/507-mutations-supported-capability-signal.md`](../../specs/architecture/507-mutations-supported-capability-signal.md) ·
**PR:** [#509](https://github.com/pyrycode/pyrycode-mobile/pull/509) ·
Size **S**, not `security-sensitive`.

## Summary

In relay mode the conversation-mutation methods are not yet implemented — `archive` / `unarchive` /
`rename` / `startNewSession` / `changeWorkspace` throw `UnsupportedOperationException` on
[`RemoteConversationRepository`](../features/remote-conversation-repository.md) and `delete` inherits the
throwing interface default — while the default [`FakeConversationRepository`](../features/conversation-repository.md)
implements every mutation. Two UI surfaces present these actions (the thread overflow menu and the Channel
Info sheet), so rather than duplicate a relay-vs-fake check inside each composable, this ticket ships a
**single capability signal off the repository**: `ConversationRepository.mutationsSupported: Boolean`
(default `true`), overridden to `false` on the remote, delegated fail-safe-deny by the
[`StableConversationRepository`](../features/stable-conversation-repository.md) facade, and snapshotted into
`ThreadUiState` by `ThreadViewModel`.

**Foundation only — no composable reads it yet.** The signal is dormant-but-testable: present in
`ThreadUiState`, consumed by nothing. In fake mode (the default binding) it reports `true` end-to-end. This
is the foundation half of #491's 4+4 split (the parent oversized at 8 production files); the consumer
[#508](https://github.com/pyrycode/pyrycode-mobile/issues/508) (`blockedBy` this ticket) reads it to hide the
actions on both surfaces. Complements the shipped one-shot guard [#490](490.md) — same thin-multi-file-thread
shape, this being the state/contract half and #490 the runtime-guard half.

## Files touched

Four production edits (three one-liners), two test edits. No new files.

- `app/src/main/java/de/pyryco/mobile/data/repository/ConversationRepository.kt` (**mod**, +12) — new
  interface member `val mutationsSupported: Boolean get() = true` (`:67`), placed after `observeQueue`,
  before `createDiscussion`. **A default *getter*, not an `= true` initializer** — interface properties have
  no backing field, so an initializer is a compile error ("Property initializers are not allowed in
  interfaces"). KDoc mirrors the `observeStall` / `observeQueue` / `delete` default-cascade style: names the
  cascade family, states that mutation-supporting impls (the fake, inline test doubles) inherit `true` with
  no override, and points at the remote's `false` override.
- `app/src/main/java/de/pyryco/mobile/data/repository/RemoteConversationRepository.kt` (**mod**, +3) —
  `override val mutationsSupported: Boolean = false` (`:1372`), alongside the throwing
  `archive`/`unarchive`/`rename`/`startNewSession`/`changeWorkspace` overrides. A class **has** a backing
  field, so an initializer is fine here (unlike the interface). One-line KDoc: relay has no v2 wire message
  for those mutations yet.
- `app/src/main/java/de/pyryco/mobile/data/repository/StableConversationRepository.kt` (**mod**, +10) —
  `override val mutationsSupported: Boolean get() = currentRepository.value?.mutationsSupported ?: false`
  (`:86-87`). **Must be a getter, not an initializer**: the facade is a process-lifetime singleton
  constructed while `currentRepository.value` is `null`, so an initializer would latch `false` **forever**,
  never reflecting a live relay. The getter re-reads `.value` on every access (exactly like the existing
  `live` getter at `:61-63`) and null-coalesces to `false`.
- `app/src/main/java/de/pyryco/mobile/ui/conversations/thread/ThreadViewModel.kt` (**mod**, +9) —
  `ThreadUiState.mutationsSupported: Boolean = true` (trailing, defaulted, `:104`); the VM captures
  `repository.mutationsSupported` **once** at construction into a private `val` (`:140`) and uses that
  captured value in **both** the `state` combine's `ThreadUiState(...)` (`:253`) and the `.stateIn`
  `initialValue` (`:262`).
- `app/src/test/java/de/pyryco/mobile/data/repository/StableConversationRepositoryTest.kt` (**mod**, +35),
  `app/src/test/java/de/pyryco/mobile/ui/conversations/thread/ThreadViewModelTest.kt` (**mod**, +34) — see
  **Testing** below.

**Not touched:** [`FakeConversationRepository`](../features/conversation-repository.md) — it inherits the
`true` default (correct: the fake supports every mutation), and no override keeps the 11 anonymous test fakes
from needing one. No composable. No `Never Update` doc.

## Patterns established

- **A capability signal is a plain `Boolean`, not a `Flow`, when the mode is static per build config.** The
  fake-vs-relay choice is a Koin module swap (`conversationRepositoryModule`, `USE_RELAY_REPOSITORY`), never a
  runtime toggle — so a **snapshot read at `ThreadViewModel` construction** is sufficient; no `StateFlow`, no
  `viewModelScope` job. Capturing the snapshot into **one** private `val` (rather than reading
  `repository.mutationsSupported` twice) guarantees the combine value and the `initialValue` can never
  disagree. Contrast the observable additions `observeStall` (#395) / `observeQueue` (#460), which *are*
  `Flow`s because their value genuinely changes per connection at runtime.
- **A capability query answers, it does not throw — a third facade posture.** The
  [`StableConversationRepository`](../features/stable-conversation-repository.md) facade already had two
  not-connected postures: cold reads render the **empty projection** (`emptyList()`/`null`), one-shots
  **throw** `IllegalStateException`. A capability read is a **third**: it must always return an answer, and
  the safe answer while absent is fail-safe-deny `false` (a gating consumer hides the impossible actions
  rather than offering them). `?: false` on the `.value` read is the plain-`Boolean` analog of `observeStall`'s
  `switchToLive(false)` — the *conceptual* fail-safe-deny model, not a literal reuse (`switchToLive` is
  `Flow`-typed).
- **The remote's `false` lives with the throwing mutations, not off on its own.** Placing
  `mutationsSupported = false` immediately above the throwing `archive`/`unarchive`/… overrides keeps the one
  capability claim adjacent to the exact methods it describes — the signal and the throws tell the same "relay
  can't do mutations yet" story and stay in sync when the wire contract eventually lands.

## Lessons learned

Two Kotlin traps gate this ticket; both were flagged in the spec and confirmed handled by code review. They
recur for **any** future capability member on this interface:

- **Interface property default must be a `get()`, not an `= value` initializer.** `val x: Boolean = true` in
  an interface is a compile error — "Property initializers are not allowed in interfaces" (no backing field).
  The default-cascade form is `val x: Boolean get() = true`. (A *class* — the remote — can use an
  initializer, which is why the two impls differ in form for the same intent.)
- **A facade override that must reflect live state has to be a getter, not an initializer.**
  `StableConversationRepository` is constructed once at app start while `currentRepository.value` is `null`.
  `override val mutationsSupported = currentRepository.value?.mutationsSupported ?: false` would evaluate that
  expression **once at construction** → `false` forever, silently never reflecting a relay that connects
  later. It must be `get() = currentRepository.value?.mutationsSupported ?: false` so it re-reads `.value` on
  every access — the same live-read shape as the existing `live` getter. The churn-back-to-`null` test
  (below) is what pins this: it proves the getter re-reads rather than snapshotting.

  These mirror the two traps memory flagged pre-implementation for this ticket (interface prop `get() = true`
  NOT `= true`; facade override MUST be a getter reading `.value`, else initializer → false-forever).

**Accepted limitation (by design):** because the VM snapshots at construction, a relay connection that lands
*after* VM construction does not flip the captured value. Intended — the mode is static per build config, and
while no connection is live the fail-safe-deny `false` is the safe default for a gating consumer. Any future
dynamic re-read is #508's concern, out of scope here.

## Testing

Unit tests only (JVM, `./gradlew test lint assembleDebug` + `spotlessCheck` all green). No `androidTest` —
no composable is touched, so `connectedAndroidTest` is N/A. Hand fakes, no MockK, consistent with both
existing test files.

- **`StableConversationRepositoryTest`** — `runCurrent()` not `advanceUntilIdle()` (per the file's
  memory-anchored rule), driving a `MutableStateFlow<ConversationRepository?>` directly:
  - `mutationsSupported_whileAbsent_isFalse` — `current.value = null` → facade reports `false` (fail-safe-deny).
  - `mutationsSupported_delegatesToLiveValue_andReReadsAcrossChurn` — `null` → `false`; a `RecordingConversationRepository`
    (inherits the `true` default) → `true`; a `ConversationRepository by RecordingConversationRepository()`
    overriding `mutationsSupported = false` (the relay's shape) → `false`; churn back to `null` → `false`
    **proves the getter re-reads `.value` live rather than snapshotting at construction**.
- **`ThreadViewModelTest`** — asserts `state.value.mutationsSupported` reflects the injected repository on
  **both** the `initialValue` (no collector) and combine (after a `collect{}`) paths:
  - `mutationsSupported_fromFakeRepository_isTrueInInitialValueAndCombine` — `FakeConversationRepository()`
    (inherits `true`) → `true` on both paths.
  - `mutationsSupported_fromNonSupportingRepository_isFalse` — a `ConversationRepository by FakeConversationRepository()`
    overriding `mutationsSupported = false` (keeps all other fake behaviour so `makeVm` assembles state
    unchanged) → `false` on both paths.
- **Existing test stays green (verified, not rewritten):** `state_initialValue_isConversationIdPlaceholderBeforeSubscription`
  asserts `vm.state.value == ThreadUiState(conversationId = …, displayName = …)`; both sides now carry
  `mutationsSupported = true` (the data-class default on the expected side, the fake's inherited `true` on the
  actual side), so equality holds.
