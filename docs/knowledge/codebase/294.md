# #294 — encrypted PairedServerStore (Keystore-wrapped credential record)

The **paired-server credential custodian of the Phase 4 reconnect chain**: an encrypted-at-rest store for the four values the phone needs to re-establish its authenticated relay session after process death — `serverId`, `token`, `relayUrl`, `serverStaticPublicKey` — all `String`, stored and reloaded byte-faithfully. Reconnect needs the **real** paired-server identity, not a boolean. Ships **dormant** — no consumer is wired; the `pairedServerExists` boolean stays the sole live source of paired-state truth until the sibling switch-over ticket. Mirrors [#291](291.md), which shipped `DeviceStaticKeyStore` before its consumer (#275) existed. `security-sensitive` (the asset is the bearer `token` + server identity). Split from [#292](https://github.com/pyrycode/pyrycode-mobile/issues/292).

See the feature doc [`paired-server-store.md`](../features/paired-server-store.md) for the evergreen "how custody works / how #275 + #276 consume it" reference. This file is the implementation record. No new ADR — this ticket is a **second consumer of [ADR 0006](../decisions/0006-keystore-wrap-at-rest-device-static-key.md)** (AES-GCM-under-Keystore wrap-at-rest), not a new mechanism.

## Summary

One portable file (`PairedServerStore.kt`: interface + `@Serializable` record + typed exception, zero `android.*`) plus one Keystore-backed impl (`KeystorePairedServerStore.kt`) in the existing `data/crypto/` package, wired with one DI binding, verified by one instrumented test file (7 `@Test` methods). **No new dependency, no gradle edit** — `AndroidKeyStore` + `javax.crypto` are framework; kotlinx.serialization + DataStore were already wired.

The encryption mechanism is unchanged from #291 / ADR-0006: AES-256-GCM under a hardware-backed, non-exportable, uid-scoped `AndroidKeyStore` wrap key, a per-encrypt Keystore-generated IV, `base64(iv ‖ ciphertext)` in the app-private `app_prefs` DataStore. What this ticket pins down is the **three deliberate divergences from #291**, plus the simplifications that fall out of the single-record shape:

1. **The plaintext is a JSON document, not raw key bytes** — `Json.encodeToString(record)` → UTF-8 → AES-GCM; load reverses it.
2. **`load()` is graceful** — returns `null` for absent *and* undecryptable/corrupt records, **never throws**. This is the **inverse** of #291's `loadOrCreate()` (which throws on decrypt failure). Justified because the record is re-fetchable from the QR → no identity-drift risk → an unreadable record safely resolves to "no paired server → re-pair."
3. **A dedicated wrap-key alias** `pyrycode.paired_server_wrap`, distinct from #291's `pyrycode.device_static_wrap` — no cross-purpose key reuse (this is a symmetric AEAD at-rest key, not #291's asymmetric X25519 Noise identity material). No hard dependency on #291.
4. **(Simplification)** One fixed pref key (no per-server namespacing) → none of #291's attacker-influenced key-collision surface; and **no `Mutex`** (no check-then-generate to serialise — `load()` is a pure read, `save()` a pure atomic overwrite).

## Files touched

Two production source files **NEW** under `app/src/main/java/de/pyryco/mobile/data/crypto/`, one DI edit, one **NEW** instrumented test:

- **`PairedServerStore.kt`** (57 lines) — the portable contract, **zero `android.*` imports** (only `kotlinx.serialization.Serializable`, which is multiplatform):
  - `interface PairedServerStore` — `suspend fun load(): PairedServer?` (graceful: null for absent OR undecryptable/corrupt, never throws) + `suspend fun save(record: PairedServer)` (encrypt + persist, overwriting; throws `PairedServerStoreException` on Keystore/IO failure).
  - `@Serializable data class PairedServer(serverId, token, relayUrl, serverStaticPublicKey)` — all four fields `String`. **A `data class`** (unlike #291's plain-class `DeviceStaticKeyPair`) — its fields are all `String`, so structural `equals`/`hashCode`/`copy` are correct and useful (tests assert `assertEquals(record, loaded)`). The **only** override is `toString()` → `"PairedServer(serverId=$serverId)"`, declared explicitly to **redact the bearer `token`** (the compiler-generated `toString` would render it in plaintext and leak it to Logcat via a stray `Log.d("$record")`). `equals`/`hashCode`/`copy` stay generated; serialization is unaffected (the wire needs the real token).
  - `class PairedServerStoreException(message, cause?)` — single typed failure for `save()`; carries no secret material (cause-class + operation only).
- **`KeystorePairedServerStore.kt`** (132 lines) — the Android-bound impl (`android.security.keystore.*` + `android.util.Base64`):
  - Constructor takes **only `DataStore<Preferences>`** (no `Context` — `AndroidKeyStore` ops go through the keystore daemon and need none), keeping `data/` portable behind the interface.
  - `load()` — `withContext(Dispatchers.IO)`; read `PREF_KEY`; **null → return null immediately** (fast empty path, no Keystore touch). If present: `decode` (base64) → **`if (blob.size <= GCM_IV_LENGTH) return null`** (the truncation guard — see Lessons) → `getWrapKey()` (non-creating; null → null) → `unwrap` (split 12-byte IV, AES-GCM decrypt) → UTF-8 → `json.decodeFromString<PairedServer>`. The catch set is the **specific** `{ GeneralSecurityException, IOException, IllegalArgumentException }` → `null`; **never `Exception`/`Throwable`**, so `CancellationException` propagates.
  - `save(record)` — `withContext(Dispatchers.IO)`; `json.encodeToString(record)` → UTF-8 → `wrap` (AES-GCM under `getOrCreateWrapKey()`, IV-prepended) → `encode` (base64) → single `dataStore.edit { prefs[PREF_KEY] = … }`. `GeneralSecurityException`/`IOException` → wrap → `throw PairedServerStoreException("paired server save failed: ${e.javaClass.simpleName}", e)`.
  - `wrap`/`unwrap` — `AES/GCM/NoPadding`; encrypt **omits any IV spec** so the Keystore emits a fresh IV per op (read from `cipher.iv`, prepended); decrypt splits the 12-byte IV back off with a `GCMParameterSpec(128, iv)`. Lifted verbatim from #291.
  - `getWrapKey()` — **non-creating** lookup (`keyStore.getKey(alias) as? SecretKey`), so `load()` never mints a key: a missing alias → blob undecryptable → `null`. `getOrCreateWrapKey()` — get-or-create the AES-256-GCM key (`PURPOSE_ENCRYPT or PURPOSE_DECRYPT`, GCM, no padding, 256-bit; no `setUserAuthenticationRequired`, no forced StrongBox), used only by `save()`.
  - `json` — one reused `Json { ignoreUnknownKeys = true }` instance (forward-compat if the record schema ever grows).
  - Companion constants — `WRAP_KEY_ALIAS = "pyrycode.paired_server_wrap"`, `PREF_KEY = stringPreferencesKey("pyrycode.paired_server")` (one record, one fixed key — server-id lives *inside* the encrypted blob, never as a pref-key component), `TRANSFORMATION`, `GCM_IV_LENGTH = 12`, `GCM_TAG_BITS = 128`, `WRAP_KEY_SIZE_BITS = 256`.
- **`di/AppModule.kt`** (+3 lines) — `single { KeystorePairedServerStore(get()) } bind PairedServerStore::class`, directly beneath the #291 `DeviceStaticKeyStore` binding; `get()` resolves the already-registered `DataStore<Preferences>`. No consumer cascade (#275/#276 not wired) → edit fan-out **1**.
- **`androidTest/.../data/crypto/KeystorePairedServerStoreTest.kt`** (151 lines, **NEW**) — `@RunWith(AndroidJUnit4::class)`, instrumented (real `AndroidKeyStore` needs a device). Per-test DataStore via `context.preferencesDataStoreFile("test_paired_server_${UUID.randomUUID()}")`; `@After` deletes the `pyrycode.paired_server_wrap` alias + the test prefs file (hermetic). `newStore()` factory; an **adversarial sample record** (pubkey with base64-std `+`/`/`/`=`, relayUrl keeping its `/v1/client` path + a query param, a long hex token) proves byte-faithfulness. ## Patterns established

- **JSON-document-then-encrypt envelope for a multi-field secret record.** Where #291 wraps raw key bytes, this store JSON-serializes a typed `@Serializable` record, UTF-8-encodes it, then runs the *same* AES-GCM wrap. Only the outer JSON document is encrypted; the field Strings pass through `kotlinx.serialization` untouched, so the hex token, the base64-STD pubkey (incl. `+`/`/`/`=`), and the relayUrl with its `/v1/client` path survive **byte-identical** — #275/#276 receive exactly what the server sent. Reuse this shape for any future multi-field secret in `data/crypto/` (the plaintext being a typed object, not field-concatenation, also means no delimiter-injection surface). `kotlinx.serialization` is multiplatform, so it does **not** break `data/` portability.
- **`data class` + explicit redacting `toString()` is the leak-guard for a secret-bearing value type.** Because all fields are `String`, the record gets correct structural `equals`/`hashCode`/`copy` for free (tests want them) — but the auto-generated `toString` would render the bearer `token`. Declaring **only** `toString()` keeps the other three generated and redacts the token in one line. (Contrast #291's `DeviceStaticKeyPair`, a *plain* class precisely because its `ByteArray` fields make a `data class`'s structural equality a trap.) Rule: a secret-bearing `data class` overrides `toString()` to a non-secret projection; it does not suppress `equals`/`hashCode`.
- **Graceful `null`-returning `load()` with a specific catch set — the inverse of #291's throw-don't-regenerate.** The catch set is the **specific** `{ GeneralSecurityException, IOException, IllegalArgumentException }` (covers `AEADBadTagException ⊂ GeneralSecurityException`, `SerializationException ⊂ IllegalArgumentException`, and `Base64.decode`'s `IllegalArgumentException`), **never `Exception`/`Throwable`** — so `CancellationException` propagates (structured-concurrency cancellation honoured) and genuine programming bugs aren't masked as a silent "no paired server → re-pair" loop. This is correct *here* (and a throw is correct in #291) because the discriminator is **identity-drift risk**: #291's keypair is unrecoverable if regenerated (→ throw); #294's record is re-fetchable from the QR (→ null is safe).
- **Single fixed pref key eliminates the attacker-influenced key-collision surface entirely.** `serverId` is a field *inside* the encrypted blob, never a pref-key or filesystem-path component — so **none** of #291's diverge-at-a-fixed-prefix-char namespacing dance is needed (that pattern exists only because #291 keys *by* the untrusted `serverId`). One record, one key, one atomic `edit { }` → no half-record state, no `Mutex` (DataStore's `edit { }` is already serialised; concurrent saves are last-writer-wins).
- **Non-creating `KeyStore.getKey` lookup on the read path.** `load()` uses `getKey(alias) as? SecretKey` (returns `null` if absent) rather than get-or-create, so a *read* never mints a wrap key — a missing alias short-circuits to `null` (→ re-pair) deterministically, instead of minting a key that then fails the GCM tag. `save()` is the only get-or-create caller. Standard shape for a graceful-read encrypted store.

## Lessons learned

Lifted from the PR's *Lessons learned* section:

- **A truncated blob would crash the graceful path — guard the IV split explicitly.** `Base64.decode` throws `IllegalArgumentException` on malformed input (caught), but a *short-but-valid-base64* decoded blob would make `copyOfRange(0, GCM_IV_LENGTH)` throw `IndexOutOfBoundsException` — which is **not** in the graceful catch set and would crash. Fixed by an explicit `if (blob.size <= GCM_IV_LENGTH) return null` check **before** the IV split, so corrupt/truncated records resolve to `null` rather than throw. Lesson: when a catch set is deliberately specific (to let `CancellationException` through), audit every pre-decrypt array operation for an *un-caught* exception it could raise on adversarial input, and guard it inline.
- **Use a non-creating Keystore lookup on `load()` so a read never mints a key.** The first instinct (get-or-create everywhere) would have a *read* create the wrap key as a side effect, then fail the later GCM-tag check to reach `null`. The non-creating `KeyStore.getKey` lookup short-circuits a missing alias straight to `null` (→ re-pair) with no key-mint side effect — cleaner and side-effect-free.
- **The instrumented round-trip cannot be JVM-tested — and "process restart" is survived by construction** (carried over from #291). Real `AndroidKeyStore` needs a device/emulator, so there is no `test/` (JVM) companion; `./gradlew check` only *compiles* the test (`compileDebugAndroidTestKotlin`), and `connectedAndroidTest` was **not** run in the PR environment (no device). A fresh `KeystorePairedServerStore` over the *same* DataStore is the automatable proxy for an app restart; genuine process death is survived because both the DataStore file and the Keystore alias outlive the process (documented in a test comment).
