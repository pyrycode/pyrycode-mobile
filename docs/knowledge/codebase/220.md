# #220 — feat(ui/sheets): `WorkspacePicker` host composable

Lands [`WorkspacePicker`](../features/workspace-picker.md), the stateful host that owns the workspace-picker flow: it composes [`WorkspacePickerSheet`](../features/workspace-picker-sheet.md) (#212) and [`CreateFolderDialog`](../features/create-folder-dialog.md) (#213), reads [`recentWorkspaces()`](../features/conversation-repository.md) ([#209](./209.md)), calls [`createWorkspaceFolder(name)`](../features/conversation-repository.md) ([#210](./210.md)) on submit, and reports the picked path back via a single `onPicked` callback. Each consumer screen contributes one `Boolean` (`visible`) to its `UiState` and one callback (`onPicked(path)`) — every other piece of wiring lives inside the host. No consumer screens are wired in this ticket; the first consumer (Channel List FAB long-press) is the next ticket and depends on this one landing first.

See [`../features/workspace-picker.md`](../features/workspace-picker.md) for the evergreen contract.

- **Visibility `public`, not `internal`.** First composable in `ui/conversations/components/` that's `public` rather than `internal` — different posture from [`WorkspacePickerSheet`](./212.md) and [`CreateFolderDialog`](./213.md). The reason: the host is the package's external contract — consumer screens in sibling packages (`ui/conversations/list/`, `ui/conversations/thread/`) call it directly, and Kotlin's default top-level visibility is `public`. The children stay `internal` because consumer screens never call them directly; they always go through the host.
- **Public wrapper + `internal` testing-seam split** is the load-bearing architectural move. The public `WorkspacePicker` does `if (!visible) return` then `koinInject<ConversationRepository>()` then delegates to `WorkspacePickerInternal(repository, ...)`. The seam takes the repository as a parameter; the Compose UI tests instantiate `FakeConversationRepository()` directly and pass it in. **The seam is `internal`, not `private`** — same shape as [`CreateFolderDialog`](./213.md)'s `CreateFolderDialogInternal` *but* with a deliberate visibility step: `private` would hide the seam from the `androidTest/` source set, and the tests need to reach it because there's no `KoinTestRule` in this codebase (no `androidTest` bootstraps Koin today, so doing it here would require new infrastructure that isn't worth the cost for one ticket). This is the third distinct seam shape now in this package: (1) [`WorkspacePickerSheet`](./212.md)'s shell + `*Content` split (`ModalBottomSheet` not renderable in the IDE preview pane or `createComposeRule()`), (2) [`CreateFolderDialog`](./213.md)'s public + file-private `*Internal` seam (lets previews inject `initialValue` without widening the public API), (3) this ticket's public + `internal` `*Internal` seam (lets androidTest bypass Koin). Don't conflate them — each solves a different problem.
- **`visible: Boolean` is a hoisted prop, not internal state.** Each consumer owns its own visibility flag; this is the established `pendingPromotion`-style pattern on the screen's `UiState` (see [`DiscussionListViewModel`](../features/discussion-list-viewmodel.md) `pendingPromotion` at line 26/48/53). The host has no internal "show/hide" state. When `visible == false`, the public composable does `return` *before* any `koinInject` / `remember` / `LaunchedEffect` — no flow subscription, no Koin lookup, no coroutine scope. Mounting the host as a permanent sibling of the screen body costs zero when invisible.
- **`onPicked` is a single callback for both "recent tap" and "newly-created path."** AC #2 calls this out explicitly: the consumer cannot distinguish. For the three near-term consumers, the next action (apply the workspace to a conversation, or seed a new discussion's workspace) is the same regardless of whether the path was recent or freshly created. This is intentional — splitting the callback would force every consumer to either route both arms to the same handler (boilerplate) or invent a meaningless distinction.
- **`onDismiss` fires only on sheet-level dismiss, never on dialog-level dismiss.** The wiring: outer `WorkspacePickerSheet(onDismiss = onDismiss)` passes through directly; the dialog's `onDismiss = { showCreateDialog = false }` flips only the dialog flag, leaving the sheet visible. This is the "two flag-flips that share the surface verb 'dismiss' route differently" contract — captured as the load-bearing test `cancelling_create_dialog_keeps_sheet_visible_and_does_not_invoke_host_onDismiss`.
- **Single `Composable`-tree body in the seam, two children:**
  ```kotlin
  WorkspacePickerSheet(
      recent = recents,
      onPick = onPicked,
      onCreateNew = { showCreateDialog = true },
      onDismiss = onDismiss,
      modifier = modifier,
  )
  if (showCreateDialog) {
      CreateFolderDialog(
          onCreate = { name ->
              showCreateDialog = false
              scope.launch {
                  val path = repository.createWorkspaceFolder(name)
                  onPicked(path)
              }
          },
          onDismiss = { showCreateDialog = false },
      )
  }
  ```
  Source order is sheet first, dialog second. M3 `AlertDialog` and `ModalBottomSheet` each manage their own `Popup` / `Window`, so source order does not affect Z-order — the dialog's window is always above the sheet's window. The order is chosen for readability.
- **Three pieces of state in the seam:** `val recents by repository.recentWorkspaces().collectAsStateWithLifecycle(initialValue = emptyList())`, `var showCreateDialog by rememberSaveable { mutableStateOf(false) }`, `val scope = rememberCoroutineScope()`. Nothing else — no `LaunchedEffect`, no `DisposableEffect`, no `produceState`. `rememberSaveable` for `showCreateDialog` survives rotation within a single host instance; when `visible` flips false → true the host is re-mounted so the saveable state is fresh (dialog starts closed).
- **Single-invocation guarantee for `createWorkspaceFolder` is structural, not stochastic.** `showCreateDialog = false` flips synchronously *before* `scope.launch { … }`. The dialog leaves composition; a second `onCreate` invocation from the same dialog instance is impossible because the button is no longer mounted. AC #2 demands "exactly once per submit"; the test asserts `picked.size == 1` after a single Create tap, but the architectural guarantee is the synchronous flag-flip — recomposition cannot retrigger a click that already unmounted its surface.
- **`scope.launch` (not `LaunchedEffect`) for the on-submit write.** The submit fires from inside a lambda passed to `CreateFolderDialog`'s `onCreate`; `LaunchedEffect` would need a keyed restart trigger, and `rememberCoroutineScope` is the canonical Compose shape for "run a coroutine when a callback fires." The scope is tied to the host's composition — if the consumer flips `visible = false` while the coroutine is in flight, the host leaves composition and the scope cancels the job. Documented in the feature doc; in Phase 0 this path is unreachable because [`FakeConversationRepository`](../features/conversation-repository.md)'s `createWorkspaceFolder` is non-suspending in practice (a `MutableStateFlow.update` then return). Phase 4 will revisit if at-least-once semantics for the write become a requirement.
- **No `Dispatchers.IO` switch.** `createWorkspaceFolder` is `suspend` but Phase 0's implementation is non-blocking; staying on `Dispatchers.Main` (Compose default for `rememberCoroutineScope`) is correct. Phase 4 implementations should switch dispatchers at the repository boundary, not here.
- **Three Compose UI tests under `androidTest/`** (not `test/`), all targeting the `WorkspacePickerInternal` seam:

  - `cancelling_create_dialog_keeps_sheet_visible_and_does_not_invoke_host_onDismiss` — tap "Create new folder under pyry-workspace…", tap Cancel. Asserts `dismissed == 0` (host's outer `onDismiss` NOT invoked), the sheet's `"Choose workspace"` title still `assertIsDisplayed`, the dialog's `"Create workspace"` title `assertDoesNotExist`. The load-bearing test for AC #4 — distinguishes "dialog dismissed" from "host dismissed," two flag-flips that share the surface verb but route differently.
  - `tapping_a_recent_row_invokes_onPicked_with_that_rows_path` — tap a known seeded recent path (`"~/Workspace/pyrycode-mobile"`, present in `FakeConversationRepository`'s default seed via the `Discussion 3` conversation), assert `picked == listOf("~/Workspace/pyrycode-mobile")`. ## Patterns established

- **`public` (no `internal`) is the right visibility for a stateful host composable that consumer screens in sibling packages call directly.** Different from the stateless children ([`WorkspacePickerSheet`](./212.md) / [`CreateFolderDialog`](./213.md) / `ConversationRow` / `ConnectionBanner` / `ToolCallRow` etc.), which are all `internal` because nothing outside the package calls them directly — consumer screens go through the host. **Rule:** if a composable is the package's external entry point (consumer screens in sibling packages call it), default to `public`. If it's only consumed within the package (a row, a bubble, a sheet body), default to `internal`. The shift from `internal` to `public` is a deliberate signal that the symbol is part of the cross-package contract.
- **Public wrapper + `internal` (not `private`) testing-seam split is the canonical shape for stateful hosts that need to bypass Koin in androidTest.** The public composable does `koinInject<T>()` and delegates to the seam; the seam takes the dependency as a parameter. **The seam is `internal`, not `private`**, because the test source set needs the symbol — `private` would hide it from `androidTest/`. **Rule:** stateful hosts that consume a Koin-injected dependency expose a `<HostName>Internal(dep, ...)` seam at `internal` visibility. The public composable is the one-line gate / Koin lookup; the seam holds the body. Consumer code MUST call the public composable; the seam is for tests only.
- **Three distinct seam shapes now exist in `ui/conversations/components/`** — don't conflate:
  1. **Shell + `*Content` split** ([`WorkspacePickerSheet`](./212.md)). The outer is `ModalBottomSheet`, structurally untestable from `createComposeRule()` and unrenderable in the IDE preview pane. Both halves are `internal`. The body is what tests and previews target.
  2. **Public + file-private `*Internal` seam** ([`CreateFolderDialog`](./213.md)). The seam exists purely so previews can inject `initialValue` (an extra parameter) without widening the public API. Tests target the public composable (the seam stays `private`).
  3. **Public + `internal` `*Internal` seam** (this ticket). The seam exists so androidTest can pass a real `FakeConversationRepository` without bootstrapping Koin. Tests target the seam (the public composable does the Koin lookup that the test wants to avoid).
  **Rule for future stateful hosts:** if you need a testing seam and the test source set must reach it, use shape #3. If you need a preview seam and tests target the public API, use shape #2. If the outer is a `Popup` / `Window` / `Dialog` / `BottomSheet` that doesn't render in `createComposeRule()`, use shape #1.
- **`if (!visible) return` lives in the public composable, NOT in the seam.** The seam is always-visible. The visibility flag is trivially-correct conditional rendering and doesn't need its own test — and the early return must happen *before* `koinInject` so consumers can mount the host permanently at zero cost when invisible. **Rule:** hoisted `visible: Boolean` props gate the composable at the topmost level; the body composable assumes it's visible.
- **`hoisted visible: Boolean` is the canonical visibility contract for stateful hosts that mount conditional UI** (dialogs, sheets, snackbars). The consumer owns the flag on its `UiState` (typically via a `combine` arm in the ViewModel — see `DiscussionListViewModel.pendingPromotion` and the `SaveAsChannelDialog` visibility from [#142](https://github.com/pyrycode/pyrycode-mobile/issues/142)). The host has no internal "show" state. **Rule:** never embed sheet / dialog visibility inside the host as `var showSheet by rememberSaveable { … }` — hoist it. The consumer needs to drive the visibility from its own state machine (e.g. to coordinate with other dialogs, to react to navigation events, to reflect ViewModel decisions). Internal "show" state would force the consumer to invent a separate trigger contract and lose the established `UiState` pattern.
- **`rememberSaveable` for transient dialog-within-host visibility** (not `rememberCoroutineScope`-launched effect, not consumer-state). The host's `showCreateDialog: Boolean` is internal because the consumer never needs to know whether the create-folder dialog is open — only the picker host coordinates that. `rememberSaveable` survives rotation; when `visible` flips false → true the host is re-mounted so the saveable state is fresh. **Rule:** state that is purely a coordination detail of the host (which child surface is currently mounted) is `rememberSaveable` inside the host. State that any consumer might need to read or override is hoisted to the consumer.
- **`scope.launch` from `rememberCoroutineScope()` (not `LaunchedEffect`) is the right shape for "run a coroutine when a callback fires."** `LaunchedEffect` is for "run a coroutine when a key changes" — would need a synthetic restart trigger here, which is more machinery than `rememberCoroutineScope` for the same behaviour. **Rule:** if the coroutine starts in response to an event (button tap, navigation result, gesture completion), use `rememberCoroutineScope` + `scope.launch`. If it starts in response to a state change (a new value flowing in, a key changing), use `LaunchedEffect(key) { … }`.
- **`collectAsStateWithLifecycle(initialValue = emptyList())` is the project's established Flow → Compose-state shape.** Same call shape as `MainActivity.kt`. **Rule:** never use `.collectAsState()` (lifecycle-unaware — keeps collecting in `STARTED` state across `STOPPED` transitions); always use `.collectAsStateWithLifecycle(initialValue)` with an explicit `initialValue` so the first-composition render path is deterministic.
- **End-to-end Compose UI tests use real `FakeConversationRepository()`, not anonymous `object : ConversationRepository { … }` stubs.** The first test re-asserts the repo state via `runBlocking { repo.recentWorkspaces().first().first() }` after the host's `createWorkspaceFolder` invocation — that's the load-bearing wiring assertion, and it only works if the test uses the real fake. **Rule:** Compose UI tests that exercise host ↔ repo wiring use the production-grade `FakeConversationRepository`; reserve hand-rolled `object` stubs for ViewModel unit tests that want to inject specific failure modes (which the fake doesn't expose).

## Lessons learned

- **`koinInject<T>()` must be called inside a composable scope — calling it conditionally after `if (!visible) return` requires the return to be a true early-exit, not a `null`-return inside a deeper scope.** The public `WorkspacePicker` does `if (!visible) return` as the *first statement* in the composable body. Calling `koinInject` before the visibility check would (a) waste a Koin lookup when invisible and (b) defeat the "zero cost when invisible" contract. Putting the `koinInject` inside the seam would mean tests would need to bootstrap Koin (the seam takes the repo as a parameter precisely because we don't want that). **Lesson:** visibility gates that wrap a Koin-resolved dependency belong at the topmost level of the public composable; the dependency lookup is the first thing inside the gate, not before it.
- **`rememberCoroutineScope` cancels on composition exit, which is the right behaviour for consumer-driven dismiss mid-write but NOT for at-least-once semantics.** When the consumer flips `visible = false` mid-write, the host leaves composition, the scope cancels, the in-flight `createWorkspaceFolder` job is cancelled, and `onPicked` is NOT called. In Phase 0 this is unreachable (the fake is synchronous); in Phase 4, this could become a problem if the write reaches the server but the response never reaches the host. **Lesson:** the choice of scope encodes a contract. `rememberCoroutineScope`'s "cancel on composition exit" is the right default for UI-bound writes that have no side effects beyond the response. If a future Phase 4 ticket needs at-least-once write semantics (the server-side state must converge regardless of the UI's fate), the scope choice changes to `applicationScope` (Koin-injected) or to a dedicated `WorkspaceRepository` job — this is documented in the host's feature doc but not implemented today, deferred until a real consumer demands it.
- **The seam's `internal` visibility crosses source-set boundaries within the same module — that's the load-bearing property.** `androidTest/` is its own source set but compiles against the module; `internal` (module-wide visibility) covers it. `private` would scope to the file. **Lesson:** the smallest visibility step that satisfies "reachable from `androidTest/` but invisible outside the module" is `internal`. Don't escalate to `public` for cross-source-set use within the same module — it leaks the seam to other modules (none exist today, but [#206](https://github.com/pyrycode/pyrycode-mobile/issues/206)'s eventual modularization triggers would change that). Don't drop to `private` either — the test can't reach it.
- **`composeTestRule.waitForIdle()` after the Create tap is a forward-compatibility defence, not strictly required today.** The fake's `createWorkspaceFolder` completes synchronously (a `MutableStateFlow.update` then return), so the `onPicked(path)` callback fires before `waitForIdle()` returns. If a future implementation of `createWorkspaceFolder` becomes genuinely `suspend`-blocking (real network call, real disk write), the test without `waitForIdle()` would race the assertion. **Lesson:** include `waitForIdle()` after any UI action that triggers a `suspend` call, even when the current fake doesn't suspend — the test is a regression artifact for the future implementation, not just the current one. Costs nothing when the implementation is synchronous.
- **The `runBlocking { repo.recentWorkspaces().first().first() }` end-to-end re-assertion in the first test is what catches "host called `onPicked` with the right path but did NOT call `createWorkspaceFolder`."** Without it, a buggy host could call `onPicked(name)` directly without ever invoking the repo, and the immediate-callback assertion would still pass. The re-assertion against the repo's recents flow validates that the write actually landed. **Lesson:** end-to-end wiring tests need at least one assertion that observes the side effect on the dependency, not just the callback shape. The path string in `onPicked` is a function of the repo's behaviour (`"pyry-workspace/$name"`), so asserting it transitively validates the call — but the second assertion makes the validation explicit.
- **The default-seeded `FakeConversationRepository` already has `"~/Workspace/pyrycode-mobile"` in `recents`** — used by the third test as the click target. The fake seeds three conversations with workspace cwds (`"~/Workspace/personal"`, `"~/Workspace/pyrycode-mobile"`, `"~/Workspace/joi-pilates"`); each cwd-affecting write bumps the recents list. **Lesson:** the test's "click a known recent" target is a function of the fake's seed; the seeded paths are stable today but if a future ticket reshapes the seed (e.g. localises paths to non-Latin-script projects), the test's click target string needs to update. The test was deliberately written against a stable seed entry (`"~/Workspace/pyrycode-mobile"`, the project's own canonical path) to maximise stability — but anchoring on seed data is a coupling worth flagging.
- **`Modifier` is forwarded to the sheet, not duplicated on the dialog.** The host's `modifier` parameter is passed only to `WorkspacePickerSheet(modifier = modifier)`; the conditional `CreateFolderDialog` gets `Modifier` (default). This is intentional — the modifier is meant to attach test tags / semantics to the picker surface, which is the always-mounted surface. The dialog is a transient overlay; attaching the same modifier to both would double-tag the test tree. **Lesson:** when forwarding a `modifier` from a host to two sibling children, route it to the structurally primary surface (the one that's always present when the host is visible), not to the conditional overlay.
