# #474 — Layer 1b: connection banner (connecting / reconnecting / offline) on the scripted-stream harness

Adds the **component-level** connection-banner coverage of the mobile interactive-stream e2e ladder
(`docs/e2e-interactive-stream.md`, **rung 2 / Layer 1b**): a scripted `ConnectionState` sequence driven
through the **real `ThreadViewModel.connectionState`** (`ConnectionStateSource.observe()` → `stateIn`, #307)
→ `ThreadScreen` → `ConnectionBanner` (#200/#201), asserting the shipped banner affordances render for
**connecting**, **reconnecting (with countdown)**, and **offline**, and are **absent when connected**. It
rides the already-shipped **#432 `ScriptedThreadHarness`**; the only change is **one scripting method + one
lifted field** in the harness, plus one new test file — all `androidTest`. **Zero production Kotlin.**

The banner reacts to its **own** connection seam, disjoint from the `FakeSessionPump` envelope stream that
drives the #432 deltas / #472 tool rows — so the harness extension here is on the connection-state source, not
the pump. Confirming that disjointness is exactly the regression class this rung guards. Last of the three
children #435 was split into 2026-06-23: #472 (tool rows, **shipped**), #473 (session divider, `blockedBy` the
unshipped #336 fold), and **#474 (this — connection banner, was `blockedBy` #472)**.

The faithful production path the test reproduces (disjoint from the pump):

```
test.pushConnectionState(state)
  → FakeConnectionStateSource.emit   (retained MutableStateFlow)
  → ThreadViewModel.connectionState  (observe().stateIn(WhileSubscribed), #307)
  → ThreadScreen(connectionState = …) → ConnectionBanner → rendered banner text (or nothing when Connected)
```

## Patterns established

- **Glyph-safe ASCII substrings — assert before/after the non-ASCII glyph, never on it.** `ConnectionBanner`
  uses inline literals with non-ASCII glyphs: `"Connecting…"` (U+2026 ellipsis) and `"Offline — tap to retry"`
  (U+2014 em-dash). Each assertion keys on an **ASCII-only substring that sits before (or after) the glyph** —
  `"Connecting"`, `"Reconnecting in 12s"`, `"tap to retry"` — so the match never depends on faithfully
  reproducing the glyph in the test source. Same class as #431's `ping`/`seed` substring lesson: assert on
  unambiguous, faithfully-typeable text. Within a single-state test only one banner is on screen, so the
  capital-`C` `"Connecting"` substring cannot collide with `Reconnecting`'s lowercase `connecting` — no
  case-sensitivity reasoning is load-bearing.
- **Asserting the full `"Reconnecting in 12s"` literal — value-surfacing, not just state-surfacing.** AC #2
  requires the *countdown value* be shown, not merely the reconnecting state. So the assertion keys on the
  whole `"Reconnecting in ${n}s"` literal (with `n = 12`), not just `"Reconnecting"` — coupling the test to
  the pushed `secondsRemaining` on purpose. (Code review flagged this coupling as a NIT and confirmed it is
  exactly what the AC wants; keep the pushed `12` and asserted `12s` in lockstep if either is touched.)
- **Present→absent fence for an absence AC.** AC #4 (banner absent when connected) is asserted as a transition
  — render `Connecting`, *then* push `Connected` and wait for the banner to vanish — not as absence from the
  default `Connected` state (which would be a trivially-absent false-green, the banner having never been
  shown). This is the spinner test's shape (`ScriptedThreadRenderTest`: `pushTurnState("thinking")` present →
  `pushTurnEnd` absent) and #472's done-row fence, applied to the connection seam.
- **New test file, not extending `ScriptedThreadRenderTest`.** A dedicated `ScriptedConnectionBannerTest.kt`
  keeps the banner scenarios cohesive and **decouples this ticket's diff from sibling #473** (divider), which
  rides the same harness next and would otherwise collide in a shared test file. The harness file is the one
  unavoidable shared edit point; the per-ticket test files keep merge surface minimal. (Same call as #472's
  `ScriptedToolRowTest.kt`; the spec's open question 2 left a single walk-through acceptable, but the
  per-state files isolate failures and read more cleanly.)
- **Four isolated `@Test`s over one walk-through.** Each `@Test` gets a fresh `@Before` harness, so the
  `Connected` default is a clean start and there is no cross-test bleed or conflation risk; the AC #4 fence
  still exercises live `Connecting → Connected` recomposition. (Architect open question 2; the choice was
  flagged in the PR body.)

## Lessons learned

- **The connection banner is robust to the subscribe-before-push race that bit the #432 spinner.** Unlike
  `turn_state`/`isThinking` (which flow through the `replay = 0` `liveSessionEvents` SharedFlow and are
  *dropped* if pushed before the VM subscribes — the #432 spinner flake), `connectionState` flows through
  `FakeConnectionStateSource.observe()` — a retained `MutableStateFlow` — into
  `stateIn(WhileSubscribed(5000), initialValue = Connected)`. A value `emit`-ted before the VM's collector
  subscribes is **retained and re-emitted** on subscribe (StateFlow semantics), exactly like #472's
  `messagesByConversation` projection. **No new readiness gate needed.** All `pushConnectionState` calls still
  go **after** `start()` (which runs `awaitReady()`) — `awaitReady` proves the screen composed and is
  collecting `connectionState`, so the thread is rendering (not loading/empty) before the first banner
  assertion. See [[two-folds-repo-wins-vm-dormant]].
- **StateFlow conflation: never push two states back-to-back without a `waitUntil` between them.** Each
  `@Test` here drives exactly one transition before asserting (and the AC #4 fence waits for `"Connecting"` to
  render before pushing `Connected`), so conflation is a non-issue. But a `MutableStateFlow` conflates — two
  pushes with no `waitUntil` in between can skip the intermediate value, so a future walk-through test must
  gate every push on a `waitUntil`.
- **No causal-fence machinery — push sequencing is the fence.** Because the harness pushes states imperatively
  from the test thread, the present→absent fence is just sequencing (push → `waitUntil` present → push →
  `waitUntil` absent), with no two-drop dance like the emulator rungs need. (Same simplification #472 noted
  for the running→done transient.)

## Verification

The deliverable **is** the tests; there is no unit test of the harness. Host-JVM checks (no device, per the
spec's strategy):

- `./gradlew compileDebugAndroidTestKotlin spotlessCheck test lint assembleDebug` all green — the androidTest
  sources compile (the mandatory gates do **not** compile androidTest, so the `compileDebugAndroidTestKotlin`
  run is explicit — [[androidtest-not-compiled-by-mandatory-gates]]). `onNodeWithText` / `onAllNodesWithText` /
  `assertIsDisplayed` are imported; `assertDoesNotExist` is a member fn (no codebase-wide import — confirmed in
  review); the new `.kt` filename matches its sole public class.
- **`connectedAndroidTest` NOT run** — no device/emulator attached; all four `@Test`s are instrumented
  `createComposeRule` (the `ScriptedThreadRenderTest` / `ScriptedToolRowTest` precedent), so the on-device
  render run is operator-run, alongside the sibling harness tests.
