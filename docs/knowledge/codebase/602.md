**Issue:** [#602](https://github.com/pyrycode/pyrycode-mobile/issues/602) ·
**Spec:** [`docs/specs/architecture/602-thread-status-row-drop-usage-segment.md`](../../specs/architecture/602-thread-status-row-drop-usage-segment.md) ·
**PR:** [#610](https://github.com/pyrycode/pyrycode-mobile/pull/610) (`177b49f`) ·
**Feature doc:** [Thread status row](../features/thread-status-row.md) ·
Split from #584 (chain: #601 → #602 → #603, middle child). #601 (StatusSheet, merged `17432ae`) landed
first; #603 (delete `ThreadUiState.tokenPercent`) is blocked by this ticket. Sibling #591 (serve a real
figure — blocked on daemon-side pyrycode PR #1215). Size **S**. Client-only — no wire call, no DTO, no
repository method, `ThreadViewModel` untouched. Code review **PASS** (2 NITs, neither blocking).

## Summary

`ThreadStatusRow` rendered `"Opus 4.7 · high · 73% used"`, colour-coding the last segment by severity
via a private `tokenPercentColor` helper — but the percentage was `ThreadViewModel.STUB_TOKEN_PERCENT`,
a constant nobody measured, so the severity colour was constant by construction. This ticket deletes the
segment rather than rewording it (contrast [#601](601.md), which reworded the sibling StatusSheet stub
to `"Context usage unavailable"`): a compact monospace status line has no room for an explanation, and
the sheet — one tap away, already honest as of #601 — is where that explanation belongs. The row now
renders exactly `"Opus 4.7 · high"`, with no percentage and no severity-derived colour anywhere in the
row.

The structural fact that let this ship standalone: `ThreadUiState` keeps `tokenPercent` and
`ThreadViewModel` keeps populating it from the stub constant — the row simply stopped *reading* it.
Nothing upstream changed, so nothing upstream needed re-testing. #603 deletes the field.

## Load-bearing design choices

- **Delete the segment rather than reword it**, diverging deliberately from the #601 pattern next door.
  A compact monospace summary line has no room for a second thing to explain; the Status sheet already
  carries the honest wording one tap away. Deleting is also what makes "no severity-derived colour
  anywhere in the row" fall out for free instead of needing a separate rule — severity lived only on the
  deleted span.
- **The surviving two-tone `onSurface` / `onSurfaceVariant` split is not flattened to one colour.** That
  split is Figma `16:58`'s static treatment (model bright, separator/effort dimmed), not severity
  colouring — flattening it would have been an unrequested visual change to a part of the row the ticket
  says stays as designed.
- **`ThreadUiState.tokenPercent` stays for now.** Deleting it here would pull `ThreadViewModel`,
  `ThreadViewModelTest`, and the five `ThreadScreen.kt` preview literals into scope, breaking the
  #601→#602→#603 split boundary. Kotlin doesn't warn on an unread `data class` property, so the unread
  field produces no lint noise in the interim; #603 removes it.

## Patterns established

Nothing new at the architecture level — this is the same defaulted/required-parameter-removal shape
#601 used on the sheet, applied to a required (non-defaulted) parameter instead: removing a **required**
param breaks every call site, so all 9 (1 production + 8 previews) were counted and edited, versus #601
where most preview/test call sites needed zero edits because they never passed the defaulted param
explicitly. Confirms the same trap generalises: **a signature-narrowing ticket must delete duplicate
previews, not mechanically strip the argument from all of them** — #601 hit it on 4 context previews,
this ticket on 8 percent-value previews.

## Lessons learned

- **A signature-narrowing ticket gets its RED for free from the compiler.** The new
  `ThreadStatusRowTest` called `ThreadStatusRow` with the parameter already gone, so
  `compileDebugAndroidTestKotlin` failed on all four call sites before the production edit landed —
  cheaper and more honest than a runtime assertion that could never have gone red on its own.
- **`onNodeWithText` defaults to `substring = false`, and that default is exactly the assertion the AC
  needs.** `"Opus 4.7 · high · "` (the dangling-separator bug) is simply not equal to
  `"Opus 4.7 · high"` — the exact match *is* the regression guard. Passing `substring = true` for
  convenience would have silently accepted the bug the ticket calls out by name.
