# #565 — Wire `recent_workspaces` to the daemon's v2 wire message

**Issue:** [#565](https://github.com/pyrycode/pyrycode-mobile/issues/565) · split from #535 (recents half; create half is #564) ·
**Spec:** `docs/specs/architecture/565-recent-workspaces-wire.md` ·
**PR:** merged directly to `main` at `ef64278` (spec `fc4c751`) ·
**Feature docs:** [Remote conversation repository](../features/remote-conversation-repository.md)
§ `recentWorkspaces` (new), § Stubs (updated), [Workspace picker](../features/workspace-picker.md)
§ Error handling / § Downstream-open (updated) ·
Size **S**, `security-sensitive` (PASS).

## Summary

Overrides `RemoteConversationRepository.recentWorkspaces()` — previously the interface's
`flowOf(emptyList())` default — with a live one-shot round-trip against the daemon's v2
`recent_workspaces` request / `recent_workspaces_list` reply (server pyrycode#888, the recents half
of the split #825), so the Workspace Picker's "Recent" section now populates instead of always
rendering empty. Each collection sends a fresh empty-`{}` `recent_workspaces` request, awaits the
correlated reply via `sendAndAwaitReply`, decodes it through the new `RecentWorkspacesListPayloadDto`,
maps to paths in **wire order** (no client re-sort — ordering/dedup are daemon-authoritative), filters
the two "no bound workspace" sentinels (`""` and `DEFAULT_SCRATCH_CWD`), and emits once. A single
`.catch { emit(emptyList()) }` fails every non-cancellation throwable closed to an empty list — not
connected, server error, or malformed reply all degrade silently rather than crashing or hanging the
collector. Registers the new `recent_workspaces_list` reply type in the inbound demux success-arm (the
load-bearing edit — a missed registration hangs the pending deferred, the same delete/create-family
hazard #532/#564 already hit). No UI change: `WorkspacePicker.kt` already collected and rendered
`recentWorkspaces()` (from its original interface-default stub) — this ticket is entirely data-layer.

This is the **leanest** read verb in the family — no projection fold (unlike `observeConversations`,
nothing is stored; each collection is independent), and a genuinely new reply type reused by no other
verb.

## Patterns established

The **guarded cold one-shot read-verb** shape for a verb with no push projection: `flow { send →
sendAndAwaitReply → decode → transform → emit }.catch { emit(fallback) }`. This differs from
`observeConversations`'s cold-flow-over-a-`StateFlow`-projection shape (that one `emitAll`s a shared
projection fed by the always-running inbound collector) and from every mutation's
suspend-fun-that-throws shape (mutations propagate failure to the caller; this flow instead degrades to
an empty success value, because the AC explicitly wants "no crash, no error UI, just an empty section").
Future one-shot reads with no server-side push feed and a "degrade silently" contract should reach for
this shape rather than either of the other two. `Flow.catch`'s cancellation-transparency (it does not
swallow `CancellationException`) is the mechanism that makes this safe for a Compose
`collectAsStateWithLifecycle` collector that gets cancelled on lifecycle STOP — confirmed in the family
for the first time here.

## Lessons learned

- **A verb with a brand-new reply type always needs the demux registration — repeats the #532/#564
  pattern for a fifth time.** Grepping the `onInbound` success-arm `when` list before assuming a
  request/reply spine is complete remains the right first move whenever a mutation or read's reply is
  not a reuse of an already-routed type.
- **A cold flow with no projection is strictly simpler to reason about than the mutation family**: no
  concurrent-write ordering, no upsert-vs-clobber question, no `StateFlow` conflation subtlety — the
  entire correctness surface is "decode the one reply correctly and filter the two sentinels." The spec
  and implementation both stayed close to the `list_conversations` template with the fold step simply
  omitted.
