# Ticket #407 — thinking indicator at the foot of the message list

**Issue:** [#407](https://github.com/pyrycode/pyrycode-mobile/issues/407) ·
**Spec:** [`docs/specs/architecture/407-thinking-indicator-thread-foot.md`](../../specs/architecture/407-thinking-indicator-thread-foot.md) ·
**PR:** [#410](https://github.com/pyrycode/pyrycode-mobile/pull/410) ·
**Feature doc:** [Thinking indicator](../features/thinking-indicator.md) ·
Split from #386, blocked by (and built on) the merged sibling [#406](406.md). Size **S**, not
`security-sensitive` (UI-only; `data/` untouched).

## Summary

The **UI half of the thinking indicator**. #406 reduced the live `turn_state` stream to a sibling
[`ThreadViewModel.isThinking: StateFlow<Boolean>`](../features/turn-state-thinking-flag.md); this slice
renders it. A new stateless [`ThinkingIndicator`](../features/thinking-indicator.md) composable — a
small indeterminate M3 `CircularProgressIndicator` + "Thinking…" label — is placed as the **final child
of the thread content `Column`, outside the empty/populated `if/else`**, so it surfaces at the
bottom/most-recent edge of the list in both the populated and the empty-thread case (AC #2: thinking
precedes the first assistant text). It is driven solely by the hoisted flag (`if (!isThinking) return`),
holds no local state, and ships light + dark previews. The flag is threaded through the stateless
`ThreadScreen` as a **defaulted** hoisted boolean (sibling to `connectionState`, **not** a
`ThreadUiState` field) and collected at the `MainActivity` call site. Code review **PASS**, zero
blocking findings.

## Load-bearing design choices

- **Placement outside the `if/else`, gated only on the flag.** The indicator is the final child of the
  content `Column`, after both the `EmptyThreadState` (empty branch) and the `LazyColumn` (populated
  branch) — each of which takes `weight(1f)`. It is wrap-height and sits directly below the weighted
  region, above the Scaffold `bottomBar` (status row + input). Because it is outside the branch and not
  gated on `hasMessages`, one placement surfaces it identically in the empty and populated cases (AC #2)
  with no duplication, and `reverseLayout = true` makes the bottom edge the visual "foot" / most-recent
  edge directly beneath the latest message.
- **Hoisted boolean, sibling to `connectionState`, not a `ThreadUiState` field.** Mirrors the #406
  data-side decision: a transient connection-scoped signal stays a separate `ThreadScreen` parameter
  beside `state`, collected with its own `collectAsStateWithLifecycle()`. Defaulting it (`= false`)
  keeps the 4 in-file previews + the 2 androidTest call sites + every other caller compiling untouched —
  only the live `MainActivity` caller sets it. `false` is the correct inert default (not thinking).
- **Early-return, not `AnimatedVisibility`.** `if (!isThinking) return` matches `ConnectionBanner`'s
  show/hide idiom exactly — the composable is a pure function of the boolean, emitting nothing when
  false (AC #1/#4 "holds no local state"). No animation is in scope; a fade-in is a design-owed nicety
  deferred to the Figma frame.
- **Merged `semantics` for the content description.** `.semantics(mergeDescendants = true) {
  contentDescription = … }` on the row makes TalkBack announce the indicator once ("Agent is thinking")
  as a single node, subsuming the decorative spinner + the visible "Thinking…" label.

## Patterns established

Nothing genuinely new — this slice **follows** established precedents rather than setting them: the
`ConnectionBanner` early-return show/hide idiom, the `EmptyThreadState` light/dark preview template, the
`cd_*` content-description string convention, the file-private spacing-`val` posture, and the
sibling-flat-parameter shape `connectionState`/#406 `isThinking` already use. The one mildly novel point
worth noting for future foot-of-list affordances: **place a flag-gated, wrap-height indicator as the
final child of the content `Column`, outside the empty/populated `if/else`**, so it surfaces in both
cases from a single call site without a `hasMessages` gate.

## Lessons learned

- **ktlint 1.5.0 wants `.semantics{…}` chained onto the closing `)` of the preceding multi-line builder
  call, not wrapped onto its own line.** When attaching `.semantics { contentDescription = … }` after a
  multi-line `.padding(…)`, ktlint requires the chained call to start on the same line as the prior
  call's closing paren (`.padding(…).semantics { … }`); putting `.semantics` on a fresh line fails the
  check. `spotlessApply` **flags but does not auto-fix** this — it has to be hand-formatted. (Lifted
  from the PR's "Lessons learned"; see [[ktlint-filename-rule-single-class]] for the related
  single-public-class filename rule this file also satisfies — `ThinkingIndicator.kt` → `ThinkingIndicator`.)
