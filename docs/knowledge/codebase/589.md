# #589 — Cover the dialog auto-focus contract

## Summary

Four of seven `InteractiveStreamE2ETest` LIVE scenarios stalled on the same 30 s wait: after opening
`RenameDialog`, `CreateFolderDialog`, or `SaveAsChannelDialog` over the thread, the wait for
`hasSetTextAction() and isFocused()` never satisfied. Nothing in the tree asserted the dialogs'
auto-focus contract at component level, so this ticket added one instrumented test per dialog
reproducing that exact predicate — and the measurement came back **red** on all three, isolated to
component level with zero relay/daemon/claude-turn cost. All three dialogs drove
`focusRequester.requestFocus()` from a `LaunchedEffect(Unit)` in the *parent* composition, before the
`AlertDialog(...)` call; the field composes in the dialog window's own sub-composition, so the request
returned cleanly (no `IllegalStateException`) but focus never landed. The fix moves each effect inside
the `text` slot, beside the field it targets — one shape applied three times, matching the architect
spec's Branch B remedy verbatim.

## Patterns established

- **A `LaunchedEffect` driving a `FocusRequester` must be declared in the same sub-composition as the
  `.focusRequester(...)` modifier it targets.** `AlertDialog` slots (`title`, `text`, `confirmButton`,
  `dismissButton`) compose in the dialog window's own sub-composition, separate from the caller. An
  effect placed in the parent composition — even one that runs and returns without throwing — is not
  guaranteed to see the field's requester node as attached. Apply this to any future `AlertDialog` or
  `ModalBottomSheet` with an auto-focus requirement; the bug is silent (no exception, no lint, no compile
  error), so it will not surface on its own.
- **Reproduce the live wait predicate verbatim in a component test, not a paraphrase.** A component
  assertion phrased as "does the field have text X and report focus" measures a related but different
  property than what the live scenario's selector actually depends on. Copying the exact
  `hasSetTextAction() and isFocused()` expression (plus the uniqueness-asserting follow-up `onNode(...)`)
  is what let this ticket produce a verdict #615 could act on.
- **Bound a focus-settling wait short (2 s here), not at the live timeout's length.** A broken contract
  then fails fast per test, and the bound stays informative: the live wait already allowed 30 s and still
  timed out, so anything the component test can't satisfy within a couple of frames is a distinct finding,
  not absorbed latency.

## Lessons learned

(Lifted from the PR #617 description's own "Lessons learned" section.)

- **A `LaunchedEffect` targeting a `FocusRequester` must live in the same composition as the
  `.focusRequester()` modifier it drives.** `AlertDialog` hosts its slots in a separate dialog window
  sub-composition, so an effect in the parent runs against a requester that is attached enough not to
  throw but not yet focusable. The failure is silent in both directions: no exception, no lint, no
  compile error — just a field that never focuses. Worth checking `ModalBottomSheet` slots for the same
  shape if one grows an auto-focus requirement.
- **`FocusRequester.requestFocus()` returning without throwing does not mean focus landed.** The absence
  of `IllegalStateException: FocusRequester is not initialized` is a real diagnostic signal, not a null
  result — it discriminates "ran too early" (throws) from "ran fine, focus went nowhere" (silent), and the
  two have different fixes. This ticket's spec pre-wrote both diagnostic branches; the observed failure
  text picked the second one before any fix was attempted.
- **A component test that isolates the suspect is cheaper than re-running the stack that surfaced it.**
  Three dialogs, one device run, ~1 minute, zero claude turns — against a 30-second-per-scenario LIVE
  suite that had already burned two full runs without localising the defect. Measured: 3 tests red
  pre-fix → 29/29 green post-fix (3 new + 26 pre-existing in the same classes, as a free regression) on
  the connected API-35 `Pixel_8`.
