# #233 — feat(ui/settings): Default-effort picker dialog + wire row

Wires the previously inert "Default effort" row in `SettingsScreen` to a Material 3 single-choice `AlertDialog` backed by `AppPreferences.defaultEffort` (the schema delivered by #231). Mechanical copy of the [#87](./87.md) `ThemePickerDialog` precedent — same dialog shape, same `(StateFlow<X>, fun onSelectX)` VM-pair shape, same fire-and-forget setter forward. Second consumer of the four-key defaults schema added in #231; the first sibling consumer (model picker, #232) and the third (workspace picker) are independent slices. This slice does **not** touch the StatusSheet effort override (#229) — that consumer's stub can be removed once its host ticket lands.

## Summary

- **New `EffortPickerDialog.kt`** in `ui/settings/` (`internal` composable, sibling to `ThemePickerDialog.kt`). M3 `AlertDialog` (`title = stringResource(R.string.settings_effort_dialog_title)`) over a `Column(Modifier.selectableGroup())` of five `Row`s (one per `Effort.entries`); each row carries `Modifier.fillMaxWidth().selectable(selected, role = Role.RadioButton, onClick = { pending = effort }).padding(vertical = 8.dp)` + `RadioButton(selected, onClick = null)` (row owns the gesture) + 8.dp `Spacer` + `Text(effort.label(), style = bodyLarge)`. OK / Cancel `TextButton`s use `android.R.string.{ok,cancel}` — no app-side string ids. Pending: `var pending by remember(selected) { mutableStateOf(selected) }` — keying on `selected` resets the radio when the parent reopens the dialog after a background change. File-top-level `internal fun Effort.label(): String` extension at the bottom of the same file returns lowercase `"low"` / `"medium"` / `"high"` / `"xhigh"` / `"max"` — labels match the existing hardcoded subtitle text and the enum identifier scheme; `SettingsScreen.kt` resolves it without an import (same package). Mechanical copy of `ThemePickerDialog.kt` with `ThemeMode` → `Effort` substitutions throughout. **Placement diverges from `ThemeMode.label()` (which lives at the bottom of `SettingsScreen.kt`)** — `Effort.label()` lives in `EffortPickerDialog.kt` to keep the `SettingsScreen.kt` file from growing further; both are `internal` same-package extensions so the call-site shape is unchanged.

## Patterns established

- **`Effort.label()` lives in `EffortPickerDialog.kt`, not `SettingsScreen.kt` — sibling-file `internal` extension is the right home when a same-package file already exists.** `ThemeMode.label()` (#87) lives at the bottom of `SettingsScreen.kt` because it predated the dialog file. `Effort.label()` skips that detour — both the row-subtitle call site (`SettingsScreen.kt`) and the dialog row labels (`EffortPickerDialog.kt`) resolve it through the same-package `internal` visibility, so the file housing the extension is a cost-of-file-growth tradeoff, not a visibility constraint. **Rule:** when a feature lands a sibling dialog file at the same time as a `.label()`-shaped enum extension, put the extension in the sibling file and leave `SettingsScreen.kt` thinner; only retrofit `ThemeMode.label()` if a future slice gives it a third caller.
- **Five-variant `Effort.entries` ranges cleanly through the `selectableGroup` pattern.** `ThemePickerDialog` (#87) shipped three rows; this slice shipped five. The Compose `selectableGroup` accessibility wrapper + per-row `selectable(role = Role.RadioButton)` shape scales without any structural change — the radio set's screen-reader announcement walks all five children naturally, no `headlineContent` recomposition cost, no `LazyColumn` needed (five rows = always-visible, no recycling benefit). **Rule:** the single-choice M3 dialog shape from #87 scales to ~7 options before needing a scrollable container; the next picker that exceeds that (Phase 3+ workspace picker?) is the one that should reach for `LazyColumn` inside `text = { … }`.
- **Boundary-value round-tripping is the right coverage for enum-pref persistence tests.** The five tests cover `LOW` and `MAX` (both enum-edge values) via the `_persistsLow` / `_persistsMax` pair, plus `XHIGH` (a middle non-default) through the re-emit walk. The middle values `MEDIUM` / `HIGH` are deliberately uncovered — `Effort.HIGH` is the default and exercised by `_initialState_emitsHigh_whenNoStoredValue`, and adding `_persistsMedium` would test the same `setDefaultEffort` round-trip the boundary tests already exercise without adding any failure mode. **Rule for future enum-pref-projection VM tests:** cover (1) fresh-default initial state, (2) pre-write initial-state mirror, (3) round-trip of both enum boundaries (`.entries.first()` and `.entries.last()`), (4) one middle value through a re-emit walk. Five tests; full AC coverage; no per-variant noise.

## Lessons learned

- **The "lift to sealed `SettingsState` on the third persisted writable preference" threshold has now been crossed — and deliberately deferred for one more slice.** [`settings-viewmodel.md`](../features/settings-viewmodel.md) and [`codebase/87.md`](./87.md) both encode the rule "the next persisted Settings preference (notification sound, default model, default effort) is the trigger to lift `themeMode` into a sealed `SettingsState` with a per-field reducer". Pre-#233 the count of writable preference pairs was two (`themeMode`, `useWallpaperColors`); this slice brings it to three (`defaultEffort`), which the rule explicitly names. The architect's spec did not lift, because (a) the AC mandates the same `(StateFlow<X>, fun onSelectX)` shape verbatim and authorises the mechanical copy, (b) the sibling slice #232 (model picker) was still in flight at architect time and lifting under #233 would force #232 to either rebase onto a new envelope or land the second mechanical-copy pair and rebase later, and (c) the lift, when it happens, should restructure all three at once. **Pattern:** when a documented threshold is crossed but the in-flight siblings haven't landed yet, the lift earns its keep once the siblings are merged — not on the first slice that crosses the threshold. The next defaults consumer (the YOLO switch row or workspace picker, whichever lands first after #232 + #233) is the right re-evaluation point. Update [`settings-viewmodel.md`](../features/settings-viewmodel.md)'s "Two-key surface" edge-case note accordingly when the next slice ships.
- **`AlertDialog`'s `text = { Column(selectableGroup()) { … } }` slot grows naturally with `.entries.forEach { … }` — no need to switch to `text = { LazyColumn { items(Effort.entries) { … } } }` at five rows.** The temptation when copying #87's three-row dialog to a five-row dialog is to "future-proof" against larger picker variants by reaching for `LazyColumn`. Resist — the M3 `AlertDialog` content slot is non-scrolling by default at small row counts, the radio-row composables don't carry per-item state that benefits from recycling, and `LazyColumn` inside a sized-by-content slot would force an explicit `Modifier.heightIn(...)` calculation. Five rows render fine in the default M3 dialog dimensions on every screen size the project targets (Min SDK 33; phone form factors). **Pattern:** stay with `Column(selectableGroup())` + `.entries.forEach { … }` for any single-choice M3 dialog backing a small enum (≤ ~7 variants); only reach for `LazyColumn` when the option count is unbounded or genuinely large.
