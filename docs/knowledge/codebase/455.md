# #455 — Layer 2c: deterministic tool-step rows (running → done, and failed)

Adds two more scenarios on the **#454 deterministic emulator harness** (rung 4 / **Layer 2c** of the
mobile interactive-stream e2e ladder, `docs/e2e-interactive-stream.md`):

1. **`tool`** — a tool step renders **running** while the tool is in flight, then **done** after the
   result (the two-drop twin of the thinking spinner).
2. **`tool-failed`** — a failing tool step renders **failed** (a single terminal drop).

This is the emulator twin of **#435** (Layer 1b, the in-process component-render case that ships the
same tool-row states). The real app on a headless emulator drives the real Noise/relay path against
the scripted `fakeclaude` backend (pyrycode #642) — **no real claude, zero claude turns**, same pass
on every re-run. **No production Kotlin** — it *exercises* the already-shipped, already
security-reviewed #387 tool-use/tool-result correlation fold and #388 tool-row status UI; it does not
modify them.

## Patterns established

- **The #454 two-drop causal fence generalises to any transient tool/turn state.** "Running" is
  transient — the fold flips the row to `Done` the instant the correlated `tool_result` arrives — so
  the `tool` scenario reuses the spinner's mechanism *unchanged*: drop A (`tool-open.jsonl`, fired on
  the 1st `send_message.enqueued`) opens and **holds** the turn (a lone `tool_use`, no `end_turn`);
  the test asserts **running**, then sends a 2nd message; drop B (`tool-done.jsonl`, fired on the 2nd
  enqueue) resolves it. The running window is arbitrarily long → no timing dependency, no race. A
  **stable** terminal state (`Failed`) needs no fence — a single drop carries use → error result →
  turn end (the `tool-failed` scenario). Rule of thumb for future scenarios: **two-drop iff the state
  auto-resolves; single-drop iff it's terminal.**
- **Asserting a state that has no positive content-description: the absence-triad.** `Done`'s icon
  carries `contentDescription = null` (`ToolCallRow.kt`), so there is no CD to wait for. "Done" is
  asserted tolerantly as a triad that uniquely identifies a running → done resolution: the running CD
  that was present is now **absent**, the failed CD **does not exist**, and the tool row is still on
  screen (the **verbatim tool name** `"Bash"` is displayed — proving the row resolved *in place* and
  did not vanish). This mirrors the spinner's present → absent shape and never keys on timing. The
  deliberate alternative — adding a test tag or a positive "done" CD to the production component — was
  rejected as out-of-scope production change.
- **Cross-drop correlation is the load-bearing fixture detail.** `applyToolResult` drops a
  `tool_result` that has no prior matching `tool_use` (keyed by `tool_use_id`), so drop A's `tool_use`
  `id` **must** equal drop B's `tool_result` `tool_use_id` — same literal `toolu_e2e` in both files
  (and a distinct `toolu_e2e_fail` for the `tool-failed` scenario). Same session ⇒ the producer
  attaches the same `conversation_id`, so the only cross-drop key the fixture author controls is the
  id, and a mismatch fails loud (the row never resolves → `waitUntil` timeout), never silent.
- **Assertions key only on status CDs + the verbatim tool name — never the summaries.** `name` and
  `is_error` pass through the producer verbatim, but `input` / `content` are summarised server-side
  into `input_summary` / `result_summary`. So the tests deliberately do **not** assert on the summary
  text (it may be truncated/reworded) — only on `cd_tool_running` / `cd_tool_failed` and `"Bash"`.

## Lessons learned

- **The `Done` tool-row state has no positive content-description** (its resolved icon's
  `contentDescription` is `null`), so "done" cannot be asserted directly. It is asserted as the
  absence-triad above — the running CD that was present is now absent, the failed CD never appears, and
  the verbatim tool name is still on screen — which uniquely identifies a running → done resolution
  without keying on timing. (Lifted from the PR's Lessons-learned section.)
- **A lone `tool_use` opening + holding a turn is the one operator-tunable assumption.** Drop A is a
  bare `tool_use` line (no preceding `responding` text, no `end_turn`), mirroring how
  `spinner-open.jsonl` is a bare `thinking` line. If a future producer requires a prior event to open
  the turn, the running-assert times out (loud, not a false pass) — the documented fix is to prepend a
  `thinking` or short `text` line to `tool-open.jsonl`, which does not affect the tool-row assertion
  (it keys on the tool CD, not the turn state). Captured in the doc's Assumptions section to confirm on
  first operator run.
- **Tool name / fixture text must not collide with always-present chrome** (the #431 →
  `e2e-seed` lesson, [[431-fakeclaude-staticuuid-vs-discussion-session]]). `TOOL_NAME = "Bash"` is
  distinct from the seeded channel name `"e2e-seed"` (top bar), the prompts `hello`/`bye`, and the
  turn-ending reply text `"ok"`/`"oops"` — so the substring/CD matches can't false-green. The
  turn-ending text is cosmetic (it only closes the turn) and is **not** asserted on.

  do **not** compile androidTest, so this is run explicitly;

- `bash -n` clean; all three fixtures valid JSON with trailing newlines.
- **Operator-run (device + host `pyry`/`pyrycode-relay`/`fakeclaude`):** the two new scenarios —
  `DETERMINISTIC=1 SCENARIO=tool|tool-failed … bash scripts/e2e-emulator.sh` — each green and
  re-running back-to-back yielding the same pass. No green e2e is claimed from the pipeline; expect to
