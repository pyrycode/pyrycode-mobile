# #488 — Fail in-flight relay requests when the connection tears down

**Issue:** [#488](https://github.com/pyrycode/pyrycode-mobile/issues/488) ·
**Spec:** [`docs/specs/architecture/488-fail-pending-requests-on-teardown.md`](../../specs/architecture/488-fail-pending-requests-on-teardown.md) ·
**PR:** [#504](https://github.com/pyrycode/pyrycode-mobile/pull/504) ·
**Feature doc:** [Remote conversation repository § the `ack`/`error` correlation primitive](../features/remote-conversation-repository.md#the-ackerror-correlation-primitive-reused-by-347348) ·
Size **XS**, `security-sensitive`.

## Summary

A single-file behavioural fix in [`RemoteConversationRepository`](../features/remote-conversation-repository.md).
Every request/reply call ([`sendAndAwaitReply`](../features/remote-conversation-repository.md#the-ackerror-correlation-primitive-reused-by-347348),
:659) registers a `CompletableDeferred` in `pendingRequests` (:208) and suspends on `await()`, completed
**only** by a correlated inbound `ack`/`error` routed through the single `init` collector. On teardown
[`RelayRepositoryCoordinator.teardownActive()`](../features/relay-repository-coordinator.md) cancels that
collector's scope — but nothing completed the still-registered deferreds, so **every** `sendAndAwaitReply`
caller (`answer_modal`, `send_message`, `promote`, `create_conversation`, `request_snapshot`,
`register_push_token`, `dequeue_message`) hung **forever** on the caller's ViewModel scope. For the
permission flow this was a **silent answer-drop** — tap Allow, coroutine hangs, nothing surfaces — and it
**blocked flipping `USE_RELAY_REPOSITORY` on** (the fake never tears a connection down, so the hang only
manifests against the real relay).

The fix wraps the single inbound collector in `try { … } finally { failAllPending() }`. On **any**
collector-termination mode the `finally` completes every registered deferred exceptionally with a plain
`IllegalStateException` and removes it, so an awaiting caller throws **promptly** instead of hanging.

## Files touched

- `app/src/main/java/de/pyryco/mobile/data/repository/RemoteConversationRepository.kt` (**mod**, +42):
  - **The one production edit site** — the `init` collector (`:266-272`): the `pump.inbound.collect { … }`
    body is now wrapped in `try { … } finally { failAllPending() }`. The `finally` covers **all three**
    collector-termination modes, satisfying AC #1's "scope is cancelled **or** `pump.inbound` completes":
    scope-cancel (the primary trigger, throws `CancellationException`), `pump.inbound` completing (returns
    normally), `pump.inbound` throwing (propagates). It runs **exactly once** per collector lifetime and
    does **not** swallow the `CancellationException` (`failAllPending` returns; cancellation keeps
    propagating — structured-concurrency-correct).
  - **`private fun failAllPending()`** (`:687`) — the teardown sweep: iterate `pendingRequests.values`,
    `completeExceptionally(cause)` + `iterator.remove()` each entry, where `cause` is one shared plain
    `IllegalStateException(PENDING_REQUEST_TORN_DOWN)`. **Non-suspending**
    (`CompletableDeferred.completeExceptionally` returns `Boolean`), so it runs to completion even inside
    the *cancelling* collector coroutine; idempotent against the caller's own `finally { remove }`.
  - **`const val PENDING_REQUEST_TORN_DOWN = "connection torn down before reply"`** (`:1547`, companion) —
    a static, payload-free message (no request content, `modalId`, or ids; never-log contract holds by

## Patterns established

- **Iterator `remove()`, not `clear()`, when a concurrent registration may race the sweep.** `failAllPending`
  iterates `pendingRequests.values.iterator()` and completes-then-`iterator.remove()`s each entry rather than
  `map.clear()`. This removes **exactly** the deferreds it completed, so a request registered concurrently
  *during* the sweep is never silently wiped without being completed — it stays registered and gets its own
  reply (or the next sweep). Weakly-consistent `ConcurrentHashMap` iteration + idempotent
  `completeExceptionally` make it safe (code-review NOTE confirmed this as the more correct choice).
- **Fail an in-flight suspend with a *non-`CancellationException`* on scope teardown.** When a `finally`
  running inside a cancelling coroutine must unblock an awaiting caller with a *surfaceable* error, complete
  the deferred with a plain `IllegalStateException` — **never** a `CancellationException` (which
  `extends IllegalStateException` on the JVM). The completion must also be **non-suspending**, or it would
  itself throw `CancellationException` immediately inside the cancelling coroutine and never run. This is the
  outbound-side companion to the inbound [[catch-illegalstate-swallows-cancellation]] rule.
- **One `try/finally` hook covers every collector-termination mode.** Wrapping a single long-lived
  `pump.inbound.collect { … }` in `try { … } finally { … }` gives one deterministic teardown seam for
  scope-cancel + stream-completes + stream-throws — no separate close path, and no second stochastic
  mechanism (belt-and-suspenders with deterministic fabric).

## Lessons learned

- **The `finally` satisfies AC #1's "scope cancelled **or** inbound completes" with one hook.** A `finally`
  on a `collect` runs for all three termination modes (scope cancel — the primary `teardownActive` trigger —
  `inbound` completing, `inbound` throwing), so no separate close path was needed. (Lifted from the PR's
  Lessons-learned section.)
- **Completing with `IllegalStateException` (not `CancellationException`, which `extends` it on the JVM) is
  load-bearing.** A `CancellationException` would make `await()` read as the caller's *own* scope dying
  rather than a surfaceable error — the "surface an error" intent would be silently lost. Reusing the exact
  type `sendAndAwaitReply`'s not-connected `check(...)` already throws also means every caller handles
  teardown-mid-await through the one failure mode it already has. (Lifted from the PR's Lessons-learned
  section; test-pinned by both `is IllegalStateException` and `!is CancellationException` asserts.)
- **The sweep-vs-`pump.close()` micro-race is deferred by evidence, not fixed.** A sub-millisecond window
  remains: between the collector's `finally` sweeping and the coordinator's subsequent `pump.close()`, a
  caller could register a *new* deferred (after the sweep iterated) while `pump.send` still returns `true`
  → never completed → hang. This is the exact "second mechanism for the same failure mode" the ticket scopes
  out — **not observed**, sub-millisecond, multi-coroutine. Adding a `withTimeout` belt on `await` now would
  ship an unneeded second mechanism (Evidence-Based Fix Selection); it is the documented follow-up **only**
  if a real hang is later observed to survive this fix. (Spec Open Questions; code-review concurred.)

## Security (`security-sensitive`)

Architect self-review **PASS** (spec `## Security review`); code review **PASS**, zero findings. Load-bearing
properties:

- **No new trust boundary, no new untrusted-input parse.** The change reads no envelope payload and decodes
  nothing; the swept `JsonElement` reply payloads are **discarded** (completed exceptionally, never
  inspected). The teardown trigger originates from the local coordinator — a malicious relay can at most
  close the socket, which already ends the connection, for which failing the pending requests is the correct
  fail-fast response (strictly better than the prior hang).
- **Never-log holds by construction.** `failAllPending` emits no log; the `IllegalStateException` carries only
  the static `PENDING_REQUEST_TORN_DOWN` literal — no `modalId`, `optionId`, message text, or conversation/
  session id. Preserves the modal/answer path never-log contract (`RelayRepositoryCoordinator` :290-291).
- **Availability, positive.** Clearing `pendingRequests` on teardown releases stale `CompletableDeferred`
  references that previously leaked per connection across reconnect churn, and unblocks caller coroutines that
  previously suspended forever. No unbounded growth.
- **Structured-concurrency-correct** — the `finally` does the non-suspending sweep and lets
  `CancellationException` propagate (no `NonCancellable`, no `catch(CancellationException)` anti-pattern).
