# #208 — feat(ui/thread): wire "Change workspace…" overflow item to the Workspace Picker

Lifts `ThreadEvent.ChangeWorkspace` out of the no-op `Unit` arm in [`ThreadViewModel.onOverflowEvent`](../features/thread-overflow-menu.md#viewmodel-dispatcher) into its own arm that flips `pendingWorkspacePicker.value = true`, opening the existing [`WorkspacePicker`](../features/workspace-picker.md) host. The overflow menu's **Change workspace…** item now opens the same picker the empty-thread workspace chip already opens ([#137](./137.md)). Everything downstream — picker render, `onWorkspacePicked(path)` → `repository.changeWorkspace(...)`, `onWorkspacePickerDismissed()` — was already wired by [#137](./137.md); this is a pure-additive "new trigger", no new state. Split from [#143](https://github.com/pyrycode/pyrycode-mobile/issues/143); the third and last per-item follow-up that drains the overflow-menu no-op group set up by [#251](./251.md).

## Summary

- **One production line, net.** `ThreadViewModel.kt:282` — the no-op arm `ThreadEvent.NewSession, ThreadEvent.ChangeWorkspace, -> Unit` (two cases) split into `ThreadEvent.ChangeWorkspace -> pendingWorkspacePicker.value = true` plus the surviving `ThreadEvent.NewSession -> Unit`. The new arm is a verbatim copy of `onWorkspaceChipTapped()`'s body (`ThreadViewModel.kt:212-213`) — same flag, same picker, no parallel flow.
- **Zero new surface.** No new field on `ThreadUiState`, no new `combine` arm, no new render call in `ThreadScreen`, no new handler method on the VM, no edit to the `WorkspacePicker` host. `pendingWorkspacePicker` (declared `ThreadViewModel.kt:104`, combined at `:155` → `ThreadUiState.workspacePickerVisible`), the picker render in `ThreadScreen`, and the picked/dismiss handlers all pre-date this ticket ([#137](./137.md)). AC #2 ("reuse, don't re-introduce") is satisfied by construction.
- **Two UI sites light up from one arm.** `ThreadEvent.ChangeWorkspace` is fired from **two** places, both no-op before this change: the overflow menu item (`ThreadOverflowMenu.kt`) and the [`ChannelInfoSheet`](../features/channel-info-sheet.md)'s "Change workspace" row (`ThreadScreen.kt`, which fires `ChangeWorkspace` then `ChannelInfoDismiss`). The single new `when` arm serves both — after this change, both entry points open the picker. Intended, no extra work; flagged so code-review wasn't surprised that the Channel Info row also "lights up."
- **The picked path emits a `SessionBoundary`.** `onWorkspacePicked(path)` → `repository.changeWorkspace(conversationId, path)`, which mints a new `Session` and surfaces a workspace-change [`SessionBoundary`](../features/session-boundary-delimiter.md) delimiter ([#135](./135.md)) in the thread. Unchanged by this ticket — owned by [#137](./137.md)'s handler — but worth noting the overflow trigger now reaches that delimiter path too.
- **One new unit test + one one-line edit to an existing test.** Net ~16 test lines.

## Patterns established

- **The "new trigger reuses the existing picker flag" pattern landed exactly as [#137](./137.md) designed it.** #137 introduced `pendingWorkspacePicker` + the three handlers (`onWorkspaceChipTapped` / `onWorkspacePicked` / `onWorkspacePickerDismissed`) specifically so the overflow entry point would be a pure-additive arm rather than a new state machine. #208 cashes that in: a single `when` arm, no new field. This is the canonical shape for "second/third UI affordance that opens an already-mounted picker/dialog" — route the event to the existing visibility flag; never stand up a parallel flow. (Same rule the [`WorkspacePicker`](../features/workspace-picker.md) host's consumer convention documents.)
- **No new VM unit test for `NewSession`'s continued no-op.** The surviving `Unit` arm has no observable side effect; the compiler-enforced exhaustive `when` is its contract. `onOverflowEvent_otherCases_doNotCallArchive` still covers it as a negative case. Matches the [#204](./204.md) reasoning for not over-testing `Unit` arms.

## Lessons learned

None worth carrying forward — the ticket was XS and landed mechanically. The one subtlety (the [`ChannelInfoSheet`](../features/channel-info-sheet.md) "Change workspace" row also fires `ChangeWorkspace` and therefore also lights up from the single arm) was anticipated in the architect spec, not discovered during implementation.

The ticket AC's residual-arm description was stale and the architect spec corrected it: the AC said the surviving no-op arm would read `NewSession, ChannelInfo -> Unit`, but on `main` `ThreadEvent.ChannelInfo` had already gained its own arm in [#226](./226.md) (`-> pendingChannelInfo.value = true`). The actual no-op arm before this change was `NewSession, ChangeWorkspace -> Unit` (two cases); after, it is `NewSession -> Unit` (one). The routing intent matched the AC; only the residual case list differed — so no `ChannelInfo` no-op branch was (re-)added. Worth remembering when an XS ticket's AC names exact `when`-arm contents: verify against current `main`, not the ticket body, because sibling tickets reshape shared `when` blocks between split-time and implementation-time.
