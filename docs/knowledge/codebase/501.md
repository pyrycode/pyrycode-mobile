# #501 — Route paste-pairing through the fingerprint-confirm gate

**Issue:** [#501](https://github.com/pyrycode/pyrycode-mobile/issues/501) ·
**Spec:** [`docs/specs/architecture/501-paste-pairing-fingerprint-gate.md`](../../specs/architecture/501-paste-pairing-fingerprint-gate.md) ·
**PR:** [#525](https://github.com/pyrycode/pyrycode-mobile/pull/525) ·
**Feature docs:** [Paste code dialog](../features/paste-code-dialog.md) (**new**) ·
[Pairing confirm gate](../features/pairing-confirm-gate.md) (**updated**) ·
Size **XS**, `security-sensitive` (pre-release blocker).

## Summary

Closes the impostor-server MITM gap on the **paste** pairing entry path. The paste-pairing dialog
([#503](https://github.com/pyrycode/pyrycode-mobile/issues/503)) shipped without the QR path's
fingerprint-confirm gate ([#343](343.md)): on a valid parse it called `confirmPairAndNavigate`
directly and persisted immediately, so a user pasting a malicious code was silently paired to an
impostor server without ever seeing its fingerprint. There were two persist paths and the
`MainActivity.kt` "ONLY … persist" comment was false. This re-points the paste Success branch into
the **same** gate the camera uses: the validated payload is handed to `ScannerEvent.QrDecoded`, which
sets `Decoded` → the shared `LaunchedEffect` derives the fingerprint and parks in `AwaitingConfirm`
→ persist happens **only** behind the Confirm button. Both entry paths now converge on one
fingerprint-gated persist. Manifests only with `USE_RELAY_REPOSITORY` on.

The inline `AlertDialog` was extracted into a stateless, **store-free** [`PasteCodeDialog`](../features/paste-code-dialog.md)
so "paste cannot persist" is true **by construction** — the dialog holds no reference to
`PairedServerStore` / `confirmPairAndNavigate`; its only success output is a raw payload string.

## Files touched

- `app/src/main/java/de/pyryco/mobile/ui/onboarding/PasteCodeDialog.kt` (**new**, 67 lines) — the
  extracted stateless dialog. `@Composable fun PasteCodeDialog(onDismiss, onValidPayload: (String) -> Unit)`.
  Owns its `pasteText` / `pasteError` via `remember` (mounts fresh on each show, so state
  re-initializes without an explicit reset — the old `pasteText=""`/`pasteError=null` reset in
  `onPasteCode` is retired). Renders the identical `AlertDialog` shipped in #503 (title "Enter pairing
  code", `OutlinedTextField` label "Pairing code" with `isError`/`supportingText`, "Pair" /"Cancel"
  buttons). The **only** behavioral change vs #503: the Success branch calls `onValidPayload(trimmed)`
  instead of persisting; Failure still sets the inline `"Invalid pairing code"`. Parses the **trimmed**
  value **once** and hands *that same* value off (no suspension between parse and callback, so the
  parsed-from and emitted strings are provably identical). Calls `parsePairingPayload` directly (pure
  top-level fn, no injection). **Logs nothing** (spec MUST-hold — the pasted string and its token must
  never reach `Log.*`).
- `app/src/main/java/de/pyryco/mobile/MainActivity.kt` (**mod**, +19/−50) — the single wiring edit.
  Deleted the inline `AlertDialog` block and the `pasteText`/`pasteError` locals; kept `showPasteDialog`.
  `onPasteCode` simplified to `{ showPasteDialog = true }` (`:259`). The dialog is now
  `PasteCodeDialog(onDismiss = { showPasteDialog = false }, onValidPayload = { payload -> showPasteDialog = false; vm.onEvent(ScannerEvent.QrDecoded(payload)) })`
  (`:281-289`). `confirmPairAndNavigate` (`:169`) is unchanged but is now the **sole** caller-site
  reached from exactly one place — `onConfirmPairing`, gated on `(state as? AwaitingConfirm)`
  (`:264-266`). The "ONLY … persist" comment (`:160-168`) was rewritten to describe **both** entry
  paths reaching it through the same `QrDecoded → Decoded → AwaitingConfirm → Confirm` sequence.
  Dropped the now-unused `AlertDialog`/`OutlinedTextField`/`Text`/`TextButton` imports.
- `app/src/androidTest/java/de/pyryco/mobile/ui/onboarding/PasteCodeDialogTest.kt` (**new**, 128 lines)
  — the dialog had **no** coverage before, so a regression re-introducing the bypass would have passed
  every test. Four instrumented contract tests (`createComposeRule`, `ScannerScreenTest` idiom):
  render (title/label/buttons), **valid paste → hands off, no inline error**, **whitespace trimmed
  before hand-off**, **invalid paste → inline error + no hand-off**, **Cancel → `onDismiss` not
  `onValidPayload`**. Because the dialog has no store handle, "nothing persists" is guaranteed by type;
  the tests pin the *callback contract*.

**Not touched:** `ScannerViewModel` (no rename of `QrDecoded` — see below), the shared `Decoded`
`LaunchedEffect`, `PairingConfirmContent`, `serverKeyFingerprint`, `PairedServerStore`, any
`data/` / crypto / network / wire surface. The actual `store.save` still lives solely in
`PairingConfirmation.kt:40` (`confirmPairingAndConnect`, [#489](489.md)), whose only caller is the
gated `onConfirmPairing` lambda — verified by the code-review blast-radius check.

## Patterns established

- **Store-free extraction for "cannot persist" security ACs.** When a security AC is phrased "X must
  not persist / must not reach the store," extract X into a stateless composable whose type has **no
  reference** to the persistence handle (`PairedServerStore` / the persist lambda). Its only output is
  a raw validated value handed to a callback; the caller decides what to do with it. This converts
  "paste can't persist" from a reviewer's *argument* into a *structural type guarantee* — the
  belt-and-suspenders split the pipeline asks for: a deterministic structural fact (dialog can't reach
  the store) **plus** a UI test pinning the callback contract. Different fabric, not two stochastic
  checks.
- **Feed the raw untrusted payload to the single derive site, not a pre-derived object.** The paste
  Success branch hands the **raw payload string** to `QrDecoded` (not `result.server`), so the
  fingerprint derive + null-guard happen at the **one** site in the shared `Decoded` effect rather
  than being duplicated into the paste path. `parsePairingPayload` is pure/deterministic, so a valid
  paste re-parses to the same `Success` — it can never fall through to the full-screen QR-worded
  `PARSE_FAILED_MSG`. A second producer of an existing untrusted-input event should route through that
  event, not shortcut past its validation.
- **A source-specific event name can serve a second producer without a rename.** `ScannerEvent.QrDecoded`
  now carries "a raw untrusted pairing payload" from **two** producers (camera + paste). A
  source-neutral rename was deliberately **out of scope** (rename fan-out across the VM, its test, and
  the camera wiring would exceed XS for no behavioral gain). If a future ticket renames it, update both
  producers together.

## Lessons learned

- **The unit-test fixture helpers are not on the androidTest classpath.** `PairingPayloadParserTest`'s
  `wrap(json())` helper (which builds a valid base64url-no-pad pairing string) lives in `src/test/` and
  is **not** visible from `src/androidTest/`. `PasteCodeDialogTest` rebuilds a valid code inline with
  `java.util.Base64` (`getUrlEncoder().withoutPadding()` for the outer wrapper, `getEncoder()` for the
  inner base64-std 32-byte `server_static_pubkey` — the two-alphabet trap, see
  [[pairing-qr-two-base64-alphabets]]). Instrumented tests were **not** run (no emulator in the
  environment); the fixture was verified by hand against `PairingPayloadParser` and compiled via
  `compileDebugAndroidTestKotlin` ([[androidtest-not-compiled-by-mandatory-gates]]).
- **Redacting `toString()` inheritance covers the second producer for free.** The pasted token flows as
  `QrDecoded(payload) → Decoded(payload)`, both of which already carry a redacting `toString()`
  (`<redacted N chars>`), so an accidental `"$state"`/`"$event"` log stays byte-safe on the paste path
  without any new redaction — routing paste through the existing event inherits the existing
  protection. The one new constraint is local: `PasteCodeDialog` itself must log nothing.
- **A fresh-mounted dialog needs no explicit state reset.** Because the dialog is mounted only inside
  `if (showPasteDialog)`, its `remember { mutableStateOf("") }` re-initializes every time it opens —
  the old imperative `pasteText=""`/`pasteError=null` reset in `onPasteCode` became dead and was
  dropped with no behavior change. (Kept `remember`, **not** `rememberSaveable` — matches #503; do not
  upgrade.)

## Security (`security-sensitive`, pre-release blocker)

Architect self-review **PASS** (spec `## Security review`); code review **PASS**, zero findings.
Load-bearing properties:

- **This ticket *is* the fix.** The pasted string is untrusted external input; pre-fix the paste path
  crossed straight to persist, bypassing the human fingerprint-compare boundary the QR path enforces
  ([#343](343.md)). Post-fix both entry sources cross the identical
  `parsePairingPayload → serverKeyFingerprint → AwaitingConfirm → Confirm-persist` boundary.
- **Single fingerprint-gated persist path (AC #2).** `confirmPairAndNavigate` is invoked from exactly
  one gated site (`onConfirmPairing`, `state as? AwaitingConfirm`); the real `store.save` is
  `PairingConfirmation.kt:40`, reachable only from there. No paste-side persist survives — the
  "ONLY … persist" comment is accurate again and now describes both paths.
- **Bad paste never reaches the full-screen error (AC #4).** The Failure branch sets the inline error
  and emits **no** event, so it never reaches the QR-worded `PARSE_FAILED_MSG` surface.
- **Decline / Back persists nothing (AC #3).** Shared with QR — `DeclinePairing → ReadyToScan`, no
  paste-specific code.
- **The double-parse is safe.** The dialog gates Success/Failure and the shared effect re-parses to
  derive; `parsePairingPayload` is pure/deterministic and the *same* `trimmed` string is fed to both,
  so a Success cannot diverge into a Failure.
- **Out of scope (pre-existing, not introduced here):** clipboard / third-party-keyboard capture of the
  pasted token is inherent to allowing paste at all (#503); this ticket neither introduces nor worsens
  it, and the fingerprint-compare gate it adds actually mitigates the *impostor* consequence even if the
  token is observed. No owner assigned; note only.

## Doc staleness fixed here vs. left as pre-existing debt

- **Fixed (falsified by this ticket):** [Pairing confirm gate](../features/pairing-confirm-gate.md)'s
  "The paste path remains ungated" limitation and its "store touched in exactly two places
  (`confirmPairAndNavigate` + `stubPairAndNavigate`)" security property — both now describe the single
  gated persist reached by both entry paths. The matching INDEX line was updated.
- **Left as pre-existing debt (from #489/#503, which have no codebase doc):** `stubPairAndNavigate` was
  removed from the code in [#489](489.md) but is still referenced in
  [`navigation.md`](../features/navigation.md), [`scanner-denied-screen.md`](../features/scanner-denied-screen.md),
  and the `scanner-screen` INDEX entry. That staleness predates #501 and is not what this ticket
  touched — deliberately left alone (Simplicity First; touch only what's necessary). A future
  #489/#503 doc pass should scrub it.
