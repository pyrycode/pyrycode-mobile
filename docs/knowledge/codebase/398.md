# #398 — wire live two-part connection status into the Settings Connection section

The **wiring slice** (slice B) of the two-part `● Relay   ● Pyrycode` connection-status line: it
threads the already-live `RelayRepositoryCoordinator.connectionStatus: StateFlow<ConnectionStatus>`
([#392](392.md)) through the MVI chain (VM → DI → host → stateless screen) into the
[`ConnectionStatusLine`](../features/connection-status-line.md) component shipped by [#397](397.md),
rendered under the **Server** row in the **Connection** section of Settings. It **draws nothing new**
— every type, flow, screen, and component it consumes already existed on `main`.

Split from #390 (slice B; `blockedBy #397`, which landed first). Slice A = #397 (the component, the
green [`success` token](../features/success-color.md), and the pure mapper). This slice delivers
**AC#1 of the parent #390** — the live data path. Motivation: live phone↔daemon testing on
**2026-06-08** surfaced a daemon-not-on-relay bug that presented only as a generic "Offline" with no
hint of *which* leg was broken; the two-part line makes both legs glanceable and self-diagnosing.

## Summary

Four production files modified, **zero new files, zero new exported types**. Surface the coordinator's
hot `connectionStatus` as a forwarded `val` on `SettingsViewModel`, inject it via Koin off the
concrete coordinator singleton, collect it lifecycle-aware at the `MainActivity` Settings host, and
pass it into the stateless `SettingsScreen`, which renders `ConnectionStatusLine` between the Server
row and the "Pair another server" row. Both legs now update live and self-diagnose which leg is
broken. 68 insertions across 4 production + 2 test files; built exactly to spec, zero deviations.

## Files touched

Production — 4 modifications:

- **`ui/settings/SettingsViewModel.kt`** (`+7`) — third constructor param
  `val connectionStatus: StateFlow<ConnectionStatus>`, forwarded **verbatim** (no `stateIn` re-wrap).
  A KDoc records why: unlike the sibling flows here (cold DataStore upstreams that need
  `stateIn(WhileSubscribed)`), this is already a process-scoped `StateFlow` shared `Eagerly` by the
  coordinator ([#392](392.md)), so `.value` is always correct. **Inject the narrow `StateFlow`, not
  the whole coordinator** — passing the concrete `RelayRepositoryCoordinator` would widen the
  dependency to `start()`/`close()`/`currentRepository` and force the unit test to construct the real
  6-arg coordinator; the narrow flow keeps the VM test a one-liner and mirrors
  [`StableConversationRepository`](../features/stable-conversation-repository.md), which takes
  `coordinator.currentRepository`, not the coordinator.
- **`di/AppModule.kt`** (`+3/-1`) —
  `viewModel { SettingsViewModel(get(), get(), get<RelayRepositoryCoordinator>().connectionStatus) }`.
  The third arg fetches the flow off the concrete coordinator singleton, exactly as the
  `currentRepository` fetch one line below does for `StableConversationRepository`. **Not**
  `get(), get(), get()` — `StateFlow<ConnectionStatus>` is not a registered Koin type, and this avoids
  a new interface/binding (AC#1). DI-safe: the coordinator is `single(createdAtStart = true)`
  *unconditionally* (`AppModule.kt:78`), so this resolves in **every** build regardless of the
  `USE_RELAY_REPOSITORY` flag (the flag only selects the `ConversationRepository` interface binding,
  not the coordinator).
- **`ui/settings/SettingsScreen.kt`** (`+13`) — new **required first** param
  `connectionStatus: ConnectionStatus` (consistent with the screen's no-default convention for state
  params); renders
  `ConnectionStatusLine(status = connectionStatus, modifier = Modifier.padding(start = 16.dp, top = 4.dp, bottom = 8.dp))`
  between the Server `SettingsRow` and the "Pair another server" row. Both `@Preview`s pass
  `ConnectionStatus(RelayLinkStatus.DaemonAbsent, PyrycodeLinkStatus.Down)` so the previews showcase
  the green-relay / red-pyrycode diagnostic. `start = 16.dp` aligns the line with the `ListItem` text
  inset so it reads as belonging to the Server row.
- **`MainActivity.kt`** (`+2`) — in the `Routes.SETTINGS` composable,
  `val connectionStatus by vm.connectionStatus.collectAsStateWithLifecycle()` alongside the existing
  collects, passed as `connectionStatus = connectionStatus` into `SettingsScreen`. Keeps the screen
  **stateless** (AC#3): the value is collected lifecycle-aware at the host and flows in via param.

Tests — 2 modifications:

- **`test/.../SettingsViewModelTest.kt`** (`+34`) — `makeVm` gains a third **defaulted** param
  (`connectionStatus: StateFlow<ConnectionStatus> = MutableStateFlow(ConnectionStatus(Offline, Down))`)
  so the 40+ existing tests stay untouched. Two new **test-first** tests pin the "forwarded live, not
  snapshotted" contract: `connectionStatus_reExposesInjectedCoordinatorValue` (the VM re-exposes the
  injected value) and `connectionStatus_reflectsUpstreamReemission` (mutate the injected
  `MutableStateFlow`, `advanceUntilIdle()`, assert `vm.connectionStatus.value` updated — proves the VM
  forwards the live flow rather than snapshotting it).
- **`androidTest/.../SettingsScreenTest.kt`** (`+9`) — the three `SettingsScreen(...)` call sites each
  gain `connectionStatus = ConnectionStatus(Offline, Down)` to compile. Mechanical compile fix; those
  tests assert on unrelated rows, so the value is non-load-bearing.

## Patterns established

- **Forward a coordinator's already-hot `StateFlow` verbatim — don't re-`stateIn` it in the VM.** The
  sibling preference flows on this VM all `stateIn(viewModelScope, WhileSubscribed)` because their
  upstream is a *cold* DataStore flow. A hot `StateFlow` shared `Eagerly` on a process-lifetime scope
  (the coordinator's `connectionStatus`) needs no re-wrap — re-wrapping would add a redundant layer
  with a worse initial value and zero benefit. The rule: **`stateIn` the cold; forward the hot.** This
  is the first non-DataStore flow exposed by [`SettingsViewModel`](../features/settings-viewmodel.md).
- **Inject the narrow signal, not the wide collaborator.** The VM needs exactly one `StateFlow`, so it
  takes that — not the concrete `RelayRepositoryCoordinator`. Fetch-the-narrow-property-at-the-Koin-site
  is now the established coordinator-consumption shape across three consumers: `currentRepository`
  (→ `StableConversationRepository`), `relayStatus` (→ #392's combine), and now `connectionStatus`
  (→ `SettingsViewModel`). None take the coordinator itself.

## Lessons learned

- **The default debug build honestly reads `Offline / Down` (both red), and that is correct — not a
  defect.** `USE_RELAY_REPOSITORY` is OFF by default, so no real relay connection is driven and the
  line shows both legs down. The phone genuinely has no relay link in that build. Against a live,
  paired daemon (relay mode) the dots reflect reality and update live. Don't "fix" the all-red debug
  state by faking a connected value — the failure modes *are* the data.
