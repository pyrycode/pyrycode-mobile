# #185 — feat(ui/thread): auto-scroll thread to follow streaming messages

Cashes the promise [#184](./184.md) explicitly deferred: while any `ThreadItem.MessageItem` in `state.items` carries `message.isStreaming = true`, [`ThreadScreen`](../features/thread-screen.md)'s `LazyColumn` keeps the streaming bubble's growing bottom edge pinned to the viewport bottom by observing item 0's measured size via `LazyListState.layoutInfo.visibleItemsInfo` and re-invoking `scrollToItem(0)` on each layout-pass size change. A user-initiated drag/fling — detected via a `NestedScrollConnection` filtered on `NestedScrollSource.UserInput` — flips a local `userScrolledAway` flag that suppresses the auto-pin; a snapshot-flow on `firstVisibleItemIndex == 0 && firstVisibleItemScrollOffset == 0` clears the flag when the user manually returns to the bottom, so auto-follow resumes for the remainder of the reveal. The auto-pin coroutine is gated by a `derivedStateOf { items.any { ... isStreaming } }`, so non-streaming threads pay zero cost. All wiring is screen-internal — no new file, no `ThreadViewModel` surface, no change to `MessageBubble` / `StreamingAssistantBody` internals.

## Patterns established

- **`snapshotFlow` over `LazyListState.layoutInfo.visibleItemsInfo[*].size` is the right primitive for "scroll behaviour reacting to an item's measured-height change".** `layoutInfo` is snapshot-backed; `snapshotFlow` re-emits only when the read state changes (each layout pass that affects item 0's measured size). Combined with `.distinctUntilChanged()` it produces exactly one emission per character revealed in the streaming bubble — no `withFrameMillis` polling, no `Choreographer` callback, no Compose internals reach. Pattern applies to any future "anchor a scrollable to a growing item" need: pin the snapshot read to the specific item's `LazyListItemInfo` field that changes (`size`, `offset`, `contentType`), let `snapshotFlow` handle the change detection, gate with `distinctUntilChanged()` to drop redundant layout passes. Equivalent for `LazyRow` substitutes the `x` size component.
- **`NestedScrollConnection` filtered on `NestedScrollSource.UserInput` is the correct user-scroll detector — not offset-drift inference.** When the streaming bubble grows naturally, the bottom anchor can transiently drift before the next layout pass; inferring "user scrolled" from `firstVisibleItemScrollOffset != 0` would false-trip on natural growth. `NestedScrollSource.UserInput` (Compose 1.7+ consolidated source covering drag + fling) is the unambiguous signal. `scrollToItem` is a direct-state mutation and does **not** generate `UserInput` events, so the auto-pin loop cannot recursively trip its own user-scroll flag. The `available.y != 0f` guard avoids false positives from zero-delta scroll events. Pattern applies to any future "yield programmatic scroll to user input" decision: route the user-input detection through `NestedScrollConnection.onPreScroll`'s `source` parameter, never infer from state drift.
- **`scrollToItem(0)` is the right primitive for tight-loop re-anchoring; `animateScrollToItem` is wrong here.** Instant, synchronous, O(1) when already pinned (no-op). Under streaming at 50 cps the worst case is ~50 invocations/sec, each microsecond-scale; no frame-budget risk. `animateScrollToItem` queues an animation whose duration overlaps subsequent ticks, producing visible stutter. Pattern: for sub-second-cadence re-anchoring driven by external state change, prefer `scrollToItem`; reserve `animateScrollToItem` for one-shot user-initiated transitions (jump-to-search-result, jump-to-mention).
- **`derivedStateOf` wrapped in `remember(<list>)` is the cheap "list-scan as Compose state" shape.** `remember(state.items) { derivedStateOf { state.items.any { ... } } }` re-runs the scan only when the underlying list reference changes, then memoizes the result as a `State<Boolean>` that Compose can read efficiently in `LaunchedEffect` keys. Naked `state.items.any { ... }` in a `LaunchedEffect` key would re-scan on every recomposition. Pattern applies to any future "feature-detection over a list of polymorphic items" gate: `remember(list) { derivedStateOf { list.any { it is Foo && it.bar } } }`.

## Lessons learned

- **Reverse-layout's "newest at bottom" is `index 0` with `firstVisibleItemScrollOffset == 0`.** `state.items.asReversed()` puts the chronologically-last item at reversed index `0`; under `LazyColumn(reverseLayout = true)`, that's drawn at the viewport bottom. Both the auto-pin's `scrollToItem(0)` and the bottom-return predicate `firstVisibleItemIndex == 0 && firstVisibleItemScrollOffset == 0` rely on this. `LazyListState.canScrollBackward` / `canScrollForward` are about "is there content past the viewport edge"; they do **not** track "is the user at the anchor". The precise predicate is the `(firstVisibleItemIndex, firstVisibleItemScrollOffset)` pair compared against `(0, 0)`. Documenting this lesson because the reverse-layout sign flip catches every newcomer who tries to swap the two values.
- **`LaunchedEffect` cancel-on-key-change is what makes AC3 free.** When `hasStreamingMessage` flips `true → false`, `LaunchedEffect(hasStreamingMessage, listState)` cancels its running coroutine and re-launches with the new key value; the early `if (!hasStreamingMessage) return@LaunchedEffect` then bails before the `snapshotFlow` collector starts. Net effect: the auto-pin collector is alive for exactly the duration of the streaming window. No explicit "stop streaming" listener needed; the `Message.isStreaming` flag flipping is what un-mounts the side effect. Same pattern composes with any future "ambient behaviour active during a transient flag" need.
- **`scrollToItem` does not generate a `UserInput` nested-scroll event.** Verified by code-read of `LazyListState.scrollToItem` (it mutates `firstVisibleItemIndex` / `firstVisibleItemScrollOffset` directly without going through the scroll dispatcher). This is what makes the auto-pin loop safe: a programmatic re-anchor cannot trip the `userScrolledAway` flag and silence subsequent auto-pins. If a future ticket replaces `scrollToItem` with `animateScrollToItem` or `scrollBy`, both of those **do** dispatch through `onPreScroll` (with `source = NestedScrollSource.SideEffect` / `UserInput` respectively); the filter `source == NestedScrollSource.UserInput` would still hold for `SideEffect`-source dispatches, but the runtime characteristics differ. Pin this against the chosen primitive — if you swap it, re-verify.
- **`StreamingAssistantBody` lifetime trade-off from [#184](./184.md) is sidestepped, not solved, by this ticket.** [#184](./184.md)'s lessons section notes that when the streaming bubble scrolls off-screen in the `LazyColumn`, the item composable is disposed, `produceState`'s coroutines cancel, and `revealedLength` resets to 0 on re-entry. The auto-pin loop here keeps the streaming bubble in the viewport during streaming, which means the typical demo path never disposes the item; Phase-0-acceptable. **But** if the user deliberately scrolls away during streaming (AC2's yield path), the bubble can still scroll off-screen and re-trigger the reset on return. Phase 4's hoist of `revealedLength` into `ThreadViewModel` keyed on `messageId` (the open follow-up from [#184](./184.md)) is the proper fix; this ticket does not pre-pay for it because the auto-pin happy path makes it visually invisible in Phase 0.
- **Phase-0 seed never flips `isStreaming` to `false` — AC3's `LaunchedEffect`-gate path is not exercised by the demo.** The seeded streaming message in `seed-channel-pyrycode-mobile` stays `isStreaming = true` forever (the fake has no stream-completion signal in Phase 0). The `LaunchedEffect(hasStreamingMessage, listState)` early-return when the flag flips false is unreachable through normal demo flow. Local verification path: temporarily change the seed's `isStreaming = true` to `false` and re-install, or read the `LaunchedEffect` gate. Phase 4's real WS feed will signal stream-end naturally and exercise the cancel path on every assistant reply. Document so the next ticket touching this code doesn't waste time wondering why the `LaunchedEffect` exit branch is "untestable".
- **`rememberLazyListState()` survives recomposition but not configuration change.** On rotation, the list re-creates and `firstVisibleItemIndex` resets to 0 — which under `reverseLayout = true` is the bottom anchor, the right place for a streaming-follow demo. No `rememberSaveable { LazyListState.Saver }` needed; adding it would preserve scroll position across rotation but would also stale-anchor away from the bottom of a still-streaming reply. Phase 0 acceptance is fine without it.
- **`distinctUntilChanged()` is load-bearing.** Compose may re-derive `layoutInfo` on layout passes that don't change item 0's size (e.g. measurement re-runs triggered by sibling state changes); without `distinctUntilChanged()`, those would invoke `scrollToItem(0)` unnecessarily. The call is cheap when already pinned, so this is an optimisation rather than a correctness fix — but the wasted recompositions add up at 50 cps × N layout passes per tick. Keep the operator unless a profiler indicates otherwise.
