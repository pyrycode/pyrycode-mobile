# #549 — Wire `archive_conversation` / `unarchive_conversation` v2 messages

**Issue:** [#549](https://github.com/pyrycode/pyrycode-mobile/issues/549) · split from #531 ·
**Spec:** [`docs/specs/architecture/549-archive-unarchive-conversation-wire.md`](../../specs/architecture/549-archive-unarchive-conversation-wire.md) ·
**PR:** [#553](https://github.com/pyrycode/pyrycode-mobile/pull/553), `92cb777` ·
**Feature doc:** [Remote conversation repository](../features/remote-conversation-repository.md) §
`archive`/`unarchive` (new) ·
Size **S**, `security-sensitive` (PASS).

## Summary

Replaces `RemoteConversationRepository.archive` / `.unarchive`'s `UnsupportedOperationException` throws
with a live v2 round-trip against the daemon's `archive_conversation` / `unarchive_conversation`
(server-side pyrycode#881, closed): encode an id-only `ArchiveConversationPayloadDto` — **shared by both
verbs**, mirroring the server's single payload for the pair — send over the same write-verb path `rename`
([#530](530.md)) uses, await the correlated `conversation_updated` reply, decode it through the #318
`ConversationResponseDto` boundary, and fold via `upsertConversation`. Both overrides delegate to one
private `sendArchiveToggle(conversationId, type)` helper parameterized by wire type, mirroring the
server's one handler registered under both verbs. Data layer only — surfacing in the ViewModels is
[#550](https://github.com/pyrycode/pyrycode-mobile/issues/550), the rung-3 e2e is
[#551](https://github.com/pyrycode/pyrycode-mobile/issues/551).

The load-bearing extension is to the **shared decode boundary**, not the repository: `ConversationResponseDto`
did not decode any archived field and `toConversation()` hardcoded `archived = false`. Left alone, an
archive reply would fold `archived = false` and the conversation would never leave the main list — archive
would silently no-op. The fix adds a **defaulted** `is_archived` field (`= false`, pyrycode#881, no
`omitempty` on the wire) and wires it into `toConversation()` (`archived = isArchived`).

## Patterns established

- **Shared request DTO for a symmetric verb pair.** When two wire verbs are a toggle of one durable flag
  (same shape, same handler, same error/reply behaviour — as pyrycode#881 framed archive/unarchive
  server-side), model one payload DTO and disambiguate by `Envelope.type`, not by minting a DTO per verb.
  Contrast `rename` vs `promote`, which deliberately do **not** share a DTO because their fields genuinely
  differ (`cwd`).
- **One private helper behind two interface overrides**, parameterized by wire-type string — the mobile
  mirror of "one server handler registered under two verbs." Reach for this shape whenever two interface
  methods would otherwise be byte-identical except for the `type` constant.
- **Extending a decode boundary is sometimes the load-bearing half of a "wire a mutation" ticket.** The new
  repository code here is almost entirely encode/send/fold boilerplate identical to `rename`; the actual
  bug this ticket prevents (`archived` never leaving `false`) lives in the shared DTO, not the new method
  bodies. When a reply reuses an existing decode type, check whether that type actually carries the new
  field before assuming "mirror the precedent" is sufficient.

## Lessons learned

- Extending a shared response DTO with a **defaulted** field (`= false`) rather than a required one avoids
  a call-site cascade across every existing decode path (`createDiscussion`, `promote`, `rename`) that
  doesn't yet send the new key — this is the standard way to extend a decode boundary consumed by multiple
  reply shapes when the server only extended one of them (pyrycode#881 touched
  `ConversationUpdatedPayload`, not `conversation_created`).
- The same DTO fix incidentally repairs a **dormant** bug in the already-shipped `rename` (#530): since
  pyrycode#881 the `rename_conversation` reply also carries `is_archived`, which `rename` was silently
  dropping (folding `archived = false` regardless of actual state). This was undetectable before #549
  because nothing could archive a conversation yet. No separate rename-specific test was added — it's
  covered by the DTO-level `is_archived` tests.
- **Out of scope, flagged not fixed:** the **list-read** path (`ConversationsPayload` /
  `ConversationSummaryDto.toConversation()`) also hardcodes `archived = false` and also drops the
  `is_archived` pyrycode#880 added to `ConversationSummary`. A freshly archived conversation (from another
  client, or before this app connects) shows as active until a verb reply re-folds it locally. This governs
  the initial/unsolicited list snapshot, not the verb fold this ticket owns — recommended as a follow-up
  ("mirror pyrycode#880 list-read `is_archived`"), not filed as part of this slice.
