# Ticket #295: route start destination via PairedServerStore; remove pairedServerExists boolean

## Implementation summary

The strangler-fig completion of the paired-state migration begun in [#294](294.md). Atomically swapped both the **read** and the **write** of paired state from the `AppPreferences.pairedServerExists` boolean over to the encrypted [`PairedServerStore`](../features/encrypted-paired-server-store.md), then deleted the boolean — so there is never a moment with two live sources of paired-state truth.

The two swap sites live in `ui/navigation/PyryNavHost.kt` (the architecture spec located them in `MainActivity.kt`, but the NavHost had already been extracted into `PyryNavHost` — see Lessons learned):

- **Start-destination read** — the `produceState<Boolean?>` block is now keyed on the injected `PairedServerStore` and gates on `pairedServerStore.load() != null` (present, decryptable record → `Routes.CHANNEL_LIST`; absent or undecryptable → `Routes.WELCOME`). The tri-state loading shape (`null` → blank `Surface`) is preserved verbatim.
- **Scanner `onTap` write** — the `Routes.SCANNER` composable persists a wire-shaped stub `PairedServer` via `save()`, navigating to the channel list on success. `ScannerScreen` stays a stateless composable (`onTap: () -> Unit`); the persist lives in the NavHost wiring, not the composable.
- **Boolean removed** (`data/preferences/AppPreferences.kt`) — the `pairedServerExists` flow, its `setPairedServerExists` setter, and the `paired_server_exists` DataStore key are all gone. `PairedServerStore` is now the sole paired-state source of truth. (`booleanPreferencesKey` stays imported — still used by other prefs.)
- **KDoc** (`data/crypto/PairedServerStore.kt`) — the "ships dormant … boolean stays the live source" line is replaced; it now states `MainActivity`/`PyryNavHost` decides the start destination from `load()` and the Scanner placeholder persists a stub via `save()`.
- **Tests** (`AppPreferencesTest.kt`) — the two obsolete cases (`pairedServerExists_defaultsToFalse`, `setPairedServerExists_true_isReflectedInNextEmit`) deleted. No new unit tests added; round-trip + empty-default coverage lives on #294's `androidTest` (`KeystorePairedServerStoreTest`).

The stub record is throwaway until QR pairing lands (#275/#276): `serverId="placeholder-server"`, a 64-char hex `token`, `relayUrl="wss://relay.invalid/v1/client"`, and a base64-STD encoding of 32 zero bytes for `serverStaticPublicKey`. Non-load-bearing — the store does no field-shape validation and no test asserts these values.

## Patterns established

- **Strangler-fig completion in a single slice.** When two live sources of truth would be a hazard, the switch-over ticket swaps both the read and the write *and* deletes the old source in the same change — never a window with two live sources. The dependency edge (`blockedBy #294`) keeps the merge order correct.
- **A fallible write behind a placeholder tap must not crash.** Unlike the old infallible `setPairedServerExists(true)`, `save()` throws `PairedServerStoreException`. The `onTap` catches it specifically (re-throwing `CancellationException` first) and no-ops on failure — the user stays on the placeholder and can re-tap. No error UI is built (the Scanner is a placeholder; a real surface lands with the QR-scanning ticket).

## Lessons learned

- **`produceState` key swap is load-bearing.** Re-keying the block from `appPreferences` to `pairedServerStore` is what makes it re-run if the injected store instance changes. Leaving the old key would keep a stale read across a (hypothetical) store swap. Both are Koin singletons so it's benign today, but the `produceState` key must name the dependency the producer actually reads.
- **`runCatching` swallows `CancellationException`.** It catches `Throwable`, so inside a coroutine a cancelled `save()` would be misreported as a failure — a structured-concurrency hazard. The shipped code uses a plain `try/catch` that re-throws `CancellationException` before handling the typed `PairedServerStoreException`.
- **The spec's file:line refs lagged a refactor.** The architecture spec located both swap sites (and the `Routes` object) in `MainActivity.kt`, but the NavHost had already been extracted into `ui/navigation/PyryNavHost.kt` (with `Routes` in `ui/navigation/Routes.kt`); `MainActivity` is now a thin shell → `PyryApp` → `PyryNavHost`. The real edits landed in `PyryNavHost.kt`. When a spec's path disagrees with the codebase, trust the symbol, not the file:line.
