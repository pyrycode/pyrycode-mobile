# #295 — route start destination via `PairedServerStore`; remove `pairedServerExists` boolean

The **strangler-fig completion** of the paired-state migration begun in [#294](294.md). Atomically swaps both the **read** (NavHost start-destination decision) and the **write** (Scanner placeholder `onTap`) of paired state from the `AppPreferences.pairedServerExists` boolean over to the encrypted [`PairedServerStore`](../features/paired-server-store.md), and deletes the boolean in the same change — so there is never a moment with two live sources of paired-state truth. The `blockedBy #294` edge kept the merge order correct. Refactor only; no UI added or changed. Split from [#292](https://github.com/pyrycode/pyrycode-mobile/issues/292).

## Summary

Three production files plus one test file. `MainActivity` now picks the start destination from `PairedServerStore.load()` (a present, decryptable record → channel list; absent or undecryptable → welcome) and the Scanner placeholder `onTap` persists a wire-shaped stub `PairedServer` via `save()` instead of flipping a boolean. The `pairedServerExists` `Flow`/setter/key and its two obsolete tests are removed, leaving the store as the sole source of paired-state truth. No new type, no new DI binding (the #294 `single { KeystorePairedServerStore(get()) } bind PairedServerStore::class` was already present), no new dependency.

## Files touched

- **`MainActivity.kt`** — both swap sites live here (the NavHost is a `private fun PyryNavHost` and `Routes` a `private object`, both in this file; there is no separate navigation package):
  - **Start-destination read** (`setContent`, ~`MainActivity.kt:78-83`) — `produceState<Boolean?>(initialValue = null, pairedServerStore) { value = pairedServerStore.load() != null }`, re-keyed from `appPreferences` onto the injected `pairedServerStore`. The tri-state is preserved verbatim: `null` → blank `Surface` while loading; `else` → `PyryNavHost(startDestination = if (v) Routes.CHANNEL_LIST else Routes.WELCOME)`. `load()` does its own `withContext(Dispatchers.IO)`, so it is called directly in the `produceState` coroutine.
  - **Scanner `onTap` write** (`composable(Routes.SCANNER)`, ~`MainActivity.kt:128-149`) — injects `koinInject<PairedServerStore>()` (replacing the old `AppPreferences` inject), keeps `rememberCoroutineScope()`, and `scope.launch { try { save(STUB_PAIRED_SERVER); navigate(CHANNEL_LIST){ popUpTo(SCANNER){inclusive=true}; launchSingleTop=true } } catch (e: PairedServerStoreException) { Log.w(TAG, …javaClass.simpleName) } }`. `ScannerScreen(onTap = …)` is unchanged — it stays a stateless composable; the persist lives in the NavHost wiring.
  - **`STUB_PAIRED_SERVER`** (`private val`, ~`MainActivity.kt:308`) — a throwaway wire-shaped record (overwritten when QR pairing lands, last-writer-wins): `serverId="placeholder-server"`, 64-char hex `token`, `relayUrl="wss://relay.invalid/v1/client"` (`.invalid` is RFC 2606 non-routable), `serverStaticPublicKey` = base64-STD of 32 zero bytes. Non-load-bearing: the store does no field-shape validation and no test asserts these values; the comment marks them placeholders.
- **`data/crypto/PairedServerStore.kt`** — one-line KDoc swap: the "ships dormant … the `pairedServerExists` boolean stays the live source" sentence is replaced with the new reality (`MainActivity` decides the start destination from `load()`; the Scanner placeholder persists a stub via `save()`; the QR consumers #275/#276 remain dormant).
- **`data/preferences/AppPreferences.kt`** — removed the `pairedServerExists: Flow<Boolean>`, the `setPairedServerExists` setter, and the `PAIRED_SERVER_EXISTS = booleanPreferencesKey("paired_server_exists")` companion entry. `booleanPreferencesKey` stays imported (still used by `use_wallpaper_colors`, `default_yolo`, `notifications_enabled`).
- **`data/preferences/AppPreferencesTest.kt`** — deleted the two now-obsolete cases (`pairedServerExists_defaultsToFalse`, `setPairedServerExists_true_isReflectedInNextEmit`). ## Patterns established

- **Strangler-fig completion in a single slice.** When two live sources of truth would be a hazard, the switch-over ticket swaps both the read and the write *and* deletes the old source in the same change — never a window with two live sources. The boolean is the sole live source right up until this slice removes it; the dependency edge (`blockedBy #294`) sequences the merge.
- **A like-for-like wiring swap onto a *fallible* API must carry the failure mode over.** The old `setPairedServerExists(true)` was infallible; `save()` throws `PairedServerStoreException`. Preserving "the placeholder tap never crashes" required a catch — and a **narrow** one (the specific `PairedServerStoreException`, not `Exception`/`Throwable`) so `CancellationException` still propagates (structured concurrency honoured), matching #294's narrow-catch discipline. The save-failure branch is a silent no-op (no error UI — the Scanner is a placeholder; a real surface lands with the QR-scanning ticket).

## Lessons learned

Lifted from [PR #297](https://github.com/pyrycode/pyrycode-mobile/pull/297)'s *Lessons learned*:

- **A wiring swap onto a fallible API silently introduces a crash path if the failure mode isn't carried over.** `PairedServerStore.save()` throws where `setPairedServerExists(true)` could not, so the Scanner `onTap` swap had to add a narrow catch (letting `CancellationException` propagate) to keep the placeholder tap crash-free. When migrating a call site from an infallible API to a throwing one, audit the new throw contract and re-establish the old site's safety guarantee.
