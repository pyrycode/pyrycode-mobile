# #213 — feat(ui/sheets): `CreateFolderDialog` stateless composable (Figma 19:44)

Lands [`CreateFolderDialog`](../features/create-folder-dialog.md), the second UI surface in the Workspace Picker flow and a sibling to [`WorkspacePickerSheet`](../features/workspace-picker-sheet.md) (#212). Renders Figma `19:44`: an M3 `AlertDialog` with the `"Create workspace"` headline, a single outlined text field carrying the floating label `"What should this workspace be called?"`, and `Cancel` / `Create` text buttons in the trailing action row. Stateless contract per spec — `onCreate: (String) -> Unit` + `onDismiss: () -> Unit`, no `ViewModel`, no repository binding, no host integration; the host that mounts the dialog after the picker's `onCreateNew` fires, owns dialog visibility, and calls [`createWorkspaceFolder`](../features/conversation-repository.md) from [#210](./210.md) on submit lands in #207. The dialog **owns its own `TextFieldValue`** (local UI state, not hoisted) because no other consumer needs to read it before submit, trims the input before emitting `onCreate`, and keeps the Create button disabled while the trimmed name is blank.

See [`../features/create-folder-dialog.md`](../features/create-folder-dialog.md) for the evergreen contract.

## Patterns established

- **Public wrapper + file-private `*Internal` seam is the canonical shape for stateless dialogs that need to demonstrate multiple AC states in previews without exposing test-only parameters on the public API.** The public composable has the minimum parameter set the host needs; the seam takes whatever extra params (`initialValue` here) the previews want to inject. Tests do NOT use the seam — they target the public composable and drive state via UI interactions (`performTextInput`). This is **different from** [#212](./212.md)'s shell/`*Content` split: there the inner exists because the outer (a `ModalBottomSheet`) is structurally untestable from `createComposeRule()`; here the inner exists purely to let previews inject initial state. **Rule:** if you need to render the composable in different visible states for previews but don't want to widen the public API to accept those states, introduce a file-private seam that takes the extra params, have the public composable delegate to it with sensible defaults, and have the Compose UI tests drive state via the public composable's interactive surface (typing, tapping, focus). Do NOT make the seam `internal` — that would tempt future code to reach into it for runtime use, which is exactly what the AC-1 "stateless contract" forbids.
- **`AlertDialog` previews can target the dialog composable directly with no scaffolding** — wrap in `PyrycodeMobileTheme(darkTheme = …) { CreateFolderDialog(...) }` and that's the whole preview. No `Box`, no `Surface`, no positional wrap. M3's `AlertDialog` paints its own scrim and surface inside the IDE preview pane, unlike `ModalBottomSheet` (which doesn't — see [#212](./212.md)'s `Surface(color = surfaceContainerLow)` workaround). **Rule for future dialogs in this codebase:** preview the dialog composable as-called inside `PyrycodeMobileTheme`; no wrapper scaffolding needed. If a future dialog wants its surroundings rendered (a host screen behind the scrim), wrap explicitly — but the default is just the theme.
- **`TextFieldValue` over `String` is the right input state shape for any `OutlinedTextField` that may need programmatic selection control** — even when the *current* contract only sets `TextRange.Zero`. The cost of `TextFieldValue` over `String` is one import and a `.text` access on read; the upside is that any future selection-on-focus, select-all-on-clear, or pre-fill-then-select-all UX is a one-line internal change instead of a state-shape migration. **Rule:** if a `OutlinedTextField`'s `value` ever needs to participate in cursor / selection logic, start with `TextFieldValue`. The repo has no `String`-backed `OutlinedTextField`s where the cursor matters, so this is the de facto baseline.
- **`derivedStateOf` for cheap derivations off a `TextFieldValue`** — even when the computation is one `.trim()` + one `isNotEmpty()`. Establishes the shape for future validation rules (length cap, regex match, uniqueness check) that the same composable might gain later. **Rule:** any derivation off `fieldValue.text` that is read by more than one consumer (here: the Create button's `enabled` AND the `onCreate(trimmedName)` argument AND the keyboard `onDone` guard) goes through `derivedStateOf`. Plain `val` recomputes per recomposition; `derivedStateOf` recomputes only when the underlying state changes.
- **All Compose UI tests target the public composable, not the seam.** AC-1 names the public symbol; the tests anchor to it so a future refactor can change the seam shape (add params, rename, inline back) without rewriting tests. The seam stays `private`, which means tests *literally cannot* reach it from the `androidTest/` source set. **Rule:** tests anchor to the public API; private testing seams are for previews only, never for tests.

## Lessons learned

- **`String.isNotEmpty()` and `String.trim().isNotEmpty()` diverge on whitespace-only input, and the AC contract is the latter.** The AC #2 wording — "Create button is disabled when the trimmed name is blank" — locks the `trim().isNotEmpty()` semantics. A future agent who simplifies the code from `derivedStateOf { fieldValue.text.trim().isNotEmpty() }` to `derivedStateOf { fieldValue.text.isNotEmpty() }` (looks like dead code; the trim already happens for the emitted name) will silently break the whitespace-only path: Create lights up on four spaces, the user taps it, and `onCreate("    ".trim()) == onCreate("")` fires with an empty string. The `create_button_stays_disabled_when_input_is_whitespace_only` test is the regression artifact — but only because it asserts `assertIsNotEnabled`, not because the implementation makes the diverge obvious. **Lesson:** the `trim()` in the derivation isn't a duplicate of the `trim()` in the emit; they encode two different AC obligations (enabled-state visibility vs. data-emission shape), and the test that catches the divergence has to test whitespace-only input specifically, not just empty input.
- **`createComposeRule()` cannot drive the software keyboard, so `KeyboardActions.onDone` is unreachable from the test.** The `KeyboardActions(onDone = { if (isCreateEnabled) onCreate(trimmedName) })` path is wired in source but no Compose UI test exercises it — `performTextInput` does not simulate an IME "Done" key press, and there is no `performImeAction(ImeAction.Done)` analogue available through `createComposeRule()` (it requires an attached `Activity` and a real `InputMethodManager`). **Lesson:** keyboard-action paths in stateless composables are tested implicitly via the same guard that the visible button uses (here: `isCreateEnabled`) — if you want explicit coverage, you need an instrumented test against `createAndroidComposeRule<ComponentActivity>()` with `Espresso.onView(...).perform(pressImeActionButton())`, which the codebase doesn't have today. Don't try to test `onDone` from `createComposeRule()`; it's structurally impossible.
- **`AlertDialog` outside-tap and back-press are structurally untestable from `createComposeRule()` for the same reason — no `Activity`, no scrim window, no hardware back dispatch.** [`WorkspacePickerSheetTest.kt`](./212.md) hit the same wall: outside-tap on a `ModalBottomSheet` requires the modal's window host. Both ticket's tests cover the same paths (the click handler on the visible button) and leave the `onDismissRequest` plumbing for visual verification + the host's own integration tests in the eventual #207. **Lesson:** if a stateless composable's contract includes "outside-tap and back-press route to `onDismiss`", the regression artifact is the *source-level wiring* (one line: `onDismissRequest = onDismiss`), not a test. Don't burn time trying to drive the scrim from `createComposeRule()`.
- **`AlertDialog`'s window machinery DOES render in the IDE preview pane, but `ModalBottomSheet`'s does NOT.** This is the asymmetry that determines whether you need a `Surface(color = surfaceContainerHigh)` wrap around the preview. For [`WorkspacePickerSheet`](./212.md) (a `ModalBottomSheet`), the previews wrap `*Content` in `Surface(color = surfaceContainerLow)` to simulate what the runtime modal would paint; the modal itself renders nothing in the preview pane. For `CreateFolderDialog` (an `AlertDialog`), the dialog renders its own scrim + surface in the preview pane, so wrapping in another `Surface` would paint a second background underneath the dialog's own surface — visually misleading. **Lesson:** preview-wrap shape depends on whether the runtime parent paints its container in the preview pane. `AlertDialog`: no wrapper needed. `ModalBottomSheet`: wrap in `Surface(color = surfaceContainerLow)`. `BottomSheetScaffold`: TBD next ticket that uses one. Check what the IDE actually paints before mirroring a precedent from a sibling component.
- **`FocusRequester.requestFocus()` inside `LaunchedEffect(Unit) { ... }` works without any extra coordination because the `LaunchedEffect` runs after the composition tree is committed.** No `LaunchedEffect(focusRequester)` indirection needed (the requester reference is stable from `remember`); no manual coordination with the `AlertDialog`'s window-attachment lifecycle. **Lesson:** for a one-shot focus request on dialog open, `LaunchedEffect(Unit) { focusRequester.requestFocus() }` is the canonical Compose-idiomatic shape and Just Works. If you ever see a focus request silently failing, the diagnosis is almost always (a) `focusRequester` not attached to a node via `Modifier.focusRequester(...)` or (b) the node isn't `focusable()` — not a lifecycle timing issue.
- **The architect spec's `"three previews total"` posture beats `@PreviewParameter` collapse for AC #3 verification.** AC #3 accepts either two preview functions OR one `@PreviewParameter`-parameterised preview; the spec recommended three discrete `@Preview`s (empty-light, filled-light, filled-dark). The three-preview shape is what shipped — easier to scan the IDE preview pane (three labelled tiles vs. one tile with a `@PreviewParameter` chip switcher), easier to lock down the dark variant separately, and aligns with the `WorkspacePickerSheet*Preview` + `WorkspacePickerSheetDarkPreview` precedent in the sibling file. **Lesson:** for stateless composables with 2–4 visible states, prefer discrete `@Preview` functions over `@PreviewParameter`. Reserve `@PreviewParameter` for cases where the state space is large enough that maintaining N preview functions becomes a hazard (5+ states, or where the states are generated rather than hand-picked).
