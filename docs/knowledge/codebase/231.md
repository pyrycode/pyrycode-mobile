# #231 — feat(data): defaults schema — Model/Effort enums + AppPreferences keys

Pure data-layer slice for the "Defaults for new conversations" feature (split from #147). Adds two new enum types (`Model`, `Effort`) and four new `Flow`/`suspend`-setter pairs on [`AppPreferences`](../features/app-preferences.md) — `defaultModel`, `defaultEffort`, `defaultYolo`, `defaultWorkspace` — exactly mirroring the existing `themeMode` / `useWallpaperColors` pattern. No UI, no consumer wiring, no `DefaultsBundle` abstraction. Unblocks the Settings model/effort/YOLO/workspace picker slices and is the schema that #228 (StatusSheet model override) and #229 (StatusSheet effort override) are stubbing pending — those consumers can now read the real defaults.

## Summary

- **Two new single-line enum files** in `data/preferences/`, mirroring `ThemeMode.kt`'s shape: `Model { OPUS_4_7, SONNET_4_6, HAIKU_4_5 }` and `Effort { LOW, MEDIUM, HIGH, XHIGH, MAX }`. Identifier-only — no `.label()` extension, no display strings. The first UI consumer (Settings model picker) owns label strings; baking them in here now would either be unused dead code or pin `String` literals into the data layer that may want to be Android string resources later. `CLAUDE.md` lists Compose Multiplatform as a walk-back trigger and asks for `data/` to stay portable — display strings are not data-layer concerns. The identifier shape (`OPUS_4_7`, `HAIKU_4_5`) documents the model unambiguously for non-UI consumers (e.g. #228 reading `defaultModel` to seed StatusSheet state).
- **Four new `Flow<T>` + `suspend fun set…` pairs on `AppPreferences`**, added in the order model → effort → yolo → workspace after the existing `useWallpaperColors` block:
  - `defaultModel: Flow<Model>` — `stringPreferencesKey("default_model")` holding `.name`; tolerant-unknown fallback `Model.entries.firstOrNull { it.name == stored } ?: Model.OPUS_4_7` (the `themeMode` shape).
  - `defaultEffort: Flow<Effort>` — same shape, fallback `Effort.HIGH`.
  - `defaultYolo: Flow<Boolean>` — `booleanPreferencesKey("default_yolo")`, default `false` (the `pairedServerExists` / `useWallpaperColors` shape).
  - `defaultWorkspace: Flow<String>` — `stringPreferencesKey("default_workspace")`, default `DEFAULT_SCRATCH_CWD` (imported from `de.pyryco.mobile.data.model`, not re-declared). Reuses the existing string-sentinel convention from `Conversation.cwd` — a `sealed Workspace { Scratch; Bound(cwd) }` would be premature abstraction for one slice of work, and downstream consumers all work in terms of `cwd: String`.
- **No `DefaultsBundle` data class.** Each field is its own flow/setter, following the "one field per Settings row" convention `AppPreferences` already encodes. Bundling four unrelated rows would lose per-row recomposition granularity (a Yolo write would recompute the Model picker subtitle) and would push validation/migration concerns into a single bag.
- **`AppPreferences`'s key threshold is now seven.** [`app-preferences.md`](../features/app-preferences.md) calls out a "~5 keys → split by domain" rule of thumb. This ticket crosses that line. Split deliberately deferred: the four new keys form a single logical group ("defaults for new conversations") that the next two-or-three Settings UI slices will consume in tandem; splitting before those land would mean re-stitching imports immediately. **Re-evaluate the split when the first non-defaults Phase-3 key (notifications) lands** — that's the natural seam between `AppPreferences` (pairing/theme + defaults bundle) and a new `NotificationPreferences`.
- **Ten new tests** appended to `AppPreferencesTest.kt`, following the existing `defaultsToX` / `setX_roundTrips` / `unparseableStoredValue_fallsBackToX` triplet pattern. The unparseable-value tests use raw `stringPreferencesKey` writes via `dataStore.edit { … }` (not the wrapper's setter) so the test specifically exercises the read-side fallback. Booleans get a `false → true → false` round-trip (mirrors `setUseWallpaperColors_roundTripsBothValues`). Workspace gets a custom-cwd round-trip plus a round-trip back to `DEFAULT_SCRATCH_CWD` to confirm the sentinel survives.

## Patterns established

- **Tolerant-unknown fallback for stored enums applies to every string-backed enum preference, not just `ThemeMode`.** The two new enum-typed flows (`defaultModel`, `defaultEffort`) use the same `entries.firstOrNull { it.name == stored } ?: <DEFAULT>` shape that `themeMode` established. Both "key absent" and "stored string not in `entries`" converge on the documented default — no throw, no `runCatching`. **Rule for future enum-typed `AppPreferences` keys:** `stringPreferencesKey` holding `.name` + `entries.firstOrNull { it.name == stored } ?: <DEFAULT>`. Never `intPreferencesKey` holding an ordinal — ordinals reshuffle on enum reorder/removal and silently corrupt the stored value across upgrades. `app-preferences.md` § "Adding a preference" already encodes this rule; the two new flows are the third and fourth instances in the codebase.
- **String-sentinel reuse over a richer sealed type.** `defaultWorkspace: Flow<String>` defaults to `DEFAULT_SCRATCH_CWD` (the same sentinel `Conversation.cwd` already uses for "no bound workspace"), not a `sealed Workspace { Scratch; Bound(cwd) }`. Downstream consumers (#228/#229 stubs + the future workspace picker) all work in `String` terms, and the sentinel is already the contract elsewhere. **Rule:** when an existing string-sentinel convention covers the same semantic distinction a sealed type would, reuse the sentinel — promote only when a real consumer can't express its branching without the type. Per `CLAUDE.md`'s "don't introduce abstractions beyond what the task requires."
- **Defer `.label()` extensions on data-layer enums until the first UI consumer.** The ticket explicitly delegated this call to the architect, and the architect deferred. **Rule for future data-layer enums:** keep them identifier-only in `data/preferences/`. The first UI consumer that needs display strings is the right place to decide whether labels live as a Kotlin extension (like `internal ThemeMode.label()` at the bottom of `SettingsScreen.kt`), as Android string resources, or as a Compose-side lookup. Pre-baking labels into the data layer either dead-codes them or pins `String` literals into a layer that should stay portable for the Compose Multiplatform walk-back.

## Lessons learned

- **Crossing the `~5 keys` split threshold doesn't automatically mean splitting.** The `app-preferences.md` rule of thumb says "once `AppPreferences` accumulates ~5 keys, consider splitting by domain." With this ticket the count goes from three to seven. Splitting now would force the next two-or-three Settings UI slices to re-stitch imports across two preference classes within the same feature, churn for no benefit. The split is deferred to the next non-defaults Phase-3 key (notifications), which is the natural seam. **Pattern:** the "~5 keys" rule means "consider," not "must" — when the new keys form a tight semantic group (here, "defaults for new conversations") that the next few slices will touch together, defer the split until a key lands that breaks the group cohesion.
- **`stringPreferencesKey` + `.name` is the right serialisation for enums, even when the enum is small.** The temptation with a three-variant or five-variant enum is to reach for `intPreferencesKey` + ordinal — smaller on disk, faster compare. Don't. Ordinals depend on declaration order, which is mutable across releases; renames keep `.name` intact across IDE refactors (the rename also rewrites the writes); and the storage cost difference is single-digit bytes per key. **Pattern:** always `stringPreferencesKey` holding `.name` for enum prefs, regardless of variant count. The existing `themeMode` ⇒ `defaultModel` / `defaultEffort` consistency makes the codebase easier to grep and the tolerant-unknown fallback shape uniform.
- **Tolerant-unknown tests must use the raw `stringPreferencesKey` write path, not the wrapper setter.** `setDefaultModel(Model.OPUS_4_7)` can't produce an unparseable value — it goes through `model.name`. To exercise the read-side fallback you have to write a garbage string directly: `dataStore.edit { it[stringPreferencesKey("default_model")] = "GPT5" }`. The test then asserts the flow emits the documented default (`Model.OPUS_4_7`). Both `defaultModel_unparseableStoredValue_fallsBackToOpus47` and `defaultEffort_unparseableStoredValue_fallsBackToHigh` follow this shape, mirroring the existing `themeMode_unparseableStoredValue_fallsBackToSystem`. **Pattern:** for any tolerant-unknown-fallback assertion, the test must write the garbage value through `dataStore.edit` with the raw typed-key builder — going through the wrapper setter exercises the wrong code path.
