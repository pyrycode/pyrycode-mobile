# #229 — feat(ui/sheets): StatusSheet — Effort + YOLO sections (Figma 20:100)

Lays the **Effort** (M3 `FilterChip` row, five chips low/medium/high/xhigh/max) and **YOLO mode** (M3 `Switch` toggle) sections beneath the existing Model section inside `StatusSheetContent`. `ThreadUiState` gains `selectedEffort: Effort` (initialised from `AppPreferences.defaultEffort`, mirroring the [#253](./253.md) `selectedModel` override pattern) and `yoloEnabled: Boolean` (always `false` initial — explicitly ignores the dormant `AppPreferences.defaultYolo` flow). `ThreadViewModel` gains `onEffortSelected(Effort)` + `onYoloToggled(Boolean)` mutators, wired from `MainActivity` via method references. The StatusSheet is the **only writer** of `yoloEnabled` — an architectural single-writer invariant enforced by `private` visibility on the `MutableStateFlow` plus a code-review `git grep` check; preserving this surface was the entire reason for the `security-sensitive` label on the issue. The third StatusSheet slice ([#230](https://github.com/pyrycode/pyrycode-mobile/issues/230) Context window) appends into the same `StatusSheetContent` without re-shaping anything established here. Split from [#146](https://github.com/pyrycode/pyrycode-mobile/issues/146); siblings are [#254](./254.md) (shell + Model section) and [#230](https://github.com/pyrycode/pyrycode-mobile/issues/230).

## Summary

- **Effort follows the `selectedModel` override pattern verbatim from [#253](./253.md).** Private `effortOverride: MutableStateFlow<Effort?>` (`null` ⇒ "use Settings default") pre-combined with `appPreferences.defaultEffort` into a private `selectedEffortFlow: Flow<Effort> = combine(default, override) { d, o -> o ?: d }`. The mutator `onEffortSelected(effort: Effort)` is a synchronous `MutableStateFlow.value` write — **no** `appPreferences.setDefaultEffort(...)` call (override is in-memory only; the AC's "does not mutate `AppPreferences`" line). Phase 4 will persist per-conversation; for now configuration change recreates the VM and the override is lost (the conversation re-derives from the Settings default).
- **YOLO deliberately diverges from the Model/Effort override pattern.** `yoloEnabled: MutableStateFlow<Boolean>` is hardcoded `MutableStateFlow(false)`; **no read of `appPreferences.defaultYolo`**, no override-vs-default combine layer. The mutator `onYoloToggled(enabled: Boolean)` is a synchronous `MutableStateFlow.value` write — the only writer of the field. The dormant `appPreferences.defaultYolo` flow and the non-functional `SettingsScreen.kt:80` local `mutableStateOf(false)` row stay as dead code per spec; this slice neither wires them nor removes them.
- **`combine`'s 5-arg overload was at capacity; a `RunConfig` pre-combiner was introduced.** The existing main `combine(conversations, items, picker, dialogs, selectedModelFlow)` already used all five typed slots. Adding two more sources would have forced the untyped vararg `combine(vararg Flow<*>, transform: (Array<*>) -> R)` overload, losing compile-time type safety on the destructuring lambda. The fix folded the three run-config flows into one upstream combine, plugged into the main combine as the fifth source:

  ```kotlin
  private data class RunConfig(
      val model: Model,
      val effort: Effort,
      val yoloEnabled: Boolean,
  )

  private val runConfigFlow: Flow<RunConfig> =
      combine(selectedModelFlow, selectedEffortFlow, yoloEnabled) { model, effort, yolo ->
          RunConfig(model, effort, yolo)
      }
  ```

  The main `combine`'s last lambda parameter renamed `selectedModel` → `runConfig`, then destructures `runConfig.model` / `runConfig.effort` / `runConfig.yoloEnabled`. `RunConfig` is `private` to the file — not exposed. This is the same pre-combine-to-stay-under-5 trick [#142](./142.md) used with `TransientDialogs` for the rename + save-as-channel dialogs; both private data classes now coexist at the bottom of `ThreadViewModel.kt`.
- **`STUB_EFFORT` companion constant deleted.** [#145](./145.md) shipped `private const val STUB_EFFORT = "high"` alongside `STUB_TOKEN_PERCENT = 73`; this slice removes the former (the field is now real ViewModel state, not a stub). `STUB_TOKEN_PERCENT` stays untouched — [#230](https://github.com/pyrycode/pyrycode-mobile/issues/230) owns that field.
- **`ThreadUiState.effort: String` retyped to `selectedEffort: Effort`** + new `yoloEnabled: Boolean = false` field. The retype is a breaking rename of one field on a data class; edit fan-out was three sites — `ThreadScreen.kt:91` (`effort = state.effort` → `effort = state.selectedEffort.label()`), `ThreadViewModelTest.kt:202+214` (string equality on `"high"` → enum equality on `Effort.HIGH`). Both production previews in `ThreadScreen.kt` build `ThreadUiState(...)` without passing the field, so they inherit the new default unchanged. The field's data-class default position keeps `selectedModel` / `selectedEffort` / `yoloEnabled` / `tokenPercent` adjacent for readability.
- **`Effort.label()` visibility widened from `internal` to top-level public** in `EffortPickerDialog.kt:77`. Now two consumers in two packages (`ui.settings` for the [#233](./233.md) `EffortPickerDialog` row text + Settings row subtitle, `ui.conversations.components` for the new `FilterChip` labels in `StatusSheet.kt`); the widening avoids a third location for the same five-arm `when` mapping. Same surface cost as `Model.label()`'s widening in [#253](./253.md) — the architect's preferred shape was the one-line visibility change in place rather than moving the extension next to the enum in `data/preferences/Effort.kt`. The original "first UI consumer owns the labels" convention (`app-preferences.md`) stays unchanged for `ThemeMode`; `Effort` and `Model` are both now partial walk-backs scoped to those two enums.
- **`Effort.entries.forEach` drives chip ordering** rather than five hand-written `FilterChip(Effort.LOW, ...)` calls. Same precedent as [#254](./254.md)'s `Model.entries.forEach` over the three model rows: source order at `data/preferences/Effort.kt` (`{ LOW, MEDIUM, HIGH, XHIGH, MAX }`) is the single source of truth; a future enum reorder or insertion propagates without parallel UI edits.
- **`FilterChip` defaults match Figma `20:131–140` exactly — no `FilterChipDefaults.filterChipColors(...)` override.** Selected: `secondaryContainer` background + `onSecondaryContainer` label, no border. Unselected: 1dp `outline` border + transparent background + `onSurfaceVariant` label. The default `FilterChipDefaults.filterChipBorder(...)` paints the unselected outline; selected state replaces border with background fill automatically. No leading icon, no trailing icon. The chip `Row` carries `Modifier.fillMaxWidth().selectableGroup().padding(horizontal = 16.dp, vertical = 4.dp)` with `Arrangement.spacedBy(8.dp)` — the `selectableGroup()` wrap lets TalkBack announce "in group of 5" at the row boundary.
- **`YoloRow` makes the entire row the touch target via `Modifier.toggleable(role = Role.Switch)`.** `Row(fillMaxWidth.toggleable(value = enabled, role = Role.Switch, onValueChange = onToggled).padding(horizontal = 16.dp, vertical = 8.dp), verticalAlignment = Alignment.CenterVertically)` with a weighted `Column { Text("Auto-accept tool calls", bodyLarge, onSurface); Text("Claude runs commands without asking for confirmation. Use carefully.", bodySmall, onSurfaceVariant) }` on the left, a 16.dp `Spacer`, and `Switch(checked = enabled, onCheckedChange = null)` on the right. **`onCheckedChange = null` is required**, not optional — passing the handler to both the row's `toggleable` and the `Switch.onCheckedChange` causes the callback to fire twice (same trap as `RadioButton(onClick = null)` inside `selectable` from [#254](./254.md)). Same canonical M3 shape as `ModelRow`'s `selectable` + `RadioButton(onClick = null)`, swapping `selectable`/`Role.RadioButton` for `toggleable`/`Role.Switch`.
- **Effort auto-closes the sheet on selection; YOLO does not.** The `StatusSheet` host inside `ThreadScreen` wraps `onEffortSelected` in the same close-then-callback wrapper [#254](./254.md) used for `onModelSelected`: `{ effort -> onEffortSelected(effort); sheetVisible = false }`. `onYoloToggled` passes straight through with **no** auto-close — toggling YOLO keeps the sheet open so the user can see the result and toggle back if they misclicked. Architect's spec called this out as the right asymmetry: a single-tap radio/chip selection is a complete action (auto-close is M3 modal-bottom-sheet convention), but a Switch toggle is a state-change the user may want to immediately reverse. The auto-close-on-Model decision from [#254](./254.md) was the open question — the resolution for the multi-section sheet is "auto-close per single-pick section, keep open for toggle sections".
- **Two new `@Preview`s satisfy the AC's "both Effort variations and YOLO on/off" requirement.** `StatusSheetEffortLowYoloOffPreview` (`Effort.LOW`, `yoloEnabled = false`) and `StatusSheetEffortMaxYoloOnPreview` (`Effort.MAX`, `yoloEnabled = true`); both reuse the canonical `PyrycodeMobileTheme { Surface(color = surfaceContainerLow, ...) { Column(padding(PaddingValues(top = 12.dp))) { StatusSheetContent(...) } } }` wrap with `showBackground = true, widthDp = 412`. The three pre-existing previews (`StatusSheetOpusPreview`, `StatusSheetSonnetPreview`, `StatusSheetHaikuPreview`) got their `StatusSheetContent(...)` calls extended with the four new parameters (`selectedEffort = Effort.HIGH, onEffortSelected = {}, yoloEnabled = false, onYoloToggled = {}`) so they keep compiling. Total five previews in the file; all light-mode, no dark sweep (the theme behaviour is identical across themes for chips + switch).
- **Six new `androidTest` Compose UI methods + four existing tests extended** in `StatusSheetTest.kt`. New: `renders_effort_section_with_all_five_chips`, `tapping_low_chip_invokes_onEffortSelected_with_low`, `selected_effort_chip_reports_selected_semantics` (pairs `assertIsSelected` for `Effort.MAX` with `assertIsNotSelected` for `low` — the negative-pinning sister assertion), `renders_yolo_section_with_title_and_supporting_text`, `tapping_yolo_row_when_off_invokes_onYoloToggled_with_true`, `tapping_yolo_row_when_on_invokes_onYoloToggled_with_false`. The pre-existing four (renders-all-three-model-rows, tap-sonnet, tap-haiku, tap-close, selection-state) got their `StatusSheetContent(...)` calls extended with `selectedEffort = Effort.HIGH, onEffortSelected = {}, yoloEnabled = false, onYoloToggled = {}`. - **Seven new `ThreadViewModel` unit tests + two existing tests updated** in `ThreadViewModelTest.kt`. New (mirroring the [#253](./253.md) `selectedModel` test shape): `selectedEffort_followsAppPreferencesDefault`, `selectedEffort_reemitsWhenAppPreferencesDefaultChanges`, `onEffortSelected_overridesPerConversationWithoutMutatingPreferences`, `onEffortSelected_overrideWinsOverSubsequentDefaultChange`, `yoloEnabled_initialValueIsFalseRegardlessOfAppPreferencesDefault` (pre-sets `prefs.setDefaultYolo(true)` then asserts `vm.state.value.yoloEnabled == false` — the AC's "YOLO ignores any app-level preference" verification line), `onYoloToggled_flipsStateAndDoesNotMutatePreferences`, `yoloEnabled_remainsFalseWhenAppPreferencesDefaultYoloChanges` (the mirror-image of the model `reemitsWhenChanges` test, proving the **opposite** — `prefs.setDefaultYolo(true)` does not flip the VM field). ## Patterns established

- **`combine`'s 5-arg overload ceiling is real — pre-combine into a file-private `data class` rather than dropping to the untyped `vararg` overload.** Two pre-combiners now live at the bottom of `ThreadViewModel.kt`: `TransientDialogs` (from [#142](./142.md), wrapping the rename + save-as-channel flags) and `RunConfig` (this slice, wrapping model + effort + YOLO). Both are `private` to the file, not exposed on `ThreadUiState`. The rule: when the main `combine` is at five sources and a new flow needs to land, pick the most cohesive existing source group (the one whose existing slot the new flow logically belongs to) and lift it into a pre-combine that returns a small `data class`. Naming convention: noun describing the group (`RunConfig`, `TransientDialogs`), not the flow shape. The fan-out is one extra `data class` declaration + one renamed lambda parameter + N destructuring reads — costs less surface than refactoring the entire main combine into the untyped vararg form, and the `data class` becomes a natural extraction point if any of its inner flows graduates to its own consumer (e.g. if `RunConfig` ever needs to be observed by a non-ThreadScreen surface, it can become `internal` or move out of the VM).
- **Two layered single-writer invariants for safety-sensitive boolean fields.** YOLO's "only the StatusSheet writes this" architectural rule is enforced **structurally** by Kotlin's visibility system (`private val yoloEnabled: MutableStateFlow<Boolean>` on the ViewModel — no other call site **can** write it without a visibility change) **and** by the AC's `git grep` check at code review (any visibility widening surfaces in the diff). The unit-test suite deliberately does **not** assert "no other call site writes the field" — that's a static structural check, not a runtime property. Apply this pattern to any future safety-sensitive field: keep the `MutableStateFlow` private, expose exactly one mutator method, and rely on the code-review grep to catch visibility drift. The architect's security-review pass (see `docs/specs/architecture/229-statussheet-effort-yolo.md` § Security review) called this out as the load-bearing invariant for the `security-sensitive` label.
- **Asymmetric auto-close in a multi-section sheet: close on single-pick sections, keep open on toggle sections.** The Model section ([#254](./254.md)) auto-closes on radio selection (single-tap completes the action). The Effort section in this slice auto-closes on chip selection for the same reason. The YOLO section does **not** auto-close on toggle — a Switch is a state-change the user may want to immediately reverse; closing the sheet would force a re-open just to undo. The wiring convention in `ThreadScreen`'s `StatusSheet(...)` host: wrap single-pick callbacks in `{ value -> upstream(value); sheetVisible = false }`, pass toggle callbacks straight through. Apply when [#230](https://github.com/pyrycode/pyrycode-mobile/issues/230)'s Context window section lands — if it's a discrete-value picker, auto-close; if it's a slider or toggle bank, keep the sheet open.
- **`Modifier.toggleable(role = Role.Switch)` on a `Row` parent + `Switch(onCheckedChange = null)` as a child** is the canonical M3 shape for a switch row whose tappable region is the whole row (title + supporting text + control). Same shape family as [#254](./254.md)'s `Modifier.selectable(role = Role.RadioButton)` + `RadioButton(onClick = null)` — the parent owns click + a11y semantics; the inner control's handler must be `null` to avoid double-firing. Apply to any future switch-row composable in this codebase. The 8.dp vertical padding (vs. the 4.dp on `ModelRow`) is deliberate — switch rows carry a two-line label so the extra breathing room avoids visual cramping; chip rows stay 4.dp because chips have their own vertical padding inside `FilterChip`.
- **Effort labels reach via the public `Effort.label()` extension in `ui.settings/EffortPickerDialog.kt`, not a duplicate `when` mapping.** Two consumers across two packages (`SettingsScreen`/`EffortPickerDialog` + `StatusSheet`) is the same threshold that triggered the [#253](./253.md) `Model.label()` widening; the rule from `app-preferences.md`'s § Design decision is "co-locate when ≥2 callers ship in the same release window and the strings are vendor-stable". `Effort` labels are vendor-neutral (`low` / `medium` / `high` / `xhigh` / `max` are CLI flag names that don't localise), so the walk-back applies cleanly. **Scoped to `Model` and `Effort` only** — `ThemeMode` still has one consumer and keeps its package-local `internal` extension. Re-evaluate per enum when a second consumer materialises.

## Lessons learned

- **`onCheckedChange = null` on the inner `Switch` inside a `toggleable` `Row` is required, not optional.** Passing the same `onCheckedChange = onToggled` to both the row's `toggleable.onValueChange` and the inner `Switch.onCheckedChange` causes the callback to fire twice — once via the row's hit detection and once via the switch's own click region. The Compose-test `assertEquals(listOf(true), toggles)` assertion catches it (the list contains `[true, true]` instead of `[true]`); the lint-clean shape is `Switch(checked = enabled, onCheckedChange = null)`. Same trap as `RadioButton(onClick = null)` from [#254](./254.md); apply universally to any M3 control wrapped inside a `selectable` / `toggleable` parent.
- **`combine`'s typed overloads top out at five `Flow<T>` arguments — go beyond that and you fall off the type-safety cliff.** Attempting `combine(f1, f2, f3, f4, f5, f6) { a, b, c, d, e, f -> ... }` resolves to the vararg `combine(vararg Flow<*>, transform: (Array<*>) -> R)` overload, which loses compile-time type knowledge on every destructured parameter (each becomes `Any?`). The fix in this slice was the `RunConfig` pre-combine; the same trap caught [#142](./142.md) one slice earlier and got the `TransientDialogs` pre-combine. The right diagnostic move when adding a flow source: count the current arg count in the main `combine` block; if it's at five, plan the pre-combine rather than trying to fit the new flow in directly. The compiler error is opaque (`Type inference failed: ...`); the early-detection signal is the existing arg count.
- **The "dormant `AppPreferences.defaultYolo` flow doesn't leak into the VM" assertion has to be written explicitly — the structural argument isn't enough.** The architect's spec called this out as the AC's load-bearing verification line: `yoloEnabled_initialValueIsFalseRegardlessOfAppPreferencesDefault` pre-calls `prefs.setDefaultYolo(true)`, sanity-checks `prefs.defaultYolo.first() == true`, then constructs the VM and asserts `state.value.yoloEnabled == false`. Without the explicit pre-set, the test would pass trivially because the data-store default is `false` — the assertion-without-pre-set verifies "the VM defaults to false" but **not** "the VM ignores the preference". The mirror-image test `yoloEnabled_remainsFalseWhenAppPreferencesDefaultYoloChanges` similarly proves the negative (`prefs.setDefaultYolo(true)` mid-stream does not flip the VM field). The lesson: when an architectural decision says "X explicitly ignores Y", write the test that would fail if X started reading Y, not the test that would pass either way.
- **`assertIsNotSelected` paired with `assertIsSelected` pins both halves of the selection semantics in one test method.** The existing `selected_row_reports_selected_semantics` from [#254](./254.md) only asserted the positive case (`assertIsSelected` on the selected row); this slice's `selected_effort_chip_reports_selected_semantics` adds the sister negative assertion (`assertIsNotSelected` on a non-selected chip). The negative-pinning surfaces a regression that the positive-only test would miss: an over-broad `selected = true` on all chips (e.g. if `selected = effort == selectedEffort` got corrupted to `selected = true`) keeps `assertIsSelected` green but fails `assertIsNotSelected`. Apply to any selection-state Compose test going forward.
- **Two `label` extensions on different receiver types in the same import scope resolve unambiguously by receiver — Kotlin doesn't need disambiguation aliases.** `ThreadScreen.kt` now imports both `de.pyryco.mobile.data.preferences.label` (`Model.label()`) and `de.pyryco.mobile.ui.settings.label` (`Effort.label()`) at the top of the file; the call sites `state.selectedModel.label()` and `state.selectedEffort.label()` each resolve to the unique extension whose receiver matches. The temptation during the implementation was to import one with `as modelLabel` / `as effortLabel` for clarity, but the resolution is already unambiguous and the alias would only add reader load. Same pattern would scale to a third `label()` extension on a third type — Kotlin's receiver dispatch handles it as long as no two extensions share the receiver type within the same import scope.
