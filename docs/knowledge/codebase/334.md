# #334 — live CameraX preview in the scanner viewport + decode drives stub-pair

The **live-camera** slice of the pairing scanner: the success producer #333 deferred. Binds a CameraX
`Preview` + a parallel `ImageAnalysis` (feeding the existing `QrCodeAnalyzer` unchanged) to the
composable's lifecycle, rendered **behind** the locked viewport overlay (Figma `13:2`). A real QR scan
now drives the existing **stub-pair persist (#295)** + navigation, replacing the temporary tap
affordance from #326; a camera-bind failure feeds the existing `CameraError → Error` seam instead of a
blank viewport. The decoded string stays **untrusted external input** — routed into the stub persist
(which writes the constant `STUB_PAIRED_SERVER`) but **not** parsed/validated/persisted-as-content
(#320) and **not** identity-confirmed (#321).

## Summary

Four production files (one new) + one instrumented test file. **All UI-layer** — camera is an Android
UI concern, kept out of portable `data/` per CLAUDE.md. **No `data/` change, no DI change, no manifest
change** (the `CAMERA` permission + non-required `camera.any` feature were declared in #326), and **no
`ScannerViewModel` change** — both the `QrDecoded → Decoded` success seam (#333) and the
`CameraError → Error` failure seam (#326) already existed with no live producer; this slice is their
producer. The architectural lever keeping `ScannerScreen` testable without a physical camera is a
**camera-preview slot**: the screen stays a stateless `when(state)` renderer and the route injects the
real CameraX composable through a `cameraPreview: @Composable () -> Unit = {}` parameter (tests default
it to `{}`).

## Files touched

- **`ui/onboarding/CameraPreview.kt`** *(new, 105 LOC)* — the live-camera composable. Public contract
  `CameraPreview(onQrDecoded: (String) -> Unit, onCameraError: (String) -> Unit, modifier: Modifier = Modifier)`:
  - **`PreviewView` via `AndroidView`**, `Modifier.fillMaxSize()`, with
    `implementationMode = PreviewView.ImplementationMode.COMPATIBLE`. **Load-bearing for AC1** — the
    default `PERFORMANCE` mode backs the preview with a `SurfaceView` in a separate window that ignores
    the parent `clip(RoundedCornerShape(24.dp))` and punches through the over-drawn reticle/gradient
    overlay. `COMPATIBLE` uses a `TextureView`, which composites **in-hierarchy** so the rounded-corner
    clip and the atmosphere/reticle drawn on top render correctly.
  - **Background analysis executor:** `remember { Executors.newSingleThreadExecutor() }` — the analyzer
    runs here (off-main, required by #333's `Tasks.await` contract: it blocks/throws on the main
    thread). `shutdown()` in `onDispose`.
  - **Fresh analyzer per composition entry:** `remember { QrCodeAnalyzer(onQrDecoded = { currentOnQrDecoded(it) }) }`
    — constructed once per `CameraPreview` composition, so the once-per-scan latch resets on each
    scanner entry (the re-scan reset #333 deferred here).
  - **`rememberUpdatedState`** wraps `onQrDecoded`/`onCameraError` so the long-lived analyzer and the
    bind-future listener always call the *current* lambda — the route allocates fresh slot lambdas on
    every recomposition, and this indirection is what makes that safe (no stale capture, no re-bind).
  - **Binding** in `DisposableEffect(Unit)`: `ProcessCameraProvider.getInstance(context)` (a
    `ListenableFuture`); on its listener — run on `ContextCompat.getMainExecutor(context)` — build a
    `Preview` (`setSurfaceProvider(previewView.surfaceProvider)`) + an `ImageAnalysis`
    (`STRATEGY_KEEP_ONLY_LATEST`, `setAnalyzer(analysisExecutor, analyzer)`), then `provider.unbindAll()`
    and `provider.bindToLifecycle(lifecycleOwner, CameraSelector.DEFAULT_BACK_CAMERA, preview, imageAnalysis)`.
    `bindToLifecycle` ties camera start/stop to the lifecycle (AC2). The whole bind is wrapped
    `try { … } catch (_: Exception) { currentOnCameraError(CAMERA_BIND_ERROR_MESSAGE) }` (AC4). The
    listener runs on **main** but only builds/binds use cases — it never calls `Tasks.await` (the
    analyzer does, on the background executor).
  - **Cleanup:** `onDispose { runCatching { cameraProviderFuture.get().unbindAll() }; analysisExecutor.shutdown() }`
    — releases the camera + executor on composition exit (e.g. on `Decoded`/navigation/back). Lifecycle
    stop is already handled by `bindToLifecycle`; `unbindAll` covers the composition-exit case.
  - **`LocalLifecycleOwner` imported from `androidx.lifecycle.compose`** (the
    `androidx.compose.ui.platform` one is deprecated and trips `lint { abortOnError = true }`).
  - **`private const val CAMERA_BIND_ERROR_MESSAGE = "Couldn't start the camera. Paste the pairing code instead."`**
    — fixed, detail-free. The caught exception is **never** interpolated (AC5 / security: no
    device/stack leak into the `Error` UI).

## Patterns established

- **Camera-preview slot keeps a device-bound screen unit-testable.** `ScannerScreen` stays a pure
  stateless `when(state)` renderer; the real CameraX composable is injected through a
  `cameraPreview: @Composable () -> Unit = {}` parameter that **defaults to `{}`**, so every Compose
  test drives every state with no physical camera, and the route is the only place that knows about the
  camera. The route additionally **gates the slot on `ReadyToScan`** (`if (state is ReadyToScan) CameraPreview(…)`),
  so the camera binds only in the one state that should hold a live feed — `PermissionRequesting`
  (behind the system dialog) and `Decoded` (handing off) render the same viewport with an empty slot.
  This is the reusable shape for "a stateless screen needs a piece of Android-only, hard-to-fake UI."
- **`COMPATIBLE`/`TextureView` to composite a CameraX preview *under* a Compose overlay + rounded clip.**
  The default `PERFORMANCE`/`SurfaceView` lives in a separate window and ignores both the parent
  `clip(RoundedCornerShape)` and any sibling drawn on top — it punches through. Any future in-Compose
  camera/video surface that must sit behind an overlay or inside a clip should set `COMPATIBLE`.
- **Move atmosphere from `Box.drawBehind` into a `matchParentSize` child to layer it *over* a back-most
  child.** `Modifier.drawBehind {}` on a `Box` paints behind **all** children, so introducing a
  back-most child (the camera) under content that was drawn via the Box's own `drawBehind` requires
  relocating that draw into a `matchParentSize` sibling placed after the back-most child. The draw is
  byte-for-byte identical; only its position in the layer stack changes.
- **`rememberUpdatedState` around long-lived callbacks fed by freshly-allocated route lambdas.** The
  `remember`ed analyzer and the `DisposableEffect(Unit)` bind listener outlive a recomposition; the
  route hands `CameraPreview` brand-new `onQrDecoded`/`onCameraError` lambdas each recomposition.
  Wrapping them in `rememberUpdatedState` lets the long-lived collaborators call the current lambda
  without re-binding the camera. (The MVI seam means those lambdas only do `vm.onEvent(...)`, so even a
  stale one would be harmless — but the idiom is the correct default and documents intent.)
- **A terminal `UiState` drives a one-shot side effect via `LaunchedEffect(state)` + a self-removing
  nav.** `Decoded` → `stubPairAndNavigate`, where the navigation pops the source destination
  (`popUpTo(SCANNER){inclusive=true}`) so the keyed effect cannot re-fire. Cleaner than a nav callback
  threaded back through the screen for a state that is, by construction, reached once per scanner entry.

## Lessons learned

Lifted from [PR #340](https://github.com/pyrycode/pyrycode-mobile/pull/340)'s *Lessons learned* + the
code-review NITs:

- **Compose lint (`abortOnError`) requires `modifier` to precede a trailing `@Composable () -> Unit`
  slot param.** The spec's draft signature listed `cameraPreview` *before* `modifier`, which fails
  `lintDebug` (the `ComposeModifierMissing` / parameter-ordering family wants `modifier` first among the
  defaulted params, slot lambda last). Put `modifier` first among defaulted params and the slot lambda
  last: `(…, modifier: Modifier = Modifier, cameraPreview: @Composable () -> Unit = {})`.
- **`onDispose` re-fetches the provider via `cameraProviderFuture.get()` on the main thread** (NIT,
  accepted). If disposal races the very first camera-HAL init (fast back-out before `getInstance`
  completes), `.get()` can *briefly* block the UI thread; `runCatching` guards exceptions but not the
  block. This is the canonical CameraX-in-Compose idiom and the spec prescribed it — no leak/crash, so
  non-blocking. If ever revisited: capture the resolved `provider` into a remembered nullable in the
  bind listener and null-check it in `onDispose` instead of re-`get()`ing.
- **`CAMERA_BIND_ERROR_MESSAGE`'s second sentence duplicates the recovery button** (cosmetic NIT,
  accepted). `ScannerErrorContent` shows the message directly above a `TextButton` labelled "Paste the
  pairing code instead", so "Couldn't start the camera. Paste the pairing code instead." repeats the
  button. The spec prescribed this exact string; shortening to "Couldn't start the camera." would read
  cleaner. Left as-is this slice.
- **Threading constraint from #333 honoured, not re-derived:** the analyzer is bound on a background
  `Executors.newSingleThreadExecutor()`; the provider-future listener runs on `getMainExecutor` and only
  builds/binds — `Tasks.await` stays off-main. Getting this backwards (binding the analyzer on the main
  executor) would throw at the first decoded frame.

## Verification

- `./gradlew check` ✅ (unit tests + Android lint + spotless) · `./gradlew assembleDebug` ✅ ·
  `./gradlew compileDebugAndroidTestKotlin` ✅ (the androidTest source set compiles). **`connectedAndroidTest`
  not run — no device/emulator** in the build environment; the new `cameraPreviewSlot_rendersBehindLockedOverlay`
  test needs a device, and `CameraPreview` itself is un-unit-tested by design (needs a physical camera /
  `ProcessCameraProvider` — mocking the bind chain has negative value; its collaborators are covered by
  #333's `QrCodeAnalyzerTest` and #326's `ScannerViewModelTest`).
- **Code review: PASS** (two cosmetic NITs above, neither blocking). All 4 ACs verified; blast radius
  (codegraph) confirmed all 11 `ScannerScreen(` call sites migrated `onTap`→`onNavigateBack` with no
  remnants, `CameraPreview` a fresh symbol with no collision, `ScannerViewModel` untouched.
- **Security review: PASS** (ticket carries `security-sensitive`). The untrusted QR payload is **not**
  read by the pairing handler — `stubPairAndNavigate` persists the constant `STUB_PAIRED_SERVER` and
  navigates a fixed route (parse/validate is #320/#321). Bind-failure message is a fixed private const,
  caught with `catch (_: Exception)` and **never** interpolated; deterministic grep
  (`grep -rn 'Log\.\|Timber' app/src/main/java/de/pyryco/mobile/ui/onboarding/`) returns nothing in the
  camera/decode path, and the redacting `toString()` on `Decoded`/`QrDecoded` (#333) remains. No new
  exported component, manifest change, network, crypto, or file I/O. Live-camera threat model: the
  viewfinder shows only what the camera points at (a QR the user is deliberately scanning); the decoded
  payload is never rendered; the pairing trigger moved tap→decode, so a transparent-overlay tap can no
  longer force a pair.
