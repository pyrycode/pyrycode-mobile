# Ticket #614 — e2e: pin and report the interactive runner in the harness (isolated-HOME only)

**Issue:** [#614](https://github.com/pyrycode/pyrycode-mobile/issues/614) ·
**Spec:** [`docs/specs/architecture/614-e2e-pin-report-interactive-runner.md`](../../specs/architecture/614-e2e-pin-report-interactive-runner.md) ·
**PR:** [#616](https://github.com/pyrycode/pyrycode-mobile/pull/616) (`b10f474`) ·
Split from #587. Size **S**, `security-sensitive` (architect self-review PASS). Code review **PASS**,
2 NITs, both non-gating. Bash + docs only — no Kotlin.

## Summary

The daemon's interactive runner (`pty` vs `stream-json`) is selected from `interactive_runner` in
`$HOME/.pyry/config.json` — no flag exists, and `resolveConfigPath()` is per-**user**, not per-instance,
so `-pyry-name` never namespaces it. `scripts/e2e-emulator.sh`'s LIVE and default-rung-3 modes both run
under the operator's real `HOME`, so before this ticket the live gate silently measured whatever the
operator's own machine happened to have configured — flip the config key for a rollback comparison and
the gate's subject changes with no signal in its output.

This ticket adds `INTERACTIVE_RUNNER=pty|stream-json`: pinnable on the isolated-HOME DETERMINISTIC path
only (seeds `<ISO_HOME>/.pyry/config.json` before the daemon spawns), refused in preflight on any
real-HOME path (LIVE or default rung 3) with an explanation naming why, and *reported* — by reading back
the file the daemon is about to read, in every mode, even when unset or when no config file exists at
all. It deliberately leaves rung 4's actual default runner unchanged; that's #613, parked upstream on a
`fakeclaude` capability gap.

## Files touched

- **`scripts/e2e-emulator.sh`** (+164, insert-only, 0 removed) — `INTERACTIVE_RUNNER` declared in the
  config block; two preflight guards (value-then-mode order, both ahead of the host-binary lookups so
  they fire before anything is spawned or written); the conditional seed write inside the existing step
  2b, `umask 077` + `mkdir -p` + `printf` to `${ISO_HOME}/.pyry/config.json` — one level *above* the
  per-instance `${ISO_HOME}/.pyry/${PYRY_NAME}/conversations.json` seeded three lines above it;
  `resolve_runner_from_config()` (a `python3 -` heredoc, since `python3` is already a hard preflight
  dependency) and `report_interactive_runner()`, called once from a single call site immediately before
  `log "starting pyry daemon…"`, covering all three spawn branches.
- **`docs/e2e-interactive-stream.md`** (+71) — new `## Interactive runner selection` section (placed
  after the Deterministic-mode block, before `## Verification status`) covering accepted values,
  DETERMINISTIC-only pinning, the real-HOME refusal, and the every-mode read-back reporting; one
  cross-reference line added to step 2 of "What the host does (deterministic seams)".

The LIVE branch (`:380-386`, the deliberate `PYRY_ALLOW_INSECURE_RELAY`-omission that enforces its TLS
posture) is untouched — the reporting call sits before the mode branches and the guard prevents the seed
write from ever reaching that branch at all.

## Load-bearing design choices

- **Report by reading back, never by echoing the request.** `report_interactive_runner()` always reads
  the config file from disk after (or instead of) writing it, rather than printing
  `${INTERACTIVE_RUNNER}` directly. This is what makes the mechanism self-verifying: if the seed ever
  landed one directory too deep (the exact path trap the spec calls out), the report would say
  `pty (daemon default — no config file at …)` instead of silently going green on the wrong runner.
- **Two preflight guards, value-then-mode order.** Validating the accepted set (`pty` / `stream-json`)
  before checking DETERMINISTIC vs real-HOME means `INTERACTIVE_RUNNER=ptty LIVE=1` reports the typo,
  not the mode error — AC1 requires the typo check to be unconditional, and this ordering is what makes
  it so (verified explicitly in both the PR's test matrix and code review).
- **The resolver never aborts, even under `set -e`.** The Python side catches every exception and always
  prints exactly one `"<runner>\t<reason>"` line with exit 0 — required because the real-HOME paths read
  a file the harness doesn't own, and an unreadable/malformed config there must be a report (`unknown`),
  not a new failure mode for paths that work today.
- **A non-string `interactive_runner` value gets its own branch**, not folded into "unset/default" —
  see Lessons learned below.
- **Reported values are clamped to a closed four-token set** (`pty` / `stream-json` / `unrecognised` /
  `unknown`); the raw file value is echoed only when it matches the accepted set. This was specified as
  the fix for a possible terminal-escape injection from a config file the harness doesn't control (noted
  SHOULD-FIX in the architect's self-review, not gating since unobserved) — no extra code beyond what the
  resolver's table already does.

## Patterns established

Nothing new at the Kotlin/architecture level — this ticket is confined to the bash harness. The
resolve-by-read-back idiom (verify the effect actually landed by re-reading the artifact under test,
rather than trusting the write succeeded) is worth reusing in any future harness change that seeds
config the daemon reads exactly once at startup.

## Lessons learned

- **A non-string `interactive_runner` is a parse failure, not a default.** Upstream decodes the field
  into a Go `string`, so `{"interactive_runner": true}` fails `config.Load` outright and the daemon
  refuses to start. The obvious `if not isinstance(value, str) or value == ""` collapses that case into
  the "unset" branch and reports `pty (daemon default)` — naming a runner the daemon will never actually
  reach. It needed its own `unknown` branch, separate from the empty-string case.
- **A guard placed after the host-binary preflight checks is untestable on a machine without those
  binaries on PATH.** The `INTERACTIVE_RUNNER=bogus` guard has to sit *before*
  `command -v "${RELAY_BIN}"` / `command -v "${PYRY_BIN}"`, or a dev machine missing those binaries dies
  at the binary lookup first and the guard is never exercised (in dev or in CI). Pure argument checks
  belong ahead of environment checks generally, and it's also what AC1's "typo takes priority over mode
  error" ordering requires.
- **Stubbing the three external binaries (`pyrycode-relay`, `pyry`, `gradlew`) into a scratch copy of the
  repo is the cheap way to dry-run this harness end-to-end without an emulator.** A `gradlew` stub that
  exits 1 makes the `cleanup` trap keep `ISO_HOME` around instead of deleting it, so the seeded tree can
  be inspected directly — `find "$ISO_HOME" -name config.json` is what actually proved the seed lands at
  `.pyry/config.json` and not `.pyry/<PYRY_NAME>/config.json`. Full end-to-end verification in this repo
  is otherwise ~1s instead of requiring a booted emulator.

## Verification

- `spotlessCheck`, `lint`, `assembleDebug` green (no Kotlin changed, so these are unaffected-by-construction
  checks, not exercises of the new code). `bash -n` and `shellcheck -S warning` clean on the harness.
- No Gradle gate touches shell at all, so the new surfaces were exercised directly (see PR #616 body for
  the full matrix): the resolver against 11–12 synthetic configs (missing file, absent/empty key, both
  accepted values, unrecognised value, non-string value, malformed/non-object JSON, unreadable file,
  ANSI-escaped value) — all exit 0, one line each, survive `set -e`; the five preflight/report scenarios
  from the spec's testing table, including the ordering check (`ptty LIVE=1` → typo, not mode error) and
  the pre-existing `LIVE=1 DETERMINISTIC=1` mutual-exclusion guard still winning.
- **AC3 no-write guarantee proven, not asserted:** `shasum -a 256 ~/.pyry/config.json` identical
  (digest, size, mtime, mode) across all real-HOME-path runs, `relay_url` still present. Code review
  independently confirmed the seed's write target derives only from `${ISO_HOME}` (a fresh `mktemp -d`)
  and never from `$HOME`, so the guard and the path are different fabric — a bypassed guard still could
  not land a write on the real HOME.
- The full rung-4 emulator suite was **not** run (needs a booted emulator, out of scope for a harness-only
  change); a pinned `stream-json` rung-4 run is not expected to go green end-to-end (that gap is #613).
- Code review PASS with 2 non-gating NITs: a cosmetic `HOME`-unresolvable fallback-path mismatch vs
  upstream (unreachable — bash always exports `HOME`, and DETERMINISTIC sets it explicitly), and a
  suggestion to add a `## Verification status` line for the new host-verifiable-without-emulator surface
  (not an AC5 requirement — AC5 asks for semantics, which the new doc section covers).
