# #438 — send `modal_answer` + `modal_cancel` control messages

The **outbound (data-out) half** of the permission/choice modal feature (Phase 3 of epic pyrycode#597,
ADR 025; split from #428 → [#437](./437.md) decode / **this** answer-send / #439 render UI / #440
read-only mode). Adds the two **phone → binary** control messages that answer or cancel a modal surfaced
by #437: two concrete suspend methods on `RemoteConversationRepository` that echo the #437-decoded
`modalId`/`optionId` back over the encrypted v2 wire. **Send + ack/error correlation only** — no render,
no read-only degrade. Mirrors [`registerPushToken`](../features/remote-conversation-repository.md#registerpushtokentoken--the-device-concern-push-registration-359)
(#359) exactly: a concrete-only outbound control method wrapping `sendAndAwaitReply` (#346).

See [Remote conversation repository § `answerModal` / `cancelModal`](../features/remote-conversation-repository.md#answermodal--cancelmodal--the-v2-modal-answercancel-control-send-438)
for the full design rationale; this file records what shipped, the line refs, and the lessons.

## Summary

- Two new **concrete** suspend methods on `RemoteConversationRepository` (NOT on the
  `ConversationRepository` interface, the `StableConversationRepository` facade, or the Fake — the
  `registerPushToken` posture): `answerModal(modalId, optionId)` sends
  `modal_answer{modal_id, option_id, answer_token}`; `cancelModal(modalId)` sends
  `modal_cancel{modal_id}`. Each builds an `Envelope` (id `requestId.incrementAndGet()`,
  `Clock.System.now()` ts, `MobileJson.encodeToJsonElement(dto)` payload) and awaits its correlated
  reply via `sendAndAwaitReply` (#346) — the empty `{}` `ack` is ignored, an `error`/not-`Open` session
  throws. **Zero new correlation infra.**
- `answer_token` is minted by a **pure** `private fun answerToken(modalId, optionId): String =
  "${modalId.length}:$modalId:$optionId"` — a deterministic, length-prefixed encoding of the answer's
  identity. No stored state, no random, no clock: purity is what gives **AC#2** by construction —
  **stable** across a retry of the same logical answer (same pair → same token → daemon dedups the
  replay to a no-op) and **distinct** across distinct answers (both ids participate). The length prefix
  makes it **injective** over opaque ids that may contain the `:` separator (`("a:b","c")` → `3:a:b:c`
  vs `("a","b:c")` → `1:a:b:c`).
- `modalId`/`optionId` are echoed **verbatim** — neither parsed nor validated (decoded by #437; the
  daemon validates `modalId` against its own outstanding modal first-answer-wins, maps `optionId`
  against its own option list — pyrycode#701/#703/#706). The phone asserts only *which* modal and
  *which* offered option, never a conversation.
- New encode DTOs in `data/network/ModalOutboundPayloads.kt` (the encode mirror of #437's decode DTOs):
  two `@Serializable internal data class`es in one file. Two `TYPE_*` constants join the companion.
  Purely additive — no existing signature changed, **zero edit fan-out** (no interface/facade/Fake/DI
  touch).
- 10 new unit tests in `RemoteConversationRepositoryTest.kt`, test-first RED→GREEN, templated on the
  `registerPushToken` quartet.

## Patterns established

None new — this slice deliberately reuses the `registerPushToken` (#359) outbound-control pattern
end-to-end (a concrete-only public suspend method building an `Envelope` and awaiting `sendAndAwaitReply`,
an encode-only `internal` DTO, the empty `ack` ignored, an `error`/not-`Open` throw inherited, no
projection mutation). It does, however, **establish one reusable design call** worth following:

- **A client-minted idempotency key should be a pure, collision-free *derivation* of the action's
  identity — not a random value plus a remembered cache.** The next outbound control needing a
  retry-stable token (a wire-required dedup key whose only properties are *uniqueness* + *stability*, with
  secrecy a non-goal — pyrycode#701) should derive it from its inputs, not mint-and-cache. The derivation
  is *stronger* than a UUID cache for the stability AC (stable across process death, zero mutable state,
  no eviction/lifecycle question) and avoids coupling the slice to the inbound resolution stream just to
  know when to evict. Use a random token only when the key must be **unpredictable** (secrecy a goal) —
  which it explicitly is not here.

## Lessons learned

- **The `answer_token` idempotency key needs no random + cache.** Deriving it as a pure, collision-free
  function of `(modalId, optionId)` gives AC#2's stability *and* uniqueness by construction, since the
  token's entire information content **is** the answer's identity. The token being derivable from the
  other two fields is *not* redundancy to remove — the wire requires the field present as the daemon's
  dedup key, and a random token would carry *less* principle (it needs external state to recover the
  stability that is already implicit in the inputs). (Lifted from the PR's Lessons-learned.)
- **The length-prefix injectivity is *deliberate* and *untested* — guard it if you ever touch the
  encoding.** `modalId`/`optionId` are opaque and may contain the `:` separator, so the modal id is
  length-prefixed (`"${modalId.length}:$modalId:$optionId"`) to keep `("a:b","c")` and `("a","b:c")` from
  aliasing to the same token. **No test exercises that case** — every test id is colon-free and UUID-ish,
  so a future refactor to a naive `"$modalId:$optionId"` join would pass the whole 10-test suite while
  silently reintroducing the collision (code-review NIT on [PR #442](https://github.com/pyrycode/pyrycode-mobile/pull/442)).
  It was left as an **optional** guard rather than added, by Evidence-Based Fix Selection: real
  `modal_id`s are daemon-minted nonces (colon-free), so the alias is practically unreachable — but if you
  change the encoding, add the one-line `answerToken("a:b","c") != answerToken("a","b:c")` assert that
  locks the invariant the code goes out of its way to provide.
- **`modal_cancel` carries no idempotency token (asymmetry with `modal_answer`).** Cancel is not
  idempotency-keyed (pyrycode#701 shape `{modal_id}`); a re-cancel of an already-resolved modal is a
  stale-`modal_id` reject the daemon handles, so there is no mobile-side dedup to mint. Don't "complete
  the symmetry" by adding a cancel token — it isn't on the wire.
