Phase-3 **UI** half of the queued-message backlog (epic pyrycode#597). Split from #462 (itself split from
#429). Size **S**, **not** `security-sensitive`. Was natively `blockedBy` [#458](458.md) (interrupt-send) to

branch cut, so the spec was designed against the merged ViewModel.

## Summary

The **user-facing drop action** that completes the queued-message backlog loop. The data path already
existed: [#460](460.md) decodes `queue_state` into [`observeQueue`](../features/queued-backlog.md), [#461](461.md)
renders it as the de-emphasized [`QueuedBacklog`](../features/queued-backlog-section.md) foot-of-list section,
and [#466](466.md) added the data-layer send [`dropQueuedMessage`](../features/queued-backlog.md). This slice
wires a **per-row trailing drop affordance** → a thread-ViewModel event → that already-built repository
method:

```
QueuedBacklog row  ──onDrop(id: Long)──▶  ThreadScreen.onDropQueued  ──MainActivity vm::onDropQueued──▶
    ThreadViewModel.onDropQueued(id)  ──viewModelScope.launch──▶  repository.dropQueuedMessage(conversationId, id)
                          (no local state mutation; fire-and-forget) │
   next queue_state ──▶ observeQueue ──▶ ThreadUiState.queuedMessages ──▶ row disappears
```

The list update is **free** — it rides the existing `observeQueue` render path with **no optimistic
mutation**: the dropped row leaves only when the daemon broadcasts the next `queue_state`. The VM handler
mirrors [`sendInterrupt`](../features/interrupt-send-path.md)'s catch contract exactly, so a failed drop is
inert (AC #4). Code review **PASS**, zero blocking findings.

## Load-bearing design choices

- **No new ViewModel ctor param — the [#466](466.md) facade-method placement pays off here.** Because
  `dropQueuedMessage` carries a `conversation_id`, #466 deliberately put it on the `ConversationRepository`
  **interface** (the `requestScreenSnapshot` precedent) rather than the concrete-only injected-lambda shape
  used for `answerModal` / `cancelModal` (which key off `modal_id` only). So `onDropQueued` calls
  `repository.dropQueuedMessage(...)` on the facade the `ThreadViewModel` already holds — no constructor
  lambda, no coordinator passthrough, no Koin wiring. Choosing the interface method one ticket upstream made
  this consumer slice a pure surface-and-wire job.
- **Catch contract mirrors `sendInterrupt` exactly — `CancellationException` rethrow FIRST.** On the JVM
  `kotlinx.coroutines.CancellationException` extends `IllegalStateException`, so the
  `catch (CancellationException) { throw e }` arm **must precede** the typed catches or a bare
  `catch (IllegalStateException)` would swallow structured cancellation ([[catch-illegalstate-swallows-cancellation]]).
  Then `RelayErrorException` (server error — e.g. stale / already-drained id) and `IllegalStateException`
  (not connected / pre-Open) are swallowed inert (AC #4). **No error surface** — unlike the modal send
  ([#451](451.md), which exposes `modalSendErrors`), a failed drop is a silent no-op: AC #4 asks only that it
  not crash and not mutate the backlog.
- **No optimistic removal (AC #3 / AC #5).** `queuedMessages` stays a pure projection of `observeQueue` inside
  the existing five-arm `state` combine — the VM's only effect is the wire send, so there is deliberately
  nothing to roll back. The disappearance is a separate, **server-driven** event that rides the already-shipped
  #460/#461 render path; the two are uncoupled in the VM.
- **`IllegalArgumentException` (`conversation.not_found`) deliberately NOT caught.** The VM always passes its
  own valid `conversationId`, so the unknown-id throw cannot occur on the real path — same posture as
  `sendInterrupt` / `sendMessage` (which pass `conversationId` with no try/catch at all). Adding a catch would
  defend an unobserved race (Evidence-Based Fix Selection). Code-review flagged this as a **non-blocking**
  awareness note, not a change request.
- **Material-default visual (design-owed).** The Figma `16-8` frame still draws no queued-backlog section and
  no drop affordance (code-review re-fetched the node and confirmed), so per spec this is a Material-default
  treatment, not a pixel match: a trailing `IconButton` + `Icons.Outlined.Close` tinted `onSurfaceVariant` —
  the conventional "remove from a list" affordance. `Close` (×, *un-queue*) over `Delete` (trash, *delete*):
  a queued message is un-queued, not destroyed. `IconButton` supplies the ≥48dp tap target. Trivially
  re-tunable when the visual lands (the same posture #461 / `ThinkingIndicator` / `StallPromotionBanner` took).

## Patterns established

- **A per-row list affordance whose action is a fire-and-forget facade send needs no new VM ctor param.**
  When the underlying op is a `ConversationRepository` interface method (the #466 / `requestScreenSnapshot`
  placement), the consumer slice is pure MVI surface-and-wire: hoist `onDrop(id)` through the stateless
  component → defaulted `ThreadScreen` param → `MainActivity vm::` binding → a VM handler that calls the
  already-injected `repository`, mirroring the screen's other swallow-on-failure sends
  ([`sendInterrupt`](../features/interrupt-send-path.md)). Reach for this whenever a row-level action triggers
  a per-conversation send that is already on the interface.

## Lessons learned

- **A `mergeDescendants = true` a11y group does NOT absorb a clickable child — the drop button stays
  addressable in the unmerged tree.** `QueuedBacklog`'s Column sets `mergeDescendants = true` for its section
  a11y group, but each clickable `IconButton` forms its **own** semantics merge boundary, so the per-row drop
  nodes stay individually addressable via `onAllNodes(hasContentDescription(dropCd), useUnmergedTree = true)`
  — the same `useUnmergedTree` access #461's per-row-**text** assertions already use. (Lifted from the
  [PR #470](https://github.com/pyrycode/pyrycode-mobile/pull/470) *Lessons learned*; extends [#461](461.md)'s
  merged-descendants lesson from text to interactive affordances.)
- **The inert-swallow test false-greens on call-count alone — capture uncaught exceptions.** The drop runs in
  a `viewModelScope.launch`, so a throw that escapes the typed catch propagates to the **default uncaught
  handler**, not into `runTest` — a `dropCalls.size == 1` assertion alone would pass even if the swallow were
  broken. The AC #4 test captures via `Thread.setDefaultUncaughtExceptionHandler` and asserts `uncaught.isEmpty()`
  (restoring the previous handler in `finally`), the only proof the catch actually ran — the same #458-class
  guard ([[430-interrupt-split]]).
