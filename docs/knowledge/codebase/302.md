# #302 — WS transport process-lifecycle: close on background, reconnect on foreground/push

The **Phase 4 transport-lifecycle layer**: a thin, stateless driver that decides **when** the relay
connection should be alive, sitting on top of the [reconnect supervisor](../features/relay-reconnect-supervisor.md)
([#307](307.md)) which decides **how** to dial/reconnect. Background → `close()`, foreground/push-wake →
`connect()`. Split from #276; depends on [#306](306.md) (transport) + [#307](307.md) (supervisor), both
landed.

See the feature doc [`lifecycle-connection-driver.md`](../features/lifecycle-connection-driver.md) for the
evergreen "how the driver works / what plugs into it" reference. This file is the implementation record.
**No new ADR** — no new state type, no transport, no network; the design choices (interface-not-concrete
seam, eager-Koin wiring, `connect()`-not-`retry()` for push) are scoped to this layer and captured below +
in the feature doc, same no-ADR posture as #306/#307.

## Scope

**A lifecycle driver that calls two existing supervisor methods on two lifecycle edges + a push-wake entry
point.** Out of scope, by design and named in the spec:

- **The reconnect/backoff loop and `ConnectionState` mapping** — that's the supervisor ([#307](307.md)).
  This ticket never touches the raw transport ([#306](306.md)) or its reconnect loop directly; driving the
  raw socket would fight the supervisor's own reconnect loop.
- **Noise re-handshake on each fresh socket** — the sibling pump ([#309](https://github.com/pyrycode/pyrycode-mobile/issues/309)). "There is no Noise here."
- **FCM push-token registration + token plumbing** — a separate future ticket. This ticket wires only the
  **wake edge** (`onPushWake()`); deciding *when* to re-close a push-opened background connection is the
  FCM ticket's job (it needs the push payload/intent).
- **A new `ConnectionState` type / banner change** — the state surface ([#196](196.md)) and the
  [`ConnectionBanner`](../features/connection-banner.md) (#200) visuals are unchanged; this ticket changes
  only *which* state is published across lifecycle edges.

## Summary

**One new production file** (`lifecycle/LifecycleConnectionDriver.kt`, ~30 LOC) + a co-located
**portable interface** (`RelayConnectionController` added to `RelayConnectionSupervisor.kt`) + **one Koin
edit** (an eager `single`), verified by **one new JVM test file** (`LifecycleConnectionDriverTest.kt`,
7 `@Test`). **One new dependency** (`androidx.lifecycle:lifecycle-process` for `ProcessLifecycleOwner`, at
the existing `lifecycleRuntimeKtx = "2.6.1"` ref).

The load-bearing facts, all test-pinned:

1. **`onStart` → `connect()`, `onStop` → `close()`, `onPushWake()` → `connect()`.** A
   `DefaultLifecycleObserver` on `ProcessLifecycleOwner` (the whole-app foreground/background signal that
   does **not** fire on config changes). The driver is **stateless** — no `StateFlow`, no mutable fields
   beyond its two injected deps; the supervisor remains the single connection-state source.
2. **Push-wake = the foreground path.** `onPushWake()` calls `connect()`, identical to foregrounding
   (AC 3). Because `connect()` is idempotent, it's correct whether foreground (loop running → no-op) or
   background (loop idle → starts), so the driver needs **no foreground/background bookkeeping**.
3. **Narrowed seam `RelayConnectionController` (portable).** A two-method, data-parameter-free interface
   (`connect()`/`close()`) declared in `data/network` alongside its only implementor, so the platform
   `lifecycle` package depends **inward** and the driver test needs only a recording double. The supervisor
   gains the interface + `override` ×2 — bodies unchanged.
4. **All AC-4 non-overlap / unpaired-idle / not-`Offline` guarantees are delegated to the supervisor.** The
   driver re-implements none of them: `connect()` idempotency, `close()` full teardown, the unpaired gate,
   and `close()` → `Connected` (not `Offline`) all already shipped in #307. The driver's only contract is
   "each background pairs with `close()`, each foreground with `connect()`."
5. **Eager Koin wiring, no `PyryApp` change.** `single(createdAtStart = true) { … .also { it.start() } }`
   constructs the driver at `startKoin` (main thread, `Application.onCreate`) and registers the observer
   immediately. Reuses the **dormant** supervisor singleton via `get<RelayConnectionSupervisor>()` upcast
   to `RelayConnectionController` — no `bind` change. Resolvable so a future FCM service can `get()` it.
6. **Zero logs.** No `Log`/`Timber`/`println` — mirrors the #306/#307 posture.

  7 `@Test`) — JVM-only. In-file doubles: a recording `FakeRelayConnectionController` (ordered
  `Call.Connect`/`Call.Close` list) and a `FakeLifecycleOwner` wrapping
  `LifecycleRegistry.createUnsafe(this)` with `foreground()` (`ON_CREATE`→`ON_START`) / `background()`
  (`ON_STOP`) helpers. No virtual clock (the driver launches no coroutines). Scenarios: foreground →
  `[Connect]`; background → `[Connect, Close]`; bg-then-fg → `[Connect, Close, Connect]`; cold start
  (`ON_CREATE`→`ON_START`) → `[Connect]`; push-wake-while-backgrounded → one extra `Connect`, **no** extra
  `Close`; rapid toggle ×3 → strictly alternating `[Connect, Close]×3` (asserted via `zipWithNext` — no two
  consecutive identical edges); and `start()` is what registers the observer (events before `start()` reach
  nothing, then `start()` syncs to the current `STARTED` state → `Connect`).

## Patterns established

- **Narrow the concrete service to a portable interface at the platform boundary.** When a platform-only
  driver (here `androidx.lifecycle.*`) needs to call into a portable service, extract a minimal,
  data-parameter-free interface (`RelayConnectionController`) **in the portable package** and have the
  platform layer depend on that — dependencies point inward, and the driver test gets a trivial recording
  double instead of standing up the full service with its fakes + clock. The interface lives beside its
  canonical implementor, not in a separate "contracts" package. (Same fakes-over-MockK spirit as #307.)
- **Eager Koin singleton as a self-registering app observer (`createdAtStart = true`).** For a
  lifecycle/app-scoped side-effect object that must register at process start, a `single(createdAtStart =
  true) { … .also { it.start() } }` constructs-and-registers it at `startKoin` without touching the
  composition root (`PyryApp`/`Application`). Keeps the wiring in one place (`AppModule`) and leaves the
  object resolvable for later callers (the future FCM service `get()`s it for `onPushWake()`).
- **Idempotent entry point = no foreground/background bookkeeping in the driver.** Because the supervisor's
  `connect()` is idempotent, the push-wake path can be **literally** the foreground path (`connect()`) with
  no "am I already connected?" state in the driver. Push a guarantee down to the layer that owns the state,
  and the caller above it stays stateless.

## Lessons learned

- **`LifecycleRegistry.createUnsafe(owner)` is the zero-dependency lifecycle test seam.** It's the
  test-only factory that **skips the main-thread check**, so a plain JVM unit test can drive
  `handleLifecycleEvent(ON_CREATE/ON_START/ON_STOP)` without a real `ProcessLifecycleOwner`, Robolectric,
  or instrumentation — and **without** adding `androidx.lifecycle:lifecycle-runtime-testing`
  (`TestLifecycleOwner` was the considered alternative; `createUnsafe` won as the zero-dep default). Reach
  for it whenever you need to test a `LifecycleObserver` on the JVM.
- **`ProcessLifecycleOwner` needs its own artifact.** `androidx.lifecycle:lifecycle-process` is **not**
  pulled in transitively by `lifecycle-runtime-ktx` (which the project already had) — the
  `ProcessLifecycleOwner` import fails to resolve until you add it explicitly. Easy to miss because the
  other `lifecycle-*` modules are already present.
- **Driver `start()` syncs to the *current* lifecycle state on `addObserver`.** Registering an observer
  doesn't just subscribe to future events — `Lifecycle` immediately walks the new observer up to the
  owner's current state. So if the process is already `STARTED` when `start()` runs (e.g. a late
  registration), `onStart` fires synchronously → `connect()`. This is exactly the cold-start behavior we
  want (`addObserver` at `startKoin`, then the process advances to `STARTED` as `MainActivity` starts), and
  the `withoutStart_…` test pins it.

## Verification

- `./gradlew test` (7 `LifecycleConnectionDriverTest` cases + full suite), `./gradlew spotlessCheck`,
  `./gradlew lint`, `./gradlew assembleDebug` — all green (per the PR). `connectedAndroidTest` **not run** —
  JVM-only driver, no device required (same posture as #306/#307). No CI configured on the repo (consistent
  with the project phase).
- **Code review: PASS.** All 5 ACs verified met; the architect security-review (Verdict **PASS**) is in the
  spec — the driver crosses no untrusted boundary, `RelayConnectionController` is data-parameter-free
  (payload-free `onPushWake()`), zero log statements, and the background-close is net-positive for the
  battery/privacy threat model (closes the idle authenticated socket). No new exported Android component
  (`Activity`/`Service`/`BroadcastReceiver`), no manifest change, no `PendingIntent`.
