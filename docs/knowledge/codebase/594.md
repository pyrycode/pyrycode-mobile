# Ticket #594 — render claude's API-retry status (attempt N/M) in the thread

**Issue:** [#594](https://github.com/pyrycode/pyrycode-mobile/issues/594) ·
**Spec:** [`docs/specs/architecture/594-api-retry-status-render.md`](../../specs/architecture/594-api-retry-status-render.md) ·
**PR:** [#599](https://github.com/pyrycode/pyrycode-mobile/pull/599) (`51a4f4d`) ·
**Feature doc:** [API-retry indicator](../features/api-retry-indicator.md) ·
Split from #582. The visible reaction to sibling data slice [#593](593.md) (PR #595, `022c0b8`), which
this consumes and was natively blocked on. Size **S**, `security-sensitive` (architect self-review
**PASS**).

## Summary

Renders #593's already-decoded `api_retry` projection in the thread, so a multi-minute retry storm is no
longer indistinguishable from normal reasoning. `ThreadViewModel.apiRetry` hoists `observeApiRetry` as a
sibling `StateFlow` — a verbatim clone of `isStalled` — and `ThreadScreen` gains a defaulted `apiRetry`
parameter that arbitrates the single foot-of-list status slot: the retry status wins whenever active, so
it and the generic thinking spinner never render stacked, and the retry shows regardless of what
`turn_state` says (the signal is conversation-level, not turn-scoped). The new `ApiRetryIndicator` clones
`ThinkingIndicator`'s M3 idiom and owns the one new decision this slice introduces — a display sanity gate
that declines an unrenderable counter (`0/0`, `9/3`, `1/2147483647`) in favour of a counter-less
"Retrying…" status rather than clamping it, preserving the carry-verbatim posture #593 chose at decode.
No repository, interface, or DI change — four production `.kt` files plus the coverage-doc entry, exactly
the shape sized against #396/#406. All gates green; code review **PASS** (1 non-gating SHOULD FIX, 1 NIT).

## Load-bearing design choices

- **Precedence lives in `ThreadScreen`, not `ThreadViewModel`.** `isThinking` is kept as a pure
  `turn_state` reduction; the either/or that decides which status wins is a screen-level rendering
  decision. Suppressing `isThinking` at its source to fold in the retry signal would make the VM's
  contract lie to the tests that assert `isThinking` directly.
- **Render-or-decline, never clamp (AC #2).** `isRenderableCounter()` is a narrowing gate — a counter is
  displayed verbatim or not displayed at all, never rewritten. Clamping would re-import at the display
  layer exactly the server-data rewrite #593's mapper refused to do at decode, breaking the carry-verbatim
  posture every sibling mapper (`stall`, `queue_state`, `turn_state`) shares.
- **`ApiRetryStatus` staying Compose-unstable is correct**, confirmed in code review: marking it
  `@Immutable` would pull a Compose annotation into `data/repository/`, which CLAUDE.md's data-layer
  portability rule (no Android/Compose assumptions in `data/`) forbids. The status flows through a plain
  `StateFlow<ApiRetryStatus>` and recomposes correctly via structural equality regardless.
- **No shared spacing-constant file with `ThinkingIndicator`.** `ApiRetryIndicator` declares its own
  private padding/spinner/gap `val`s rather than importing `ThinkingIndicator`'s — deliberate, per
  CLAUDE.md's "don't refactor adjacent code while you're there" and the `StallPromotionBanner` precedent
  of the same non-sharing choice.

## Patterns established

Nothing genuinely new at the architecture level — this slice is explicitly the third instance of the
early-return / sibling-`StateFlow` / defaulted-hoisted-parameter / merged-`semantics` / design-owed-M3
pattern `ThinkingIndicator` (#406/#407) and `StallPromotionBanner` (#396) already established. Two points
worth carrying forward for the next status-affordance ticket:

- **A single foot-of-list slot can be arbitrated by an either/or at the screen, keyed off a sibling
  domain-typed `StateFlow`**, rather than collapsing two signals into one flag. This is the template for
  any future status that needs to *replace* (not stack with) an existing affordance in the same slot —
  contrast `StallPromotionBanner`, which lives in an independent slot and co-renders freely.
- **A render-or-decline display gate belongs next to the component it renders for, private and named,
  with its bound rationale in the KDoc** — not folded into the upstream mapper, and not exposed as a
  config value. #593 explicitly deferred this exact fix to this ticket at review time; the shape it took
  (a single 3-condition boolean predicate, `1..total && total <= 99`) is the template for any future
  display-side sanity gate over an otherwise-trusted-but-hostile-daemon-reachable counter.

## Lessons learned

- **`onNodeWithText` on a merged semantics tree can hide a label behind an explicit
  `contentDescription`.** For the "no unusable counter reaches the screen" negative assertions (AC #2),
  the test runs with `useUnmergedTree = true` so the raw label `Text` can't be masked by the merged
  node's description. The unmerged tree can only ever find *more* nodes than the merged one, so it's the
  strictly stronger check for any *absence*-of-text claim against a `semantics(mergeDescendants = true)`
  component — worth defaulting to for that class of assertion generally, not just here.
- **Spotless collapses a multi-line single-expression function onto one line even past 120 chars.**
  `private fun …isRenderableCounter(): Boolean =` with a hand-wrapped body was reformatted to a 126-char
  single line by `spotlessApply`, and `spotlessCheck` fails on the pre-wrapped form. Write
  single-expression bodies inline and let spotless arbitrate the line length rather than pre-wrapping.
- **The spec's premise that #396 was androidTest-only turned out to be false, and mattered.** `isStalled`
  actually has 3 plain-JVM unit tests in `ThreadViewModelTest.kt` (`:1207`/`:1216`/`:1235`) from #396's
  own PR, contradicting the spec's "no new `test/` unit test" framing. This slice shipped without an
  equivalent JVM test for the `apiRetry` hoist, so — unlike `isStalled` — the hoist and the display-gate
  interplay live *only* in the device-gated rung-2 tests, outside the mandatory (non-device) pipeline.
  Flagged in code review as a non-gating SHOULD FIX with the fix deferred to whatever ticket next touches
  `ThreadViewModelTest.kt`'s `apiRetry`-adjacent coverage — do not assume a UI-render slice needs no JVM
  test purely because it clones a component precedent; check the precedent's actual test files, not its
  ticket description.
- **`ThreadScreenChannelInfoTest.delete_confirm_dialog_displays_title_and_body`** fails on a pre-existing
  2-node "Test channel" text collision, unrelated to this diff — reproduced identically on `main` at
  `c41af0a` in a clean `git worktree add --detach` scratch checkout before concluding it wasn't caused by
  this change, then filed as [#598](https://github.com/pyrycode/pyrycode-mobile/issues/598) rather than
  fixed inline. The `…ui.conversations.thread` androidTest package baseline is 85 tests / 1 known
  pre-existing failure as of this ticket.
