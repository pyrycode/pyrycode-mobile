# #498 — Drain the stale retry signal before a fresh backoff

**Issue:** [#498](https://github.com/pyrycode/pyrycode-mobile/issues/498) ·
**Spec:** [`docs/specs/architecture/498-drain-stale-retry-signal-before-backoff.md`](../../specs/architecture/498-drain-stale-retry-signal-before-backoff.md) ·
**PR:** [#519](https://github.com/pyrycode/pyrycode-mobile/pull/519) ·
**Feature doc updated:** [Relay reconnect supervisor](../features/relay-reconnect-supervisor.md) ·
Size **XS**, **not** security-sensitive (pure timing — no untrusted input, no key material). Commit `7dd9438`.

## Summary

Fixes a backoff-timing defect in [`RelayConnectionSupervisor`](../features/relay-reconnect-supervisor.md)
([#307](307.md)). `retry()` writes `Unit` into a **CONFLATED** channel (`retrySignal`, `:80`), whose sole
job is to *collapse a backoff wait that is happening now*. But when `retry()` is called while the loop sits
inside `transport.events.collect` (**`Connected`** — no receiver waiting on the signal), the `Unit` **buffers**
in the channel with nothing to consume it. On the *next* drop, the first `collapsibleWait` (`:223`,
`withTimeoutOrNull(ms) { retrySignal.receive() }`) immediately consumes that stale buffered `Unit` and returns
early — collapsing a backoff that should have waited its full jittered interval.

Observable effect: a tap-to-retry (or a [#302](302.md) lifecycle `connect()`/`retry()`) that arrived during a
*healthy* connection pre-arms the *next* drop's reconnect to fire **instantly** instead of after backoff. LOW
severity, self-correcting on subsequent attempts (only the *first* wait after the drop is shortened). Manifests
only with `USE_RELAY_REPOSITORY` on; filed from the Cross-Repo Code Review 2026-07-03.

The fix drains the channel once at the **top of `backoff()`**, before any of its three wait branches. Of the
ticket's two candidate directions (drain a stale signal vs. only accept the signal while a wait is in progress),
the architect chose **drain** — it discards exactly the stale pre-drop signals and nothing else. One production
statement (`:194`); the rest of the diff is the AC#1 regression test.

**Same subsystem as [#493](493.md) / [#495](495.md) / [#496](496.md)** (the reconnect/backoff lifecycle) — but
unlike those, this is *pure timing*: no async clear outliving its scope, no crypto, no untrusted wire byte.

## The fix

One statement at the head of `backoff()` (`:194`), before the `daemonAbsent` check:

```kotlin
private suspend fun backoff(attempt: Int, daemonAbsent: Boolean) {
    // Drain any stale retry signal buffered while no wait was in progress (#498): a retry() issued
    // during a healthy connection (loop inside events.collect) leaves a Unit in the CONFLATED
    // retrySignal with no receiver. Discarding it here — before the first collapsibleWait — stops
    // it pre-collapsing this fresh backoff. A retry() arriving *during* a wait lands after this
    // drain, so it still collapses the wait as intended (AC#2).
    while (retrySignal.tryReceive().isSuccess) { /* discard a stale pre-drop signal */ }
    val base = backoffBaseSeconds(attempt)
    // … daemonAbsent (:197) | sub-cap per-second loop (:205) | cap (:214) — all three follow the drain
}
```

- `tryReceive()` is **non-suspending and never throws** on an empty channel (returns a failed `ChannelResult`);
  `retrySignal` is never closed in this class's lifetime, so only the empty case ever occurs — **no error surface**.
- `CONFLATED` holds at most one element, so a single `tryReceive()` is logically sufficient; the `while` loop is
  the robust, intent-revealing form (drains regardless of channel capacity) and costs at most one extra no-op poll.
- **Placement is load-bearing.** The drain is at the **top of `backoff()`**, not inside `collapsibleWait()`.
  `collapsibleWait` runs *per-second* in the sub-cap countdown loop (`:205-213`); draining there would eat a retry
  that arrives *during* a multi-second countdown → **breaks AC#2**. At the top of `backoff()` it runs exactly once
  per drop, before the first `receive()`, so it can only ever remove a signal that predates *this* `backoff()` call.

**Why AC#2 (retry *during* a wait still collapses) is preserved:** the drain completes *before* `collapsibleWait`
suspends on `receive()`. A retry arriving *during* the wait is `trySend`'d *after* the drain has already run, so
it lands in the channel while `receive()` is (or is about to be) suspended on it → collapses the wait exactly as
before. The drain provably removes only pre-`backoff()` signals.

**Why `retry()` itself is untouched (AC#3):** the fix is entirely on the consume side. `retry()` stays
`connect()` (idempotent) + `retrySignal.trySend(Unit)` (`:121-124`) — non-blocking, never throws, by construction.

## Patterns established

- **A CONFLATED signal channel is only meaningful while a receiver is waiting — drain it at the head of the
  consumer before its first `receive()`.** The `retrySignal`'s entire contract is "collapse the wait that is
  happening *now*." A `Unit` buffered while no wait was in progress (the loop was inside `events.collect`, or in
  the `Connecting` window before `Up`) is stale by definition — the retry's `connect()` half already did its job
  and there was no backoff to collapse. Draining at the consumer's entry point discards exactly those, and the
  conflation guarantees there is at most one to discard. This is the deterministic-code counterpart to the
  conflation semantics: conflation coalesces a *burst* of taps into one wakeup, but it also *retains* a lone tap
  indefinitely — the drain is what bounds that retention to "this backoff only."

## Lessons learned

- **CONFLATED conflates *and retains*; a buffered signal outlives the window it was meant for.** The bug is a
  direct consequence of the two jobs the CONFLATED channel does: it collapses a burst of `retry()` taps into one
  wakeup (the anti-storm property, wanted), *and* it holds a single un-consumed `Unit` forever until someone
  receives it (unwanted, once the wait it targeted is long gone). A signal channel whose producer can fire while
  no consumer is parked needs an explicit drain at the consumer's entry, or the next consumer inherits a stale
  wakeup. The general shape: *if a `trySend` can happen with no receiver suspended, the receiver must assume the
  buffer may hold a signal that predates its current reason to wait.*
- **The drain's correctness hinges on where it runs, not just that it runs.** Top-of-`backoff()` vs.
  inside-`collapsibleWait()` is the whole ballgame: the former drains once-per-drop (removes only stale signals,
  preserves AC#2); the latter would drain once-per-*second* in the sub-cap countdown and swallow a legitimate
  in-progress retry. When adding a drain to a channel that has *both* a "before the wait" and a "during the wait"
  consumer path, place it strictly before the first `receive()` and never on the per-iteration path.
- **`retry()` consumes no `random`, so the seeded-interval arithmetic is unperturbed by a retry-while-connected.**
  The AC#1 test asserts an *exact* re-dial time via `intervalsFor(1).first()` (the first seeded `nextDouble()`
  interval). Because `retry()` only touches `connect()` + `trySend` and never draws from the jitter RNG, a
  `retry()` issued before the drop does not shift the seeded sequence — the drop's first interval is still
  `intervalsFor(1).first()`. This is why the test can assert exact ms (`advanceTimeBy(interval - 1)` → still
  `Reconnecting`, `advanceTimeBy(1)` → re-dialled) rather than a tolerance band, mirroring the proven
  `repeated4404_staysDaemonAbsent_onTheExistingBackoffSchedule` sibling.

## Accepted boundary (not a defense to build)

Under the multi-threaded production dispatcher (`Dispatchers.Default`), a `retry()` whose `trySend` races into
the sub-microsecond gap between `events.collect` completing and the drain executing could be discarded — costing
one full backoff interval (base-1 ≈ 1 s) before re-dial. This is the **opposite, gentler direction** of the same
LOW/self-correcting class the ticket already accepts, does **not** reproduce under the single-threaded
`StandardTestDispatcher` the tests use (no suspension point in that gap → the drain provably only ever removes
genuinely-stale signals), and adding synchronization for an unobserved race would be over-engineering. Per
**Evidence-Based Fix Selection**, it is left undefended; the architect flagged it, and code review concurred and
put it on the record. Noted here so a future reader understands the boundary, not as a TODO.

## Testing

Unit only (`./gradlew testDebugUnitTest --tests "de.pyryco.mobile.data.network.RelayConnectionSupervisorTest"`;
`./gradlew test lint assembleDebug` all green, `spotlessCheck` clean). `runTest` virtual clock, seeded
`Random(SEED)`, single-threaded `StandardTestDispatcher`, settled with `runCurrent()`. **Confirmed RED against
the un-drained `backoff()` before the fix, GREEN after** (per `CLAUDE.md` § Conventions test-first).
`connectedAndroidTest` not run — pure `data/`-layer change, no instrumented surface (same posture as
[#307](307.md) / [#493](493.md) / [#496](496.md)).

**New — AC#1** (`retryWhileConnected_doesNotShortenFirstBackoffAfterLaterDrop`):

1. `connect(); runCurrent()`; `factory.created[0].emitUp(); runCurrent()` → assert `Connected`.
2. `retry()` **while Connected** (loop inside `events.collect`, no wait in progress); `runCurrent()`. Assert
   **still `Connected`** and `factory.created.size == 1` — `connect()` is idempotent (loop already running) and
   the signal buffers with no receiver, so **no re-dial** while healthy.
3. `factory.created[0].emitDown(); runCurrent()` → assert `Reconnecting(ceil(interval / 1000.0).toInt())` where
   `interval = intervalsFor(1).first()`.
4. `advanceTimeBy(interval - 1); runCurrent()` → assert **still `Reconnecting`** and `factory.created.size == 1`
   (backoff **not** collapsed by the stale signal — **the core assertion**; without the drain this would already
   be `Connecting`/size 2).
5. `advanceTimeBy(1); runCurrent()` → assert `Connecting` and `factory.created.size == 2` (re-dialled **only**
   after the full jittered interval). `supervisor.close()`.

**Regression — AC#2** (`retry_collapsesPendingBackoffWithoutThrowing`, unchanged): the drain runs before the wait
on an empty channel, then the mid-wait `retry()` still collapses. **AC#3 / benign paths**
(`benignUnpaired_doesNotDialAndStaysConnected`, the backoff-progression / stability / 4404 tests): all untouched
and green — the drain is a no-op whenever no stale signal was buffered.

## Review / posture

Code review **PASS** ([PR #519](https://github.com/pyrycode/pyrycode-mobile/pull/519), zero findings — no MUST
FIX, no SHOULD FIX, no NITs). Not security-sensitive, but the touched surface is adjacent to the supervisor's
**anti-reconnect-storm** posture (capped-exponential backoff + `retry()`-doesn't-reset-`attempt` + the CONFLATED
channel): the pre-fix behaviour let one specific edge (a retry while healthy) shorten the *first* wait after a
later drop, so the fix marginally *strengthens* that posture — the full jittered interval is now always honoured.
No new interleaving, no signature change, blast radius zero (`backoff()` is private with a single caller,
`retrySignal` is a private field).
