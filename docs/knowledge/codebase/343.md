# #343 — fingerprint confirm gate before pairing persists

The **security checkpoint** of the QR-pairing flow. Interposes a human-confirmation gate between
#320's parse and the persist: on `PairingParseResult.Success` the `MainActivity` `Decoded` effect now
derives the #342 static-key fingerprint and parks in a new `AwaitingConfirm` VM state **instead of
saving**; a full-screen `PairingConfirmContent` renders the fingerprint verbatim (colon-lowercase-hex,
selectable, content-described) with copy telling the user to compare it against the desktop's
`Static-key fp:` line. The **only** scan-path `save` now runs behind the Confirm button; Decline and
system Back persist nothing and re-arm the scanner. See the evergreen
[Pairing confirm gate](../features/pairing-confirm-gate.md) feature doc.

## Summary

4 modified production files, 0 new (under the ≥5 split gate) — **+408 LOC incl. tests**. One new pure
top-level fn (`serverKeyFingerprint`), one new sealed `ScannerUiState` member (`AwaitingConfirm`), two
new `ScannerEvent` members (`PairingPrepared`, `DeclinePairing`), one new private composable
(`PairingConfirmContent`), and the `Decoded`-binding rewire. No new file, no DI change, no model
change, no new dependency. PO sized S; architect-confirmed S. Design-later (no Figma) — see Lessons.

## Patterns established

- **Confirm is a route-scope callback, NOT a `ScannerEvent`.** The persist is a `suspend save` +
  navigation the VM cannot own (its contract: no `viewModelScope`, no Android types). Confirm is wired
  like `onPasteCode`/`onNavigateBack` — a lambda in the composable mirroring `stubPairAndNavigate`. Only
  Decline (a pure state transition) is an event. This keeps #320's "orchestration lives in the
  composable, the VM stays a pure reducer" split intact; reuse it for any future confirm/persist gate.
- **The fingerprint and the saved record are two fields of one immutable `AwaitingConfirm`** — bound,
  not recomputed. Confirm saves `state.server` (the exact record the displayed `fingerprint` was derived
  from); there is **no path that shows fp(A) but saves B**, no TOCTOU between display and persist. The
  load-bearing review property: the developer must read `state.server`, never re-run the parse/derive
  pipeline at confirm time.
- **Re-validate-to-`null` over let-`require`-throw.** `serverKeyFingerprint` re-checks 32 bytes and
  returns `null` rather than calling `staticKeyFingerprint` (whose `require(size == 32)` *throws*)
  directly — an uncaught throw inside the `LaunchedEffect` coroutine would crash the pairing flow. The
  `null` branch is structurally unreachable for a freshly-parsed `Success` (#320 already proved
  base64-std-of-32-bytes), but this is **deterministic belt-and-suspenders** (different fabric: code,
  not a second stochastic check) that converts the impossible-but-fatal case into the same route-to-Error
  path as a parse failure.
- **`BackHandler` gated on the confirm state.** `BackHandler(enabled = state is AwaitingConfirm)` makes
  system Back behave as Decline (return to scanner, persist nothing) while confirming, and pops normally
  otherwise — so Back can't bypass the gate by popping the whole scanner route to Welcome.
- **Confirm-after-close is a no-op by construction.** `onConfirmPairing` reads the *current* collected
  state via `as? AwaitingConfirm`; if a back/decline already moved state to `ReadyToScan`, the cast is
  `null` and confirm does nothing — **a save cannot fire after the gate closed.** Double-confirm is
  benign (idempotent same-record overwrite + `launchSingleTop`/`popUpTo` nav dedupe); a `Saving` state to
  prevent it was deliberately omitted (Evidence-Based Fix Selection — unobserved, harmless).

## Lessons learned

Lifted from [PR #345](https://github.com/pyrycode/pyrycode-mobile/pull/345)'s *Lessons learned*:

- **Compose lint `ComposableParameterOrder` forces `modifier` before default-valued params.** The spec
  asked for the two new `ScannerScreen` callbacks "after `onPasteCode`, before `modifier`", but the
  project's Compose lint requires `modifier` to precede default-valued params — so `onConfirmPairing` /
  `onDeclinePairing` sit **after `modifier`**, before the trailing `cameraPreview`. All callers use named
  args, so the reorder is safe. (Same lint family that bit the `cameraPreview` slot ordering in #334 —
  see [`codebase/334.md`](334.md).)

Other notes:

- **Design-later, no Figma.** The locked file `g2HIq2UyPhslEoHRokQmHG` has no confirm-pairing /
  fingerprint surface (re-verified 2026-06-01 across all 599 nodes). The security behavior (AC #1–#4) is
  visual-independent and fully specified, so `PairingConfirmContent` is a clean, **deliberately
  non-decorative** Material 3 surface — no atmospheric styling that would pre-empt the eventual design. A
  visual-fidelity retrofit is owed as a follow-up when the view is drawn; the design source re-anchors to
  the new `node-id` then.
- **Instrumented confirm-surface tests compile but were not run** (no emulator/device connected) — they
  pass `compileDebugAndroidTestKotlin`. Same coverage posture as #320/#334: the live-path device smoke is
  manual (scan a `pyry pair` QR → confirm screen → compare fp → Confirm → channel list; Decline/Back →
  scanner re-armed, nothing persisted).

## Verification

- `./gradlew test` + `spotlessCheck` + `lint` + `assembleDebug` — all green (per PR #345). New unit
  tests pass: VM `PairingPrepared`/`DeclinePairing` transitions; `serverKeyFingerprint`
  valid/wrong-len/non-base64/parse→derive seam (pins the pinned vector `32:0b:5e:a9:9e:65:3b:c2`
  byte-for-byte through the base64-std decode).
- **Code review: PASS.** The load-bearing properties verified: the rewired `Decoded` effect no longer
  saves (the only scan-path `save` is `confirmPairAndNavigate`, behind Confirm); the fingerprint↔record
  binding (confirm saves the same immutable `AwaitingConfirm.server` the fp was derived from — no
  re-derive/re-parse); the token never reaches `PairingConfirmContent`; decline/back/derive-failure
  persist nothing; logs emit only fixed category strings + `e.javaClass.simpleName`.
- **Security review: PASS** (architect self-review in the spec; this slice *is* the QR-TOFU MITM
  control). Named-but-out-of-scope: tapjacking/overlay synthesizing a Confirm tap (recommended
  follow-up — obscured-touch filtering at the Activity-window level, a cross-cutting hardening, not a
  one-composable bolt-on); X25519 curve-point validity (Noise_IK layer, #302/#309); the still-ungated
  paste path (`onPasteCode = stubPairAndNavigate` — a future real-paste ticket routes paste through
  parse → `serverKeyFingerprint` → the same gate).
