# #304 — Noise_IK re-key triggers: 1-hour timer + inbound `rekey_request` dispatch (initiator)

The **trigger half** of the mobile re-key loop: wires the two re-key entry points — a session-scoped
**1-hour timer** and an inbound **`rekey_request`** envelope — into the landed [Noise session pump](../features/noise-session-pump.md)
([#309](309.md)), driving the landed in-place re-key mechanism [#303](303.md)
(`writeRekeyInit`/`readRekeyResp`). It **invokes both, re-implements neither** — pure `data/network`
orchestration glue. The mobile mirror of the Go binary's re-key initiator (`pyrycode`
[#450](https://github.com/pyrycode/pyrycode/issues/450) timer + emit / [#454](https://github.com/pyrycode/pyrycode/issues/454)
inbound `rekey_request` discriminator), riding #309's `PumpState.Open` the way Go's rode `V2SessionManager`'s
open state. Split from #299; depends on **#309 / #303 / #306 (all merged)**.

See the feature doc [`noise-session-pump.md`](../features/noise-session-pump.md) for the evergreen "how
the pump works / how re-key fits" reference (its § open-state dispatch, § re-key triggers, and § state +
concurrency now cover the trigger surface). This file is the implementation record. **No new ADR** —
consumes [ADR 0004](../decisions/0004-vendor-noise-java-crypto.md) (vendored `noise-java` suite) and
[ADR 0005](../decisions/0005-okhttp-websocket-engine.md) (OkHttp WS) via #303/#306/#309; aligns with
pyrycode-side ADR 024 § Re-key policy. `security-sensitive` — the asset is the encrypted transport across
the rotation, the device static key `s` re-obtained per re-key, and the new/old CipherStates.

## Scope

**The trigger wiring only — two entry points + the completion route.** Sized **S**, kept whole. All
production changes land **inside** `NoiseSessionPump.kt` + one additive helper on `NoiseSessionFactory.kt`:
**no new exported type, no new public class/interface, no DI change** (the one new ctor param is defaulted
and the sole construction site is the test). Out of scope, by design and named in the spec:

- **The re-key *mechanism*** (the fresh IK handshake + atomic CipherState swap + peer-static continuity) —
  [#303](303.md). This ticket calls `writeRekeyInit`/`readRekeyResp`; it does not re-implement the swap.
- **A phone-side re-key reply timeout** (the mobile analog of Go #450's 30 s window) — deliberately
  **omitted** (evidence-based: no observed stuck-session). On a reliable ordered WS/TCP transport every
  failure mode converges on teardown → #307 reconnect without an explicit timer (see Patterns). A bounded
  `withTimeoutOrNull` re-key window is the fix *if* a stuck re-key is ever observed.
- **`reason`-specific behavior** (`compromise` → force re-pair / security banner) — the payload is not
  decoded; discriminating on `type` alone is the whole forward-compat story. A future consumer decodes
  `reason` tolerantly when it needs it.
- **#302 lifecycle wiring** — the pump still ships dormant (no Koin binding); #302 constructs it per
  connection and passes the default `rekeyIntervalMs`. Unchanged by this ticket.

## Summary

**Two production source files modified** (`NoiseSessionPump.kt` → 300 lines, ~+82; `NoiseSessionFactory.kt`
→ 74 lines, +16), verified by **one extended JVM test file** (`NoiseSessionPumpTest.kt` → 776 lines,
**11 new `@Test` → 25 total**). **Purely additive: zero edit fan-out** (the new ctor param is defaulted;
`reloadDeviceStaticKey` is new; `writeRekeyInit`/`readRekeyResp` had no prior consumers — this pump is
their first, confirmed by `codegraph` callers → none). No new dependency (`kotlinx.coroutines.sync.Mutex`
already in use). No new logs.

The load-bearing facts, all test-pinned:

1. **Two triggers, one funnel, serialised + coalescing.** Both entry points call one
   `private suspend fun initiateRekey()` (`NoiseSessionPump.kt:230-253`), guarded by a `rekeyMutex: Mutex`
   so the timer coroutine and the `rekey_request` handler are mutually exclusive — `writeRekeyInit`'s
   `check(pendingRekey == null)` can never trip from a double-initiate; the second caller sees
   `rekeyInFlight == true` and **coalesces** (the mobile analog of Go #450's `skipped_already_awaiting`).
2. **The 1-hour timer is one-shot, session-scoped, re-armed only by a completed handshake.**
   `rebaseRekeyTimer()` (`:213`) cancels any armed job and launches a fresh `delay(rekeyIntervalMs) →
   initiateRekey()` in the pump scope. Called from exactly two points, **both in the single drive
   coroutine** (so `rekeyTimerJob` has no race): on reaching `PumpState.Open` (`:164`, the
   handshake-completion arm) and after a successful `readRekeyResp` (`:204`, the re-base-from-swap). The
   interval is `REKEY_INTERVAL_MS = 3_600_000L` (1 h, `protocol-mobile.md` § Re-key); injected small in
   tests via the new defaulted ctor param.
3. **The inbound `rekey_request` is intercepted at the producer, never forwarded.** In `onOpenFrame`'s
   `noise_msg` branch, after the existing decrypt + `Envelope` parse, `envelope.type == TYPE_REKEY_REQUEST`
   → `scope.launch { initiateRekey() }` (`:187-191`) and is **not** sent to `inboundChannel` — #278 never
   sees transport-control envelopes, and the single-consumer `inbound` contract is honoured by intercepting
   at the producer rather than adding a second collector. Launched (not awaited inline) so the keystore
   re-load can't stall the collector.
4. **The re-key `noise_resp` completes the swap via the open-state seam — it does not tear down.** A new
   `TYPE_NOISE_RESP` branch (`:197-205`, the documented #304 seam #309 left in `onOpenFrame`'s `when`,
   before the `else`): a `noise_resp` with no re-key in flight throws (`if (!rekeyInFlight) throw …
   "unexpected noise_resp with no re-key in flight"` — protocol violation → teardown); otherwise
   `readRekeyResp(base64StdDecode(frame.data))` swaps in the new keys, `rekeyInFlight = false`, and the
   timer re-bases. **No `rekey_ack` is sent** — the next successful AEAD round-trip under the new keys is
   the implicit ack.
5. **The device static `s` is re-loaded per re-key and zeroed in a `finally` with no preceding suspension.**
   The new `NoiseSessionFactory.reloadDeviceStaticKey()` (`:61`) re-supplies `s`; `initiateRekey` zeroes
   its copy (`s.fill(0)`, `:250`) regardless of outcome. There is **no suspension point** between the
   re-load returning and the `finally`, so a cancelling teardown cannot skip the wipe; `session.close()`
   independently wipes the session's copy inside `pendingRekey` (belt-and-suspenders). The bounded
   device-key RAM window #298/#303 fought for is preserved across **every** hourly re-key. **The coalesce
   check precedes the re-load** (`if (rekeyInFlight || …) return@withLock` is the first statement under the
   mutex), so a flood of coalesced nudges never even loads `s`.
6. **A re-key `noise_resp` MAC failure (rotated `rs` / relay MITM) tears the session down.** `readRekeyResp`
   throws `NoiseSessionException`, which the drive coroutine's existing `catch` routes to `teardown` → #307
   reconnects with a fresh full handshake. #303's fail-RETAIN keeps the old keys valid right up to
   `session.close()`, so **no half-swapped state is ever observable**.

## Patterns established

- **Two triggers → one funnel, serialised by a `Mutex` + coalescing on a `@Volatile` flag.** When several
  independent producers can initiate the *same* one-at-a-time operation, route them through a single
  `suspend` funnel under one mutex and coalesce on a flag set inside the lock — the second caller skips,
  not double-initiates. Here it protects #303's `check(pendingRekey == null)` (a double-initiate would be a
  caller bug → `IllegalStateException`). The mobile analog of Go #450's `skipped_already_awaiting`. The
  flag is set **inside the lock, before the observable side-effect** (the `noise_init` send), so by wire
  causality (the `noise_resp` cannot arrive before the server reads the `noise_init`) plus `@Volatile`
  visibility, the single sequential collector always reads `true` when the matching resp arrives. *General
  rule: set the in-flight flag before the event that can race its observation, under the same lock that
  serialises the initiators.*
- **Coalesce-before-side-effect ordering is security-load-bearing, not just an optimisation.** The coalesce
  check is the **first** statement under the mutex, *before* `reloadDeviceStaticKey()`. A flood of
  authenticated `rekey_request` nudges therefore never even loads the high-value device static `s` — no
  extra RAM exposure, no amplification (each real re-key still needs a full round-trip the server must
  complete). Ordering the cheap coalesce guard ahead of the expensive/sensitive load is what makes the
  nudge-flood benign.
- **Re-supply the high-value secret per use, zero it in a suspension-free `finally` (carried from #303,
  realised here).** The pump is the "future pump" #303's decision (B) named: it re-loads `s` via the new
  `reloadDeviceStaticKey()` for each re-key and zeroes its copy in a `finally` with **no suspension point**
  between the load and the wipe — so cancellation/teardown cannot skip it — backed by `session.close()`
  independently wiping the session's copy in `pendingRekey`. Caching `s` on the multi-hour pump would have
  re-resident the phone's long-term identity in RAM and defeated the bound on every hourly rotation.
- **Intercept a transport-control message at the producer, not via a second collector.** `rekey_request` is
  decrypted in the *one* inbound collector and acted on there (`scope.launch { initiateRekey() }`) — never
  forwarded to the single-consumer `inbound`. Adding a second collector would fight #306/#309's
  single-consumer contract; intercepting at the producer keeps #278 free of transport-control envelopes.
  *When a single-consumer stream carries both domain and control messages, branch at the sole producer.*
- **The re-key `noise_init` sends outside the outbound ordering lock — deliberately.** `outboundLock`
  guards the encrypt→enqueue pair so wire order == AEAD nonce order; the re-key `noise_init` carries **no**
  transport-AEAD payload (it is a raw handshake frame, and the protocol explicitly permits app `noise_msg`
  traffic to interleave with the re-key handshake on the *current* keys until the swap). Taking
  `outboundLock` across the suspend `reloadDeviceStaticKey()` would needlessly couple the re-key to
  outbound. *The ordering lock is for nonce-ordered AEAD frames only; handshake frames are outside it.*
- **Pump *policy* on top of #303 *mechanism*: teardown-on-rekey-MAC-failure uses fail-RETAIN, doesn't
  fight it.** #303's `readRekeyResp` is fail-RETAIN so the *mechanism* never corrupts itself (old keys
  intact, re-key retryable) — it leaves the response *policy* to the pump. In the open state the only
  legitimate `noise_resp` is one completing the re-key against the pinned `rs`; a MAC failure means the
  peer is not the pinned `rs` (rotated key / MITM), so the pump **tears down** (→ #307 reconnect with a
  fresh full handshake), mirroring its existing "an undecryptable frame tears the session down" rule.
  Fail-RETAIN is still load-bearing: it keeps the old keys valid right up to `session.close()`, so no
  half-swapped state is observable. (Belt-and-suspenders, *different fabric*: the mechanism's deterministic
  retain underwrites the pump's teardown policy.)
- **Type-only discriminator for forward-compat — don't decode what you don't act on.** Discriminating on
  `Envelope.type == "rekey_request"` alone (the payload `reason` is never decoded) makes an unknown /
  absent / extra `reason` value *impossible* to crash on — the AC's forward-compat clause is satisfied by
  construction, not by a tolerant decoder. YAGNI: a future `reason`-consuming ticket decodes it then.

## Lessons learned

Lifted from the PR's *Lessons learned* section:

- **A test fake that returns the *same* mutable secret buffer each call breaks once a second consumer
  zeroes its copy.** The pump-test `FakeDeviceStaticKeyStore` previously handed back the **same**
  `DeviceStaticKeyPair` instance every `loadOrCreate`. `NoiseSessionFactory.create()` zeroes its copy of
  the private key after the constructor copies it into the DH state — so the per-re-key
  `reloadDeviceStaticKey()` (a *second* load) would hand back a now-**zeroed** scalar and the re-key
  handshake would silently run on all-zero `s`. Fix: the fake hands out a **fresh copy per call**
  (`privateKey.copyOf()`), matching the real `KeystoreDeviceStaticKeyStore` contract (which mints a new
  buffer each call — exactly so a caller zeroing its copy never corrupts the stored key). *When a store
  hands out a caller-owned, caller-zeroed buffer, its test fake must mint a fresh copy per call too — a
  shared-instance fake hides a use-after-zero the moment a second consumer appears.*
- **A small injected timer interval re-fires under `advanceUntilIdle()` after a completed re-key.** With
  the re-key timer armed on a tiny test interval, `advanceUntilIdle()` *after* completing a re-key also
  drives the **re-based** timer to fire (one more `noise_init`) — so an assertion like "no extra frame sent
  after the `noise_resp`" (the no-`rekey_ack` check) must process the resp with `runCurrent()`, **not**
  `advanceUntilIdle()`, to avoid advancing the virtual clock past the re-based boundary. *Under
  `runTest`, use `runCurrent()` to settle an event without advancing time; reserve `advanceTimeBy` /
  `advanceUntilIdle` for genuine waits — a re-armed one-shot timer will fire if you over-advance.*
