# Ticket #609 — decode `unrecognized_message` and fold it into the thread

**Issue:** [#609](https://github.com/pyrycode/pyrycode-mobile/issues/609) ·
**Spec:** [`docs/specs/architecture/609-decode-unrecognized-message.md`](../../specs/architecture/609-decode-unrecognized-message.md) ·
**PR:** [#619](https://github.com/pyrycode/pyrycode-mobile/pull/619) (`0fdc1dd`) ·
**Feature doc:** [Unrecognized message row](../features/unrecognized-message-row.md) ·
Split from #585. Blocked by #608 (landed, PR #612). Blocks #586. Size **S**, `security-sensitive`
(architect self-review **PASS**).

## Summary

Adds the decode arm and thread fold for the daemon's `unrecognized_message` wire frame, so a claude
message the interactive daemon's stream-json parser could not map now reaches the thread as the
`ThreadItem.UnrecognizedMessage` row #608 shipped, instead of being silently discarded by the inbound
demux's `else -> Unit`. #608 built the destination type and row; this slice is purely the decode-and-fold
— no UI changed. Spec followed verbatim; no rework.

## Patterns established

Nothing new — this ticket is a deliberate clone of `session_transition`'s decode-arm/decoder/fold shape
(#578), the same "clone, don't generalize" call #597 and #601 already made for their sibling arms. The
one addition to the established repertoire: **a client-owned row-id counter is sufficient when it's
scoped correctly.** `unrecognizedRowId` is a plain `AtomicLong` (mirroring `requestId` for idiom
consistency, not because concurrency demands it — the inbound demux is a single collector), and its
uniqueness guarantee rests on three structural facts rather than the counter itself: the repository is
connection-scoped (#351), `StableConversationRepository.observeMessages` uses `flatMapLatest` so a
reconnect drops the previous connection's projection outright, and no reader ever observes rows from two
instances merged. Ordinals may be skipped (a `site`-rejected frame still consumes an
`incrementAndGet()`) — the invariant is uniqueness, not density. Any future frame needing a client-stamped
row id can reuse this reasoning rather than re-deriving it.

## Lessons learned

- **A JSON-string test fixture needs `buildJsonObject`, not the file's usual raw-string interpolation.**
  `raw` is a wire field that is itself a JSON blob carried as a plain `String`. Interpolating it into the
  test envelope's usual `"""{"raw":"$raw"}"""` pattern breaks on the first embedded quote and silently
  produces a malformed payload — the test ends up probing the wrong thing. Build it with
  `buildJsonObject { put(...) }` instead.
- **Asserting a `Clock.System.now()`-stamped field needs a time window, not a non-null check.**
  `occurredAt` is a non-nullable `Instant`, so "assert it's non-null" is vacuous — it can't be anything
  else. Sample `Clock.System.now()` on either side of the push and assert the stamp falls inside that
  window instead; this is the pattern to reuse for any future client-stamped timestamp field.
- Confirms the ticket's known false-green: kotlinx's tree decoder accepts a quoted primitive
  (`{"truncated": "true"}`) even at `isLenient = false`, so the malformed-payload test must use a
  genuinely wrong shape (missing field / wrong type), not a stringified boolean.
