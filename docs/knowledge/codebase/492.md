# #492 — Hoist the current-modal projection to the process-scoped coordinator

**Issue:** [#492](https://github.com/pyrycode/pyrycode-mobile/issues/492) ·
**Spec:** [`docs/specs/architecture/492-hoist-modal-projection-process-scoped.md`](../../specs/architecture/492-hoist-modal-projection-process-scoped.md) ·
**PR:** [#510](https://github.com/pyrycode/pyrycode-mobile/pull/510) ·
**Feature docs updated:** [Current-modal state](../features/current-modal-state.md),
[Relay repository coordinator](../features/relay-repository-coordinator.md), [Modal events](../features/modal-events.md) ·
Size **S**, `security-sensitive`. Commit `76862f7`.

## Summary

The "which modal is open" projection (`ModalUiState`) was folded **per-thread-screen** inside
[`ThreadViewModel`](../features/thread-screen.md) ([#445](445.md)), whose collection only began when a
thread screen was navigated onto the back stack. The daemon can raise a permission/choice modal while the
app shows the channel list (or is closed). The coordinator's [`modalEvents`](../features/modal-events.md)
seam is `replay = 0`, so a `modal_shown` fired **before any subscriber existed** was dropped — the prompt
stayed outstanding daemon-side while the phone rendered nothing. This blocks flipping
`USE_RELAY_REPOSITORY`; it manifests only with the relay repository live.

This relocates the fold **once, to the process-scoped [`RelayRepositoryCoordinator`](../features/relay-repository-coordinator.md)**
(started `Eagerly` for the coordinator's process-lifetime scope, mirroring `currentRepository` /
`connectionStatus`), so the projection accumulates whether or not a thread screen is subscribed. The
ViewModel now **re-exposes** the coordinator's `StateFlow<ModalUiState>` verbatim instead of folding the raw
event stream itself. `arm / answer / cancel` behaviour — and its tests — is unchanged. It is an atomic
relocation of an existing, already-tested fold (VM → coordinator) plus its type move: net **negative**
production LOC (the coordinator gains a ~6-line fold; the VM deletes a ~26-line fold).

## The layering decision (the "decide first" the filing flagged)

The coordinator lives in `data/` and cannot see `ui/conversations/thread/`, where `ModalUiState` + its
pure `reduce` used to live. `reduce` is a **pure function with no Android/UI dependency** — it imports only
`ModalEvent` / `ModalOption`, both already in `data/model`. Resolution: **move the whole `ModalUiState.kt`
file to `data/model`** and let the coordinator own the fold. `data/model` is the correct home — it already
holds the sibling projection type `ConnectionStatus` and the source `ModalEvent`/`ModalOption`, and the
type stays portable (no Android import, honouring the Compose-Multiplatform walk-back constraint).

**Rejected alternative** (per the ticket's layering note): expose coordinator state as raw `ModalEvent` and
re-fold in the VM. That forks the fold logic, and re-folding a `replay = 0` stream in a screen-scoped VM
**re-introduces the exact drop bug** this ticket fixes. Not done.

## The teardown decision (security-relevant): RETAIN, not reset

A process-scoped fold outlives connection churn. **Decision: the projection retains its last value across
`teardownActive` (connection drop) — no reset to `Hidden`.** This is the natural behaviour of the `scan`
downstream of `flatMapLatest` (between connections `activeRemoteRepo` is `null → emptyFlow()`, so no event
flows and `scan` holds its last accumulator).

- **Retaining is safe** because the answer path is guarded by *deterministic code*, not the projection:
  `coordinator.answerModal` / `cancelModal` throw `IllegalStateException` when no connection is active, which
  the VM catches and surfaces as a one-shot `modalSendErrors` snackbar — **no answer is ever sent on a dead
  connection**. `modalId`s are unique per modal instance, so even on a *fresh* connection a stale answer
  cannot match a new modal (daemon rejects the unknown `modalId` → `RelayErrorException` → same one-shot
  error). Belt-and-suspenders with **different fabric**: the projection is UI state; the guard is
  deterministic code (the pairing pattern established by [#490](490.md)).
- **Clearing would be worse.** Resetting to `Hidden` on a transient drop would blank a still-outstanding
  modal, and — absent a *confirmed* daemon replay-on-reconnect for already-observed modals (the replay
  cursor advances past seen events, so re-raise is **not** guaranteed) — it would not come back,
  re-introducing the exact "outstanding daemon-side, phone shows nothing" bug.
- Net effect of a stale `Open` after a drop: at worst a cosmetic lingering prompt that a subsequent
  `modal_shown` (last-shown-wins) or a replayed `modal_dismissed` supersedes. Never a confidentiality or
  integrity defect.

## Patterns established

- **Hoist a `replay = 0` fold to the process-scoped layer when the event can precede the subscriber.** A
  screen-scoped `scan`/`stateIn` over a `replay = 0` seam drops any event fired before the screen mounts.
  When the source outlives the screen (here: the daemon raises modals while the app is on the channel list
  or closed), fold **once** at the process-scoped coordinator — the layer that already owns the
  reconnection-surviving seam and outlives any screen — and have the screen VM re-expose the hoisted
  `StateFlow` rather than re-derive it. This is the same "accumulate a `replay=0`-derived stream `Eagerly`
  so `.value` is always the true current projection" precedent as `currentRepository` / `connectionStatus`.
- **A pure fold with no Android dependency belongs in `data/model`, so the data layer can own it.** When a
  projection type + its `reduce` need to move from `ui/` to a data-visible package to let a `data/` owner
  fold it, `data/model` is the home (portable, Compose-Multiplatform-safe) — do a `git mv` + one package
  line so git records a rename and every importer is updated atomically (a move cannot relocate a symbol
  without touching its definition and every importer in the same commit).
- **Teardown = RETAIN when a deterministic guard already prevents the unsafe action.** A process-scoped UI
  projection that outlives connection churn should hold its last value, not reset, when a *separate
  deterministic code path* (the `answerModal`/`cancelModal` null-guard + unique `modalId`) already makes
  acting on a stale value fail-closed. Belt-and-suspenders with different fabric (the [#490](490.md)
  pairing): don't reset UI state to defend a failure the deterministic guard already covers.

## Lessons learned

- **`SharingStarted.Eagerly` (not `WhileSubscribed`) is load-bearing for a `scan`-fold over a `replay = 0`
  stream — and this reason travelled with the fold from the VM to the coordinator.** `scan` re-emits its
  initial accumulator on every fresh upstream collection; under `WhileSubscribed` a resubscribe past the
  stop window restarts the `scan` and overwrites a retained `Open` with the `Hidden` seed, and because the
  source is `replay = 0` the prior events do not replay to rebuild it — a still-open modal silently clears.
  `Eagerly` on the process-scoped scope runs the accumulator exactly once for the process lifetime, so
  `.value` is always the true current projection. (This was true at the VM too; hoisting to a
  *process-lifetime* scope makes it even more clearly correct — the scope only ends at `close()`.)
- **Kotlin gotcha (carried in the moved file):** `scan`'s accumulator type is inferred from the initial
  value, so `scan(ModalUiState.Hidden) { … }` infers `R = ModalUiState.Hidden` (the singleton type) and
  rejects a lambda returning `ModalUiState.Open`. Type it explicitly:
  `scan<ModalEvent, ModalUiState>(ModalUiState.Hidden)`.
- **The `.value`-with-no-collector read *is* the regression proof.** Because `currentModal` is a hot
  `stateIn(Eagerly)`, the AC #4 coordinator test asserts `env.coordinator.currentModal.value` after a
  `pump.push(modalShownEnvelope("m1"))` with **no** collector attached — reading `.value` with no subscriber
  is exactly what proves the process-scoped fold accumulated an event fired before any thread screen
  existed. Contrast the cold-flow `liveSessionEvents` test, which needs a `backgroundScope.launch { …
  collect }` to observe anything.
- **Unrelated pre-existing androidTest break (not caused here).** `compileDebugAndroidTestKotlin` fails on a
  stale `SettingsScreenTest.kt` — a `serverLabel` param added by sibling **#503** left its androidTest
  untouched. Not a mandatory gate ([[androidtest-not-compiled-by-mandatory-gates]]) and out of scope for
  this ticket; flagged so a future run doesn't misattribute it. `ThreadScreenModalTest` itself needed only
  the added import.

## Security (`security-sensitive`)

Architect self-review **PASS**; code review **PASS**. Load-bearing properties, all preserved from the moved
`reduce` and the untouched coordinator body:

- **No logging** of any modal field anywhere on this path — the moved `reduce`, the new `stateIn`, and the
  coordinator all emit nothing. The modal `title`/`prompt` may name a sensitive command/path.
- **Verbatim inert carry** — `ModalUiState.Open` mirrors `ModalEvent.Shown` field-for-field; no parse,
  coerce, trim, or reorder. Output-encoding stays the render slice's ([#446](446.md)) job (the untrusted →
  trusted boundary is the *unchanged* `data/network` decode point).
- **Exact-`modalId` dismiss match** — an out-of-band `modal_dismissed` cannot clear a non-matching open
  modal (spoofed-dismiss safety).
- **Process-scoping crosses no tenant boundary** — one fixed paired daemon; modals carry no
  `conversation_id` (existing semantics), so a single app-level `StateFlow` is correct. The `scan` holds one
  `ModalUiState` (last-shown-wins), so a `modal_shown` flood is O(1) memory — DoS-resistant.
- **Accepted, flagged for the pass (not a blocker):** hoisting extends the in-memory lifetime of an
  unresolved `Open`'s `title`/`prompt` from screen-scope to process-scope. This is inherent to the fix (the
  projection must outlive the screen), stays heap-only (never disked, logged, or transmitted — no
  `rememberSaveable`/DataStore), and is superseded on the next `Shown`/`Dismissed`.

## Open questions / follow-ups

- **Daemon modal replay-on-reconnect.** The teardown=RETAIN decision is conservative precisely because it is
  unconfirmed whether the daemon re-raises an already-observed-but-still-outstanding modal after a reconnect
  (the replay cursor advances past seen events). If a future wire signal *guarantees* re-raise or dismissal
  on reconnect, a follow-up could switch to clear-on-teardown for a cleaner UX. Out of scope here — do not
  build a defence for an unobserved failure.
