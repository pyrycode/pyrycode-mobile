# #348 — `RemoteConversationRepository.promote` over v2 (`promote_conversation`)

Fills the last `#314` mutation stub (`promote`) on the already-merged
[`RemoteConversationRepository`](../features/remote-conversation-repository.md) with a live
[Mobile Protocol v2](../features/mobile-protocol-v2-wire-layer.md) round-trip: encode a
`promote_conversation` request, correlate its **typed `conversation_updated` reply** through the class's
**single** `init` inbound collector, **decode** that reply into the returned promoted `Conversation`, and
**confirmed-upsert** it into the list projection only after the decode succeeds — so a scratch discussion
flips into the Channels tier. This is the **third and last** mutation method to land on the #314 axis
(after [#346](346.md) `sendMessage` and [#347](347.md) `createDiscussion`); it **reuses** #346's
`sendAndAwaitReply` correlation primitive + `mapError`, [#318](318.md)'s
`ConversationResponseDto.toConversation()` decode mapper, and #347's `upsertConversation` fold, and adds
**one new** `promote_conversation` request encoder.

See the feature doc [`remote-conversation-repository.md`](../features/remote-conversation-repository.md)
§ "`promote`" for the evergreen reference; this file is the implementation record.

## The central design point: structural parity with #347 (load-bearing)

`promote` is `createDiscussion` (#347) with **three** deltas — everything else (build-request →
`sendAndAwaitReply` → decode-reply → confirmed-fold → return the reply's value) is byte-for-byte the same
shape:

1. **Request carries three required fields** (`conversation_id`, `name`, `cwd`) — vs. create's two-field
   optional payload. All three are non-null on the wire; there is no `explicitNulls` elision to reason
   about.
2. **The reply is `conversation_updated`** (routed into the existing success arm) — vs.
   `conversation_created`. **Both decode through the same #318 `ConversationResponseDto`** (one DTO models
   both response types — identical field set, see [#318](318.md)).
3. **`cwd` resolution** — `promote`'s `workspace` arg is `String?`, but the wire `cwd` is a required
   `String`. The null case ("promote in place") resolves to the conversation's existing `cwd`. Create had
   no such resolution (it omits a null `cwd` and the server assigns a scratch cwd).

The reply still rides the **same** correlation primitive: `sendAndAwaitReply` hands the raw reply
`JsonElement` back to the caller, which decodes it **in the caller's coroutine** (never inside the lone
inbound collector). The only `onInbound` change is adding `conversation_updated` to the success arm — it
previously fell through the intentional `else` reserved for these mutation deltas.

## Summary

One production class touched (`RemoteConversationRepository`) plus one new encode-only request DTO under
`data/network/`. The response mapper (#318), correlation primitive + `mapError` (#346), and the
`upsertConversation` fold (#347) are all **reused, not built** — this slice is almost pure composition
with one new request encoder and one new `cwd`-resolution line.

- **`data/network/`** — `PromoteConversationPayloadDto` (encode-only `promote_conversation` request DTO,
  its own file per the ktlint single-public-type rule; **all three fields required/non-null** — contrast
  `CreateConversationPayloadDto`'s optional `cwd`).
- **`RemoteConversationRepository`** — adds `conversation_updated` to the existing `ack` /
  `conversation_created` success arm (one shared branch, body unchanged), fills `promote` (resolve `cwd` →
  build request → `sendAndAwaitReply` → decode → `upsertConversation` → return), and reuses
  `upsertConversation` verbatim (this is its **second** call site — the evidence #347 deferred
  generalization to; no abstraction added, the helper already fits). New companion constants
  `TYPE_PROMOTE_CONVERSATION` / `TYPE_CONVERSATION_UPDATED`.
- **Tests** — ten new cases mapping to the ACs, plus the `startPromote` / `conversationUpdatedEnvelope`
  helper pair, and the `stubMethods_…` update (removed the `promote` assertion).

## Patterns established

- **The confirmed-fold helper `upsertConversation` is now a confirmed two-consumer helper — and stays
  un-generalized.** #347 deferred any abstraction of the upsert-by-id CAS fold until a second call site
  appeared; this slice **is** that second site and reuses it **verbatim** — the helper already fits both
  `createDiscussion`'s insert and `promote`'s in-place replacement (both are "upsert by `id`"). The open
  question #347 flagged is **resolved, not deferred**: no further abstraction is warranted (the second
  consumer is the evidence the helper is right-shaped, not that it needs splitting). The upsert replaces
  the existing **unpromoted** discussion entry in place with the promoted one — same `id`, so the list
  count is unchanged and the conversation flips tiers (gone from Discussions, present in Channels) on the
  next `observeConversations` re-emit (AC #2), with no duplicate row.
- **`conversation_updated` doubles as an unsolicited broadcast — the success arm must no-op the
  uncorrelated case.** #274 broadcasts `conversation_updated` to all phones on a conversation change. This
  slice routes it through the correlated success arm, which **safely no-ops** an envelope whose
  `inReplyTo` matches no pending request (the broadcast carries none, or null). So a forged/broadcast
  `conversation_updated` cannot silently mutate the projection via this path — only a reply correlated to
  a *live local promote request* completes a deferred, and the resulting upsert is the conversation the
  local user asked to promote. An unsolicited change still refreshes the list only via the authoritative
  `conversations` snapshot, not this delta. Covered by `promote_uncorrelatedUpdatedReply_isNoOpAndCollectorSurvives`.
- **A required-on-the-wire field resolved client-side from the read projection (`cwd` resolution).** The
  domain signature has a *nullable* `workspace`, but the wire `cwd` is *required*. A null `workspace`
  ("promote in place") resolves to the conversation's existing cwd read from `projection.value` — the
  remote analog of the fake's `cwd = workspace ?: record.conversation.cwd`. This is a new shape: a third
  `projection` interaction that **reads** (not just writes) the read-path state, synchronously and
  lock-free, to assemble a request. The read-then-upsert pair is intentionally **not** atomic — the
  resolved cwd is request data, not a guarded invariant (a concurrent snapshot landing between only
  changes which authoritative cwd the request carries; benign). See [[phase4-request-encoders-live-in-mutation-tickets]].

## Lessons learned

The PR ([#357](https://github.com/pyrycode/pyrycode-mobile/pull/357)) carried no *Lessons learned*
section; the non-obvious points worth recording:

- **`conversation.not_found` IS exercised here — the AC-#3 branch #347 could not reach.** Unlike
  `createDiscussion` (which references no existing conversation, so `mapError`'s `conversation.not_found`
  → `IllegalArgumentException` branch was dead for it), `promote` references an **existing** conversation,
  so promoting an unknown id is a meaningful server error and is tested directly
  (`promote_onConversationNotFound_throwsIllegalArgumentAndLeavesListUnchanged`). `mapError` is reused
  **unchanged** — this slice is the first to actually drive that branch end-to-end. The test asserts both
  `is IllegalArgumentException` **and** `!is RelayErrorException` (it must be the bare-IAE branch, not the
  catch-all), and that the list is left unmutated.
- **The returned `cwd` is the server's reply value, not the request's resolved cwd.** The request resolves
  a `cwd` to *send* (from `workspace` or the projection), but the returned `Conversation.cwd` always comes
  from the `conversation_updated` reply via `toConversation()` — server-authoritative (AC #1 "the resolved
  cwd"). A dedicated test (`promote_onUpdatedReply_returnsPromotedConversationWithServerCwd`) sends a null
  workspace (resolving the scratch cwd into the request) but pushes a reply with a *different* cwd
  (`/work/wp`) and asserts the return is the reply's `/work/wp` — proving the return never echoes the
  request's resolved value. Identical to #347's "return the reply's cwd, not the input."
- **The `?: ""` cwd fallback is unreachable from the shipped UI, tested anyway, and gets no throw.** The
  final `?: ""` only fires when `workspace` is null **and** the conversation is absent from the projection
  (projection still `null`, or an unknown id) — not reachable from the shipped promote UI, which only
  promotes a *visible* (hence loaded) discussion. A test exercises it
  (`promote_nullWorkspaceNoProjectionEntry_fallsBackToEmptyCwd`) to prove it sends a well-formed-but-empty
  `cwd` rather than crashing. **No `check`/throw was added** for this should-not-happen state — adding one
  would be a defense for an unobserved failure mode (Evidence-Based Fix Selection). Whether the server
  defaults or rejects an empty `cwd` on promote is undefined (its `promote_conversation` wire handler
  isn't built yet — #274 shipped only the DTO structs; `Registry.Promote(id, name)` #218 doesn't even
  consume `cwd`); a server rejection of `""` would surface cleanly as `RelayErrorException`, never a crash.
- **`sendAndAwaitReply` + `mapError` + `upsertConversation` are all reused verbatim — only a new request
  encoder, a new success-`type` in the `when` arm, and one `cwd`-resolution line were written.** The
  typed-vs-bare reply difference (vs. #346's empty `ack`) is entirely in the caller's decode, exactly as
  #347 established; the registry is typed `<JsonElement>` precisely so it serves both bare and typed
  callers. This validates the #346/#347 composition once more: the third mutation added the least new code
  of the three.

## Verification

- `./gradlew test`, `./gradlew check`, `./gradlew assembleDebug` — all green (QA gate comment on PR #357).
- The ten new tests map to the ACs: request shape with explicit workspace
  (`{"conversation_id":"disc","name":"weekly-planning","cwd":"/work/wp"}` — AC #1/#4); request shape with
  null workspace resolving the existing cwd from the projection (`cwd == DEFAULT_SCRATCH_CWD`, asserted as
  the **constant** — the new-decision test, seeds the projection first); null workspace with no projection
  entry falling back to `""` (AC #1/#4); `conversation_updated` reply → promoted `Conversation` with the
  **reply's** cwd (AC #1); `observeConversations` tier flip across `All` / `Channels` / `Discussions`
  collectors (AC #2 — `disc` present in Channels, absent from Discussions, no duplicate, count unchanged);
  `conversation.not_found` → `IllegalArgumentException` with the list unchanged (AC #3 — the branch #347
  could not exercise); other server `error` → `RelayErrorException(code)` with the list unchanged (AC #3);
  not-`Open` (`sendResult = false`) → `IllegalStateException` with the list unchanged (AC #3/#4); malformed
  `conversation_updated` (omitted `cwd`) → the #318 decode exception (a `SerializationException`, an
  `IllegalArgumentException` subtype) with the list unchanged; and correlation hygiene (an uncorrelated
  `conversation_updated` is a no-op and a later real promote still round-trips). Driven with the
  `runCurrent()` (not `advanceUntilIdle()`) idiom — see [[remote-repo-test-runcurrent-not-advanceuntilidle]].
- **Pure `data/`-layer slice** — no instrumented test, no `ComposeTestRule`; zero `android.*` imports.
  See [[data-layer-android-import-exception]].
- **Code review: PASS** ([PR #357](https://github.com/pyrycode/pyrycode-mobile/pull/357), no MUST/SHOULD
  FIX findings). The reviewer verified all four ACs, that the `cwd` resolution reads the real scratch cwd
  via #316's verbatim-`cwd` list mapper, that decode-before-upsert means no failure path mutates
  `projection`, that the success-arm extension safely no-ops the unsolicited broadcast, and (security pass)
  that no logging/secrets were added and the resolved `cwd` is the client's own state, never opened as a
  path. The architect's `## Security review` (Verdict: PASS) was present in the spec — the required
  `security-sensitive` pass was not skipped.

## Open hand-offs (carried, not introduced)

- **Connection-drop-mid-promote leak.** The same single-entry `pendingRequests` leak [#346](346.md) /
  [#347](347.md) documented: if the connection scope is cancelled while a caller awaits, the deferred
  never completes until the *caller* is cancelled (the ViewModel scope on screen exit →
  `CancellationException`). No timeout added (no observed hang; a timeout value is a product call). A
  future slice or the connection coordinator ([#351](351.md)) may fail all `pendingRequests` on
  disconnect. Flagged, not fixed (Evidence-Based Fix Selection).
- **Server empty-`cwd` semantics on promote (informational).** The `?: ""` fallback only fires in the
  unreachable-from-UI case (see Lessons learned). The server's `promote_conversation` wire handler isn't
  built yet, so whether it defaults or rejects an empty `cwd` is undefined. No action now — the common
  path resolves a real cwd; a server rejection of `""` surfaces cleanly as `RelayErrorException`. Revisit
  only if the server handler lands and rejects empty for the common path (it should not).
- **UI error-surface for promote.** `promote` now joins `sendMessage` / `createDiscussion` as a method
  that throws on server `error` / not-connected. The two production callers
  (`DiscussionListViewModel.confirmPromotion()` passing `workspace = null`; `ThreadViewModel`'s
  `resolveWorkspace(...)` → `null` for `WorkspaceChoice.SCRATCH`) are still fire-and-forget against the
  Fake binding; surfacing these exceptions in the UI is owned by the **#350** wiring/error-surface
  hand-off — out of scope here. The signature is **unchanged**, so there is no consumer call-site cascade.
