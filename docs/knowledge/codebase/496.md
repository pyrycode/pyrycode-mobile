# #496 — Close-then-connect race can clear the new loop's live connection

**Issue:** [#496](https://github.com/pyrycode/pyrycode-mobile/issues/496) ·
**Spec:** [`docs/specs/architecture/496-close-then-connect-liveconnection-race.md`](../../specs/architecture/496-close-then-connect-liveconnection-race.md) ·
**PR:** [#517](https://github.com/pyrycode/pyrycode-mobile/pull/517) ·
**Feature doc updated:** [Relay reconnect supervisor](../features/relay-reconnect-supervisor.md) ·
Size **XS**, `security-sensitive`. Commit `29e3a4a`.

## Summary

Closes a connection-lifecycle race in [`RelayConnectionSupervisor`](../features/relay-reconnect-supervisor.md)
([#307](307.md)). `close()` is `@Synchronized`: it cancels the supervision loop, then **synchronously**
nulls `liveConnection`. But coroutine cancellation is cooperative, so the cancelled loop's `finally` — which
**also** nulls `liveConnection` — runs later, at the loop's next cancellation checkpoint, **outside** that
`@Synchronized` lock. If a fresh `connect()` had already started a loop that reached `Up` and published its
transport to `liveConnection`, the old loop's stale `finally` **unconditionally** nulled the field, wiping the
**new** loop's live connection. `currentConnection` then read `null` over an open socket, so
[`RelayRepositoryCoordinator`](../features/relay-repository-coordinator.md) ([#351](351.md)) never saw the
transport, never built a pump for it, and the connection was **silently dead until the next reconnect**.
Manifests only with `USE_RELAY_REPOSITORY` on; filed from the Cross-Repo Code Review 2026-07-03. The user-
visible trigger is a background→quick-foreground (or push-wake right after a teardown).

The fix makes the `finally`'s clear a **compare-and-clear on identity**: it may null `liveConnection` only if
the field still referentially holds *this loop's own* `transport`. `transport.close()` on the next line stays
unconditional, so every loop always releases its own socket. One production line changed; the bulk of the diff
is the deterministic interleaving test.

**Same race *class* as [#493](493.md)** — an async clear that outlives the state it was scoped to. #493 was a
`combine` of two independently-mutated `StateFlow`s at the coordinator layer; this is a cancelled loop's
`finally` at the supervisor layer. Both are fixed by keying the write to the identity of the thing it belongs
to rather than blindly clearing a shared holder.

## The fix

**Before** (`RelayConnectionSupervisor.kt` `finally`) — an unconditional clear:

```kotlin
} finally {
    stabilityTimer?.cancel()
    liveConnection.value = null            // wipes whatever is current — even a NEWER loop's transport
    transport.close()
}
```

**After** (`:176`) — an atomic compare-and-clear keyed on this loop's own `transport`:

```kotlin
} finally {
    stabilityTimer?.cancel()               // cancel before reading the flag (no late write)
    // Compare-and-clear on identity (#496): a cancelled loop's finally runs OUTSIDE the
    // @Synchronized close()/connect() lock, so it must clear liveConnection only when it
    // still holds *this* loop's transport — never a value a newer loop already published.
    liveConnection.update { current -> if (current === transport) null else current }
    transport.close()                      // unchanged, unconditional — every loop releases its socket
}
```

**Why `update {}` and not the plain `if (liveConnection.value === transport) liveConnection.value = null`
the ticket sketched:** the supervision scope runs on `Dispatchers.Default` (multi-threaded), so the
check-then-act must be a single atomic compare-and-clear, not a non-atomic read-then-write. `update {}` is the
same one-liner and matches AC #2's "compare-and-clear on identity" wording literally. (Functionally the plain
`if` is safe too here — `close()` pre-nulls `liveConnection` before the new loop starts and a cancelled loop's
transport is never re-published, so no writer restores `transport` after the read — but the atomic form spares
the reviewer from reconstructing that argument. Code review flagged this as a NIT endorsing the atomic choice.)

**Behavior-preserving on every other path** (covered by existing tests, no new ones needed):

- *Normal socket `Down` → redial* (`singleDrop_…`): the loop's own `transport` is still what `liveConnection`
  holds → `=== transport` true → cleared to `null`, exactly as today.
- *Normal `close()`* (`close_tearsDownTransportAndStopsLoop`): `close()` synchronously nulls `liveConnection`
  first; the loop's `finally` then reads `null` (not its transport) → skips → stays `null`, and
  `transport.close()` still releases the socket. Net result identical.
- *Mid-dial cancel before `Up`*: `liveConnection` was never set to this transport → `=== transport` false →
  skip (setting `null = null` was a no-op before anyway).

## Patterns established

- **An async clear that runs outside the lock its scope was published under must be keyed to the identity of
  what it's clearing — never a blind null of the shared holder.** A cancelled coroutine's `finally` (or any
  deferred cleanup) can run *after* a successor has already re-published the same holder. Guard the clear with
  `if (holder === myOwnValue)` (atomically, via `MutableStateFlow.update {}` under a multi-threaded
  dispatcher) so cleanup can only ever retract the value *it itself* published. This is the supervisor-layer
  sibling of [#493](493.md)'s "derive from ONE switched source" — same disease (an async operation outliving
  the state it was scoped to), different-shaped cure at a different layer.
- **Scope only the *identity-sensitive* half of a `finally`; keep resource release unconditional.** The
  `finally` does two things — clear a published reference (identity-sensitive: only if it's still mine) and
  release a socket (always: every loop owns exactly one transport and must close it). Guarding the clear must
  **not** accidentally guard the release. Here `transport.close()` stayed on its own unconditional line
  precisely so socket-release is never scoped away (AC #3).

## Lessons learned

Lifted from the PR's *Lessons learned* section (saved as reusable memory
[[deterministic-cancelled-finally-race-test]]):

- **A naive close→connect→single-`runCurrent()` interleaving is false-green — it passes on the *buggy* code
  too.** `StandardTestDispatcher` runs queued tasks FIFO, and `close()` enqueues the old loop's
  cancellation-resume *before* `connect()` enqueues the new loop. So the old loop's `finally` runs while
  `liveConnection` is still `null` (a harmless `null → null` no-op) **before** the new loop ever publishes — the
  race window never opens. Reproducing the bug requires genuinely **holding the old loop's `finally` past the
  point the new loop publishes**, then releasing it. The technique: give the old loop's dial a
  `GatedRelayTransport` whose `events` flow, on cancellation, parks in its own `finally` inside
  `withContext(NonCancellable) { release.await() }`. Because the supervisor's `events.collect { … }` can't
  return until that flow completes, the supervisor's `finally` (the fix site) is deferred until the test opens
  the gate — letting the new loop reach `Up` and publish in between. Then `release.complete(Unit); runCurrent()`
  runs the held `finally` **last**, which is the moment the un-guarded code wipes the new transport (test RED)
  and the guarded code leaves it intact (test GREEN).

## Testing

Unit only (`./gradlew spotlessCheck test lint assembleDebug` all green). `runTest` virtual clock,
`StandardTestDispatcher(testScheduler)` settled with `runCurrent()` (never `advanceUntilIdle()` — no timers to
advance), seeded `Random(SEED)`, `supervisor.close()` cleans up. **Confirmed RED against the un-guarded
`finally` before the fix, GREEN after** (per `CLAUDE.md` § Conventions test-first). `connectedAndroidTest` not
run — pure `data/`-layer change, no instrumented surface (same posture as [#307](307.md)/[#493](493.md)).

The one added test, `closeThenConnect_oldLoopFinally_doesNotClearNewLoopConnection`, drives the interleaving
deterministically:

1. `connect(); runCurrent()` → old loop dials the `GatedRelayTransport`, reaches `Up`, publishes it. Assert
   `currentConnection.value === gated`, `state() == Connected`.
2. `close(); connect(); runCurrent()` → `close()` cancels the old loop + synchronously nulls `liveConnection`;
   the new loop dials `fresh` and awaits `Up`; the old loop's cancellation-resume **parks in the gate's
   `NonCancellable` cleanup** (its `finally` not yet reached). Assert `currentConnection.value == null`.
3. `fresh.emitUp(); runCurrent()` → new loop publishes **while the old loop's `finally` is held**. Assert
   `currentConnection.value === fresh`.
4. `release.complete(Unit); runCurrent()` → the old loop's held `finally` **finally** runs. **Key assertion:**
   `assertSame(fresh, currentConnection.value)` — the new transport survives (would be `null` on the un-guarded
   `finally`). Also `assertTrue(gated.closeCalls >= 1)` (AC #3: the old loop still released its own socket).

**Regression safety (AC #4 + normal-drop):** the existing `close_tearsDownTransportAndStopsLoop` and
`singleDrop_…` tests are **untouched and green** — the proof the guard preserves both the normal-`close()`
socket-release/`assertNull(currentConnection)` and the normal-`Down` redial paths.

## Security (`security-sensitive`)

Architect self-review **PASS** (in the spec's § Security review); code review **PASS**
([PR #517](https://github.com/pyrycode/pyrycode-mobile/pull/517), one NIT endorsing the atomic `update {}`).
The change strictly **narrows** an existing race and is availability-positive:

- **Concurrency** — converts an unconditional cross-loop clear into an identity-keyed compare-and-clear, so a
  loop's `finally` can no longer wipe a transport published by a *different* loop. No new coroutine, scope,
  mutex, or suspension point; the loop's cancellation-atomicity is unchanged; `close()`'s clear stays under
  `@Synchronized`.
- **Availability** — the pre-fix behavior *is* the defect: a benign background→foreground timing wiped a live
  connection and stranded the user offline until the next backoff. The guard removes that silent
  denial-of-connection; it adds no unbounded wait or pinnable resource (transport lifecycle + backoff schedule
  unchanged).
- **Key material / no-log contract** — the supervisor observes only the transport's `events` (`Up`/`Down`),
  never `inbound` frames or any Noise key material; `transport.close()` stays unconditional so no socket leaks
  open, and downstream a wrongly-null `currentConnection` is what *denies* the coordinator the transport
  (dropping is always fail-safe there — `teardownActive → pump.close()` wipes keys). The guard reads/writes an
  in-memory reference and logs nothing; the supervisor's no-log contract holds.
- **No trust boundary added or moved** — the change reshapes one internal reference-write; it parses no wire
  bytes. Untrusted-wire parsing lives downstream in
  [`RemoteConversationRepository`](../features/remote-conversation-repository.md)/`MobileWireCodec`, untouched.
