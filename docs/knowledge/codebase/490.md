# #490 — Guard every one-shot repository call in the relay-mode view-models

**Issue:** [#490](https://github.com/pyrycode/pyrycode-mobile/issues/490) ·
**Spec:** [`docs/specs/architecture/490-guard-relay-oneshot-repo-calls.md`](../../specs/architecture/490-guard-relay-oneshot-repo-calls.md) ·
**PR:** [#506](https://github.com/pyrycode/pyrycode-mobile/pull/506) ·
**Feature doc:** [Guarded repo launch](../features/guarded-repo-launch.md) (new) ·
Size **S**, `security-sensitive`.

## Summary

The nine older conversation-action launches fired one-shot repository calls in `viewModelScope` with **no
`try/catch`**: `ThreadViewModel.sendMessage` / `onWorkspacePicked` + the `Archive` / `DeleteConfirm` /
`RenameSubmit` / `SaveAsChannelSubmit` arms of `onOverflowEvent`, `ChannelListViewModel`'s two
create-discussion paths (`CreateDiscussionTapped` / `WorkspacePicked`), and `DiscussionListViewModel.confirmPromotion`.
Under [`FakeConversationRepository`](../features/conversation-repository.md) these never throw, so the gap was
invisible — but under the relay repository (behind `USE_RELAY_REPOSITORY`, the flip this ticket unblocks) each
can throw `RelayErrorException` (a crafted server `error` frame), `IllegalStateException` (not-connected /
not-wired interface default), or `UnsupportedOperationException` (`archive` / `rename` / `changeWorkspace` are
not yet wired on [`RemoteConversationRepository`](../features/remote-conversation-repository.md)). An uncaught
throw in `viewModelScope` reaches the default uncaught-exception handler and **kills the process**.

The fix introduces **one** module-internal extension — `internal fun ViewModel.launchGuardedRepoCall(block)`
(new `ui/conversations/GuardedRepoLaunch.kt`) — and routes all nine sites through it. The helper rethrows
`CancellationException` **first** (it extends `IllegalStateException` on the JVM), then inertly swallows the
three relay failure types with **no logging** (`RelayErrorException.message` is server-supplied). Each site's
edit is mechanical: `viewModelScope.launch {` → `launchGuardedRepoCall {`, body unchanged. This is the
**deterministic** safety net paired with the separate "hide unimplemented actions" UI ticket — different
fabric: hiding the affordance is a product decision; the guard must hold even if an action slips the UI filter.

## Files touched

- `app/src/main/java/de/pyryco/mobile/ui/conversations/GuardedRepoLaunch.kt` (**new**, +43) — the sole shared
  guard. One top-level `internal fun ViewModel.launchGuardedRepoCall(block: suspend () -> Unit)` (no class, so
  ktlint's single-class-filename rule doesn't apply — see [[ktlint-filename-rule-single-class]]). Package
  `de.pyryco.mobile.ui.conversations`, the shared parent of `thread/` and `list/`. Four catch arms in a
  load-bearing order:
  ```kotlin
  viewModelScope.launch {
      try {
          block()
      } catch (e: CancellationException) {
          throw e // MUST be first: j.u.c.CancellationException extends ISE on the JVM (the #451 rework)
      } catch (e: RelayErrorException) {
          // Inert: server error swallowed. Never log e.message (server-supplied).
      } catch (e: IllegalStateException) {
          // Inert: not-connected / not-wired interface-default swallowed.
      } catch (e: UnsupportedOperationException) {
          // Inert: not-yet-wired remote method swallowed.
      }
  }
  ```
  `RelayErrorException` / `IllegalStateException` / `UnsupportedOperationException` are mutually independent
  (none subclasses another) so their relative order is free; the order mirrors `sendAnswer` for readability.
  **`IllegalArgumentException` is deliberately not caught** — the sites always pass their own current
  `conversationId`, so an IAE signals a programming bug and should crash (fail-fast); it is a `RuntimeException`
  sibling of ISE, so the ISE arm does not swallow it.
- `app/src/main/java/de/pyryco/mobile/ui/conversations/thread/ThreadViewModel.kt` (**mod**, +7/−6) — six sites:
  `sendMessage` (`:424`), `onWorkspacePicked` (`:439`), and the `Archive` / `DeleteConfirm` / `RenameSubmit` /
  `SaveAsChannelSubmit` arms of `onOverflowEvent` (`:593`–`:623`). The `Archive` / `DeleteConfirm`
  `navigationChannel.send(ThreadNavigation.PopBack)` **stays inside** the guarded block, after the repo call —
  a throwing mutation jumps to the catch and skips the pop-back (AC #4). Import added; `retry()` (launches
  `connectionStateSource.retry()`, not a repo call) left untouched.
- `app/src/main/java/de/pyryco/mobile/ui/conversations/list/ChannelListViewModel.kt` (**mod**, +3/−3) — the two
  create-discussion launches (`CreateDiscussionTapped` `:128`, `WorkspacePicked` `:137`); each keeps its
  follow-on `navigationChannel.send(ToThread(conversation.id))` **inside** the guard, so a failed create does
  not navigate (AC #4). `import kotlinx.coroutines.launch` dropped (no longer referenced).
- `app/src/main/java/de/pyryco/mobile/ui/conversations/list/DiscussionListViewModel.kt` (**mod**, +2/−1) —
  `confirmPromotion` (`:101`). No side effect after the `promote` call.
- `app/src/test/java/de/pyryco/mobile/ui/conversations/ThrowingConversationRepository.kt` (**new**, +47) — a
  `ConversationRepository by delegate` decorator (delegate defaults to a seeded `FakeConversationRepository`)
  that throws a configured `failWith: Throwable` from the seven mutation methods the nine sites call
  (`sendMessage` / `changeWorkspace` / `archive` / `delete` / `rename` / `promote` / `createDiscussion`).
  Interface delegation forwards every `observe*` read to the fake's seed data, so each VM's `state` pipeline
  still assembles; only the mutations throw. A `failWith`-only constructor lets a test loop over the three
  handled types.
- `app/src/test/java/…/thread/ThreadViewModelTest.kt` (**mod**, +116), `…/list/ChannelListViewModelTest.kt`
  (**mod**, +69), `…/list/DiscussionListViewModelTest.kt` (**mod**, +39) — see **Testing** below.

**Not touched:** any repository/facade/transport code (the guard sits **above** the transport, catching an
already-parsed exception — no socket, frame, timeout, or TLS surface); `FakeConversationRepository` (never
throws these, so AC #5 holds — existing VM suites stay green); no `Never Update` doc.

## Patterns established

- **One shared guard, not nine inline `try/catch`.** The nine catch blocks would have been byte-identical
  (~72 lines of production duplication) and would have forced the cancellation-ordering + no-log invariants to
  be re-proven per site. Collapsing them into one `internal fun ViewModel.launchGuardedRepoCall` (~15 lines)
  lets both invariants be verified **once**. Route relay-mode one-shot repository calls through it rather than
  a bare `viewModelScope.launch`; the pattern's evergreen home is [Guarded repo launch](../features/guarded-repo-launch.md).
- **Inert swallow, not an error surface — because none of these sites had one.** The guard mirrors the
  **inert-swallow** posture of `ThreadViewModel.onDropQueued` / `sendInterrupt` (empty catch bodies), **not**
  the error-channel posture of `sendAnswer` / `sendCancel`. Adding a snackbar / error channel to any of the
  nine is unrequested scope — the ticket requires "fail quietly," and evidence (no observed need for a
  per-action error toast on these paths) says defer. A user-facing error surface for these actions is a
  separate, later decision.
- **Keep the follow-on side effect inside the guarded block.** For the four side-effect sites
  (Archive/Delete → `PopBack`; the two create-discussion → `ToThread`), the `navigationChannel.send(...)` sits
  **after** the repo call, **inside** the block — so a throwing repo call jumps to the catch and skips the
  send. Do **not** hoist the send out of the guard "to keep the block small": that would fire navigation on a
  failed action.
- **Deterministic fabric for the deterministic half.** Belt-and-suspenders with the "hide unimplemented
  actions" UI ticket: the UI filter is the stochastic/product half, the code-level guard is the deterministic
  half — they must be different fabric, and the guard holds even if an action slips the filter.

## Lessons learned

- **The `CancellationException`-first arm is load-bearing, not cosmetic.** On the JVM
  `java.util.concurrent.CancellationException extends IllegalStateException`, so a bare
  `catch (IllegalStateException)` before it would swallow `viewModelScope` teardown and break structured
  cancellation — the exact [#451](451.md) rework this ticket must not repeat. Pinned by
  `guardedRepoCall_scopeCancellationMidCall_propagatesCancellationInert`. See
  [[catch-illegalstate-swallows-cancellation]].
- **A throw escaping a `viewModelScope`-launched coroutine does NOT fail `runTest`.** `viewModelScope` is a
  separate `SupervisorJob`, so an uncaught throw from a guarded launch reaches the **default uncaught-exception
  handler**, not the test's exception aggregator. The only proof the typed catch actually ran is to install a
  `Thread.setDefaultUncaughtExceptionHandler` capture (restored in `finally`) and assert the capture list is
  empty. Every swallow test in all three VM suites uses this harness — the same one
  `ThreadViewModelTest`'s `onInterrupt` / `onDropQueued` swallow tests established.
- **`ChannelListViewModelTest.newDataStore()` reuses a fixed temp filename — hoist ONE `prefs` before a
  looping test.** The `@get:Rule TemporaryFolder` `newDataStore()` helper produces `tmp.newFile("app_prefs.preferences_pb")`
  with a **fixed name**, so constructing a fresh `AppPreferences(newDataStore())` per loop iteration throws
  `IOException` (file already exists) on the second pass. The swallow test loops over three failure types, so
  it builds **one** `val prefs = AppPreferences(newDataStore())` **before** the loop and reuses it across
  every `makeVm(ThrowingConversationRepository(failure), prefs)`. (ThreadVM / DiscussionVM tests don't hit this
  — their VMs take no `AppPreferences`.)

## Security (`security-sensitive`)

Architect self-review **PASS**; code review **PASS**. Load-bearing properties:

- **The untrusted datum crosses into exactly one place.** `RelayErrorException.message` (server-supplied via a
  crafted `error` frame) reaches only the `catch (RelayErrorException)` arm of `launchGuardedRepoCall`, which
  is **empty** and never reads `e.message`. Nothing downstream holds it: no state write, no emitted event, no
  log. Centralizing the catch means the never-log confidentiality invariant is asserted in **one** function,
  not scattered across nine sites — the whole point of the DRY decision from a security lens.
- **Availability hardening.** This *is* the fix for a remote-triggerable process-crash (uncaught throw in
  `viewModelScope`). The inert swallow performs **no retry**, so a hostile relay spamming `error` frames
  cannot amplify into a retry storm — each guarded call is one-shot per user gesture.
- **Structured-concurrency-correct.** The `catch (CancellationException) { throw e }`-first ordering preserves
  the [#451](451.md) invariant; no catch arm writes a `StateFlow`; mid-send cancellation rethrows and skips the
  side-effect `send` (no partial state — the one-shots hold no optimistic local mutation).
- **OUT OF SCOPE, named for the follow-up:** the pre-existing `state` cold-read
  `.catch { emit(Error(e.message ?: …)) }` in [`ChannelListViewModel.kt:111`](../features/channel-list-viewmodel.md)
  and [`DiscussionListViewModel.kt:64`](../features/discussion-list-viewmodel.md) surfaces a raw exception
  message to the UI — on the remote path that could be a server-supplied `RelayErrorException.message`. That is
  the **read** flow, not one of the nine one-shot mutation launches this ticket guards, and it predates this
  change. **Recommended follow-up ticket:** sanitize those two `.catch` arms to generic copy only. Not gated on
  here; #490 was deliberately **not** expanded to touch it (scope discipline).

## Testing

Unit tests only (`./gradlew testDebugUnitTest`; the full `test lint assembleDebug` + `spotlessCheck` all pass).
No instrumented tests — the change is VM-internal with no androidTest surface. Each VM suite mirrors the
existing `onInterrupt` / `onDropQueued` swallow + scope-cancellation harness.

- **AC #2/#3 swallow — one test per VM.** Loop `failWith` over
  `[IllegalStateException, RelayErrorException(code, false, "no"), UnsupportedOperationException]`; for each,
  build the VM on a `ThrowingConversationRepository(failWith)`, invoke every guarded path for that VM, and
  assert the uncaught-handler capture list is empty:
  - `ThreadViewModelTest.guardedRepoCalls_whenRepositoryThrowsEachHandledType_areSwallowedWithoutCrashing`
    (all six ThreadVM sites).
  - `ChannelListViewModelTest.createDiscussionPaths_whenCreateThrowsEachHandledType_areSwallowedWithoutCrashing`
    (both create-discussion paths; **one hoisted `prefs`** — see Lessons learned).
  - `DiscussionListViewModelTest.confirmPromotion_whenPromoteThrowsEachHandledType_isSwallowedWithoutCrashing`
    (open the promotion dialog on a seeded discussion first, then `PromoteConfirmed`).
- **AC #4 side-effect skipped.** With a throwing repo, collect `navigationEvents`, invoke the site,
  `advanceUntilIdle()`, assert **no** navigation was emitted:
  - `ThreadViewModelTest.guardedRepoCalls_whenArchiveOrDeleteThrows_doNotPopBack` — no `PopBack`.
  - `ChannelListViewModelTest.createDiscussionPaths_whenCreateThrows_doNotNavigateToThread` — no `ToThread`.
- **AC #3 cancellation propagates — one representative path** (the guard is shared, so one path proves the
  ordering for all). `ThreadViewModelTest.guardedRepoCall_scopeCancellationMidCall_propagatesCancellationInert`:
  an `archive` `await()`s a never-completing `CompletableDeferred` (suspends in-flight); the VM is hosted in a
  `ViewModelStore`; `store.clear()` cancels `viewModelScope`; asserts no crash **and** the `PopBack` side
  effect is skipped.
- **AC #5 fake mode unchanged** — no new test; the existing VM suites already exercise these paths against
  `FakeConversationRepository` and stay green (the guard is transparent when nothing throws).
