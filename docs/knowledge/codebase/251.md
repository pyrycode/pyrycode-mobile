# #251 — feat(ui/thread): ThreadOverflowMenu composable + sealed ThreadEvent + VM archive wiring

Lands three pieces of the eventual thread overflow menu without mounting it: (a) a stateless `ThreadOverflowMenu` composable rendering an M3 `DropdownMenu` with the five common items, (b) a `sealed interface ThreadEvent` with one `data object` per item, and (c) `ThreadViewModel.onOverflowEvent(event)` dispatcher whose `Archive` branch calls `repository.archive(state.value.conversationId)` inside `viewModelScope` (the other four cases are intentionally empty handler bodies). `ThreadOverflowMenu` is exported but has **no production caller** — `ThreadTopAppBar.onOverflowClick` remains a no-op. The host wiring (`expanded` state in `ThreadScreen`, mount inside `ThreadTopAppBar`, `onEvent = vm::onOverflowEvent` binding in `MainActivity`) is the scope of follow-up [#252](https://github.com/pyrycode/pyrycode-mobile/issues/252). Split from [#203](https://github.com/pyrycode/pyrycode-mobile/issues/203).

## Summary

- **`sealed interface ThreadEvent` co-located with `ThreadViewModel`** at the top of `ThreadViewModel.kt` (above the `ThreadUiState` data class). Five `data object` cases — `NewSession`, `Rename`, `ChangeWorkspace`, `Archive`, `ChannelInfo` — all parameterless. `data object` (not plain `object`) chosen for the auto-generated `toString`/`equals` so the Compose-test assertion `log == listOf("dismiss", "event:NewSession")` reads cleanly without a custom matcher. Placement-next-to-VM follows the consumer; the `DiscussionListEvent` / `ChannelListEvent` precedent of declaring next to the screen file did not fit because in this slice the screen does not yet consume the sealed surface.
- **Scope is overflow-only — existing plain handlers on `ThreadViewModel` are not migrated.** Pre-#251, `ThreadViewModel` exposed six plain methods (`sendMessage`, `retry`, `onWorkspaceChipTapped`, `onWorkspacePicked`, `onWorkspacePickerDismissed`, `onModelSelected`). `ThreadEvent` lives **alongside** those, not as a replacement — option (ii) from the convention question on [#203](https://github.com/pyrycode/pyrycode-mobile/issues/203) (introduce the sealed surface for the new event family only); option (iii) (migrate all six plain handlers alongside the overflow work) was rejected as oversized for an S-budget slice. The `(state, onEvent)` collapse for `ThreadScreen` itself stays deferred per [the existing thread-screen note](../features/thread-screen.md).
- **`ThreadViewModel.onOverflowEvent(event: ThreadEvent)` is a 10-line `when` dispatcher.** `Archive` launches `repository.archive(state.value.conversationId)` inside `viewModelScope` — same shape as the existing `sendMessage` launcher (no new dispatcher, no `Job` retention, no error handling). The other four cases are an exhaustive `Unit` branch — exhaustive `when` over a sealed surface means a missing case is a compile error, so no TODO comments / no stub bodies needed.
- **Conversation id is read from `state.value.conversationId`, not the captured `private val conversationId`.** Both resolve to the same value (the data-class default of `ThreadUiState.conversationId` mirrors the constructor-captured field, and no mutation path overwrites it), but `state.value.conversationId` matches the existing `sendMessage` pattern at `ThreadViewModel.kt:106` — one read-site convention for downstream-readers to grep.
- **Stateless `ThreadOverflowMenu(expanded, onDismiss, onEvent, modifier)` in its own file** at `app/src/main/java/de/pyryco/mobile/ui/conversations/thread/ThreadOverflowMenu.kt`. Material 3 `DropdownMenu` containing five `DropdownMenuItem`s in this exact order: New session, Rename, Change workspace…, Archive, Channel info. Each item's `onClick = { onDismiss(); onEvent(ThreadEvent.X) }` — dismiss-before-handler — mirrors the precedent at `DiscussionListScreen.kt:209-212` (`onClick = { menuExpanded = false; onSaveAsChannel() }`). Ordering is load-bearing for both the Compose-test combined-log assertion and the downstream host wiring (dialogs / sheets / nav transitions from these events need the menu closed before mounting to avoid Compose layout layering issues).
- **Single `onEvent: (ThreadEvent) -> Unit` sink — not per-item callbacks.** The ticket left the shape at the architect's discretion but required dispatch through `ThreadEvent`. Single-sink chosen because (1) it is the direct CLAUDE.md MVI convention and matches `ChannelListScreen` / `DiscussionListScreen`'s screen-level event surfaces, (2) the host (#252) binds `onEvent = vm::onOverflowEvent` directly with no per-callback → sealed-event mapping layer, (3) the Compose test is one event-recording lambda instead of five. The `ChannelInfoSheet` per-callback shape is the sibling precedent for **sheets** (heterogeneous distinct affordances spread across sections); the menu is a homogeneous list of identically-typed events so the sealed-sink shape fits better. The same composable signature is what #252's mount will bind into.
- **Five new `strings.xml` keys with `thread_overflow_` prefix.** `thread_overflow_new_session` / `_rename` / `_change_workspace` / `_archive` / `_channel_info`. The `Change workspace…` label uses U+2026 horizontal-ellipsis (not three dots) per Material 3 guidance for "this action opens further UI" — same convention as `save_as_channel_action` ("Save as channel…") at `strings.xml:11`. All five render via `stringResource(...)` inside the composable — no string literals in the menu body.
- **Two new VM unit tests** (`ThreadViewModelTest.kt:497-530`) using a new private `RecordingRepo` test double — not `FakeConversationRepository`. `RecordingRepo` mirrors the `DiscussionListViewModelTest` `RecordingRepo` pattern: per-method recording lists with `TODO("not used")` stubs for unused contract methods. `archive(conversationId)` records into `archiveCalls: MutableList<String>` (list rather than counter so both call count *and* id can be asserted). `observeConversations` / `observeMessages` / `observeLastMessage` return `flowOf(emptyList())` / `flowOf(null)` because the VM subscribes to all three at construction via the `combine` block — non-emitting stubs would hang the test. The two tests pin: (a) `Archive` calls `archive("seed-channel-personal")` exactly once, (b) the other four cases produce zero calls.
- **Five new Compose tests** (`ThreadOverflowMenuTest.kt`) using `createComposeRule` + `PyrycodeMobileTheme` wrapper + `InstrumentationRegistry.getInstrumentation().targetContext.getString(resId)` lookup for i18n-safe label assertions. One "render in documented order when expanded" test asserts all five `R.string.thread_overflow_*` labels render; five per-item tests use the **combined-recorder pattern** — a single `val log = mutableListOf<String>()` with `onDismiss = { log.add("dismiss") }` and `onEvent = { log.add("event:$it") }`, asserted as `log == listOf("dismiss", "event:NewSession")`. The combined-recorder log makes the dismiss-before-event ordering AC directly testable in a single assertion (Compose-test can't observe call ordering across two separate recorders).
- **No mount in `ThreadTopAppBar`, no `expanded` state in `ThreadScreen`, no `MainActivity` binding.** [#252](https://github.com/pyrycode/pyrycode-mobile/issues/252) owns all three. The `onOverflowClick: () -> Unit = {}` parameter on `ThreadScreen` / `ThreadTopAppBar` is unchanged. Stubbed-but-unwired posture matches the existing pattern for `onTitleClick` (waiting on #141 rename dialog) and the current `onOverflowClick` itself, and lets the contract land with full unit + Compose-test coverage before the surface change in #252.
- **No new dependencies, no Koin changes, no `gradle/libs.versions.toml` edits.** `DropdownMenu` / `DropdownMenuItem` ship in the existing `composeBom = 2026.02.01`. No new icon imports (the menu has no leading icons). The `ThreadViewModel` Koin binding at `AppModule.kt:36` is unchanged — `onOverflowEvent` adds no constructor parameter.

## Patterns established

- **Single-`onEvent`-sink composable for homogeneous menus/lists; per-callback shape for heterogeneous sheets.** The contrast is `ThreadOverflowMenu(expanded, onDismiss, onEvent, modifier)` vs [`ChannelInfoSheet`](../features/channel-info-sheet.md)'s six named callbacks. The rule: when every emitted event is the same shape (no per-event payload, no per-event downstream UI variation worth naming in the type system), use one `onEvent: (FooEvent) -> Unit` sink; when affordances are visually-grouped distinct surfaces that downstream tickets may swap independently (rename dialog ≠ workspace picker ≠ archive confirmation), use named callbacks. Don't mix shapes inside one composable.
- **`data object` (not plain `object`) for parameterless sealed cases.** Sole behavioural difference is the auto-generated `toString`/`equals`/`hashCode`. The `toString` makes Compose-test assertion failures (`log == listOf("dismiss", "event:NewSession")`) readable without a custom matcher. If a future ticket adds a payload field (`Rename(newName: String)`, etc.) the case migrates to `data class` — `data object` is the lowest-friction predecessor for that migration.
- **Co-locate the screen-feature sealed event type next to its primary consumer.** `ThreadEvent` lives in `ThreadViewModel.kt` because the VM dispatcher (`onOverflowEvent`) is the only consumer in this slice — even though the precedent `DiscussionListEvent` / `ChannelListEvent` declare next to the screen file. When the screen layer becomes the dispatch site (the eventual `ThreadScreen(state, onEvent)` collapse), the placement may be relocated; either location keeps the same package.
- **Combined-log recorder for asserting cross-callback ordering in Compose tests.** When two recorders fire from one user action and the assertion is "X happens before Y", use one shared `mutableListOf<String>` with both recorders pushing tagged entries (`"dismiss"`, `"event:NewSession"`) and assert the list equals the expected ordered shape. Two separate recorders (a counter + a list) can't express order; the combined log can. Apply to any future Compose test that needs to pin "A fires before B" inside a single `onClick`.
- **`thread_overflow_*` namespacing for the menu's string keys.** Adopt `<feature>_<role>` for any future menu that ships before a global i18n pass (the existing keys `discussion_list_*`, `channel_list_*`, `promote_dialog_*`, `settings_*` follow the same shape — `<screen>_<role>` for user-facing copy, `cd_*` for content descriptions). The five `thread_overflow_*` keys are the canonical home for any future thread-overflow follow-up that needs to localise an existing item label or add a sixth.

## Lessons learned

- **`RecordingRepo` for VM unit tests > `FakeConversationRepository` when the assertion is "did the VM call method X?".** `FakeConversationRepository` requires the test to project the call's effect through `observeConversations` and assert against the resulting `Conversation` set (the archive-removes-from-non-archived-filter contract). That's a real coupling against the fake's internal projection — replace the fake with a buggy stub that re-emits the wrong set and the test silently passes. `RecordingRepo` reads the call out directly (`repo.archiveCalls == listOf(id)`), one indirection less and one less coupled. Use `FakeConversationRepository` when the test cares about the repository's observable contract (the `state_*` tests in this same file); use `RecordingRepo` when the test cares about the VM's *call shape*.
- **`flowOf(emptyList())` / `flowOf(null)` defaults on `observe*` methods are non-optional for `RecordingRepo`.** The VM subscribes to all three (`observeConversations`, `observeMessages`, the implicit `observeLastMessage` if added later) at construction via the `combine` block. Returning a non-emitting flow (e.g. `Flow { /* never emits */ }`) hangs the `combine` — it never produces a first value, the `WhileSubscribed(5_000)` `stateIn` stays on `initialValue`, and any test that does `vm.state.first { … }` deadlocks. The `flowOf(...)` shape emits one value and completes, which is enough for `combine` to produce a first frame and for `WhileSubscribed` to start.
- **`DropdownMenu` already dismisses itself on outside-tap; explicit item taps are the only path that needs to call dismiss.** `onDismissRequest = onDismiss` covers the back-press + scrim-tap paths. Inside `DropdownMenuItem.onClick`, calling `onDismiss()` before `onEvent(...)` is the load-bearing pattern — both because the Compose test pins the ordering in its combined-log assertion *and* because downstream host wiring (dialogs / sheets / nav transitions opened from these events) needs the menu closed before the new surface mounts to avoid Compose layout layering issues. Inverting the order ("emit the event, let the host close the menu") would push close-coordination into every event handler and break the surface-switch invariant whenever the host fires a dialog open instead of a screen swap.
- **`InstrumentationRegistry.getInstrumentation().targetContext.getString(resId)` is the right lookup for `androidTest` Compose tests asserting against translated labels.** `composeTestRule.activity.getString(...)` is the alternative but requires `createAndroidComposeRule<Activity>()` (heavier — provisions a real activity); the instrumentation registry is already wired by `@RunWith(AndroidJUnit4::class)` and reads the same `strings.xml` that the production composable resolves. Use this whenever a Compose test asserts on text that comes from `stringResource(...)` rather than an inline literal — pinning the literal in the test body would diverge silently the first time the English copy changes without a test update.
- **`ThreadEvent` could have lived in its own file but didn't, because the sole consumer is `ThreadViewModel`.** A standalone `ThreadEvent.kt` would have telegraphed "ready for an external consumer" prematurely. Co-located with the VM, the sealed surface signals "this is the VM's event vocabulary; widen scope when the screen consumes it." When [#252](https://github.com/pyrycode/pyrycode-mobile/issues/252)'s mount work lands `onEvent = vm::onOverflowEvent` at the `MainActivity` destination block, the type stays where it is — the screen now becomes a second consumer but the placement-next-to-VM still resolves to one source of truth in the same package.
