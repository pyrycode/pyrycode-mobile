# #497 — Synchronize handshake-phase crypto methods against `close()`

**Issue:** [#497](https://github.com/pyrycode/pyrycode-mobile/issues/497) ·
**Spec:** [`docs/specs/architecture/497-synchronize-handshake-phase-crypto.md`](../../specs/architecture/497-synchronize-handshake-phase-crypto.md) ·
**PR:** [#518](https://github.com/pyrycode/pyrycode-mobile/pull/518) ·
**Feature doc updated:** [Noise_IK session](../features/noise-ik-session.md) ·
Size **XS**, `security-sensitive`. Commit `e5902b1`.

## Summary

Closes a **use-after-wipe** window in [`NoiseIkSession`](../features/noise-ik-session.md) ([#298](298.md)).
The class already commits to its instance monitor as a **deterministic backstop** — `encrypt`/`decrypt`/`close`
(and, since [#303](303.md), `writeRekeyInit`/`readRekeyResp`) are all `@Synchronized` — against the silent,
catastrophic nonce-reuse a same-direction race would cause under ChaCha20-Poly1305. The two **handshake-phase**
entry points, `writeInit` and `readResp`, were the last un-synchronized methods. `close()` wipes and nulls
`handshake` (the device static-key copy + handshake secrets); it could run concurrently with an in-flight
`writeInit`/`readResp` — e.g. a transport `Down` teardown landing mid-handshake while the pump is still driving
the IK exchange — and the handshake path could then dereference `handshake` **after** `close()` destroyed it.

The fix adds `@Synchronized` to both methods (they lock on `this`, the same monitor the other five already
acquire) plus a one-line KDoc **Threading** edit so the enumerated synchronized set matches the code. Method
bodies are untouched. Manifests only with `USE_RELAY_REPOSITORY` on; filed from the Cross-Repo Code Review
2026-07-03. **Same class of defensive crypto-lifecycle hardening as the sibling findings** [#495](495.md)
(re-key response watchdog) and [#496](496.md) (close-then-connect race).

## The fix

Two annotations + one KDoc line — one production file, no body changes.

```kotlin
@Synchronized
fun writeInit(): ByteArray { … }             // NoiseIkSession.kt:127 — body unchanged
@Synchronized
fun readResp(resp: ByteArray): String { … }  // :145 — body unchanged
```

KDoc **Threading** paragraph (`:52-59`) — the enumerated set grew from `[encrypt]/[decrypt]/[close]` to
`[writeInit]/[readResp]/[encrypt]/[decrypt]/[close]`, and gained the clause that a teardown `[close]` firing
mid-handshake therefore cannot destroy `handshake` out from under an in-flight `[writeInit]/[readResp]`.

**Why the annotation, not a race test.** `@Synchronized` on an instance method sets the JVM `ACC_SYNCHRONIZED`
method flag (it does **not** compile to a `monitorenter` block), locking on `this` — the same monitor, no new
lock object, no lock ordering. After the change `close()` and an in-flight handshake step are mutually
exclusive: `close()` either runs fully first (the step then reads `handshake == null` → the existing
`IllegalStateException("session is closed")`, a clean caller-bug signal, **not** a wipe-corrupted read), or it
waits for the bounded step and then wipes. The interleaved-mid-body ordering — the use-after-wipe — is excluded.

The `close()`-waits-before-wipe path extends the [#298](298.md) device-static-key RAM window by at most **one
bounded, non-blocking crypto op** (`hs.writeMessage`/`hs.readMessage` over ≤128 KiB buffers — the inbound cap
is enforced upstream at the WS transport, [#306](306.md)). That is the correct behaviour: you cannot safely
wipe key material *during* a step that is reading it, and the extension is negligible against #298's
whole-handshake bound.

## Patterns established

- **When a class commits to a monitor as a deterministic backstop, the enumerated synchronized set is an
  invariant — join it in full, and make the doc match the code.** `NoiseIkSession` treats the lock as *the
  floor*, not a per-method optimization; leaving two methods off the set was a latent gap even though the
  single-pump contract said the race "should not occur." The fix isn't just the two annotations — it's
  restoring the property "every method that touches shared cipher/handshake state is `@Synchronized`, and the
  KDoc says so." Extending an established local synchronization pattern is cheap deterministic code mirroring a
  neighbour, per **Evidence-Based Fix Selection** — not a speculative new mechanism.
- **Make the doc-matches-code invariant *executable*.** Rather than trust prose, the ticket lands a reflective
  test asserting `Modifier.isSynchronized` over the **full** documented set (the two new methods *plus* the
  existing five). Enumerating the whole set — not just the two new entries — locks the invariant against a
  future refactor silently dropping an annotation off any method. This is the deterministic, executable form of
  AC #2 ("the doc's enumerated set matches the code").

## Lessons learned

- **A structural/annotation assertion is the honest bar when there is no injectable mid-body seam — do not
  ship a flaky race test.** `writeInit`/`readResp` are plain synchronous JVM methods with no coroutine
  suspension point mid-body, so (unlike [#496](496.md)'s coroutine-`finally` seam, which had a cancellation
  point to gate deterministically) there is nothing to interleave a two-thread close-vs-handshake test against.
  Any such test would be timing-dependent and false-green-prone. The guarantee here is **structural** — the two
  methods join an already-tested five-method pattern — so the reflective `Modifier.isSynchronized` assertion
  (deterministic: `@Synchronized` sets `ACC_SYNCHRONIZED`, observable via reflection, no threads) plus the
  unchanged-behaviour suite *is* the honest bar. Contrast [#496](496.md), where a genuine interleaving *was*
  reproducible and therefore *was* required.
- **"No blocking I/O under the lock" needs the caller-supplied callback traced, not assumed.** Code review
  flagged that the spec's blanket "no blocking I/O under the lock" glossed over the one indirection:
  `writeInit` → private `buildHello()` → the injected `lastEventId()` supplier. In production
  ([#416](416.md), `AppModule.kt`) that supplier is `{ get<RelayRepositoryCoordinator>().replayCursor.latest }`
  — and `ReplayCursor.latest` is a `MutableStateFlow.value`, a **lock-free volatile read** behind a
  cached-singleton Koin lookup. No foreign lock is acquired while the session monitor is held, so no ABBA cycle
  with `close()` can form and the "no blocking under the lock" claim holds. The lesson: a "pure in-memory"
  method that invokes a caller-supplied lambda is only lock-safe if that lambda is *verified* lock-free — trace
  it before adding a lock above it.

## Testing

Unit-only (`./gradlew spotlessCheck test lint assembleDebug` all green). No instrumented test — pure-JVM
`noise-java`, byte-array in/out; `connectedAndroidTest` not run (no device needed, same posture as
[#298](298.md)/[#303](303.md)).

- **AC #3 — the structural assertion.** `synchronizedSet_coversHandshakeLifecycleAndRekeyMethods` looks up each
  of the seven methods via `NoiseIkSession::class.java.getDeclaredMethod(name, …paramTypes)` (`ByteArray::class.java`
  for the `[B` params) and asserts `java.lang.reflect.Modifier.isSynchronized(method.modifiers)` is `true` for
  all of them: `writeInit()`, `readResp(ByteArray)`, `encrypt(ByteArray)`, `decrypt(ByteArray)`, `close()`,
  `writeRekeyInit(ByteArray)`, `readRekeyResp(ByteArray)`. Deterministic — no threads, no timing, not flaky.
  Signatures are unmangled (no `@JvmName`/inline-class), so the reflected names are exact and `getDeclaredMethod`
  resolves.
- **AC #4 — unchanged behaviour.** The existing suite (handshake round-trip, re-key happy path + atomic swap +
  peer-static continuity, AEAD round-trip + direction/AD/prologue guards, state guards, close idempotence)
  stays green. The annotation is single-threaded-transparent.

## Security (`security-sensitive`)

Architect self-review **PASS** (9-category findings list in the spec's `## Security review`); code review
**PASS** ([PR #518](https://github.com/pyrycode/pyrycode-mobile/pull/518), zero findings above the NIT
threshold). The change **strictly strengthens** the posture:

- **Concurrency / crypto** — this is the fix's category. `close()` and an in-flight `writeInit`/`readResp`
  become mutually exclusive on `this`; the mid-body interleaving that caused the use-after-wipe is excluded. The
  added lock can only *reduce* interleaving, so it cannot open a nonce- or key-reuse window. No deadlock:
  `writeInit`/`readResp` call only the non-synchronized private helpers `buildHello()`/`parseHelloAck()`, never
  another `@Synchronized` method on `this` (reentrant anyway); single monitor, no lock ordering. No RNG/KDF/
  primitive change.
- **Secrets / key hygiene** — strengthening. The change closes a use-after-wipe of the device static-key copy +
  handshake secrets held in `handshake`. No new field holds the key/token, no new `Log`/`toString` surface;
  `NoiseIkSession` stays a plain class (not a `data class`).
- **No trust boundary moved** — `readResp` remains the sole untrusted→trusted crossing (network `noise_resp` →
  post-MAC `hello_ack`); the change gates on no attacker-controlled value, relocates no parse, weakens no
  validation. No blocking I/O runs under the lock (the `lastEventId()` callback path is lock-free, verified by
  code review — see Lessons learned), so a hostile relay cannot stall the pump while it holds the monitor.
- **Threat model** — the addressed threat is a mid-handshake teardown racing the pump's handshake driver, a
  **local memory-safety / secret-hygiene** defect, not remotely exploitable: it requires the single-pump
  contract to already be violated internally. Defense-in-depth, consistent with #298's bounded RAM window and
  the class's deterministic-backstop posture.
