# #451 — wire modal answer/cancel + arming/second-confirm + error to the live send path

**Issue:** [#451](https://github.com/pyrycode/pyrycode-mobile/issues/451) ·
**Spec:** [`docs/specs/architecture/451-wire-modal-answer-cancel-arming-error.md`](../../specs/architecture/451-wire-modal-answer-cancel-arming-error.md) ·
**PR:** [#453](https://github.com/pyrycode/pyrycode-mobile/pull/453) ·
**Feature doc:** [Modal answer flow](../features/modal-answer-flow.md) ·
Split from #444 (the **interaction** half of #439). **This is the behavior half** — the `ThreadViewModel`
decision logic + the outbound send wiring; **no UI of its own**. The render of the armed/second-confirm
affordance + dismiss snackbar + route-host forward is the sibling slice **#452**, `blockedBy` this one.
Size **S**, `security-sensitive`.

## Summary

The **behavior glue** of the permission/choice-modal interaction surface. It connects the shipped
[#445](445.md) projection ([`currentModal`](../features/current-modal-state.md) /
`ModalUiState.Open.defaultOptionId`) to [#438](438.md)'s concrete outbound send methods
(`RemoteConversationRepository.answerModal` / `cancelModal`), via (1) a new **outbound** passthrough on
[`RelayRepositoryCoordinator`](../features/relay-repository-coordinator.md) — the mirror of #445's inbound
`modalEvents` seam — and (2) `ThreadViewModel` decision logic that turns option taps / cancel into
`answerModal` / `cancelModal` calls. The one real behavior decision is the **fail-safe-deny UX belt**: the
producer's highlighted default (`Open.defaultOptionId`) answers on a **single** tap; any other option
**arms** and requires an explicit **second confirm** of the *same* armed option before it sends; a failed
send surfaces a one-shot, payload-free error signal. **No `ThreadScreen.kt` / `MainActivity.kt` touch** —
the screen's `onModalOption` / `onModalCancel` hooks stay unforwarded, exactly as #445 shipped `currentModal`
before #446 rendered it. Built test-first; all gates green; code review **PASS** after one rework (below).

## Patterns established

None new — this slice reuses the established seams end-to-end: the **outbound** passthrough is the mirror
of #445's inbound `modalEvents` `flatMapLatest` seam (a suspend call instead of a flow, because answer/cancel
are request/reply); the **defaulted-ctor-param** inertness trick is #445/#406's (a suspend lambda instead of
a flow, because the path is outbound); the **sibling `StateFlow` + one-shot `Channel` event** are the
`currentModal` / `navigationEvents` idioms. It does confirm two reusable calls:

- **An outbound control path is injected as a defaulted suspend lambda, not the coordinator/concrete repo.**
  A flow models an inbound stream; an outbound call needs a suspend lambda. Keeping the VM holding only the
  lambda (not the facade-bypassing concrete repo or the coordinator) keeps the VM dependency minimal and
  unit-testable with a plain recording lambda — no fake coordinator.
- **The behavior slice owns the transient interaction state; the render slice renders it** — the
  #445→#446 seam analog. `armedOptionId` (a scoped sibling `StateFlow`) is exposed here for #452 to draw the
  armed affordance, just as `currentModal` was exposed by #445 for #446 to draw the overlay.

## Lessons learned

- **`catch (IllegalStateException)` swallows `CancellationException` on the JVM/Android — the same trap as
  `catch (Exception)`, in disguise.** This is the **rework defect** (code review FAILed PR #453's first
  pass). `kotlinx.coroutines.CancellationException` is a `typealias` for `java.util.concurrent.CancellationException`,
  which **`extends IllegalStateException`** — so an `IllegalStateException` catch matches a coroutine
  cancellation. It is reachable here: when `viewModelScope` is cancelled (VM cleared / user leaves the
  thread) while a send is suspended in `sendAndAwaitReply` → `CompletableDeferred.await()`, `await()` throws
  a **raw** `CancellationException`, the catch swallows it, structured cancellation breaks, and a spurious
  `modalSendErrorChannel.trySend(Unit)` fires. **Fix (one line per send method):** `catch (e:
  CancellationException) { throw e }` **must precede** the typed catches in **both** `sendAnswer` *and*
  `sendCancel` (`:418`/`:438`), with the `kotlinx.coroutines.CancellationException` import. A broad `catch
  (Exception)` / `catch (Throwable)` is forbidden for the identical reason. The original spec's `§ Security
  review` had *certified the opposite* ("CancellationException is not caught, so structured cancellation is
  preserved") — a false fail-closed certification, the **architect's** column on a `security-sensitive`
  ticket, which is why the rework routed `needs-rework:architect` not `…:developer`. See
  [[catch-illegalstate-swallows-cancellation]]. The regression test
  `modalSend_scopeCancellationMidSend_doesNotEmitErrorSignal` (`:550`) hosts the VM in a real
  `ViewModelStore`, suspends a send on a never-completing deferred, `store.clear()`s the scope, and asserts
  **no** `modalSendErrors` fires — verified RED→GREEN (remove the rethrow → spurious error). Any future
  suspend send-path that `catch`es `IllegalStateException` needs the same leading rethrow.
- **The stale-arm guard is structural, not a clearing coroutine.** Scoping the arm to its own `modalId`
  makes a stale arm **inert by construction**: `armedOptionId` derives `null` for a non-matching modal (so
  it can't be displayed), and the second-confirm equality `armedModalOption.value == ArmedModalOption(
  open.modalId, optionId)` requires a modalId match (so it can't auto-confirm a fresh modal). No reactive
  arm-clear coroutine was built — the scoping *is* the "resets on resolve" property (Simplicity First +
  belt-and-suspenders-with-deterministic-fabric: the deterministic guard is the equality, not a stochastic
  clear). Tested by `staleArm_cannotPreArmAFreshModal`.
- **The arm clears on the send *attempt*, not on success.** `sendAnswer` sets `armedModalOption.value =
  null` **before** launching — the second-confirm gesture is consumed whether the send succeeds or fails.
  `currentModal` stays `Open` until the daemon resolves it, so the user may answer again after a failure;
  the VM does **not** auto-retry (first-answer-wins is server-side, so a blind retry could race the daemon's
  dedup). Keeping it armed for a one-tap retry is a deferred #452 UX call, not built here.

## Security (`security-sensitive`)

This opens the **decision-to-send** path for a permission answer (it injects "allow/deny this command" into
the supervised `claude`). The load-bearing properties (architect self-review **PASS** after the rework
correction; code review **PASS**):

- **The VM answers the modal it knows is open, not a UI-claimed one.** `onModalOption`/`onModalCancel`
  derive `modalId` from `currentModal.value`; the UI supplies only the tapped `optionId`. A compromised UI
  cannot redirect an answer to a *different* modal; the daemon validates the `optionId` against its own
  option list (pyrycode#706).
- **Fail-safe-deny preserved.** Single-tap is gated to `optionId == open.defaultOptionId` (the producer's
  deny/safe option — `reject_once` / `exit`); every other option requires an explicit second confirm of the
  *same* armed option. No auto-answer, no destructive-vocabulary interpretation — the gate is data-driven
  off `defaultOptionId`, over-capturing `reject_always` (a harmless deny variant).
- **No trust-bearing value minted here.** `answer_token` is minted by #438's concrete repo; this slice
  mints nothing.
- **Never-log.** The error event carries `Unit`; no `Log.*`/`println`/`Timber` in the VM send methods or the
  coordinator passthrough (code-review-verified); `RelayErrorException`'s message is caught and not surfaced.
- **Structured cancellation preserved** — the `CancellationException`-rethrow above (the corrected property).
- **Tapjacking** on the live answer buttons (touch-obscured filtering) is owned by **#452** (the slice that
  makes the taps live + draws the buttons), inherited from #446's note; mitigated *by design* here since the
  single-tap option is the deny default.
