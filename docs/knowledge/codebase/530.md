# #530 — `RemoteConversationRepository.rename` over v2 (`rename_conversation`)

**Issue:** [#530](https://github.com/pyrycode/pyrycode-mobile/issues/530) ·
**Spec:** [`docs/specs/architecture/530-wire-rename-conversation.md`](../../specs/architecture/530-wire-rename-conversation.md) ·
**PR:** [#538](https://github.com/pyrycode/pyrycode-mobile/pull/538) ·
**Feature doc:** [Remote conversation repository](../features/remote-conversation-repository.md) § `rename` (updated) ·
Size **S**, `security-sensitive` (PASS).

## Summary

Fills the last open mutation stub on `RemoteConversationRepository` — `rename` — replacing its
`UnsupportedOperationException` throw with a live v2 round-trip against the daemon's
`rename_conversation` message (server-side [pyrycode/pyrycode#820](https://github.com/pyrycode/pyrycode/issues/820)).
The shape is [`promote`](348.md) minus `cwd`: encode a new `RenameConversationPayloadDto
{conversation_id, name}` → `sendAndAwaitReply` → decode the correlated `conversation_updated` reply
through the existing #318 `ConversationResponseDto.toConversation()` boundary → `upsertConversation` →
return the server-authoritative `Conversation`. The single fold re-emits both AC surfaces (conversation
list tier + thread top bar `displayName`) — no ViewModel change needed. `rename` is now wired end-to-end;
tapping **Rename** (`RenameDialog`, thread overflow menu / Channel Info sheet) actually persists.

## Files touched

- **`app/src/main/java/de/pyryco/mobile/data/network/RenameConversationPayloadDto.kt`** (new, 31 lines) —
  encode-only request DTO, own file (ktlint single-public-type rule). Both fields (`conversation_id`,
  `name`) required/non-null — deliberately **not** a reuse of `PromoteConversationPayloadDto` (promote
  also carries a required `cwd`, which rename neither has nor means).
- **`app/src/main/java/de/pyryco/mobile/data/repository/RemoteConversationRepository.kt`** (+42/−4):
  - `rename` (`:1380`) — build the `rename_conversation` `Envelope` → `sendAndAwaitReply` (throws on
    server `error` / not-`Open` before any mutation) → `MobileJson.decodeFromJsonElement<ConversationResponseDto>(reply).toConversation()`
    → `upsertConversation(conversation)` → `return conversation`. No per-error catch — inherits
    `mapError`/`sendAndAwaitReply`'s centralized mapping unchanged (same as `promote`).
  - New companion constant `TYPE_RENAME_CONVERSATION = "rename_conversation"` adjacent to
    `TYPE_PROMOTE_CONVERSATION`. No second reply-type constant — `TYPE_CONVERSATION_UPDATED` (already
    present from #348) is reused; the send path decodes the correlated reply regardless of `type`.
  - `onInbound`'s success arm is **unchanged** — `conversation_updated` was already routed there by #348
    for `promote`'s reply, so rename's reply rides the same branch with zero additional wiring.
- **`app/src/test/java/de/pyryco/mobile/data/repository/RemoteConversationRepositoryTest.kt`** (+205) —
  a `startRename` helper (sibling of `startPromote`, drops the `workspace` param) plus seven tests
  mirroring the `promote_*` suite: request-encode (exactly two keys, no `cwd`), success round-trip +
  fold into `observeConversations`, server-authoritative name (reply's name wins over the request's),
  not-connected → `IllegalStateException` (no fold), `conversation.not_found` → `IllegalArgumentException`
  (no fold), other server error → `RelayErrorException` (no fold), malformed reply → decode throws (no fold).

**Not touched** (all reused verbatim, zero fan-out): `ConversationResponseDto`/`toConversation()` (#318,
reply decode is identical to `promote`'s), `upsertConversation` (#347/#348, the confirmed-fold), the
`#490` `launchGuardedRepoCall` guard, `ThreadViewModel.kt` (the `RenameSubmit` call site is unchanged —
it already ran inside the guard, passing `state.value.conversationId`), and
`ThreadViewModelTest.kt` (the existing `guardedRepoCalls_whenRepositoryThrowsEachHandledType_areSwallowedWithoutCrashing`
test already covers "a failing rename does not crash"; no duplicate test added).

## Patterns established

None new — this ticket is a second, confirming instance of the `promote`-shaped mutation template
(`#346`/`#347`/`#348`'s build-request → `sendAndAwaitReply` → decode-reply → confirmed-fold → return
shape), not a new pattern. Worth noting for future stub-fills on this class: **a mutation minus a field**
(rename = promote minus `cwd`) is cheap to spec and implement precisely because #348 already proved the
shape; look for the nearest shipped sibling before designing a new mutation from scratch.

## Lessons learned

- **The apparent AC tension (IAE crashes vs. "failed rename is a silent no-op") is not a contradiction —
  it's the `#490` guard's existing, deliberate posture, reused unchanged.** `conversation.not_found` →
  `IllegalArgumentException` is real (mirrors `promote`/`sendMessage`), and `GuardedRepoLaunch.kt:26-27`
  deliberately does **not** catch IAE (treats an unknown-conversation id as an impossible-by-construction
  programming-bug signal). It's reachable-safe here because the call site always passes the
  currently-open, hence server-known, `conversationId` — identical reachability profile to `promote`. No
  guard change, no new catch arm needed; this ticket is proof the existing invariant generalizes to a
  second mutation without modification.
- **Zero-fan-out mutation stub-fills need no ViewModel/UI touch at all.** Because `observeConversations`
  and the thread top bar's `displayName` were already derived from the `projection` `StateFlow` that
  `upsertConversation` writes to, wiring the wire message was sufficient to satisfy both AC surfaces (list
  tier + top bar) — confirmed by the pre-existing `state_displayName_reemitsOnRename` VM test, which
  needed no change. Worth checking for any remaining Phase-4 stub before assuming a UI-layer companion
  ticket is required.
