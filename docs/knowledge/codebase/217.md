# #217 — feat(ui/sheets): `ChannelInfoSheet` stateless composable (Figma 20:48)

Lands [`ChannelInfoSheet`](../features/channel-info-sheet.md), the second **sheet** composable in `ui/conversations/components/` (after [`WorkspacePickerSheet`](./212.md)). Renders Figma `20:48`: a conversation-name title row with a close icon, **About** section with five label / value rows (workspace path, created, last activity, session count, message count), **Memory** section with an empty-state `None` text + `Install` button (or, when populated, a right-aligned column of plugin names), **Actions** 2×2 grid (Rename | Change workspace, Archive | Delete) of `FilledTonalButton` cells, and a low-opacity `Channel ID: …` footer whose long-press copies the ID via `LocalClipboardManager`. Stateless contract per spec — no `ViewModel`, no repository binding, no time-formatting, no entry-point integration; the host that wires this sheet into the Channel List long-press / Thread overflow flows, computes the relative-time labels, and pairs it with the rename / archive / delete confirmation surfaces lands in the follow-up host ticket.

See [`../features/channel-info-sheet.md`](../features/channel-info-sheet.md) for the evergreen contract.

This is the canonical Compose row-cell shape — the weight is a property of the layout context (where the cell sits), not the cell's intrinsic identity.

## Patterns established

- **`ChannelInfoUiModel` data class colocated in the composable's file, `internal` visibility, no `equals`/`hashCode` override.** First "UI model" type explicitly named `*UiModel` in `ui/conversations/components/` — the package's existing types are repository / domain models ([`Conversation`](../features/data-model.md), [`Message`](../features/data-model.md), [`ThreadItem`](../features/conversation-repository.md)) that flow through the UI, not UI-shaped projections of them. The `ChannelInfoUiModel` is deliberately distinct: it's the **caller-pre-rendered** projection the host produces from the repository's data, not a transparent passthrough of repository types. **Rule for future stateless composables that need a multi-field projection of repository state:** colocate a `*UiModel` data class in the composable's own file, `internal`, no manual `equals`/`hashCode` (Kotlin's data-class generation is correct and stable for Compose's structural-equality recomposition checks). The host owns the projection mapping; the composable owns nothing but the UI contract.
- **The `ModalBottomSheet` shell + `*Content` body split is now a package-wide convention, not a one-off.** [#212](./212.md) established it; this ticket carries it verbatim for a second sheet. Any future sheet in `ui/conversations/components/` follows the same shape without re-litigating: public `internal` composable that wraps `ModalBottomSheet(onDismissRequest = onDismiss, sheetState = sheetState) { *Content(...) }`, sibling `internal` `*Content` that holds the body and takes the same callbacks minus `sheetState`, previews and tests target `*Content`. **Rule:** if you're adding a new `ModalBottomSheet`-based composable to this package, mirror this ticket's file structure; the split is load-bearing for both previews and tests.
- **Pre-rendered label strings are the caller's responsibility, not the composable's.** `createdLabel: String` and `lastActivityLabel: String` arrive as `"3 weeks ago"` / `"2 hours ago"` already formatted — the composable does no `kotlinx.datetime` resolution, no resource lookup, no plural handling. The host computes the labels via a shared relative-time helper (today: TBD; the helper that [`ConversationRow`](../features/conversation-row.md) uses is the natural reuse target) and passes them in. **Rule:** stateless composables in this package never own time formatting, number formatting, or any locale-sensitive projection — that's a host concern. The composable's contract is "render these strings exactly", not "produce these strings from this data".
- **`combinedClickable` long-press copy follows the [`ConversationRow.kt:7,44`](../features/conversation-row.md) shape verbatim.** Same `@OptIn(ExperimentalFoundationApi::class)`, same `remember { MutableInteractionSource() }`, same `indication = null` when the affordance shouldn't paint a ripple. **Rule:** any new long-press affordance in this codebase uses `combinedClickable` (not a custom gesture detector); pair it with `LocalHapticFeedback.performHapticFeedback(HapticFeedbackType.LongPress)` for user-facing confirmation when no other surface (snackbar / toast) is wired to fire on success.
- **`LocalClipboardManager` is the project's default clipboard API today.** The newer `LocalClipboard` / `Clipboard.setClipEntry` shape compiles but generates a deprecation warning at the legacy call site; the spec retains the legacy API explicitly because (a) it's the AC's literal requirement and (b) migration day is the day the legacy API is removed from the BOM, not now. **Rule:** new clipboard-write call sites use `LocalClipboardManager.current.setText(AnnotatedString(...))` until the entire codebase is migrated in a single atomic pass.

## Lessons learned

- **`TextOverflow.StartEllipsis` only fires when the right `Text` has a layout constraint that's narrower than its measured width** — for the workspace row, that means dropping the leading `Spacer(weight(1f))` and giving the right `Text` itself `Modifier.weight(1f)`. The "spacer + right-aligned text" shape from the default `AboutRow` branch leaves the right `Text` at its intrinsic width, which for short values is fine (no overflow) but for long paths means the text grows the row beyond `fillMaxWidth` and gets clipped instead of ellipsized. Took one preview round to spot — the four short-value rows all rendered correctly with the spacer; only the workspace path on a 412dp width revealed the constraint problem. **Lesson:** when a `Row` cell needs to ellipsize, give *that cell* the weight, not a sibling `Spacer`. The weight is what tells the layout system "this is the cell that should shrink to fit the available space"; without it, the text measures to intrinsic width and overflow has nothing to bite against.
- **`combinedClickable`'s deprecation surface for `LocalClipboardManager` is loud but expected.** The IDE flags `LocalClipboardManager` and `clipboardManager.setText` as deprecated, suggesting `LocalClipboard` + `Clipboard.setClipEntry`. The spec explicitly retains the legacy API; the warnings are accepted noise. **Lesson:** when a spec carries an explicit direction against a deprecation suggestion, leave the deprecation warning rather than "fixing" it — the spec captures a reason (the legacy API is the AC's literal wording) and silencing the warning by migration changes the user-facing contract underneath the spec without flagging it. If you think the deprecation is worth chasing, raise it as a follow-up ticket; don't tuck the migration into a UI-render ticket.
- **`FilledTonalButton`'s default `ButtonDefaults.ContentPadding` is `horizontal = 24.dp, vertical = 8.dp`, larger than Figma `20:96`'s `py-[10px]` would imply** — the cells render taller than Figma's strict 40px height. The spec explicitly accepts this delta as visually negligible; overriding `contentPadding` to match Figma would buy back ~4dp of vertical space at the cost of slightly cramped touch targets (the M3 default exists for a reason — it's the minimum accessible tap height). **Lesson:** Figma-locked layouts that come from web-style designs (`py-[10px]`-style classes) sometimes specify padding that violates native Android touch-target guidance; trust the M3 component defaults over the Figma pixel value when the difference is small. Document the deviation in the spec so reviewers don't keep flagging it.
- **The `ChannelInfoUiModel` data class with eight fields is on the upper edge of "still readable at the call site"** — a host that constructs one is going to be ~10 lines of named-argument assignments. If a future iteration adds a ninth field (per-conversation tag chips, notification preference, last-paired-device — all plausible), consider whether the new field belongs on the model or whether it should live in a sibling sub-model (e.g. `ChannelInfoUiModel.Notifications`). Compose's structural-equality recomposition cost scales linearly with field count; eight is fine, fifteen starts to merit a re-shape. **Lesson:** UI-model data classes are cheap to widen by one field but expensive to refactor once a half-dozen call sites construct them. Flag any second-field-addition that crosses the ten-field threshold as a refactor candidate.
