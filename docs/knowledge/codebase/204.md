# #204 — feat(ui/thread): context-aware overflow menu items (discussion vs channel)

Wraps the five common items the [`ThreadOverflowMenu`](../features/thread-overflow-menu.md) ([#251](./251.md), mounted [#252](./252.md)) renders with one conditional item on each side: discussions get a leading **Save as channel…** that emits `ThreadEvent.SaveAsChannel`; channels get a trailing **Install memory plugin** that opens `MEMORY_PLUGIN_DOCS_URL` via `LocalUriHandler.current.openUri(...)`. The two new items are mutually exclusive — there is no third state. The `SaveAsChannel` event is a no-op `Unit` arm in `ThreadViewModel.onOverflowEvent` (joins the existing `NewSession`, `ChangeWorkspace`, `ChannelInfo` no-op group); the promotion-dialog wiring is #142's scope, parallel to [#141](./141.md)'s rename dialog wiring. Split from [#140](https://github.com/pyrycode/pyrycode-mobile/issues/140); the third per-item follow-up after [#141](./141.md) (`Rename`) and [#252](./252.md)'s mount.

## Summary

- **`ThreadOverflowMenu` gained one `isPromoted: Boolean` parameter** between `expanded` and `onDismiss` — "what to render" parameters grouped before "what to do" callbacks, no default value (the caller `ThreadTopAppBar` always knows). The composable body adds two `if` blocks wrapping the five existing common items: `if (!isPromoted) { DropdownMenuItem(text = Save as channel…, onClick = { onDismiss(); onEvent(ThreadEvent.SaveAsChannel) }) }` at the top, `if (isPromoted) { DropdownMenuItem(text = Install memory plugin, onClick = { onDismiss(); uriHandler.openUri(MEMORY_PLUGIN_DOCS_URL) }) }` at the bottom. The five common items between them are untouched.
- **`ThreadEvent.SaveAsChannel` is a `data object` case** — added to the sealed surface in `ThreadViewModel.kt` after `ChannelInfo`. The dispatch in `onOverflowEvent` is a no-op (joins the existing `NewSession, ChangeWorkspace, ChannelInfo, → Unit` arm; one-line edit). No dialog mounting, no `repository.promote(...)` call — that's #142's scope, parallel to [#141](./141.md)'s rename slice (which filled `Rename` from no-op → `pendingRenameDialog.value = true`). The exhaustive `when` over the sealed surface means the case must exist at compile time so the spec adds it now and #142 fills the body.
- **No `InstallMemoryPlugin` event.** The install-memory-plugin item is URL-handler-only — `LocalUriHandler.current.openUri(MEMORY_PLUGIN_DOCS_URL)` runs synchronously from the item's `onClick`. Routing through the VM would add a hop with no state effect (the VM has no business state to mutate; the URL handler is the only side effect, and it's already a UI-layer concern). Same one-side-effect-per-item shape — just with the side effect happening at a different layer than `SaveAsChannel`'s eventual repository call.
- **`MEMORY_PLUGIN_DOCS_URL` is reused, not duplicated.** The constant already lives at `SessionBoundaryDelimiter.kt:37` as `internal const val MEMORY_PLUGIN_DOCS_URL: String = "https://pyryco.de/docs/memory-plugins"` for the empty-thread "install a memory plugin" `TextButton`. The ticket's Technical Notes suggested a `private const val` inside `ThreadOverflowMenu.kt`; the architect spec overruled that — `internal` scope already permits cross-package import from `ui/conversations/components/` to `ui/conversations/thread/`, and Phase 3+ swap-to-real-install-endpoint becomes a one-grep edit instead of two. Import added: `de.pyryco.mobile.ui.conversations.components.MEMORY_PLUGIN_DOCS_URL`.
- **`save_as_channel_action` is reused too.** The "Save as channel…" string already exists at `strings.xml:11` (added with `DiscussionListScreen.kt:208`'s long-press promote menu, [#25](./25.md)). The architect spec called out reuse explicitly — a parallel `thread_overflow_save_as_channel` key would split the localization surface across two identical-English entries. Only one new key was added: `thread_overflow_install_memory_plugin = "Install memory plugin"` (`thread_overflow_*` namespace per the [#251](./251.md) convention).
- **`ThreadTopAppBar` and `ThreadScreen` thread `isPromoted` down the chain.** `ThreadTopAppBar` grew one parameter `isPromoted: Boolean` placed between `onOverflowEvent` and `modifier` — keeps overflow-menu params adjacent. `ThreadScreen` passes `isPromoted = state.isPromoted` to `ThreadTopAppBar` inside the `topBar = { ... }` block; **no new screen parameter** because `ThreadUiState.isPromoted` already flows through `state: ThreadUiState` (the field was introduced upstream and is projected from `Conversation.isPromoted` in `ThreadViewModel`'s `combine` block — this ticket does not touch the projection). No `MainActivity` edit.
- **Test surface: two new visibility tests + two new tap tests; five existing tap tests updated.** All seven existing `ThreadOverflowMenuTest` `setContent` blocks gained `isPromoted = true` (channel mode is consistent across all five tap-an-existing-item tests; the items are present in both modes). The render-order test was split into two — `discussion_menu_items_render_in_documented_order_when_expanded` (`isPromoted = false`, asserts `save_as_channel_action` displayed at the top + `thread_overflow_install_memory_plugin` `assertDoesNotExist()`) and `channel_menu_items_render_in_documented_order_when_expanded` (`isPromoted = true`, mirror assertion). Two new per-item tests: `tapping_save_as_channel_dismisses_then_dispatches_event` (combined-log assertion `log == listOf("dismiss", "event:SaveAsChannel")`) and `tapping_install_memory_plugin_dismisses_and_opens_docs_url` (asserts `log == listOf("dismiss")` — `onEvent` never invoked — and a `RecordingUriHandler.openedUris == listOf(MEMORY_PLUGIN_DOCS_URL)` injected via `CompositionLocalProvider(LocalUriHandler provides fakeHandler)`).
- **`RecordingUriHandler` is a six-line file-local test double.** `class RecordingUriHandler : UriHandler { val openedUris = mutableListOf<String>(); override fun openUri(uri: String) { openedUris += uri } }` — mirrors `SessionBoundaryDelimiter.kt`'s `androidTest` injection seam shape. No Mockito / MockK; same direct-test-double convention as `RecordingRepo` ([#251](./251.md)) and `FakeConnectionStateSource`.
- **No new VM unit tests for `SaveAsChannel`.** The branch is a no-op with no observable side effect to assert; the compiler-enforced exhaustive `when` is the contract. No `ThreadViewModelTest` edits. The `onOverflowEvent_otherCases_doNotCallArchive` test from [#251](./251.md) (post-[#141](./141.md) iteration list `[NewSession, ChangeWorkspace, ChannelInfo]`) was *not* extended to include `SaveAsChannel` in this slice — the test asserts `archiveCalls.isEmpty()` and any case that doesn't call `archive` trivially satisfies it; adding `SaveAsChannel` to the iteration list would not catch a future bug `SaveAsChannel → repository.archive(...)` doesn't already catch.

## Patterns established

- **UI-side `LocalUriHandler.current.openUri(...)` is the canonical shape for "tap this menu item to open a URL" — no VM event hop.** Side-effect-from-`DropdownMenuItem.onClick` is fine when the side effect has no business meaning the VM has authority over (no state mutation, no repository call, no semantic consequence). Routing through a VM event would add a hop with no purpose. The contrast is `Save as channel…`'s dispatch through `ThreadEvent.SaveAsChannel` — that *does* go through the VM because the eventual promotion-dialog flow ([#142](https://github.com/pyrycode/pyrycode-mobile/issues/142)) needs the VM as authority over the dialog visibility flag and the `repository.promote(id, name)` launcher. Apply the discriminator to any future "open URL from menu item" case — if the URL is the entire side effect, capture `LocalUriHandler` and call `openUri` inline; if there's additional VM state to manage, route through an event.
- **Shared `internal const val` URL constants stay where the first caller lives, not in a parallel `Urls.kt`.** `MEMORY_PLUGIN_DOCS_URL` stayed at `SessionBoundaryDelimiter.kt:37` even though there are now two callers — both consume it via import. The `internal` scope is exactly the cross-package permission needed inside the same module. Moving the constant to a shared `ui/conversations/components/MemoryPlugin.kt` or `Urls.kt` peer file is a one-line refactor better paired with the Phase 3+ swap-to-install-endpoint work (which changes the URL anyway). Don't pre-extract for a future ticket that will rewrite the constant.
- **Reuse existing strings.xml keys when the English label is identical to an existing entry.** `save_as_channel_action` is reused across `DiscussionListScreen.kt:208` (long-press promote menu) and now `ThreadOverflowMenu.kt:29`. A parallel `thread_overflow_save_as_channel` key was rejected for the same reason `MEMORY_PLUGIN_DOCS_URL` is reused — two identical-English entries split the localization surface. The discriminator: same English copy + same semantic action → one key.
- **Mutually-exclusive conditional menu items render as two `if` blocks wrapping the always-rendered common items, not as a `when` over `isPromoted`.** A `when (isPromoted) { true -> { ...channel items... }; false -> { ...discussion items... } }` would either duplicate the five common items in both branches (~30 lines repeated) or collapse to the same `if` pair around two extra items. The `if` pair directly expresses "discussions get one extra item at index 0; channels get one extra item at the end" and matches AC wording 1:1. Apply to any future menu where a small number of mutually-exclusive items wrap a shared core.

## Lessons learned

- **`onEvent` is never invoked from the install-memory-plugin item — assert `log == listOf("dismiss")`, not by counting events.** The natural first instinct in the tap-then-URL test is to assert "events.size == 0" with a separate `mutableListOf<ThreadEvent>()` recorder. But the combined-log pattern already records dismisses *and* events into one list; checking `log == listOf("dismiss")` proves both "dismiss fired" *and* "no event fired" in a single equality assertion, with the same shape as the other six per-item tests. Don't introduce a second recorder when the first one already pins both halves of the contract.
- **`CompositionLocalProvider(LocalUriHandler provides fakeHandler) { ThreadOverflowMenu(...) }` must wrap *inside* `PyrycodeMobileTheme`, not outside.** `PyrycodeMobileTheme` is itself a `MaterialTheme { ... }` wrapper that provides Material-3 `CompositionLocal`s (color scheme, typography, shapes). Wrapping the URI handler provider *outside* the theme works for the URI handler — `LocalUriHandler` is a platform local independent of the theme — but defies the "nest test-specific providers inside the theme" convention and would break the moment a future test needs to override a theme-provided local (where outside-the-theme overrides would be shadowed by the theme's own `CompositionLocalProvider`). Keep the theme as the outermost frame and nest provider stacks inside it. The pattern matches `SessionBoundaryDelimiter.kt`'s test-time injection shape verbatim.
- **`UriHandler` is a Compose interface, not an Android one — the fake doesn't need `androidx.test.*` imports.** `androidx.compose.ui.platform.UriHandler` is a pure Kotlin interface (`fun openUri(uri: String)`); implementing it requires no Robolectric / Espresso / `ActivityScenario` machinery. Avoid reaching for `androidx.test.platform.app.InstrumentationRegistry` or `Intent` mocking when the side effect's surface is a Compose-platform local — the Compose-local injection is one-import, the Android-intent simulation would be ten.
- **The architect spec called the "preferred position assertion" `fetchSemanticsNodes()` + sequence equality; the implementation went with the "acceptable fallback" of visibility + tap-coverage.** Reading `fetchSemanticsNodes()` and asserting the in-order text sequence is the *directly-testable* expression of "Save as channel… at index 0" / "Install memory plugin at the last index", but the Compose-test toolkit's `fetchSemanticsNodes()` API in this codebase's `composeBom = 2026.02.01` produces verbose assertions (no built-in `assertOrderedTexts` matcher). The fallback the implementation took — assert visibility + assert the absence of the other-mode item + per-tap coverage of every item — is weaker on position but matches what the pre-#204 `menu_items_render_in_documented_order_when_expanded` test already did. Order-by-tap-coverage is the convention here; a future ticket that ships a stricter `assertOrderedTexts` helper can tighten all the order assertions in one place.
