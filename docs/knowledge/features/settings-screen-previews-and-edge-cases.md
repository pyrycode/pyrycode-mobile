# Settings screen — edge cases and previews

Every section below moved here verbatim and kept its heading, so its anchors are unchanged. Part of [Settings screen](settings-screen.md); see that document for the rest.

## Edge cases / limitations

- **All switch rows now persist end-to-end — no placeholder switches remain (as of #268).** The Use-wallpaper-colors (#89), Default-YOLO (#234), and Push-notifications (#268) switches all route through [`SettingsViewModel`](settings-viewmodel.md) → `AppPreferences`; toggle one, force-stop, relaunch, and its saved switch state sticks. The wallpaper switch no longer changes the app root's static dark palette. The screen no longer holds any `remember { mutableStateOf(...) }` switch local — the last one (`pushNotifications`) was removed in #268. Default YOLO and Push notifications are **write-live but read-dead**: persistence works, but nothing consumes the values yet (per-conversation YOLO stays off per #229; notification *delivery* is Phase 4). Don't add `rememberSaveable` or wire either into a consumer "just in case" — both are deliberate scope boundaries.
- **Use-wallpaper-colors initial-state surprise.** A user upgrading from a pre-#89 build will see the switch jump from "on" (the prior cosmetic stub initial state) to "off" (the persisted default from #88). This is correct: the placeholder was never persisted, so there's nothing to migrate. The app root now uses the static dark palette even if the stored switch is ON. Worth knowing only so a future "the Material You switch turned itself off after the update!" report doesn't trigger a bisect.
- **Most non-switch row taps are still no-ops** including the "Add" pill, every Memory row, and the Notifications section's "Notification sound" row. No nav, no toast. The interactive exceptions are: every Connection-section host row (since #750 — a non-owner row navigates to that host's own Settings; since #751 the owner's row instead opens the Edit host modal on itself, so every row in the section now acts — see below and [Host editor](host-editor.md)), the Storage section's "Archived discussions" row (since #94 — navigates to the in-app [Archived Discussions screen](archived-discussions-screen.md) for this destination's own owner; inert when it owns none, since #715), the Storage section's "Log data" row (since #683 — opens the [`DebugBundleModal`](settings-viewmodel-how-it-works.md#log-data-download-683) on this destination's own owner; inert when it owns none, the same nullable-`onClick` rule as the row above it), the About section's "About" row (since #271 — navigates to the dedicated [About screen](about-screen.md); the former inline Open-source / Privacy / License rows and their behaviors moved there), the Appearance section's Theme row (since #87 — opens the `ThemePickerDialog`), and the Defaults section's "Default model" row (since #232 — `ModelPickerDialog`), "Default effort" row (since #233 — `EffortPickerDialog`), and "Default workspace" row (since #235 — opens the reused [`WorkspacePicker`](workspace-picker.md) host). The three switch rows — Use-wallpaper-colors (#89), Default YOLO (#234), Push notifications (#268) — are interactive via their `Switch`'s `onCheckedChange`, not a row `onClick`. Remaining external-link handlers (Memory) are Phase 3+ tickets.
- **Every saved host's full server id and relay URL are on screen at once (#750), not only the destination's own.** Accepted in the #750 security review as a widening of the exposure #749 already accepted, not a new category: neither value is authentication material (the pairing token and server static key never reach this screen), and the same inventory was already one tap away via the channel-list tree and `EditHostModal`. A screenshot or accessibility read now harvests the full paired-host list in one shot rather than one host at a time — worth knowing before treating "shows only my own host" as an invariant this screen still holds.
- **Row identity across a re-render is keyed by `serverId`, not position (#750).** `SettingsScreen`'s Connection section wraps each `HostIdentityRow` in `key(row.serverId)` inside a plain `Column` — Compose otherwise matches slots by call order, so a reorder (a rename that moves a record, a re-pair) would hand one host's composition to another. Shipped as a guard ahead of #751's edit/unpair slice, which is the case that would have made a missing key's blast radius observable rather than cosmetic. Don't remove it as "unnecessary" when giving a row further local state.
- **AC4 after a removal needs no navigation code, and has none (#751).** Nothing in the Settings route reacts to a host-list change: `PairedServerCollectionStore.remove` bumps the store's revision, `hosts()` re-emits, `connection` re-resolves, the removed host's row disappears, and — if it was the owner — `ownerMissing` flips true and the section falls back to the copy #750 already ships (see [Host ownership](settings-screen-how-it-works.md#host-ownership-749-750)). The destination itself never pops or retargets. Adding a pop or a navigate-away here on the theory that "the screen just lost its host" is the failure mode this design deliberately avoids, not a missing feature.

## Previews

Two `@Preview`s, both `private`, both at `widthDp = 412` to match Figma's frame width and the rest of the codebase:

- `SettingsScreenLightPreview` — `PyrycodeMobileTheme(darkTheme = false) { SettingsScreen(connection = PREVIEW_CONNECTION, themeMode = ThemeMode.SYSTEM, useWallpaperColors = false, archivedDiscussionCount = 11, defaultModel = Model.OPUS_4_7, defaultEffort = Effort.HIGH, defaultYolo = false, pushNotifications = true, defaultWorkspace = DEFAULT_SCRATCH_CWD, defaultWorkspaceLabel = null, workspacePickerVisible = false, onSelectTheme = {}, onToggleUseWallpaperColors = {}, onSelectDefaultModel = {}, onSelectDefaultEffort = {}, onToggleDefaultYolo = {}, onTogglePushNotifications = {}, onDefaultWorkspaceTapped = {}, onSelectDefaultWorkspace = {}, onWorkspacePickerDismissed = {}, onOpenHost = {}, onPairServer = {}, onBack = {}, onOpenArchivedDiscussions = {}, onOpenAbout = {}) }`. The `pushNotifications = true` literal (#268) matches the preference's ON-by-default so the toggle renders ON in the preview pane, consistent with Figma `17:2`. `PREVIEW_CONNECTION` (#750, replacing #749's single `host = Owned(...)` literal) is a private `SettingsConnectionState.Loaded` fixture with **two** hosts — the owner first (`Pyrybox`, `DaemonAbsent`/`Down`, so the green-relay / red-pyrycode diagnostic is visible) and a second, unnamed host (`Connected`/`Connected`, name falling back to its server id) — so the preview pane shows the owner badge, a chevron on the other row, and the unnamed-host fallback in one screenshot. `defaultWorkspace = DEFAULT_SCRATCH_CWD, defaultWorkspaceLabel = null` (#723) keeps this preview at the frame's own unbound state, so it stays comparable to the pre-#723 baseline and Figma's own "scratch" render.
- `SettingsScreenDarkPreview` — same as the light preview except `darkTheme = true` and (since #723) `defaultWorkspace = "~/Workspace/Projects/pyrycode-mobile"` with `defaultWorkspaceLabel = "Pyrycode Mobile"` — the named state the light preview's frame-fidelity requirement can't show, visible in one screenshot without a dedicated third preview.

Both previews must pass `themeMode` and `onSelectTheme` explicitly since #87 dropped the `themeMode` default, `onOpenArchivedDiscussions` since #94, `useWallpaperColors` + `onToggleUseWallpaperColors` since #89, `archivedDiscussionCount` since #164, `defaultEffort` + `onSelectDefaultEffort` since #233, `defaultModel` + `onSelectDefaultModel` since #232, `defaultYolo` + `onToggleDefaultYolo` since #234, the `defaultWorkspace` / `workspacePickerVisible` + workspace-picker callbacks since #235, `pushNotifications` + `onTogglePushNotifications` since #268, `onOpenAbout` since #271, `host` + `onPairServer` since #749, (#750) `onOpenHost` alongside `host`'s replacement by `connection`, `defaultWorkspaceLabel` since #723, and since #751 `hostEditor` (both previews pass `null` — closed, the frame's own state; the modal has its own two previews, see [Shared mobile modal](mobile-modal.md)) plus the five editor callbacks, and since #683 `logData` (both previews pass `null` — closed, same rule — plus the four Log data callbacks; `DebugBundleModal` carries its own five-state `@Preview` matrix, see [SettingsViewModel — how it works § Log data download](settings-viewmodel-how-it-works.md#log-data-download-683)). The `archivedDiscussionCount = 11` literal mirrors the reference frame value Figma 17:2 ships, so the supporting line `"11 archived"` is visible in the preview pane (a `0` literal would render `"0 archived"`, which is correct but less informative as a visual check); `defaultEffort = Effort.HIGH` and `defaultModel = Model.OPUS_4_7` match both the persistence-layer defaults and the pre-wire-up hardcoded subtitles, so the rows' appearance is unchanged from the visual baseline. The `onOpenLicense = {}` argument was dropped from both previews in #163 alongside the `SettingsScreen` parameter. No dedicated preview for the disabled-pre-S branch — Compose `@Preview` doesn't easily simulate a lower runtime SDK level, and the disabled path is structurally simple (M3 default-disabled colors + helper-text supporting line); a curious developer can eyeball it by flipping `dynamicColorSupported = false` temporarily. No dedicated no-host / owner-missing / `Resolving` preview for `connection` either — `HostIdentityRow` carries its own two-`@Preview` matrix (see [Settings screen — how it works § `HostIdentityRow`](settings-screen-how-it-works.md#hostidentityrow-sibling-file)), and those three cases are each a single `SettingsRow` call or nothing at all, not worth a dedicated preview of the whole screen.

`ConnectionStatusLine` legs use `clearAndSetSemantics`, so a test asserting the rendered status must match a leg's `contentDescription` (e.g. `"Relay: connected"`), not its visible label text (`"Connected"`) — an assertion against the visible text finds nothing and misreads as "the status is missing" rather than "the matcher is wrong" (#749). Since #750 every drawn host contributes its own status legs, so an assertion against `"Relay: connected"` must be made **by presence**, not uniqueness — `onNodeWithContentDescription` fails on ambiguity the moment two saved hosts are both connected. See [`SettingsNavigationTest.assertShowsAlphaConnected`](#testing) below.

`SettingsNavigationTest` (`app/src/androidTest/.../ui/settings/SettingsNavigationTest.kt`, #749; extended #750, #751) is the production-route counterpart, mounting `PyryNavHost` directly rather than through `MainActivity` — see [Navigation § Testing](navigation.md#testing) and [Dependency injection § Testing](dependency-injection.md#testing) for its scenarios; it, not `SettingsScreenTest`, is what proves the gear's capture, back-stack restoration and the selection-independence AC1/AC2 require, plus (#750) that every saved host is drawn with live identity/status and that tapping a non-owner row hops to that host's own Settings without growing the back stack, and (#751) `tappingTheOwnersRowOpensTheEditorOnTheCapturedHostNotTheSelectedOne` — the join between `SettingsScreen`'s `onEditHost` and `SettingsViewModel.openOwnerHostEditor` lives in `PyryNavHost` and is invisible to both screen-level and view-model-level tests, so this test taps the owner's row on the production graph with a *different* host selected and asserts the modal's name field carries the captured owner's name, proving the security review's "never on selection" claim end to end. Its `assertBadgedRowIs(owner, other)` helper was restated by #751 (`2d53a1d`, a rework commit after the verifier's device gate caught the stale assertion, and after a sibling miss in the same helper in a second file — see below): it now identifies the owner directly, by asserting the "This server" badge is a descendant of the owner's own row and absent from the other's, rather than by the pre-#751 property that the owner's row carried **no** click action — the property this ticket deliberately reverses. That direct assertion was unavailable before #751: `HostIdentityRow` adds no semantics node of its own unless it's given an `onClick`, so a "row contains both this name and the badge" subtree matcher matched every common ancestor (root, container, scroll group) and failed on ambiguity; #751 giving the owner's row a real `onClick` is what yields one semantics node per row and makes the badge's own row addressable. **The gap the rework exposed:** the same stale "no click action" assertion also lived in `SettingsNavigationTest.assertBadgedRowIs` itself — a *second* copy of the property `SettingsScreenTest`'s equivalent had already been restated for — so restating one file's assertion and not sweeping its sibling left three tests red on the verifier's device gate. Both are now the direct form; a future assertion on "the owner's row" should default to checking what's true of that row's own subtree, not what's absent from its interactions.
