# ThreadOverflowMenu

Stateless Material 3 `DropdownMenu` (#251) listing common thread-overflow actions in this exact order — **Reset session**, **Rename**, **Archive**, **Channel info**, **Background tasks** — wrapped since [#204](../codebase/204.md) by **two context-aware items**: discussions (`isPromoted == false`) get a leading **Save as channel…** (emits `ThreadEvent.SaveAsChannel`); channels get a trailing **Install memory plugin** only when the current session's memory-search report confirms absence (opens `MEMORY_PLUGIN_DOCS_URL` via `LocalUriHandler.current.openUri(...)` — no `ThreadEvent`). Installed, disabled, unavailable, unknown and omitted reports do not offer installation. **Since [#1561](../../specs/architecture/1561-thread-edit-channel.md), Rename's own slot is itself context-aware**: a channel reads **Edit** there instead, opening the Edit channel modal (`ThreadEvent.EditChannel`); a discussion still reads Rename and opens the rename dialog. Edit is hidden exactly where Rename was, since both sit inside the same `mutationsSupported` block — see [events and behaviour](thread-overflow-menu-events-and-behaviour.md#what-it-does). Sole consumer of the [`ThreadEvent`](thread-overflow-menu-events-and-behaviour.md#threadevent) sealed surface introduced in [#251](../codebase/251.md). Mounted in production since [#252](../codebase/252.md) inside `ThreadTopAppBar`'s `actions` slot (wrapped in a `Box` alongside the existing `MoreVert` `IconButton` so the M3 `DropdownMenu` anchors directly below the icon); the screen-owned `expanded` flag lives on `ThreadScreen` as `var overflowExpanded by rememberSaveable { mutableStateOf(false) }`, and `MainActivity` binds `onOverflowEvent = vm::onOverflowEvent` so each ViewModel-owned menu action reaches `ThreadViewModel.onOverflowEvent(...)`. `ThreadScreen` passes `state.isPromoted` and `state.runConfig.memorySearch` through `ThreadTopAppBar`; a replacement report or conversation change updates the item while the menu is open. A search plugin retrieves stored knowledge; installing one does not capture the conversation or restore the agent's old context.

[#382](../codebase/382.md) had added a **leading, unconditional** item, "Show the literal screen", placed above both promotion conditionals and reachable via a pure-navigation `onShowLiteralScreen: () -> Unit` callback that bypassed `onEvent`. **[#883](../../specs/architecture/883-retire-literal-screen.md) retired it**: the daemon deleted the server-side screen-snapshot render path, so `onShowLiteralScreen` and the `literal_screen/{serverId}/{conversationId}` destination it opened are gone from `ThreadOverflowMenu`, `ThreadTopAppBar`, `ThreadScreen` and `MainActivity`. Background tasks also bypasses `onEvent`: its UI-local `onBackgroundTasks` callback opens the existing panel after dismissing the menu (#1631). It is always available, independent of promotion, mutation support or running-task count. See [the approved design addition](../../../app/src/androidTest/assets/design-1220/README.md#approved-additions-without-a-separate-frame).

Package: `de.pyryco.mobile.ui.conversations.thread` (`app/src/main/java/de/pyryco/mobile/ui/conversations/thread/`). File: `ThreadOverflowMenu.kt`. Sibling to [`ThreadScreen`](thread-screen.md), `ThreadTopAppBar.kt`, [`ThreadInputBar`](thread-input-bar.md), and `ThreadViewModel.kt` (where `ThreadEvent` and `onOverflowEvent` live).

**Reset session** keeps the `thread_overflow_new_session` resource and
`ThreadEvent.NewSession` event names. It targets the open conversation through the
[remote control send](remote-conversation-repository-control-sends.md#startnewsession--explicitly-targeted-v2-new_session).
A failed send leaves the thread intact and shows “Couldn't reset the session.
Check your connection.” (`new_session_failed`). Successful sending leaves local
session state unchanged until inbound events arrive; reset progress is tracked
separately by [#630](https://github.com/pyrycode/pyrycode-mobile/issues/630).

## Shape

```kotlin
@Composable
fun ThreadOverflowMenu(
    expanded: Boolean,
    isPromoted: Boolean,
    onDismiss: () -> Unit,
    onEvent: (ThreadEvent) -> Unit,
    modifier: Modifier = Modifier,
    mutationsSupported: Boolean = true,               // new in #508 — false hides mutation items
    memorySearch: MemorySearchReport = MemorySearchReport.Unknown,
    onBackgroundTasks: () -> Unit = {},
)
```

- **`mutationsSupported` placement is load-bearing: it sits *after* `modifier`** ([#508](../codebase/508.md)). A new defaulted `@Composable` param placed *before* `modifier` is an Android Lint `ComposeParameterOrder` error (compiles fine, fails `./gradlew lint`) — see [[compose-parameter-order-lint-defaulted-after-modifier]]. Defaulted `= true` mirrors `ThreadUiState.mutationsSupported = true` so the ~10 existing test call sites compile untouched; the default is a preview/test seam only — production always threads the real value (see [What it does](thread-overflow-menu-events-and-behaviour.md#what-it-does)).

- **`onBackgroundTasks` defaults to `{}` after `modifier`** for isolated callers, satisfying Compose parameter order. Production forwards it through `ThreadTopAppBar` to the screen-owned panel flag; no ViewModel event or repository call is needed.

- **`memorySearch` defaults to `Unknown`** for previews and isolated callers. Production passes the current report; `shouldOfferMemoryInstall()` requires aggregate `Absent` and no installed provider, so missing status never becomes an install prompt.

- **`public`** (default visibility) — exported so the [#252](../codebase/252.md) host (and the `androidTest` Compose tests) can render it.
- **Stateless.** No `remember`, no `mutableStateOf`. `expanded` / `isPromoted` / `onDismiss` are hoisted to the host; today's `ThreadOverflowMenuTest` passes `expanded = true` literal to render immediately without a host state machine.
- **`isPromoted` placement: between `expanded` and `onDismiss`** — keeps the "what to render" parameters grouped before the "what to do" callbacks. No default value (matches `expanded` / `onDismiss` / `onEvent`; the host always knows). Added in [#204](../codebase/204.md). Drives which of the two mutually-exclusive context-specific items renders alongside the common items.
- **`onEvent: (ThreadEvent) -> Unit` handles ViewModel-owned actions.** Direct CLAUDE.md MVI convention. The host ([#252](../codebase/252.md)) binds `onEvent = vm::onOverflowEvent` with no per-callback → sealed-event mapping layer. The contrast against [`ChannelInfoSheet`](channel-info-sheet.md)'s six named callbacks is by design — sheets are heterogeneous, menus are homogeneous; see [the per-ticket Patterns established note](../codebase/251.md#patterns-established).
- **`modifier` defaulted but exposed** so the host can pass placement / sizing modifiers if needed; today no caller uses it.

## Preview

None. The menu has no per-state visual variants worth previewing in isolation (it's `expanded = true` ⇒ the applicable rows, or `false` ⇒ nothing). Post-[#252](../codebase/252.md) the host-rendered open-menu state can be exercised through the existing `ThreadScreen` previews by tapping the icon at runtime; no `@Preview` was added in either slice because the four `ThreadScreen` previews already cover the surrounding chrome and the menu itself is system-popup-windowed (Compose `@Preview` doesn't draw popup windows).
