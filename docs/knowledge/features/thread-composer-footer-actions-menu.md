## Actions menu (#884)

`enum class ComposerAction(val value: String, val label: String, val command: String?)` (`ThreadComposerFooter.kt`) is the closed, client-owned table behind the Actions menu, after desktop's `ComposerActionsMenu` / `composerActionAvailability.ts`, in menu order: `ResetSession` ("Reset session", no command — it dispatches the overflow menu's existing `ThreadEvent.NewSession` path, not a message), `CompactSession` ("Compact session", `/compact`), `KnowledgeCapture` ("Knowledge capture", `/knowledge-capture`). Background tasks is available through the count-free [top menu](thread-overflow-menu.md) and running-task pill, not Actions (#1668). Every field is a Kotlin constant; nothing the workspace publishes is ever shown, handed back or sent through this menu — see [Options overlay § Trust boundary](options-overlay.md#trust-boundary) for how that floor is enforced on the overlay side.

`footerMenu(FooterControl.Actions, runConfig, mutationsSupported, absentActions)` is never `null`: its options are `ComposerAction.entries`, `ResetSession` dropped unless `mutationsSupported` (the overflow menu's own Reset session item stays, under the same gate), each row `enabled = it !in absentActions`, and `FooterMenu.actions = true` so [`OptionsOverlay`](options-overlay.md) draws button-mode rows instead of a radio group. `footerControlEnabled(Actions, …, connected)` skips the `writable && !outstanding` rule every other control follows — a command send addresses no session and writes no setting, so there is nothing to disable on that account — but it is not unconditional: while the host is not connected (#1319), it returns `false` like every other control, since the tap would otherwise reach `onComposerCommand` only to be dropped there.

**Absence proof.** `internal fun absentComposerActions(menu: SlashCommandMenu?, slashCommands: Boolean = true): Set<ComposerAction>` (`ThreadViewModel.kt`) returns the command-bearing actions that are absent for either of two independent reasons. The published slash-command menu ([#882](https://github.com/pyrycode/pyrycode-mobile/issues/882)) proves a command absent fail-open by construction: it needs a non-null `menu`, `droppedCommands == 0` (a negative count proves nothing), no row with `"name"` or `"aliases"` in its `truncatedFields` (a truncated `description` or `argument_hint` still proves), and no row whose `name` or any alias exactly equals the command with its leading slash stripped — no case fold, no trim, no slash on either side. Anything short of that leaves every command available from the menu's side. Separately (#1111), a `SessionSettings.capabilities` list reporting `slashCommands == false` — a `multi_agent` session that does not answer slash commands at all — marks every command-bearing action absent regardless of what the menu says; `slashCommands == true`, the default, adds nothing and never re-enables a command the menu already proved absent (the two sources are unioned, not compared). `ResetSession` carries no `command` and is unaffected by either rule. The private `slashCommandMenu: Flow<SlashCommandMenu?>` (`repository.observeSlashCommandMenu(conversationId).onStart { emit(null) }.distinctUntilChanged()`) is folded into `state` with one more `.combine(slashCommandMenu) { uiState, menu -> uiState.copy(absentActions = absentComposerActions(menu, uiState.runConfig.capabilities?.slashCommands ?: true), slashCommands = menu?.rows) }` step after the `runConfig` combine — the same reason [Thread composer footer § Running model](thread-composer-footer.md#running-model-891) rides its own separate combine. `ThreadUiState.absentActions` carries only the verdict, never a published string, and the flag itself is never rendered — see [Thread composer footer § Sourcing](thread-composer-footer.md#sourcing).

**Dispatch and send.** `ThreadScreen`'s overlay `onSelect` resolves the tapped `value` through `ComposerAction.fromValue`: an unknown value dispatches nothing, `ResetSession` becomes `onOverflowEvent(ThreadEvent.NewSession)` — the existing #540/#625 reset path, gated by `mutationsSupported` exactly as the overflow menu's own item, and every other action becomes `onComposerCommand(action)`. `ThreadViewModel.onComposerCommand(action)` returns without sending when `action.command == null` (Reset never reaches this function) or when `action in state.value.absentActions` — a deterministic backstop behind the greyed-out row, in case a stale overlay composition still delivers a tap. It then refuses, logging `outcome=busy`, while `_attachmentsSending` is already true: an earlier attachment send still owns the pending files, and sending them again would upload and name them twice.

With pending files (`draftStore.attachmentsFor(serverId, conversationId)` non-empty), the command goes through the same `sendWithAttachments(text, attachments, onUploaded, onSent)` that `sendMessage` uses, following desktop's `sendText`, which hands `takeAttachments` to both of its callers (#1348). `sendWithAttachments` uploads under `_attachmentsSending`, then — once every upload has succeeded and **before** the send ([#1355](https://github.com/pyrycode/pyrycode-mobile/issues/1355)) — calls `onUploaded` and removes the sent snapshot's entries from the strip, then sends and calls `onSent`. `onComposerCommand` passes an `onUploaded` that does nothing (unlike `sendMessage`'s, which clears the draft) and an `onSent` that only logs `event=composer_action action=<value> outcome=sent`, so the typed draft — even one that equals the command text — is never cleared. Because this path runs through `sendWithAttachments`, it also opens the local "Thinking…" send window (`sendInLocalWindow`) and emits into `sentMessages`, exactly as a typed message with files does; a text-only command does neither. The repository draws the command's own echo the moment it issues the send, same as any other message (#1355), so a command with files appears in the thread before the daemon replies, same as the attachment strip clearing ahead of it.

With no pending files, `onComposerCommand` runs `launchGuardedRepoCall { effortRecall.awaitWrite(); repository.sendMessage(conversationId, command) }` as before — the guarded body minus the draft clear and attachment pick-up, so the typed draft and (absent) attachments are left untouched, and no local send window opens. The repository draws the echo as it issues this send too, so the command shows in the thread immediately. A failed send, either way, is swallowed exactly as a composer send's is, and since #1355 no longer unwinds the echo it already drew — unlike before #1355, when the command never appeared in the thread on a failure because nothing was ever inserted. Every outcome logs a static `event=composer_action action=<value> outcome=sent|absent|busy` line — never a conversation id, a command's effect, or menu content.

The daemon appends an attachment's file paths after the message text (`composeAttachmentPrompt`, pyrycode `internal/relay/handlers/send_message.go`), so a command sent with files reaches Claude Code as `/<cmd>` followed by that block — for `/compact`, read as the command's own summary instructions rather than files to open. How real Claude actually handles a command sent with files is untested here; see [the real-Claude ladder](../../e2e-interactive-stream.md) for the follow-up scenario this carried the work to (#1460).
