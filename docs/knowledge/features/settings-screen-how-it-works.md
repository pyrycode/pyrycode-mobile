Part of [Settings screen](settings-screen.md); see that document for what it does, its configuration/usage wiring, its edge cases, its previews and its links.

## How it works

Stateless Composable with **no** local placeholder switch state since #268 — the last one (`pushNotifications`) became VM-backed, after the `defaultYolo` local had already gone in #234. What remains in the body: three local dialog open-state flags (`showThemeDialog` from #87, `showModelDialog` from #232, `showEffortDialog` from #233) and (since #89) one `val dynamicColorSupported = Build.VERSION.SDK_INT >= Build.VERSION_CODES.S` near the top of the body for the Use-wallpaper-colors row's enabled/disabled gate. All seven persisted-state pairs (`themeMode` / `onSelectTheme`, `useWallpaperColors` / `onToggleUseWallpaperColors`, `defaultModel` / `onSelectDefaultModel`, `defaultEffort` / `onSelectDefaultEffort`, `defaultYolo` / `onToggleDefaultYolo`, `pushNotifications` / `onTogglePushNotifications`), plus the `defaultWorkspace` row + `workspacePickerVisible` host triple from #235, are hoisted to [`SettingsViewModel`](settings-viewmodel.md); no other repository or ViewModel is touched.

```kotlin
@Composable
fun SettingsScreen(
    connection: SettingsConnectionState,   // #750, replacing #749's host: SettingsHostState
    themeMode: ThemeMode,
    useWallpaperColors: Boolean,
    archivedDiscussionCount: Int,
    defaultModel: Model,
    defaultEffort: Effort,
    defaultYolo: Boolean,
    pushNotifications: Boolean,           // #268
    defaultWorkspace: String,             // #235
    workspacePickerVisible: Boolean,      // #235
    onSelectTheme: (ThemeMode) -> Unit,
    onToggleUseWallpaperColors: (Boolean) -> Unit,
    onSelectDefaultModel: (Model) -> Unit,
    onSelectDefaultEffort: (Effort) -> Unit,
    onToggleDefaultYolo: (Boolean) -> Unit,
    onTogglePushNotifications: (Boolean) -> Unit,   // #268
    onDefaultWorkspaceTapped: () -> Unit,           // #235
    onSelectDefaultWorkspace: (String) -> Unit,     // #235
    onWorkspacePickerDismissed: () -> Unit,         // #235
    onOpenHost: (String) -> Unit,                   // #750
    hostEditor: HostEditorState?,                   // #751
    onEditHost: () -> Unit,                         // #751
    onEditHostNameSubmitted: (String) -> Unit,       // #751
    onHostUnpairRequested: () -> Unit,               // #751
    onHostUnpairConfirmed: () -> Unit,               // #751
    onHostUnpairDeclined: () -> Unit,                // #751
    onEditHostDismissed: () -> Unit,                 // #751
    onPairServer: () -> Unit,                       // #749
    onBack: () -> Unit,
    onOpenArchivedDiscussions: (() -> Unit)?,   // nullable since #715
    onOpenAbout: () -> Unit,
    modifier: Modifier = Modifier,
)
```

All thirty-one leading parameters are required, in that order (#751 inserted seven — `hostEditor` plus its six driving callbacks — between `onOpenHost` and `onPairServer`, the widest single jump the signature has taken since #235's workspace-picker surface). Parameter ordering since #232 groups state values together (`connection` since #750, replacing #749's `host`, then `themeMode`, `useWallpaperColors`, `archivedDiscussionCount`, `defaultModel`, `defaultEffort`, `defaultYolo`, `pushNotifications`, `defaultWorkspace`, `workspacePickerVisible`, then `hostEditor` since #751), then event callbacks together (`onSelectTheme`, `onToggleUseWallpaperColors`, `onSelectDefaultModel`, `onSelectDefaultEffort`, `onToggleDefaultYolo`, `onTogglePushNotifications`, `onDefaultWorkspaceTapped`, `onSelectDefaultWorkspace`, `onWorkspacePickerDismissed`, `onOpenHost` since #750, `onEditHost` / `onEditHostNameSubmitted` / `onHostUnpairRequested` / `onHostUnpairConfirmed` / `onHostUnpairDeclined` / `onEditHostDismissed` since #751, `onPairServer` since #749), then nav callbacks (`onBack`, `onOpenArchivedDiscussions`, `onOpenAbout`), then `modifier` — matches the Compose stdlib's grouping convention. `hostEditor` sits in the state group directly after `workspacePickerVisible` — both are "is a caller-owned overlay open" state — and its six callbacks sit in the event group directly after `onOpenHost`, mirroring the Connection section's own layout: the owner's row (which the editor belongs to) is drawn inline with the other saved-host rows, not in a section of its own. `onOpenHost` sits directly before `onPairServer`, mirroring the Connection section's own row order (saved-host rows, then the pairing row); `onPairServer` sits at the end of the event-callback group because the Connection section's pairing row is the last row #749 wires and sits above every event-callback row it's grouped with in the signature; both precede the nav-callback group because neither is `NavController`-facing in the screen's own terms, even though their production wiring does navigate. Within each group, the Defaults pair ordering (`defaultModel` before `defaultEffort` before `defaultYolo`, same for the callbacks) mirrors the row order in the screen body and the Figma `17:2` "Defaults for new conversations" section; `pushNotifications` / `onTogglePushNotifications` (#268) sit after the Defaults pairs in each group, tracking the row's position in the Notifications section below, so a top-to-bottom read of the signature still matches a top-to-bottom read of the screen. `themeMode` lost its `ThemeMode.SYSTEM` default in #87 once the row became interactive — when the value drives a writable affordance, every call site must wire it explicitly so a forgotten preview can't render a stale literal. `onSelectTheme` (added #87), `onOpenArchivedDiscussions` (added #94; the sole exception to the no-default *and* non-null rule below — widened to `(() -> Unit)?` in #715, since a destination owning no host has no archive to open and `SettingsRow`'s own `onClick: (() -> Unit)?` already renders `null` as inert), the `useWallpaperColors` / `onToggleUseWallpaperColors` pair (added #89), `archivedDiscussionCount` (added #164), the `defaultEffort` / `onSelectDefaultEffort` pair (added #233), the `defaultModel` / `onSelectDefaultModel` pair (added #232), the `defaultYolo` / `onToggleDefaultYolo` pair (added #234), the `defaultWorkspace` / `workspacePickerVisible` + `onDefaultWorkspaceTapped` / `onSelectDefaultWorkspace` / `onWorkspacePickerDismissed` workspace-picker surface (added #235), the `pushNotifications` / `onTogglePushNotifications` pair (added #268), `onOpenAbout` (added #271), `onPairServer` (added #749), `onOpenHost` (added #750), and `hostEditor` plus its six callbacks (added #751) likewise carry no defaults — the rule is: navigation/event callbacks → no default; static display state with a neutral safe value → default OK, but the moment that display state gains a writable counterpart **or** drives a Figma-mandated visible string, drop the default (#164's `archivedDiscussionCount = 0` would happen to be a neutral safe value, but the AC requires every call site to wire the real count so a forgotten preview can't render a stale "0 archived" while the live value is non-zero; #233's `defaultEffort`, #232's `defaultModel`, #234's `defaultYolo`, and #268's `pushNotifications` follow the same rule — `pushNotifications`'s `true` is a neutral safe value, but the row is now writable so every call site wires it). `connection` (#750) carries no default either, for the same reason `host` didn't before it — `SettingsConnectionState.Resolving` would be a plausible-looking neutral value, but the AC requires every call site to distinguish it from a genuinely loaded list, so a forgotten preview can't render "still resolving" forever. `hostEditor` (#751) follows the same rule for a different reason: `null` *is* the correct value most of the time (the modal is closed far more often than open), so there is no wrong neutral literal to default to — the parameter carries no default simply because every other event/overlay parameter on this signature doesn't, not because a wrong guess is possible. Production wires all seven VM-backed pairs, the count projection, the workspace-picker flag, `connection`, `onOpenHost`, and (#751) `hostEditor` plus its six callbacks from `composable(Routes.SETTINGS)` (see [Settings ViewModel](settings-viewmodel.md)). The `onOpenLicense: () -> Unit` parameter from #91 was dropped in #163 along with the License row's `onClick` wiring.

Skeleton:

- `Scaffold` with an M3 `TopAppBar` — `title = stringResource(R.string.settings_title)` ("Settings"), `navigationIcon` is the canonical back-arrow `IconButton` (`Icons.AutoMirrored.Filled.ArrowBack` + `R.string.cd_back`) wired to the `onBack` callback. Same shape as `DiscussionListScreen`.
- Body is a `Column(Modifier.padding(inner).fillMaxSize().verticalScroll(rememberScrollState()).padding(bottom = 32.dp))` — `Column` + `verticalScroll`, not `LazyColumn`, because the row count is fixed at ~18 items and the heterogeneous row shapes make item-keying noisy with no recycling benefit.
- **No** `remember { mutableStateOf(...) }` placeholder switch state remains as of #268 — the last one (`pushNotifications = true`) was removed when the row became VM-backed (the `defaultYolo = false` local had already gone in #234, and `materialYou = true` in #89). The only `remember { mutableStateOf(false) }` locals declared inside the `Scaffold` content lambda now are dialog open-state: (since #87) `showThemeDialog`, (since #232) `showModelDialog`, (since #233) `showEffortDialog`. None are `rememberSaveable` — the dialog open-state flags deliberately reset on re-entry so a stale picker can't reopen on top of a screen the user navigated back to. The three `if (show…Dialog)` picker blocks sit in the file in the same order as their backing rows (Theme → Model → Effort) — see [`../codebase/232.md`](../codebase/232.md) § Patterns established for the rule. Every persisted toggle/value the screen shows is now hoisted to the VM (see § Notifications and § Use-wallpaper-colors row).
- The Connection section's Server row was replaced by [`HostIdentityRow`](#hostidentityrow-sibling-file) in #749, superseding #398's fixed `Server` `SettingsRow` + separate `ConnectionStatusLine`; #750 widened the single row into a list, and #751 gave the owner's row a click action of its own. `when (connection) { Resolving -> Unit ; is Loaded -> { connection.hosts.forEach { row -> key(row.serverId) { HostIdentityRow(..., onClick = if (row.isOwner) ({ onEditHost() }) else ({ onOpenHost(row.serverId) }), trailing = if (row.isOwner) ({ HostOwnerTrailing() }) else ({ ChevronIcon() })) } } ; if (hosts.isEmpty()) SettingsRow(settings_host_none) else if (ownerMissing) SettingsRow(settings_host_unknown) } }` sits where the old `Server` row + `ConnectionStatusLine` pair did, directly above the `Pair another server` row — no intervening `ConnectionStatusLine` call in this file any more; `HostIdentityRow` draws its own beneath the identity `ListItem` at the same `start = 16.dp, top = 4.dp, bottom = 8.dp` inset #398 established. `Resolving` renders nothing rather than a placeholder, so the join's first-read latency can't flash wrong copy for one frame. Each row is wrapped in `key(row.serverId)` because Compose otherwise matches a plain `Column`'s children by call order — without the key, a reorder would hand one host's composition to another; shipped in #750 as a guard ahead of #751's edit/unpair slice, which is the case that made a missing key's blast radius observable rather than cosmetic. `HostOwnerTrailing()` (#751, private, same file) replaces the bare `HostOwnerBadge()` the owner's row drew before — see § Composables below. See § Host ownership below and [`../codebase/398.md`](../codebase/398.md) for the superseded status-line-only wiring.
- The Appearance → Theme row's `supporting` text is sourced from the `themeMode` parameter via an `internal` `ThemeMode.label()` extension at the bottom of `SettingsScreen.kt` (`SYSTEM → "System"` since #163 — was `"System default"` between #86 and #163; `LIGHT → "Light"`, `DARK → "Dark"` unchanged). Visibility was widened from `private` to `internal` in #87 so `ThemePickerDialog.kt` (same package) imports the same definition for its three radio labels — single source of truth for the row subtitle and the dialog options. The strings are hardcoded, deliberately not routed through `strings.xml`. Pinned by `SettingsLabelsTest.kt` (pure-Kotlin JUnit, #163) — one assertion per arm.
- The Theme row's `onClick` flips `showThemeDialog = true` (#87). When `showThemeDialog`, an `if`-guarded `ThemePickerDialog(selected = themeMode, onConfirm = { mode -> onSelectTheme(mode); showThemeDialog = false }, onDismiss = { showThemeDialog = false })` block sits above the body `Column`. See `ThemePickerDialog` below.
- The Defaults section's "Default model" row was wired in #232. `supporting = defaultModel.label()` resolves through the top-level `fun Model.label(): String` extension at `data/preferences/Model.kt` (added in [#253](../codebase/253.md)'s partial walk-back of #231's "defer labels to first UI consumer" convention; the StatusSheet model section pre-empted the Settings picker as the first consumer). `SettingsScreen.kt` resolves it via an explicit `import de.pyryco.mobile.data.preferences.label`. Returns `"Opus 4.7"` / `"Sonnet 4.6"` / `"Haiku 4.5"` — product-vendor names that match the pre-#232 hardcoded subtitle and the labels used by [`StatusSheet`](status-sheet.md)'s Model section. The row's `onClick` flips `showModelDialog = true`; when set, an `if`-guarded `ModelPickerDialog(selected = defaultModel, onConfirm = { model -> onSelectDefaultModel(model); showModelDialog = false }, onDismiss = { showModelDialog = false })` block sits between the `ThemePickerDialog` and `EffortPickerDialog` blocks (matching the row ordering — see § `ModelPickerDialog` below).
- The Defaults section's "Default effort" row was wired in #233. `supporting = defaultEffort.label()` resolves through the `Effort.label()` extension declared at file scope in `EffortPickerDialog.kt` (same package, no import needed) and returns lowercase `"low"` / `"medium"` / `"high"` / `"xhigh"` / `"max"` — labels match the enum's identifier scheme and the pre-#233 hardcoded subtitle. The extension was originally `internal` (#233); [#229](../codebase/229.md) widened it to top-level public when the StatusSheet's `FilterChip` row became the second consumer in `ui.conversations.components` — the Settings call site is unchanged across the visibility widening (`internal` still resolved in the same package; `public` resolves a strict superset of locations). The row's `onClick` flips `showEffortDialog = true`; when set, an `if`-guarded `EffortPickerDialog(selected = defaultEffort, onConfirm = { effort -> onSelectDefaultEffort(effort); showEffortDialog = false }, onDismiss = { showEffortDialog = false })` block sits adjacent to the `ModelPickerDialog` block (same shape, swap `Model` → `Effort`). See `EffortPickerDialog` below.
- The Defaults section's "Default YOLO" row was wired in #234. It's a VM-backed M3 `Switch` row (no picker dialog — YOLO is a single boolean, so it mirrors the [Use-wallpaper-colors row](#) shape, not the picker rows): `SettingsRow(headline = "Default YOLO", supporting = "off", trailing = { Switch(checked = defaultYolo, onCheckedChange = onToggleDefaultYolo) })`. `checked` mirrors `AppPreferences.defaultYolo`; `onCheckedChange` routes straight to `SettingsViewModel.onToggleDefaultYolo` → `AppPreferences.setDefaultYolo` (fire-and-forget, no confirm step — distinct from the picker rows' OK/Cancel). No row-level `onClick` (the Switch owns the gesture). The static `supporting = "off"` literal is **preserved unchanged** — the sibling picker rows show their current value (e.g. "high", "Opus 4.7") but #234's scope was deliberately "only the `checked` source and the `onCheckedChange` target change," so the dynamic "on"/"off" subtitle is a flagged follow-up (see [`../codebase/234.md`](../codebase/234.md) and the spec's Open questions). The persisted value is real but **read-dead** — no consumer acts on it; per #229 the StatusSheet does not seed per-conversation YOLO from it. The `Default workspace` row below it was wired to the reused [`WorkspacePicker`](workspace-picker.md) host in #235 (`onClick = onDefaultWorkspaceTapped`), so the Defaults section has no placeholder rows left.
- The Use-wallpaper-colors row (#89) sits directly beneath the Theme row in the Appearance section. Inline `SettingsRow(headline = stringResource(R.string.settings_use_wallpaper_colors), supporting = if (!dynamicColorSupported) stringResource(R.string.settings_use_wallpaper_colors_unsupported) else null, trailing = { Switch(checked = useWallpaperColors, onCheckedChange = onToggleUseWallpaperColors, enabled = dynamicColorSupported) })`. No row-level `onClick` — consistent with the `defaultYolo` / `pushNotifications` switch rows. `Switch.enabled = false` handles both the visual disabled state and the no-op tap behaviour on Android < 12 — the `onCheckedChange` callback is passed unconditionally because M3's `Switch` ignores it when `enabled = false`. The headline string was `"Use wallpaper colors"` between #89 and #163; #163 reverted it to `"Use Material You dynamic color"` to match Figma `17:2`.
- The Notifications section's "Push notifications when claude responds" row was wired in #268. Like the Default-YOLO row it's a VM-backed M3 `Switch` (no picker dialog — a single boolean): `SettingsRow(headline = "Push notifications when claude responds", trailing = { Switch(checked = pushNotifications, onCheckedChange = onTogglePushNotifications) })`. `checked` mirrors `AppPreferences.notificationsEnabled`; `onCheckedChange` routes to `SettingsViewModel.onTogglePushNotifications` → `AppPreferences.setNotificationsEnabled` (fire-and-forget, no confirm step). **No `supporting` arg** (unlike Default YOLO's static `"off"`) — Figma `17:2` gives this row no subtitle, and #268 preserved that. **Defaults ON:** the backing preference is the only boolean in `AppPreferences` defaulting `true` (Figma renders the toggle ON, contrasting the OFF Default-YOLO toggle directly above), so `SettingsViewModel.pushNotifications` uses `initialValue = true` to avoid an OFF→ON flicker on cold open. Persisted but **read-dead** — notification *delivery* is Phase 4. This wire-up removed the screen's last `remember { mutableStateOf(true) }` placeholder local. See [`../codebase/268.md`](../codebase/268.md).
- The Storage → Archived discussions row gained a live `"N archived"` supporting line in #164. Inline `SettingsRow(headline = stringResource(R.string.archived_discussions_settings_row), supporting = stringResource(R.string.archived_discussions_count_supporting, archivedDiscussionCount), trailing = { ChevronIcon() }, onClick = onOpenArchivedDiscussions)`. The format string `%1$d archived` accepts a single `Int` arg; `0` renders as `"0 archived"` per Figma 17:2's empty-state behavior (row stays present and tappable). The pre-#164 hardcoded subtitle was first `"11 archived"` (the #64 visual stub) then dropped to nothing (#94); #164 wires it to `SettingsViewModel.archivedDiscussionCount` via the new `archivedDiscussionCount: Int` parameter. The value comes from `ConversationRepository.observeConversations(ConversationFilter.Archived) | count { !it.isPromoted }` — see [Settings ViewModel](settings-viewmodel.md). Pluralisation deliberately not routed through `<plurals>` (no plurals precedent in the project, English `"0 / 1 / 11 archived"` are all grammatical) — switching later is mechanical and isolated.
- The About section is a single navigable entry since #271: `SettingsRow(headline = stringResource(R.string.about_settings_row), trailing = { ChevronIcon() }, onClick = onOpenAbout)` under a kept `SettingsSectionHeader("About")`. The four former inline rows (Version + build SHA, Open source via `Intent.ACTION_VIEW`, inert Privacy policy, text-only "License: MIT") were extracted verbatim into the [About screen](about-screen.md) — along with the `val context = LocalContext.current` capture (#90), the `ExternalLinkIcon` composable, and the `SOURCE_REPO_URL` const. The `BuildConfig.VERSION_NAME` / `GIT_SHA` reads (#90/#165, including the `GitShaValueSource` Gradle wiring) now live on [`AboutScreen`](about-screen.md); see [About screen](about-screen.md) and [`../codebase/165.md`](../codebase/165.md) for the `ValueSource` shape that's unchanged by the move.

### Host ownership (#749, #750, #751)

The destination is owned by the exact server id the channel list's settings gear captured into the
route at tap time — never by whichever host is currently selected. `SettingsScreen` itself is
selection-agnostic: it renders whatever `SettingsConnectionState` the `connection` parameter carries,
and that value already reflects exact-owner resolution done in
[`SettingsViewModel`](settings-viewmodel.md). Two Figma deviations from node `17:2`, both AC-driven:
the frame's literal **"Server"** headline becomes each host's own name (its server id when unnamed);
and the frame's trailing chevron, dropped by #749 because nothing on the single row navigated yet, is
back on every row since #750 — a non-owner row opens that host's own Settings, so the chevron is
honest again for it. The owner's own row carries the chevron too, alongside a short "This server"
(`R.string.settings_host_current`) badge — badge *and* chevron together, per #751's
[`HostOwnerTrailing`](#composables-in-the-same-file-mostly-private) — but the tap it opens is
different: since #751 the owner's row opens the Edit host modal on itself (see
[Host editor](host-editor.md)) rather than navigating anywhere, reusing the same modal and machine
the channel list's own host row already drives. The badge is a deliberate deviation the frame never
had to resolve, since it draws only one host and so never needed to say *which* one is open. A static
string with no format argument, so no host identity can ride into it and be read aloud by TalkBack.
Before #751 the owner's row had no click action at all, since nothing on this screen could yet act on
it; **that "the owner's row is inert" property is gone**, and a few `androidTest` assertions that
depended on it (`SettingsScreenTest`, `SettingsNavigationTest.assertBadgedRowIs`) needed restating
against the badge directly rather than against the absence of a click action — see
[Settings screen § Testing](settings-screen.md) for what broke and how it was fixed.

`SettingsConnectionState.Resolving` (before the VM's join of the saved-host list has produced its
first value) renders nothing, so the join's first-read latency can't flash wrong copy for one frame.
`Loaded` draws one [`HostIdentityRow`](#hostidentityrow-sibling-file) per saved host, each `key`ed by
`serverId`; below the rows, an empty list draws `R.string.settings_host_none` ("No host is paired")
and a non-blank owner absent from the list draws `R.string.settings_host_unknown` ("This host is no
longer paired") — **empty list wins when both are true** (unpairing the last host while its own
Settings is open satisfies both branches at once): "no host is paired" is both true and the one that
names the way out, with the pairing row directly beneath it. `ownerMissing` is still reported
truthfully by the view model in that state — it's a fact about the owner, not a copy-selection
signal — so the precedence lives in this one `if`/`else if`, not upstream. Neither copy state hides
the `Pair another server` row beneath it — with no host paired at all, that row is the only useful
thing left in the Connection section, and #749 wired it live (`onClick = onPairServer`, previously
`onClick = {}`) for exactly that reason.

### `HostIdentityRow` (sibling file)

Stateless composable in `ui/settings/HostIdentityRow.kt` (#749; gained `onClick` and `trailing`
in #750): renders one host's resolved `name`, `serverId`, `relayUrl` and `status: ConnectionStatus`
through the Connection section's existing `SettingsRow`/`ListItem` treatment — `name` as the
`ListItem` headline, `serverId` then `relayUrl` as two supporting lines, with
[`ConnectionStatusLine`](connection-status-line.md) beneath at the section's existing
`start = 16.dp, top = 4.dp, bottom = 8.dp` inset. `onClick: (() -> Unit)? = null` and
`trailing: (@Composable () -> Unit)? = null` both default to absent — the inert shape #749 shipped
when nothing on this screen navigated — and since #750 the caller passes them per row. #751 changed
*what* the owner's arm passes, not the component: `onEditHost` (opens the Edit host modal on this
destination's own host) + `HostOwnerTrailing()` (badge and chevron together) for the owner, a real
`onOpenHost(row.serverId)` callback + `ChevronIcon()` alone for every other saved host — every row now
passes a non-null `onClick`, where #750 had left the owner's `null`. The click target is the whole
`Column` including the status line beneath the identity `ListItem`, so the
affordance covers everything the row describes, not just its headline. Because the `ListItem`'s own
surface merges its descendants separately from the outer clickable `Column`, `serverId` and the "This
server" badge sit on a *descendant* of the click target, never on the click target's own node — a
device-test matcher that requires both on one node (`hasText(serverId) and hasClickAction()`) finds
nothing and times out live; match instead as `hasClickAction() and hasAnyDescendant(hasText(serverId))`,
as `SettingsScreenTest` and `InteractiveStreamE2ETest#interactiveTurn_twoHostsDefaultsAndArchive_stayPerHost`
(#1086) do. `SettingsRow`'s own rows (headline, supporting text and click action all on one node) need no
such split. Takes four already-resolved
display values plus the two optional slots rather than a `SettingsConnectionState` or a row model, so
the same component draws every row in the Connection section's list instead of a second treatment
being built for it; `name` is resolved once, in `SettingsHostRow.name`
([Settings ViewModel](settings-viewmodel.md)), so every caller of this row agrees on the
unnamed-host fallback.

All three strings originate in a scanned QR payload or locally-entered host metadata, and the
pairing parser bounds none of them in length (tracked as #752). A private `BoundedLine` helper
clamps each with `take(MAX_WORKSPACE_LABEL_CHARS)` (the same 128-char clamp
[`EditHostModal`](../../../app/src/main/java/de/pyryco/mobile/ui/components/EditHostModal.kt) uses)
before it reaches text layout, and renders with `maxLines = 1` + ellipsis overflow — `maxLines`
bounds only what is painted, so the clamp (not the overflow) is what keeps an oversized value a
truncation rather than a measurement stall. The relay URL is display text only here, same as
`EditHostModal`'s identity row: nothing on this screen opens or dials it.

### Composables in the same file (mostly `private`)

- `SettingsSectionHeader(text)` — `Text` with `MaterialTheme.typography.labelLarge` in `MaterialTheme.colorScheme.primary`, padding `(start=16, end=16, top=16, bottom=4)`.
- `SettingsRow(headline, supporting?, trailing?, onClick?)` is **internal since #271** so [`AboutScreen`](about-screen.md) shares the same treatment. It uses a `Row` with a weighted text `Column` on the surrounding `surface` colour. Supporting text uses `bodySmall`, 12 sp with a 16 sp line height. At normal text size, rows are 62 dp with supporting text, 52 dp for a single-line switch row, 48 dp for a tappable plain row and 44 dp for an inert plain row. Text wraps and rows grow at larger font scales. The native switch retains its 48 dp touch target. A non-null `onClick` makes the row clickable; otherwise it remains inert.
- `ChevronIcon()` — 20dp `Icons.AutoMirrored.Filled.KeyboardArrowRight`, decorative (`contentDescription = null`). Still `private` here; reused in place by the new About entry row.
- `HostOwnerBadge()` — `private`, since #749; the short "This server" (`R.string.settings_host_current`) label. Drawn alone as the owner row's `trailing` through #750; since #751 it's one half of `HostOwnerTrailing()` below rather than the whole trailing slot.
- `HostOwnerTrailing()` — `private`, since #751. `Row(verticalAlignment = Alignment.CenterVertically) { HostOwnerBadge() ; Spacer(Modifier.width(8.dp)) ; ChevronIcon() }` — the owner row's badge and the frame's own chevron, alongside each other rather than one replacing the other, matching the Figma frame's badge-then-chevron order (the frame's other rows put the chevron last at the right edge).
- `ExternalLinkIcon()` — **moved to [`AboutScreen.kt`](about-screen.md) in #271** with the rows that use it (the 18dp `painterResource(R.drawable.ic_open_in_new)` decorative vector; `material-icons-extended` is banned project-wide, so the asset ships as a per-file vector drawable). No longer defined in `SettingsScreen.kt`.
- `AddPill(onClick)` — `TextButton` (not `OutlinedButton`) with 16dp leading `Icons.Default.Add`, `Spacer(width=4.dp)`, and "Add" text in `MaterialTheme.typography.labelLarge`. The architect's spec called `OutlinedButton` with a fallback to `TextButton` if the default border was too prominent; the developer picked `TextButton` outright after the eyeball check against the Figma screenshot. The `+` icon takes `contentDescription = stringResource(R.string.cd_add_memory_plugin)` because it's the only labelled interactive control inside the pill.

### `ThemePickerDialog` (sibling file)

`internal` composable in `ui/settings/ThemePickerDialog.kt` (#87). M3 `AlertDialog` with `title = stringResource(R.string.settings_theme_dialog_title)` ("Theme") over a `Column(Modifier.selectableGroup())` of three `Row`s — one per `ThemeMode.entries`. Each row carries `Modifier.fillMaxWidth().selectable(selected, role = Role.RadioButton, onClick = { pending = mode }).padding(vertical = 8.dp)` plus `RadioButton(selected, onClick = null)` (the row owns the gesture) + 8.dp `Spacer` + `Text(mode.label(), style = bodyLarge)`. Buttons: `confirmButton = TextButton { onConfirm(pending) }` labelled `android.R.string.ok`; `dismissButton = TextButton { onDismiss() }` labelled `android.R.string.cancel`. `onDismissRequest = onDismiss`, so scrim taps and back-press route through the same path as Cancel — `pending` is discarded. Pending choice: `var pending by remember(selected) { mutableStateOf(selected) }` — the `selected` key resets the radio when the parent reopens the dialog after the persisted value changed in the background. Why OK / Cancel over tap-to-commit: the entire app's color scheme repaints on confirm, so an explicit confirm step matches AC #2's "confirming" / "cancelling" wording and avoids accidental-tap repaints.

### `ModelPickerDialog` (sibling file)

`internal` composable in `ui/settings/ModelPickerDialog.kt` (#232). Mechanical copy of `ThemePickerDialog` with `ThemeMode` → `Model` substitutions: M3 `AlertDialog` with `title = stringResource(R.string.settings_model_dialog_title)` ("Default model") over a `Column(Modifier.selectableGroup())` of three `Row`s (one per `Model.entries`) — same per-row `selectable + RadioButton(onClick = null) + Spacer + Text(model.label(), style = bodyLarge)` shape, same OK / Cancel `TextButton`s with `android.R.string.{ok,cancel}` labels, same `var pending by remember(selected) { mutableStateOf(selected) }` pending pattern, same `onDismissRequest = onDismiss` semantics. The three-row count is the same as `ThemePickerDialog`'s. **Imports `Model.label()` from `data/preferences/Model.kt`; does not declare its own extension** — diverges from `EffortPickerDialog.kt` where `Effort.label()` lives at file scope because the data-layer enum was identifier-only at the time (per [#231](../codebase/231.md)'s "defer labels to first UI consumer" convention). `Model.label()` was co-located with the enum in [#253](../codebase/253.md)'s partial walk-back (StatusSheet model section + status-row consumer pre-empted the Settings picker as the first consumer); see [App preferences § design-decision-defer-label-extensions-on-data-layer-enums](app-preferences.md#design-decision-defer-label-extensions-on-data-layer-enums) for the per-enum walk-back rule. The three labels (`"Opus 4.7"` / `"Sonnet 4.6"` / `"Haiku 4.5"`) stay in the `when` body rather than fanning into `strings.xml` — same single-source-of-truth precedent as `ThemeMode.label()` / `Effort.label()`, plus the product-vendor names are intentionally non-localised.

### `EffortPickerDialog` (sibling file)

`internal` composable in `ui/settings/EffortPickerDialog.kt` (#233). Mechanical copy of `ThemePickerDialog` with `ThemeMode` → `Effort` substitutions: M3 `AlertDialog` with `title = stringResource(R.string.settings_effort_dialog_title)` ("Default effort") over a `Column(Modifier.selectableGroup())` of five `Row`s (one per `Effort.entries`) — same per-row `selectable + RadioButton(onClick = null) + Spacer + Text(effort.label(), style = bodyLarge)` shape, same OK / Cancel `TextButton`s with `android.R.string.{ok,cancel}` labels, same `var pending by remember(selected) { mutableStateOf(selected) }` pending pattern, same `onDismissRequest = onDismiss` semantics. The five-row count fits comfortably inside the default M3 dialog dimensions; no `LazyColumn` or `heightIn(...)` ceremony needed — see [`../codebase/233.md`](../codebase/233.md) § Lessons learned for when that threshold would matter. **The `Effort.label()` extension lives at file scope in `EffortPickerDialog.kt`, not in `SettingsScreen.kt`** (diverges from `ThemeMode.label()`'s placement) — `SettingsScreen.kt`'s row subtitle and the dialog's row text both resolve it; pre-[#229](../codebase/229.md) through same-package `internal` visibility, post-#229 through the widened top-level public form. The widening was triggered by the StatusSheet `FilterChip` row in [#229](../codebase/229.md) becoming the second consumer one package over — the architect chose the one-line `internal → public` diff over moving the extension next to the enum in `data/preferences/Effort.kt`, since the file is already the natural home for label-string ownership. The five labels (`"low"` / `"medium"` / `"high"` / `"xhigh"` / `"max"`) deliberately stay in the `when` body rather than fanning into `strings.xml` — same precedent as `ThemeMode.label()` (one source of truth for the row subtitle, the dialog options, and the chip row; out-of-scope `strings.xml` cleanup is rejected by `CLAUDE.md`).

### Strings

Twelve string ids in `strings.xml`: `settings_title` ("Settings"), `cd_add_memory_plugin` ("Add memory plugin"), `settings_theme_dialog_title` ("Theme", added #87 for the `ThemePickerDialog` title), `settings_model_dialog_title` ("Default model", added #232 for the `ModelPickerDialog` title), `settings_effort_dialog_title` ("Default effort", added #233 for the `EffortPickerDialog` title), `settings_use_wallpaper_colors` ("Use Material You dynamic color" since #163; was "Use wallpaper colors" between #89 and #163), `settings_use_wallpaper_colors_unsupported` ("Requires Android 12 or newer", added #89 for the disabled-pre-S `supporting` line), `archived_discussions_count_supporting` ("%1$d archived", added #164 for the Storage row's live supporting line), `about_settings_row` ("About", added #271 for the navigable About entry — the sibling `about_title` for the screen's TopAppBar lives with [`AboutScreen`](about-screen.md)), `settings_host_none` ("No host is paired") and `settings_host_unknown` ("This host is no longer paired") — both added #749 for the Connection section's two copy states — and `settings_host_current` ("This server", added #750 for the owner's badge) — all three deliberately **argument-free**: `settings_host_none`/`settings_host_unknown` are announced verbatim by the screen-reader shell, so an embedded host name or relay address would be read aloud, and neither state has a host whose identity it is entitled to show; `settings_host_current` labels a row whose own three lines already carry that host's identity, so the badge adds no new identity of its own — and the pre-existing `cd_back`. All three pickers' OK / Cancel buttons reuse `android.R.string.ok` / `android.R.string.cancel` — no app-side strings for those. **The remaining row headlines and subtitles are hardcoded inline as Kotlin `String` literals** — per the ticket they're intentional scaffolding placeholders that Phase 3 will replace wholesale by data-layer wiring, so routing them through `strings.xml` would create work the resource files can't usefully own. Extracting the Use-wallpaper-colors headlines in #89 is the exception: the row became real persisted state, the helper string had to land somewhere localisable, and the precedent for extracting "row that became real" was set by `archived_discussions_settings_row` in #94. #164 extends the same "row that became real" rule to the live-count supporting line. The three Theme labels (`"System"` / `"Light"` / `"Dark"`) live as the body of the `internal` `ThemeMode.label()` extension and are reused by both the row subtitle and the dialog rows; the three Model labels (`"Opus 4.7"` / `"Sonnet 4.6"` / `"Haiku 4.5"`) live in the public `fun Model.label()` extension co-located with the enum at `data/preferences/Model.kt` since [#253](../codebase/253.md) and are reused by both the row subtitle and the `ModelPickerDialog` rows (plus the StatusSheet model section); the five Effort labels (`"low"` / `"medium"` / `"high"` / `"xhigh"` / `"max"`) live in the parallel `Effort.label()` extension (in `EffortPickerDialog.kt`, not `SettingsScreen.kt` — see § `EffortPickerDialog` above) for the same single-source-of-truth reason. The `license_title` id from #91 was deleted in #163 alongside the orphaned `LicenseScreen` (see § About).
