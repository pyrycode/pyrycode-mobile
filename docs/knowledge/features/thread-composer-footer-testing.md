- **Remembered effort recall ([#686](https://github.com/pyrycode/pyrycode-mobile/issues/686), waits for eligibility since [#1310](https://github.com/pyrycode/pyrycode-mobile/issues/1310)):** `ThreadViewModelEffortRecallTest` covers, with a `ScriptedRepo`-style fixture and an in-memory `RememberedEffortStore`: nothing remembered sends no write and stores nothing; a remembered, published level with an empty saved effort produces exactly one write to this session, the pending shows the level, and the refreshed reading decides the settled display; a saved choice (including one another device made) is preserved with no write; a rejected recall reverts and signals like a tap, stores nothing, and a later reading in the same opening sends no second write; an effort tap before the decision cancels the recall, only the tap's write goes out, and the tap's level is remembered; a successful tap is remembered while a failed tap, a model-only write and passive readings are not; a successful tap through the real `AppPreferences` store survives a restart (a new `AppPreferences` over the same DataStore file); a send while the recall write is outstanding reaches the repository only after the ack, while a send before any reading is never held; and two conversations sharing one store each get a write addressed only to their own session, with a replaced-session reading triggering nothing until the live session's own reading arrives. Since #1310, `no_session` and `unpublished` are waiting conditions, not terminal skips, and the class covers both directions: a non-writable (empty-session) reading sends nothing, then a later reading once the live session arrives starts exactly one write, and a subsequent empty-effort reading in the same opening sends no second one; a selected model lacking the remembered level sends nothing, then selecting a model that offers it starts exactly one write, with later readings sending no second one. Two more cases pin that waiting still yields to a terminal outcome: a saved choice that arrives while waiting on the model ends the recall even though a later reading offers the level; an effort tap received while waiting on a session ends the recall even though a later reading both gains the session and offers the level, and only the tap's level is sent and remembered. `AppPreferencesTest` gained the `rememberedEffort` round-trip, absent-on-fresh-store, and restart-survival cases, plus a case proving `setRememberedEffort` leaves `defaultEffort` untouched and vice versa. No rung-3 scenario: the live recall and restart proof belongs to [#545](https://github.com/pyrycode/pyrycode-mobile/issues/545).

New `ComposerActionAvailabilityTest` (12 cases) covers `absentComposerActions` directly: a complete menu lacking the command proves it absent while `ResetSession` is never in the result; no menu, a nonzero dropped count and a *negative* dropped count each prove nothing; a truncated `name` or `aliases` anywhere in the menu proves nothing, while a truncated `description` or `argument_hint` still proves; a name or alias match keeps a command available; and the match is exact — no leading slash, no case fold, no trim. New `ThreadViewModelComposerActionsTest` (8 cases) drives `onComposerCommand` against a `FakeConversationRepository`-backed fixture that records sends: Compact and Knowledge Capture send their command to the VM's own conversation and leave the draft alone, including a draft that equals the command text; a thrown send (both `RelayErrorException` and `IllegalStateException`) is swallowed without an uncaught exception, the draft untouched, and no `outcome=sent` logged; a seeded complete menu without `compact` puts it in `state.absentActions`, `onComposerCommand` then sends nothing and logs `outcome=absent`, while Knowledge Capture still sends; an alias match keeps Compact available; a seeded menu for *another* conversation never greys this one's rows; and `ResetSession` through `onComposerCommand` sends nothing (it never reaches the guarded send at all). `ThreadComposerFooterTest` (Robolectric) gained cases for the Actions button leading the row and opening its three button-mode rows in top-to-bottom order; Reset session dispatching `ThreadEvent.NewSession` and closing the overlay; a command row dispatching `onComposerCommand` and closing the overlay; Reset session absent (not merely disabled) without `mutationsSupported`; a seeded-absent row rendering disabled and inert to a tap while the other two rows stay enabled; and an outside tap and Back each closing the Actions overlay with no dispatch. - **Session capability list ([#1111](https://github.com/pyrycode/pyrycode-mobile/issues/1111)):** `SessionSettingsPayloadsTest` (`app/src/test/.../network/`) covers the decode boundary: a reply without `capabilities` decodes `SessionSettings.capabilities == null`; a present object decodes both arrays and ignores undeclared keys (the protocol's own Codex example); an object without `slash_commands` decodes `true`; `slash_commands: false` decodes `false`; and an object missing either required array, or a non-object value, throws — the frame fails exactly like any other malformed field. `FooterMenuTest` gained cases with a `capabilities` list seeded on `ThreadRunConfig`: the effort menu offers only the intersection of the selected row's levels and `effortLevels`; the permission menu offers only `permissionModes` plus `Bypass approvals` unconditionally; `Auto` still needs `supportsAutoMode` even when the list includes it; and with no list, both menus are unchanged from their pre-#1111 behaviour (the existing six-mode / full-levels cases). `ComposerActionAvailabilityTest` gained `absentComposerActions(menu, slashCommands = false)` cases: Compact session and Knowledge capture are both absent whether `menu` is `null`, a complete menu naming them, or anything else, while Reset session is never affected; `slashCommands = true` (the default) leaves the menu-only verdict unchanged. `ThreadViewModelComposerActionsTest` gained a settings reading with `capabilities.slashCommands = false` putting both commands in `state.absentActions` and `onComposerCommand` sending neither, plus `true` and an absent `capabilities` both leaving nothing newly absent. `ThreadViewModelPermissionTest` gained a case where a `capabilities.permissionModes` list omits the confirmed-adjacent mode and `onPermissionModeSelected` sends nothing for it, mirroring the menu's own filter so the two paths cannot disagree. No rung-3 scenario: the phone does not advertise `multi_agent` until [#1119](https://github.com/pyrycode/pyrycode-mobile/issues/1119), so no daemon sends the list yet — see [Thread composer footer § Sourcing — Permission mode](thread-composer-footer.md#permission-mode-650) and [Actions menu](thread-composer-footer-actions-menu.md#actions-menu-884) for the design.
- **Trailing icons on a full footer ([#1032](https://github.com/pyrycode/pyrycode-mobile/issues/1032)):** `ThreadComposerFooterLayoutTest` (`app/src/test`) covers the pure `footerShrinkCap` directly — everything fits → `Int.MAX_VALUE`; one wide label over budget → only it is capped and the fitted sum equals `available` exactly; every label over budget → an equal shared cap; zero `available` → every button capped to 0. `ThreadComposerFooterWidthTest` (`app/src/sharedTest`, its own class, `@GraphicsMode(NATIVE)` at class level so Robolectric measures labels with real fonts) hosts `ThreadComposerFooter` inside `DeviceConfigurationOverride.ForcedSize(411.dp, 800.dp)` — a 1080px Pixel 8 — showing "Actions, Manual approval, default, medium": both the paperclip and the Status opener are asserted `isDisplayed()`, 24dp wide since #1659, inside the footer's bounds, and each fires its callback once on a tap; all four buttons stay displayed. Before the fix it failed with the paperclip squeezed to 24.5dp. The default Robolectric graphics mode measures labels too narrow to reproduce the bug, and Robolectric's default 320dp width is already narrow enough that a naive fix could still pass there while breaking at phone width — both the forced width and `@GraphicsMode(NATIVE)` are needed to catch it. See [Thread composer footer § Trailing icons stay outside the weighted text region](thread-composer-footer.md#trailing-icons-stay-outside-the-weighted-text-region-1032) for the layout this proves, and [Development & verification § Where a screen test goes](development-verification-gates.md#where-a-screen-test-goes) for the `ForcedSize` / `@GraphicsMode(NATIVE)` guidance this test follows. No rung-3 scenario: this is a layout-only fix with no operator-facing flow change.
- **Context usage segment ([#946](https://github.com/pyrycode/pyrycode-mobile/issues/946), computed since [#1411](https://github.com/pyrycode/pyrycode-mobile/issues/1411)):** `ThreadViewModelContextUsageTest` (a per-conversation `MutableStateFlow<Map<String, ContextUsage>>` `ScriptedRepo`, plus a `SessionSettings?` flow) covers: no reading or settings before anything arrives → `contextPercent == null`; a reading → computed from its own `totalTokens`/`maxTokens`, not its reported `percentage` (50,000/200,000 is pinned to 25% even when the reading's `percentage` field says 84); a replaced reading → the new computed percentage; no reading at all → `SessionSettings.usedTokens`/`.windowTokens` fills in; a reading present with settings also available outranks them, and clearing the reading (what a session transition or reconnect does to the repository's map) falls back to the settings figure; a settings pair with a zero window stays `null` even though `settingsAvailable` is true; a reading only for another conversation never appears on this one. `ContextPercentTest` (new, `app/src/test/.../thread/`) pins the pure function itself: the rounding edges (0.5%→1, 0.49%→0, 84.5%→85), the clamp in both directions, a reading with `maxTokens = 0` giving `null` rather than falling back, and a settings window `<= 0` giving `null`. `ThreadComposerFooterTest` (Robolectric): `contextSegment_showsTheReportedPercentage_andTheSheetAgrees` asserts `"Cxt: 84%"` with its `"Context usage 84%"` description and, after opening the sheet from the trailing icon, `"84% used"` there too; `contextSegment_withoutAReading_saysUnavailable_andShowsNoNumber` asserts `"Cxt: n/a"` / `"Context usage unavailable"` in the footer and `"Not reported yet"` in Run configuration and zero nodes anywhere containing a `%` character; `contextSegment_showsAReplacedReading_andOpensNoOverlay` re-seeds `contextPercent` and asserts the new value replaces the old one with no overlay opened (`hasClickAction()` is false on the segment). `StatusSheetTest`'s `renders_the_reported_context_percentage_in_place_of_the_unavailable_line` asserts `"84% used"` replaces the unavailable line with no former Context window helper caption. These footer/sheet screen tests set `contextPercent` directly, so they are unaffected by where the value now comes from. No rung-4 twin: whether the scripted `fakeclaude` path makes the daemon publish `context_usage` is not established by either ticket; #1411's settings-fallback path has no rung-3 scenario either, since it is a change in where an existing surface's value comes from, not a new operator flow. See [Thread composer footer § Context usage segment](thread-composer-footer-context-usage.md#context-usage-segment-946-computed-since-1411) for the design, and [e2e coverage](../../e2e-interactive-stream.md) for the rung-3 scenario.

## Related

The five live settings scenarios restored by [#1397](https://github.com/pyrycode/pyrycode-mobile/issues/1397)
cover per-conversation model changes, inherited effort, remembered effort, operator bypass and footer
readings after reconnect. Their shared settings helper ignores a held reply and waits for the live
connection's reply. The reconnect scenario keeps the context percentage and announced model across the
reconnect. Its next turn must finish and increase the context token count, proving that the connection
delivered fresh data even when the displayed percentage stays the same.
