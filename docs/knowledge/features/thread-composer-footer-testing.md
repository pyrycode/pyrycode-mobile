## Testing

- **Unit** (`app/src/test/.../thread/FooterMenuTest.kt`) exercises `footerMenu` against constructed `ThreadRunConfig`s: no menu / an empty published menu / a selected row with no effort levels / no matching row all resolve to `null`; a real menu resolves to options in daemon order with verbatim `value`s; `notListed` is asserted to be `droppedModels + hiddenChoices` even in cases where `choices.size` would suggest a different number, guarding the "never recomputed from the row count" rule. Since #650, it also covers Permission: hidden (`null` menu/label) on `permissionMode == ""`; all six `PermissionModeOption` labels; `Auto` offered only when the selected row's `supportsAutoMode` is true; an unrecognised value produces an inert label with no option selected and nothing listed; `footerControlEnabled` gated by `pendingPermission` independently of `pendingModel` / `pendingEffort`.
- **Unit** (`app/src/test/.../thread/ThreadViewModelPermissionTest.kt`, new in #650): the label tracks only the confirmed reading and is hidden on `""` even with a non-empty session id; Bypass approvals sends `yolo = true` with no `permissionMode`, every other choice sends `permissionMode` with no `yolo`; nothing is sent for the confirmed mode, an empty session id, an unrecognised value or unsupported `auto`; the label is unchanged while pending and after an ack until a reading reports the new mode; the settle loop re-reads immediately then every 500 ms, stops on the requested mode, survives an early old-mode reading, expires at 15 s, and never opens a second `observeSessionSettings` subscription (a held read blocks the next refresh); a refusal and an `IllegalStateException` each clear the pending mark, send one error signal and one re-read; a `null` reading and a reading for another session both cancel the outstanding write and hide the label; a late ack from a cancelled write starts no settle; and `currentSessionId` differing from the reading's session id hides the permission label while `ThreadRunConfig.modelLabel` / `effortLabel` stay put.
- **Compose** (`app/src/sharedTest/.../thread/ThreadComposerFooterTest.kt`, replacing the deleted `ThreadStatusRowTest`), hosted on `ThreadScreen` with mutable state: buttons show the current labels and the trailing icon opens the Status sheet in one tap; tapping the model button lists only the published model labels and choosing one calls `onModelSelected` exactly once and closes the overlay; the effort overlay lists only the selected row's levels, and a row with no levels leaves the effort button disabled with nothing opening on tap; tapping the input field while an overlay is open dismisses it, selects nothing, and leaves the field unfocused; the pending state renders its `stateDescription` and clears back to the saved label once a confirming reading lands; every option row is asserted `isDisplayed()` (pinning the `IntrinsicSize.Max` width fix — see [Options overlay](options-overlay.md#the-column-intrinsicsizemax-before-verticalscroll)); a non-zero `droppedModels` renders the not-listed caption; and switching `conversationId` while an overlay is open closes it. Since #650: the permission button opens the six-mode menu (`Auto approval` hidden without `supportsAutoMode`), and is absent from the row entirely when `permissionMode` is `""`.
- **Compose** (`app/src/sharedTest/.../components/StatusSheetTest.kt`): `has_no_yolo_switch` asserts the sheet renders no YOLO row or switch at all, now that the permission control lives only in this footer — see [Status sheet](status-sheet.md).
- No rung-3 real-daemon scenario landed in #650; the live Plan → Bypass approvals → Manual approval transition (and its tool approval) is [#687](https://github.com/pyrycode/pyrycode-mobile/issues/687)'s, not this file's. The Model/Effort live scenario is covered by #679.
- **Remembered effort recall ([#686](https://github.com/pyrycode/pyrycode-mobile/issues/686)):** `ThreadViewModelEffortRecallTest` (new) covers, with a `ScriptedRepo`-style fixture and an in-memory `RememberedEffortStore`: nothing remembered sends no write and stores nothing; a remembered, published level with an empty saved effort produces exactly one write to this session, the pending shows the level, and the refreshed reading decides the settled display; a saved choice (including one another device made) is preserved with no write; an unpublished level and a non-writable (empty-session) reading both send nothing; a rejected recall reverts and signals like a tap, stores nothing, and a later reading in the same opening sends no second write; an effort tap before the decision cancels the recall, only the tap's write goes out, and the tap's level is remembered; a successful tap is remembered while a failed tap, a model-only write and passive readings are not; a successful tap through the real `AppPreferences` store survives a restart (a new `AppPreferences` over the same DataStore file); a send while the recall write is outstanding reaches the repository only after the ack, while a send before any reading is never held; and two conversations sharing one store each get a write addressed only to their own session, with a replaced-session reading triggering nothing until the live session's own reading arrives. `AppPreferencesTest` gained the `rememberedEffort` round-trip, absent-on-fresh-store, and restart-survival cases, plus a case proving `setRememberedEffort` leaves `defaultEffort` untouched and vice versa. No rung-3 scenario: the live recall and restart proof belongs to [#545](https://github.com/pyrycode/pyrycode-mobile/issues/545).
- **Applied effort ([#889](https://github.com/pyrycode/pyrycode-mobile/issues/889)):** `FooterMenuTest`'s `config(...)` builder grew an `appliedEffort` parameter — saved and applied disagreeing resolves the label/selection to the applied value; `Unavailable` / `Applied("")` / `NotReported`, each with and without a saved choice, resolve to the selection, label ("Effort" when empty) and note the design lays out above; a pending tap outranks applied and clears the note; an applied value outside the published levels still becomes the label with no option marked selected. New `ThreadViewModelAppliedEffortTest`: an older daemon's `Unavailable` reading falls back to the saved choice with its note; a reading alone sends no `setSessionSettings`; a late reply for a replaced session never shows the old applied value; a rejection rolls back to the pre-tap display for both an applied value and no selection; a post-ack refresh reading's applied value wins over the tapped level. One `ThreadComposerFooterTest` case renders a `NotReported` config as "Effort" with the not-reported state description; one `StatusSheetTest` case asserts the note caption renders below the effort chips. No rung-3 scenario: the ticket assigns the live proof of applied effort to [#545](https://github.com/pyrycode/pyrycode-mobile/issues/545).
- **Actions menu ([#884](https://github.com/pyrycode/pyrycode-mobile/issues/884)):** `FooterMenuTest` covers the Actions branch of `footerMenu` directly — the three rows in order with nothing selected and `actions = true`; Reset session dropped when `mutationsSupported = false`; a seeded `absentActions` set disabling only the matching row; `footerControlEnabled(Actions, …)` true with no session and with a model/permission write pending; and that the new `mutationsSupported` / `absentActions` parameters are no-ops for every other control. New `ComposerActionAvailabilityTest` (12 cases) covers `absentComposerActions` directly: a complete menu lacking the command proves it absent while `ResetSession` is never in the result; no menu, a nonzero dropped count and a *negative* dropped count each prove nothing; a truncated `name` or `aliases` anywhere in the menu proves nothing, while a truncated `description` or `argument_hint` still proves; a name or alias match keeps a command available; and the match is exact — no leading slash, no case fold, no trim. New `ThreadViewModelComposerActionsTest` (8 cases) drives `onComposerCommand` against a `FakeConversationRepository`-backed fixture that records sends: Compact and Knowledge Capture send their command to the VM's own conversation and leave the draft alone, including a draft that equals the command text; a thrown send (both `RelayErrorException` and `IllegalStateException`) is swallowed without an uncaught exception, the draft untouched, and no `outcome=sent` logged; a seeded complete menu without `compact` puts it in `state.absentActions`, `onComposerCommand` then sends nothing and logs `outcome=absent`, while Knowledge Capture still sends; an alias match keeps Compact available; a seeded menu for *another* conversation never greys this one's rows; and `ResetSession` through `onComposerCommand` sends nothing (it never reaches the guarded send at all). `ThreadComposerFooterTest` (Robolectric) gained cases for the Actions button leading the row and opening its three button-mode rows in top-to-bottom order; Reset session dispatching `ThreadEvent.NewSession` and closing the overlay; a command row dispatching `onComposerCommand` and closing the overlay; Reset session absent (not merely disabled) without `mutationsSupported`; a seeded-absent row rendering disabled and inert to a tap while the other two rows stay enabled; and an outside tap and Back each closing the Actions overlay with no dispatch. No rung-3 scenario: the AC assigns the live proof to [#679](https://github.com/pyrycode/pyrycode-mobile/issues/679).

  Adding the Actions button widened the footer row and moved the buttons after it: `ThreadComposerFooterTest`'s pre-existing `outsideTap_dismissesWithoutSelecting_andNeverReachesTheComposer` tapped the input field's own centre as its "outside" point, and at Robolectric's 320dp width the Model overlay (opened from its new, further-right position) now covers that centre — the tap landed inside the overlay and silently selected a model instead of dismissing it. The fix moved the tap to the field's start, which the scrim still covers; the footer layout itself is unchanged, and the fix is test-side only. Any further button added ahead of Model will move the overlays again and can reopen the same failure mode — a fixed offset from an edge is more robust here than a fixed offset from the field's centre.

  Seeding `FakeConversationRepository.setSlashCommandMenu` (a `MutableStateFlow` write) before asserting on `ThreadViewModel.state.value` needs `advanceUntilIdle()` even with an `UnconfinedTestDispatcher` installed as `Main` — unlike a scripted fake's plain `MutableSharedFlow.emit`, which does not need it. See [Development & verification § Test scheduling and harnesses](development-verification.md#test-scheduling-and-harnesses) for the general rule this instance follows.
- **Context usage segment ([#946](https://github.com/pyrycode/pyrycode-mobile/issues/946)):** `ThreadViewModelContextUsageTest` (new, a per-conversation `MutableStateFlow<Map<String, ContextUsage>>` `ScriptedRepo`) covers: no reading before any frame arrives → `contextPercent == null`; a reading → its `percentage` verbatim, pinned against a total/max ratio that disagrees with it (50,000/200,000 would be 25%, the reading says 84%); a replaced reading → the new percentage; a cleared reading (what a session transition or reconnect does to the repository's map) → `null` again; a reading only for another conversation → never appears on this one; and `SessionSettings.usedTokens`/`.windowTokens` populated with no `ContextUsage` reading still leaves `contextPercent` `null` — pinning that the transcript-derived settings figures never fill in for it. `ThreadComposerFooterTest` (Robolectric): `contextSegment_showsTheReportedPercentage_andTheSheetAgrees` asserts `"Cxt: 84%"` with its `"Context usage 84%"` description and, after opening the sheet from the trailing icon, `"84% used"` there too; `contextSegment_withoutAReading_saysUnavailable_andShowsNoNumber` asserts `"Cxt: n/a"` / `"Context usage unavailable"` on both surfaces and zero nodes anywhere containing a `%` character; `contextSegment_showsAReplacedReading_andOpensNoOverlay` re-seeds `contextPercent` and asserts the new value replaces the old one with no overlay opened (`hasClickAction()` is false on the segment). `StatusSheetTest`'s `renders_the_reported_context_percentage_in_place_of_the_unavailable_line` asserts `"84% used"` replaces the unavailable line while the caption stays. No rung-4 twin: whether the scripted `fakeclaude` path makes the daemon publish `context_usage` is not established by this ticket. See [Thread composer footer § Context usage segment](thread-composer-footer.md#context-usage-segment-946) for the design, and [e2e coverage](../../e2e-interactive-stream.md) for the rung-3 scenario.
