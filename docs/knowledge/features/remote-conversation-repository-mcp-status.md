# Remote conversation repository — the MCP status reading and the reconnect/toggle sends

Part of [Remote conversation repository — the Phase 4 `ConversationRepository`](remote-conversation-repository.md); see that document for what the repository does overall. Sibling to the [model-list and slash-command-list menus](remote-conversation-repository-model-and-slash-command-menus.md), split out as its own document from the start (#1343) rather than folded into the main document's size cap, since it already carries three request verbs and five flags.

## What it holds

`McpStatusProjection` (#1343) is one more connection-scoped status projection, the `ModelMenuProjection` shape: it owns the decode, the retained state, the three outbound sends and their refusal correlation, constructed once per `RemoteConversationRepository` instance from the shared `send`/`negotiatedCapabilities`/`nextRequestId` the repository's other projections already use. **Deliberately not in [`HostReadings`](relay-repository-coordinator.md)**: unlike `SlashCommandMenuProjection`, which #1317 promoted to a held-per-host reading, the MCP reading stays per connection on purpose — a reconnect starts from nothing and the surface that wants it (#1344's Channel info list, #1345's failure notice) asks again. That re-ask is the designed recovery path, not a gap to close.

`ConversationRepository.observeMcpStatus(conversationId): Flow<McpStatus>` returns one value that carries a report and five flags together, not five+1 separate streams — see [Conversation repository § `McpStatus`](conversation-repository.md#shape) for the domain type and the rule that a report clears all five flags in the same emission a collector sees it in, so nothing can observe a fresh report beside a stale flag.

## The push and the correlated reply — `mcp_status`

One frame shape serves three deliveries: pushed once per eligible claude child, and the correlated answer to each of the three requests below (by `in_reply_to`, which `apply` only consumes — never routes on). Decode boundary: `McpStatusPayloadDto.toReport()` in `data/network/McpStatusPayloads.kt`, the `ContextUsagePayloads.kt` strict-required-DTO shape: every key required, no Kotlin default, so a missing or wrong-typed key fails the decode outright rather than falling back to a value this type cannot legitimately hold. The one value-level reject is a negative `dropped_servers`, which `toReport()` turns into `null` the same way `ContextUsageProjection` rejects a negative percentage.

- **Routes on the payload's own `conversation_id`, never on what the ask named** — the `ModelMenuProjection`/`request_model_list` rule applied here too: a frame naming another conversation can only ever write that conversation's entry, so a daemon answering an ask for A with B's id cannot land B's rows under A.
- **Replaces the report and clears all five flags** (desktop's `setMcpStatus`): `servers: []` is a report of no servers, distinct from the `null` "no report yet" a fresh `McpStatus()` starts at. `droppedServers` is carried verbatim, never recomputed from `servers.size`.
- **Malformed drops the one envelope**, same idiom as every `onInbound` arm: the prior report and flags stand, the single inbound collector survives, and the caught `IllegalArgumentException` is discarded because kotlinx-serialization can quote the offending input — which here is claude-authored server text.
- **Gated on the negotiated `interactive` capability**, the same arm shape as `context_usage` and `model_list` — a non-interactive connection never decodes this frame or any of the three requests below.

## The three outbound sends and their refusal correlation

`mcp_status_request`, `mcp_reconnect` and `mcp_toggle` (wire SSOT: pyrycode `docs/protocol-mobile.md` §§ "Asking for MCP status on demand" and "Actuating MCP servers on demand") each always carry `conversation_id`; the two actuation verbs also always carry `server_name`, and `mcp_toggle` always carries `enabled` with no default, independent of `MobileJson`'s own default-encoding setting. `ConversationRepository.requestMcpStatus`/`reconnectMcpServer`/`toggleMcpServer` are fire-and-forget `Unit` methods — the answer arrives only on `observeMcpStatus`, never as a return value — and are the **reasoned exception** to the "one-shot outbound `Unit` send defaults to `error(...)`" convention; see [Conventions § the no-op default exception](conversation-repository-conventions.md#conventions) for why "when nothing can be sent, nothing is set" is this contract's own outcome, not silent drift.

- **One ledger, keyed by the request's own envelope id, never by the server name or the requested state.** `asks: ConcurrentHashMap<Long, Pair<Verb, String>>` (verb + conversation id) is disjoint from `RelayRequests`' waiters and from `ModelMenuProjection`'s own `modelListAsks` by construction — every id comes from the same one counter, so an `in_reply_to` resolves in at most one of these ledgers. Not capped: each entry is one user-triggered send on this connection, consumed by its correlated `mcp_status` or `error`, or removed if the send itself failed, and the whole table dies with the connection.
- **A reconnect or toggle sets its waiting flag before the send, not after.** Setting it first means a refusal arriving immediately cannot be overwritten by a late "begin" write landing after it — the same race `ModelMenuProjection`'s ask-ledger ordering avoids. The prior flag value is read from the same atomic `getAndUpdate` that sets it, so a concurrent caller cannot read a stale "I set it" result; a failed or throwing send rolls the flag back **only if this call is the one that set it**, which is not a retry — nothing re-sends on this path.
- **Guards return before anything is set:** an empty `conversationId`, or a connection without the negotiated `interactive` capability, sends nothing and sets no flag — the daemon would leave either inert anyway. `requestMcpStatus` has no waiting flag of its own; a status ask only ever sets `unavailable`, and only through a refusal.
- **Every correlated refusal is the single merged `error.code` `mcp_actuation.refused`** for both actuation verbs — the daemon does not distinguish causes on this wire, so `applyRefusal` does not read the code for those two; it settles `reconnecting`/`toggling` → `false` and `reconnectRefused`/`toggleRefused` → `true` on **any** code, including one that fails to decode. A toggle refusal can never settle as a reconnect one and vice versa: each ask records its own verb at send time, not inferred from the reply. A status-ask refusal is the one branch that does read `ErrorPayload.code` — only `mcp_status.unavailable` sets `McpStatus.unavailable`; `protocol.malformed` and `conversation.not_found` set nothing, matching desktop's `mcpStatusBridge.ts`.
- **No refusal of any kind touches the held report.** `setMcpStatus` is the only writer of `report`.
- **`endMcpReconnectWait`/`endMcpToggleWait` clear only their own waiting flag** (desktop's `endMcpReconnectWait`/`endMcpToggleWait`) — they do not touch `reconnectRefused`/`toggleRefused` or the report. These exist so the surface that started a wait (#1344) can release it if it goes away before an answer arrives; a daemon or relay that drops the reply would otherwise leave the flag stuck.

## Never logs

Server names, statuses and errors are claude-authored and are held for display only — never compared except by equality, never used as a map key, never logged, and never built into an exception message. `McpServerStatus.toString()` is overridden to omit every field (`"McpServerStatus(redacted)"`), the `AttachmentOffer.toString` precedent, so `McpStatusReport` and `McpStatus` cannot leak one of these strings through an accidental log line or assertion message either, since both inherit the redaction through their lists. A refusal's envelope carries no server text at all, so nothing on the refusal path needs a redaction rule of its own.

## For #1344 and #1345

The report and the five flags are the only state this ticket produces; rendering them was out of scope here. #1344 (Channel info's MCP servers section, see [Channel info sheet § MCP servers section](channel-info-sheet.md#mcp-servers-section)) renders all five `McpServerStatus` strings as inert text bounded to 256 Unicode code points (`boundMcpText`) — they carry no length bound beyond the transport frame cap, and the daemon's 256-byte `error` cap on the refusal path is not a bound on these. The code-point cut alone does not stop a status or error made of newlines from drawing an unusually tall row; a line bound on top of it is a known, non-blocking gap. #1345's failure notice still has to read `unavailable`/`reconnectRefused`/`toggleRefused` and is the surface expected to call `requestMcpStatus` again after a reconnect, since the reading starts empty on every new connection — #1344's Channel info section already does both of those, as its own re-ask-on-open and three notices.
