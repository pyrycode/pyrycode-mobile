### Attachment slot (since #984)

`MessageContainer` draws `MessageAttachments(message.attachments, attachmentStates, onAttachmentShown, onRetryAttachment, onOpenAttachment, onSaveAttachment, onRequestAttachment)` before `body()`, then `MessageMetaRow` last — attachments, text, meta row, for both roles (since #1513; before that it drew `body()` first) — and only when `message.attachments` is non-empty, so a text-only bubble lays out exactly as before. The decision (`16:8`) puts the attachment the text talks about in view first; `Message`'s one `content` field and unpositioned `attachments` can't express the Figma frame's attachment-between-paragraphs layout, so this is the closest the app can render. `MessageAttachments`, `AttachmentViewState`, `AttachmentSource`, `AttachmentTarget` and the thumbnail decoder live in a sibling file, `MessageAttachments.kt`, in this same package; `MessageBubble.kt` and `MessageContainer` only wire them in. This is the design's `Slot` inside the shared `Message` component (`16:8`) — a 160 × 160 image for an image-type attachment, or Figma's `File field` row (`132:4605`) for everything else. The Figma frame draws no visible save control, so #985's save action rides the same slot as a long-press rather than adding anything to the render — see [Open and save](#open-and-save-since-985) below. Since #1329 that same `File field` row is also what a *not yet fetched* file draws as — see [Fetch on open](#fetch-on-open-since-1329) below.

**No empty text block on an attachment-only message.** `private fun Message.hasNoBody(): Boolean = attachments.isNotEmpty() && content.isBlank()`. Both bubble roles skip their `Text`/`MarkdownText` call when this is true — the user arm with an early `if (message.hasNoBody()) return@MessageContainer`, the assistant arm's finalized branch with `else if (!message.hasNoBody())`. A message with both attachments and text is unaffected; a text-only message always keeps its body, since `hasNoBody()` requires attachments to be present.

**View state, keyed by attachment id.** `AttachmentViewState` is `Loading`, `Ready(source: AttachmentSource, displayName: String?, mimeType: String?)`, `NotFound` (final, no retry), or `Failed` (retryable). An id absent from the map is *not* always `Loading`: since #1329 it draws `Loading` only when the attachment [fetches on show](#fetch-on-open-since-1329); otherwise it draws as the ready file row with no request behind it, so a row never shows loading for a fetch nobody started — see [Load lifecycle](#load-lifecycle-since-984) and [Fetch on open](#fetch-on-open-since-1329) below. `AttachmentSource` is `Original(uri: String)` — the phone's own picked file, read through its still-live grant — or `Kept(file: File)` — `AttachmentStore`'s retained copy (see [Attachment retrieval](attachment-retrieval.md)). Both `AttachmentSource` and `Ready` override `toString()` to redact the URI/path/hints, so neither can reach a log line or a crash trace through a default data-class render. Only `Ready` is actionable — see [Open and save](#open-and-save-since-985) below.

**Name and MIME resolution — the reference wins, retrieval only fills gaps.** `MessageAttachment.displayName` / `mimeType` (#983's reference, set at send/history/offer time) take precedence; a blank or absent one falls back to `Ready.displayName` / `mimeType` (retrieval's sanitised hints, #899). An attachment is image-kind only when the resolved MIME starts with `image/`. The MIME is a layout hint, never a handler choice — a wrong hint, or a decode failure, ends in the file row. The same resolved name and MIME are what #985's `AttachmentTarget` carries to open and save.

**Image slot.** `Modifier.sizeIn(maxWidth = 160.dp, maxHeight = 160.dp).aspectRatio(1f)`, not `Modifier.size(160.dp)`: on a screen narrow enough that the bubble's lane is under 160dp, a fixed `size()` squeezed only the width and left the box non-square (measured 140 × 160 on the 320dp Robolectric test screen). `sizeIn` + `aspectRatio` gives a true 160 × 160 square at the 412dp reference width and a smaller square, never a rectangle, on a narrower one — and never `fillMaxWidth()`, which would pin the bubble to its lane (see [MessageBubble § Fill vs. hug](message-bubble.md#fill-vs-hug-the-streaming-arm-keeps-fillmaxwidth-since-644)). The slot holds this size from its first frame (`Loading`) to its last (`Ready`, decoded), so a thumbnail that lands late never moves the row or the thread's scroll position — the one exception is a decode failure, which falls back to the file row and does resize, visibly, which is the AC's own requirement.

Decoding runs in a `produceState<Thumbnail>(Thumbnail.Pending, source, decoder, sizePx)` keyed on the `AttachmentSource`, so it restarts if the source changes (e.g. `Original` → `Kept` on a page reload) and cancels when the item leaves composition. `AttachmentThumbnailDecoder` is a `fun interface` (`suspend fun decode(source, sizePx): ImageBitmap?`) behind `internal val LocalAttachmentThumbnailDecoder = staticCompositionLocalOf<AttachmentThumbnailDecoder?> { null }`; a `null` local falls through to `PlatformThumbnailDecoder`, so a test or preview supplies a fake without threading a parameter through every call site. The platform decoder runs on `Dispatchers.IO`, uses `ImageDecoder.createSource(file)` for `Kept` and `ImageDecoder.createSource(resolver, uri)` for `Original` — but only after `isForeignContentUri` passes, the same refusal `ComposerAttachmentStrip`'s `rememberThumbnail` and `ContentResolverAttachmentReader` apply, so a hostile provider cannot turn its own URI into a thumbnail of this app's private files. `ImageDecoder.decodeBitmap`'s header listener calls `thumbnailTargetSize(width, height, sizePx)` and sets that as the decode target — downscale only, short side covers `sizePx`, long side capped at `4 × sizePx`, each side at least 1, `null` for a non-positive dimension. This runs before any pixel buffer is allocated, so a 10⁶ × 160 header cannot allocate hundreds of MB before the cap is even read; any exception, or a `null` target, is caught and yields `null` (not rethrown — cancellation is the one exception re-thrown unchanged). A `null` decode result — or `state` being `NotFound`/`Failed` — falls back to `AttachmentFileRow`.

**File row (`File field`).** `FileGlyph` — the 45 × 60 `ic_attachment_file` page icon (the composer strip's `FileTile` glyph, #933) with `attachmentTypeLabel(name)` centred on its fold, 44dp wide — sits 12dp before a `Column` holding the name (`bodySmall`, `maxLines = 1`, `TextOverflow.MiddleEllipsis`, inside `Modifier.weight(1f, fill = false)` so a long name shrinks to the bubble's lane instead of widening it) and a status line: "Loading…" / "File not found" / "Couldn't load file" + a `TextButton` "Retry" / nothing for `Ready`. An absent name (reference and retrieval both null or blank) shows `R.string.thread_attachment_unnamed` ("Attachment") in both the name line and the glyph's fallback label. The page, type label, filename and status use the bubble's `LocalContentColor` at `ATTACHMENT_CONTENT_ALPHA = 0.80f`. Figma's inverse-primary tint was too faint for 12sp text on both fixed dark bubble fills; the bubble-relative color keeps the design's artwork and geometry legible. The [412 × 892 comparison](../../../app/src/androidTest/assets/attachment-1290/side-by-side-412x892.png) and [labelled overlay and difference](../../../app/src/androidTest/assets/attachment-1290/attachment-detail-overlay-difference.png) document that intentional tint departure from [File field (132:4605)](https://www.figma.com/design/g2HIq2UyPhslEoHRokQmHG?node-id=132-4605), inspected 2026-09-30. Figma does not show loading, failure, retry, open or save states; their existing behavior stays in the row.

**Test coverage cannot assert a shortened name through semantics.** `onNodeWithText(fullName)` still matches after `TextOverflow.MiddleEllipsis` truncates the drawn glyphs, because Compose semantics carry the whole string regardless of what is rendered. `MessageAttachmentsTest.longName_isShortenedWithinTheBubble_whichStaysInsideItsLane` asserts the drawn node's measured bounds instead — one line (`height < 20.dp`) and inside the bubble's lane — not that the text node's string is shorter. The enlarged-text case also checks the name and Retry bounds at 1.5× font scale; the [320 × 640 capture](../../../app/src/androidTest/assets/attachment-1290/emulator-compact-320x640-large-text.png) records the rendered layout. Since #985 this lookup needs `onNodeWithText(name, useUnmergedTree = true)`: making the row `combinedClickable` (see [Open and save](#open-and-save-since-985)) merges its child text into the row's own semantics node, so the un-flagged lookup started measuring the whole 60dp row instead of the name label alone.

#### Open and save (since #985)

Only a `Ready` attachment is actionable. `MessageAttachmentItem` wraps the image slot or the file row in `Modifier.combinedClickable(onClick = onOpen, onLongClick = onSave, onClickLabel = R.string.thread_attachment_open, onLongClickLabel = R.string.thread_attachment_save)` exactly when `state is Ready`, built once per item as `AttachmentTarget(attachmentId, name, mimeType)` — the same resolved name and MIME the row already shows. `Loading`, `NotFound` and `Failed` offer neither open nor save and add no click semantics. Since #1621 they consume taps with a no-op `pointerInput { detectTapGestures() }`, preventing taps from reaching the bubble’s meta-row toggle. The failed row keeps its existing Retry button, which handles its own tap. TalkBack reads the long-press as its own named action ("Save") rather than a hidden gesture, since the Figma frame draws no visible save control.

`MessageBubble` and `MessageAttachments` both gained `onOpenAttachment`/`onOpen` and `onSaveAttachment`/`onSave` parameters (`(AttachmentTarget) -> Unit`, default no-op) threaded straight through to this modifier — see [MessageBubble § Shape](message-bubble.md#shape). The mechanics of opening (the non-exported `FileProvider`, the `ACTION_VIEW` intent and its one read grant) and saving (the `ACTION_CREATE_DOCUMENT` picker and the byte-exact copy) are not this file's concern: they live in `ui/conversations/thread/AttachmentActions.kt`, built by `rememberAttachmentActions(attachmentStates, onOpenMarkdown) { notice -> ... }` in [Thread screen](thread-screen.md) and passed down as `onOpenAttachment = actions.open` / `onSaveAttachment = actions.save`. See [Attachment retrieval § Host store](attachment-retrieval.md#host-store--datacacheattachmentstorekt) for the provider itself, and `docs/specs/architecture/985-open-and-save-message-attachment.md` for the full design and its security review.

**A markdown file opens in-app instead (#1027).** `open` first checks `isMarkdownAttachmentName(target.displayName)`: a `Ready` row whose name ends in `.md`/`.markdown` (any case), from either `Kept` or `Original`, calls `onOpenMarkdown(attachmentId)` — the thread reads and strictly decodes the file, and only a readable, valid-UTF-8 result navigates to the [Markdown reader screen](markdown-reader-screen.md). No intent, no `FileProvider` URI, and no other app is involved for this branch; every other file type keeps the `openAttachment` view-intent path above unchanged. See [Markdown reader screen § Routing a tap to the reader](markdown-reader-screen.md#routing-a-tap-to-the-reader) for the full routing and load sequence, including why the reader needs its own byte bound (composition cost, not retrieval's memory bound) and why a double tap cannot buffer a second navigation.

`MessageAttachmentsTest` covers the click wiring at this layer: a `Ready` file row's tap sends `onOpen` and its long-press sends `onSave`, both carrying the row's own `AttachmentTarget`; a `Ready` image slot's tap sends `onOpen`; and `Loading`, `Failed` and `NotFound` items assert no click action at all (`assertHasNoClickAction`) and call neither callback even under a forced tap or long-press. The intent, the provider's one root and the save copy are `AttachmentActionsTest`'s concern (Robolectric, `app/src/test/`), not this file's.

#### Load lifecycle (since #984)

`MessageAttachmentItem` fires `LaunchedEffect(id) { onAttachmentShown(attachment) }` the moment it is composed — inside the thread's `LazyColumn`, that means only when the row is on screen (plus the list's own prefetch window). `ThreadViewModel.onAttachmentShown` (#1329: takes the attachment, not just its id) returns immediately unless the attachment [fetches on show](#fetch-on-open-since-1329); only then does it claim the id with a compare-and-set inside `_attachmentStates.update { }` (`claimAttachment { it == null }`) before starting a load, so two calls for the same id — a recomposition, or scrolling the row off and back on — start at most one. `onRetryAttachment` claims only from `Failed` (`NotFound` has no retry control to call it from). The load itself: `draftStore.sentOriginal(serverId, conversationId, id)` first — if it returns a URI and `attachmentReader.canRead(uri)` is still true, the state becomes `Ready(Original(uri), null, null)` and `retrieveAttachment` is never called; otherwise `repository.retrieveAttachment` runs and its result maps `Retrieved → Ready(Kept(file), ...)`, `NotFound → NotFound`, and `TooLarge`/`Invalid`/`Unavailable`/any non-cancellation throw → `Failed`. One `RelayLog.d` line per load: `event=thread_attachment_load id=<A> outcome=original|retrieved|not_found|failed` — never a name, URI, path or MIME type. See [Composer drafts and attachments § Sent originals](thread-screen-composer-drafts-and-attachments.md#composer-pending-attachments) and [Attachment retrieval](attachment-retrieval.md) for the two sources this resolves between, and [`AttachmentReader.canRead`](thread-screen-composer-drafts-and-attachments.md#composer-pending-attachments) for why a stalled or revoked grant still falls through to retrieval rather than hanging.

#### Fetch on open (since #1329)

A thread no longer retrieves every attachment it scrolls past. Only what the slot draws as a picture is fetched when its row is shown; everything else waits for a tap. The rule, `loadsOnShow` in `MessageAttachments.kt`, is decided from the reference alone, mirroring desktop's `isImageAttachmentName` (`src/renderer/src/screens/conversation/attachmentIsImage.ts`):

- A non-blank `mimeType` on the reference decides it: `image/…` fetches on show, anything else waits.
- With no type but a non-blank `displayName` — the shape of a daemon offer, `attachmentOfferRow` — the name's extension decides, against desktop's exact set (`png`, `jpg`, `jpeg`, `gif`, `webp`, `avif`, `bmp`), compared case-insensitively on the text after the last dot; a name with no dot is not an image. Do not add types here: the point is that both clients fetch the same files on sight.
- With neither type nor name, the reference fetches on show. This is the **history-row exception**: a row replayed from history carries no reference metadata, so the only way to learn what it is is to retrieve it. Desktop has no equivalent row, since it never draws attachments from history.

**A deferred file draws exactly like a ready one, before anything was requested.** An id with no entry in `attachmentStates` used to always mean `Loading`; now it means `Loading` only when `loadsOnShow` is true for that attachment, and otherwise the plain `File field` row with no status line — see View state above. Its `combinedClickable` calls `onRequest(attachment, AttachmentAction.OPEN)` on tap and `onRequest(attachment, AttachmentAction.SAVE)` on long-press, the same click/long-click labels the `Ready` row uses.

`ThreadViewModel.onAttachmentRequested(attachment, action)` claims the load exactly as `onAttachmentShown` does (`claimAttachment { it == null }`) — a tap on a row already loading, ready or failed claims nothing — and, only when the claim succeeds, records `attachment to action` against the id before starting the same `loadAttachment`. When that load settles, the pending entry is removed in the same continuation that writes the settled state: a `Ready` result sends one `AttachmentLoaded(target, source, action)` through a buffered channel (`ThreadViewModel.attachmentLoads`); `Failed` and `NotFound` just drop the entry, so neither opens nor saves, and a later Retry (which claims only from `Failed`) never records an action and so never opens anything by itself. This keeps the open/save decision inside the same claim-then-load the load lifecycle above already used for `onAttachmentShown` — a tap is just a second way to start that same load, with an action attached.

`ThreadScreen` collects `attachmentLoads` into `AttachmentActions.loaded` (`rememberAttachmentActions` in [Open and save](#open-and-save-since-985) above). **The effect carries the loaded `AttachmentSource` rather than looking it up in `attachmentStates`, because it can reach its collector before the recomposition that would have made that lookup succeed.** `rememberAttachmentActions` reads `rememberUpdatedState(states)`; an effect that said only "open id X" would find no `Ready` entry yet and silently do nothing. `loaded` therefore skips the `Ready` guard `open`/`save` use for a direct tap, and opens or launches the save picker straight from the event's own source. `ThreadScreenAttachmentLoadTest` pins this by delivering an `AttachmentLoaded` while `attachmentStates` is still empty and asserting it still opens (or saves). The save picker's own result still resolves its source from the live `states` when it arrives, since by then they are current.

A file this phone sent that is still readable is deferred the same way as any other non-image file — the rule reads the reference, not its origin — but its tap resolves through `sentOriginal`/`canRead` with no relay request, so it still opens on one tap.

`ThreadViewModelAttachmentRetrievalTest` and `AttachmentLoadsOnShowTest` cover the rule and the claim/settle/effect machinery; `MessageAttachmentsTest` and `ThreadScreenAttachmentLoadTest` cover the deferred row's drawing, its tap/long-press wiring, and the delivered-effect race. See `docs/specs/architecture/1329-fetch-non-image-attachment-on-open.md` for the full design and its security review.
