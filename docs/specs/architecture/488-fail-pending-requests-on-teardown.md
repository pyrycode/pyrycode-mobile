# #488 — Fail in-flight relay requests when the connection tears down

**Size:** XS · **Security-sensitive:** yes (self-review below) · **Design source:** N/A — no UI surface (pure data-layer teardown behaviour; the observable effect is an existing suspend call throwing instead of hanging).

A single-file behavioural fix in `RemoteConversationRepository`: when the connection tears down, complete every registered `pendingRequests` deferred exceptionally so an awaiting `sendAndAwaitReply` caller (a tapped permission answer, a sent message, a promote, …) throws **promptly** instead of suspending forever. The regression test is the bulk of the diff.

## Context

Every request/reply call routes through `sendAndAwaitReply` (:652): it registers a `CompletableDeferred` in `pendingRequests`, calls `pump.send`, and suspends on `deferred.await()`. The deferred is completed **only** by a correlated inbound reply (`ack`/`error`) demuxed through the single `init` collector (:264). On teardown the coordinator cancels that collector's scope (`teardownActive()` → `current.scope.cancel()`, coordinator :269) — but nothing completes the still-registered deferreds. So `send_message`, `answer_modal`, `cancel_modal`, `promote`, `create_conversation`, `request_snapshot`, `register_push_token`, `dequeue_message` — every `sendAndAwaitReply` caller — hangs forever on the caller's (ViewModel) scope.

For the permission flow this is a **silent answer-drop**: the user taps Allow, the coroutine hangs, nothing surfaces. It blocks flipping `USE_RELAY_REPOSITORY` on, because `FakeConversationRepository` never tears a connection down — the hang only manifests against the real relay.

Note `interrupt` (:1303) is **not** affected: it is fire-and-forget over plain `pump.send`, registers no deferred.

## Design

**One production edit + one small private helper**, both in `RemoteConversationRepository.kt`.

### 1. Wrap the inbound collector in `try/finally`

The `init` collector body (:263-265) gains a `finally` that runs the teardown sweep:

```kotlin
init {
    scope.launch {
        try {
            pump.inbound.collect { envelope -> onInbound(envelope) }
        } finally {
            failAllPending()
        }
    }
}
```

The `finally` covers **all three** collector-termination modes, satisfying AC #1's "scope is cancelled **or** `pump.inbound` completes":

| Termination | `collect` behaviour | `finally` runs? |
| --- | --- | --- |
| `scope.cancel()` (primary — `teardownActive`) | throws `CancellationException` | yes |
| `pump.inbound` completes (pump closes its stream) | returns normally | yes |
| `pump.inbound` throws | propagates | yes |

The `finally` runs **exactly once** per collector lifetime (the collector is launched once). It does **not** catch/swallow the `CancellationException` — `failAllPending` is non-suspending, returns, and cancellation continues to propagate, so the coroutine still completes as cancelled (correct structured-concurrency posture; no `catch(CancellationException)` anti-pattern).

### 2. `failAllPending()` — the teardown hook

Contract (signature + behaviour; developer writes the body in the codebase idiom):

```kotlin
/** Complete every still-registered pending request exceptionally and clear the map … */
private fun failAllPending()
```

Behaviour:
- Complete **every** currently-registered deferred in `pendingRequests` with a single **plain `IllegalStateException`** carrying a static, payload-free message, then remove/clear the entries (AC #1: "completed exceptionally and the map is cleared").
- **Non-suspending** — `CompletableDeferred.completeExceptionally` returns `Boolean`, does not suspend. This is why it survives a `finally` running inside a *cancelling* coroutine (a suspending call there would throw `CancellationException` immediately; a non-suspending one runs to completion). The ticket's Technical Notes call this out explicitly.
- Idempotent w.r.t. caller-side removal: `completeExceptionally` on an already-completed/removed deferred is a no-op, so the caller's own `finally { remove }` racing this sweep is harmless. `ConcurrentHashMap` makes the concurrent iterate/clear vs. caller register/remove safe.

**Exception type — `IllegalStateException`, deliberately not `CancellationException`.** Two reasons, both load-bearing:
1. **Uniform failure mode.** `sendAndAwaitReply`'s not-connected path already throws `IllegalStateException` via `check(...)` (:656). Reusing it means every awaiting caller (and its ViewModel) handles teardown-mid-await through the exact same catch it already has for "session not connected" — no new failure mode is introduced (the ticket's stated goal).
2. **Cancellation-safety.** `java.util.concurrent.CancellationException extends IllegalStateException` (memory: *catch(IllegalStateException) swallows CancellationException*). We rely on the subtype relationship in *one* direction only: a plain `IllegalStateException` is **not** a `CancellationException`, so completing the deferred with it makes `await()` throw a real, surfaceable error — not something a caller's `catch(CancellationException) { throw e }` guard would re-raise as its own cancellation. Completing with a `CancellationException` would be the bug: `await()` would throw cancellation, the caller might treat it as its own scope dying, and the "surface an error" intent would be lost. So the message-free `IllegalStateException` is the exact right type.

Optionally add a `private const val` for the message (e.g. in the existing companion, mirroring the `ERROR_*` constants) — the string must be static and carry no payload/`modalId`/request content (never-log contract).

### Why nothing else changes

- `onInbound` is fully **non-suspending** (synchronous map folds + `tryEmit`). Cancellation is delivered only at `collect`'s internal suspension (awaiting the next element), so a fold is never interrupted mid-flight — no partial-state hazard, and `failAllPending` never races a half-applied `onInbound`.
- `failAllPending` runs **sequentially after** `collect` ends, in the same collector coroutine — never concurrently with the `TYPE_ACK`/`TYPE_ERROR` completion arms.
- `RelayRepositoryCoordinator.teardownActive()` is already correct on its side (`scope.cancel()` triggers the collector's `finally`); no coordinator edit, no second file.

## State + concurrency model

- **Trigger:** `scope.cancel()` from the coordinator's `teardownActive` (the connection-scoped child scope passed into the repo's constructor). The collector coroutine receives `CancellationException` at its `collect` suspension → `finally`.
- **Dispatcher:** whatever `scope` the coordinator supplies (`Dispatchers.Default` in production). No dispatcher switch introduced.
- **Concurrency surface:** `pendingRequests` (`ConcurrentHashMap`) is written by caller coroutines (register/remove) and read+cleared by the single collector's `finally`. Weakly-consistent iteration + idempotent completion make the sweep safe against concurrent caller removal.
- **Cancellation propagation:** the `finally` performs only the non-suspending sweep and lets `CancellationException` propagate — the coroutine completes as cancelled. No `NonCancellable`, no `withContext`.

## Error handling

- The awaiting caller (`sendAndAwaitReply` → `deferred.await()`) resumes with the injected `IllegalStateException` and rethrows it (its `finally { pendingRequests.remove }` runs harmlessly — entry already cleared). This lands identically to the pre-existing not-connected `check(...)` failure, so downstream callers (`sendMessage`, `answerModal`, etc. — all documented to throw `IllegalStateException` "when the session is not connected") need **no** change.
- Post-teardown callers that start a *new* `sendAndAwaitReply` fail fast at `check(pump.send(...))`: once `pump.close()` has run, `send` returns `false` → `IllegalStateException` without ever awaiting. So the only window in which a caller reaches `await()` is while the pump is still `Open`, and the sweep unblocks any such caller.

## Testing strategy

Unit only (`./gradlew testDebugUnitTest --tests "…RemoteConversationRepositoryTest"`), new tests in `RemoteConversationRepositoryTest.kt`, `runTest` + `runCurrent()` idiom. No instrumented test. No production-code timeout (see § Open questions).

**Test 1 — teardown-mid-await via scope cancellation (required; AC #2 + #3, the primary trigger).** Scenarios, not code:
- Build `FakeSessionPump` (default `sendResult = true` ⇒ `Open`) and a **cancellable repo scope on the test scheduler, separate from `backgroundScope`** — e.g. `CoroutineScope(coroutineContext + Job())` (inherits the `TestDispatcher`, fresh root `Job` so cancelling it does not tear the test down). Construct `RemoteConversationRepository(pump, repoScope)`.
- `startSend(repo, "conv", "hi")` (launches the caller on `backgroundScope`), then `runCurrent()` — the caller registers its deferred, `pump.send` records + returns `true`, the caller suspends on `await()`. Optionally assert the getter still reports not-completed (proves it was hanging).
- `repoScope.cancel()` (simulates `teardownActive()`'s `current.scope.cancel()`), then `runCurrent()` to drain the `finally → failAllPending → await throws → runCatching` cascade.
- Assert: the result **is a failure**, the exception **is an `IllegalStateException`**, and it **is not a `CancellationException`** (pins the type choice — the memory-lesson invariant).

**Test 2 — teardown via inbound completion (recommended; AC #1's "or `pump.inbound` completes" branch).**
- Add `fun close() { inboundChannel.close() }` to `FakeSessionPump`.
- Same setup but the repo may use `backgroundScope` directly (no separate scope needed). Start a pending `send`, `runCurrent()`.
- `pump.close()` ⇒ `receiveAsFlow()` completes ⇒ `collect` returns ⇒ `finally`. `runCurrent()`.
- Assert the awaiting call failed with `IllegalStateException`.

Both tests assert the same observable — the awaiting call throws promptly with `IllegalStateException`. "The map is cleared" (AC #1) is an internal invariant of `failAllPending`; it is **not** asserted directly (that would require exposing private state) — it is covered by code review plus the completed-and-removed deferred the throw tests exercise. Do not add a `@VisibleForTesting` accessor for it.

(`sendMessage` is used as the representative caller because it needs no modal fixtures; `answerModal`/`cancelModal`/`promote` share the identical `sendAndAwaitReply` primitive, so one caller exercises the fix for all.)

## Open questions

- **Timeout-on-`await` belt — deferred, per the ticket and Evidence-Based Fix Selection.** The `finally`-block completion is deterministic and fully satisfies the AC. A narrow theoretical race remains: between the collector's `finally` running the sweep and the coordinator's subsequent `pump.close()`, a caller could register a *new* deferred (after the sweep iterated) while `pump.send` still returns `true` (pump not yet closed) → that deferred is never completed → hang. This is (a) the exact "second mechanism for the same failure mode" the ticket scopes out, (b) sub-millisecond and multi-coroutine, and (c) **not observed**. Do **not** add a timeout now. If a real hang is later observed to survive this fix, the follow-up is the ticket's documented `withTimeout` on `await` — a separate slice.

## Security review

**Verdict:** PASS

**Findings:**

- **[Trust boundaries]** No new external trust boundary and no new untrusted-input parse. The change is purely local teardown behaviour: it reads no envelope payload and decodes nothing. The teardown trigger (`scope.cancel()` / inbound completion) originates from the local coordinator, never from an inbound frame — a malicious relay cannot *induce* a spurious sweep beyond closing the socket, and closing the socket *already* ends the connection, for which failing the pending requests is the correct fail-fast response (strictly better than the current hang). No attack surface added.
- **[Tokens, secrets, credentials]** None minted, stored, transmitted, or read. The swept deferreds carry `JsonElement` reply payloads that are **discarded** (completed exceptionally, never inspected). The injected `IllegalStateException` carries only a static, code-authored string.
- **[Error messages, logs, telemetry]** `failAllPending` emits **no log** and the exception message is a static literal — no `modalId`, no `optionId`, no message text, no conversation/session id, no request payload. This holds the never-log contract the ticket calls out (`RelayRepositoryCoordinator` :290-291) and matches every existing `onInbound` arm's silent-drop posture. Reusing the pre-existing not-connected `IllegalStateException` shape adds no new log site.
- **[Concurrency]** One added non-suspending sweep in the collector's `finally`, sequential after `collect` ends — never concurrent with the `TYPE_ACK`/`TYPE_ERROR` completion arms (same coroutine) and never mid-`onInbound` (folds are non-suspending, cancellation lands only at the `collect` suspension). Caller-side register/remove vs. the sweep is `ConcurrentHashMap`-safe and idempotent. No new lock, no new coroutine, no dispatcher change. The `finally` does not swallow `CancellationException` (structured-concurrency-correct).
- **[Availability / resource]** Positive: clearing `pendingRequests` on teardown releases stale `CompletableDeferred` references that previously leaked per connection across reconnect churn, and unblocks caller coroutines that previously suspended forever. No unbounded growth introduced.
- **[Cryptographic primitives / subprocess / file operations]** Not applicable — none touched.
- **[Threat model alignment]** The fix converts a silent indefinite hang (a real availability/UX defect the ticket frames as a "silent answer-drop") into a prompt, uniform, non-logging failure. It lowers no authentication or authorization bar and changes no wire byte.
