## Design

In `runConfigFlow`, carry settings into the context combine only when their nonempty session identity matches this conversation's current session. Keep all other settings facets on their existing path. A context reply remains preferred and may render while replacement settings are pending. Do not clear `contextPercent` in `forLiveSession`: that would also hide a fresh context reply merely because settings are old. Keep percentage arithmetic and request edges unchanged. Repository invalidation already exists; test it through actual inbound frames instead of adding another invalidation owner.

`ContextUsageProjection` retains each conversation's latest decoded transition across reconnects. After replacement, `apply` requires source ownership as well as source time: an existing envelope producer tag must match the replacement session, and an untagged reading needs correlation to this connection's latest context request registered after invalidation. Timestamp-free unsolicited legacy pushes cannot establish ownership. A remembered reading must additionally have `asOf` at or after the boundary. Current tagged pushes and eligible correlated replies render before settings. The bounded request ledger holds one request per conversation, includes a connection identity to prevent request-id reuse across reconnects, and is invalidated before the reset-ended edge can issue its new request. Synchronize request registration and inbound admission on the projection; no coroutine suspends while holding that monitor. `onSessionTransition` retains the newest boundary monotonically. A separate `clear` handles authoritative family invalidation. No wire or daemon changes are needed; supplied live state retains its existing `SessionLiveAdmission` gate.

Shared-file overlaps: #1682, #1689, #1690, #1691, #1693, #1695, #1766, #1869, #1879, #1896, #2009, #2032, #2057, #2088, #2089, #2090, #2091, #2092, #2098, #2099, #2100, #2102, #2104, #2112, #2114, #2117, #2118 and #2119 touch the live class. Other methods or adjacent assertions can merge normally; #1869's retired observer edit is separate from our appended Context window assertion. No ViewModel overlap. Keep edits local.

Legacy post-turn pushes remain useful after replacement: an untagged, uncorrelated fresh push is a refresh signal, not proof of session ownership. Refresh signals are enabled by a post-boundary non-idle turn state; a delayed predecessor push alone must not add an ask during reset completion. A new turn also enables refresh after an idle eviction with no reset edge. When enabled and no context request is pending, `apply` returns its conversation for `routeInbound` to request a correlated current reading outside the projection monitor. A pending reset or refresh request coalesces further signals. Correlated errors retire only that connection's matching request; a rejected remembered reply also retires its matching request, allowing the next post-turn signal to refresh. Neither errors nor rejected pushes replace the held value. Current producer-tagged and supplied-state pushes continue to apply directly. This preserves ongoing updates without inventing provenance for the unchanged legacy bytes. There are no timed retries or new collectors.

Sizing: one session-freshness deliverable, four acceptance criteria, approximately 500 written lines including tests/plan, zero new exported types or simultaneous consumer updates, one fallback rejection branch. All limits hold.

## State and concurrency model

No new production jobs, flows or dispatchers. The pairing-scoped projection retains the latest transition and one pending request per conversation across reconnects with `HostReadings`. Its monitor joins outbound request registration with the existing serialized inbound collector; connection termination removes that connection's requests. Existing `viewModelScope` collects settings and conversation readings; the repository's single inbound collector publishes transition invalidation. Existing cancellation and background socket closure remain. Settings used for fallback are filtered in the same combined input that contains conversation identity, without resubscribing to the settings flow and its side effects.

The projection also holds a per-conversation refresh-enabled bit, cleared with each invalidation and armed by a subsequent non-idle turn. It retains no turn content or turn identifiers. This preserves the reset-ended ask count when a delayed old push crosses the reset-ended collector, without suppressing later legitimate legacy updates.

## Security review

**Verdict:** PASS

- [Trust boundaries] Keep `routeInbound` and existing typed decoders as the boundary. Settings must match the current session. MUST FIX from the verifier: both delayed remembered replies and timestamp-free old post-turn pushes can cross replacement. After transition, admit only current tagged producers or an untagged reply correlated to a post-invalidation request on this connection; an explicit conflicting producer always loses. Also reject remembered context predating the latest boundary. Test production inbound, rather than treating arrival time or missing `asOf` as session proof. The revised design passes.
- [Tokens, secrets and credentials] Token counts are numerical usage readings, not credentials. No credential generation, storage or access changes.
- [Files and storage] No new disk I/O, paths, persistence or backup configuration; filtering is in memory.
- [Android attack surface] No manifest, exported components, intents, providers or WebView changes. Existing plain Compose text renders only client-owned reading copy.
- [Cryptography] No Noise, key, nonce or authentication changes; conversation reset does not reset transport cryptographic state.
- [Network and I/O] Reuse bounded decoded inputs and existing guarded context requests; no new retry timer, timeout, URL, frame type or capability. After replacement, a legacy fresh push triggers a current correlated read only when none is pending. The unchanged daemon resolver validates successor ownership; the client never promotes an untagged push based on arrival order. Error replies and rejected remembered answers release their own request so a later turn can refresh after an unavailable reset reply. An unsolicited or mismatched error cannot release another connection's request.
- [Errors, logs and telemetry] Keep static reset-end/reconnect request logs. Never log readings, payloads, conversation/session identifiers, message text, credentials or decrypted bytes; no new telemetry.
- [Concurrency] No extra production collector or suspended read/write. Filter settings against identity in one existing combined input. Synchronize the per-conversation boundary and bounded request ledger because outbound registration and inbound admission can use different dispatchers. Invalidate before publishing reset completion. Retain the greatest transition timestamp and use connection identity alongside request ids. Test delayed replies before/after settings and fresh context, repeated transitions, reconnect and cross-conversation isolation.
- [Threat model] Malicious relay delay/drop yields existing unavailable/error behavior without plaintext leakage. Hostile frames stay behind existing decoder/admission rules; this filter cannot authenticate a dishonest daemon. Rooted-device token theft and accessibility/screenshots remain existing platform/Keystore concerns, unchanged by numerical-source selection. No security posture is weakened.
