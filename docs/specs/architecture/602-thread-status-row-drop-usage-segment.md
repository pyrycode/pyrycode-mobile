# 602 — ThreadStatusRow: drop the fabricated context-usage segment

Issue: [pyrycode/pyrycode-mobile#602](https://github.com/pyrycode/pyrycode-mobile/issues/602). Size: **S**.

Middle child of the #584 split chain **#601 → #602 → #603**. #601 landed as `17432ae`; #603 (delete the ViewModel stub state) is blocked by this ticket. Sibling #591 serves the real figure — blocked on pyrycode PR #1215.

## Context

`ThreadStatusRow` is the compact monospace line pinned above the input bar. It renders `Opus 4.7 · high · 73% used` and colour-codes the last segment by severity via a private `tokenPercentColor` helper (`onSurfaceVariant` < 50%, `warning` < 95%, `error` above). The percentage is `ThreadViewModel.STUB_TOKEN_PERCENT = 73` plumbed through `ThreadUiState.tokenPercent` — so the row editorialises about a number nobody measured, at a severity that is constant by construction.

#601 replaced the same stub in the Status *sheet* with the honest "Context usage unavailable". This ticket does **not** mirror that wording into the row. It deletes the segment. Rationale (endorsed, not merely inherited from the ticket body): a compact monospace summary has no room for an explanation, "context n/a" is a second thing to explain rather than a fix, and the sheet — one tap away, already honest as of `17432ae` — is where the explanation belongs. Deleting the segment is also what makes the "no severity-derived colour" criterion fall out for free instead of needing a separate rule.

**The structural fact that makes this shippable alone:** `ThreadUiState` keeps `tokenPercent` and `ThreadViewModel` keeps populating it. The row simply stops *reading* it. Nothing upstream changes, so nothing upstream needs re-testing. #603 deletes the field; #591 re-wires a real one.

Client-only: no wire call, no DTO, no repository method, no `ThreadViewModel` edit.

### `ThreadStatusRow.kt`

**Edit order matters.** Every deletion shifts the line numbers below it. Work **bottom-up** — previews first, then the helper, then the body, then the signature, then the imports — or anchor each edit on a symbol name rather than a line number.

#### Signature

Delete `tokenPercent: Int,` (`:40`). The parameter list becomes `model`, `effort`, `onExpandClick`, `modifier = Modifier` — the existing relative order is preserved, so this does not disturb the `ComposeParameterOrder` lint rule (no parameter is added, and `modifier` stays last).

#### Body

Two edits inside `buildAnnotatedString` and one above it:

- Delete `val percentColor = tokenPercentColor(tokenPercent)` (`:46`).
- Change the separator span (`:50`) from `" · $effort · "` to **`" · $effort"`** — drop the trailing ` · ` only; the leading ` · ` between model and effort stays.
- Delete the usage span (`:51`) entirely.

The `model` span (`:49`, `onSurface`) and the separator/effort span (`:50`, `onSurfaceVariant`) both survive with their colours. The rendered text becomes exactly:

```
Opus 4.7 · high
```

**On the AC's "no severity-derived colour anywhere in the row":** the surviving two-tone `onSurface` / `onSurfaceVariant` split is *not* severity-derived — it is the static treatment Figma `16:58` specifies and #145 implemented. Do **not** flatten both spans to a single colour; that would be an unrequested visual change to a part of the row the ticket says stays as designed. Severity lived only on the deleted span.

The `Row`, its `clickable` / `semantics { role = Role.Button }` / `padding` / `alpha`, the `Text` styling, the 4.dp `Spacer` and the trailing `Icon` with `cd_thread_status_expand` are all untouched.

- **`tokenPercentColor` (`:80-88`)** — delete the `@Composable` annotation line at `:80` along with the function. The ticket body's `:81-88` omits the annotation; leaving it orphaned is a compile error.   | `ThreadStatusRowLight20Preview` | `ThreadStatusRowLightPreview` | `"StatusRow — Light"` |
  | `ThreadStatusRowDark20Preview` | `ThreadStatusRowDarkPreview` | `"StatusRow — Dark"` |

Nothing else in this file changes. In particular the five `tokenPercent = 73,` lines at `:672`, `:695`, `:731`, `:858`, `:881` are arguments to `ThreadUiState(...)`, not to `ThreadStatusRow(...)` — they stay valid because `ThreadUiState` keeps the field, and they belong to #603.

## State + concurrency model

Nothing changes. No flow added or removed, no `viewModelScope` job, no dispatcher choice, no `StateFlow` shape change. `ThreadViewModel.state` emits an identical `ThreadUiState` before and after.

Recomposition is strictly reduced: `ThreadStatusRow` previously recomposed on any `tokenPercent` change and now does not read the field at all. Since the value is a constant today the practical delta is zero, but the direction is correct. No new lambda captures, no unstable parameter types, no `remember` needed.

`ThreadUiState` is left with one now-unread field. That is deliberate and is exactly what lets this slice compile and ship standalone — Kotlin does not warn on an unread `data class` property, so this produces no lint noise. #603 removes it.

## Error handling

No new failure modes; one existing one disappears. `tokenPercentColor`'s `coerceIn(0, 100)` clamp existed only to keep an out-of-range stub from indexing off the severity ladder, and it goes with its only call site. The row now renders two spans built purely from `String` parameters and cannot fail.

Nothing surfaces to the user as a banner or dialog. The honest-failure surface for context usage is the Status sheet (#601), one tap away via the unchanged expand affordance.

## Testing strategy

**Unit (`./gradlew test`): unaffected.** `ThreadViewModelTest.kt:1693` and `:1708` still assert `tokenPercent` is `0` then `73`; the ViewModel is untouched, so they still pass. **Do not delete them** — they are #603's to remove.

**Instrumented (`./gradlew connectedAndroidTest`): one new file.**

`app/src/androidTest/java/de/pyryco/mobile/ui/conversations/thread/ThreadStatusRowTest.kt`, package `de.pyryco.mobile.ui.conversations.thread`.

**Test the composable directly**, not through `ThreadScreen`. `ThreadStatusRow` is public in the same package, so `setContent { PyrycodeMobileTheme { ThreadStatusRow(...) } }` isolates the surface, keeps assertions unambiguous, and avoids the scaffold noise (and the known-red sibling test) that a screen-level harness would drag in. Clone the structural shape of `StallPromotionBannerTest.kt` — rule, theme wrapper, `string(resId)` helper — not its `ThreadScreen(...)` setup.

**Semantics note before you write matchers:** `Modifier.clickable` merges its descendants' semantics, so the whole row surfaces as one merged node carrying both the text and the icon's content description. `onNodeWithText(...)` and `onNodeWithContentDescription(...)` therefore resolve to that same node, and `performClick()` on either reaches `onExpandClick`. If a matcher unexpectedly finds zero or multiple nodes, reach for `useUnmergedTree = true` — but do **not** weaken the exact-match text assertion to get a match.

Scenarios:

- **`renders_model_and_effort_only`** — render with `model = "Opus 4.7"`, `effort = "high"`. Assert `onNodeWithText("Opus 4.7 · high")` is displayed. **This is the load-bearing assertion.** `onNodeWithText` defaults to `substring = false`, so an exact match is what catches a dangling trailing separator: `"Opus 4.7 · high · "` is not equal to `"Opus 4.7 · high"`. Do not pass `substring = true` here — that would silently accept the bug the AC calls out.
- **`no_usage_segment_is_rendered`** — same setup. Assert `onNodeWithText("% used", substring = true).assertDoesNotExist()` and `onNodeWithText("%", substring = true).assertDoesNotExist()`. The second is the stronger statement and guards against a future partial reintroduction.
- **`separator_is_built_from_the_parameters`** — render with a different pair (e.g. `model = "Sonnet 4.6"`, `effort = "medium"`) and assert `onNodeWithText("Sonnet 4.6 · medium")` is displayed. Confirms the surviving string is composed from the params rather than hardcoded around the deletion.
- **`expand_affordance_is_unchanged`** — assert the node matched by `stringResource`-equivalent `R.string.cd_thread_status_expand` is displayed, then `performClick()` it and assert an `onExpandClick` counter incremented to 1. The ticket's Technical Notes name this behaviour as untouched; this is the regression guard for that claim.

Four tests, no fixtures, no fakes, no MockK. `onNodeWithText` / `onNodeWithContentDescription` / `performClick` / `assertIsDisplayed` need imports; `assertDoesNotExist` is a member and needs none. Keep the import block alphabetically ordered — a misplaced import passes `lint` but fails `spotlessCheck`.

**No live rung.** There is no daemon interaction to exercise.

## Open questions

- **Figma has no two-segment variant.** Confirmed by reading node `16:58` (see § Design source). Worth adding one so #591 and any future redesign have an anchor — flagged for Juhana, not blocking.
- **`ThreadUiState` keeps one unread field** between this ticket and #603. Intentional: it is what makes this slice compile and ship standalone. Do **not** pre-emptively delete it here; that pulls `ThreadViewModel`, `ThreadViewModelTest` and five `ThreadScreen.kt` preview literals into scope and breaks the sibling boundary. This ticket's single deleted line at `:191` shifts #603's line references below it by one — #603's own PO pass re-verifies them.
- **This spec deliberately does not mirror #601's "Context usage unavailable" into the row.** If a future reviewer asks why the two surfaces disagree: the sheet explains, the row summarises, and a compact monospace line has no room for the explanation that makes an "unavailable" token meaningful. Reopen the question only if #591 slips indefinitely and users report confusion at the row.
